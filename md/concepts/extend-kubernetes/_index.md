کوبرنتیز بسیار پیکربندی‌پذیر و توسعه‌پذیر است. در نتیجه، به‌ندرت نیازی به فورک کردن کد پروژه کوبرنتیز یا ارسال وصله (patch) به آن وجود دارد.

این راهنما گزینه‌های سفارشی‌سازی یک کلاستر کوبرنتیز را شرح می‌دهد. مخاطب آن
{{< glossary_tooltip text="اپراتورهای کلاستر" term_id="cluster-operator" >}} هستند که می‌خواهند بدانند چگونه کلاستر کوبرنتیز خود را با نیازهای محیط کاری‌شان تطبیق دهند. توسعه‌دهندگانی که قصد دارند
{{< glossary_tooltip text="توسعه‌دهنده پلتفرم" term_id="platform-developer" >}} شوند یا
{{< glossary_tooltip text="مشارکت‌کنندگان" term_id="contributor" >}} پروژه کوبرنتیز نیز این راهنما را به‌عنوان مقدمه‌ای بر نقاط توسعه و الگوهای موجود، به همراه مزایا و محدودیت‌های آن‌ها مفید خواهند یافت.

رویکردهای سفارشی‌سازی را می‌توان به‌طور کلی به دو دسته تقسیم کرد: [پیکربندی](#configuration) که فقط شامل تغییر آرگومان‌های خط فرمان، فایل‌های پیکربندی محلی یا منابع API است؛ و [افزونه‌ها](#extensions) که شامل اجرای برنامه‌های اضافی، سرویس‌های شبکه‌ای اضافی یا هر دو است.
تمرکز اصلی این سند بر _افزونه‌ها_ است.

<!-- body -->

## پیکربندی {#configuration}

*فایل‌های پیکربندی* و *آرگومان‌های خط فرمان* در بخش [مرجع](/docs/reference/) مستندات آنلاین و با یک صفحه برای هر فایل اجرایی توضیح داده شده‌اند:

* [`kube-apiserver`](/docs/reference/command-line-tools-reference/kube-apiserver/)
* [`kube-controller-manager`](/docs/reference/command-line-tools-reference/kube-controller-manager/)
* [`kube-scheduler`](/docs/reference/command-line-tools-reference/kube-scheduler/)
* [`kubelet`](/docs/reference/command-line-tools-reference/kubelet/)
* [`kube-proxy`](/docs/reference/command-line-tools-reference/kube-proxy/)

ممکن است آرگومان‌های خط فرمان و فایل‌های پیکربندی همیشه در یک سرویس کوبرنتیز میزبانی‌شده یا در یک توزیع با نصب مدیریت‌شده قابل تغییر نباشند. در صورتی که قابل تغییر باشند، معمولاً فقط اپراتور کلاستر می‌تواند آن‌ها را تغییر دهد. علاوه بر این، آن‌ها ممکن است در نسخه‌های آتی کوبرنتیز تغییر کنند و تنظیم‌شان ممکن است نیازمند راه‌اندازی مجدد پردازه‌ها باشد. به همین دلایل، باید فقط زمانی از آن‌ها استفاده کرد که گزینه دیگری وجود ندارد.

*APIهای سیاست‌گذاری* داخلی، مانند [ResourceQuota](/docs/concepts/policy/resource-quotas/)،
[NetworkPolicy](/docs/concepts/services-networking/network-policies/) و کنترل دسترسی مبتنی بر نقش
([RBAC](/docs/reference/access-authn-authz/rbac/))، APIهای داخلی کوبرنتیز هستند که تنظیمات سیاست‌گذاری را به‌صورت اعلانی (declarative) فراهم می‌کنند.
این APIها معمولاً حتی با سرویس‌های کوبرنتیز میزبانی‌شده و نصب‌های مدیریت‌شده کوبرنتیز نیز قابل استفاده‌اند.
APIهای سیاست‌گذاری داخلی از همان قراردادهای سایر منابع کوبرنتیز، مانند Pod، پیروی می‌کنند.
وقتی از یک API سیاست‌گذاری [پایدار](/docs/reference/using-api/#api-versioning) استفاده می‌کنید، مانند سایر APIهای کوبرنتیز از یک [سیاست پشتیبانی تعریف‌شده](/docs/reference/using-api/deprecation-policy/) بهره‌مند می‌شوید.
به این دلایل، در موارد مناسب، APIهای سیاست‌گذاری بر *فایل‌های پیکربندی* و *آرگومان‌های خط فرمان* ترجیح داده می‌شوند.

## افزونه‌ها {#extensions}

افزونه‌ها اجزای نرم‌افزاری‌ای هستند که کوبرنتیز را گسترش می‌دهند و به‌طور عمیق با آن یکپارچه می‌شوند.
آن‌ها کوبرنتیز را برای پشتیبانی از انواع جدید و انواع تازه‌ای از سخت‌افزار تطبیق می‌دهند.

بسیاری از مدیران کلاستر از یک نمونه کوبرنتیز میزبانی‌شده یا توزیعی استفاده می‌کنند.
این کلاسترها با افزونه‌های از پیش نصب‌شده عرضه می‌شوند. در نتیجه، بیشتر کاربران کوبرنتیز نیازی به نصب افزونه نخواهند داشت و شمار کاربرانی که نیاز به نوشتن افزونه‌های جدید دارند حتی کمتر است.

### الگوهای افزونه {#extension-patterns}

کوبرنتیز طوری طراحی شده است که با نوشتن برنامه‌های کلاینت خودکارسازی شود. هر برنامه‌ای که از API کوبرنتیز بخواند و/یا در آن بنویسد می‌تواند خودکارسازی مفیدی فراهم کند. *خودکارسازی* می‌تواند روی کلاستر یا خارج از آن اجرا شود. با پیروی از راهنمایی‌های این سند می‌توانید خودکارسازی‌های بسیار در دسترس و مقاوم بنویسید.
خودکارسازی معمولاً با هر کلاستر کوبرنتیز، از جمله کلاسترهای میزبانی‌شده و نصب‌های مدیریت‌شده، کار می‌کند.

الگوی مشخصی برای نوشتن برنامه‌های کلاینت وجود دارد که به‌خوبی با کوبرنتیز کار می‌کند و الگوی
{{< glossary_tooltip term_id="controller" text="کنترل‌کننده" >}}
نامیده می‌شود. کنترل‌کننده‌ها معمولاً `.spec` یک آبجکت را می‌خوانند، احتمالاً اقداماتی انجام می‌دهند و سپس `.status` آبجکت را به‌روزرسانی می‌کنند.

یک کنترل‌کننده کلاینتی برای API کوبرنتیز است. وقتی کوبرنتیز خودش کلاینت باشد و یک سرویس راه دور را فراخوانی کند، کوبرنتیز این را *webhook* می‌نامد. سرویس راه دور *webhook backend* نامیده می‌شود. همانند کنترل‌کننده‌های سفارشی، webhookها نیز یک نقطه شکست (point of failure) اضافه می‌کنند.

{{< note >}}
خارج از کوبرنتیز، اصطلاح «webhook» معمولاً به سازوکاری برای اعلان‌های ناهمگام اشاره دارد، که در آن فراخوانی webhook نقش یک اعلان یک‌طرفه به سیستم یا مؤلفه‌ای دیگر را دارد. در اکوسیستم کوبرنتیز، حتی فراخوانی‌های HTTP همگام نیز اغلب «webhook» نامیده می‌شوند.
{{< /note >}}

در مدل webhook، کوبرنتیز یک درخواست شبکه‌ای به یک سرویس راه دور ارسال می‌کند.
در مدل جایگزین *Plugin باینری*، کوبرنتیز یک فایل باینری (برنامه) را اجرا می‌کند.
پلاگین‌های باینری توسط kubelet (برای مثال [پلاگین‌های ذخیره‌سازی CSI](https://kubernetes-csi.github.io/docs/)
و [پلاگین‌های شبکه CNI](/docs/concepts/extend-kubernetes/compute-storage-net/network-plugins/))
و توسط kubectl (به [گسترش kubectl با پلاگین‌ها](/docs/tasks/extend-kubectl/kubectl-plugins/) مراجعه کنید) استفاده می‌شوند.

#### راهنمای شکل

1. کاربران اغلب با استفاده از `kubectl` با API کوبرنتیز تعامل می‌کنند. [پلاگین‌ها](#client-extensions)
   رفتار کلاینت‌ها را سفارشی می‌کنند. افزونه‌های عمومی‌ای وجود دارند که می‌توانند برای کلاینت‌های مختلف به‌کار روند، و همچنین روش‌های خاصی برای گسترش `kubectl` وجود دارد.

1. سرور API همه درخواست‌ها را مدیریت می‌کند. چند نوع نقطه توسعه در سرور API امکان احراز هویت درخواست‌ها، یا مسدود کردن آن‌ها بر اساس محتوایشان، ویرایش محتوا و مدیریت حذف را فراهم می‌کنند. این موارد در بخش [افزونه‌های دسترسی به API](#api-access-extensions) شرح داده شده‌اند.

1. سرور API انواع مختلفی از *منابع* را ارائه می‌دهد. *انواع منابع داخلی*، مانند
   `pods`، توسط پروژه کوبرنتیز تعریف می‌شوند و قابل تغییر نیستند.
   برای آشنایی با گسترش API کوبرنتیز، [افزونه‌های API](#api-extensions) را بخوانید.

1. زمان‌بند کوبرنتیز [تصمیم می‌گیرد](/docs/concepts/scheduling-eviction/assign-pod-node/)
   پادها روی کدام نودها قرار گیرند. راه‌های متعددی برای گسترش زمان‌بندی وجود دارد که در بخش [افزونه‌های زمان‌بندی](#scheduling-extensions) شرح داده شده‌اند.

1. بخش زیادی از رفتار کوبرنتیز توسط برنامه‌هایی به نام
   {{< glossary_tooltip term_id="controller" text="کنترل‌کننده‌ها" >}} پیاده‌سازی می‌شود که
   کلاینت سرور API هستند. کنترل‌کننده‌ها اغلب همراه با منابع سفارشی به‌کار می‌روند.
   برای اطلاعات بیشتر، [ترکیب APIهای جدید با خودکارسازی](#combining-new-apis-with-automation) و
   [تغییر منابع داخلی](#changing-built-in-resources) را بخوانید.

1. kubelet روی سرورها (نودها) اجرا می‌شود و کمک می‌کند پادها مانند سرورهای مجازی با IPهای مخصوص خود در شبکه کلاستر ظاهر شوند. [پلاگین‌های شبکه](#network-plugins) امکان پیاده‌سازی‌های مختلف شبکه پادها را فراهم می‌کنند.

1. می‌توانید از [پلاگین‌های دستگاه](#device-plugins) برای یکپارچه‌سازی سخت‌افزار سفارشی یا سایر امکانات ویژه محلی نود استفاده کنید و آن‌ها را در اختیار Podهایی که در کلاستر شما اجرا می‌شوند قرار دهید. kubelet از کار با پلاگین‌های دستگاه پشتیبانی می‌کند.

   kubelet همچنین
   {{< glossary_tooltip text="حجم‌ها (volume)" term_id="volume" >}} را برای پادها و کانتینرهایشان mount و unmount می‌کند.
   می‌توانید از [پلاگین‌های ذخیره‌سازی](#storage-plugins) برای افزودن پشتیبانی از انواع جدید ذخیره‌سازی و سایر انواع حجم استفاده کنید.

## افزونه‌های کلاینت {#client-extensions}

پلاگین‌های kubectl فایل‌های باینری جداگانه‌ای هستند که رفتار زیرفرمان‌های مشخصی را اضافه یا جایگزین می‌کنند.
ابزار `kubectl` همچنین می‌تواند با [پلاگین‌های اعتبارنامه](/docs/reference/access-authn-authz/authentication/#client-go-credential-plugins) یکپارچه شود.
این افزونه‌ها فقط بر محیط محلی هر کاربر تأثیر می‌گذارند و بنابراین نمی‌توانند سیاست‌های سراسری سایت را اعمال کنند.

اگر می‌خواهید ابزار `kubectl` را گسترش دهید، [گسترش kubectl با پلاگین‌ها](/docs/tasks/extend-kubectl/kubectl-plugins/) را بخوانید.

## افزونه‌های API {#api-extensions}

### تعریف‌های منبع سفارشی {#custom-resource-definitions}

اگر می‌خواهید کنترل‌کننده‌های جدید، آبجکت‌های پیکربندی برنامه یا سایر APIهای اعلانی تعریف کنید و آن‌ها را با ابزارهای کوبرنتیز مانند `kubectl` مدیریت کنید، افزودن یک _منبع سفارشی (Custom Resource)_ به کوبرنتیز را در نظر بگیرید.

برای اطلاعات بیشتر درباره منابع سفارشی، راهنمای مفهومی
[منابع سفارشی](/docs/concepts/extend-kubernetes/api-extension/custom-resources/) را ببینید.

### لایه تجمیع API {#api-aggregation-layer}

می‌توانید از [لایه تجمیع API](/docs/concepts/extend-kubernetes/api-extension/apiserver-aggregation/) کوبرنتیز استفاده کنید تا API کوبرنتیز را با سرویس‌های اضافی مانند
[Metrics API](/docs/concepts/cluster-administration/observability/#metrics-api) یکپارچه کنید.

### ترکیب APIهای جدید با خودکارسازی {#combining-new-apis-with-automation}

ترکیب یک API منبع سفارشی و یک حلقه کنترل، الگوی
{{< glossary_tooltip term_id="controller" text="کنترل‌کننده‌ها" >}} نامیده می‌شود. اگر کنترل‌کننده شما جای یک اپراتور انسانی را می‌گیرد که زیرساخت را بر اساس یک وضعیت مطلوب مستقر می‌کند، آنگاه ممکن است کنترل‌کننده از
{{< glossary_tooltip text="الگوی اپراتور" term_id="operator-pattern" >}} نیز پیروی کند.
الگوی اپراتور برای مدیریت برنامه‌های خاص به‌کار می‌رود؛ معمولاً این‌ها برنامه‌هایی هستند که وضعیت (state) را نگهداری می‌کنند و مدیریت آن‌ها نیازمند دقت است.

همچنین می‌توانید APIهای سفارشی و حلقه‌های کنترل خودتان را برای مدیریت سایر منابع، مانند ذخیره‌سازی، یا برای تعریف سیاست‌ها (مانند محدودیت کنترل دسترسی) بسازید.

### تغییر منابع داخلی {#changing-built-in-resources}

وقتی API کوبرنتیز را با افزودن منابع سفارشی گسترش می‌دهید، منابع افزوده‌شده همیشه در گروه‌های API جدید قرار می‌گیرند. نمی‌توانید گروه‌های API موجود را جایگزین یا تغییر دهید.
افزودن یک API به‌طور مستقیم به شما اجازه نمی‌دهد رفتار APIهای موجود (مانند Pod) را تحت تأثیر قرار دهید، در حالی که
_افزونه‌های دسترسی به API_ چنین امکانی را فراهم می‌کنند.

## افزونه‌های دسترسی به API {#api-access-extensions}

وقتی درخواستی به سرور API کوبرنتیز می‌رسد، ابتدا _احراز هویت_ می‌شود، سپس _مجوزدهی_ می‌شود،
و پس از آن مشمول انواع مختلفی از _کنترل پذیرش (admission control)_ قرار می‌گیرد (برخی درخواست‌ها در واقع احراز هویت نمی‌شوند و با آن‌ها رفتار ویژه‌ای می‌شود). برای اطلاعات بیشتر درباره این جریان، [کنترل دسترسی به API کوبرنتیز](/docs/concepts/security/controlling-access/) را ببینید.

هر یک از مراحل جریان احراز هویت / مجوزدهی در کوبرنتیز نقاط توسعه‌ای ارائه می‌دهد.

### احراز هویت {#authentication}

[احراز هویت](/docs/reference/access-authn-authz/authentication/) سرصفحه‌ها (headers) یا گواهی‌های موجود در همه درخواست‌ها را به نام کاربری کلاینتی که درخواست را ارسال می‌کند نگاشت می‌کند.

کوبرنتیز چند روش احراز هویت داخلی را پشتیبانی می‌کند. همچنین می‌تواند پشت یک پروکسی احراز هویت قرار گیرد، و در صورتی که این روش‌ها نیازهای شما را برآورده نکنند، می‌تواند توکن موجود در سرصفحه `Authorization:` را برای تأیید به یک سرویس راه دور ارسال کند (یک [webhook احراز هویت](/docs/reference/access-authn-authz/authentication/#webhook-token-authentication)).

### مجوزدهی {#authorization}

[مجوزدهی](/docs/reference/access-authn-authz/authorization/) تعیین می‌کند که کاربران مشخص بتوانند منابع API را بخوانند، بنویسند و عملیات دیگری روی آن‌ها انجام دهند. این فرایند در سطح کل منابع عمل می‌کند -- و بر اساس فیلدهای دلخواه آبجکت تمایز قائل نمی‌شود.

اگر گزینه‌های مجوزدهی داخلی نیازهای شما را برآورده نکنند، یک
[webhook مجوزدهی](/docs/reference/access-authn-authz/webhook/)
امکان فراخوانی کدی سفارشی را فراهم می‌کند که تصمیم مجوزدهی را می‌گیرد.

### کنترل پذیرش پویا {#dynamic-admission-control}

پس از مجاز شدن یک درخواست، اگر عملیات نوشتن باشد، از مراحل
[کنترل پذیرش (Admission Control)](/docs/reference/access-authn-authz/admission-controllers/) نیز عبور می‌کند.
علاوه بر مراحل داخلی، چند افزونه وجود دارد:

* [webhook سیاست ایمیج (Image Policy)](/docs/reference/access-authn-authz/admission-controllers/#imagepolicywebhook)
  محدود می‌کند که چه ایمیج‌هایی می‌توانند در کانتینرها اجرا شوند.
* برای اتخاذ تصمیم‌های دلخواه کنترل پذیرش، می‌توان از یک
  [webhook پذیرش (Admission webhook)](/docs/reference/access-authn-authz/extensible-admission-controllers/#admission-webhooks)
  عمومی استفاده کرد. webhookهای پذیرش می‌توانند ایجاد یا به‌روزرسانی را رد کنند.
  برخی webhookهای پذیرش داده‌های درخواست ورودی را پیش از آنکه کوبرنتیز آن را بیشتر پردازش کند، تغییر می‌دهند.

## افزونه‌های زیرساخت {#infrastructure-extensions}

### پلاگین‌های دستگاه {#device-plugins}

_پلاگین‌های دستگاه_ به یک نود اجازه می‌دهند از طریق یک
[Device Plugin](/docs/concepts/extend-kubernetes/compute-storage-net/device-plugins/)
منابع جدید نود را (علاوه بر منابع داخلی مانند cpu و memory) کشف کند.

### پلاگین‌های ذخیره‌سازی {#storage-plugins}

پلاگین‌های {{< glossary_tooltip text="Container Storage Interface" term_id="csi" >}} (CSI) راهی برای گسترش کوبرنتیز با پشتیبانی از انواع جدید حجم فراهم می‌کنند. حجم‌ها می‌توانند توسط ذخیره‌سازی خارجی پایدار پشتیبانی شوند، یا ذخیره‌سازی موقت ارائه دهند، یا یک رابط فقط‌خواندنی برای اطلاعات با استفاده از الگوی سیستم فایل عرضه کنند.

کوبرنتیز همچنین از پلاگین‌های [FlexVolume](/docs/concepts/storage/volumes/#flexvolume) پشتیبانی می‌کند
که از کوبرنتیز نسخه v1.23 منسوخ شده‌اند (به نفع CSI).

پلاگین‌های FlexVolume به کاربران اجازه می‌دهند انواع حجمی را که به‌طور بومی توسط کوبرنتیز پشتیبانی نمی‌شوند mount کنند. وقتی Podی را اجرا می‌کنید که به ذخیره‌سازی FlexVolume متکی است، kubelet یک پلاگین باینری را برای mount کردن حجم فراخوانی می‌کند.
پیشنهاد طراحی بایگانی‌شده [FlexVolume](https://git.k8s.io/design-proposals-archive/storage/flexvolume-deployment.md)
جزئیات بیشتری درباره این رویکرد دارد.

[پرسش‌های متداول پلاگین حجم کوبرنتیز برای فروشندگان ذخیره‌سازی](https://github.com/kubernetes/community/blob/main/sig-storage/volume-plugin-faq.md#kubernetes-volume-plugin-faq-for-storage-vendors)
شامل اطلاعات عمومی درباره پلاگین‌های ذخیره‌سازی است.

### پلاگین‌های شبکه {#network-plugins}

کلاستر کوبرنتیز شما برای داشتن یک شبکه Pod فعال و پشتیبانی از سایر جنبه‌های مدل شبکه کوبرنتیز به یک _پلاگین شبکه_ نیاز دارد.

[پلاگین‌های شبکه](/docs/concepts/extend-kubernetes/compute-storage-net/network-plugins/)
به کوبرنتیز اجازه می‌دهند با توپولوژی‌ها و فناوری‌های شبکه‌ای مختلف کار کند.

### پلاگین‌های ارائه‌دهنده اعتبارنامه ایمیج در kubelet {#kubelet-image-credential-provider-plugins}

{{< feature-state for_k8s_version="v1.26" state="stable" >}}
ارائه‌دهنده‌های اعتبارنامه ایمیج در kubelet پلاگین‌هایی برای kubelet هستند که اعتبارنامه‌های رجیستری ایمیج را به‌صورت پویا دریافت می‌کنند. سپس این اعتبارنامه‌ها هنگام pull کردن ایمیج‌ها از رجیستری‌های ایمیج کانتینر که با پیکربندی مطابقت دارند، استفاده می‌شوند.

این پلاگین‌ها می‌توانند با سرویس‌های خارجی ارتباط برقرار کنند یا برای دریافت اعتبارنامه‌ها از فایل‌های محلی استفاده کنند. به این ترتیب، kubelet نیازی ندارد برای هر رجیستری اعتبارنامه‌های ثابت داشته باشد و می‌تواند از روش‌ها و پروتکل‌های احراز هویت مختلف پشتیبانی کند.

برای جزئیات پیکربندی پلاگین، به
[پیکربندی یک ارائه‌دهنده اعتبارنامه ایمیج در kubelet](/docs/tasks/administer-cluster/kubelet-credential-provider/)
مراجعه کنید.

## افزونه‌های زمان‌بندی {#scheduling-extensions}

زمان‌بند نوع ویژه‌ای از کنترل‌کننده است که پادها را مشاهده می‌کند و آن‌ها را به نودها اختصاص می‌دهد. زمان‌بند پیش‌فرض را می‌توان به‌طور کامل جایگزین کرد، در حالی که از سایر مؤلفه‌های کوبرنتیز همچنان استفاده می‌شود، یا
[چند زمان‌بند](/docs/tasks/extend-kubernetes/configure-multiple-schedulers/)
می‌توانند هم‌زمان اجرا شوند.

این کار مستلزم تلاش قابل‌توجهی است و تقریباً همه کاربران کوبرنتیز درمی‌یابند که نیازی به تغییر زمان‌بند ندارند.

می‌توانید کنترل کنید کدام [پلاگین‌های زمان‌بندی](/docs/reference/scheduling/config/#scheduling-plugins)
فعال باشند، یا مجموعه‌هایی از پلاگین‌ها را با [پروفایل‌های زمان‌بند](/docs/reference/scheduling/config/#multiple-profiles) نام‌دار مختلف مرتبط کنید.
همچنین می‌توانید پلاگین خودتان را بنویسید که با یک یا چند مورد از
[نقاط توسعه](/docs/concepts/scheduling-eviction/scheduling-framework/#extension-points) kube-scheduler یکپارچه شود.

در نهایت، مؤلفه داخلی `kube-scheduler` از یک
[webhook](https://git.k8s.io/design-proposals-archive/scheduling/scheduler_extender.md)
پشتیبانی می‌کند که به یک backend راه دور HTTP (افزونه زمان‌بند) اجازه می‌دهد نودهایی را که kube-scheduler برای یک Pod انتخاب می‌کند فیلتر و/یا اولویت‌بندی کند.

{{< note >}}
با webhook افزونه زمان‌بند (scheduler extender) فقط می‌توانید بر فیلتر کردن نودها
و اولویت‌بندی نودها تأثیر بگذارید؛ سایر نقاط توسعه از طریق یکپارچه‌سازی webhook در دسترس نیستند.
{{< /note >}}
