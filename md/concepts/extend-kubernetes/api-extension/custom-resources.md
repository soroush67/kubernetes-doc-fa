*منابع سفارشی* (Custom resources) نمونه‌هایی از انواع منابع هستند که از طریق افزونه‌های API به کوبرنتیز اضافه می‌شوند. این صفحه توضیح می‌دهد که چه زمانی باید یک منبع سفارشی به کلاستر کوبرنتیز خود اضافه کنید و چه زمانی بهتر است از یک سرویس مستقل استفاده کنید. همچنین دو روش افزودن منابع سفارشی و نحوهٔ انتخاب میان آن‌ها را شرح می‌دهد.

<!-- body -->
## منابع سفارشی

هر *منبع* یک نقطهٔ پایانی (endpoint) در [API کوبرنتیز](/docs/concepts/overview/kubernetes-api/) است که مجموعه‌ای از {{< glossary_tooltip text="آبجکت‌های API" term_id="object" >}} از یک نوع مشخص را ذخیره می‌کند؛ برای مثال، منبع داخلی *pods* شامل مجموعه‌ای از آبجکت‌های Pod است.

هر *منبع سفارشی* افزونه‌ای بر API کوبرنتیز است که لزوماً در نصب پیش‌فرض کوبرنتیز در دسترس نیست. منبع سفارشی نشان‌دهندهٔ سفارشی‌سازی یک نصب خاص از کوبرنتیز است. با این حال، امروزه بسیاری از قابلیت‌های اصلی کوبرنتیز با استفاده از منابع سفارشی ساخته می‌شوند و همین امر کوبرنتیز را ماژولارتر کرده است.

منابع سفارشی می‌توانند از طریق ثبت پویا (dynamic registration) در یک کلاستر در حال اجرا ظاهر یا حذف شوند و مدیران کلاستر می‌توانند منابع سفارشی را مستقل از خود کلاستر به‌روزرسانی کنند. پس از نصب یک منبع سفارشی، کاربران می‌توانند با استفاده از {{< glossary_tooltip text="kubectl" term_id="kubectl" >}} آبجکت‌های آن را ایجاد کنند و به آن‌ها دسترسی داشته باشند؛ درست همان‌طور که با منابع داخلی مانند *Pods* کار می‌کنند.

## کنترل‌کننده‌های سفارشی

منابع سفارشی به‌تنهایی فقط امکان ذخیره و بازیابی داده‌های ساختاریافته را فراهم می‌کنند. وقتی یک منبع سفارشی را با یک *کنترل‌کنندهٔ سفارشی* (custom controller) ترکیب کنید، منابع سفارشی یک _API اعلانی_ (declarative API) واقعی فراهم می‌کنند.

[API اعلانی](/docs/concepts/overview/kubernetes-api/) کوبرنتیز تفکیک مسئولیت‌ها را الزامی می‌کند. شما وضعیت مطلوب منبع خود را اعلام می‌کنید و کنترل‌کنندهٔ کوبرنتیز وضعیت فعلی آبجکت‌های کوبرنتیز را با وضعیت مطلوب اعلام‌شده همگام نگه می‌دارد. این رویکرد برخلاف API دستوری (imperative) است که در آن به سرور *دستور می‌دهید* چه کاری انجام دهد.

می‌توانید یک کنترل‌کنندهٔ سفارشی را روی یک کلاستر در حال اجرا و مستقل از چرخهٔ عمر کلاستر مستقر و به‌روزرسانی کنید. کنترل‌کننده‌های سفارشی با هر نوع منبعی کار می‌کنند، اما به‌ویژه در ترکیب با منابع سفارشی کارآمدند. [الگوی Operator](/docs/concepts/extend-kubernetes/operator/) منابع سفارشی و کنترل‌کننده‌های سفارشی را با هم ترکیب می‌کند. با کنترل‌کننده‌های سفارشی می‌توانید دانش حوزه‌ای مربوط به برنامه‌های خاص را در قالب افزونه‌ای از API کوبرنتیز پیاده‌سازی کنید.

## آیا باید یک منبع سفارشی به کلاستر کوبرنتیز خود اضافه کنم؟

هنگام ایجاد یک API جدید، بررسی کنید که آیا بهتر است [API خود را با APIهای کلاستر کوبرنتیز تجمیع کنید](/docs/concepts/extend-kubernetes/api-extension/apiserver-aggregation/) یا API شما مستقل باقی بماند.

| در این موارد تجمیع API را در نظر بگیرید: | در این موارد API مستقل را ترجیح دهید: |
| ---------------------------- | ---------------------------- |
| مدل API شما [اعلانی](#declarative-apis) است. | طراحی API شما با مدل [اعلانی](#declarative-apis) سازگار نیست. |
| می‌خواهید انواع جدیدتان با `kubectl` قابل خواندن و نوشتن باشند. | به پشتیبانی از `kubectl` نیازی نیست. |
| می‌خواهید انواع جدیدتان را در کنار انواع داخلی، در یک رابط کاربری کوبرنتیز مانند داشبورد مشاهده کنید. | به پشتیبانی رابط کاربری کوبرنتیز نیازی نیست. |
| در حال توسعهٔ یک API جدید هستید. | از قبل برنامه‌ای دارید که API شما را ارائه می‌دهد و به‌خوبی کار می‌کند. |
| حاضرید محدودیت قالبی را که کوبرنتیز بر مسیرهای منابع REST اعمال می‌کند، مانند گروه‌های API و فضاهای نام (namespace)، بپذیرید. (به [نمای کلی API](/docs/concepts/overview/kubernetes-api/) مراجعه کنید.) | برای سازگاری با یک REST API ازپیش‌تعریف‌شده، به مسیرهای REST مشخصی نیاز دارید. |
| منابع شما به‌طور طبیعی در دامنهٔ یک کلاستر یا فضاهای نام یک کلاستر قرار می‌گیرند. | منابعی با دامنهٔ کلاستر یا فضای نام مناسب نیستند و به کنترل بر جزئیات مسیرهای منابع نیاز دارید. |
| می‌خواهید از [قابلیت‌های پشتیبانی API کوبرنتیز](#common-features) دوباره استفاده کنید. | به این قابلیت‌ها نیازی ندارید. |

### رابط‌های API اعلانی

در یک API اعلانی، معمولاً این ویژگی‌ها وجود دارد:

- این API از تعداد نسبتاً کمی آبجکت (منبع) نسبتاً کوچک تشکیل شده است.
- آبجکت‌ها پیکربندی برنامه‌ها یا زیرساخت را تعریف می‌کنند.
- آبجکت‌ها نسبتاً به‌ندرت به‌روزرسانی می‌شوند.
- انسان‌ها اغلب نیاز دارند آبجکت‌ها را بخوانند و بنویسند.
- عملیات اصلی روی آبجکت‌ها از نوع CRUD (ایجاد، خواندن، به‌روزرسانی و حذف) است.
- به تراکنش‌های میان چند آبجکت نیازی نیست: این API وضعیت مطلوب را نشان می‌دهد، نه وضعیت دقیق را.

رابط‌های API دستوری اعلانی نیستند. نشانه‌هایی که ممکن است API شما اعلانی نباشد عبارت‌اند از:

- کلاینت می‌گوید «این کار را انجام بده» و پس از اتمام کار، یک پاسخ همگام دریافت می‌کند.
- کلاینت می‌گوید «این کار را انجام بده»، سپس یک شناسهٔ عملیات (operation ID) دریافت می‌کند و برای تشخیص تکمیل درخواست باید یک آبجکت Operation جداگانه را بررسی کند.
- از فراخوانی‌های رویه‌ای از راه دور (RPC) صحبت می‌کنید.
- حجم زیادی از داده به‌طور مستقیم ذخیره می‌شود؛ برای مثال، بیش از چند کیلوبایت به ازای هر آبجکت یا بیش از هزاران آبجکت.
- به دسترسی با پهنای باند بالا (ده‌ها درخواست در ثانیه به‌طور پیوسته) نیاز است.
- داده‌های کاربر نهایی (مانند تصاویر، اطلاعات شناسایی شخصی یا PII و غیره) یا سایر داده‌های بزرگ‌مقیاسی که برنامه‌ها پردازش می‌کنند، ذخیره می‌شوند.
- عملیات طبیعی روی آبجکت‌ها از نوع CRUD نیستند.
- این API را نمی‌توان به‌سادگی به‌صورت آبجکت مدل‌سازی کرد.
- تصمیم گرفته‌اید عملیات در انتظار را با یک شناسهٔ عملیات یا یک آبجکت عملیات نمایش دهید.

## آیا باید از ConfigMap استفاده کنم یا از یک منبع سفارشی؟

اگر هر یک از موارد زیر صدق می‌کند، از ConfigMap استفاده کنید:

* یک قالب فایل پیکربندی موجود و به‌خوبی مستندشده، مانند `mysql.cnf` یا `pom.xml`، وجود دارد.
* می‌خواهید کل پیکربندی را در یک کلید از ConfigMap قرار دهید.
* کاربرد اصلی فایل پیکربندی این است که برنامه‌ای که در یک Pod روی کلاستر شما اجرا می‌شود، فایل را بخواند تا خود را پیکربندی کند.
* مصرف‌کنندگان فایل ترجیح می‌دهند به‌جای API کوبرنتیز، آن را از طریق یک فایل در Pod یا یک متغیر محیطی در Pod دریافت کنند.
* می‌خواهید هنگام به‌روزرسانی فایل، به‌روزرسانی‌های تدریجی (rolling update) را از طریق Deployment و موارد مشابه انجام دهید.

{{< note >}}
برای داده‌های حساس از یک {{< glossary_tooltip text="Secret" term_id="secret" >}} استفاده کنید که مشابه ConfigMap است، اما امنیت بیشتری دارد.
{{< /note >}}

اگر بیشتر موارد زیر صدق می‌کند، از یک منبع سفارشی (CRD یا API تجمیع‌شده) استفاده کنید:

* می‌خواهید از کتابخانه‌های کلاینت و ابزارهای خط فرمان کوبرنتیز برای ایجاد و به‌روزرسانی منبع جدید استفاده کنید.
* می‌خواهید `kubectl` در سطح بالا از آن پشتیبانی کند؛ برای مثال، `kubectl get my-object object-name`.
* می‌خواهید خودکارسازی جدیدی بسازید که به‌روزرسانی‌های آبجکت جدید را زیر نظر بگیرد و سپس عملیات CRUD را روی آبجکت‌های دیگر انجام دهد، یا برعکس.
* می‌خواهید خودکارسازی‌ای بنویسید که به‌روزرسانی‌های آبجکت را مدیریت کند.
* می‌خواهید از قراردادهای API کوبرنتیز مانند `.spec`، `.status` و `.metadata` استفاده کنید.
* می‌خواهید آبجکت، انتزاعی بر روی مجموعه‌ای از منابع کنترل‌شده یا خلاصه‌ای از منابع دیگر باشد.

## افزودن منابع سفارشی

کوبرنتیز دو روش برای افزودن منابع سفارشی به کلاستر شما فراهم می‌کند:

- استفاده از CRDها ساده است و ایجاد آن‌ها به هیچ برنامه‌نویسی نیاز ندارد.
- [تجمیع API](/docs/concepts/extend-kubernetes/api-extension/apiserver-aggregation/) به برنامه‌نویسی نیاز دارد، اما کنترل بیشتری بر رفتارهای API، مانند نحوهٔ ذخیره‌سازی داده‌ها و تبدیل میان نسخه‌های API، فراهم می‌کند.

کوبرنتیز این دو گزینه را برای پاسخ به نیازهای کاربران مختلف ارائه می‌دهد تا نه سهولت استفاده فدا شود و نه انعطاف‌پذیری.

رابط‌های API تجمیع‌شده، سرورهای API فرعی‌ای هستند که پشت سرور API اصلی قرار می‌گیرند و سرور اصلی برای آن‌ها نقش پروکسی را ایفا می‌کند. این چیدمان [تجمیع API](/docs/concepts/extend-kubernetes/api-extension/apiserver-aggregation/)(AA) نامیده می‌شود. از دید کاربران، API کوبرنتیز گسترش‌یافته به نظر می‌رسد.

با CRDها، کاربران می‌توانند بدون افزودن سرور API دیگری، انواع جدیدی از منابع ایجاد کنند. برای استفاده از CRDها نیازی به درک تجمیع API ندارید.

صرف‌نظر از نحوهٔ نصب، منابع جدید «منابع سفارشی» نامیده می‌شوند تا از منابع داخلی کوبرنتیز (مانند podها) متمایز شوند.

{{< note >}}
از منبع سفارشی به‌عنوان محل ذخیره‌سازی داده‌های برنامه، داده‌های کاربر نهایی یا داده‌های پایش استفاده نکنید: طراحی‌های معماری‌ای که داده‌های برنامه را درون API کوبرنتیز ذخیره می‌کنند، معمولاً نشان‌دهندهٔ طراحی‌ای با وابستگی بیش از حد تنگاتنگ هستند.

از نظر معماری، معماری‌های برنامه‌های [بومی ابر](https://www.cncf.io/about/faq/#what-is-cloud-native) (cloud native) اتصال سست (loose coupling) میان مؤلفه‌ها را ترجیح می‌دهند. اگر بخشی از بار کاری شما برای عملیات روزمرهٔ خود به یک سرویس پشتیبان نیاز دارد، آن سرویس پشتیبان را به‌عنوان یک مؤلفه اجرا کنید یا آن را به‌عنوان یک سرویس خارجی به کار ببرید. به این ترتیب، بار کاری شما برای عملکرد عادی خود به API کوبرنتیز وابسته نخواهد بود.
{{< /note >}}

## آبجکت‌های CustomResourceDefinition

منبع API [CustomResourceDefinition](/docs/tasks/extend-kubernetes/custom-resources/custom-resource-definitions/) امکان تعریف منابع سفارشی را فراهم می‌کند. با تعریف یک آبجکت CRD، منبع سفارشی جدیدی با نام و طرح‌واره‌ای (schema) که خودتان تعیین می‌کنید ایجاد می‌شود. خود API کوبرنتیز منبع سفارشی شما را ارائه می‌دهد و ذخیره‌سازی آن را مدیریت می‌کند. نام خود آبجکت CRD باید یک [نام زیردامنهٔ DNS](/docs/concepts/overview/working-with-objects/names#dns-subdomain-names) معتبر باشد که از نام منبع تعریف‌شده و گروه API آن به دست می‌آید؛ برای جزئیات بیشتر به [نحوهٔ ایجاد یک CRD](/docs/tasks/extend-kubernetes/custom-resources/custom-resource-definitions#create-a-customresourcedefinition) مراجعه کنید. علاوه بر این، نام هر آبجکتی که نوع/منبع آن با یک CRD تعریف شده است نیز باید یک نام زیردامنهٔ DNS معتبر باشد.

به این ترتیب، دیگر لازم نیست برای مدیریت منبع سفارشی، سرور API خودتان را بنویسید؛ اما ماهیت عمومی این پیاده‌سازی باعث می‌شود انعطاف‌پذیری کمتری نسبت به [تجمیع سرور API](#api-server-aggregation) داشته باشید.

برای نمونه‌ای از نحوهٔ ثبت یک منبع سفارشی جدید، کار با نمونه‌های نوع منبع جدید و استفاده از یک کنترل‌کننده برای مدیریت رویدادها، به [نمونهٔ کنترل‌کنندهٔ سفارشی](https://github.com/kubernetes/sample-controller) مراجعه کنید.

## تجمیع سرور API

معمولاً هر منبع در API کوبرنتیز به کدی نیاز دارد که درخواست‌های REST را پردازش کند و ذخیره‌سازی ماندگار آبجکت‌ها را مدیریت کند. سرور API اصلی کوبرنتیز منابع داخلی مانند *pods* و *services* را مدیریت می‌کند و می‌تواند منابع سفارشی را نیز به‌صورت عمومی از طریق [CRDها](#customresourcedefinitions) مدیریت کند.

[لایهٔ تجمیع](/docs/concepts/extend-kubernetes/api-extension/apiserver-aggregation/) به شما امکان می‌دهد با نوشتن و استقرار سرور API خودتان، پیاده‌سازی‌های تخصصی برای منابع سفارشی خود ارائه دهید. سرور API اصلی درخواست‌های مربوط به منابع سفارشی‌ای را که شما مدیریت می‌کنید به سرور API شما واگذار می‌کند و به این ترتیب آن‌ها را در دسترس همهٔ کلاینت‌های خود قرار می‌دهد.

## انتخاب روشی برای افزودن منابع سفارشی

استفاده از CRDها آسان‌تر است و رابط‌های API تجمیع‌شده انعطاف‌پذیری بیشتری دارند. روشی را انتخاب کنید که به بهترین شکل نیازهای شما را برآورده می‌کند.

معمولاً CRDها در این موارد گزینهٔ مناسبی هستند:

* تعداد فیلدهای شما اندک است.
* از منبع در داخل شرکت خود یا به‌عنوان بخشی از یک پروژهٔ متن‌باز کوچک (و نه یک محصول تجاری) استفاده می‌کنید.

### مقایسهٔ سهولت استفاده

ایجاد CRDها آسان‌تر از رابط‌های API تجمیع‌شده است.

| CRDها                        | API تجمیع‌شده |
| --------------------------- | -------------- |
| به برنامه‌نویسی نیاز ندارند. کاربران می‌توانند هر زبانی را برای کنترل‌کنندهٔ CRD انتخاب کنند. | به برنامه‌نویسی و ساخت فایل باینری و ایمیج نیاز دارد. |
| به اجرای سرویس اضافی نیازی نیست؛ سرور API خودش CRDها را مدیریت می‌کند. | باید یک سرویس اضافی ایجاد شود که ممکن است با خطا مواجه شود. |
| پس از ایجاد CRD، به پشتیبانی مداوم نیازی نیست. همهٔ رفع اشکال‌ها در جریان ارتقاهای معمول Master کوبرنتیز اعمال می‌شوند. | ممکن است لازم باشد به‌طور دوره‌ای رفع اشکال‌ها را از upstream دریافت کنید و سرور API تجمیع‌شده را دوباره بسازید و به‌روزرسانی کنید. |
| نیازی به مدیریت چند نسخه از API خود ندارید؛ برای مثال، وقتی کلاینت این منبع را در اختیار دارید، می‌توانید آن را همگام با API ارتقا دهید. | باید چند نسخه از API خود را مدیریت کنید؛ برای مثال، هنگام توسعهٔ افزونه‌ای برای اشتراک‌گذاری با دیگران. |

### قابلیت‌های پیشرفته و انعطاف‌پذیری

رابط‌های API تجمیع‌شده قابلیت‌های پیشرفته‌تری برای API و امکان سفارشی‌سازی سایر قابلیت‌ها، برای مثال لایهٔ ذخیره‌سازی، را ارائه می‌دهند.

| قابلیت | توضیحات | CRDها | API تجمیع‌شده |
| ------- | ----------- | ---- | -------------- |
| اعتبارسنجی | به کاربران کمک می‌کند از خطاها جلوگیری کنند و به شما امکان می‌دهد API خود را مستقل از کلاینت‌ها تکامل دهید. این قابلیت‌ها زمانی بیشترین فایده را دارند که کلاینت‌های زیادی وجود داشته باشند که نتوانند همگی هم‌زمان به‌روزرسانی شوند. | بله. بیشتر اعتبارسنجی‌ها را می‌توان در CRD با استفاده از [اعتبارسنجی OpenAPI v3.0](/docs/tasks/extend-kubernetes/custom-resources/custom-resource-definitions/#validation) مشخص کرد. با feature gate [CRDValidationRatcheting](/docs/tasks/extend-kubernetes/custom-resources/custom-resource-definitions/#validation-ratcheting) می‌توان اعتبارسنجی‌های ناموفقی را که با OpenAPI مشخص شده‌اند، در صورتی که بخش ناموفق منبع تغییر نکرده باشد، نادیده گرفت. سایر اعتبارسنجی‌ها با افزودن یک [وب‌هوک اعتبارسنجی (Validating Webhook)](/docs/reference/access-authn-authz/admission-controllers/#validatingadmissionwebhook-alpha-in-1-8-beta-in-1-9) پشتیبانی می‌شوند. | بله، بررسی‌های اعتبارسنجی دلخواه |
| مقداردهی پیش‌فرض | موارد بالا را ببینید | بله، یا از طریق کلیدواژهٔ `default` در [اعتبارسنجی OpenAPI v3.0](/docs/tasks/extend-kubernetes/custom-resources/custom-resource-definitions/#defaulting) (در نسخهٔ 1.17 به وضعیت GA رسیده است)، یا از طریق یک [وب‌هوک تغییردهنده (Mutating Webhook)](/docs/reference/access-authn-authz/admission-controllers/#mutatingadmissionwebhook) (هرچند این وب‌هوک هنگام خواندن آبجکت‌های قدیمی از etcd اجرا نمی‌شود). | بله |
| چندنسخه‌ای بودن | امکان ارائهٔ یک آبجکت یکسان از طریق دو نسخهٔ API را فراهم می‌کند. می‌تواند تغییرات API مانند تغییر نام فیلدها را آسان‌تر کند. اگر نسخه‌های کلاینت خود را در اختیار دارید، اهمیت کمتری دارد. | [بله](/docs/tasks/extend-kubernetes/custom-resources/custom-resource-definition-versioning) | بله |
| ذخیره‌سازی سفارشی | در صورتی که به ذخیره‌سازی با حالت کارایی متفاوت (برای مثال، یک پایگاه دادهٔ سری زمانی به‌جای ذخیره‌ساز کلید-مقدار) یا جداسازی به دلایل امنیتی (برای مثال، رمزگذاری اطلاعات حساس و غیره) نیاز دارید. | خیر | بله |
| منطق تجاری سفارشی | هنگام ایجاد، خواندن، به‌روزرسانی یا حذف یک آبجکت، بررسی‌ها یا اقدامات دلخواه را انجام می‌دهد. | بله، با استفاده از [وب‌هوک‌ها](/docs/reference/access-authn-authz/extensible-admission-controllers/#admission-webhooks). | بله |
| زیرمنبع Scale | به سیستم‌هایی مانند HorizontalPodAutoscaler و PodDisruptionBudget امکان می‌دهد با منبع جدید شما تعامل داشته باشند. | [بله](/docs/tasks/extend-kubernetes/custom-resources/custom-resource-definitions/#scale-subresource)  | بله |
| زیرمنبع Status | کنترل دسترسی دقیق را ممکن می‌کند؛ به این صورت که کاربر بخش spec و کنترل‌کننده بخش status را می‌نویسد. همچنین امکان افزایش Generation آبجکت را هنگام تغییر داده‌های منبع سفارشی فراهم می‌کند (به بخش‌های spec و status جداگانه در منبع نیاز دارد). | [بله](/docs/tasks/extend-kubernetes/custom-resources/custom-resource-definitions/#status-subresource) | بله |
| سایر زیرمنابع | عملیاتی غیر از CRUD، مانند "logs" یا "exec"، اضافه می‌کند. | خیر | بله |
| وصلهٔ strategic-merge-patch | نقاط پایانی جدید از درخواست PATCH با `Content-Type: application/strategic-merge-patch+json` پشتیبانی می‌کنند. این قابلیت برای به‌روزرسانی آبجکت‌هایی مفید است که ممکن است هم به‌صورت محلی و هم از سوی سرور تغییر کنند. برای اطلاعات بیشتر، به [«به‌روزرسانی درجای آبجکت‌های API با استفاده از kubectl patch»](/docs/tasks/manage-kubernetes-objects/update-api-object-kubectl-patch/) مراجعه کنید. | خیر | بله |
| پروتکل بافرها | منبع جدید از کلاینت‌هایی که می‌خواهند از Protocol Buffers استفاده کنند پشتیبانی می‌کند. | خیر | بله |
| طرح‌وارهٔ OpenAPI | آیا برای انواع، طرح‌واره‌ای از نوع OpenAPI (swagger) وجود دارد که بتوان آن را به‌صورت پویا از سرور دریافت کرد؟ آیا با اطمینان از اینکه فقط فیلدهای مجاز تنظیم می‌شوند، کاربر از غلط املایی در نام فیلدها محافظت می‌شود؟ آیا انواع داده اعمال می‌شوند (به عبارت دیگر، اجازه داده نمی‌شود یک `int` در فیلدی از نوع `string` قرار گیرد)؟ | بله، بر اساس طرح‌وارهٔ [اعتبارسنجی OpenAPI v3.0](/docs/tasks/extend-kubernetes/custom-resources/custom-resource-definitions/#validation) (در نسخهٔ 1.16 به وضعیت GA رسیده است). | بله |
| نام نمونه | آیا این سازوکار افزونه محدودیتی بر نام آبجکت‌هایی که نوع/منبع آن‌ها به این شیوه تعریف شده است اعمال می‌کند؟ | بله، نام چنین آبجکتی باید یک نام زیردامنهٔ DNS معتبر باشد. | خیر |

### ویژگی‌های مشترک

وقتی یک منبع سفارشی را، چه از طریق CRD و چه از طریق AA، ایجاد می‌کنید، API شما در مقایسه با پیاده‌سازی آن در خارج از پلتفرم کوبرنتیز ویژگی‌های بسیاری به دست می‌آورد:

| ویژگی | کاری که انجام می‌دهد |
| ------- | ------------ |
| عملیات CRUD | نقاط پایانی (endpoint) جدید از عملیات پایه‌ی CRUD از طریق HTTP و `kubectl` پشتیبانی می‌کنند |
| پایش (Watch) | نقاط پایانی جدید از عملیات Watch کوبرنتیز از طریق HTTP پشتیبانی می‌کنند |
| کشف (Discovery) | کلاینت‌هایی مانند `kubectl` و داشبورد به‌طور خودکار عملیات فهرست‌کردن، نمایش و ویرایش فیلد را روی منابع شما ارائه می‌دهند |
| قابلیت json-patch | نقاط پایانی جدید از PATCH با `Content-Type: application/json-patch+json` پشتیبانی می‌کنند |
| قابلیت merge-patch | نقاط پایانی جدید از PATCH با `Content-Type: application/merge-patch+json` پشتیبانی می‌کنند |
| پروتکل HTTPS | نقاط پایانی جدید از HTTPS استفاده می‌کنند |
| احراز هویت داخلی | دسترسی به افزونه برای احراز هویت از API server اصلی (لایه‌ی تجمیع) استفاده می‌کند |
| مجوزدهی داخلی | دسترسی به افزونه می‌تواند از همان سازوکار مجوزدهی API server اصلی، برای مثال RBAC، دوباره استفاده کند. |
| نهایی‌کننده‌ها (Finalizers) | حذف منابع افزونه را تا زمان انجام پاک‌سازی خارجی مسدود می‌کنند. |
| وب‌هوک‌های پذیرش (Admission Webhooks) | در هر عملیات ایجاد، به‌روزرسانی یا حذف، مقادیر پیش‌فرض را تنظیم و منابع افزونه را اعتبارسنجی می‌کنند. |
| نمایش در رابط کاربری و خط فرمان | ابزار Kubectl و داشبورد می‌توانند منابع افزونه را نمایش دهند. |
| تنظیم‌نشده در برابر خالی | کلاینت‌ها می‌توانند فیلدهای تنظیم‌نشده را از فیلدهایی که مقدار صفر دارند تشخیص دهند. |
| تولید کتابخانه‌های کلاینت | کوبرنتیز کتابخانه‌های کلاینت عمومی و همچنین ابزارهایی برای تولید کتابخانه‌های کلاینت مختص هر نوع ارائه می‌دهد. |
| برچسب‌ها و حاشیه‌نویسی‌ها (annotations) | فراداده‌ای مشترک میان آبجکت‌ها که ابزارها می‌دانند چگونه آن را برای منابع اصلی و سفارشی ویرایش کنند. |

## آماده‌سازی برای نصب یک منبع سفارشی

پیش از افزودن یک منبع سفارشی به کلاستر، باید به چند نکته توجه کنید.

### کد شخص ثالث و نقاط خرابی جدید

ایجاد یک CRD به‌خودی‌خود نقطه‌ی خرابی جدیدی اضافه نمی‌کند (برای مثال، باعث اجرای کد شخص ثالث روی API server شما نمی‌شود)؛ اما بسته‌ها (مثلاً Chartها) یا دیگر بسته‌های نصبی اغلب علاوه بر CRDها، یک Deployment از کد شخص ثالث را نیز شامل می‌شوند که منطق کسب‌وکار منبع سفارشی جدید را پیاده‌سازی می‌کند.

نصب یک Aggregated API server همیشه به اجرای یک Deployment جدید نیاز دارد.

### ذخیره‌سازی

منابع سفارشی به همان شیوه‌ی ConfigMapها فضای ذخیره‌سازی مصرف می‌کنند. ایجاد تعداد بیش از حد منابع سفارشی ممکن است فضای ذخیره‌سازی API server شما را بیش از ظرفیت آن پر کند.

منابع سفارشی بر اساس نسخه‌ی ذخیره‌سازی فعلی منبع، که در spec مربوط به CRD تعریف شده است، ذخیره می‌شوند. هر به‌روزرسانی یک منبع سفارشی، از نسخه‌ی ذخیره‌سازیِ تعریف‌شده‌ی فعلی برای ذخیره‌ی منبع استفاده می‌کند. همه‌ی نسخه‌های دیگر برای کارکرد درست یا باید همه‌ی فیلدهای آن نسخه را داشته باشند یا تبدیل‌هایی (conversion) برای آن تعریف کنند.

ممکن است Aggregated API serverها از همان ذخیره‌سازی API server اصلی استفاده کنند که در این صورت همین هشدار درباره‌ی آن‌ها نیز صدق می‌کند.

### احراز هویت، مجوزدهی و ممیزی

CRDها همیشه از همان سازوکار احراز هویت، مجوزدهی و ثبت گزارش ممیزی (audit logging) استفاده می‌کنند که منابع داخلی API server شما به کار می‌برند.

اگر برای مجوزدهی از RBAC استفاده می‌کنید، بیشتر نقش‌های RBAC به منابع جدید دسترسی نمی‌دهند (به‌جز نقش cluster-admin یا هر نقشی که با قواعد wildcard ایجاد شده باشد). بنابراین باید به‌صراحت به منابع جدید دسترسی بدهید. معمولاً CRDها و Aggregated APIها همراه با تعریف نقش‌های جدیدی برای انواعی که اضافه می‌کنند ارائه می‌شوند.

ممکن است Aggregated API serverها از همان سازوکار احراز هویت، مجوزدهی و ممیزی API server اصلی استفاده کنند یا نکنند.

## دسترسی به یک منبع سفارشی

برای دسترسی به منابع سفارشی می‌توان از [کتابخانه‌های کلاینت](/docs/reference/using-api/client-libraries/) کوبرنتیز استفاده کرد. همه‌ی کتابخانه‌های کلاینت از منابع سفارشی پشتیبانی نمی‌کنند، اما کتابخانه‌های کلاینت _Go_ و _Python_ این پشتیبانی را دارند.

وقتی یک منبع سفارشی اضافه می‌کنید، می‌توانید با این ابزارها به آن دسترسی داشته باشید:

- `kubectl`
- کلاینت پویای (dynamic client) کوبرنتیز.
- یک کلاینت REST که خودتان می‌نویسید.
- کلاینتی که با [ابزارهای تولید کلاینت کوبرنتیز](https://github.com/kubernetes/code-generator) تولید شده است
  (تولید چنین کلاینتی کاری پیشرفته است، اما برخی پروژه‌ها ممکن است یک کلاینت را همراه با CRD یا AA ارائه دهند).


## انتخابگرهای فیلد منابع سفارشی

[انتخابگرهای فیلد](/docs/concepts/overview/working-with-objects/field-selectors/) (Field Selectors) به کلاینت‌ها امکان می‌دهند منابع سفارشی را بر اساس مقدار یک یا چند فیلد منبع انتخاب کنند.

همه‌ی منابع سفارشی از انتخابگرهای فیلد `metadata.name` و `metadata.namespace` پشتیبانی می‌کنند.
