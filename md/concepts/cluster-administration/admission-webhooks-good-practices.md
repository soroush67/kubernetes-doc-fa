این صفحه روش‌های خوب و ملاحظاتی را برای طراحی
_admission webhookها_ (وب‌هوک‌های پذیرش) در کوبرنتیز ارائه می‌دهد. این اطلاعات برای
گردانندگان کلاستری در نظر گرفته شده است که سرورهای admission webhook یا برنامه‌های شخص ثالثی را اجرا می‌کنند
که درخواست‌های API شما را تغییر می‌دهند یا اعتبارسنجی می‌کنند.

پیش از خواندن این صفحه، اطمینان حاصل کنید که با مفاهیم زیر
آشنا هستید:

* [کنترل‌کننده‌های پذیرش](/docs/reference/access-authn-authz/admission-controllers/)
* [Admission webhookها](/docs/reference/access-authn-authz/extensible-admission-controllers/#what-are-admission-webhooks)

## اهمیت طراحی خوب webhook {#why-good-webhook-design-matters}

کنترل پذیرش زمانی رخ می‌دهد که هر درخواست ایجاد، به‌روزرسانی یا حذفی
به API کوبرنتیز ارسال شود. کنترل‌کننده‌های پذیرش درخواست‌هایی را که با
معیارهای مشخصی که شما تعریف می‌کنید مطابقت دارند رهگیری می‌کنند. سپس این درخواست‌ها به
mutating admission webhookها یا validating admission webhookها ارسال می‌شوند. این webhookها
اغلب برای اطمینان از اینکه فیلدهای مشخصی در مشخصات آبجکت‌ها وجود داشته باشند یا
مقادیر مجاز مشخصی داشته باشند نوشته می‌شوند.

Webhookها سازوکاری قدرتمند برای گسترش API کوبرنتیز هستند. webhookهای بدطراحی‌شده
اغلب به دلیل میزان کنترلی که بر آبجکت‌های کلاستر دارند، به اختلال در بارهای کاری
منجر می‌شوند. همانند دیگر سازوکارهای گسترش API،
آزمودن webhookها در مقیاس بزرگ از نظر سازگاری با
همهٔ بارهای کاری، دیگر webhookها، افزونه‌ها و پلاگین‌ها دشوار است.

افزون بر این، کوبرنتیز در هر انتشار، API را با قابلیت‌های جدید،
ارتقای قابلیت‌ها به وضعیت بتا یا پایدار، و منسوخ‌سازی‌ها گسترش می‌دهد یا تغییر می‌دهد. حتی
APIهای پایدار کوبرنتیز نیز احتمالاً تغییر خواهند کرد. برای نمونه، API مربوط به `Pod`
در نسخهٔ v1.29 تغییر کرد تا قابلیت
[کانتینرهای Sidecar](/docs/concepts/workloads/pods/sidecar-containers/) به آن افزوده شود.
اگرچه به‌ندرت پیش می‌آید که یک آبجکت کوبرنتیز به دلیل یک API جدید کوبرنتیز وارد وضعیت معیوب شود،
webhookهایی که با نسخه‌های پیشین یک API مطابق انتظار کار می‌کردند،
ممکن است نتوانند با تغییرات جدیدتر آن API سازگار شوند. این امر ممکن است
پس از ارتقای کلاسترهایتان به نسخه‌های جدیدتر، به رفتار غیرمنتظره منجر شود.

این صفحه سناریوهای رایج خرابی webhook و نحوهٔ پرهیز از آن‌ها را با
طراحی و پیاده‌سازی محتاطانه و سنجیدهٔ webhookها شرح می‌دهد.

## تشخیص اینکه آیا از admission webhookها استفاده می‌کنید {#identify-admission-webhooks}

حتی اگر admission webhookهای خودتان را اجرا نکنید، برخی برنامه‌های شخص ثالث
که در کلاسترهایتان اجرا می‌کنید ممکن است از mutating یا validating admission
webhookها استفاده کنند.

برای بررسی اینکه آیا کلاستر شما mutating admission webhookای دارد، فرمان
زیر را اجرا کنید:

```shell
kubectl get mutatingwebhookconfigurations
```
خروجی، همهٔ mutating admission controllerهای موجود در کلاستر را فهرست می‌کند.

برای بررسی اینکه آیا کلاستر شما validating admission webhookای دارد، فرمان
زیر را اجرا کنید:

```shell
kubectl get validatingwebhookconfigurations
```
خروجی، همهٔ validating admission controllerهای موجود در کلاستر را فهرست می‌کند.

## کارایی و تأخیر {#performance-latency}

این بخش توصیه‌هایی را برای بهبود کارایی و کاهش
تأخیر شرح می‌دهد. به‌طور خلاصه، این توصیه‌ها عبارت‌اند از:

* webhookها را ادغام کنید و تعداد فراخوانی‌های API در هر webhook را محدود کنید.
* از لاگ‌های ممیزی برای یافتن webhookهایی که به‌طور مکرر یک کار یکسان را انجام می‌دهند استفاده کنید.
* برای دسترس‌پذیری webhook از متعادل‌سازی بار استفاده کنید.
* برای هر webhook مقدار مهلت زمانی (timeout) کوچکی تعیین کنید.
* نیازهای دسترس‌پذیری کلاستر را در طراحی webhook در نظر بگیرید.

### طراحی admission webhookها برای تأخیر کم {#design-admission-webhooks-low-latency}

mutating admission webhookها به‌صورت متوالی فراخوانی می‌شوند. بسته به پیکربندی
mutating webhookها، برخی webhookها ممکن است چندین بار فراخوانی شوند. هر فراخوانی mutating
webhook تأخیری به فرایند پذیرش می‌افزاید. این برخلاف validating
webhookهاست که به‌صورت موازی فراخوانی می‌شوند.

هنگام طراحی mutating webhookها، نیازمندی‌ها و میزان تحمل تأخیر خود را
در نظر بگیرید. هرچه تعداد mutating webhookها در کلاستر شما بیشتر باشد،
احتمال افزایش تأخیر بیشتر است.

برای کاهش تأخیر، موارد زیر را در نظر بگیرید:

* webhookهایی را که تغییر مشابهی را روی آبجکت‌های مختلف انجام می‌دهند ادغام کنید.
* تعداد فراخوانی‌های API در منطق سرور mutating webhook را کاهش دهید.
* شرایط تطبیق هر mutating webhook را محدود کنید تا تعداد
  webhookهایی که با یک درخواست API مشخص فعال می‌شوند کاهش یابد.
* webhookهای کوچک را در یک سرور و پیکربندی واحد ادغام کنید تا به
  ترتیب‌دهی و سازمان‌دهی کمک شود.

### جلوگیری از حلقه‌های ناشی از کنترل‌کننده‌های رقیب {#prevent-loops-competing-controllers}

هر مؤلفهٔ دیگری را که در کلاستر شما اجرا می‌شود و ممکن است با
تغییراتی که webhook شما ایجاد می‌کند تعارض داشته باشد در نظر بگیرید. برای نمونه، اگر webhook شما برچسبی اضافه کند
که کنترل‌کنندهٔ دیگری آن را حذف می‌کند، webhook شما دوباره فراخوانی می‌شود. این امر
به یک حلقه منجر می‌شود.

برای تشخیص این حلقه‌ها، موارد زیر را امتحان کنید:

1.  سیاست ممیزی کلاستر خود را به‌روزرسانی کنید تا رویدادهای ممیزی را ثبت کند. از
    پارامترهای زیر استفاده کنید:
    
      * `level`: `RequestResponse`
      * `verbs`: `["patch"]`
      * `omitStages`: `RequestReceived`

    قاعدهٔ ممیزی را طوری تنظیم کنید که برای منابع مشخصی که webhook شما
    تغییر می‌دهد رویداد ایجاد کند.

1.  رویدادهای ممیزی خود را برای یافتن webhookهایی بررسی کنید که چندین بار با
    اعمال یک وصلهٔ (patch) یکسان روی یک آبجکت یکسان دوباره فراخوانی می‌شوند، یا آبجکتی که
    یکی از فیلدهایش چندین بار به‌روزرسانی و بازگردانده می‌شود.

### تعیین مقدار مهلت زمانی کوچک {#small-timeout}

admission webhookها باید تا حد امکان سریع ارزیابی شوند (معمولاً در حد
میلی‌ثانیه)، زیرا به تأخیر درخواست‌های API می‌افزایند. برای webhookها از مهلت زمانی
کوچکی استفاده کنید.

برای جزئیات، به
[مهلت‌های زمانی](/docs/reference/access-authn-authz/extensible-admission-controllers/#timeouts) مراجعه کنید.

### استفاده از متعادل‌کنندهٔ بار برای تضمین دسترس‌پذیری webhook {#load-balancer-webhook}

admission webhookها باید از شکلی از متعادل‌سازی بار بهره بگیرند تا دسترس‌پذیری بالا
و مزایای کارایی را فراهم کنند. اگر یک webhook درون
کلاستر اجرا می‌شود، می‌توانید چندین backend برای webhook را پشت یک Service از نوع
`ClusterIP` اجرا کنید.

### استفاده از مدل استقرار با دسترس‌پذیری بالا {#ha-deployment}

هنگام طراحی webhook خود، نیازمندی‌های دسترس‌پذیری کلاستر را در نظر بگیرید.
برای نمونه، در زمان از کار افتادن نودها یا قطعی‌های یک ناحیه، کوبرنتیز Podها را
`NotReady` علامت‌گذاری می‌کند تا متعادل‌کننده‌های بار بتوانند ترافیک را به نواحی و
نودهای در دسترس هدایت کنند. این به‌روزرسانی‌های Podها ممکن است mutating webhookهای شما را فعال کنند. بسته به
تعداد Podهای متأثر، سرور mutating webhook در معرض خطر اتمام مهلت زمانی
یا ایجاد تأخیر در پردازش Podها قرار می‌گیرد. در نتیجه، ترافیک به آن سرعتی که نیاز دارید
بازمسیریابی نمی‌شود.

هنگام نوشتن webhookهای خود، وضعیت‌هایی مانند مثال پیشین را در نظر بگیرید.
عملیاتی را که نتیجهٔ واکنش کوبرنتیز به رویدادهای اجتناب‌ناپذیر است
مستثنا کنید.

## پالایش درخواست‌ها {#request-filtering}

این بخش توصیه‌هایی را برای پالایش اینکه کدام درخواست‌ها
webhookهای مشخصی را فعال کنند ارائه می‌دهد. به‌طور خلاصه، این توصیه‌ها عبارت‌اند از:

* دامنهٔ webhook را محدود کنید تا اجزای سیستمی و درخواست‌های فقط‌خواندنی را در بر نگیرد.
* webhookها را به فضاهای نام مشخصی محدود کنید.
* از شرایط تطبیق (match conditions) برای پالایش ریزدانه‌ی درخواست‌ها استفاده کنید.
* همهٔ نسخه‌های یک آبجکت را تطبیق دهید.

### محدود کردن دامنهٔ هر webhook {#webhook-limit-scope}

admission webhookها تنها زمانی فراخوانی می‌شوند که یک درخواست API با پیکربندی
webhook متناظر مطابقت داشته باشد. دامنهٔ هر webhook را محدود کنید تا فراخوانی‌های غیرضروری
سرور webhook کاهش یابد. محدودیت‌های دامنهٔ زیر را در نظر بگیرید:

* از تطبیق آبجکت‌های فضای نام `kube-system` پرهیز کنید. اگر Podهای خودتان را
  در فضای نام `kube-system` اجرا می‌کنید، از یک
  [`objectSelector`](/docs/reference/access-authn-authz/extensible-admission-controllers/#matching-requests-objectselector)
  استفاده کنید تا از تغییر یک بار کاری حیاتی جلوگیری شود.
* leaseهای نود را که به‌صورت آبجکت‌های Lease در فضای نام سیستمی
  `kube-node-lease` وجود دارند تغییر ندهید. تغییر leaseهای نود ممکن است به
  شکست ارتقای نودها منجر شود. تنها زمانی کنترل‌های اعتبارسنجی را روی آبجکت‌های Lease در این
  فضای نام اعمال کنید که مطمئن باشید این کنترل‌ها کلاستر شما را به خطر
  نمی‌اندازند.
* TokenReview، SubjectAccessReview یا سایر
  [منابع مجازی احراز هویت و مجوزدهی](/docs/reference/access-authn-authz/extensible-admission-controllers/#excluded-virtual-resources) را تطبیق ندهید.
  این‌ها همیشه درخواست‌های فقط‌خواندنی هستند و رهگیری آن‌ها ممکن است کلاستر شما را
  مختل کند. از کوبرنتیز v1.37 به بعد، admission webhookها به‌طور پیش‌فرض برای
  این منابع فراخوانی نمی‌شوند.
* هر webhook را با استفاده از یک
  [`namespaceSelector`](/docs/reference/access-authn-authz/extensible-admission-controllers/#matching-requests-namespaceselector) به یک فضای نام مشخص محدود کنید.

### پالایش درخواست‌های مشخص با استفاده از شرایط تطبیق {#filter-match-conditions}

کنترل‌کننده‌های پذیرش از چندین فیلد پشتیبانی می‌کنند که می‌توانید از آن‌ها برای تطبیق درخواست‌هایی
که معیارهای مشخصی را برآورده می‌کنند استفاده کنید. برای نمونه، می‌توانید از یک `namespaceSelector` برای
پالایش درخواست‌هایی که یک فضای نام مشخص را هدف قرار می‌دهند استفاده کنید.

برای پالایش ریزدانه‌تر درخواست‌ها، از فیلد `matchConditions` در
پیکربندی webhook خود استفاده کنید. این فیلد به شما اجازه می‌دهد چندین عبارت CEL بنویسید که
برای اینکه یک درخواست admission webhook شما را فعال کند، همگی باید به `true` ارزیابی شوند. استفاده از
`matchConditions` ممکن است تعداد فراخوانی‌های سرور webhook شما را به‌طور چشمگیری
کاهش دهد.

برای جزئیات، به
[تطبیق درخواست‌ها: `matchConditions`](/docs/reference/access-authn-authz/extensible-admission-controllers/#matching-requests-matchconditions) مراجعه کنید.

### تطبیق همهٔ نسخه‌های یک API {#match-all-versions}

به‌طور پیش‌فرض، admission webhookها روی همهٔ نسخه‌های API که یک منبع مشخص را
تحت تأثیر قرار می‌دهند اجرا می‌شوند. فیلد `matchPolicy` در پیکربندی webhook این
رفتار را کنترل می‌کند. مقدار `Equivalent` را در فیلد `matchPolicy` تعیین کنید یا
این فیلد را حذف کنید تا webhook بتواند روی هر نسخه‌ای از API اجرا شود.

برای جزئیات، به
[تطبیق درخواست‌ها: `matchPolicy`](/docs/reference/access-authn-authz/extensible-admission-controllers/#matching-requests-matchpolicy) مراجعه کنید.

## دامنهٔ تغییر و ملاحظات فیلدها {#mutation-scope-considerations}

این بخش توصیه‌هایی را دربارهٔ دامنهٔ تغییرات و ملاحظات ویژهٔ
فیلدهای آبجکت ارائه می‌دهد. به‌طور خلاصه، این توصیه‌ها عبارت‌اند از:

* تنها فیلدهایی را وصله کنید که نیاز به وصله دارند.
* مقادیر آرایه‌ها را بازنویسی نکنید.
* در صورت امکان، از اثرات جانبی در تغییرات پرهیز کنید.
* از خودتغییری پرهیز کنید.
* در حالت باز شکست بخورید (fail open) و وضعیت نهایی را اعتبارسنجی کنید.
* برای به‌روزرسانی‌های آیندهٔ فیلدها در نسخه‌های بعدی برنامه‌ریزی کنید.
* از فعال‌شدن webhookها توسط خودشان جلوگیری کنید.
* آبجکت‌های تغییرناپذیر را تغییر ندهید.

### وصله‌کردن تنها فیلدهای لازم {#patch-required-fields}

سرورهای admission webhook پاسخ‌های HTTP ارسال می‌کنند تا نشان دهند با یک
درخواست مشخص API کوبرنتیز چه باید کرد. این پاسخ یک آبجکت AdmissionReview است.
یک mutating webhook می‌تواند با استفاده از فیلد `patchType` و فیلد `patch` در پاسخ،
فیلدهای مشخصی را برای تغییر پیش از اجازهٔ پذیرش اضافه کند. اطمینان حاصل کنید
که تنها فیلدهایی را تغییر می‌دهید که به تغییر نیاز دارند.

برای نمونه، یک mutating webhook را در نظر بگیرید که پیکربندی شده است تا اطمینان حاصل کند
Deploymentهای `web-server` دست‌کم سه نسخهٔ تکثیرشده دارند. هنگامی که درخواستی برای
ایجاد یک آبجکت Deployment با پیکربندی webhook شما مطابقت دارد، webhook
باید تنها مقدار فیلد `spec.replicas` را به‌روزرسانی کند.

### مقادیر آرایه‌ها را بازنویسی نکنید {#dont-overwrite-arrays}

فیلدهای موجود در مشخصات آبجکت‌های کوبرنتیز ممکن است شامل آرایه باشند. برخی آرایه‌ها
جفت‌های key:value دارند (مانند فیلد `envVar` در مشخصات یک کانتینر)،
در حالی که برخی دیگر بدون کلید هستند (مانند فیلد `readinessGates` در مشخصات
یک Pod). ترتیب مقادیر در یک فیلد آرایه‌ای ممکن است در برخی
وضعیت‌ها اهمیت داشته باشد. برای نمونه، ترتیب آرگومان‌ها در فیلد `args` مشخصات
یک کانتینر ممکن است بر کانتینر اثر بگذارد.

هنگام تغییر آرایه‌ها، موارد زیر را در نظر بگیرید:

* هر جا که ممکن است، به‌جای `replace` از عملیات JSONPatch با نام `add` استفاده کنید تا
  از جایگزینی تصادفی یک مقدار لازم جلوگیری شود.
* با آرایه‌هایی که از جفت‌های key:value استفاده نمی‌کنند همچون مجموعه (set) رفتار کنید.
* اطمینان حاصل کنید که لازم نیست مقادیر فیلدی که تغییر می‌دهید
  ترتیب مشخصی داشته باشند.
* جفت‌های key:value موجود را بازنویسی نکنید، مگر در صورت ضرورت مطلق.
* هنگام تغییر فیلدهای برچسب احتیاط کنید. یک تغییر تصادفی ممکن است
  باعث از کار افتادن انتخابگرهای برچسب شود و به رفتار ناخواسته بینجامد.

### پرهیز از اثرات جانبی {#avoid-side-effects}

اطمینان حاصل کنید که webhookهای شما تنها روی محتوای AdmissionReview
ارسال‌شده به آن‌ها عمل می‌کنند و تغییرات خارج از این مسیر (out-of-band) ایجاد نمی‌کنند. این تغییرات
اضافی که _اثرات جانبی_ (side effects) نامیده می‌شوند، اگر به‌درستی هماهنگ نشوند
ممکن است در طول پذیرش تعارض ایجاد کنند. اگر یک webhook هیچ اثر جانبی‌ای نداشته باشد،
فیلد `.webhooks[].sideEffects` باید برابر با `None` تنظیم شود.

اگر اثرات جانبی در طول ارزیابی پذیرش لازم باشند، باید هنگام
پردازش آبجکت AdmissionReview‌ای که `dryRun` آن برابر با `true` است سرکوب شوند،
و فیلد `.webhooks[].sideEffects` باید برابر با `NoneOnDryRun` تنظیم شود.

برای جزئیات، به
[اثرات جانبی](/docs/reference/access-authn-authz/extensible-admission-controllers/#side-effects) مراجعه کنید.

### پرهیز از خودتغییری {#avoid-self-mutation}

webhookای که درون کلاستر اجرا می‌شود، اگر طوری پیکربندی شده باشد که منابع لازم برای
راه‌اندازی Podهای خودش را رهگیری کند، ممکن است برای استقرار خودش بن‌بست (deadlock)
ایجاد کند.

برای نمونه، یک mutating admission webhook پیکربندی شده است تا درخواست‌های **create** برای Pod
را تنها در صورتی بپذیرد که برچسب مشخصی (مانند `env: prod`) در Pod تنظیم شده باشد.
سرور webhook در یک Deployment اجرا می‌شود که برچسب `env` را تنظیم نمی‌کند.

هنگامی که نودی که Podهای سرور webhook را اجرا می‌کند ناسالم می‌شود، Deployment
مربوط به webhook تلاش می‌کند Podها را روی نود دیگری دوباره زمان‌بندی کند. با این حال، سرور
webhook موجود درخواست‌ها را رد می‌کند، زیرا برچسب `env` تنظیم نشده است. در
نتیجه، جابه‌جایی نمی‌تواند انجام شود.

فضای نامی را که webhook شما در آن اجرا می‌شود با یک
[`namespaceSelector`](/docs/reference/access-authn-authz/extensible-admission-controllers/#matching-requests-namespaceselector) مستثنا کنید.

### پرهیز از حلقه‌های وابستگی {#avoid-dependency-loops}

حلقه‌های وابستگی ممکن است در سناریوهایی مانند موارد زیر رخ دهند:

* دو webhook، Podهای یکدیگر را بررسی می‌کنند. اگر هر دو webhook هم‌زمان
  در دسترس نباشند، هیچ‌یک از آن‌ها نمی‌تواند راه‌اندازی شود.
* webhook شما اجزای افزونه‌ای کلاستر، مانند افزونه‌های شبکه
  یا افزونه‌های ذخیره‌سازی، را که webhook شما به آن‌ها وابسته است رهگیری می‌کند. اگر هم webhook و هم
  افزونهٔ وابسته در دسترس نباشند، هیچ‌یک از این دو مؤلفه نمی‌تواند کار کند.

برای پرهیز از این حلقه‌های وابستگی، موارد زیر را امتحان کنید:

* از
  [ValidatingAdmissionPolicyها](/docs/reference/access-authn-authz/validating-admission-policy/)
  استفاده کنید تا از ایجاد وابستگی‌ها پرهیز شود.
* از اعتبارسنجی یا تغییر webhookهای دیگر توسط webhookها جلوگیری کنید.
  [مستثنا کردن فضاهای نام مشخص](/docs/reference/access-authn-authz/extensible-admission-controllers/#matching-requests-namespaceselector)
  از فعال‌سازی webhook خود را در نظر بگیرید.
* با استفاده از یک
  [`objectSelector`](/docs/reference/access-authn-authz/extensible-admission-controllers/#matching-requests-objectselector) از عمل‌کردن webhookهای خود روی افزونه‌های وابسته جلوگیری کنید.

### شکست در حالت باز و اعتبارسنجی وضعیت نهایی {#fail-open-validate-final-state}

mutating admission webhookها از فیلد پیکربندی `failurePolicy` پشتیبانی می‌کنند.
این فیلد نشان می‌دهد که اگر webhook شکست بخورد، سرور API باید درخواست را بپذیرد یا
رد کند. شکست webhook ممکن است به دلیل اتمام مهلت زمانی یا خطاهای
منطق سرور رخ دهد.

به‌طور پیش‌فرض، admission webhookها فیلد `failurePolicy` را برابر با Fail قرار می‌دهند. سرور API
در صورت شکست webhook، درخواست را رد می‌کند. با این حال، رد کردن درخواست‌ها به‌طور
پیش‌فرض ممکن است باعث شود درخواست‌های منطبق با سیاست‌ها نیز در زمان از کار افتادن webhook
رد شوند.

با تنظیم فیلد `failurePolicy` برابر با Ignore، اجازه دهید mutating webhookهای شما «در حالت باز شکست بخورند»
(fail open). از یک کنترل‌کنندهٔ اعتبارسنج برای بررسی وضعیت درخواست‌ها استفاده کنید تا اطمینان حاصل شود
با سیاست‌های شما مطابقت دارند.

این رویکرد مزایای زیر را دارد:

* از کار افتادن mutating webhook مانع استقرار منابع منطبق با سیاست‌ها نمی‌شود.
* اعمال سیاست در طول کنترل پذیرش اعتبارسنج انجام می‌شود.
* mutating webhookها با دیگر کنترل‌کننده‌های کلاستر تداخل ندارند.

### برنامه‌ریزی برای به‌روزرسانی‌های آیندهٔ فیلدها {#plan-future-field-updates}

به‌طور کلی، webhookهای خود را با این فرض طراحی کنید که APIهای کوبرنتیز ممکن است
در نسخه‌های بعدی تغییر کنند. سروری ننویسید که پایداری یک
API را مسلم فرض کند. برای نمونه، انتشار کانتینرهای sidecar در کوبرنتیز
فیلد `restartPolicy` را به API مربوط به Pod اضافه کرد.

### جلوگیری از فعال‌شدن webhook توسط خودش {#prevent-webhook-self-trigger}

mutating webhookهایی که به طیف گسترده‌ای از درخواست‌های API پاسخ می‌دهند ممکن است
ناخواسته خودشان را فعال کنند. برای نمونه، webhookای را در نظر بگیرید که
به همهٔ درخواست‌های کلاستر پاسخ می‌دهد. اگر webhook را طوری پیکربندی کنید که برای هر تغییر،
آبجکت‌های Event ایجاد کند، به درخواست‌های ایجاد آبجکت‌های Event خودش
پاسخ خواهد داد.

برای پرهیز از این وضعیت، تنظیم یک برچسب یکتا روی همهٔ منابعی که
webhook شما ایجاد می‌کند را در نظر بگیرید. این برچسب را از شرایط تطبیق webhook خود مستثنا کنید.

### آبجکت‌های تغییرناپذیر را تغییر ندهید {#dont-change-immutable-objects}

برخی از آبجکت‌های کوبرنتیز در سرور API نمی‌توانند تغییر کنند. برای نمونه، هنگامی که
یک {{< glossary_tooltip text="Pod ایستا" term_id="static-pod" >}} مستقر می‌کنید،
kubelet روی نود یک
{{< glossary_tooltip text="Pod آینه‌ای" term_id="mirror-pod" >}} در سرور
API ایجاد می‌کند تا Pod ایستا را دنبال کند. با این حال، تغییرات در Pod آینه‌ای
به Pod ایستا منتقل نمی‌شوند.

در طول پذیرش، برای تغییر این آبجکت‌ها تلاش نکنید. همهٔ Podهای آینه‌ای
حاشیه‌نویسی `kubernetes.io/config.mirror` را دارند. برای مستثنا کردن Podهای آینه‌ای و در عین حال کاهش
خطر امنیتی نادیده‌گرفتن یک حاشیه‌نویسی، اجازه دهید Podهای ایستا تنها در
فضاهای نام مشخصی اجرا شوند.

## ترتیب و خودتوانی (idempotence) در mutating webhookها {#ordering-idempotence}

این بخش توصیه‌هایی را دربارهٔ ترتیب webhookها و طراحی webhookهای خودتوان (idempotent)
ارائه می‌دهد. به‌طور خلاصه، این توصیه‌ها عبارت‌اند از:

* به ترتیب اجرای مشخصی متکی نباشید.
* تغییرات را پیش از پذیرش اعتبارسنجی کنید.
* بررسی کنید که آیا تغییرات شما توسط کنترل‌کننده‌های دیگر بازنویسی می‌شوند.
* اطمینان حاصل کنید که مجموعهٔ mutating webhookها خودتوان است، نه فقط
  تک‌تک webhookها.

### به ترتیب فراخوانی mutating webhookها متکی نباشید {#dont-rely-webhook-order}

mutating admission webhookها با ترتیب ثابتی اجرا نمی‌شوند. عوامل گوناگونی
ممکن است زمان فراخوانی یک webhook مشخص را تغییر دهند. به اجرای webhook خود
در نقطهٔ مشخصی از فرایند پذیرش متکی نباشید. webhookهای دیگر همچنان ممکن است
آبجکت تغییرداده‌شدهٔ شما را تغییر دهند.

توصیه‌های زیر ممکن است به کمینه‌کردن خطر تغییرات ناخواسته
کمک کنند:

* [تغییرات را پیش از پذیرش اعتبارسنجی کنید](#validate-mutations)
* از یک سیاست فراخوانی مجدد (reinvocation policy) استفاده کنید تا تغییرات آبجکت توسط افزونه‌های دیگر را مشاهده کنید
  و در صورت نیاز webhook را دوباره اجرا کنید. برای جزئیات، به
  [سیاست فراخوانی مجدد](/docs/reference/access-authn-authz/extensible-admission-controllers/#reinvocation-policy) مراجعه کنید.

### اطمینان از خودتوان بودن mutating webhookهای کلاستر {#ensure-mutating-webhook-idempotent}

هر mutating admission webhook باید _خودتوان_ (idempotent) باشد. webhook باید
بتواند روی آبجکتی که قبلاً تغییر داده است اجرا شود، بدون آنکه فراتر از تغییر اولیه،
تغییرات بیشتری ایجاد کند.

افزون بر این، همهٔ mutating webhookهای کلاستر شما باید به‌عنوان یک
مجموعه خودتوان باشند. پس از پایان مرحلهٔ تغییر در کنترل پذیرش،
هر mutating webhook منفرد باید بتواند روی یک آبجکت اجرا شود بدون آنکه
تغییرات بیشتری در آن آبجکت ایجاد کند.

بسته به محیط شما، تضمین خودتوانی در مقیاس بزرگ ممکن است
دشوار باشد. توصیه‌های زیر ممکن است کمک کنند:

* از کنترل‌کننده‌های پذیرش اعتبارسنج برای تأیید وضعیت نهایی
  بارهای کاری حیاتی استفاده کنید.
* استقرارهای خود را در یک کلاستر آزمایشی (staging) بیازمایید تا ببینید آیا آبجکتی
  چندین بار توسط یک webhook یکسان تغییر می‌کند یا نه.
* اطمینان حاصل کنید که دامنهٔ هر mutating webhook مشخص و محدود است.

نمونه‌های زیر منطق تغییر خودتوان را نشان می‌دهند:

1. برای یک درخواست **create** مربوط به Pod، فیلد
  `.spec.securityContext.runAsNonRoot` آن Pod را برابر با true قرار دهید.

1. برای یک درخواست **create** مربوط به Pod، اگر فیلد
   `.spec.containers[].resources.limits` یک کانتینر تنظیم نشده باشد، محدودیت‌های منابع
   پیش‌فرض را تنظیم کنید.

1. برای یک درخواست **create** مربوط به Pod، اگر کانتینری با نام `foo-sidecar` از قبل وجود نداشته باشد،
   یک کانتینر sidecar با نام `foo-sidecar` تزریق کنید.

در این موارد، webhook را می‌توان با ایمنی دوباره فراخوانی کرد، یا می‌تواند آبجکتی را بپذیرد که
فیلدهایش از قبل تنظیم شده‌اند.

نمونه‌های زیر منطق تغییر غیرخودتوان را نشان می‌دهند:

1. برای یک درخواست **create** مربوط به Pod، یک کانتینر sidecar با نام
   `foo-sidecar` به‌همراه پسوندی از مُهر زمانی فعلی (مانند
   `foo-sidecar-19700101-000000`) تزریق کنید.

   فراخوانی مجدد webhook ممکن است باعث شود همان sidecar چندین بار
   در یک Pod تزریق شود، هر بار با نام کانتینر متفاوت. به همین ترتیب،
   اگر sidecar از قبل در پادی که کاربر ارائه کرده وجود داشته باشد، webhook ممکن است کانتینرهای تکراری تزریق کند.

1. برای یک درخواست **create**/**update** مربوط به Pod، اگر Pod برچسب `env`
   را داشته باشد آن را رد کنید، و در غیر این صورت برچسب `env: prod` را به Pod اضافه کنید.

   فراخوانی مجدد webhook باعث می‌شود webhook روی خروجی خودش شکست بخورد.

1. برای یک درخواست **create** مربوط به Pod، بدون بررسی اینکه آیا کانتینر `foo-sidecar`
   وجود دارد یا نه، یک کانتینر sidecar با نام `foo-sidecar` اضافه کنید.

   فراخوانی مجدد webhook به کانتینرهای تکراری در Pod منجر می‌شود که
   درخواست را نامعتبر می‌کند و سرور API آن را رد می‌کند.

## آزمون و اعتبارسنجی تغییرات {#mutation-testing-validation}

این بخش توصیه‌هایی را برای آزمودن mutating webhookها و
اعتبارسنجی آبجکت‌های تغییریافته ارائه می‌دهد. به‌طور خلاصه، این توصیه‌ها عبارت‌اند از:

* webhookها را در محیط‌های آزمایشی (staging) بیازمایید.
* از تغییراتی که اعتبارسنجی‌ها را نقض می‌کنند پرهیز کنید.
* ارتقاهای نسخهٔ فرعی (minor) را از نظر پسرفت‌ها و تعارض‌ها بیازمایید.
* آبجکت‌های تغییریافته را پیش از پذیرش اعتبارسنجی کنید.

### آزمودن webhookها در محیط‌های آزمایشی {#test-in-staging-environments}

آزمون جامع باید بخش اصلی چرخهٔ انتشار برای webhookهای جدید یا به‌روزشده
باشد. در صورت امکان، هر تغییری در webhookهای کلاستر خود را در یک محیط آزمایشی
که شباهت زیادی به کلاسترهای تولیدی شما دارد بیازمایید. دست‌کم،
استفاده از ابزاری مانند [minikube](https://minikube.sigs.k8s.io/docs/) یا
[kind](https://kind.sigs.k8s.io/) را برای ایجاد یک کلاستر آزمایشی کوچک برای تغییرات webhook
در نظر بگیرید.

### اطمینان از اینکه تغییرات اعتبارسنجی‌ها را نقض نمی‌کنند {#ensure-mutations-dont-violate-validations}

mutating webhookهای شما نباید هیچ‌یک از اعتبارسنجی‌هایی را که پیش از پذیرش روی یک
آبجکت اعمال می‌شوند نقض کنند. برای نمونه، mutating webhookای را در نظر بگیرید که
درخواست پیش‌فرض CPU یک Pod را برابر با مقدار مشخصی قرار می‌دهد. اگر محدودیت CPU آن Pod
روی مقداری کمتر از درخواست تغییریافته تنظیم شده باشد، Pod در پذیرش شکست می‌خورد.

هر mutating webhook را در برابر اعتبارسنجی‌هایی که در کلاستر شما اجرا می‌شوند بیازمایید.

### آزمودن ارتقاهای نسخهٔ فرعی برای اطمینان از رفتار سازگار {#test-minor-version-upgrades}

پیش از ارتقای کلاسترهای تولیدی خود به یک نسخهٔ فرعی جدید، webhookها
و بارهای کاری خود را در یک محیط آزمایشی بیازمایید. نتایج را مقایسه کنید تا اطمینان حاصل شود
که webhookهای شما پس از ارتقا همچنان مطابق انتظار کار می‌کنند.

افزون بر این، از منابع زیر برای آگاهی از تغییرات API استفاده کنید:

* [یادداشت‌های انتشار کوبرنتیز](/releases/)
* [وبلاگ کوبرنتیز](/blog/)

### اعتبارسنجی تغییرات پیش از پذیرش {#validate-mutations}

mutating webhookها پیش از اجرای هر validating webhookای تا پایان اجرا می‌شوند. هیچ
ترتیب پایداری برای اعمال تغییرات روی آبجکت‌ها وجود ندارد. در نتیجه،
تغییرات شما ممکن است توسط mutating webhookای که در زمان بعدی اجرا می‌شود بازنویسی شوند.

یک کنترل‌کنندهٔ پذیرش اعتبارسنج مانند ValidatingAdmissionWebhook یا
ValidatingAdmissionPolicy به کلاستر خود اضافه کنید تا اطمینان حاصل شود تغییرات شما
همچنان وجود دارند. برای نمونه، mutating webhookای را در نظر بگیرید که فیلد
`restartPolicy: Always` را به init containerهای مشخصی اضافه می‌کند تا آن‌ها به‌صورت
کانتینرهای sidecar اجرا شوند. می‌توانید یک validating webhook اجرا کنید تا اطمینان حاصل شود که آن
init containerها پس از تکمیل همهٔ تغییرات، پیکربندی `restartPolicy: Always` را
حفظ کرده‌اند.

برای جزئیات، به منابع زیر مراجعه کنید:

* [Validating Admission Policy](/docs/reference/access-authn-authz/validating-admission-policy/)
* [ValidatingAdmissionWebhookها](/docs/reference/access-authn-authz/admission-controllers/#validatingadmissionwebhook)

## استقرار mutating webhook {#mutating-webhook-deployment}

این بخش توصیه‌هایی را برای استقرار mutating admission
webhookها ارائه می‌دهد. به‌طور خلاصه، این توصیه‌ها عبارت‌اند از:

* پیکربندی webhook را به‌تدریج منتشر کنید و مشکلات را به تفکیک
  فضای نام پایش کنید.
* دسترسی ویرایش منابع پیکربندی webhook را محدود کنید.
* اگر سرور webhook درون کلاستر است، دسترسی به فضای نامی که سرور webhook را اجرا می‌کند
  محدود کنید.

### نصب و فعال‌سازی یک mutating webhook {#install-enable-mutating-webhook}

هنگامی که آمادهٔ استقرار mutating webhook خود در یک کلاستر هستید، عملیات را به
ترتیب زیر انجام دهید:

1.  سرور webhook را نصب و راه‌اندازی کنید.
1.  فیلد `failurePolicy` را در مانیفست MutatingWebhookConfiguration
    برابر با Ignore قرار دهید. این کار به شما امکان می‌دهد از اختلال‌های ناشی از webhookهای نادرست‌پیکربندی‌شده پرهیز کنید.
1.  فیلد `namespaceSelector` را در مانیفست MutatingWebhookConfiguration
    برابر با یک فضای نام آزمایشی قرار دهید.
1.  MutatingWebhookConfiguration را در کلاستر خود مستقر کنید.

webhook را در فضای نام آزمایشی پایش کنید تا هر مشکلی را بیابید، سپس
webhook را در فضاهای نام دیگر منتشر کنید. اگر webhook درخواست API‌ای را رهگیری کند که
قرار نبوده رهگیری کند، انتشار را متوقف کنید و دامنهٔ پیکربندی
webhook را اصلاح کنید.

### محدود کردن دسترسی ویرایش به mutating webhookها {#limit-edit-access}

mutating webhookها کنترل‌کننده‌های قدرتمندی در کوبرنتیز هستند. از RBAC یا سازوکار
مجوزدهی دیگری برای محدود کردن دسترسی به پیکربندی‌ها و سرورهای webhook خود استفاده کنید.
در RBAC، اطمینان حاصل کنید که دسترسی‌های زیر تنها در اختیار موجودیت‌های قابل‌اعتماد
قرار دارند:

* فعل‌ها (Verbs): **create**، **update**، **patch**، **delete**، **deletecollection**
* گروه API: `admissionregistration.k8s.io/v1`
* نوع API: MutatingWebhookConfigurations

اگر سرور mutating webhook شما در کلاستر اجرا می‌شود، دسترسی برای ایجاد یا
تغییر هر منبعی در آن فضای نام را محدود کنید.
