شبکه‌بندی بخش اصلی کوبرنتیز است، اما درک دقیق شیوهٔ کارکرد مورد انتظار آن می‌تواند دشوار باشد. در این زمینه باید به چهار مسئلهٔ متمایز شبکه پرداخت:

1. ارتباط بسیار تنگاتنگ کانتینر با کانتینر: این مسئله با {{< glossary_tooltip text="Podها" term_id="pod" >}} و ارتباط از طریق `localhost` حل می‌شود.
2. ارتباط Pod با Pod: تمرکز اصلی این سند بر همین مسئله است.
3. ارتباط Pod با Service: این مسئله در [Serviceها](/docs/concepts/services-networking/service/) پوشش داده شده است.
4. ارتباط بیرون از کلاستر با Service: این مسئله نیز در Serviceها پوشش داده شده است.

<!-- body -->

جوهرهٔ کوبرنتیز اشتراک ماشین‌ها میان برنامه‌هاست. معمولاً اشتراک ماشین‌ها مستلزم آن است که اطمینان حاصل شود دو برنامه نمی‌کوشند از پورت‌های یکسانی استفاده کنند. هماهنگ‌کردن پورت‌ها میان چندین توسعه‌دهنده در مقیاس بزرگ بسیار دشوار است و کاربران را در معرض مشکلاتی در سطح کلاستر قرار می‌دهد که خارج از کنترل آن‌هاست.

تخصیص پویای پورت پیچیدگی‌های فراوانی به سیستم تحمیل می‌کند: هر برنامه باید پورت‌ها را به‌صورت flag دریافت کند، سرورهای API باید بدانند چگونه شماره‌های پورت پویا را در بلوک‌های پیکربندی درج کنند، سرویس‌ها باید بدانند چگونه یکدیگر را پیدا کنند و مانند آن. کوبرنتیز به‌جای درگیرشدن با این مسائل، رویکرد متفاوتی در پیش می‌گیرد.

برای آشنایی با مدل شبکهٔ کوبرنتیز، [این صفحه](/docs/concepts/services-networking/) را ببینید.

## بازه‌های نشانی IP در کوبرنتیز

کلاسترهای کوبرنتیز باید برای Podها، Serviceها و نودها نشانی‌های IP غیرهم‌پوشان تخصیص دهند. این نشانی‌ها از بازه‌ای از نشانی‌های در دسترس برداشته می‌شوند که در مؤلفه‌های زیر پیکربندی شده است:

- افزونهٔ شبکه برای تخصیص نشانی IP به Podها پیکربندی می‌شود.
- مؤلفهٔ kube-apiserver برای تخصیص نشانی IP به Serviceها پیکربندی می‌شود.
- مؤلفهٔ kubelet یا cloud-controller-manager برای تخصیص نشانی IP به نودها پیکربندی می‌شود.

## انواع شبکه‌بندی کلاستر {#cluster-network-ipfamilies}

کلاسترهای کوبرنتیز را می‌توان بر اساس خانواده‌های IP پیکربندی‌شده در دسته‌های زیر قرار داد:

- فقط IPv4: افزونهٔ شبکه، kube-apiserver و kubelet/cloud-controller-manager طوری پیکربندی شده‌اند که فقط نشانی‌های IPv4 تخصیص دهند.
- فقط IPv6: افزونهٔ شبکه، kube-apiserver و kubelet/cloud-controller-manager طوری پیکربندی شده‌اند که فقط نشانی‌های IPv6 تخصیص دهند.
- [دوپشته‌ای (dual-stack)](/docs/concepts/services-networking/dual-stack/) به‌صورت IPv4/IPv6 یا IPv6/IPv4:
  - افزونهٔ شبکه برای تخصیص نشانی‌های IPv4 و IPv6 پیکربندی شده است.
  - مؤلفهٔ kube-apiserver برای تخصیص نشانی‌های IPv4 و IPv6 پیکربندی شده است.
  - مؤلفهٔ kubelet یا cloud-controller-manager برای تخصیص نشانی‌های IPv4 و IPv6 پیکربندی شده است.
  - همهٔ مؤلفه‌ها باید بر سر خانوادهٔ IP اصلی پیکربندی‌شده توافق داشته باشند.

کلاسترهای کوبرنتیز فقط خانواده‌های IP موجود در آبجکت‌های Pod، Service و Node را در نظر می‌گیرند و به IPهای واقعی موجودیت‌هایی که این آبجکت‌ها نمایندهٔ آن‌ها هستند کاری ندارند. برای نمونه، یک سرور یا یک پاد ممکن است چندین نشانی IP روی رابط‌های خود داشته باشد، اما هنگام پیاده‌سازی مدل شبکهٔ کوبرنتیز و تعیین نوع کلاستر، فقط نشانی‌های IP موجود در `node.status.addresses` یا `pod.status.ips` در نظر گرفته می‌شوند.

## چگونه مدل شبکهٔ کوبرنتیز را پیاده‌سازی کنیم

مدل شبکه را محیط اجرای کانتینر روی هر نود پیاده‌سازی می‌کند. رایج‌ترین محیط‌های اجرای کانتینر برای مدیریت قابلیت‌های شبکه و امنیتی خود از افزونه‌های [Container Network Interface](https://github.com/containernetworking/cni) (CNI) استفاده می‌کنند. افزونه‌های CNI گوناگونی از فروشندگان مختلف وجود دارد. برخی از آن‌ها فقط قابلیت‌های پایه‌ای مانند افزودن و حذف رابط‌های شبکه را فراهم می‌کنند و برخی دیگر راهکارهای پیشرفته‌تری ارائه می‌دهند، مانند یکپارچگی با دیگر سیستم‌های هماهنگ‌سازی کانتینر، اجرای چندین افزونهٔ CNI، قابلیت‌های پیشرفتهٔ IPAM و مانند آن.

برای دیدن فهرستی ناکامل از افزونه‌های شبکه‌ای که کوبرنتیز پشتیبانی می‌کند، [این صفحه](/docs/concepts/cluster-administration/addons/#networking-and-network-policy) را ببینید.
