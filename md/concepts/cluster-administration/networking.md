شبکه‌بندی بخش اصلی کوبرنتیز است، اما درک دقیق نحوهٔ عملکرد مورد انتظار آن می‌تواند دشوار باشد. چهار مسئلهٔ شبکه‌ای متمایز وجود دارد که باید به آن‌ها پرداخت:

1. ارتباطات کانتینر به کانتینر با وابستگی بسیار زیاد: این مسئله با {{< glossary_tooltip text="Podها" term_id="pod" >}} و ارتباطات `localhost` حل می‌شود.
2. ارتباطات Pod به Pod: تمرکز اصلی این سند بر همین مورد است.
3. ارتباطات Pod به Service: این مورد در [Serviceها](/docs/concepts/services-networking/service/) پوشش داده شده است.
4. ارتباطات بیرون به Service: این مورد نیز در Serviceها پوشش داده شده است.

<!-- body -->

کوبرنتیز بر پایهٔ اشتراک‌گذاری ماشین‌ها میان برنامه‌ها بنا شده است. معمولاً اشتراک‌گذاری ماشین‌ها مستلزم آن است که اطمینان حاصل شود دو برنامه تلاش نمی‌کنند از پورت‌های یکسان استفاده کنند. هماهنگ‌سازی پورت‌ها میان تعداد زیادی توسعه‌دهنده در مقیاس بزرگ بسیار دشوار است و کاربران را با مشکلاتی در سطح کلاستر مواجه می‌کند که خارج از کنترل آن‌هاست.

تخصیص پویای پورت پیچیدگی‌های زیادی به سیستم وارد می‌کند: هر برنامه باید پورت‌ها را به‌صورت flag دریافت کند، API serverها باید بدانند چگونه شماره پورت‌های پویا را در بلوک‌های پیکربندی درج کنند، سرویس‌ها باید بدانند چگونه یکدیگر را پیدا کنند و موارد دیگر. کوبرنتیز به‌جای مواجهه با این پیچیدگی‌ها، رویکردی متفاوت در پیش می‌گیرد.

برای آشنایی با مدل شبکهٔ کوبرنتیز، [اینجا](/docs/concepts/services-networking/) را ببینید.

## بازه‌های آدرس IP در کوبرنتیز

کلاسترهای کوبرنتیز لازم است آدرس‌های IP غیرهم‌پوشان را برای Podها، Serviceها و نودها از بازه‌ای از آدرس‌های در دسترس تخصیص دهند که در مؤلفه‌های زیر پیکربندی می‌شود:

- افزونهٔ شبکه (network plugin) برای تخصیص آدرس‌های IP به Podها پیکربندی می‌شود.
- kube-apiserver برای تخصیص آدرس‌های IP به Serviceها پیکربندی می‌شود.
- kubelet یا cloud-controller-manager برای تخصیص آدرس‌های IP به نودها پیکربندی می‌شود.

## انواع شبکه‌بندی کلاستر {#cluster-network-ipfamilies}

کلاسترهای کوبرنتیز را با توجه به خانواده‌های IP پیکربندی‌شده می‌توان به دسته‌های زیر تقسیم کرد:

- فقط IPv4: افزونهٔ شبکه، kube-apiserver و kubelet/cloud-controller-manager طوری پیکربندی شده‌اند که فقط آدرس‌های IPv4 تخصیص دهند.
- فقط IPv6: افزونهٔ شبکه، kube-apiserver و kubelet/cloud-controller-manager طوری پیکربندی شده‌اند که فقط آدرس‌های IPv6 تخصیص دهند.
- [دوپشته‌ای (dual-stack)](/docs/concepts/services-networking/dual-stack/) IPv4/IPv6 یا IPv6/IPv4:
  - افزونهٔ شبکه برای تخصیص آدرس‌های IPv4 و IPv6 پیکربندی شده است.
  - kube-apiserver برای تخصیص آدرس‌های IPv4 و IPv6 پیکربندی شده است.
  - kubelet یا cloud-controller-manager برای تخصیص آدرس‌های IPv4 و IPv6 پیکربندی شده است.
  - همهٔ مؤلفه‌ها باید بر سر خانوادهٔ IP اصلی پیکربندی‌شده توافق داشته باشند.

کلاسترهای کوبرنتیز فقط خانواده‌های IP موجود در آبجکت‌های Pod، Service و Node را در نظر می‌گیرند، صرف‌نظر از IPهای موجود آبجکت‌های نمایندگی‌شده. برای مثال، یک سرور یا یک Pod می‌تواند چندین آدرس IP تخصیص‌یافته به رابط‌های خود داشته باشد، اما هنگام پیاده‌سازی مدل شبکهٔ کوبرنتیز و تعیین نوع کلاستر، فقط آدرس‌های IP موجود در `node.status.addresses` یا `pod.status.ips` در نظر گرفته می‌شوند.

## نحوهٔ پیاده‌سازی مدل شبکهٔ کوبرنتیز

مدل شبکه توسط container runtime در هر نود پیاده‌سازی می‌شود. رایج‌ترین container runtimeها از افزونه‌های [Container Network Interface](https://github.com/containernetworking/cni) (CNI) برای مدیریت قابلیت‌های شبکه و امنیتی خود استفاده می‌کنند. افزونه‌های CNI متعددی از فروشندگان مختلف وجود دارند. برخی از این‌ها فقط قابلیت‌های پایهٔ افزودن و حذف رابط‌های شبکه را فراهم می‌کنند، در حالی که برخی دیگر راه‌حل‌های پیچیده‌تری ارائه می‌دهند، مانند یکپارچه‌سازی با سایر سیستم‌های ارکستریشن کانتینر، اجرای چندین افزونهٔ CNI، قابلیت‌های پیشرفتهٔ IPAM و موارد مشابه.

برای مشاهدهٔ فهرستی غیرجامع از افزونه‌های شبکه‌ای که کوبرنتیز از آن‌ها پشتیبانی می‌کند، [این صفحه](/docs/concepts/cluster-administration/addons/#networking-and-network-policy) را ببینید.
