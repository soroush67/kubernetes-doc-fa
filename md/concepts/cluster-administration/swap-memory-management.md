کوبرنتیز را می‌توان طوری پیکربندی کرد که روی یک {{< glossary_tooltip text="نود" term_id="node" >}} از حافظهٔ swap استفاده کند؛
در این حالت کرنل می‌تواند با انتقال صفحه‌ها به فضای ذخیره‌سازی پشتیبان، حافظهٔ فیزیکی را آزاد کند.
این قابلیت در موارد کاربرد متعددی سودمند است.
برای نمونه، نودهایی که بارهای کاری بهره‌مند از swap را اجرا می‌کنند،
مانند بارهای کاری‌ای که ردپای حافظهٔ بزرگی دارند اما در هر لحظه تنها به بخشی از آن حافظه دسترسی پیدا می‌کنند.
همچنین این قابلیت به جلوگیری از خاتمه‌یافتن Podها هنگام جهش‌های فشار حافظه کمک می‌کند،
نودها را در برابر جهش‌های حافظه در سطح سیستم که ممکن است پایداری آن‌ها را به خطر بیندازد محافظت می‌کند،
مدیریت انعطاف‌پذیرتر حافظه را روی نود ممکن می‌سازد و مزایای بسیار دیگری نیز دارد.

برای آشنایی با پیکربندی swap در کلاستر خود، مطلب
[پیکربندی حافظهٔ swap روی نودهای کوبرنتیز](/docs/tutorials/cluster-management/provision-swap-memory/) را بخوانید.

<!-- body -->

## پشتیبانی سیستم‌عامل

* نودهای لینوکسی از swap پشتیبانی می‌کنند؛ برای فعال‌سازی آن باید هر نود را پیکربندی کنید.
  به‌طور پیش‌فرض، kubelet روی نود لینوکسی‌ای که swap در آن فعال است **اجرا نمی‌شود**.
* نودهای ویندوزی به فضای swap نیاز دارند.
  به‌طور پیش‌فرض، kubelet روی نود ویندوزی‌ای که swap در آن غیرفعال است **اجرا نمی‌شود**.

## این قابلیت چگونه کار می‌کند؟

روش‌های گوناگونی برای تصور استفاده از swap روی یک نود وجود دارد.
اگر kubelet از قبل روی نودی در حال اجرا باشد، پس از تأمین swap باید دوباره راه‌اندازی شود تا آن را شناسایی کند.

هنگامی که kubelet روی نودی اجرا می‌شود که swap در آن تأمین شده و در دسترس است
(با پیکربندی `failSwapOn: false`)، kubelet:
- می‌تواند روی این نودِ دارای swap اجرا شود.
- به پیاده‌سازی واسط زمان اجرای کانتینر (CRI)، که اغلب «زمان اجرای کانتینر» نامیده می‌شود، دستور می‌دهد
که به‌طور پیش‌فرض هیچ حافظهٔ swapای به بارهای کاری کوبرنتیز اختصاص ندهد.

پیکربندی swap روی یک نود از طریق
[`memorySwap` در KubeletConfiguration](/docs/reference/config-api/kubelet-config.v1) در اختیار مدیر کلاستر قرار می‌گیرد.
شما به‌عنوان مدیر کلاستر می‌توانید با تنظیم `memorySwap.swapBehavior` رفتار نود را
در حضور حافظهٔ swap مشخص کنید.

### رفتارهای swap

باید یک [رفتار swap](/docs/reference/node/swap-behavior/) را برای استفاده انتخاب کنید.
نودهای مختلف کلاستر شما می‌توانند از رفتارهای swap متفاوتی استفاده کنند.

رفتارهای swap قابل انتخاب برای نودهای لینوکسی عبارت‌اند از:

`NoSwap` (پیش‌فرض)
: بارهای کاری‌ای که به‌صورت Pod روی این نود اجرا می‌شوند از swap استفاده نمی‌کنند و نمی‌توانند استفاده کنند.

`LimitedSwap`
: بارهای کاری کوبرنتیز می‌توانند از حافظهٔ swap بهره ببرند.

{{< note >}}
اگر رفتار NoSwap را انتخاب کنید و kubelet را طوری پیکربندی کنید که وجود فضای swap را تحمل کند
(`failSwapOn: false`)، بارهای کاری شما هیچ استفاده‌ای از swap نمی‌کنند.

با این حال، فرایندهای بیرون از کانتینرهای مدیریت‌شده توسط کوبرنتیز، مانند سرویس‌های systemd
(و حتی خود kubelet!) **می‌توانند** از swap استفاده کنند.
{{< /note >}}

برای آشنایی با فعال‌سازی swap در کلاستر خود می‌توانید مطلب [پیکربندی حافظهٔ swap روی نودهای کوبرنتیز](/docs/tutorials/cluster-management/provision-swap-memory/) را بخوانید.

### یکپارچگی با زمان اجرای کانتینر

kubelet از API زمان اجرای کانتینر استفاده می‌کند و به زمان اجرای کانتینر دستور می‌دهد
پیکربندی مشخصی را (برای نمونه، در حالت cgroup v2، مقدار `memory.swap.max`) به‌گونه‌ای اعمال کند که
پیکربندی swap مطلوب برای یک کانتینر فعال شود. در زمان‌های اجرایی که از گروه‌های کنترلی (control groups یا cgroups) استفاده می‌کنند،
زمان اجرای کانتینر مسئول نوشتن این تنظیمات در cgroup سطح کانتینر است.

## مشاهده‌پذیری استفاده از swap

### آمار متریک‌ها در سطح نود و کانتینر

kubelet اکنون آمار متریک‌ها را در سطح نود و کانتینر گردآوری می‌کند؛
این آمار از طریق endpointهای HTTP مربوط به kubelet یعنی `/metrics/resource` (که عمدتاً ابزارهای پایش
مانند Prometheus از آن استفاده می‌کنند) و `/stats/summary` (که عمدتاً Autoscalerها از آن استفاده می‌کنند) در دسترس است.
این امکان به کلاینت‌هایی که می‌توانند مستقیماً از kubelet درخواست کنند اجازه می‌دهد
هنگام استفاده از `LimitedSwap` میزان استفاده از swap و حافظهٔ swap باقی‌مانده را پایش کنند.
افزون بر این، متریک `machine_swap_bytes` به cadvisor اضافه شده است تا
ظرفیت کل swap فیزیکی ماشین را نشان دهد.
برای اطلاعات بیشتر [این صفحه](/docs/reference/instrumentation/node-metrics/) را ببینید.

برای نمونه، این متریک‌های `/metrics/resource` پشتیبانی می‌شوند:
- `node_swap_usage_bytes`: میزان فعلی استفادهٔ نود از swap بر حسب بایت.
- `container_swap_usage_bytes`: میزان فعلی استفادهٔ کانتینر از swap بر حسب بایت.
- `container_swap_limit_bytes`: میزان فعلی حد swap کانتینر بر حسب بایت.

### استفاده از `kubectl top --show-swap`

پرس‌وجوی متریک‌ها ارزشمند است، اما تا حدی دشوار است، زیرا این متریک‌ها
برای استفادهٔ نرم‌افزارها طراحی شده‌اند، نه انسان‌ها.
برای آنکه این داده‌ها به شیوه‌ای کاربرپسندتر مصرف شوند،
فرمان `kubectl top` گسترش یافته است تا با استفاده از پرچم `--show-swap` از متریک‌های swap پشتیبانی کند.

برای دریافت اطلاعات دربارهٔ میزان استفاده از swap روی نودها، می‌توان از `kubectl top nodes --show-swap` استفاده کرد:
```shell
kubectl top nodes --show-swap
```

خروجی‌ای مشابه زیر به دست می‌آید:
```

node2   5m           10%      6Mi             10%         2Mi            0%   
node3   3m           10%      4Mi             10%         <unknown>      <unknown>   
```

برای دریافت اطلاعات دربارهٔ میزان استفادهٔ Podها از swap، می‌توان از `kubectl top pods --show-swap` استفاده کرد:
```shell
kubectl top pod -n kube-system --show-swap
```

خروجی‌ای مشابه زیر به دست می‌آید:

### گزارش ظرفیت swap نودها به‌عنوان بخشی از وضعیت نود

فیلد وضعیت جدیدی به نام `node.status.nodeInfo.swap.capacity` به نود اضافه شده است تا ظرفیت swap یک نود را گزارش کند.

برای نمونه، می‌توان از فرمان زیر برای بازیابی ظرفیت swap نودهای یک کلاستر استفاده کرد:
```shell
kubectl get nodes -o go-template='{{range .items}}{{.metadata.name}}: {{if .status.nodeInfo.swap.capacity}}{{.status.nodeInfo.swap.capacity}}{{else}}<unknown>{{end}}{{"\n"}}{{end}}'
```

خروجی‌ای مشابه زیر به دست می‌آید:
```
node1: 21474836480
node2: 42949664768
node3: <unknown>
```

{{< note >}}

مقدار `<unknown>` نشان می‌دهد که فیلد `.status.nodeInfo.swap.capacity` برای آن Node تنظیم نشده است.
این احتمالاً به این معناست که نود swap تأمین‌شده ندارد، یا با احتمال کمتر،
kubelet قادر به تعیین ظرفیت swap نود نیست.

{{< /note >}}

### کشف swap با استفاده از Node Feature Discovery (NFD) {#node-feature-discovery}

[Node Feature Discovery](https://github.com/kubernetes-sigs/node-feature-discovery)
یک افزونهٔ کوبرنتیز برای شناسایی ویژگی‌ها و پیکربندی سخت‌افزار است.
می‌توان از آن برای کشف اینکه کدام نودها دارای swap تأمین‌شده هستند استفاده کرد.

برای نمونه، برای اینکه بفهمید کدام نودها دارای swap تأمین‌شده هستند،
از فرمان زیر استفاده کنید:
```shell
kubectl get nodes -o jsonpath='{range .items[?(@.metadata.labels.feature\.node\.kubernetes\.io/memory-swap)]}{.metadata.name}{"\t"}{.metadata.labels.feature\.node\.kubernetes\.io/memory-swap}{"\n"}{end}'
```

خروجی‌ای مشابه زیر به دست می‌آید:
```
k8s-worker1: true
k8s-worker2: true
k8s-worker3: false
```

در این مثال، swap روی نودهای `k8s-worker1` و `k8s-worker2` تأمین شده است، اما روی `k8s-worker3` تأمین نشده است.

## ریسک‌ها و ملاحظات

{{< caution >}}

اکیداً توصیه می‌شود فضای swap رمزگذاری شود.
برای اطلاعات بیشتر بخش حجم‌های مبتنی بر حافظه [حجم‌های مبتنی بر حافظه](#memory-backed-volumes) را ببینید.

{{< /caution >}}

در دسترس بودن swap روی یک سیستم، پیش‌بینی‌پذیری را کاهش می‌دهد.
اگرچه swap می‌تواند با در دسترس قرار دادن RAM بیشتر کارایی را افزایش دهد، بازگرداندن داده‌ها
به حافظه عملیاتی سنگین است که گاهی چندین مرتبهٔ بزرگی کندتر است
و می‌تواند به افت‌های غیرمنتظرهٔ کارایی منجر شود.
افزون بر این، swap رفتار سیستم را تحت فشار حافظه تغییر می‌دهد.
فعال‌سازی swap خطر همسایه‌های پرسروصدا (noisy neighbors) را افزایش می‌دهد،
به این صورت که Podهایی که مکرراً از RAM خود استفاده می‌کنند ممکن است باعث شوند Podهای دیگر به swap منتقل شوند.
همچنین، از آنجا که swap امکان استفادهٔ بیشتر از حافظه را برای بارهای کاری کوبرنتیز فراهم می‌کند که نمی‌توان آن را به‌طور پیش‌بینی‌پذیر محاسبه کرد،
و به دلیل پیکربندی‌های غیرمنتظرهٔ چیدمان،
زمان‌بند در حال حاضر میزان استفاده از حافظهٔ swap را در نظر نمی‌گیرد.
این امر خطر همسایه‌های پرسروصدا را تشدید می‌کند.

کارایی نودی که حافظهٔ swap در آن فعال است به ذخیره‌سازی فیزیکی زیربنایی بستگی دارد.
هنگامی که از حافظهٔ swap استفاده می‌شود، در محیطی که از نظر تعداد عملیات I/O
در ثانیه (IOPS) محدود است، مانند یک ماشین مجازی ابری با
محدودسازی I/O، کارایی در مقایسه با رسانه‌های ذخیره‌سازی سریع‌تر مانند درایوهای حالت جامد
یا NVMe به‌طور چشمگیری بدتر خواهد بود.
از آنجا که swap ممکن است فشار IO ایجاد کند، توصیه می‌شود به daemonهای حیاتی سیستم
اولویت بالاتری از نظر تأخیر IO داده شود. بخش مرتبط را در
بخش [روش‌های توصیه‌شده](#good-practice-for-using-swap-in-a-kubernetes-cluster) در ادامه ببینید.

### حجم‌های مبتنی بر حافظه

روی نودهای لینوکسی، حجم‌های مبتنی بر حافظه (مانند mountهای حجم [`secret`](/docs/concepts/configuration/secret/)
یا [`emptyDir`](/docs/concepts/storage/volumes/#emptydir) با `medium: Memory`)
با سیستم فایل `tmpfs` پیاده‌سازی می‌شوند.
محتوای چنین حجم‌هایی باید همواره در حافظه باقی بماند و بنابراین نباید
به دیسک منتقل (swap) شود.
برای اطمینان از اینکه محتوای چنین حجم‌هایی در حافظه باقی می‌ماند، از گزینهٔ tmpfs به نام `noswap`
استفاده می‌شود.

کرنل لینوکس از نسخهٔ 6.3 به‌طور رسمی از گزینهٔ `noswap` پشتیبانی می‌کند (اطلاعات بیشتر
را می‌توانید در [الزامات نسخهٔ کرنل لینوکس](/docs/reference/node/kernel-version-requirements/#requirements-other) بیابید).
با این حال، توزیع‌های مختلف اغلب تصمیم می‌گیرند این گزینهٔ mount را به نسخه‌های قدیمی‌تر
لینوکس نیز backport کنند.

برای بررسی اینکه آیا نود از گزینهٔ `noswap` پشتیبانی می‌کند یا نه، kubelet کارهای زیر را انجام می‌دهد:
* اگر نسخهٔ کرنل بالاتر از 6.3 باشد، فرض می‌شود که گزینهٔ `noswap` پشتیبانی می‌شود.
* در غیر این صورت، kubelet هنگام راه‌اندازی تلاش می‌کند یک tmpfs آزمایشی را با گزینهٔ `noswap` mount کند.
  اگر kubelet با خطایی حاکی از گزینهٔ ناشناخته شکست بخورد، فرض می‌شود که `noswap`
  پشتیبانی نمی‌شود و بنابراین استفاده نخواهد شد.
  یک مدخل لاگ kubelet منتشر می‌شود تا به کاربر هشدار دهد که حجم‌های مبتنی بر حافظه ممکن است به دیسک منتقل شوند.
  اگر kubelet موفق شود، tmpfs آزمایشی حذف می‌شود و گزینهٔ `noswap` مورد استفاده قرار می‌گیرد.
  * اگر گزینهٔ `noswap` پشتیبانی نشود، kubelet یک مدخل لاگ هشدار منتشر می‌کند
    و سپس به اجرای خود ادامه می‌دهد.

برای نمونه‌ای از راه‌اندازی swap، [پیکربندی حافظهٔ swap روی نودهای کوبرنتیز](/docs/tutorials/cluster-management/provision-swap-memory/) را ببینید.
با این حال، مدیریت swap رمزگذاری‌شده در حیطهٔ kubelet نیست؛
بلکه یک دغدغهٔ عمومی پیکربندی سیستم‌عامل است و باید در همان سطح به آن پرداخته شود.
تأمین swap رمزگذاری‌شده برای کاهش این ریسک بر عهدهٔ مدیر سیستم است.

### بیرون‌رانی‌ها (Evictions)

پیکربندی آستانه‌های بیرون‌رانی حافظه برای نودهای دارای swap می‌تواند دشوار باشد.

هنگامی که swap غیرفعال است، منطقی است که آستانه‌های بیرون‌رانی kubelet را
کمی پایین‌تر از ظرفیت حافظهٔ نود پیکربندی کنیم.
دلیل این است که می‌خواهیم کوبرنتیز پیش از آنکه حافظهٔ نود تمام شود
و OOM killer (Out Of Memory) فراخوانی شود، بیرون‌راندن Podها را آغاز کند، زیرا OOM killer از کوبرنتیز آگاه نیست
و بنابراین مواردی مانند QoS، اولویت Pod یا سایر عوامل خاص کوبرنتیز را در نظر نمی‌گیرد.

هنگامی که swap فعال است، وضعیت پیچیده‌تر است.
در لینوکس، پارامتر `vm.min_free_kbytes` آستانهٔ حافظه‌ای را تعریف می‌کند که کرنل
از آن به بعد بازپس‌گیری تهاجمی حافظه را آغاز می‌کند، که شامل انتقال صفحه‌ها به swap نیز می‌شود.
اگر آستانه‌های بیرون‌رانی kubelet به‌گونه‌ای تنظیم شوند که بیرون‌رانی
پیش از آغاز بازپس‌گیری حافظه توسط کرنل رخ دهد، ممکن است بارهای کاری
هرگز نتوانند هنگام فشار حافظهٔ نود به swap منتقل شوند.
از سوی دیگر، تنظیم آستانه‌های بیرون‌رانی در سطحی بیش از حد بالا می‌تواند باعث شود حافظهٔ نود تمام شود
و OOM killer فراخوانی شود، که آن هم مطلوب نیست.

برای رفع این مسئله، توصیه می‌شود آستانه‌های بیرون‌رانی kubelet
کمی پایین‌تر از مقدار `vm.min_free_kbytes` تنظیم شوند.
به این ترتیب، نود می‌تواند پیش از آنکه kubelet بیرون‌راندن Podها را آغاز کند، swap کردن را شروع کند
و به بارهای کاری اجازه دهد داده‌های بلااستفاده را به swap منتقل کنند و از وقوع بیرون‌رانی جلوگیری شود.
از سوی دیگر، از آنجا که این مقدار تنها کمی پایین‌تر است، احتمالاً kubelet پیش از تمام شدن حافظهٔ نود
بیرون‌راندن Podها را آغاز می‌کند و در نتیجه از OOM killer اجتناب می‌شود.

مقدار `vm.min_free_kbytes` را می‌توان با اجرای فرمان زیر روی نود تعیین کرد:
```shell
cat /proc/sys/vm/min_free_kbytes
```

### فضای swap بلااستفاده

در رفتار `LimitedSwap`، مقدار swap در دسترس برای یک Pod به‌طور خودکار
بر اساس نسبت حافظهٔ درخواست‌شده به کل حافظهٔ نود تعیین می‌شود
(برای جزئیات بیشتر، [بخش زیر](#how-is-the-swap-limit-being-determined-with-limitedswap) را ببینید).

این طراحی به این معناست که معمولاً بخشی از swap برای بارهای کاری کوبرنتیز
محدود باقی می‌ماند.
برای نمونه، از آنجا که کوبرنتیز {{< skew currentVersion >}} اجازهٔ استفاده از swap را به
Podهای {{< glossary_tooltip text="کلاس QoS" term_id="qos-class" >}} از نوع Guaranteed نمی‌دهد،
مقداری از swap که متناسب با درخواست حافظهٔ Podهای Guaranteed است
توسط بارهای کاری کوبرنتیز بلااستفاده باقی می‌ماند.

این رفتار در شرایطی که بسیاری از Podها واجد شرایط swap نیستند، ریسک‌هایی به همراه دارد.
از سوی دیگر، این رفتار عملاً مقداری حافظهٔ swap رزروشده برای سیستم نگه می‌دارد که فرایندهای
خارج از حیطهٔ کوبرنتیز، مانند daemonهای سیستم و حتی خود kubelet، می‌توانند از آن استفاده کنند.

## روش‌های خوب برای استفاده از swap در یک کلاستر کوبرنتیز

### غیرفعال‌سازی swap برای daemonهای حیاتی سیستم

در مرحلهٔ آزمایش و بر اساس بازخورد کاربران، مشاهده شد که کارایی
daemonها و سرویس‌های حیاتی سیستم ممکن است کاهش یابد.
این بدان معناست که daemonهای سیستم، از جمله kubelet، ممکن است کندتر از معمول عمل کنند.
اگر با این مشکل مواجه شدید، توصیه می‌شود cgroup مربوط به system slice را طوری پیکربندی کنید
که از swap کردن جلوگیری شود (یعنی `memory.swap.max=0` را تنظیم کنید).

### محافظت از daemonهای حیاتی سیستم از نظر تأخیر I/O

swap می‌تواند بار I/O روی یک نود را افزایش دهد.
هنگامی که فشار حافظه باعث می‌شود کرنل به‌سرعت صفحه‌ها را به swap منتقل کند و از آن بازگرداند،
daemonها و سرویس‌های حیاتی سیستم که به عملیات I/O وابسته‌اند ممکن است
دچار افت کارایی شوند.

برای کاهش این مشکل، به کاربران systemd توصیه می‌شود system slice را از نظر تأخیر I/O در اولویت قرار دهند.
برای کاربرانی که از systemd استفاده نمی‌کنند،
توصیه می‌شود یک cgroup اختصاصی برای daemonها و فرایندهای سیستم راه‌اندازی کنند و به همین شیوه تأخیر I/O را در اولویت قرار دهند.
این کار را می‌توان با تنظیم `io.latency` برای system slice انجام داد
و بدین ترتیب اولویت I/O بالاتری به آن اعطا کرد.
برای اطلاعات بیشتر [مستندات cgroup](https://www.kernel.org/doc/Documentation/admin-guide/cgroup-v2.rst) را ببینید.

### swap و نودهای control plane

پروژهٔ کوبرنتیز توصیه می‌کند نودهای control plane بدون هیچ فضای swap پیکربندی‌شده‌ای اجرا شوند.
control plane عمدتاً میزبان Podهایی با QoS از نوع Guaranteed است، بنابراین معمولاً می‌توان swap را غیرفعال کرد.
نگرانی اصلی این است که swap کردن سرویس‌های حیاتی روی control plane می‌تواند تأثیر منفی بر کارایی داشته باشد.

### استفاده از یک دیسک اختصاصی برای swap

پروژهٔ کوبرنتیز توصیه می‌کند هر زمان که نودهایی با swap فعال اجرا می‌کنید، از swap رمزگذاری‌شده استفاده کنید.
اگر swap روی یک پارتیشن یا سیستم فایل ریشه قرار داشته باشد، بارهای کاری ممکن است
با فرایندهای سیستمی که نیاز به نوشتن روی دیسک دارند تداخل ایجاد کنند.
هنگامی که از یک دیسک مشترک استفاده می‌کنند، فرایندها می‌توانند swap را تحت فشار قرار دهند
و I/O مربوط به kubelet، زمان اجرای کانتینر و systemd را مختل کنند، که بر سایر بارهای کاری تأثیر می‌گذارد.
از آنجا که فضای swap روی دیسک قرار دارد، اطمینان از اینکه دیسک برای موارد کاربرد مورد نظر به‌اندازهٔ کافی سریع است اهمیت حیاتی دارد.
به‌عنوان جایگزین، می‌توان اولویت‌های I/O را میان نواحی نگاشت‌شدهٔ مختلفِ یک دستگاه پشتیبان واحد پیکربندی کرد.

### زمان‌بندی آگاه از swap

کوبرنتیز {{< skew currentVersion >}} از تخصیص Podها به نودها به شیوه‌ای که
میزان استفاده از حافظهٔ swap را در نظر بگیرد پشتیبانی نمی‌کند. زمان‌بند معمولاً از _درخواست‌ها_ (requests) برای منابع زیرساختی
برای هدایت جای‌گذاری Podها استفاده می‌کند و Podها فضای swap درخواست نمی‌کنند؛ آن‌ها فقط `memory` درخواست می‌کنند.
این بدان معناست که زمان‌بند هنگام تصمیم‌گیری‌های زمان‌بندی حافظهٔ swap را در نظر نمی‌گیرد.
اگرچه ما به‌طور فعال روی این موضوع کار می‌کنیم، هنوز پیاده‌سازی نشده است.

برای اینکه مدیران اطمینان حاصل کنند Podها روی نودهای دارای
حافظهٔ swap زمان‌بندی نمی‌شوند مگر آنکه به‌طور مشخص برای استفاده از آن در نظر گرفته شده باشند،
مدیران می‌توانند نودهای دارای swap را taint کنند تا از این مشکل جلوگیری شود.
taintها تضمین می‌کنند بارهای کاری‌ای که swap را تحمل می‌کنند تحت بار به نودهای بدون swap سرریز نشوند.

### انتخاب ذخیره‌سازی برای کارایی بهینه

دستگاه ذخیره‌سازی‌ای که برای فضای swap تعیین می‌شود در حفظ پاسخ‌گویی سیستم
هنگام استفادهٔ زیاد از حافظه نقشی حیاتی دارد.
درایوهای دیسک سخت چرخشی (HDD) برای این کار مناسب نیستند، زیرا ماهیت مکانیکی آن‌ها تأخیر قابل‌توجهی ایجاد می‌کند
و به افت شدید کارایی و thrashing سیستم منجر می‌شود.
برای نیازهای کارایی امروزی، دستگاهی مانند درایو حالت جامد (SSD) احتمالاً انتخاب مناسبی برای swap است،
زیرا دسترسی الکترونیکی کم‌تأخیر آن کندی را به حداقل می‌رساند.


## جزئیات رفتار swap

### حد swap در LimitedSwap چگونه تعیین می‌شود؟

پیکربندی حافظهٔ swap، از جمله محدودیت‌های آن، چالش قابل‌توجهی
به شمار می‌رود. نه‌تنها این پیکربندی مستعد پیکربندی نادرست است، بلکه از آنجا که یک ویژگی در سطح سیستم است، هر
پیکربندی نادرستی می‌تواند به‌جای یک بار کاری مشخص، کل نود را به خطر
بیندازد. برای کاهش این ریسک و تضمین سلامت نود، ما
swap را با پیکربندی خودکار محدودیت‌ها پیاده‌سازی کرده‌ایم.

با `LimitedSwap`، Podهایی که در دستهٔ QoS از نوع Burstable قرار نمی‌گیرند (یعنی
Podهای با QoS از نوع `BestEffort`/`Guaranteed`) از استفاده از حافظهٔ swap منع می‌شوند.
Podهای با QoS از نوع `BestEffort` الگوهای مصرف حافظهٔ غیرقابل‌پیش‌بینی دارند و
اطلاعاتی دربارهٔ میزان استفادهٔ خود از حافظه ارائه نمی‌دهند، که تعیین تخصیص ایمن
حافظهٔ swap را دشوار می‌کند.
در مقابل، Podهای با QoS از نوع `Guaranteed` معمولاً برای برنامه‌هایی به کار می‌روند که به
تخصیص دقیق منابع مشخص‌شده توسط بار کاری متکی‌اند و حافظه باید بی‌درنگ در دسترس باشد.
برای حفظ تضمین‌های امنیتی و سلامت نود که پیش‌تر ذکر شد،
این Podها هنگامی که `LimitedSwap` فعال است اجازهٔ استفاده از حافظهٔ swap را ندارند.
افزون بر این، Podهای با اولویت بالا اجازهٔ استفاده از swap را ندارند تا اطمینان حاصل شود حافظه‌ای
که مصرف می‌کنند همواره در RAM قرار دارد و بنابراین آمادهٔ استفاده است.

پیش از تشریح جزئیات محاسبهٔ حد swap، لازم است اصطلاحات زیر تعریف شوند:
* `nodeTotalMemory`: کل مقدار حافظهٔ فیزیکی در دسترس روی نود.
* `totalPodsSwapAvailable`: کل مقدار حافظهٔ swap روی نود که برای استفادهٔ Podها در دسترس است (ممکن است بخشی از حافظهٔ swap برای استفادهٔ سیستم رزرو شده باشد).
* `containerMemoryRequest`: درخواست حافظهٔ کانتینر.

محدودیت swap به این صورت پیکربندی می‌شود:  
( `containerMemoryRequest` / `nodeTotalMemory` ) × `totalPodsSwapAvailable`

به بیان دیگر، مقدار swapای که یک کانتینر می‌تواند استفاده کند متناسب با
درخواست حافظهٔ آن، کل حافظهٔ فیزیکی نود و کل مقدار حافظهٔ swap روی
نود که برای استفادهٔ Podها در دسترس است، تعیین می‌شود.

توجه به این نکته مهم است که برای کانتینرهای درون Podهای با QoS از نوع Burstable، می‌توان
با تعیین درخواست‌های حافظه‌ای برابر با حدهای حافظه، از استفاده از swap صرف‌نظر کرد.
کانتینرهایی که به این شیوه پیکربندی شوند به حافظهٔ swap دسترسی نخواهند داشت.
