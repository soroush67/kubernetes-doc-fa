## مدل شبکهٔ کوبرنتیز

مدل شبکهٔ کوبرنتیز از چند بخش تشکیل شده است:

* هر [پاد](/docs/concepts/workloads/pods/) در کلاستر یک نشانی IP یکتا در سطح کل کلاستر
  دریافت می‌کند.

  * هر پاد فضای نام (namespace) شبکهٔ خصوصی خود را دارد که میان همهٔ کانتینرهای
    درون آن پاد مشترک است. فرایندهایی که در کانتینرهای مختلفِ یک پاد اجرا می‌شوند،
    می‌توانند از طریق `localhost` با یکدیگر ارتباط برقرار کنند.

* _شبکهٔ پاد_ (که شبکهٔ کلاستر نیز نامیده می‌شود) ارتباط میان پادها را برعهده دارد.
  این شبکه تضمین می‌کند که (مگر آنکه شبکه عمداً بخش‌بندی شده باشد):

  * همهٔ پادها بتوانند با همهٔ پادهای دیگر ارتباط برقرار کنند، چه روی یک
    [نود](/docs/concepts/architecture/nodes/) باشند و چه روی نودهای مختلف.
    پادها می‌توانند بدون استفاده از پراکسی یا ترجمهٔ نشانی (NAT) مستقیماً با یکدیگر
    ارتباط برقرار کنند.

    در ویندوز، این قاعده دربارهٔ پادهایی که از شبکهٔ میزبان استفاده می‌کنند صدق نمی‌کند.

  * عامل‌های روی یک نود (مانند دیمن‌های سیستمی یا kubelet) بتوانند با همهٔ پادهای
    آن نود ارتباط برقرار کنند.

* با API مربوط به [Service](/docs/concepts/services-networking/service/) می‌توانید
  برای سرویسی که یک یا چند پاد پشتیبان آن را پیاده‌سازی می‌کنند، یک نشانی IP یا نام
  میزبان پایدار (و بلندمدت) فراهم کنید، در حالی که پادهای تشکیل‌دهندهٔ آن سرویس ممکن است
  به‌مرور زمان تغییر کنند.

  * کوبرنتیز آبجکت‌های
    [EndpointSlice](/docs/concepts/services-networking/endpoint-slices/)
    را به‌طور خودکار مدیریت می‌کند تا اطلاعاتی دربارهٔ پادهایی که در حال حاضر پشتیبان
    یک Service هستند، فراهم شود.

  * هر پیاده‌سازی پراکسی سرویس، مجموعهٔ آبجکت‌های Service و EndpointSlice را
    زیر نظر می‌گیرد و با استفاده از APIهای سیستم‌عامل یا ارائه‌دهندهٔ ابری برای رهگیری
    یا بازنویسی بسته‌ها، صفحهٔ داده (data plane) را طوری برنامه‌ریزی می‌کند که ترافیک
    سرویس به پشتیبان‌های آن هدایت شود.

* با API مربوط به [Gateway](/docs/concepts/services-networking/gateway/)
  (یا نسخهٔ پیشین آن، [Ingress](/docs/concepts/services-networking/ingress/))
  می‌توانید Serviceها را برای کلاینت‌های بیرون از کلاستر در دسترس قرار دهید.

  * هنگام استفاده از یک {{< glossary_tooltip term_id="cloud-provider">}} پشتیبانی‌شده،
    سازوکاری ساده‌تر اما با قابلیت پیکربندی کمتر برای ورود ترافیک به کلاستر از طریق
    [`type: LoadBalancer`](/docs/concepts/services-networking/service/#loadbalancer)
    در API مربوط به Service در دسترس است.

* [NetworkPolicy](/docs/concepts/services-networking/network-policies) یک API داخلی
  کوبرنتیز است که با آن می‌توانید ترافیک میان پادها، یا میان پادها و دنیای بیرون را
  کنترل کنید.

در سامانه‌های کانتینری قدیمی‌تر، اتصال خودکاری میان کانتینرهای روی میزبان‌های مختلف
وجود نداشت. به همین دلیل، اغلب لازم بود میان کانتینرها به‌طور صریح پیوند ایجاد شود، یا
پورت‌های کانتینر به پورت‌های میزبان نگاشت شوند تا کانتینرهای روی میزبان‌های دیگر بتوانند
به آن‌ها دسترسی داشته باشند. در کوبرنتیز به این کار نیازی نیست؛ در مدل کوبرنتیز، از
دیدگاه تخصیص پورت، نام‌گذاری، کشف سرویس، توزیع بار، پیکربندی برنامه و مهاجرت، می‌توان
با پادها تقریباً مانند ماشین‌های مجازی یا میزبان‌های فیزیکی رفتار کرد.

تنها بخش‌های اندکی از این مدل را خودِ کوبرنتیز پیاده‌سازی می‌کند. برای بخش‌های دیگر،
کوبرنتیز APIها را تعریف می‌کند، اما قابلیت‌های متناظر را مؤلفه‌های خارجی فراهم می‌کنند
که برخی از آن‌ها اختیاری هستند:

* راه‌اندازی فضای نام شبکهٔ پاد را نرم‌افزارهای سطح سیستمی برعهده دارند که
  [رابط محیط اجرای کانتینر](/docs/concepts/containers/cri/) را پیاده‌سازی می‌کنند.

* خودِ شبکهٔ پاد را یک
  [پیاده‌سازی شبکهٔ پاد](/docs/concepts/cluster-administration/addons/#networking-and-network-policy)
  مدیریت می‌کند. در لینوکس، بیشتر محیط‌های اجرای کانتینر برای تعامل با پیاده‌سازی شبکهٔ
  پاد از {{< glossary_tooltip text="رابط شبکهٔ کانتینر (CNI)" term_id="cni" >}}
  استفاده می‌کنند؛ به همین دلیل این پیاده‌سازی‌ها اغلب _افزونه‌های CNI_ نامیده می‌شوند.

* کوبرنتیز یک پیاده‌سازی پیش‌فرض برای پراکسی سرویس به نام
  {{< glossary_tooltip term_id="kube-proxy">}} ارائه می‌دهد، اما برخی پیاده‌سازی‌های
  شبکهٔ پاد به‌جای آن از پراکسی سرویس مخصوص خود استفاده می‌کنند که یکپارچگی بیشتری با
  سایر بخش‌های آن پیاده‌سازی دارد.

* معمولاً پیاده‌سازی NetworkPolicy نیز برعهدهٔ پیاده‌سازی شبکهٔ پاد است. (برخی
  پیاده‌سازی‌های ساده‌تر شبکهٔ پاد از NetworkPolicy پشتیبانی نمی‌کنند، یا ممکن است
  مدیر کلاستر شبکهٔ پاد را بدون پشتیبانی از NetworkPolicy پیکربندی کند. در این موارد،
  API همچنان وجود دارد، اما هیچ اثری ندارد.)

* [پیاده‌سازی‌های](https://gateway-api.sigs.k8s.io/implementations/) فراوانی از
  Gateway API وجود دارد؛ برخی از آن‌ها مختص محیط‌های ابری خاصی هستند، برخی بیشتر بر
  محیط‌های «bare metal» (سخت‌افزار فیزیکی) تمرکز دارند و برخی دیگر عمومی‌ترند.

## {{% heading "whatsnext" %}}

با آموزش [اتصال برنامه‌ها با Serviceها](/docs/tutorials/services/connect-applications-service/)
می‌توانید از طریق یک مثال عملی با Serviceها و شبکهٔ کوبرنتیز آشنا شوید.

صفحهٔ [شبکهٔ کلاستر](/docs/concepts/cluster-administration/networking/) توضیح می‌دهد
که چگونه شبکهٔ کلاستر خود را راه‌اندازی کنید و همچنین نمای کلی از فناوری‌های مرتبط
ارائه می‌دهد.

برای آشنایی با مفاهیم خاص شبکه، این صفحه‌ها را ببینید:

* [Service](/docs/concepts/services-networking/service/) - در معرض دسترس قرار دادن یک برنامه در پشت یک نقطهٔ پایانی واحد رو به بیرون
* [Ingress](/docs/concepts/services-networking/ingress/) - مسیریابی HTTP/HTTPS آگاه از پروتکل با استفاده از URIها، نام‌های میزبان و مسیرها
* [Gateway API](/docs/concepts/services-networking/gateway/) - تأمین پویای زیرساخت و مسیریابی پیشرفتهٔ ترافیک
* [سیاست‌های شبکه](/docs/concepts/services-networking/network-policies/) - کنترل جریان ترافیک در سطح نشانی IP یا پورت (لایهٔ ۳ یا ۴ مدل OSI)
* [DNS برای Serviceها و پادها](/docs/concepts/services-networking/dns-pod-service/) - کشف سرویس‌ها درون کلاستر با استفاده از DNS
