## حساب‌های سرویس چه هستند؟ {#what-are-service-accounts}

حساب سرویس (service account) نوعی حساب غیرانسانی است که در کوبرنتیز یک هویت متمایز در کلاستر کوبرنتیز فراهم می‌کند. Podهای برنامه، مؤلفه‌های سیستم و موجودیت‌های داخل و خارج کلاستر می‌توانند از اعتبارنامه‌های یک ServiceAccount مشخص استفاده کنند تا خود را با هویت همان ServiceAccount معرفی کنند. این هویت در موقعیت‌های گوناگونی کاربرد دارد؛ از جمله احراز هویت در برابر API server یا پیاده‌سازی سیاست‌های امنیتی مبتنی بر هویت.

حساب‌های سرویس به‌صورت آبجکت‌های ServiceAccount در API server وجود دارند. حساب‌های سرویس ویژگی‌های زیر را دارند:

* **وابسته به فضای نام:** هر حساب سرویس به یک
  {{<glossary_tooltip text="فضای نام" term_id="namespace">}} کوبرنتیز وابسته است. هر فضای نام هنگام ایجاد شدن یک [ServiceAccount با نام `default`](#default-service-accounts) دریافت می‌کند.

* **سبک:** حساب‌های سرویس در کلاستر وجود دارند و در API کوبرنتیز تعریف می‌شوند. می‌توانید برای انجام وظایف مشخص، به‌سرعت حساب‌های سرویس ایجاد کنید.

* **قابل‌حمل:** یک بسته‌ی پیکربندی برای یک بار کاری کانتینری پیچیده ممکن است شامل تعریف حساب‌های سرویس برای مؤلفه‌های سیستم باشد. سبک بودن حساب‌های سرویس و وابستگی هویت‌ها به فضای نام، این پیکربندی‌ها را قابل‌حمل می‌کند.

حساب‌های سرویس با حساب‌های کاربری تفاوت دارند؛ حساب‌های کاربری متعلق به کاربران انسانیِ احراز هویت‌شده در کلاستر هستند. به‌طور پیش‌فرض، حساب‌های کاربری در API server کوبرنتیز وجود ندارند و API server هویت کاربران را داده‌ای مبهم (opaque) در نظر می‌گیرد. برای احراز هویت با یک حساب کاربری می‌توانید از روش‌های متعددی استفاده کنید. برخی از توزیع‌های کوبرنتیز ممکن است APIهای افزونه‌ی سفارشی برای نمایش حساب‌های کاربری در API server اضافه کنند.

| توضیح | ServiceAccount | کاربر یا گروه |
| --- | --- | --- |
| محل | API کوبرنتیز (آبجکت ServiceAccount) | خارجی |

### حساب‌های سرویس پیش‌فرض {#default-service-accounts}

هنگامی که یک کلاستر ایجاد می‌کنید، کوبرنتیز به‌طور خودکار برای هر فضای نام در کلاستر شما یک آبجکت ServiceAccount با نام `default` ایجاد می‌کند. اگر کنترل دسترسی مبتنی بر نقش (RBAC) فعال باشد، حساب‌های سرویس `default` در هر فضای نام به‌طور پیش‌فرض هیچ مجوزی جز
[مجوزهای پیش‌فرض کشف API](/docs/reference/access-authn-authz/rbac/#default-roles-and-role-bindings)
ندارند؛ این مجوزها را کوبرنتیز به همه‌ی موجودیت‌های احراز هویت‌شده اعطا می‌کند.
اگر آبجکت ServiceAccount با نام `default` را در یک فضای نام حذف کنید،
{{< glossary_tooltip text="control plane" term_id="control-plane" >}}
یک آبجکت جدید جایگزین آن می‌کند.

اگر یک Pod را در یک فضای نام مستقر کنید و
[به‌صورت دستی یک ServiceAccount به آن Pod اختصاص ندهید](#assign-to-pod)، کوبرنتیز ServiceAccount با نام `default` در همان فضای نام را به Pod اختصاص می‌دهد.

## موارد استفاده از حساب‌های سرویس کوبرنتیز {#use-cases}

به‌عنوان یک رهنمود کلی، می‌توانید در سناریوهای زیر از حساب‌های سرویس برای فراهم کردن هویت استفاده کنید:

* Podهای شما باید با API server کوبرنتیز ارتباط برقرار کنند؛ برای مثال در موقعیت‌هایی مانند موارد زیر:
  * فراهم کردن دسترسی فقط‌خواندنی به اطلاعات حساس ذخیره‌شده در Secretها.
  * اعطای [دسترسی میان فضاهای نام](#cross-namespace)؛ مثلاً اینکه به یک Pod در فضای نام `example` اجازه دهید آبجکت‌های Lease را در فضای نام `kube-node-lease` بخواند، فهرست کند و تغییرات آن‌ها را دنبال کند.
* Podهای شما باید با یک سرویس خارجی ارتباط برقرار کنند. برای مثال، یک Pod بار کاری برای استفاده از یک API ابری تجاری به هویت نیاز دارد و ارائه‌دهنده‌ی تجاری امکان پیکربندی یک رابطه‌ی اعتماد مناسب را فراهم می‌کند.
* [احراز هویت در برابر یک رجیستری خصوصی ایمیج با استفاده از `imagePullSecret`](/docs/tasks/configure-pod-container/configure-service-account/#add-imagepullsecrets-to-a-service-account).
* یک سرویس خارجی باید با API server کوبرنتیز ارتباط برقرار کند؛ برای مثال، احراز هویت در کلاستر به‌عنوان بخشی از یک خط لوله‌ی CI/CD.
* در کلاستر خود از نرم‌افزار امنیتی شخص ثالثی استفاده می‌کنید که بر اساس هویت ServiceAccount در Podهای مختلف، آن Podها را در زمینه‌های (context) متفاوت گروه‌بندی می‌کند.

## نحوه‌ی استفاده از حساب‌های سرویس {#how-to-use}

برای استفاده از یک حساب سرویس کوبرنتیز، مراحل زیر را انجام دهید:

1. با استفاده از یک کلاینت کوبرنتیز مانند `kubectl` یا با مانیفستی که آبجکت را تعریف می‌کند، یک آبجکت ServiceAccount ایجاد کنید.
1. با استفاده از یک سازوکار مجوزدهی مانند
   [RBAC](/docs/reference/access-authn-authz/rbac/)
   به آبجکت ServiceAccount مجوز بدهید.
1. هنگام ایجاد Pod، آبجکت ServiceAccount را به Podها اختصاص دهید.
   
   اگر از این هویت در یک سرویس خارجی استفاده می‌کنید، به‌جای این کار
   [توکن ServiceAccount را دریافت کنید](#get-a-token) و آن را در همان سرویس به کار ببرید.

برای مشاهده‌ی دستورالعمل‌ها، به
[پیکربندی حساب‌های سرویس برای Podها](/docs/tasks/configure-pod-container/configure-service-account/) مراجعه کنید.

### اعطای مجوز به یک ServiceAccount {#grant-permissions}

می‌توانید از سازوکار داخلی
[کنترل دسترسی مبتنی بر نقش (RBAC)](/docs/reference/access-authn-authz/rbac/)
در کوبرنتیز استفاده کنید تا حداقل مجوزهای موردنیاز هر حساب سرویس را به آن اعطا کنید. ابتدا یک *نقش* (role) ایجاد می‌کنید که دسترسی را اعطا می‌کند و سپس آن نقش را به ServiceAccount خود *پیوند* (bind) می‌دهید. با RBAC می‌توانید مجموعه‌ای حداقلی از مجوزها تعریف کنید تا مجوزهای حساب سرویس از اصل کمترین امتیاز پیروی کنند. در نتیجه، Podهایی که از آن حساب سرویس استفاده می‌کنند بیش از آنچه برای عملکرد درست لازم است مجوز دریافت نمی‌کنند.

برای مشاهده‌ی دستورالعمل‌ها، به
[مجوزهای ServiceAccount](/docs/reference/access-authn-authz/rbac/#service-account-permissions) مراجعه کنید.

#### دسترسی میان فضاهای نام با استفاده از ServiceAccount {#cross-namespace}

با RBAC می‌توانید به حساب‌های سرویس یک فضای نام اجازه دهید روی منابع فضای نام دیگری در کلاستر عملیات انجام دهند. برای مثال، سناریویی را در نظر بگیرید که در آن یک حساب سرویس و یک Pod در فضای نام `dev` دارید و می‌خواهید Pod شما Jobهای در حال اجرا در فضای نام `maintenance` را ببیند. می‌توانید یک آبجکت Role ایجاد کنید که مجوز فهرست کردن آبجکت‌های Job را اعطا می‌کند. سپس یک آبجکت RoleBinding در فضای نام `maintenance` ایجاد می‌کنید تا آن Role را به آبجکت ServiceAccount پیوند دهد. اکنون Podهای فضای نام `dev` می‌توانند با استفاده از آن حساب سرویس، آبجکت‌های Job را در فضای نام `maintenance` فهرست کنند.

### اختصاص یک ServiceAccount به Pod {#assign-to-pod}

برای اختصاص یک ServiceAccount به Pod، فیلد `spec.serviceAccountName` را در مشخصات Pod تنظیم می‌کنید. سپس کوبرنتیز به‌طور خودکار اعتبارنامه‌های آن ServiceAccount را در اختیار Pod قرار می‌دهد. در نسخه‌ی v1.22 و بعد از آن، کوبرنتیز با استفاده از API مربوط به `TokenRequest` یک توکن کوتاه‌مدت با **چرخش خودکار** دریافت می‌کند و آن را به‌صورت یک
[حجم projected](/docs/concepts/storage/projected-volumes/#serviceaccounttoken) mount می‌کند.

به‌طور پیش‌فرض، کوبرنتیز اعتبارنامه‌های ServiceAccount اختصاص‌یافته را در اختیار Pod قرار می‌دهد؛ چه این ServiceAccount همان `default` باشد و چه یک ServiceAccount سفارشی که خودتان مشخص کرده‌اید.

برای جلوگیری از تزریق خودکار اعتبارنامه‌های یک ServiceAccount مشخص یا ServiceAccount با نام `default` توسط کوبرنتیز، فیلد `automountServiceAccountToken` را در مشخصات Pod خود برابر `false` قرار دهید.

در نسخه‌های پیش از 1.22، کوبرنتیز یک توکن ایستا و بلندمدت را به‌صورت یک Secret در اختیار Pod قرار می‌دهد.

#### دریافت دستی اعتبارنامه‌های ServiceAccount {#get-a-token}

اگر لازم است اعتبارنامه‌های یک ServiceAccount را در مسیری غیراستاندارد mount کنید، یا آن‌ها را برای مخاطبی (audience) غیر از API server نیاز دارید، از یکی از روش‌های زیر استفاده کنید:

* [رابط برنامه‌نویسی TokenRequest](/docs/reference/kubernetes-api/authentication-resources/token-request-v1/)
  (توصیه‌شده): از درون *کد برنامه‌ی* خود یک توکن کوتاه‌مدت حساب سرویس درخواست کنید. این توکن به‌طور خودکار منقضی می‌شود و می‌تواند پس از انقضا چرخش یابد.
  اگر برنامه‌ای قدیمی دارید که از کوبرنتیز آگاه نیست، می‌توانید از یک کانتینر جانبی (sidecar) در همان Pod استفاده کنید تا این توکن‌ها را دریافت کند و در اختیار بار کاری برنامه قرار دهد.
* [پروجکشن حجم توکن (Token Volume Projection)](/docs/tasks/configure-pod-container/configure-service-account/#serviceaccount-token-volume-projection)
  (این روش نیز توصیه می‌شود): در کوبرنتیز v1.20 و بعد از آن، با استفاده از مشخصات Pod به kubelet اعلام کنید که توکن حساب سرویس را به‌صورت یک *حجم projected* به Pod اضافه کند. توکن‌های projected به‌طور خودکار منقضی می‌شوند و kubelet پیش از انقضای توکن، آن را چرخش می‌دهد.
* [توکن‌های حساب سرویس ذخیره‌شده در Secret](/docs/tasks/configure-pod-container/configure-service-account/#manually-create-an-api-token-for-a-serviceaccount)
  (توصیه نمی‌شود): می‌توانید توکن‌های حساب سرویس را به‌صورت Secretهای کوبرنتیز در Podها mount کنید. این توکن‌ها منقضی نمی‌شوند و چرخش نمی‌یابند. در نسخه‌های پیش از v1.24، برای هر حساب سرویس به‌طور خودکار یک توکن دائمی ایجاد می‌شد.
  این روش دیگر توصیه نمی‌شود، به‌ویژه در مقیاس بزرگ، زیرا اعتبارنامه‌های ایستا و بلندمدت خطرهایی به همراه دارند. [feature gate با نام LegacyServiceAccountTokenNoAutoGeneration](/docs/reference/command-line-tools-reference/feature-gates-removed)
  (که از کوبرنتیز v1.24 تا v1.26 به‌طور پیش‌فرض فعال بود) مانع از آن می‌شد که کوبرنتیز این توکن‌ها را به‌طور خودکار برای ServiceAccountها ایجاد کند. این feature gate در نسخه‌ی v1.27 حذف شد، زیرا به وضعیت GA ارتقا یافت. همچنان می‌توانید توکن‌های حساب سرویس بدون انقضا را به‌صورت دستی ایجاد کنید، اما باید پیامدهای امنیتی آن را در نظر بگیرید.

#### محدودیت مخاطب نود برای توکن‌های حساب سرویس {#node-audience-restriction}

{{< feature-state feature_gate_name="ServiceAccountNodeAudienceRestriction" >}}

هنگامی که [feature gate](/docs/reference/command-line-tools-reference/feature-gates/) با نام `ServiceAccountNodeAudienceRestriction` فعال باشد، افزونه‌ی پذیرش (admission plugin)
[NodeRestriction](/docs/reference/access-authn-authz/admission-controllers#noderestriction)
مخاطب‌هایی را که kubelet هنگام ایجاد توکن‌های حساب سرویس از طریق API مربوط به `TokenRequest` می‌تواند درخواست کند، محدود می‌کند. به‌طور پیش‌فرض، kubelet فقط می‌تواند برای مخاطب‌هایی توکن درخواست کند که Podهای همان نود پیش‌تر به آن‌ها ارجاع داده‌اند (از طریق حجم‌های projected توکن حساب سرویس یا درخواست‌های توکن درایور CSI). مدیران می‌توانند با قواعد RBAC و فعل `request-serviceaccounts-token-audience` به kubeletها دسترسی به مخاطب‌های بیشتری بدهند.

این محدودیت فقط بر kubeletها (هویت‌های نود) اعمال می‌شود و بر دیگر فراخوان‌های API مربوط به `TokenRequest` تأثیری ندارد. برای جزئیات بیشتر و نمونه‌های RBAC، به
[محدودیت مخاطب توکن حساب سرویس](/docs/reference/access-authn-authz/node/#service-account-token-audience-restriction) مراجعه کنید.

{{< note >}}
برای برنامه‌هایی که خارج از کلاستر کوبرنتیز شما اجرا می‌شوند، ممکن است به ایجاد یک توکن بلندمدت ServiceAccount که در یک Secret ذخیره می‌شود فکر کنید. این روش امکان احراز هویت را فراهم می‌کند، اما پروژه‌ی کوبرنتیز توصیه می‌کند از آن پرهیز کنید.
توکن‌های حامل (bearer token) بلندمدت یک خطر امنیتی به شمار می‌آیند، زیرا اگر افشا شوند، ممکن است از آن‌ها سوءاستفاده شود. به‌جای آن، استفاده از یک روش جایگزین را بررسی کنید. برای مثال، برنامه‌ی خارجی شما می‌تواند با استفاده از یک کلید خصوصی به‌خوبی محافظت‌شده `and` یک گواهی احراز هویت کند، یا از سازوکاری سفارشی مانند یک [وب‌هوک احراز هویت](/docs/reference/access-authn-authz/authentication/#webhook-token-authentication) استفاده کند که خودتان پیاده‌سازی می‌کنید.

همچنین می‌توانید با استفاده از TokenRequest برای برنامه‌ی خارجی خود توکن‌های کوتاه‌مدت دریافت کنید.
{{< /note >}}

### محدود کردن دسترسی به Secretها (منسوخ‌شده) {#enforce-mountable-secrets}

{{< feature-state for_k8s_version="v1.32" state="deprecated" >}}

{{< note >}}
حاشیه‌نویسی `kubernetes.io/enforce-mountable-secrets` از کوبرنتیز v1.32 منسوخ شده است. برای جداسازی دسترسی به Secretهای mount‌شده، از فضاهای نام جداگانه استفاده کنید.
{{< /note >}}

کوبرنتیز یک حاشیه‌نویسی (annotation) با نام `kubernetes.io/enforce-mountable-secrets` فراهم می‌کند که می‌توانید آن را به ServiceAccountهای خود اضافه کنید. با اعمال این حاشیه‌نویسی، Secretهای آن ServiceAccount فقط روی انواع مشخصی از منابع قابل mount شدن هستند و به این ترتیب وضعیت امنیتی کلاستر شما بهبود می‌یابد.

می‌توانید این حاشیه‌نویسی را با استفاده از یک مانیفست به ServiceAccount اضافه کنید:

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  annotations:
    kubernetes.io/enforce-mountable-secrets: "true"
  name: my-serviceaccount
  namespace: my-namespace
```
هنگامی که مقدار این حاشیه‌نویسی برابر "true" باشد، control plane کوبرنتیز تضمین می‌کند که Secretهای این ServiceAccount مشمول محدودیت‌های مشخصی در mount شدن باشند.

1. نام هر Secret که به‌صورت حجم در یک Pod mount می‌شود باید در فیلد `secrets` از ServiceAccount آن Pod آمده باشد.
1. نام هر Secret که در یک Pod با `envFrom` به آن ارجاع داده می‌شود نیز باید در فیلد `secrets` از ServiceAccount آن Pod آمده باشد.
1. نام هر Secret که در یک Pod با `imagePullSecrets` به آن ارجاع داده می‌شود نیز باید در فیلد `secrets` از ServiceAccount آن Pod آمده باشد.

مدیران کلاستر با شناخت و اعمال این محدودیت‌ها می‌توانند وضعیت امنیتی سخت‌گیرانه‌تری را حفظ کنند و اطمینان یابند که فقط منابع مناسب به Secretها دسترسی دارند.

## احراز هویت اعتبارنامه‌های حساب سرویس {#authenticating-credentials}

هر ServiceAccount برای احراز هویت در برابر API server کوبرنتیز و هر سیستم دیگری که رابطه‌ی اعتماد با آن وجود دارد، از
{{<glossary_tooltip term_id="jwt" text="توکن‌های وب JSON">}}  (JWT) امضاشده
استفاده می‌کند. بسته به نحوه‌ی صدور توکن (یا با محدودیت زمانی از طریق `TokenRequest` یا با سازوکار قدیمی مبتنی بر Secret)، توکن ServiceAccount ممکن است زمان انقضا، مخاطب و زمانی داشته باشد که توکن از آن به بعد *معتبر می‌شود*. هنگامی که کلاینتی که به‌عنوان یک ServiceAccount عمل می‌کند تلاش می‌کند با API server کوبرنتیز ارتباط برقرار کند، سرآیند `Authorization: Bearer <token>` را در درخواست HTTP قرار می‌دهد. API server اعتبار این توکن حامل را به شرح زیر بررسی می‌کند:

1. امضای توکن را بررسی می‌کند.
1. بررسی می‌کند که آیا توکن منقضی شده است یا نه.
1. بررسی می‌کند که آیا ارجاع‌های آبجکت در ادعاهای (claims) توکن در حال حاضر معتبر هستند یا نه.
1. بررسی می‌کند که آیا توکن در حال حاضر معتبر است یا نه.
1. ادعاهای مخاطب را بررسی می‌کند.

رابط برنامه‌نویسی TokenRequest برای هر ServiceAccount _توکن‌های مقید_ (bound tokens) تولید می‌کند. این پیوند به طول عمر کلاینتی وابسته است که به‌عنوان آن ServiceAccount عمل می‌کند، مانند یک Pod. برای مشاهده‌ی نمونه‌ای از طرح‌واره و محتوای JWT یک توکن مقید حساب سرویس Pod، به [پروجکشن حجم توکن](/docs/tasks/configure-pod-container/configure-service-account/#serviceaccount-token-volume-projection) مراجعه کنید.

برای توکن‌هایی که با API مربوط به `TokenRequest` صادر شده‌اند، API server همچنین بررسی می‌کند که ارجاع آبجکت مشخصی که از ServiceAccount استفاده می‌کند هنوز وجود داشته باشد؛ این تطبیق بر اساس
{{< glossary_tooltip term_id="uid" text="شناسه‌ی یکتای" >}} آن آبجکت انجام می‌شود. برای توکن‌های قدیمی که به‌صورت Secret در Podها mount شده‌اند، API server توکن را با Secret مقایسه می‌کند.

برای اطلاعات بیشتر درباره‌ی فرایند احراز هویت، به
[احراز هویت](/docs/reference/access-authn-authz/authentication/#service-account-tokens) مراجعه کنید.

### احراز هویت اعتبارنامه‌های حساب سرویس در کد خودتان {#authenticating-in-code}

اگر سرویس‌هایی از خودتان دارید که باید اعتبارنامه‌های حساب سرویس کوبرنتیز را اعتبارسنجی کنند، می‌توانید از روش‌های زیر استفاده کنید:

* [رابط برنامه‌نویسی TokenReview](/docs/reference/kubernetes-api/authentication-resources/token-review-v1/)
  (توصیه‌شده)
* کشف OIDC

پروژه‌ی کوبرنتیز توصیه می‌کند از رابط برنامه‌نویسی TokenReview استفاده کنید، زیرا این روش توکن‌هایی را که به آبجکت‌های API مانند Secretها، ServiceAccountها، Podها یا Nodeها مقید هستند، هنگام حذف آن آبجکت‌ها باطل می‌کند. برای مثال، اگر Podی را که حاوی یک توکن projected از ServiceAccount است حذف کنید، کلاستر آن توکن را بلافاصله باطل می‌کند و هر TokenReview بلافاصله با شکست مواجه می‌شود. اما اگر به‌جای آن از اعتبارسنجی OIDC استفاده کنید، کلاینت‌های شما تا زمانی که توکن به برچسب زمانی انقضای خود برسد، همچنان آن را معتبر در نظر می‌گیرند.

برنامه‌ی شما باید همیشه مخاطبی را که می‌پذیرد تعریف کند و بررسی کند که مخاطب‌های توکن با مخاطب‌های موردانتظار برنامه مطابقت داشته باشند. این کار به محدود کردن دامنه‌ی توکن کمک می‌کند تا فقط در برنامه‌ی شما و نه در جای دیگری قابل استفاده باشد.

## جایگزین‌ها

* توکن‌های خود را با سازوکاری دیگر صادر کنید و سپس با استفاده از
  [احراز هویت توکن از طریق وب‌هوک](/docs/reference/access-authn-authz/authentication/#webhook-token-authentication)
  توکن‌های حامل را با سرویس اعتبارسنجی خودتان اعتبارسنجی کنید.
* هویت‌های خودتان را در اختیار Podها قرار دهید.
  * [از افزونه‌ی درایور CSI مربوط به SPIFFE استفاده کنید تا SVIDهای SPIFFE را به‌صورت جفت گواهی‌های X.509 در اختیار Podها قرار دهید](https://cert-manager.io/docs/projects/csi-driver-spiffe/).
    {{% thirdparty-content single="true" %}}
  * [از یک سرویس مش مانند Istio برای ارائه‌ی گواهی به Podها استفاده کنید](https://istio.io/latest/docs/tasks/security/cert-management/plugin-ca-cert/).
* بدون استفاده از توکن‌های حساب سرویس، از خارج کلاستر در برابر API server احراز هویت کنید:
  * [API server را طوری پیکربندی کنید که توکن‌های OpenID Connect (OIDC) را از ارائه‌دهنده‌ی هویت شما بپذیرد](/docs/reference/access-authn-authz/authentication/#openid-connect-tokens).
  * برای احراز هویت در کلاستر خود، از حساب‌های سرویس یا حساب‌های کاربری استفاده کنید که با یک سرویس خارجی مدیریت هویت و دسترسی (IAM)، مثلاً سرویس یک ارائه‌دهنده‌ی ابری، ایجاد شده‌اند.
  * [از رابط برنامه‌نویسی CertificateSigningRequest همراه با گواهی‌های کلاینت استفاده کنید](/docs/tasks/tls/managing-tls-in-a-cluster/).
* [kubelet را طوری پیکربندی کنید که اعتبارنامه‌ها را از یک رجیستری ایمیج دریافت کند](/docs/tasks/administer-cluster/kubelet-credential-provider/).
* از یک افزونه‌ی دستگاه (Device Plugin) برای دسترسی به یک ماژول پلتفرم مورد اعتماد (TPM) مجازی استفاده کنید؛ این ماژول امکان احراز هویت با یک کلید خصوصی را فراهم می‌کند.
