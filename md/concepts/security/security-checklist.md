<!-- overview -->

هدف این چک‌لیست ارائهٔ فهرستی پایه از راهنمایی‌هاست و برای هر موضوع، پیوندهایی به مستندات جامع‌تر در اختیار می‌گذارد. این فهرست ادعای کامل بودن ندارد و قرار است به‌مرور تکامل یابد.

دربارهٔ نحوهٔ خواندن و استفاده از این سند:

- ترتیب موضوعات نشان‌دهندهٔ ترتیب اولویت آن‌ها نیست.
- برخی از موارد چک‌لیست در پاراگراف زیر فهرستِ هر بخش به‌تفصیل شرح داده شده‌اند.

{{< caution >}}
چک‌لیست‌ها به‌تنهایی برای دستیابی به وضعیت امنیتی مطلوب **کافی نیستند**. وضعیت امنیتی مطلوب به توجه و بهبود مداوم نیاز دارد، اما چک‌لیست می‌تواند نخستین گام در مسیر بی‌پایان آمادگی امنیتی باشد. برخی از توصیه‌های این چک‌لیست ممکن است برای نیازهای امنیتی خاص شما بیش از حد سخت‌گیرانه یا بیش از حد سهل‌گیرانه باشند. از آنجا که امنیت کوبرنتیز نسخه‌ای واحد و مناسب برای همه نیست، هر دسته از موارد چک‌لیست باید بر اساس شرایط خودش ارزیابی شود.
{{< /caution >}}

<!-- body -->

## احراز هویت و مجوزدهی

- [ ] پس از راه‌اندازی اولیه (bootstrapping)، از گروه `system:masters` برای احراز هویت کاربران یا مؤلفه‌ها استفاده نمی‌شود.
- [ ] مؤلفهٔ kube-controller-manager با فعال بودن `--use-service-account-credentials` اجرا می‌شود.
- [ ] از گواهی ریشه محافظت می‌شود (یا با یک CA آفلاین، یا با یک CA آنلاینِ مدیریت‌شده که کنترل‌های دسترسی مؤثری دارد).
- [ ] تاریخ انقضای گواهی‌های میانی و نهایی (leaf) حداکثر ۳ سال پس از زمان حال است.
- [ ] فرایندی برای بازبینی دوره‌ای دسترسی‌ها وجود دارد و فاصلهٔ میان بازبینی‌ها بیش از ۲۴ ماه نیست.
- [ ] برای راهنمایی دربارهٔ احراز هویت و مجوزدهی، از [روش‌های خوب کنترل دسترسی مبتنی بر نقش](/docs/concepts/security/rbac-good-practices/) پیروی می‌شود.

پس از راه‌اندازی اولیه، نه کاربران و نه مؤلفه‌ها نباید با هویت `system:masters` در API کوبرنتیز احراز هویت شوند. به همین ترتیب، باید از اجرای کل kube-controller-manager با هویت `system:masters` پرهیز کرد. در واقع، `system:masters` فقط باید به‌عنوان سازوکار دسترسی اضطراری (break-glass) استفاده شود، نه به‌عنوان کاربر مدیر.

## امنیت شبکه

- [ ] افزونه‌های CNI در حال استفاده از سیاست‌های شبکه پشتیبانی می‌کنند.
- [ ] سیاست‌های شبکهٔ ورودی (ingress) و خروجی (egress) روی همهٔ بارهای کاری کلاستر اعمال شده‌اند.
- [ ] در هر فضای نام (namespace)، سیاست‌های شبکهٔ پیش‌فرضی وجود دارند که همهٔ پادها را انتخاب می‌کنند و همه‌چیز را رد می‌کنند.
- [ ] در صورت لزوم، از یک سرویس مش (service mesh) برای رمزنگاری همهٔ ارتباطات درون کلاستر استفاده می‌شود.
- [ ] هیچ‌یک از API کوبرنتیز، API مربوط به kubelet و etcd به‌صورت عمومی روی اینترنت در دسترس نیستند.
- [ ] دسترسی بارهای کاری به API فراداده‌های ابری (cloud metadata API) فیلتر می‌شود.
- [ ] استفاده از LoadBalancer و ExternalIPs محدود شده است.

شماری از [افزونه‌های رابط شبکهٔ کانتینر (CNI)](/docs/concepts/extend-kubernetes/compute-storage-net/network-plugins/) قابلیت محدود کردن منابع شبکه‌ای را فراهم می‌کنند که پادها می‌توانند با آن‌ها ارتباط برقرار کنند. این کار معمولاً از طریق [سیاست‌های شبکه](/docs/concepts/services-networking/network-policies/) انجام می‌شود که منبعی وابسته به فضای نام برای تعریف قوانین در اختیار می‌گذارند. سیاست‌های شبکهٔ پیش‌فرضی که در هر فضای نام همهٔ پادها را انتخاب می‌کنند و تمام ترافیک خروجی و ورودی را مسدود می‌کنند، برای به‌کارگیری رویکرد فهرست مجاز (allow list) مفیدند و اطمینان می‌دهند که هیچ بار کاری از قلم نمی‌افتد.

همهٔ افزونه‌های CNI رمزنگاری داده‌ها در حین انتقال را فراهم نمی‌کنند. اگر افزونهٔ انتخاب‌شده این قابلیت را نداشته باشد، یک راه‌حل جایگزین می‌تواند استفاده از سرویس مش برای فراهم کردن آن باشد.

مخزن دادهٔ etcd در control plane باید کنترل‌هایی برای محدود کردن دسترسی داشته باشد و به‌صورت عمومی روی اینترنت در دسترس نباشد. افزون بر این، برای ارتباط امن با آن باید از TLS متقابل (mTLS) استفاده شود. مرجع صدور گواهی (CA) که برای این منظور به کار می‌رود باید مختص etcd باشد.

دسترسی خارجی از اینترنت به سرور API کوبرنتیز باید محدود شود تا API به‌صورت عمومی در معرض دسترسی قرار نگیرد. مراقب باشید، زیرا بسیاری از توزیع‌های مدیریت‌شدهٔ کوبرنتیز به‌طور پیش‌فرض سرور API را به‌صورت عمومی در دسترس قرار می‌دهند. در این صورت می‌توانید برای دسترسی به سرور از یک میزبان واسط (bastion host) استفاده کنید.

دسترسی به API مربوط به [kubelet](/docs/reference/command-line-tools-reference/kubelet/) باید محدود شود و به‌صورت عمومی در دسترس نباشد؛ زیرا تنظیمات پیش‌فرض احراز هویت و مجوزدهی، در حالتی که هیچ فایل پیکربندی‌ای با فلگ `--config` مشخص نشده باشد، بیش از حد سهل‌گیرانه‌اند.

اگر از یک ارائه‌دهندهٔ ابری برای میزبانی کوبرنتیز استفاده می‌شود، دسترسی پادها به API فراداده‌های ابری در نشانی `169.254.169.254` نیز باید محدود شود، یا در صورت عدم نیاز مسدود شود، زیرا ممکن است به نشت اطلاعات منجر شود.

برای اطلاعات بیشتر دربارهٔ محدود کردن استفاده از LoadBalancer و ExternalIPs، به [CVE-2020-8554: Man in the middle using LoadBalancer or ExternalIPs](https://github.com/kubernetes/kubernetes/issues/97076) و [کنترل‌کنندهٔ پذیرش DenyServiceExternalIPs](/docs/reference/access-authn-authz/admission-controllers/#denyserviceexternalips) مراجعه کنید.

## امنیت Pod

- [ ] مجوزهای RBAC برای `create`، `update`، `patch` و `delete` بارهای کاری فقط در صورت لزوم اعطا می‌شوند.
- [ ] سیاست مناسبی از استانداردهای امنیتی Pod (Pod Security Standards) برای همهٔ فضاهای نام اعمال و اجباری شده است.
- [ ] برای بارهای کاری محدودیت حافظه تعیین شده است و مقدار آن برابر با مقدار درخواست (request) یا کمتر از آن است.
- [ ] ممکن است برای بارهای کاری حساس محدودیت CPU تعیین شود.
- [ ] روی نودهایی که از آن پشتیبانی می‌کنند، Seccomp با پروفایل مناسبی از فراخوانی‌های سیستمی برای برنامه‌ها فعال است.
- [ ] روی نودهایی که از آن پشتیبانی می‌کنند، AppArmor یا SELinux با پروفایل مناسب برای برنامه‌ها فعال است.

مجوزدهی RBAC اهمیت حیاتی دارد، اما [آن‌قدر جزئی‌نگر نیست که بتواند روی منابع Podها مجوزدهی انجام دهد](/docs/concepts/security/rbac-good-practices/#workload-creation) (یا روی هر منبعی که Podها را مدیریت می‌کند). تنها سطح جزئی‌نگری، فعل‌های API روی خود منبع است؛ برای مثال `create` روی Podها. بدون کنترل پذیرش (admission) اضافی، مجوز ایجاد این منابع دسترسی مستقیم و نامحدود به نودهای زمان‌بندی‌پذیر کلاستر را فراهم می‌کند.

[استانداردهای امنیتی Pod](/docs/concepts/security/pod-security-standards/) سه سیاست متفاوت privileged، baseline و restricted را تعریف می‌کنند که نحوهٔ تنظیم فیلدهای `PodSpec` را از نظر امنیتی محدود می‌کنند. این استانداردها را می‌توان در سطح فضای نام با کنترل پذیرش جدید [Pod Security](/docs/concepts/security/pod-security-admission/)، که به‌طور پیش‌فرض فعال است، یا با یک وب‌هوک پذیرش (admission webhook) شخص ثالث اجباری کرد. توجه داشته باشید که برخلاف کنترل پذیرش حذف‌شدهٔ PodSecurityPolicy که جایگزین آن شده است، کنترل پذیرش [Pod Security](/docs/concepts/security/pod-security-admission/) را می‌توان به‌آسانی با وب‌هوک‌های پذیرش و سرویس‌های خارجی ترکیب کرد.

سیاست `restricted` در کنترل پذیرش Pod Security، که سخت‌گیرانه‌ترین سیاست از مجموعهٔ [استانداردهای امنیتی Pod](/docs/concepts/security/pod-security-standards/) است، [می‌تواند در چند حالت عمل کند](/docs/concepts/security/pod-security-admission/#pod-security-admission-labels-for-namespaces): `warn`، `audit` یا `enforce`. به این ترتیب می‌توان مناسب‌ترین [زمینهٔ امنیتی (security context)](/docs/tasks/configure-pod-container/security-context/) را به‌تدریج و مطابق با بهترین روش‌های امنیتی اعمال کرد. با این حال، [زمینهٔ امنیتی](/docs/tasks/configure-pod-container/security-context/) پادها باید برای موارد استفادهٔ خاص به‌طور جداگانه بررسی شود تا امتیازها و دسترسی‌هایی که پادها ممکن است فراتر از استانداردهای امنیتی ازپیش‌تعریف‌شده داشته باشند، محدود شوند.

برای یک آموزش عملی دربارهٔ [Pod Security](/docs/concepts/security/pod-security-admission/)، پست وبلاگ [Kubernetes 1.23: Pod Security Graduates to Beta](/blog/2021/12/09/pod-security-admission-beta/) را ببینید.

[محدودیت‌های حافظه و CPU](/docs/concepts/configuration/manage-resources-containers/) باید تعیین شوند تا میزان حافظه و CPU که یک پاد می‌تواند روی یک نود مصرف کند محدود شود و در نتیجه از حملات احتمالی DoS از سوی بارهای کاری مخرب یا نفوذشده جلوگیری شود. چنین سیاستی را می‌توان با یک کنترل‌کنندهٔ پذیرش اجباری کرد. توجه داشته باشید که محدودیت‌های CPU مصرف را محدود (throttle) می‌کنند و بنابراین ممکن است اثرات ناخواسته‌ای بر قابلیت‌های مقیاس‌پذیری خودکار یا بر کارایی داشته باشند؛ یعنی بر اجرای فرایند به‌صورت best effort با منابع CPU موجود.

{{< caution >}}
اگر محدودیت حافظه بیشتر از مقدار درخواست باشد، ممکن است کل نود در معرض مشکلات OOM قرار گیرد.
{{< /caution >}}

### فعال‌سازی Seccomp

واژهٔ Seccomp مخفف secure computing mode (حالت محاسبات امن) است و از نسخهٔ 2.6.12 یکی از قابلیت‌های هستهٔ لینوکس بوده است. با آن می‌توان امتیازهای یک فرایند را در محیطی ایزوله (sandbox) محدود کرد و فراخوانی‌هایی را که فرایند می‌تواند از فضای کاربر به هسته انجام دهد، محدود ساخت. کوبرنتیز به شما امکان می‌دهد پروفایل‌های seccomp بارگذاری‌شده روی یک نود را به‌طور خودکار روی Podها و کانتینرهای خود اعمال کنید.

قابلیت Seccomp می‌تواند با کاهش سطح حملهٔ فراخوانی‌های سیستمی هستهٔ لینوکس که درون کانتینرها در دسترس است، امنیت بارهای کاری شما را بهبود دهد. حالت فیلتر seccomp از BPF بهره می‌گیرد تا فهرستی مجاز یا ممنوع از فراخوانی‌های سیستمی مشخص ایجاد کند که پروفایل نامیده می‌شوند.

از کوبرنتیز 1.27 به بعد، می‌توانید استفاده از `RuntimeDefault` را به‌عنوان پروفایل پیش‌فرض seccomp برای همهٔ بارهای کاری فعال کنید. یک [آموزش امنیتی](/docs/tutorials/security/seccomp/) دربارهٔ این موضوع در دسترس است. افزون بر این، [Kubernetes Security Profiles Operator](https://github.com/kubernetes-sigs/security-profiles-operator) پروژه‌ای است که مدیریت و استفاده از seccomp را در کلاسترها آسان می‌کند.

{{< note >}}
قابلیت Seccomp فقط روی نودهای لینوکسی در دسترس است.
{{< /note >}}

### فعال‌سازی AppArmor یا SELinux

#### AppArmor

ماژول [AppArmor](/docs/tutorials/security/apparmor/) یکی از ماژول‌های امنیتی هستهٔ لینوکس است که روشی آسان برای پیاده‌سازی کنترل دسترسی اجباری (MAC) و ممیزی بهتر از طریق لاگ‌های سیستم فراهم می‌کند. روی نودهایی که از آن پشتیبانی می‌کنند، یک پروفایل پیش‌فرض AppArmor اجباری می‌شود؛ همچنین می‌توان یک پروفایل سفارشی پیکربندی کرد. ماژول AppArmor نیز مانند seccomp از طریق پروفایل‌ها پیکربندی می‌شود. هر پروفایل یا در حالت اجباری (enforcing) اجرا می‌شود که دسترسی به منابع غیرمجاز را مسدود می‌کند، یا در حالت شکایت (complain) که فقط تخلف‌ها را گزارش می‌دهد. پروفایل‌های AppArmor به‌ازای هر کانتینر و با یک حاشیه‌نویسی (annotation) اعمال می‌شوند و به این ترتیب فرایندها دقیقاً همان امتیازهای لازم را به دست می‌آورند.

{{< note >}}
ماژول AppArmor فقط روی نودهای لینوکسی در دسترس است و در [برخی از توزیع‌های لینوکس](https://gitlab.com/apparmor/apparmor/-/wikis/home#distributions-and-ports) فعال است.
{{< /note >}}

#### SELinux

ماژول [SELinux](https://github.com/SELinuxProject/selinux-notebook/blob/main/src/selinux_overview.md) نیز یکی از ماژول‌های امنیتی هستهٔ لینوکس است که سازوکاری برای پشتیبانی از سیاست‌های امنیتی کنترل دسترسی، از جمله کنترل‌های دسترسی اجباری (MAC)، فراهم می‌کند. برچسب‌های SELinux را می‌توان [از طریق بخش `securityContext`](/docs/tasks/configure-pod-container/security-context/#assign-selinux-labels-to-a-container) به کانتینرها یا پادها اختصاص داد.

{{< note >}}
ماژول SELinux فقط روی نودهای لینوکسی در دسترس است و در [برخی از توزیع‌های لینوکس](https://en.wikipedia.org/wiki/Security-Enhanced_Linux#Implementations) فعال است.
{{< /note >}}

## لاگ‌ها و ممیزی

- [ ] لاگ‌های ممیزی (audit logs)، در صورت فعال بودن، در برابر دسترسی عمومی محافظت می‌شوند.


## جای‌گذاری Pod

- [ ] جای‌گذاری پادها مطابق با سطوح حساسیت برنامه انجام می‌شود.
- [ ] برنامه‌های حساس به‌صورت ایزوله روی نودهای جداگانه یا با محیط‌های اجرای ایزولهٔ (sandboxed) مشخص اجرا می‌شوند.

پادهایی که در سطوح حساسیت متفاوتی قرار دارند، برای مثال پاد یک برنامه و سرور API کوبرنتیز، باید روی نودهای جداگانه مستقر شوند. هدف از ایزوله‌سازی نودها این است که اگر کسی از کانتینر یک برنامه فرار (breakout) کند، مستقیماً به برنامه‌هایی با سطح حساسیت بالاتر دسترسی پیدا نکند و نتواند به‌آسانی درون کلاستر جابه‌جا شود. این جداسازی باید اجباری شود تا از استقرار تصادفی پادها روی یک نود مشترک جلوگیری شود. این کار را می‌توان با قابلیت‌های زیر اجباری کرد:

[انتخابگرهای نود](/docs/concepts/scheduling-eviction/assign-pod-node/)
: جفت‌های کلید-مقدار در مشخصات پاد که تعیین می‌کنند پاد روی کدام نودها مستقر شود. این موارد را می‌توان در سطح فضای نام و کلاستر با کنترل‌کنندهٔ پذیرش [PodNodeSelector](/docs/reference/access-authn-authz/admission-controllers/#podnodeselector) اجباری کرد.

[PodTolerationRestriction](/docs/reference/access-authn-authz/admission-controllers/#podtolerationrestriction)
: کنترل‌کنندهٔ پذیرشی که به مدیران امکان می‌دهد [تحمل‌های (tolerations)](/docs/concepts/scheduling-eviction/taint-and-toleration/) مجاز درون یک فضای نام را محدود کنند. پادهای درون یک فضای نام فقط می‌توانند از تحمل‌هایی استفاده کنند که در کلیدهای حاشیه‌نویسی آبجکت فضای نام مشخص شده‌اند؛ این کلیدها مجموعه‌ای از تحمل‌های پیش‌فرض و مجاز را تعیین می‌کنند.

[RuntimeClass](/docs/concepts/containers/runtime-class/)
: منبع RuntimeClass قابلیتی برای انتخاب پیکربندی محیط اجرای کانتینر است. پیکربندی محیط اجرای کانتینر برای اجرای کانتینرهای یک Pod استفاده می‌شود و می‌تواند به بهای سربار کارایی، ایزوله‌سازی بیشتر یا کمتری از میزبان فراهم کند.

## Secretها

- [ ] از ConfigMapها برای نگهداری داده‌های محرمانه استفاده نمی‌شود.
- [ ] رمزنگاری داده‌ها در حالت سکون (encryption at rest) برای API مربوط به Secret پیکربندی شده است.
- [ ] در صورت لزوم، سازوکاری برای تزریق رازهای ذخیره‌شده در ذخیره‌سازهای شخص ثالث مستقر شده و در دسترس است.
- [ ] توکن‌های حساب سرویس (service account) در پادهایی که به آن‌ها نیاز ندارند مانت نمی‌شوند.
- [ ] به‌جای توکن‌های بدون انقضا، از [حجم (volume) توکن حساب سرویس محدودشده](/docs/reference/access-authn-authz/service-accounts-admin/#bound-service-account-token-volume) استفاده می‌شود.

رازهای (secrets) موردنیاز پادها باید به‌جای جایگزین‌هایی مانند ConfigMap، در Secretهای کوبرنتیز ذخیره شوند. منابع Secret ذخیره‌شده در etcd باید [در حالت سکون رمزنگاری شوند](/docs/tasks/administer-cluster/encrypt-data/).

پادهایی که به رازها نیاز دارند، باید آن‌ها را به‌طور خودکار از طریق حجم‌ها مانت کنند؛ ترجیحاً به‌گونه‌ای که در حافظه ذخیره شوند، مانند [گزینهٔ `emptyDir.medium`](/docs/concepts/storage/volumes/#emptydir). همچنین می‌توان از سازوکارهایی برای تزریق رازها از ذخیره‌سازهای شخص ثالث به‌صورت حجم استفاده کرد، مانند [Secrets Store CSI Driver](https://secrets-store-csi-driver.sigs.k8s.io/). این روش بر اعطای دسترسی RBAC به رازها برای حساب سرویس پادها ترجیح دارد. با این کار می‌توان رازها را به‌صورت متغیرهای محیطی یا فایل به پاد افزود. توجه داشته باشید که روش متغیر محیطی، در مقایسه با سازوکار مجوزها روی فایل‌ها، ممکن است به دلیل ثبت crash dumpها در لاگ‌ها و ماهیت غیرمحرمانهٔ متغیرهای محیطی در لینوکس، بیشتر در معرض نشت باشد.

توکن‌های حساب سرویس نباید در پادهایی که به آن‌ها نیاز ندارند مانت شوند. این کار را می‌توان با تنظیم [`automountServiceAccountToken`](/docs/tasks/configure-pod-container/configure-service-account/#use-the-default-service-account-to-access-the-api-server) روی `false` پیکربندی کرد؛ یا درون حساب سرویس تا در کل فضای نام اعمال شود، یا به‌طور خاص برای یک پاد. در کوبرنتیز نسخهٔ v1.22 و بالاتر، برای اعتبارنامه‌های حساب سرویس با محدودیت زمانی از [حساب‌های سرویس محدودشده](/docs/reference/access-authn-authz/service-accounts-admin/#bound-service-account-token-volume) استفاده کنید.

## ایمیج‌ها

- [ ] محتوای غیرضروری ایمیج‌های کانتینر را به حداقل برسانید.
- [ ] ایمیج‌های کانتینر طوری پیکربندی شده‌اند که با کاربر بدون امتیاز (unprivileged) اجرا شوند.
- [ ] ارجاع به ایمیج‌های کانتینر با digestهای sha256 (به‌جای تگ‌ها) انجام می‌شود، یا منشأ ایمیج با بررسی امضای دیجیتال آن در زمان استقرار [از طریق کنترل پذیرش](/docs/tasks/administer-cluster/verify-signed-artifacts/#verifying-image-signatures-with-admission-controller) تأیید می‌شود.
- [ ] ایمیج‌های کانتینر به‌طور منظم در زمان ساخت و در زمان استقرار اسکن می‌شوند و نرم‌افزارهای دارای آسیب‌پذیری شناخته‌شده وصله می‌شوند.

هر ایمیج کانتینر باید فقط حداقل موارد لازم برای اجرای برنامه‌ای را که بسته‌بندی می‌کند در بر داشته باشد؛ ترجیحاً فقط خود برنامه و وابستگی‌هایش، و ایمیج از کوچک‌ترین پایهٔ ممکن ساخته شود. به‌ویژه، ایمیجی که در محیط عملیاتی استفاده می‌شود نباید شامل پوسته (shell) یا ابزارهای اشکال‌زدایی باشد، زیرا برای عیب‌یابی می‌توان از یک [کانتینر اشکال‌زدایی موقت](/docs/tasks/debug/debug-application/debug-running-pod/#ephemeral-container) استفاده کرد.

ایمیج‌ها را طوری بسازید که مستقیماً با یک کاربر بدون امتیاز شروع به کار کنند؛ برای این کار از [دستور `USER` در Dockerfile](https://docs.docker.com/develop/develop-images/dockerfile_best-practices/#user) استفاده کنید. [زمینهٔ امنیتی](/docs/tasks/configure-pod-container/security-context/#set-the-security-context-for-a-pod) امکان می‌دهد ایمیج کانتینر با کاربر و گروه مشخصی از طریق `runAsUser` و `runAsGroup` اجرا شود، حتی اگر این موارد در مانیفست ایمیج مشخص نشده باشند. با این حال، مجوزهای فایل در لایه‌های ایمیج ممکن است اجرای فرایند با یک کاربر بدون امتیاز جدید را، بدون تغییر ایمیج، ناممکن کنند.

از تگ‌ها برای ارجاع به ایمیج استفاده نکنید، به‌ویژه از تگ `latest`؛ زیرا ایمیجی که پشت یک تگ قرار دارد به‌آسانی در رجیستری تغییرپذیر است. استفاده از digest کامل `sha256` را که برای مانیفست ایمیج یکتاست ترجیح دهید. این سیاست را می‌توان از طریق [ImagePolicyWebhook](/docs/reference/access-authn-authz/admission-controllers/#imagepolicywebhook) اجباری کرد. امضای ایمیج‌ها را نیز می‌توان در زمان استقرار به‌طور خودکار [با یک کنترل‌کنندهٔ پذیرش تأیید کرد](/docs/tasks/administer-cluster/verify-signed-artifacts/#verifying-image-signatures-with-admission-controller) تا اصالت و یکپارچگی آن‌ها بررسی شود.

اسکن کردن ایمیج کانتینر می‌تواند از ورود آسیب‌پذیری‌های بحرانی همراه با ایمیج کانتینر به کلاستر جلوگیری کند. اسکن ایمیج باید پیش از استقرار ایمیج کانتینر در کلاستر کامل شود و معمولاً به‌عنوان بخشی از فرایند استقرار در یک خط لولهٔ CI/CD انجام می‌شود. هدف از اسکن ایمیج، به دست آوردن اطلاعاتی دربارهٔ آسیب‌پذیری‌های احتمالی ایمیج کانتینر و راه‌های پیشگیری از آن‌هاست؛ مانند امتیاز [Common Vulnerability Scoring System (CVSS)](https://www.first.org/cvss/). اگر نتیجهٔ اسکن ایمیج‌ها با قوانین انطباق خط لوله ترکیب شود، فقط ایمیج‌های کانتینری که به‌درستی وصله شده‌اند به محیط عملیاتی راه پیدا می‌کنند.

## کنترل‌کننده‌های پذیرش

- [ ] مجموعه‌ای مناسب از کنترل‌کننده‌های پذیرش فعال شده است.
- [ ] یک سیاست امنیتی Pod به‌وسیلهٔ Pod Security Admission و/یا یک کنترل‌کنندهٔ
  پذیرش وب‌هوک اعمال می‌شود.
- [ ] افزونه‌ها و وب‌هوک‌های زنجیرهٔ پذیرش به‌صورت امن پیکربندی شده‌اند.

کنترل‌کننده‌های پذیرش (admission controllers) می‌توانند به بهبود امنیت کلاستر کمک کنند. با این حال،
از آنجا که API server را گسترش می‌دهند، خودشان نیز ممکن است خطراتی به همراه داشته باشند و
[باید به‌درستی ایمن شوند](/blog/2022/01/19/secure-your-admission-controllers-and-webhooks/).

فهرست‌های زیر تعدادی از کنترل‌کننده‌های پذیرش را معرفی می‌کنند که می‌توان برای تقویت وضعیت
امنیتی کلاستر و برنامهٔ خود از آن‌ها استفاده کرد. این فهرست‌ها شامل کنترل‌کننده‌هایی نیز هستند
که ممکن است در بخش‌های دیگر این سند به آن‌ها اشاره شده باشد.

گروه نخست کنترل‌کننده‌های پذیرش شامل افزونه‌هایی است که
[به‌طور پیش‌فرض فعال هستند](/docs/reference/access-authn-authz/admission-controllers/#which-plugins-are-enabled-by-default).
توصیه می‌شود آن‌ها را فعال نگه دارید، مگر اینکه دقیقاً بدانید چه می‌کنید:

[`CertificateApproval`](/docs/reference/access-authn-authz/admission-controllers/#certificateapproval)
: بررسی‌های مجوزدهی بیشتری انجام می‌دهد تا اطمینان حاصل شود کاربرِ تأییدکننده اجازهٔ تأیید
درخواست گواهی را دارد.

[`CertificateSigning`](/docs/reference/access-authn-authz/admission-controllers/#certificatesigning)
: بررسی‌های مجوزدهی بیشتری انجام می‌دهد تا اطمینان حاصل شود کاربرِ امضاکننده اجازهٔ امضای
درخواست‌های گواهی را دارد.

[`CertificateSubjectRestriction`](/docs/reference/access-authn-authz/admission-controllers/#certificatesubjectrestriction)
: هر درخواست گواهی‌ای را که در آن «group» (یا «organization attribute») برابر با
`system:masters` تعیین شده باشد، رد می‌کند.

[`LimitRanger`](/docs/reference/access-authn-authz/admission-controllers/#limitranger)
: محدودیت‌های API مربوط به LimitRange را اعمال می‌کند.

[`MutatingAdmissionWebhook`](/docs/reference/access-authn-authz/admission-controllers/#mutatingadmissionwebhook)
: امکان استفاده از کنترل‌کننده‌های سفارشی را از طریق وب‌هوک‌ها فراهم می‌کند. این کنترل‌کننده‌ها
ممکن است درخواست‌هایی را که بررسی می‌کنند تغییر دهند.

[`PodSecurity`](/docs/reference/access-authn-authz/admission-controllers/#podsecurity)
: جایگزین Pod Security Policy است و زمینه‌های امنیتی (security contexts) Podهای مستقرشده را
محدود می‌کند.

[`ResourceQuota`](/docs/reference/access-authn-authz/admission-controllers/#resourcequota)
: سهمیه‌های منابع را اعمال می‌کند تا از مصرف بیش از حد منابع جلوگیری شود.

[`ValidatingAdmissionWebhook`](/docs/reference/access-authn-authz/admission-controllers/#validatingadmissionwebhook)
: امکان استفاده از کنترل‌کننده‌های سفارشی را از طریق وب‌هوک‌ها فراهم می‌کند. این کنترل‌کننده‌ها
درخواست‌هایی را که بررسی می‌کنند تغییر نمی‌دهند.

گروه دوم شامل افزونه‌هایی است که به‌طور پیش‌فرض فعال نیستند، اما در وضعیت دسترس‌پذیری عمومی
(general availability) قرار دارند و برای بهبود وضعیت امنیتی شما توصیه می‌شوند:

[`DenyServiceExternalIPs`](/docs/reference/access-authn-authz/admission-controllers/#denyserviceexternalips)
: هرگونه استفادهٔ جدید از فیلد `Service.spec.externalIPs` را رد می‌کند. این کار راهکاری برای کاهش
اثر آسیب‌پذیری
[CVE-2020-8554: Man in the middle using LoadBalancer or ExternalIPs](https://github.com/kubernetes/kubernetes/issues/97076)
است.

[`NodeRestriction`](/docs/reference/access-authn-authz/admission-controllers/#noderestriction)
: مجوزهای kubelet را محدود می‌کند تا فقط بتواند منابع API مربوط به Podهایی را که متعلق به خودش
هستند یا منبع API نودی را که خودش را نمایندگی می‌کند تغییر دهد. همچنین از استفادهٔ kubelet از
حاشیه‌نویسی (annotation) `node-restriction.kubernetes.io/` جلوگیری می‌کند؛ مهاجمی که به
اعتبارنامه‌های kubelet دسترسی داشته باشد، می‌تواند از این حاشیه‌نویسی برای اثرگذاری بر جای‌گیری
Podها روی نودِ تحت کنترل خود استفاده کند.

گروه سوم شامل افزونه‌هایی است که به‌طور پیش‌فرض فعال نیستند، اما می‌توان استفاده از آن‌ها را
برای برخی موارد کاربرد خاص در نظر گرفت:

[`AlwaysPullImages`](/docs/reference/access-authn-authz/admission-controllers/#alwayspullimages)
: استفاده از آخرین نسخهٔ یک ایمیج برچسب‌دار را الزامی می‌کند و اطمینان حاصل می‌کند که
مستقرکننده اجازهٔ استفاده از آن ایمیج را دارد.

[`ImagePolicyWebhook`](/docs/reference/access-authn-authz/admission-controllers/#imagepolicywebhook)
: امکان اعمال کنترل‌های بیشتر بر ایمیج‌ها را از طریق وب‌هوک‌ها فراهم می‌کند.
