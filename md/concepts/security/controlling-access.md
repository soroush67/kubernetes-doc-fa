<!-- overview -->
این صفحه مروری بر کنترل دسترسی به API کوبرنتیز ارائه می‌دهد.

<!-- body -->
کاربران با استفاده از `kubectl`، کتابخانه‌های کلاینت، یا با ارسال درخواست‌های REST به
[API کوبرنتیز](/docs/concepts/overview/kubernetes-api/) دسترسی پیدا می‌کنند. هم کاربران انسانی و هم
[حساب‌های سرویس کوبرنتیز](/docs/tasks/configure-pod-container/configure-service-account/) می‌توانند
برای دسترسی به API مجوز بگیرند.
هنگامی که یک درخواست به API می‌رسد، از چندین مرحله عبور می‌کند که در
نمودار زیر نشان داده شده‌اند:

![نمودار مراحل پردازش درخواست برای یک درخواست API کوبرنتیز](/images/docs/admin/access-control-overview.svg)

## امنیت انتقال

به‌طور پیش‌فرض، API server کوبرنتیز روی پورت 6443 در نخستین رابط شبکهٔ
غیر localhost گوش می‌دهد و با TLS محافظت می‌شود. در یک کلاستر کوبرنتیز تولیدی معمول،
API روی پورت 443 سرویس می‌دهد. پورت را می‌توان با `--secure-port` و
نشانی IP شنود را با فلگ `--bind-address` تغییر داد.

API server یک گواهی‌نامه ارائه می‌کند. این گواهی‌نامه ممکن است با استفاده از
یک مرجع صدور گواهی‌نامهٔ (CA) خصوصی امضا شده باشد، یا مبتنی بر یک زیرساخت کلید عمومی مرتبط
با یک CA عموماً شناخته‌شده باشد. گواهی‌نامه و کلید خصوصی متناظر آن را می‌توان
با استفاده از فلگ‌های `--tls-cert-file` و `--tls-private-key-file` تنظیم کرد.

اگر کلاستر شما از یک مرجع صدور گواهی‌نامهٔ خصوصی استفاده می‌کند، به نسخه‌ای از گواهی‌نامهٔ آن CA
نیاز دارید که در `~/.kube/config` روی کلاینت پیکربندی شده باشد، تا بتوانید
به اتصال اعتماد کنید و مطمئن باشید که رهگیری نشده است.

کلاینت شما می‌تواند در این مرحله یک گواهی‌نامهٔ کلاینت TLS ارائه کند.

## احراز هویت

پس از برقراری TLS، درخواست HTTP به مرحلهٔ احراز هویت می‌رود.
این مرحله در نمودار به‌عنوان گام **1** نشان داده شده است.
اسکریپت ایجاد کلاستر یا مدیر کلاستر، API server را طوری پیکربندی می‌کند که
یک یا چند ماژول احراز هویت‌کننده (Authenticator) را اجرا کند.
احراز هویت‌کننده‌ها با جزئیات بیشتر در
[احراز هویت](/docs/reference/access-authn-authz/authentication/) توصیف شده‌اند.

ورودی مرحلهٔ احراز هویت کل درخواست HTTP است؛ با این حال، این مرحله معمولاً
سرآیندها و/یا گواهی‌نامهٔ کلاینت را بررسی می‌کند.

ماژول‌های احراز هویت شامل گواهی‌نامه‌های کلاینت، گذرواژه و توکن‌های ساده،
توکن‌های راه‌اندازی (bootstrap token)، و JSON Web Tokenها (که برای حساب‌های سرویس استفاده می‌شوند) هستند.

می‌توان چندین ماژول احراز هویت را مشخص کرد که در این صورت هر یک به ترتیب امتحان می‌شود،
تا زمانی که یکی از آن‌ها موفق شود.

اگر درخواست قابل احراز هویت نباشد، با کد وضعیت HTTP 401 رد می‌شود.
در غیر این صورت، کاربر به‌عنوان یک `username` مشخص احراز هویت می‌شود و نام کاربری
برای استفاده در تصمیم‌های مراحل بعدی در دسترس قرار می‌گیرد. برخی از احراز هویت‌کننده‌ها
عضویت‌های گروهی کاربر را نیز فراهم می‌کنند، در حالی که سایر احراز هویت‌کننده‌ها
این کار را نمی‌کنند.

اگرچه کوبرنتیز از نام‌های کاربری برای تصمیم‌های کنترل دسترسی و در ثبت لاگ درخواست‌ها استفاده می‌کند،
آبجکتی به نام `User` ندارد و نام‌های کاربری یا سایر اطلاعات مربوط به
کاربران را در API خود ذخیره نمی‌کند.

## مجوزدهی

پس از آنکه درخواست به‌عنوان درخواستی از یک کاربر مشخص احراز هویت شد، درخواست باید
مجوزدهی شود. این مرحله در نمودار به‌عنوان گام **2** نشان داده شده است.

یک درخواست باید شامل نام کاربری درخواست‌کننده، اقدام درخواست‌شده، و
آبجکتی که اقدام بر آن تأثیر می‌گذارد باشد. درخواست در صورتی مجوز می‌گیرد که یک سیاست موجود
اعلام کند که کاربر مجوز انجام اقدام درخواست‌شده را دارد.

برای مثال، اگر Bob سیاست زیر را داشته باشد، تنها می‌تواند پادها را در فضای نام `projectCaribou` بخواند:

```json
{
    "apiVersion": "abac.authorization.kubernetes.io/v1beta1",
    "kind": "Policy",
    "spec": {
        "user": "bob",
        "namespace": "projectCaribou",
        "resource": "pods",
        "readonly": true
    }
}
```

اگر Bob درخواست زیر را ارسال کند، درخواست مجوز می‌گیرد زیرا او
مجاز به خواندن آبجکت‌ها در فضای نام `projectCaribou` است:

```json
{
  "apiVersion": "authorization.k8s.io/v1beta1",
  "kind": "SubjectAccessReview",
  "spec": {
    "resourceAttributes": {
      "namespace": "projectCaribou",
      "verb": "get",
      "group": "unicorn.example.org",
      "resource": "pods"
    }
  }
}
```

اگر Bob درخواستی برای نوشتن (`create` یا `update`) در آبجکت‌های
فضای نام `projectCaribou` ارسال کند، مجوز او رد می‌شود. اگر Bob درخواستی
برای خواندن (`get`) آبجکت‌ها در فضای نام دیگری مانند `projectFish` ارسال کند، مجوز او رد می‌شود.

مجوزدهی کوبرنتیز مستلزم آن است که از ویژگی‌های رایج REST برای تعامل
با سیستم‌های کنترل دسترسی موجود در سطح سازمان یا در سطح ارائه‌دهندهٔ ابری استفاده کنید.
استفاده از قالب‌بندی REST اهمیت دارد، زیرا این سیستم‌های کنترلی ممکن است
علاوه بر API کوبرنتیز با APIهای دیگری نیز تعامل داشته باشند.

کوبرنتیز از چندین ماژول مجوزدهی، مانند حالت ABAC، حالت RBAC،
و حالت Webhook پشتیبانی می‌کند. هنگامی که یک مدیر کلاستری ایجاد می‌کند، ماژول‌های
مجوزدهی‌ای را که باید در API server استفاده شوند پیکربندی می‌کند. اگر بیش از یک
ماژول مجوزدهی پیکربندی شده باشد، کوبرنتیز هر ماژول را بررسی می‌کند و اگر
هر یک از ماژول‌ها درخواست را مجاز کند، درخواست می‌تواند ادامه یابد. اگر همهٔ
ماژول‌ها درخواست را رد کنند، درخواست رد می‌شود (کد وضعیت HTTP 403).

برای آشنایی بیشتر با مجوزدهی کوبرنتیز، از جمله جزئیات ایجاد
سیاست‌ها با استفاده از ماژول‌های مجوزدهی پشتیبانی‌شده، به [مجوزدهی](/docs/reference/access-authn-authz/authorization/) مراجعه کنید.

## کنترل پذیرش

ماژول‌های کنترل پذیرش، ماژول‌های نرم‌افزاری‌ای هستند که می‌توانند درخواست‌ها را تغییر دهند یا رد کنند.
علاوه بر ویژگی‌هایی که در اختیار ماژول‌های مجوزدهی قرار دارد، ماژول‌های کنترل
پذیرش می‌توانند به محتوای آبجکتی که در حال ایجاد یا تغییر است دسترسی داشته باشند.

کنترل‌کننده‌های پذیرش بر درخواست‌هایی عمل می‌کنند که یک آبجکت را ایجاد، تغییر یا حذف می‌کنند یا به آن متصل می‌شوند (proxy).
کنترل‌کننده‌های پذیرش بر درخواست‌هایی که صرفاً آبجکت‌ها را می‌خوانند عمل نمی‌کنند.
هنگامی که چندین کنترل‌کنندهٔ پذیرش پیکربندی شده باشند، به ترتیب فراخوانی می‌شوند.

این مرحله در نمودار به‌عنوان گام **3** نشان داده شده است.

برخلاف ماژول‌های احراز هویت و مجوزدهی، اگر هر یک از ماژول‌های کنترل‌کنندهٔ پذیرش
درخواست را رد کند، درخواست بلافاصله رد می‌شود.

علاوه بر رد کردن آبجکت‌ها، کنترل‌کننده‌های پذیرش می‌توانند مقادیر پیش‌فرض پیچیده‌ای را نیز برای
فیلدها تنظیم کنند.

ماژول‌های کنترل پذیرش موجود در [کنترل‌کننده‌های پذیرش](/docs/reference/access-authn-authz/admission-controllers/) توصیف شده‌اند.

پس از آنکه درخواستی از همهٔ کنترل‌کننده‌های پذیرش عبور کرد، با استفاده از روال‌های اعتبارسنجی
آبجکت API متناظر اعتبارسنجی می‌شود و سپس در مخزن آبجکت‌ها نوشته می‌شود (که به‌عنوان گام **4** نشان داده شده است).

## ممیزی

ممیزی کوبرنتیز مجموعه‌ای مرتبط با امنیت و به ترتیب زمانی از رکوردها را فراهم می‌کند که توالی اقدامات انجام‌شده در یک کلاستر را مستند می‌کند.
کلاستر فعالیت‌های ایجادشده توسط کاربران، توسط برنامه‌هایی که از API کوبرنتیز استفاده می‌کنند، و توسط خود control plane را ممیزی می‌کند.

برای اطلاعات بیشتر، به [ممیزی](/docs/tasks/debug/debug-cluster/audit/) مراجعه کنید.
