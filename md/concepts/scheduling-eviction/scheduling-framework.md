_چارچوب زمان‌بندی_ (scheduling framework) یک معماری افزونه‌پذیر برای زمان‌بند کوبرنتیز است.
این چارچوب از مجموعه‌ای از APIهای «افزونه» (plugin) تشکیل شده است که مستقیماً درون زمان‌بند کامپایل می‌شوند.
این APIها امکان می‌دهند بیشتر قابلیت‌های زمان‌بندی به‌صورت افزونه پیاده‌سازی شوند،
در حالی که «هسته»ٔ زمان‌بندی سبک و قابل نگهداری باقی می‌ماند. برای اطلاعات فنی بیشتر درباره‌ی
طراحی این چارچوب، به [پیشنهاد طراحی چارچوب زمان‌بندی][kep] مراجعه کنید.

[kep]: https://github.com/kubernetes/enhancements/blob/master/keps/sig-scheduling/624-scheduling-framework/README.md

<!-- body -->

## گردش کار چارچوب {#framework-workflow}

چارچوب زمان‌بندی چند نقطه‌ی توسعه (extension point) تعریف می‌کند. افزونه‌های زمان‌بند
ثبت می‌شوند تا در یک یا چند نقطه‌ی توسعه فراخوانی شوند. برخی از این افزونه‌ها
می‌توانند تصمیم‌های زمان‌بندی را تغییر دهند و برخی صرفاً جنبه‌ی اطلاعاتی دارند.

هر تلاش برای زمان‌بندی یک Pod به دو مرحله تقسیم می‌شود:
**چرخه‌ی زمان‌بندی** (scheduling cycle) و **چرخه‌ی اتصال** (binding cycle).

### چرخه‌ی زمان‌بندی و چرخه‌ی اتصال {#scheduling-cycle-binding-cycle}

چرخه‌ی زمان‌بندی یک نود را برای Pod انتخاب می‌کند و چرخه‌ی اتصال آن تصمیم را در
کلاستر اعمال می‌کند. یک چرخه‌ی زمان‌بندی و یک چرخه‌ی اتصال با هم
«بافت زمان‌بندی» (scheduling context) نامیده می‌شوند.

چرخه‌های زمان‌بندی به‌صورت ترتیبی اجرا می‌شوند، در حالی که چرخه‌های اتصال ممکن است به‌صورت همزمان اجرا شوند.

اگر مشخص شود که Pod قابل زمان‌بندی نیست یا خطای داخلی رخ دهد، چرخه‌ی زمان‌بندی یا اتصال می‌تواند لغو شود.
در این صورت Pod به صف بازگردانده می‌شود و دوباره تلاش می‌شود.

## رابط‌ها {#interfaces}

تصویر زیر بافت زمان‌بندی یک Pod و رابط‌هایی (interfaces) را نشان می‌دهد
که چارچوب زمان‌بندی در اختیار می‌گذارد.

یک افزونه می‌تواند چند رابط را پیاده‌سازی کند تا وظایف پیچیده‌تر یا
حالت‌مند (stateful) را انجام دهد.

برخی رابط‌ها با نقاط توسعه‌ی زمان‌بند مطابقت دارند که از طریق
[پیکربندی زمان‌بند](/docs/reference/scheduling/config/#extension-points) قابل تنظیم هستند.

{{< figure src="/images/docs/scheduling-framework-extensions.png" title="نقاط توسعه‌ی چارچوب زمان‌بندی" class="diagram-large">}}

### PreEnqueue {#pre-enqueue}

این افزونه‌ها پیش از افزودن Podها به صف فعال داخلی فراخوانی می‌شوند؛ صفی که در آن Podها
آماده‌ی زمان‌بندی علامت‌گذاری می‌شوند.

فقط زمانی که همه‌ی افزونه‌های PreEnqueue مقدار `Success` را برگردانند، Pod اجازه‌ی ورود به صف فعال را می‌یابد.
در غیر این صورت، Pod در فهرست داخلی Podهای غیرقابل زمان‌بندی قرار می‌گیرد و شرط (condition) `Unschedulable` برای آن ثبت نمی‌شود.

برای جزئیات بیشتر درباره‌ی نحوه‌ی کار صف‌های داخلی زمان‌بند، به
[Scheduling queue in kube-scheduler](https://github.com/kubernetes/community/blob/f03b6d5692bd979f07dd472e7b6836b2dad0fd9b/contributors/devel/sig-scheduling/scheduler_queues.md)
مراجعه کنید.

### EnqueueExtension {#enqueueextension}

EnqueueExtension رابطی است که افزونه از طریق آن می‌تواند بر اساس تغییرات کلاستر کنترل کند
که آیا زمان‌بندی Podهای ردشده توسط این افزونه دوباره تلاش شود یا خیر.
افزونه‌هایی که PreEnqueue، PreFilter، Filter، Reserve یا Permit را پیاده‌سازی می‌کنند باید این رابط را نیز پیاده‌سازی کنند.

### QueueingHint {#queueinghint}

{{< feature-state feature_gate_name="SchedulerQueueingHints" >}}

QueueingHint یک تابع فراخوانی‌شونده (callback) است که تصمیم می‌گیرد آیا یک Pod می‌تواند دوباره به صف فعال یا صف backoff برگردانده شود.
این تابع هر بار که نوع مشخصی از رویداد یا تغییر در کلاستر رخ دهد اجرا می‌شود.
وقتی QueueingHint تشخیص دهد که رویداد ممکن است Pod را قابل زمان‌بندی کند،
Pod در صف فعال یا صف backoff قرار می‌گیرد
تا زمان‌بند زمان‌بندی Pod را دوباره تلاش کند.

### QueueSort {#queue-sort}

این افزونه‌ها برای مرتب‌سازی Podها در صف زمان‌بندی استفاده می‌شوند. یک افزونه‌ی مرتب‌سازی صف
در اصل تابعی به نام `Less(Pod1, Pod2)` فراهم می‌کند. در هر زمان فقط یک افزونه‌ی
مرتب‌سازی صف می‌تواند فعال باشد.

### PreFilter {#pre-filter}

این افزونه‌ها برای پیش‌پردازش اطلاعات مربوط به Pod یا بررسی شرایط مشخصی که
کلاستر یا Pod باید برآورده کند استفاده می‌شوند. اگر یک افزونه‌ی PreFilter
خطا برگرداند، چرخه‌ی زمان‌بندی لغو می‌شود.

### Filter {#filter}

این افزونه‌ها برای حذف نودهایی استفاده می‌شوند که نمی‌توانند Pod را اجرا کنند. برای هر
نود، زمان‌بند افزونه‌های filter را به ترتیب پیکربندی‌شده‌ی آن‌ها فراخوانی می‌کند. اگر هر
افزونه‌ی filter نود را نامناسب (infeasible) علامت‌گذاری کند، افزونه‌های باقی‌مانده برای
آن نود فراخوانی نمی‌شوند. نودها ممکن است به‌صورت همزمان ارزیابی شوند.

### PostFilter {#post-filter}

این افزونه‌ها پس از مرحله‌ی Filter فراخوانی می‌شوند، اما فقط زمانی که هیچ نود مناسبی
برای Pod پیدا نشده باشد. افزونه‌ها به ترتیب پیکربندی‌شده‌ی خود فراخوانی می‌شوند. اگر
هر افزونه‌ی postFilter نود را `Schedulable` علامت‌گذاری کند، افزونه‌های باقی‌مانده
فراخوانی نخواهند شد. نمونه‌ی متداول پیاده‌سازی PostFilter، تصاحب (preemption) است که
تلاش می‌کند با تصاحب منابع Podهای دیگر، Pod را قابل زمان‌بندی کند.

### PreScore {#pre-score}

این افزونه‌ها برای انجام کار «پیش‌امتیازدهی» استفاده می‌شوند که وضعیتی اشتراک‌پذیر تولید می‌کند
تا افزونه‌های Score از آن استفاده کنند. اگر یک افزونه‌ی PreScore خطا برگرداند،
چرخه‌ی زمان‌بندی لغو می‌شود.

### Score {#scoring}

این افزونه‌ها برای رتبه‌بندی نودهایی استفاده می‌شوند که از مرحله‌ی فیلتر عبور کرده‌اند.
زمان‌بند هر افزونه‌ی امتیازدهی را برای هر نود فراخوانی می‌کند. بازه‌ای کاملاً
مشخص از اعداد صحیح برای نمایش حداقل و حداکثر امتیاز وجود دارد. پس از مرحله‌ی
[NormalizeScore](#normalize-scoring)، زمان‌بند امتیازهای نود از همه‌ی افزونه‌ها را
بر اساس وزن‌های پیکربندی‌شده‌ی افزونه‌ها ترکیب می‌کند.

#### امتیازدهی بر اساس ظرفیت {#scoring-capacity}

{{< feature-state feature_gate_name="StorageCapacityScoring" >}}

feature gate با نام `VolumeCapacityPriority` در نسخه‌ی v1.32 برای پشتیبانی از ذخیره‌سازی
تأمین‌شده به‌صورت ایستا (static) استفاده می‌شد. از نسخه‌ی v1.33، feature gate جدید `StorageCapacityScoring`
جایگزین gate قدیمی `VolumeCapacityPriority` شده و پشتیبانی از ذخیره‌سازی تأمین‌شده به‌صورت پویا (dynamic) را نیز افزوده است.
وقتی `StorageCapacityScoring` فعال باشد، افزونه‌ی VolumeBinding در kube-scheduler گسترش می‌یابد
تا نودها را بر اساس ظرفیت ذخیره‌سازی هر کدام امتیازدهی کند.
این قابلیت برای حجم‌های (volume) CSI که از [ظرفیت ذخیره‌سازی](/docs/concepts/storage/storage-capacity/) پشتیبانی می‌کنند کاربرد دارد،
از جمله ذخیره‌سازی محلی که توسط یک درایور CSI پشتیبانی می‌شود.

### NormalizeScore {#normalize-scoring}

این افزونه‌ها برای تغییر امتیازها پیش از آن استفاده می‌شوند که زمان‌بند رتبه‌بندی نهایی
نودها را محاسبه کند. افزونه‌ای که برای این نقطه‌ی توسعه ثبت شده باشد، با
نتایج [Score](#scoring) همان افزونه فراخوانی می‌شود. این فراخوانی
در هر چرخه‌ی زمان‌بندی برای هر افزونه یک بار انجام می‌شود.

برای مثال، فرض کنید افزونه‌ای به نام `BlinkingLightScorer` نودها را بر اساس این رتبه‌بندی می‌کند که
چند چراغ چشمک‌زن دارند.

```go
func ScoreNode(_ *v1.pod, n *v1.Node) (int, error) {
    return getBlinkingLightCount(n)
}
```

با این حال، حداکثر تعداد چراغ‌های چشمک‌زن ممکن است در مقایسه با
`NodeScoreMax` کوچک باشد. برای رفع این مشکل، `BlinkingLightScorer` باید برای این
نقطه‌ی توسعه نیز ثبت شود.

```go
func NormalizeScores(scores map[string]int) {
    highest := 0
    for _, score := range scores {
        highest = max(highest, score)
    }
    for node, score := range scores {
        scores[node] = score*NodeScoreMax/highest
    }
}
```

اگر هر افزونه‌ی NormalizeScore خطا برگرداند، چرخه‌ی زمان‌بندی
لغو می‌شود.

{{< note >}}
افزونه‌هایی که می‌خواهند کار «پیش از رزرو» (pre-reserve) انجام دهند، باید از
نقطه‌ی توسعه‌ی NormalizeScore استفاده کنند.
{{< /note >}}

### Reserve {#reserve}

افزونه‌ای که رابط Reserve را پیاده‌سازی می‌کند دو متد دارد، یعنی `Reserve`
و `Unreserve`، که به ترتیب پشتوانه‌ی دو مرحله‌ی اطلاعاتی زمان‌بندی با نام Reserve
و Unreserve هستند. افزونه‌هایی که وضعیت زمان اجرا را نگهداری می‌کنند (که «افزونه‌های
حالت‌مند» نیز نامیده می‌شوند) باید از این مراحل استفاده کنند تا زمان‌بند هنگام رزرو و آزادسازی رزرو منابع
روی یک نود برای یک Pod مشخص، آن‌ها را مطلع کند.

مرحله‌ی Reserve پیش از آن رخ می‌دهد که زمان‌بند Pod را واقعاً به نود تعیین‌شده‌اش متصل (bind) کند. این مرحله برای
جلوگیری از شرایط رقابتی (race condition) وجود دارد، در حالی که زمان‌بند منتظر
موفقیت اتصال است. متد `Reserve` هر افزونه‌ی Reserve ممکن است موفق شود
یا شکست بخورد؛ اگر فراخوانی یک متد `Reserve` شکست بخورد، افزونه‌های بعدی اجرا نمی‌شوند
و مرحله‌ی Reserve ناموفق در نظر گرفته می‌شود. اگر متد `Reserve` همه‌ی
افزونه‌ها موفق شود، مرحله‌ی Reserve موفق در نظر گرفته می‌شود و
بقیه‌ی چرخه‌ی زمان‌بندی و چرخه‌ی اتصال اجرا می‌شوند.

مرحله‌ی Unreserve در صورتی فعال می‌شود که مرحله‌ی Reserve یا یکی از مراحل بعدی شکست بخورد.
در این حالت، متد `Unreserve` **همه‌ی** افزونه‌های Reserve به ترتیب معکوس
فراخوانی متدهای `Reserve` اجرا می‌شود. این مرحله برای
پاک‌سازی وضعیت مرتبط با Pod رزروشده وجود دارد.

{{< caution >}}
پیاده‌سازی متد `Unreserve` در افزونه‌های Reserve باید
خودتوان (idempotent) باشد و نباید شکست بخورد.
{{< /caution >}}

### Permit {#permit}

افزونه‌های _Permit_ در پایان چرخه‌ی زمان‌بندی برای هر Pod فراخوانی می‌شوند تا
از اتصال به نود کاندید جلوگیری کنند یا آن را به تأخیر بیندازند. یک افزونه‌ی permit می‌تواند یکی از
این سه کار را انجام دهد:

1.  **تأیید (approve)** \
    وقتی همه‌ی افزونه‌های Permit یک Pod را تأیید کنند، آن Pod برای اتصال ارسال می‌شود.

1.  **رد (deny)** \
    اگر هر افزونه‌ی Permit یک Pod را رد کند، Pod به صف زمان‌بندی بازگردانده می‌شود.
    این کار مرحله‌ی Unreserve را در [افزونه‌های Reserve](#reserve) فعال می‌کند.

1.  **انتظار (wait)** (با مهلت زمانی) \
    اگر یک افزونه‌ی Permit مقدار «wait» را برگرداند، Pod در یک فهرست داخلی Podهای «در انتظار»
    نگه داشته می‌شود و چرخه‌ی اتصال این Pod آغاز می‌شود اما بلافاصله مسدود می‌ماند تا
    تأیید شود. اگر مهلت زمانی به پایان برسد، **wait** به **deny** تبدیل می‌شود
    و Pod به صف زمان‌بندی بازگردانده می‌شود و مرحله‌ی
    Unreserve در [افزونه‌های Reserve](#reserve) فعال می‌شود.

{{< note >}}
اگرچه هر افزونه‌ای می‌تواند به فهرست Podهای «در انتظار» دسترسی داشته باشد و آن‌ها را تأیید کند
(به [`FrameworkHandle`](https://git.k8s.io/enhancements/keps/sig-scheduling/624-scheduling-framework#frameworkhandle) مراجعه کنید)،
انتظار می‌رود فقط افزونه‌های permit اتصال Podهای رزروشده‌ای را تأیید کنند که در وضعیت «در انتظار» هستند.
پس از تأیید یک Pod، به مرحله‌ی [PreBind](#pre-bind) ارسال می‌شود.
{{< /note >}}

### PreBind {#pre-bind}

این افزونه‌ها برای انجام هر کاری استفاده می‌شوند که پیش از اتصال یک Pod لازم است. برای
مثال، یک افزونه‌ی pre-bind ممکن است پیش از اجازه‌ی اجرای Pod روی نود هدف، یک حجم شبکه‌ای را
تأمین کند و آن را روی نود هدف mount کند.

اگر هر افزونه‌ی PreBind خطا برگرداند، Pod [رد](#reserve) شده و
به صف زمان‌بندی بازگردانده می‌شود.

### Bind {#bind}

این افزونه‌ها برای اتصال یک Pod به یک Node استفاده می‌شوند. افزونه‌های Bind تا زمانی که
همه‌ی افزونه‌های PreBind کامل نشده باشند فراخوانی نمی‌شوند. هر افزونه‌ی bind به
ترتیب پیکربندی‌شده فراخوانی می‌شود. یک افزونه‌ی bind می‌تواند انتخاب کند که Pod داده‌شده را
مدیریت کند یا نه. اگر یک افزونه‌ی bind مدیریت یک Pod را بپذیرد، **افزونه‌های bind باقی‌مانده
نادیده گرفته می‌شوند**.

### PostBind {#post-bind}

این یک رابط اطلاعاتی است. افزونه‌های post-bind پس از اتصال موفق
یک Pod فراخوانی می‌شوند. این مرحله پایان یک چرخه‌ی اتصال است و می‌تواند برای
پاک‌سازی منابع مرتبط استفاده شود.

## API افزونه {#plugin-api}

API افزونه دو گام دارد. نخست، افزونه‌ها باید ثبت و
پیکربندی شوند، سپس از رابط‌های نقاط توسعه استفاده می‌کنند. رابط‌های نقاط توسعه
شکل زیر را دارند.

```go
type Plugin interface {
    Name() string
}

type QueueSortPlugin interface {
    Plugin
    Less(*v1.pod, *v1.pod) bool
}

type PreFilterPlugin interface {
    Plugin
    PreFilter(context.Context, *framework.CycleState, *v1.pod) error
}

// ...
```

## پیکربندی افزونه {#plugin-configuration}

می‌توانید افزونه‌ها را در پیکربندی زمان‌بند فعال یا غیرفعال کنید. اگر از
کوبرنتیز v1.18 یا جدیدتر استفاده می‌کنید، بیشتر
[افزونه‌های](/docs/reference/scheduling/config/#scheduling-plugins) زمان‌بندی در حال استفاده‌اند و
به‌صورت پیش‌فرض فعال هستند.

علاوه بر افزونه‌های پیش‌فرض، می‌توانید افزونه‌های زمان‌بندی خود را نیز پیاده‌سازی کنید
و آن‌ها را در کنار افزونه‌های پیش‌فرض پیکربندی نمایید. برای جزئیات بیشتر می‌توانید به
[scheduler-plugins](https://github.com/kubernetes-sigs/scheduler-plugins) مراجعه کنید.

اگر از کوبرنتیز v1.18 یا جدیدتر استفاده می‌کنید، می‌توانید مجموعه‌ای از افزونه‌ها را
به‌عنوان یک پروفایل زمان‌بند (scheduler profile) پیکربندی کنید و سپس چند پروفایل تعریف کنید تا با انواع مختلف بار کاری سازگار شود.
برای اطلاعات بیشتر به [پروفایل‌های چندگانه](/docs/reference/scheduling/config/#multiple-profiles) مراجعه کنید.
