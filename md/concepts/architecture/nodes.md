<!-- overview -->

کوبرنتیز {{< glossary_tooltip text="بار کاری" term_id="workload" >}} شما را
با قرار دادن {{< glossary_tooltip text="کانتینرها" term_id="container" >}} در Podها و اجرای آن‌ها روی _نودها_ اجرا می‌کند.
یک نود، بسته به کلاستر، ممکن است یک ماشین مجازی یا فیزیکی باشد. هر نود
توسط
{{< glossary_tooltip text="control plane" term_id="control-plane" >}}
مدیریت می‌شود و سرویس‌های لازم برای اجرای
{{< glossary_tooltip text="Podها" term_id="pod" >}} را در خود دارد.

معمولاً در یک کلاستر چندین نود دارید؛ در یک محیط آموزشی یا محیطی با منابع محدود،
ممکن است تنها یک نود داشته باشید.

[اجزای](/docs/concepts/architecture/#node-components) یک نود عبارت‌اند از
{{< glossary_tooltip text="kubelet" term_id="kubelet" >}}، یک
{{< glossary_tooltip text="محیط اجرای کانتینر" term_id="container-runtime" >}} و
{{< glossary_tooltip text="kube-proxy" term_id="kube-proxy" >}}.

<!-- body -->

## مدیریت

دو روش اصلی برای افزودن نودها به
{{< glossary_tooltip text="سرور API" term_id="kube-apiserver" >}} وجود دارد:

1. kubelet روی یک نود، خودش را در control plane ثبت می‌کند
2. شما (یا کاربر انسانی دیگری) یک آبجکت Node را به‌صورت دستی اضافه می‌کنید

پس از اینکه یک {{< glossary_tooltip text="آبجکت" term_id="object" >}} Node ایجاد کردید،
یا kubelet روی یک نود خودش را ثبت کرد، control plane بررسی می‌کند که آیا آبجکت Node جدید
معتبر است یا نه. برای نمونه، اگر تلاش کنید یک Node را از مانیفست JSON زیر ایجاد کنید:

```json
{
  "kind": "Node",
  "apiVersion": "v1",
  "metadata": {
    "name": "10.240.79.157",
    "labels": {
      "name": "my-first-k8s-node"
    }
  }
}
```

کوبرنتیز یک آبجکت Node را به‌صورت داخلی (بازنمایی) ایجاد می‌کند. کوبرنتیز بررسی می‌کند
که آیا kubeletای در سرور API ثبت شده است که با فیلد `metadata.name`
آن Node مطابقت داشته باشد. اگر نود سالم باشد (یعنی همهٔ سرویس‌های لازم در حال اجرا باشند)،
واجد شرایط اجرای Pod است. در غیر این صورت، آن نود تا زمانی که سالم شود
در همهٔ فعالیت‌های کلاستر نادیده گرفته می‌شود.

{{< note >}}
کوبرنتیز آبجکت مربوط به Node نامعتبر را نگه می‌دارد و به بررسی اینکه آیا
سالم می‌شود یا نه ادامه می‌دهد.

شما یا یک {{< glossary_tooltip term_id="controller" text="کنترل‌کننده">}} باید آبجکت Node را
به‌طور صریح حذف کنید تا این بررسی سلامت متوقف شود.
{{< /note >}}

نام یک آبجکت Node باید یک
[نام زیردامنهٔ DNS](/docs/concepts/overview/working-with-objects/names#dns-subdomain-names) معتبر باشد.

### یکتایی نام نود

[نام](/docs/concepts/overview/working-with-objects/names#names) یک Node را شناسایی می‌کند. دو Node
نمی‌توانند هم‌زمان نام یکسانی داشته باشند. کوبرنتیز همچنین فرض می‌کند که منبعی با نام
یکسان، همان آبجکت است. در مورد یک Node، به‌طور ضمنی فرض می‌شود که نمونه‌ای که از
نام یکسانی استفاده می‌کند، وضعیت یکسان (مانند تنظیمات شبکه و محتوای دیسک ریشه) و ویژگی‌هایی مانند
برچسب‌های نود یکسانی خواهد داشت. اگر نمونه‌ای بدون تغییر نامش دگرگون شود، این امر ممکن است به ناسازگاری‌هایی منجر شود.
اگر Node نیاز به جایگزینی یا به‌روزرسانی اساسی داشته باشد، آبجکت Node موجود باید
ابتدا از سرور API حذف شود و پس از به‌روزرسانی دوباره اضافه شود.

### خودثبتی نودها

هنگامی که پرچم kubelet با نام `--register-node` برابر با true باشد (حالت پیش‌فرض)، kubelet تلاش می‌کند
خودش را در سرور API ثبت کند. این الگوی ترجیحی است که بیشتر توزیع‌ها از آن استفاده می‌کنند.

برای خودثبتی، kubelet با گزینه‌های زیر راه‌اندازی می‌شود:

- `--kubeconfig` - مسیر اعتبارنامه‌ها برای احراز هویت خود در سرور API.
- `--cloud-provider` - نحوهٔ ارتباط با یک {{< glossary_tooltip text="ارائه‌دهندهٔ ابری" term_id="cloud-provider" >}}
  برای خواندن فراداده‌های مربوط به خود.
- `--register-node` - ثبت خودکار در سرور API.
- `--register-with-taints` - ثبت نود با فهرست داده‌شده‌ای از
  {{< glossary_tooltip text="taintها" term_id="taint" >}} (به‌صورت `<key>=<value>:<effect>` و جداشده با ویرگول).

  اگر `register-node` برابر با false باشد، هیچ اثری ندارد.
- `--node-ip` - فهرست اختیاری و جداشده با ویرگول از نشانی‌های IP نود.
  برای هر خانوادهٔ نشانی تنها می‌توانید یک نشانی تعیین کنید.
  برای نمونه، در یک کلاستر تک‌پشته‌ای IPv4، این مقدار را برابر با نشانی IPv4ای قرار می‌دهید که
  kubelet باید برای نود استفاده کند.
  برای جزئیات اجرای یک کلاستر دوپشته‌ای، به [پیکربندی دوپشته‌ای IPv4/IPv6](/docs/concepts/services-networking/dual-stack/#configure-ipv4-ipv6-dual-stack)
  مراجعه کنید.

  اگر این آرگومان را ارائه ندهید، kubelet از نشانی IPv4 پیش‌فرض نود (در صورت وجود) استفاده می‌کند؛
  اگر نود هیچ نشانی IPv4 نداشته باشد، kubelet از نشانی IPv6 پیش‌فرض نود استفاده می‌کند.
- `--node-labels` - {{< glossary_tooltip text="برچسب‌هایی" term_id="label" >}} که هنگام ثبت نود
  در کلاستر اضافه می‌شوند (محدودیت‌های برچسبی را که توسط
  [افزونهٔ پذیرش NodeRestriction](/docs/reference/access-authn-authz/admission-controllers/#noderestriction) اعمال می‌شود ببینید).
- `--node-status-update-frequency` - تعیین می‌کند kubelet هر چند وقت یک‌بار وضعیت نود خود را به سرور API ارسال کند.

هنگامی که [حالت مجوزدهی Node](/docs/reference/access-authn-authz/node/) و
[افزونهٔ پذیرش NodeRestriction](/docs/reference/access-authn-authz/admission-controllers/#noderestriction)
فعال باشند، kubeletها تنها مجازند منبع Node خودشان را ایجاد یا تغییر دهند.

{{< note >}}
همان‌طور که در بخش [یکتایی نام نود](#node-name-uniqueness) اشاره شد،
هنگامی که پیکربندی Node نیاز به به‌روزرسانی دارد، روش خوبی است که نود را دوباره
در سرور API ثبت کنید. برای نمونه، اگر kubelet با مجموعهٔ جدیدی از
`--node-labels` دوباره راه‌اندازی شود اما از همان نام Node استفاده شود، تغییر
اعمال نخواهد شد، زیرا برچسب‌ها تنها هنگام ثبت Node در سرور API تنظیم (یا تغییر) می‌شوند.

اگر پیکربندی Node هنگام راه‌اندازی مجدد kubelet تغییر کند، Podهایی که از قبل روی آن Node زمان‌بندی شده‌اند
ممکن است رفتار نادرستی داشته باشند یا مشکلاتی ایجاد کنند. برای نمونه، یک Pod
که از قبل در حال اجراست ممکن است نسبت به برچسب‌های جدید تخصیص‌یافته به Node دچار taint شود، در حالی که
Podهای دیگری که با آن Pod ناسازگارند بر اساس این برچسب جدید
زمان‌بندی می‌شوند. ثبت مجدد نود تضمین می‌کند که همهٔ Podها تخلیه و به‌درستی
دوباره زمان‌بندی شوند.
{{< /note >}}

### مدیریت دستی نود

می‌توانید آبجکت‌های Node را با استفاده از
{{< glossary_tooltip text="kubectl" term_id="kubectl" >}} ایجاد و تغییر دهید.

هنگامی که می‌خواهید آبجکت‌های Node را به‌صورت دستی ایجاد کنید، پرچم kubelet را به‌صورت `--register-node=false` تنظیم کنید.

می‌توانید آبجکت‌های Node را صرف‌نظر از تنظیم `--register-node` تغییر دهید.
برای نمونه، می‌توانید روی یک Node موجود برچسب بگذارید یا آن را غیرقابل‌زمان‌بندی علامت‌گذاری کنید.

می‌توانید با افزودن یک یا چند برچسب `node-role.kubernetes.io/<role>: <role>` به نود، نقش(های) اختیاری برای نودها تعیین کنید؛ نویسه‌های `<role>`
به قواعد [نحو](/docs/concepts/overview/working-with-objects/labels/#syntax-and-character-set) برچسب‌ها محدود هستند.

کوبرنتیز مقدار برچسب را برای نقش‌های نود نادیده می‌گیرد؛ طبق عرف، می‌توانید آن را برابر با همان رشته‌ای قرار دهید که برای نقش نود در کلید برچسب به کار برده‌اید.

می‌توانید از برچسب‌های روی نودها همراه با انتخابگرهای نود (node selectors) روی Podها برای کنترل
زمان‌بندی استفاده کنید. برای نمونه، می‌توانید یک Pod را محدود کنید تا تنها واجد شرایط اجرا روی
زیرمجموعه‌ای از نودهای موجود باشد.

علامت‌گذاری یک نود به‌عنوان غیرقابل‌زمان‌بندی، مانع از آن می‌شود که زمان‌بند پادهای جدیدی را روی
آن Node قرار دهد، اما بر Podهای موجود روی آن Node اثری ندارد. این کار به‌عنوان یک
گام مقدماتی پیش از راه‌اندازی مجدد نود یا سایر عملیات نگه‌داری سودمند است.

برای علامت‌گذاری یک Node به‌عنوان غیرقابل‌زمان‌بندی، این فرمان را اجرا کنید:

```shell
kubectl cordon $NODENAME
```

برای جزئیات بیشتر، به [تخلیهٔ ایمن یک نود](/docs/tasks/administer-cluster/safely-drain-node/)
مراجعه کنید.

{{< note >}}
Podهایی که بخشی از یک {{< glossary_tooltip term_id="daemonset" >}} هستند، اجرا شدن روی
یک Node غیرقابل‌زمان‌بندی را تحمل می‌کنند. DaemonSetها معمولاً سرویس‌هایی محلی برای نود فراهم می‌کنند
که باید روی Node اجرا شوند، حتی اگر آن Node در حال تخلیه از برنامه‌های بار کاری باشد.
{{< /note >}}

## وضعیت نود

وضعیت یک Node شامل اطلاعات زیر است:

* [نشانی‌ها](/docs/reference/node/node-status/#addresses)
* [شرایط](/docs/reference/node/node-status/#condition)
* [ظرفیت و قابل‌تخصیص](/docs/reference/node/node-status/#capacity)
* [اطلاعات](/docs/reference/node/node-status/#info)

می‌توانید از `kubectl` برای مشاهدهٔ وضعیت یک Node و سایر جزئیات آن استفاده کنید:

```shell
kubectl describe node <insert-node-name-here>
```

برای جزئیات بیشتر، به [وضعیت نود](/docs/reference/node/node-status/) مراجعه کنید.

## ضربان‌های نود

ضربان‌هایی که نودهای کوبرنتیز ارسال می‌کنند، به کلاستر شما کمک می‌کنند در دسترس بودن
هر نود را تعیین کند و هنگام تشخیص خرابی‌ها اقدام لازم را انجام دهد.

برای نودها دو شکل ضربان وجود دارد:

* به‌روزرسانی‌های [`.status`](/docs/reference/node/node-status/) یک Node.
* آبجکت‌های [Lease](/docs/concepts/architecture/leases/)
  درون {{< glossary_tooltip term_id="namespace" text="فضای نام">}}
  `kube-node-lease`.
  هر Node یک آبجکت Lease مرتبط دارد.

## کنترل‌کنندهٔ نود

{{< glossary_tooltip text="کنترل‌کنندهٔ" term_id="controller" >}} نود یکی از
اجزای control plane کوبرنتیز است که جنبه‌های گوناگون نودها را مدیریت می‌کند.

کنترل‌کنندهٔ نود در طول عمر یک نود نقش‌های متعددی دارد. نخستین نقش، تخصیص یک
بلوک CIDR به نود هنگام ثبت آن است (اگر تخصیص CIDR فعال باشد).

نقش دوم، به‌روز نگه‌داشتن فهرست داخلی نودهای کنترل‌کنندهٔ نود با
فهرست ماشین‌های موجود ارائه‌دهندهٔ ابری است. هنگام اجرا در یک محیط
ابری، هرگاه نودی ناسالم باشد، کنترل‌کنندهٔ نود از ارائه‌دهندهٔ ابری
می‌پرسد که آیا ماشین مجازی آن نود هنوز در دسترس است یا نه. اگر نباشد، کنترل‌کنندهٔ
نود، آن نود را از فهرست نودهای خود حذف می‌کند.

نقش سوم، پایش سلامت نودهاست. کنترل‌کنندهٔ نود
مسئول موارد زیر است:

- در صورتی که نودی دسترس‌ناپذیر شود، به‌روزرسانی شرط `Ready`
  در فیلد `.status` آن Node. در این حالت کنترل‌کنندهٔ نود
  شرط `Ready` را برابر با `Unknown` قرار می‌دهد.
- اگر نودی همچنان دسترس‌ناپذیر بماند: آغاز
  [بیرون‌رانی آغازشده از طریق API](/docs/concepts/scheduling-eviction/api-eviction/)
  برای همهٔ Podهای روی نود دسترس‌ناپذیر. به‌طور پیش‌فرض، کنترل‌کنندهٔ نود
  میان علامت‌گذاری نود به‌صورت `Unknown` و ارسال نخستین درخواست بیرون‌رانی،
  ۵ دقیقه صبر می‌کند.

به‌طور پیش‌فرض، کنترل‌کنندهٔ نود هر ۵ ثانیه یک‌بار وضعیت هر نود را بررسی می‌کند.
این بازه را می‌توان با استفاده از پرچم `--node-monitor-period` در مؤلفهٔ
`kube-controller-manager` پیکربندی کرد.

### محدودیت نرخ بیرون‌رانی

در بیشتر موارد، کنترل‌کنندهٔ نود نرخ بیرون‌رانی را به
`--node-eviction-rate` (پیش‌فرض 0.1) در ثانیه محدود می‌کند؛ یعنی پادها را
از بیش از ۱ نود در هر ۱۰ ثانیه بیرون نمی‌راند.

رفتار بیرون‌رانی نود زمانی تغییر می‌کند که نودی در یک ناحیهٔ دسترس‌پذیری (availability zone) مشخص
ناسالم شود. کنترل‌کنندهٔ نود بررسی می‌کند که چه درصدی از نودهای آن ناحیه
هم‌زمان ناسالم هستند (یعنی شرط `Ready` آن‌ها `Unknown` یا `False` است):

- اگر نسبت نودهای ناسالم دست‌کم برابر با `--unhealthy-zone-threshold`
  (پیش‌فرض 0.55) باشد، نرخ بیرون‌رانی کاهش می‌یابد.
- اگر کلاستر کوچک باشد (یعنی تعداد نودهایش کمتر از یا برابر با
  `--large-cluster-size-threshold` باشد که پیش‌فرض آن 50 است)، بیرون‌رانی‌ها متوقف می‌شوند.
- در غیر این صورت، نرخ بیرون‌رانی به `--secondary-node-eviction-rate`
  (پیش‌فرض 0.01) در ثانیه کاهش می‌یابد.

دلیل پیاده‌سازی این سیاست‌ها به تفکیک ناحیهٔ دسترس‌پذیری این است که ممکن است یک
ناحیهٔ دسترس‌پذیری از control plane جدا شود، در حالی که سایر نواحی
متصل باقی بمانند. اگر کلاستر شما در چندین ناحیهٔ دسترس‌پذیری ارائه‌دهندهٔ ابری گسترده نشده باشد،
سازوکار بیرون‌رانی، دسترس‌ناپذیری به تفکیک ناحیه را در نظر نمی‌گیرد.

یکی از دلایل کلیدی توزیع نودها در چندین ناحیهٔ دسترس‌پذیری این است که
هنگام از کار افتادن کامل یک ناحیه، بار کاری بتواند به نواحی سالم منتقل شود.
بنابراین، اگر همهٔ نودهای یک ناحیه ناسالم باشند، کنترل‌کنندهٔ نود با
نرخ عادی `--node-eviction-rate` بیرون‌رانی می‌کند. حالت مرزی زمانی است که همهٔ نواحی
کاملاً ناسالم باشند (هیچ‌یک از نودهای کلاستر سالم نباشد). در چنین
حالتی، کنترل‌کنندهٔ نود فرض می‌کند که مشکلی در اتصال
میان control plane و نودها وجود دارد و هیچ بیرون‌رانی‌ای انجام نمی‌دهد.
(اگر قطعی‌ای رخ داده باشد و برخی نودها دوباره ظاهر شوند، کنترل‌کنندهٔ نود
پادها را از نودهای باقی‌مانده‌ای که ناسالم یا دسترس‌ناپذیر هستند بیرون می‌راند.)

کنترل‌کنندهٔ نود همچنین مسئول بیرون‌راندن پادهایی است که روی نودهای دارای
taintهای `NoExecute` اجرا می‌شوند، مگر اینکه آن پادها آن taint را تحمل کنند.
کنترل‌کنندهٔ نود همچنین {{< glossary_tooltip text="taintهایی" term_id="taint" >}}
متناظر با مشکلات نود، مانند دسترس‌ناپذیری یا آماده نبودن نود، اضافه می‌کند. این بدان معناست
که زمان‌بند Podها را روی نودهای ناسالم قرار نخواهد داد.

## ردیابی ظرفیت منابع {#node-capacity}

آبجکت‌های Node اطلاعات مربوط به ظرفیت منابع Node را دنبال می‌کنند؛ برای نمونه، مقدار
حافظهٔ موجود و تعداد پردازنده‌ها.
نودهایی که [خودثبتی](#self-registration-of-nodes) می‌کنند، ظرفیت خود را هنگام
ثبت گزارش می‌دهند. اگر یک Node را [به‌صورت دستی](#manual-node-administration) اضافه کنید،
باید اطلاعات ظرفیت نود را هنگام افزودن آن تنظیم کنید.

{{< glossary_tooltip text="زمان‌بند" term_id="kube-scheduler" >}} کوبرنتیز اطمینان حاصل می‌کند که
منابع کافی برای همهٔ Podهای روی یک Node وجود دارد. زمان‌بند بررسی می‌کند که مجموع
درخواست‌های کانتینرهای روی نود از ظرفیت نود بیشتر نباشد.
این مجموع درخواست‌ها شامل همهٔ کانتینرهایی است که kubelet مدیریت می‌کند، اما
کانتینرهایی را که مستقیماً توسط محیط اجرای کانتینر راه‌اندازی شده‌اند و همچنین
فرایندهایی را که بیرون از کنترل kubelet اجرا می‌شوند شامل نمی‌شود.

{{< note >}}
اگر می‌خواهید منابعی را به‌طور صریح برای فرایندهای غیر Pod رزرو کنید، به
[رزرو منابع برای daemonهای سیستمی](/docs/tasks/administer-cluster/reserve-compute-resources/#system-reserved) مراجعه کنید.
{{< /note >}}

## توپولوژی نود

{{< feature-state feature_gate_name="TopologyManager" >}}

اگر [feature gate](/docs/reference/command-line-tools-reference/feature-gates/) با نام `TopologyManager`
را فعال کرده باشید،
kubelet می‌تواند هنگام تصمیم‌گیری دربارهٔ تخصیص منابع از راهنمایی‌های توپولوژی استفاده کند.
برای اطلاعات بیشتر، به [کنترل سیاست‌های مدیریت توپولوژی روی یک نود](/docs/tasks/administer-cluster/topology-manager/)
مراجعه کنید.
