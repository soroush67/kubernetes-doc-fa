<!-- overview -->

کوبرنتیز {{< glossary_tooltip text="بار کاری" term_id="workload" >}} شما را اجرا می‌کند. برای این کار، {{< glossary_tooltip text="کانتینرها" term_id="container" >}} را درون Podها قرار می‌دهد تا روی _نودها_ اجرا شوند. هر نود، بسته به کلاستر، می‌تواند یک ماشین مجازی یا فیزیکی باشد. هر نود را {{< glossary_tooltip text="control plane" term_id="control-plane" >}} مدیریت می‌کند و سرویس‌های لازم برای اجرای {{< glossary_tooltip text="Podها" term_id="pod" >}} را در خود دارد.

معمولاً یک کلاستر چندین نود دارد. در محیط‌های آموزشی یا محیط‌هایی با منابع محدود، ممکن است فقط یک نود داشته باشید.

[مؤلفه‌های](/docs/concepts/architecture/#node-components) یک نود عبارت‌اند از {{< glossary_tooltip text="kubelet" term_id="kubelet" >}}، یک {{< glossary_tooltip text="محیط اجرای کانتینر" term_id="container-runtime" >}} و {{< glossary_tooltip text="kube-proxy" term_id="kube-proxy" >}}.

<!-- body -->

## مدیریت

دو روش اصلی برای افزودن نودها به {{< glossary_tooltip text="سرور API" term_id="kube-apiserver" >}} وجود دارد:

1. kubelet روی نود، خودش را در control plane ثبت می‌کند.
2. شما (یا کاربر انسانی دیگری) یک آبجکت Node را به‌صورت دستی اضافه می‌کنید.

پس از آنکه یک {{< glossary_tooltip text="آبجکت" term_id="object" >}} Node ایجاد کردید یا kubelet روی نود خودش را ثبت کرد، control plane بررسی می‌کند که آبجکت Node جدید معتبر باشد. برای مثال، اگر بخواهید یک Node را از مانیفست JSON زیر ایجاد کنید:

```json
{
  "kind": "Node",
  "apiVersion": "v1",
  "metadata": {
    "name": "10.240.79.157",
    "labels": {
      "name": "my-first-k8s-node"
    }
  }
}
```

کوبرنتیز یک آبجکت Node را به‌صورت داخلی (به‌عنوان بازنمایی نود) ایجاد می‌کند. سپس بررسی می‌کند که آیا kubeletی متناظر با فیلد `metadata.name` این Node در سرور API ثبت شده است یا نه. اگر نود سالم باشد (یعنی همهٔ سرویس‌های لازم در حال اجرا باشند)، صلاحیت اجرای Pod را دارد. در غیر این صورت، تا زمانی که نود سالم شود، در هیچ فعالیتی از کلاستر به آن توجه نمی‌شود.

{{< note >}}
کوبرنتیز آبجکتِ Node نامعتبر را نگه می‌دارد و همچنان بررسی می‌کند که آیا سالم می‌شود یا نه.

برای توقف این بررسی سلامت، شما یا یک {{< glossary_tooltip term_id="controller" text="کنترل‌کننده">}} باید آبجکت Node را به‌طور صریح حذف کنید.
{{< /note >}}

نام هر آبجکت Node باید یک [نام زیردامنهٔ DNS](/docs/concepts/overview/working-with-objects/names#dns-subdomain-names) معتبر باشد.

### یکتایی نام نود

هر Node با [نام](/docs/concepts/overview/working-with-objects/names#names) خود شناسایی می‌شود. دو Node نمی‌توانند هم‌زمان نام یکسانی داشته باشند. کوبرنتیز همچنین فرض می‌کند منابعی که نام یکسانی دارند، یک آبجکت واحد هستند. در مورد Node، به‌طور ضمنی فرض می‌شود نمونه‌ای که از همان نام استفاده می‌کند، وضعیت یکسان (مانند تنظیمات شبکه و محتوای دیسک ریشه) و ویژگی‌های یکسانی مانند برچسب‌های نود دارد. اگر نمونه‌ای بدون تغییر نامش دگرگون شود، ممکن است ناسازگاری‌هایی پیش بیاید. اگر لازم است Node جایگزین شود یا به‌طور اساسی به‌روزرسانی شود، ابتدا باید آبجکت Node موجود را از سرور API حذف کرد و پس از به‌روزرسانی دوباره آن را اضافه کرد.

### ثبت خودکار نودها

وقتی فلگ `--register-node` در kubelet برابر با true باشد (مقدار پیش‌فرض)، kubelet تلاش می‌کند خودش را در سرور API ثبت کند. این الگوی ترجیحی است و بیشتر توزیع‌ها از آن استفاده می‌کنند.

برای ثبت خودکار، kubelet با گزینه‌های زیر اجرا می‌شود:

- گزینهٔ `--kubeconfig`: مسیر اعتبارنامه‌هایی که kubelet با آن‌ها خود را نزد سرور API احراز هویت می‌کند.
- گزینهٔ `--cloud-provider`: نحوهٔ ارتباط با یک {{< glossary_tooltip text="ارائه‌دهندهٔ ابری" term_id="cloud-provider" >}} برای خواندن فراداده‌های مربوط به خود نود.
- گزینهٔ `--register-node`: ثبت خودکار در سرور API.
- گزینهٔ `--register-with-taints`: ثبت نود با فهرست مشخص‌شده‌ای از {{< glossary_tooltip text="taintها" term_id="taint" >}} (به‌صورت `<key>=<value>:<effect>` و جداشده با ویرگول).

  اگر `register-node` برابر با false باشد، این گزینه هیچ اثری ندارد.
- گزینهٔ `--node-ip`: فهرستی اختیاری از نشانی‌های IP نود که با ویرگول از هم جدا شده‌اند. برای هر خانوادهٔ نشانی فقط می‌توانید یک نشانی تعیین کنید. برای مثال، در یک کلاستر تک‌پشته‌ای IPv4، این مقدار را برابر با نشانی IPv4 قرار می‌دهید که kubelet باید برای نود به کار ببرد. برای جزئیات اجرای کلاستر دوپشته‌ای، به [پیکربندی دوپشته‌ای IPv4/IPv6](/docs/concepts/services-networking/dual-stack/#configure-ipv4-ipv6-dual-stack) مراجعه کنید.

  اگر این آرگومان را تعیین نکنید، kubelet از نشانی IPv4 پیش‌فرض نود (در صورت وجود) استفاده می‌کند. اگر نود هیچ نشانی IPv4 نداشته باشد، kubelet از نشانی IPv6 پیش‌فرض نود استفاده می‌کند.
- گزینهٔ `--node-labels`: {{< glossary_tooltip text="برچسب‌هایی" term_id="label" >}} که هنگام ثبت نود در کلاستر اضافه می‌شوند (محدودیت‌های برچسبی را که [افزونهٔ پذیرش NodeRestriction](/docs/reference/access-authn-authz/admission-controllers/#noderestriction) اعمال می‌کند ببینید).
- گزینهٔ `--node-status-update-frequency`: تعیین می‌کند kubelet هر چند وقت یک‌بار وضعیت نود خود را به سرور API ارسال کند.

وقتی [حالت مجوزدهی Node](/docs/reference/access-authn-authz/node/) و [افزونهٔ پذیرش NodeRestriction](/docs/reference/access-authn-authz/admission-controllers/#noderestriction) فعال باشند، هر kubelet فقط مجاز است منبع Node مربوط به خودش را ایجاد یا ویرایش کند.

{{< note >}}
همان‌طور که در بخش [یکتایی نام نود](#node-name-uniqueness) گفته شد، وقتی پیکربندی Node نیاز به به‌روزرسانی دارد، بهتر است نود را دوباره در سرور API ثبت کنید. برای مثال، اگر kubelet با مجموعهٔ جدیدی از `--node-labels` دوباره راه‌اندازی شود اما همان نام Node به کار رود، تغییر اعمال نمی‌شود؛ زیرا برچسب‌ها فقط هنگام ثبت Node در سرور API تنظیم (یا تغییر) می‌شوند.

اگر پیکربندی Node هنگام راه‌اندازی مجدد kubelet تغییر کند، Podهایی که پیش‌تر روی آن Node زمان‌بندی شده‌اند ممکن است رفتار نادرستی داشته باشند یا مشکلاتی ایجاد کنند. برای مثال، ممکن است Podی که در حال اجراست با برچسب‌های جدیدِ اختصاص‌یافته به Node ناسازگار شود، در حالی که Podهای دیگری که با آن Pod ناسازگارند بر اساس همین برچسب جدید زمان‌بندی شوند. ثبت مجدد نود تضمین می‌کند که همهٔ Podها تخلیه شوند و به‌درستی دوباره زمان‌بندی شوند.
{{< /note >}}

### مدیریت دستی نودها

می‌توانید با {{< glossary_tooltip text="kubectl" term_id="kubectl" >}} آبجکت‌های Node را ایجاد و ویرایش کنید.

اگر می‌خواهید آبجکت‌های Node را به‌صورت دستی ایجاد کنید، فلگ `--register-node=false` را در kubelet تنظیم کنید.

ویرایش آبجکت‌های Node، صرف‌نظر از مقدار `--register-node`، امکان‌پذیر است. برای مثال، می‌توانید روی یک Node موجود برچسب بگذارید یا آن را غیرقابل‌زمان‌بندی علامت بزنید.

می‌توانید با افزودن یک یا چند برچسب `node-role.kubernetes.io/<role>: <role>` به نود، نقش (یا نقش‌های) اختیاری برای آن تعیین کنید. نویسه‌های `<role>` تابع قواعد [نحو](/docs/concepts/overview/working-with-objects/labels/#syntax-and-character-set) برچسب‌ها هستند.

کوبرنتیز مقدار برچسب را برای نقش‌های نود نادیده می‌گیرد. طبق عرف، می‌توانید این مقدار را برابر با همان رشته‌ای قرار دهید که برای نقش نود در کلید برچسب به کار برده‌اید.

می‌توانید از برچسب‌های Nodeها همراه با انتخابگرهای نود (node selector) در Podها برای کنترل زمان‌بندی استفاده کنید. برای مثال، می‌توانید Pod را طوری محدود کنید که فقط روی زیرمجموعه‌ای از نودهای موجود قابل اجرا باشد.

علامت‌گذاری یک نود به‌عنوان غیرقابل‌زمان‌بندی، مانع از آن می‌شود که زمان‌بند Podهای جدیدی روی آن Node قرار دهد، اما بر Podهای موجود روی آن اثری ندارد. این کار به‌عنوان گامی مقدماتی پیش از راه‌اندازی مجدد نود یا سایر کارهای نگهداری مفید است.

برای علامت‌گذاری یک Node به‌عنوان غیرقابل‌زمان‌بندی، دستور زیر را اجرا کنید:

```shell
kubectl cordon $NODENAME
```

برای جزئیات بیشتر، به [تخلیهٔ ایمن یک نود](/docs/tasks/administer-cluster/safely-drain-node/) مراجعه کنید.

{{< note >}}
Podهایی که بخشی از یک {{< glossary_tooltip term_id="daemonset" >}} هستند، اجرا شدن روی Node غیرقابل‌زمان‌بندی را تحمل می‌کنند. DaemonSetها معمولاً سرویس‌های محلیِ نود را فراهم می‌کنند که باید حتی هنگام تخلیهٔ برنامه‌های بار کاری از Node، روی آن در حال اجرا بمانند.
{{< /note >}}

## ضربان قلب نودها

ضربان‌های قلب (heartbeat) که نودهای کوبرنتیز ارسال می‌کنند، به کلاستر کمک می‌کنند در دسترس بودن هر نود را تشخیص دهد و هنگام شناسایی خرابی‌ها اقدام کند.

نودها دو نوع ضربان قلب دارند:

* به‌روزرسانی‌های [`.status`](/docs/reference/node/node-status/) هر Node.
* آبجکت‌های [Lease](/docs/concepts/architecture/leases/) در {{< glossary_tooltip term_id="namespace" text="فضای نام">}} `kube-node-lease`. هر Node یک آبجکت Lease مرتبط دارد.

## کنترل‌کنندهٔ نود

{{< glossary_tooltip text="کنترل‌کنندهٔ" term_id="controller" >}} نود یکی از مؤلفه‌های control plane کوبرنتیز است که جنبه‌های گوناگون نودها را مدیریت می‌کند.

کنترل‌کنندهٔ نود در طول عمر یک نود چندین نقش دارد. نخستین نقش، اختصاص یک بلوک CIDR به نود هنگام ثبت آن است (در صورتی که تخصیص CIDR فعال باشد).

نقش دوم، به‌روز نگه داشتن فهرست داخلی نودهای کنترل‌کنندهٔ نود با فهرست ماشین‌های در دسترسِ ارائه‌دهندهٔ ابری است. هنگام اجرا در محیط ابری، هر زمان که نودی ناسالم باشد، کنترل‌کنندهٔ نود از ارائه‌دهندهٔ ابری می‌پرسد که آیا ماشین مجازی آن نود هنوز در دسترس است یا نه. اگر در دسترس نباشد، کنترل‌کنندهٔ نود آن نود را از فهرست نودهای خود حذف می‌کند.

نقش سوم، پایش سلامت نودهاست. کنترل‌کنندهٔ نود مسئول کارهای زیر است:

- اگر نودی غیرقابل‌دسترس شود، شرط `Ready` را در فیلد `.status` آن Node به‌روزرسانی می‌کند. در این حالت، کنترل‌کنندهٔ نود شرط `Ready` را برابر با `Unknown` قرار می‌دهد.
- اگر نود همچنان غیرقابل‌دسترس بماند، برای همهٔ Podهای روی آن نود [بیرون‌رانی آغازشده از طریق API](/docs/concepts/scheduling-eviction/api-eviction/) را راه می‌اندازد. به‌طور پیش‌فرض، کنترل‌کنندهٔ نود از لحظهٔ علامت‌گذاری نود به‌عنوان `Unknown` تا ارسال نخستین درخواست بیرون‌رانی، ۵ دقیقه صبر می‌کند.

به‌طور پیش‌فرض، کنترل‌کنندهٔ نود هر ۵ ثانیه وضعیت هر نود را بررسی می‌کند. این بازه را می‌توان با فلگ `--node-monitor-period` در مؤلفهٔ `kube-controller-manager` پیکربندی کرد.

### محدودیت نرخ بیرون‌رانی

در بیشتر موارد، کنترل‌کنندهٔ نود نرخ بیرون‌رانی را به `--node-eviction-rate` (پیش‌فرض 0.1) در ثانیه محدود می‌کند؛ یعنی در هر ۱۰ ثانیه، Podها را از بیش از یک نود بیرون نمی‌راند.

وقتی نودی در یک منطقهٔ دسترس‌پذیری (availability zone) مشخص ناسالم شود، رفتار بیرون‌رانی نود تغییر می‌کند. کنترل‌کنندهٔ نود بررسی می‌کند که چند درصد از نودهای آن منطقه هم‌زمان ناسالم هستند (یعنی شرط `Ready` آن‌ها `Unknown` یا `False` است):

- اگر نسبت نودهای ناسالم دست‌کم برابر با `--unhealthy-zone-threshold` (پیش‌فرض 0.55) باشد، نرخ بیرون‌رانی کاهش می‌یابد.
- اگر کلاستر کوچک باشد (یعنی تعداد نودهایش کمتر یا مساوی `--large-cluster-size-threshold` باشد که پیش‌فرض آن ۵۰ است)، بیرون‌رانی‌ها متوقف می‌شوند.
- در غیر این صورت، نرخ بیرون‌رانی به `--secondary-node-eviction-rate` (پیش‌فرض 0.01) در ثانیه کاهش می‌یابد.

دلیل اجرای این سیاست‌ها به تفکیک منطقهٔ دسترس‌پذیری این است که ممکن است یک منطقه از control plane جدا شود، در حالی که سایر مناطق همچنان متصل بمانند. اگر کلاستر شما در چند منطقهٔ دسترس‌پذیری ارائه‌دهندهٔ ابری گسترده نشده باشد، سازوکار بیرون‌رانی در دسترس نبودنِ هر منطقه را جداگانه در نظر نمی‌گیرد.

یکی از دلایل اصلی توزیع نودها در چند منطقهٔ دسترس‌پذیری این است که اگر یک منطقه به‌طور کامل از کار بیفتد، بتوان بار کاری را به مناطق سالم منتقل کرد. بنابراین اگر همهٔ نودهای یک منطقه ناسالم باشند، کنترل‌کنندهٔ نود با نرخ عادیِ `--node-eviction-rate` بیرون‌رانی می‌کند. حالت مرزی زمانی است که همهٔ مناطق کاملاً ناسالم باشند (هیچ‌یک از نودهای کلاستر سالم نباشد). در چنین حالتی، کنترل‌کنندهٔ نود فرض می‌کند که مشکلی در اتصال میان control plane و نودها وجود دارد و هیچ بیرون‌رانی‌ای انجام نمی‌دهد. (اگر قطعی رخ داده باشد و برخی نودها دوباره ظاهر شوند، کنترل‌کنندهٔ نود Podها را از نودهای باقی‌مانده‌ای که ناسالم یا غیرقابل‌دسترس هستند بیرون می‌راند.)

کنترل‌کنندهٔ نود همچنین مسئول بیرون‌راندن Podهایی است که روی نودهای دارای taint از نوع `NoExecute` اجرا می‌شوند، مگر آنکه آن Podها این taint را تحمل کنند. کنترل‌کنندهٔ نود همچنین {{< glossary_tooltip text="taintهایی" term_id="taint" >}} متناظر با مشکلات نود، مانند غیرقابل‌دسترس بودن یا آماده نبودن نود، اضافه می‌کند. به این ترتیب، زمان‌بند Podها را روی نودهای ناسالم قرار نمی‌دهد.

## پیگیری ظرفیت منابع {#node-capacity}

آبجکت‌های Node اطلاعات مربوط به ظرفیت منابع Node را نگه می‌دارند؛ برای مثال، مقدار حافظهٔ در دسترس و تعداد CPUها. نودهایی که [خودشان را ثبت می‌کنند](#self-registration-of-nodes)، ظرفیت خود را هنگام ثبت گزارش می‌دهند. اگر Node را به‌صورت [دستی](#manual-node-administration) اضافه کنید، باید هنگام افزودن آن، اطلاعات ظرفیت نود را نیز تنظیم کنید.

{{< glossary_tooltip text="زمان‌بند" term_id="kube-scheduler" >}} کوبرنتیز تضمین می‌کند که برای همهٔ Podهای روی یک Node منابع کافی وجود داشته باشد. زمان‌بند بررسی می‌کند که مجموع درخواست‌های کانتینرهای روی نود از ظرفیت نود بیشتر نباشد. این مجموع درخواست‌ها شامل همهٔ کانتینرهایی است که kubelet مدیریت می‌کند، اما کانتینرهایی را که مستقیماً محیط اجرای کانتینر راه‌اندازی کرده و نیز فرایندهایی را که خارج از کنترل kubelet اجرا می‌شوند در بر نمی‌گیرد.

{{< note >}}
اگر می‌خواهید منابعی را به‌طور صریح برای فرایندهای غیر Pod رزرو کنید، به [رزرو منابع برای دیمن‌های سیستمی](/docs/tasks/administer-cluster/reserve-compute-resources/#system-reserved) مراجعه کنید.
{{< /note >}}

## توپولوژی نود

{{< feature-state feature_gate_name="TopologyManager" >}}

اگر [feature gate](/docs/reference/command-line-tools-reference/feature-gates/) با نام `TopologyManager` را فعال کرده باشید، kubelet می‌تواند هنگام تصمیم‌گیری دربارهٔ تخصیص منابع از راهنمایی‌های توپولوژی استفاده کند. برای اطلاعات بیشتر، به [کنترل سیاست‌های مدیریت توپولوژی روی یک نود](/docs/tasks/administer-cluster/topology-manager/) مراجعه کنید.
