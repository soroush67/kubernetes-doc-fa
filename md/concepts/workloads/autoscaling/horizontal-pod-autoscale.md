در کوبرنتیز، یک _HorizontalPodAutoscaler_ به‌طور خودکار یک منبع بار کاری (مانند
یک {{< glossary_tooltip text="Deployment" term_id="deployment" >}} یا
{{< glossary_tooltip text="StatefulSet" term_id="statefulset" >}}) را به‌روزرسانی می‌کند، با
این هدف که ظرفیت به‌طور خودکار متناسب با تقاضا مقیاس‌دهی شود.

مقیاس‌دهی افقی به این معناست که پاسخ به افزایش بار، استقرار
{{< glossary_tooltip text="Podهای" term_id="pod" >}} بیشتر است.
این با مقیاس‌دهی _عمودی_ متفاوت است؛ مقیاس‌دهی عمودی در کوبرنتیز به معنای
اختصاص منابع بیشتر (برای مثال: حافظه یا CPU) به Podهایی است که از قبل
برای آن بار کاری در حال اجرا هستند.

اگر بار کاهش یابد و تعداد Podها بیشتر از حداقل پیکربندی‌شده باشد،
HorizontalPodAutoscaler به منبع بار کاری (Deployment، StatefulSet
یا منبع مشابه دیگر) دستور می‌دهد که مقیاس خود را کاهش دهد.

مقیاس‌دهی خودکار افقی Pod برای آبجکت‌هایی که قابل مقیاس‌دهی نیستند (برای مثال:
یک {{< glossary_tooltip text="DaemonSet" term_id="daemonset" >}}) کاربرد ندارد.

HorizontalPodAutoscaler به‌صورت یک منبع API کوبرنتیز و یک
{{< glossary_tooltip text="کنترل‌کننده" term_id="controller" >}} پیاده‌سازی شده است.
منبع، رفتار کنترل‌کننده را تعیین می‌کند.
کنترل‌کننده‌ی مقیاس‌دهی خودکار افقی Pod که درون
{{< glossary_tooltip text="control plane" term_id="control-plane" >}} کوبرنتیز اجرا می‌شود، به‌طور دوره‌ای
مقیاس مطلوب هدف خود (برای مثال، یک Deployment) را تنظیم می‌کند تا با متریک‌های مشاهده‌شده‌ای مانند میانگین
استفاده از CPU، میانگین استفاده از حافظه، یا هر متریک سفارشی دیگری که شما تعیین می‌کنید، مطابقت داشته باشد.

یک [مثال گام‌به‌گام](/docs/tasks/run-application/horizontal-pod-autoscale-walkthrough/) از استفاده از
مقیاس‌دهی خودکار افقی Pod وجود دارد.

شکل ۱. HorizontalPodAutoscaler مقیاس یک Deployment و ReplicaSet آن را کنترل می‌کند

کوبرنتیز مقیاس‌دهی خودکار افقی Pod را به‌صورت یک حلقه‌ی کنترلی پیاده‌سازی می‌کند که به‌طور متناوب اجرا می‌شود
(یک فرایند پیوسته نیست). این بازه با پارامتر
`--horizontal-pod-autoscaler-sync-period` در
[`kube-controller-manager`](/docs/reference/command-line-tools-reference/kube-controller-manager/)
تنظیم می‌شود (و بازه‌ی پیش‌فرض ۱۵ ثانیه است).

در هر دوره یک بار، controller manager میزان استفاده از منابع را در برابر
متریک‌های مشخص‌شده در تعریف هر HorizontalPodAutoscaler پرس‌وجو می‌کند. controller manager
منبع هدف تعریف‌شده توسط `scaleTargetRef` را پیدا می‌کند،
سپس Podها را بر اساس برچسب‌های `.spec.selector` منبع هدف انتخاب می‌کند
و متریک‌ها را یا از API متریک‌های منابع (برای متریک‌های منبع به‌ازای هر Pod)،
یا از API متریک‌های سفارشی (برای همه‌ی متریک‌های دیگر) دریافت می‌کند.

- برای متریک‌های منبع به‌ازای هر Pod (مانند CPU)، کنترل‌کننده متریک‌ها را
  از API متریک‌های منابع برای هر Podای که HorizontalPodAutoscaler هدف قرار داده است دریافت می‌کند.
  سپس، اگر یک مقدار هدف برای میزان استفاده (utilization) تنظیم شده باشد، کنترل‌کننده مقدار استفاده
  را به‌صورت درصدی از
  [درخواست منبع](/docs/concepts/configuration/manage-resources-containers/#requests-and-limits)
  معادل در کانتینرهای هر Pod محاسبه می‌کند. اگر یک مقدار خام هدف تنظیم شده باشد، مقادیر خام متریک مستقیماً استفاده می‌شوند.
  سپس کنترل‌کننده میانگین میزان استفاده یا مقدار خام را (بسته به نوع
  هدف مشخص‌شده) در میان همه‌ی Podهای هدف محاسبه می‌کند و نسبتی تولید می‌کند که برای مقیاس‌دهی
  تعداد رپلیکاهای مطلوب به کار می‌رود.

  لطفاً توجه داشته باشید که اگر برای برخی از کانتینرهای Pod درخواست منبع مربوطه تنظیم نشده باشد،
  میزان استفاده از CPU برای آن Pod تعریف نخواهد شد و مقیاس‌دهنده‌ی خودکار
  هیچ اقدامی برای آن متریک انجام نخواهد داد. برای اطلاعات بیشتر درباره‌ی نحوه‌ی کار الگوریتم مقیاس‌دهی خودکار،
  بخش [جزئیات الگوریتم](#algorithm-details) را در ادامه ببینید.

- برای متریک‌های سفارشی به‌ازای هر Pod، کنترل‌کننده مشابه متریک‌های منبع به‌ازای هر Pod عمل می‌کند،
  با این تفاوت که با مقادیر خام کار می‌کند، نه با مقادیر میزان استفاده.

- برای متریک‌های آبجکت و متریک‌های خارجی، یک متریک واحد دریافت می‌شود که
  آبجکت موردنظر را توصیف می‌کند. این متریک با مقدار هدف مقایسه می‌شود
  تا همانند بالا یک نسبت تولید شود. در نسخه‌ی API `autoscaling/v2`،
  می‌توان این مقدار را به‌صورت اختیاری پیش از انجام مقایسه بر تعداد Podها
  تقسیم کرد.

کاربرد رایج HorizontalPodAutoscaler این است که آن را طوری پیکربندی کنند که متریک‌ها را از
{{< glossary_tooltip text="APIهای تجمیع‌شده" term_id="aggregation-layer" >}}
(`metrics.k8s.io`، `custom.metrics.k8s.io` یا `external.metrics.k8s.io`) دریافت کند. API `metrics.k8s.io`
معمولاً توسط افزونه‌ای به نام Metrics Server ارائه می‌شود که باید جداگانه راه‌اندازی شود.
برای اطلاعات بیشتر درباره‌ی متریک‌های منابع، به
[Metrics Server](/docs/tasks/debug/debug-cluster/resource-metrics-pipeline/#metrics-server) مراجعه کنید.

بخش [پشتیبانی از APIهای متریک](#support-for-metrics-apis) تضمین‌های پایداری و وضعیت پشتیبانی این
APIهای مختلف را توضیح می‌دهد.

کنترل‌کننده‌ی HorizontalPodAutoscaler به منابع بار کاری متناظری که از مقیاس‌دهی پشتیبانی می‌کنند (مانند Deploymentها
و StatefulSet) دسترسی پیدا می‌کند. هر یک از این منابع یک زیرمنبع به نام `scale` دارند؛ رابطی که به شما امکان می‌دهد
تعداد رپلیکاها را به‌صورت پویا تنظیم کنید و وضعیت فعلی هر یک از آن‌ها را بررسی کنید.
برای اطلاعات کلی درباره‌ی زیرمنابع در API کوبرنتیز، به
[مفاهیم API کوبرنتیز](/docs/reference/using-api/api-concepts/) مراجعه کنید.

### جزئیات الگوریتم

از ابتدایی‌ترین دیدگاه، کنترل‌کننده‌ی HorizontalPodAutoscaler
بر اساس نسبت میان مقدار مطلوب متریک و مقدار فعلی متریک
عمل می‌کند:

```math
\begin{equation*}
desiredReplicas = ceil\left\lceil currentReplicas \times \frac{currentMetricValue}{desiredMetricValue} \right\rceil
\end{equation*}
```

برای مثال، اگر مقدار فعلی متریک `200m` و مقدار مطلوب
`100m` باشد، تعداد رپلیکاها دو برابر خواهد شد، زیرا
\\( { 200.0 \div 100.0 } = 2.0 \\).  
اگر در عوض مقدار فعلی `50m` باشد، تعداد رپلیکاها
نصف خواهد شد، زیرا \\( { 50.0 \div 100.0 } = 0.5 \\). اگر این نسبت به‌اندازه‌ی کافی به 1.0 نزدیک باشد (در محدوده‌ی یک
[رواداری قابل پیکربندی](#tolerance) که به‌طور پیش‌فرض 0.1 است)، control plane از هرگونه اقدام مقیاس‌دهی
صرف‌نظر می‌کند.

هنگامی که `targetAverageValue` یا `targetAverageUtilization` مشخص شده باشد،
مقدار `currentMetricValue` با گرفتن میانگین متریک داده‌شده
در میان همه‌ی Podهای موجود در هدف مقیاس HorizontalPodAutoscaler محاسبه می‌شود.

پیش از بررسی رواداری و تصمیم‌گیری درباره‌ی مقادیر نهایی، control
plane همچنین بررسی می‌کند که آیا متریکی مفقود است یا نه، و چه تعداد از Podها
[`Ready`](/docs/concepts/workloads/pods/pod-lifecycle/#pod-conditions) هستند.
برای متریک‌های منبع به‌ازای هر Pod، همه‌ی Podهایی که برچسب زمانی حذف (deletion timestamp) برایشان تنظیم شده است
(آبجکت‌هایی که برچسب زمانی حذف دارند در حال خاموش شدن /
حذف شدن هستند) نادیده گرفته می‌شوند و همه‌ی Podهای ناموفق کنار گذاشته می‌شوند.
برای متریک‌های خارجی و متریک‌های آبجکت، تعداد رپلیکاها بر اساس
تعداد Podهای Running و Ready تعیین می‌شود؛ Podهای در حال خاتمه که هنوز Ready هستند
همچنان در این مجموع شمرده می‌شوند.

اگر یک Pod خاص متریک نداشته باشد، برای بعد کنار گذاشته می‌شود؛ Podهای
فاقد متریک برای تنظیم مقدار نهایی مقیاس‌دهی استفاده خواهند شد.

هنگام مقیاس‌دهی بر اساس CPU، اگر هر Podای هنوز آماده نشده باشد (هنوز در حال
راه‌اندازی است یا احتمالاً سالم نیست) _یا_ جدیدترین نقطه‌ی متریک برای
آن Pod مربوط به پیش از آماده شدن آن باشد، آن Pod نیز کنار گذاشته می‌شود.

به دلیل محدودیت‌های فنی، کنترل‌کننده‌ی HorizontalPodAutoscaler
هنگام تصمیم‌گیری درباره‌ی کنار گذاشتن برخی متریک‌های CPU نمی‌تواند به‌طور دقیق نخستین زمانی را
که یک Pod آماده می‌شود تعیین کند. در عوض،
یک Pod را «هنوز آماده‌نشده» در نظر می‌گیرد اگر آماده نباشد و در یک بازه‌ی زمانی کوتاه و قابل پیکربندی
از زمان شروع آن به حالت آماده گذار کرده باشد.
این مقدار با گزینه‌ی خط فرمان `--horizontal-pod-autoscaler-initial-readiness-delay`
پیکربندی می‌شود و مقدار پیش‌فرض آن ۳۰ ثانیه است.
پس از آنکه یک Pod آماده شد، کنترل‌کننده هر گذار به حالت
آماده را در صورتی نخستین گذار در نظر می‌گیرد که در یک بازه‌ی زمانی طولانی‌تر و قابل پیکربندی
از زمان شروع آن رخ داده باشد. این مقدار با
گزینه‌ی خط فرمان `--horizontal-pod-autoscaler-cpu-initialization-period` پیکربندی می‌شود
و مقدار پیش‌فرض آن ۵ دقیقه است.

سپس نسبت مقیاس پایه‌ی \\( currentMetricValue \over desiredMetricValue \\)
با استفاده از Podهای باقی‌مانده‌ای که در مراحل بالا کنار گذاشته یا حذف نشده‌اند محاسبه می‌شود.

اگر متریک مفقودی وجود داشته باشد، control plane میانگین را به‌صورت
محافظه‌کارانه‌تری دوباره محاسبه می‌کند و فرض می‌کند آن Podها در صورت کاهش مقیاس ۱۰۰٪ از
مقدار مطلوب و در صورت افزایش مقیاس ۰٪ از آن را مصرف می‌کردند. این کار
شدت هرگونه مقیاس‌دهی احتمالی را تعدیل می‌کند.

افزون بر این، اگر Podهای هنوز آماده‌نشده وجود داشته باشند و بار کاری بدون
در نظر گرفتن متریک‌های مفقود یا Podهای هنوز آماده‌نشده افزایش مقیاس می‌یافت،
کنترل‌کننده به‌صورت محافظه‌کارانه فرض می‌کند که Podهای هنوز آماده‌نشده ۰٪
از متریک مطلوب را مصرف می‌کنند و بدین ترتیب شدت افزایش مقیاس را باز هم تعدیل می‌کند.

پس از در نظر گرفتن Podهای هنوز آماده‌نشده و متریک‌های مفقود،
کنترل‌کننده نسبت استفاده را دوباره محاسبه می‌کند. اگر نسبت جدید جهت مقیاس‌دهی را
معکوس کند یا در محدوده‌ی رواداری باشد، کنترل‌کننده هیچ اقدام مقیاس‌دهی‌ای
انجام نمی‌دهد. در سایر موارد، از نسبت جدید برای تصمیم‌گیری درباره‌ی هرگونه تغییر در
تعداد Podها استفاده می‌شود.

توجه داشته باشید که مقدار _اصلی_ میانگین میزان استفاده، بدون در نظر گرفتن
Podهای هنوز آماده‌نشده یا متریک‌های مفقود، از طریق وضعیت HorizontalPodAutoscaler
گزارش می‌شود، حتی زمانی که از نسبت استفاده‌ی جدید
استفاده می‌شود.

اگر چند متریک در یک HorizontalPodAutoscaler مشخص شده باشد، این
محاسبه برای هر متریک انجام می‌شود و سپس بزرگ‌ترین تعداد رپلیکای مطلوب
انتخاب می‌شود. اگر هر یک از این متریک‌ها قابل تبدیل
به تعداد رپلیکای مطلوب نباشد (برای مثال به دلیل خطا در دریافت متریک‌ها
از APIهای متریک) و متریک‌هایی که قابل دریافت هستند کاهش مقیاس را پیشنهاد کنند،
مقیاس‌دهی انجام نمی‌شود. این بدان معناست که HPA همچنان
قادر به افزایش مقیاس است، اگر یک یا چند متریک مقدار `desiredReplicas` بزرگ‌تر از
مقدار فعلی بدهند.

در نهایت، درست پیش از آنکه HPA هدف را مقیاس‌دهی کند، توصیه‌ی مقیاس ثبت می‌شود.
کنترل‌کننده همه‌ی توصیه‌ها را در یک پنجره‌ی قابل پیکربندی در نظر می‌گیرد و
بالاترین توصیه را از درون آن پنجره انتخاب می‌کند. می‌توانید این مقدار را با استفاده از
گزینه‌ی خط فرمان `--horizontal-pod-autoscaler-downscale-stabilization` پیکربندی کنید که مقدار پیش‌فرض آن ۵ دقیقه است.
این بدان معناست که کاهش‌های مقیاس به‌تدریج رخ می‌دهند و اثر مقادیر متریکی را که به‌سرعت
نوسان می‌کنند هموار می‌سازند.

## آمادگی Pod و متریک‌های مقیاس‌دهی خودکار

کنترل‌کننده‌ی HorizontalPodAutoscaler (HPA) دو گزینه‌ی خط فرمان دارد که بر نحوه‌ی جمع‌آوری متریک‌های CPU از Podها در هنگام راه‌اندازی اثر می‌گذارند:

1. `--horizontal-pod-autoscaler-cpu-initialization-period` (پیش‌فرض: ۵ دقیقه)

  این گزینه بازه‌ی زمانی پس از شروع یک Pod را تعریف می‌کند که در طی آن **میزان استفاده‌ی آن از CPU نادیده گرفته می‌شود**، مگر آنکه:
    - Pod در وضعیت `Ready` باشد **و**
    - نمونه‌ی متریک به‌طور کامل در دوره‌ای گرفته شده باشد که Pod در وضعیت `Ready` بوده است.

  این گزینه‌ی خط فرمان کمک می‌کند تا **استفاده‌ی بالا و گمراه‌کننده از CPU** توسط Podهای در حال راه‌اندازی (برای مثال: برنامه‌های Java در حال گرم شدن) در تصمیم‌های مقیاس‌دهی HPA کنار گذاشته شود.

1. `--horizontal-pod-autoscaler-initial-readiness-delay` (پیش‌فرض: ۳۰ ثانیه)

  این گزینه یک دوره‌ی تأخیر کوتاه پس از شروع یک Pod را تعریف می‌کند که در طی آن کنترل‌کننده‌ی HPA با Podهایی که در حال حاضر `Unready` هستند به‌عنوان Podهای هنوز در حال راه‌اندازی رفتار می‌کند، **حتی اگر پیش‌تر برای مدت کوتاهی به `Ready` گذار کرده باشند**.

  این گزینه برای این منظور طراحی شده است که:
    - از در نظر گرفتن Podهایی که در هنگام راه‌اندازی به‌سرعت میان `Ready` و `Unready` نوسان می‌کنند جلوگیری کند.
    - پیش از آنکه HPA متریک‌های Podها را معتبر بداند، پایداری سیگنال آمادگی اولیه را تضمین کند.


این گزینه‌های خط فرمان را فقط می‌توانید در سطح کل کلاستر تنظیم کنید.

### رفتارهای کلیدی برای آمادگی Pod {#pod-readiness-key-behaviors}

- اگر یک Pod در وضعیت `Ready` باشد و در همین وضعیت باقی بماند، حتی در طول دوره‌ی تأخیر نیز می‌توان آن را به‌عنوان ارائه‌دهنده‌ی متریک به حساب آورد.
- اگر یک Pod به‌سرعت میان `Ready` و `Unready` جابه‌جا شود، متریک‌های آن تا زمانی که به‌طور پایدار `Ready` در نظر گرفته شود نادیده گرفته می‌شوند.

### روش مناسب برای آمادگی Pod {#pod-readiness-good-practices}

- یک `startupProbe` پیکربندی کنید که تا زمانی که دوره‌ی استفاده‌ی بالا از CPU سپری نشده است موفق نشود، یا
- با استفاده از `initialDelaySeconds` اطمینان حاصل کنید که `readinessProbe` شما فقط **پس از** فروکش کردن جهش CPU وضعیت `Ready` را گزارش می‌کند.

و در حالت ایدئال، `--horizontal-pod-autoscaler-cpu-initialization-period` را نیز طوری تنظیم کنید که **مدت زمان راه‌اندازی را پوشش دهد**.

## آبجکت API

HorizontalPodAutoscaler یک نوع (kind) API در گروه API
`autoscaling` کوبرنتیز است. نسخه‌ی پایدار فعلی را می‌توان در
نسخه‌ی API `autoscaling/v2` یافت که از مقیاس‌دهی بر اساس
حافظه و متریک‌های سفارشی پشتیبانی می‌کند. فیلدهای جدیدی که در
`autoscaling/v2` معرفی شده‌اند، هنگام کار با `autoscaling/v1`
به‌صورت حاشیه‌نویسی (annotation) حفظ می‌شوند.

هنگامی که یک آبجکت API از نوع HorizontalPodAutoscaler ایجاد می‌کنید، مطمئن شوید که نام مشخص‌شده یک
[نام زیردامنه‌ی DNS](/docs/concepts/overview/working-with-objects/names#dns-subdomain-names) معتبر باشد.
جزئیات بیشتر درباره‌ی این آبجکت API را می‌توانید در
[آبجکت HorizontalPodAutoscaler](/docs/reference/generated/kubernetes-api/{{< param "version" >}}/#horizontalpodautoscaler-v2-autoscaling) بیابید.

## پایداری مقیاس بار کاری {#flapping}

هنگام مدیریت مقیاس گروهی از رپلیکاها با استفاده از HorizontalPodAutoscaler،
ممکن است به دلیل ماهیت پویای متریک‌های ارزیابی‌شده، تعداد رپلیکاها
مدام و به‌طور مکرر نوسان کند. این پدیده گاهی _thrashing_
یا _flapping_ نامیده می‌شود. این مفهوم مشابه مفهوم _هیسترزیس_ (hysteresis) در سایبرنتیک است.

## مقیاس‌دهی خودکار در هنگام به‌روزرسانی تدریجی

کوبرنتیز به شما امکان می‌دهد یک به‌روزرسانی تدریجی (rolling update) روی یک Deployment انجام دهید. در این
حالت، Deployment مدیریت ReplicaSetهای زیربنایی را برای شما بر عهده می‌گیرد.
هنگامی که مقیاس‌دهی خودکار را برای یک Deployment پیکربندی می‌کنید، یک
HorizontalPodAutoscaler را به یک Deployment واحد متصل می‌کنید. HorizontalPodAutoscaler
فیلد `replicas` آن Deployment را مدیریت می‌کند. کنترل‌کننده‌ی deployment مسئول
تنظیم `replicas` در ReplicaSetهای زیربنایی است، به‌طوری که مجموع آن‌ها در طول rollout و پس از آن
به عددی مناسب برسد.

اگر یک به‌روزرسانی تدریجی روی StatefulSetای انجام دهید که تعداد رپلیکاهای آن
به‌صورت خودکار مقیاس‌دهی می‌شود، StatefulSet مجموعه‌ی Podهای خود را مستقیماً مدیریت می‌کند (هیچ منبع میانی
مشابه ReplicaSet وجود ندارد).

## پشتیبانی از متریک‌های منابع

هر هدف HPA را می‌توان بر اساس میزان استفاده از منابع توسط Podهای موجود در هدف مقیاس‌دهی، مقیاس‌دهی کرد.
هنگام تعریف مشخصات Pod، درخواست‌های منابع مانند `cpu` و `memory` باید
مشخص شوند. این مقادیر برای تعیین میزان استفاده از منابع به کار می‌روند و کنترل‌کننده‌ی HPA از آن‌ها
برای افزایش یا کاهش مقیاس هدف استفاده می‌کند. برای استفاده از مقیاس‌دهی مبتنی بر میزان استفاده از منابع، یک منبع متریک
مانند زیر مشخص کنید:

```yaml
type: Resource
resource:
  name: cpu
  target:
    type: Utilization
    averageUtilization: 60
```
با این متریک، کنترل‌کننده‌ی HPA میانگین میزان استفاده‌ی Podهای موجود در هدف
مقیاس‌دهی را در ۶۰٪ نگه می‌دارد. میزان استفاده (utilization) نسبت میان مصرف فعلی منبع و منابع
درخواست‌شده‌ی Pod است. برای جزئیات بیشتر درباره‌ی نحوه‌ی محاسبه و میانگین‌گیری میزان استفاده،
به بخش [الگوریتم](#algorithm-details) مراجعه کنید.

{{< note >}}
از آنجا که مصرف منابع همه‌ی کانتینرها با هم جمع می‌شود، میزان استفاده‌ی کل Pod ممکن است
مصرف منابع هر کانتینر را به‌طور دقیق نشان ندهد. این می‌تواند به وضعیت‌هایی منجر شود که در آن‌ها
یک کانتینر منفرد با مصرف بالا در حال اجرا باشد، ولی HPA مقیاس را افزایش ندهد، زیرا مصرف کلی
Pod همچنان در محدوده‌ی قابل‌قبول است.
{{< /note >}}

### متریک‌های منابع کانتینر

{{< feature-state feature_gate_name="HPAContainerMetrics" >}}

API مربوط به HorizontalPodAutoscaler همچنین از یک منبع متریک کانتینر پشتیبانی می‌کند که در آن HPA می‌تواند
مصرف منابع کانتینرهای منفرد را در مجموعه‌ای از Podها ردیابی کند تا منبع هدف را مقیاس‌دهی کند.
این کار به شما امکان می‌دهد آستانه‌های مقیاس‌دهی را برای کانتینرهایی که در یک Pod خاص بیشترین اهمیت را دارند پیکربندی کنید.
برای مثال، اگر یک برنامه‌ی وب و یک کانتینر sidecar دارید که لاگ‌گیری را فراهم می‌کند، می‌توانید بر اساس مصرف
منابع برنامه‌ی وب مقیاس‌دهی کنید و کانتینر sidecar و مصرف منابع آن را نادیده بگیرید.

اگر منبع هدف را طوری بازبینی کنید که مشخصات Pod جدیدی با مجموعه‌ی متفاوتی از کانتینرها داشته باشد،
در صورتی که کانتینر تازه اضافه‌شده نیز باید برای مقیاس‌دهی استفاده شود، باید مشخصات HPA را
نیز بازبینی کنید. اگر کانتینر مشخص‌شده در منبع متریک وجود نداشته باشد یا فقط در زیرمجموعه‌ای
از Podها وجود داشته باشد، آن Podها نادیده گرفته می‌شوند و توصیه دوباره محاسبه می‌شود. برای جزئیات بیشتر
درباره‌ی محاسبه، به بخش [الگوریتم](#algorithm-details) مراجعه کنید. برای استفاده از منابع کانتینر در مقیاس‌دهی خودکار، یک منبع
متریک را به شکل زیر تعریف کنید:

```yaml
type: ContainerResource
containerResource:
  name: cpu
  container: application
  target:
    type: Utilization
    averageUtilization: 60
```

در مثال بالا، کنترل‌کننده‌ی HPA هدف را طوری مقیاس‌دهی می‌کند که میانگین میزان استفاده از cpu
در کانتینر `application` همه‌ی Podها ۶۰٪ باشد.

{{< note >}}
اگر نام کانتینری را که یک HorizontalPodAutoscaler در حال ردیابی آن است تغییر دهید، می‌توانید
این تغییر را با ترتیب مشخصی انجام دهید تا اطمینان حاصل شود که مقیاس‌دهی در طول اعمال تغییر
در دسترس و مؤثر باقی می‌ماند. پیش از به‌روزرسانی منبعی که کانتینر را تعریف می‌کند
(مانند یک Deployment)، باید HPA مرتبط را طوری به‌روزرسانی کنید که هم نام جدید و هم نام
قدیمی کانتینر را ردیابی کند. به این ترتیب، HPA می‌تواند در سراسر فرایند به‌روزرسانی
یک توصیه‌ی مقیاس‌دهی محاسبه کند.

پس از آنکه تغییر نام کانتینر را در منبع بار کاری rollout کردید، با حذف
نام قدیمی کانتینر از مشخصات HPA، پیکربندی را مرتب کنید.
{{< /note >}}

## مقیاس‌دهی بر اساس متریک‌های سفارشی

{{< feature-state for_k8s_version="v1.23" state="stable" >}}

(نسخه‌ی API `autoscaling/v2beta2` پیش‌تر این قابلیت را به‌عنوان یک ویژگی بتا ارائه می‌کرد)

به شرط آنکه از نسخه‌ی API `autoscaling/v2` استفاده کنید، می‌توانید یک HorizontalPodAutoscaler را
طوری پیکربندی کنید که بر اساس یک متریک سفارشی (که در کوبرنتیز یا هیچ‌یک از اجزای کوبرنتیز تعبیه نشده است) مقیاس‌دهی کند.
سپس کنترل‌کننده‌ی HorizontalPodAutoscaler این متریک‌های سفارشی را از API کوبرنتیز
پرس‌وجو می‌کند.

برای الزامات، به [پشتیبانی از APIهای متریک](#support-for-metrics-apis) مراجعه کنید.

## مقیاس‌دهی بر اساس چند متریک

{{< feature-state for_k8s_version="v1.23" state="stable" >}}

(نسخه‌ی API `autoscaling/v2beta2` پیش‌تر این قابلیت را به‌عنوان یک ویژگی بتا ارائه می‌کرد)

به شرط آنکه از نسخه‌ی API `autoscaling/v2` استفاده کنید، می‌توانید چند متریک را برای
مقیاس‌دهی یک HorizontalPodAutoscaler مشخص کنید. در این صورت، کنترل‌کننده‌ی HorizontalPodAutoscaler هر متریک را ارزیابی می‌کند
و بر اساس آن متریک یک مقیاس جدید پیشنهاد می‌دهد. HorizontalPodAutoscaler بیشینه‌ی مقیاس
توصیه‌شده برای هر متریک را برمی‌گزیند و بار کاری را به آن اندازه تنظیم می‌کند (به شرط آنکه این مقدار از
بیشینه‌ی کلی‌ای که پیکربندی کرده‌اید بزرگ‌تر نباشد).

## پشتیبانی از APIهای متریک

به‌طور پیش‌فرض، کنترل‌کننده‌ی HorizontalPodAutoscaler متریک‌ها را از مجموعه‌ای از APIها دریافت می‌کند.
برای اینکه کنترل‌کننده بتواند به این APIها دسترسی داشته باشد، مدیران کلاستر باید اطمینان حاصل کنند که:

- [لایه‌ی تجمیع API](/docs/tasks/extend-kubernetes/configure-aggregation-layer/) فعال باشد.

- APIهای متناظر ثبت شده باشند:

  - برای متریک‌های منابع، این API همان [API](/docs/reference/external-api/metrics.v1beta1/) `metrics.k8s.io` است
    که معمولاً توسط [metrics-server](https://github.com/kubernetes-sigs/metrics-server) ارائه می‌شود.
    این API را می‌توان به‌صورت یک افزونه‌ی کلاستر راه‌اندازی کرد.

    {{< note >}}
    HorizontalPodAutoscaler در حال حاضر از API `metrics.k8s.io/v1beta1`
    برای متریک‌های منابع پشتیبانی می‌کند. هنوز از `metrics.k8s.io/v1` پشتیبانی نمی‌کند.
    {{< /note >}}

  - برای متریک‌های سفارشی، این API همان [API](/docs/reference/external-api/custom-metrics.v1beta2/) `custom.metrics.k8s.io` است.
    این API توسط سرورهای API «آداپتور» که فروشندگان راهکارهای متریک ارائه می‌کنند فراهم می‌شود.
    با خط لوله‌ی متریک خود بررسی کنید که آیا آداپتور متریک کوبرنتیز در دسترس است یا نه.

  - برای متریک‌های خارجی، این API همان [API](/docs/reference/external-api/external-metrics.v1beta1/) `external.metrics.k8s.io` است.
    این API ممکن است توسط همان آداپتورهای متریک سفارشی که در بالا ذکر شد ارائه شود.

برای اطلاعات بیشتر درباره‌ی این مسیرهای مختلف متریک و تفاوت‌های آن‌ها، لطفاً پیشنهادهای طراحی مربوطه را برای
[HPA V2](https://git.k8s.io/design-proposals-archive/autoscaling/hpa-v2.md)،
[custom.metrics.k8s.io](https://git.k8s.io/design-proposals-archive/instrumentation/custom-metrics-api.md)
و [external.metrics.k8s.io](https://git.k8s.io/design-proposals-archive/instrumentation/external-metrics-api.md) ببینید.

برای مثال‌هایی از نحوه‌ی استفاده از آن‌ها،
[راهنمای گام‌به‌گام استفاده از متریک‌های سفارشی](/docs/tasks/run-application/horizontal-pod-autoscale-walkthrough/#autoscaling-on-multiple-metrics-and-custom-metrics)
و [راهنمای گام‌به‌گام استفاده از متریک‌های خارجی](/docs/tasks/run-application/horizontal-pod-autoscale-walkthrough/#autoscaling-on-metrics-not-related-to-kubernetes-objects) را ببینید.

## رفتار مقیاس‌دهی قابل پیکربندی

{{< feature-state for_k8s_version="v1.23" state="stable" >}}

(نسخه‌ی API `autoscaling/v2beta2` پیش‌تر این قابلیت را به‌عنوان یک ویژگی بتا ارائه می‌کرد)

اگر از API نسخه‌ی `v2` مربوط به HorizontalPodAutoscaler استفاده کنید، می‌توانید از فیلد `behavior`
(به [مرجع API](/docs/reference/kubernetes-api/workload-resources/horizontal-pod-autoscaler-v2/#HorizontalPodAutoscalerSpec) مراجعه کنید)
برای پیکربندی رفتارهای جداگانه‌ی افزایش مقیاس و کاهش مقیاس استفاده کنید.
این رفتارها را با تنظیم `scaleUp` و / یا `scaleDown`
زیر فیلد `behavior` مشخص می‌کنید.

سیاست‌های مقیاس‌دهی به شما امکان می‌دهند نرخ تغییر رپلیکاها را در هنگام مقیاس‌دهی کنترل کنید.
همچنین از دو تنظیم می‌توان برای جلوگیری از [flapping](#flapping) استفاده کرد: می‌توانید یک
_پنجره‌ی پایدارسازی_ برای هموارسازی تعداد رپلیکاها و یک رواداری برای نادیده گرفتن
نوسانات جزئی متریک در زیر یک آستانه‌ی مشخص تعیین کنید.

### سیاست‌های مقیاس‌دهی

یک یا چند سیاست مقیاس‌دهی را می‌توان در بخش `behavior` از spec مشخص کرد.
هنگامی که چند سیاست مشخص شده باشد، سیاستی که بیشترین میزان تغییر را مجاز می‌داند
به‌طور پیش‌فرض انتخاب می‌شود. مثال زیر این رفتار را
در هنگام کاهش مقیاس نشان می‌دهد:

```yaml
behavior:
  scaleDown:
    policies:
    - type: Pods
      value: 4
      periodSeconds: 60
    - type: Percent
      value: 10
      periodSeconds: 60
```

`periodSeconds` طول بازه‌ی زمانی گذشته‌ای را نشان می‌دهد که سیاست باید در آن برقرار باشد.
بیشینه‌ی مقداری که می‌توانید برای `periodSeconds` تنظیم کنید ۱۸۰۰ (نیم ساعت) است.
سیاست نخست _(Pods)_ اجازه می‌دهد حداکثر ۴ رپلیکا در یک دقیقه کاهش یابند. سیاست دوم
_(Percent)_ اجازه می‌دهد حداکثر ۱۰٪ از رپلیکاهای فعلی در یک دقیقه کاهش یابند.

از آنجا که به‌طور پیش‌فرض سیاستی که بیشترین میزان تغییر را مجاز می‌داند انتخاب می‌شود، سیاست دوم
فقط زمانی استفاده خواهد شد که تعداد رپلیکاهای Pod بیش از ۴۰ باشد. با ۴۰ رپلیکا یا کمتر، سیاست نخست اعمال خواهد شد.
برای نمونه، اگر ۸۰ رپلیکا وجود داشته باشد و هدف باید به ۱۰ رپلیکا کاهش یابد،
در گام نخست ۸ رپلیکا کم خواهد شد. در تکرار بعدی، هنگامی که تعداد
رپلیکاها ۷۲ است، ۱۰٪ از Podها برابر ۷٫۲ است، اما این عدد به ۸ گرد می‌شود. در هر حلقه‌ی
کنترل‌کننده‌ی مقیاس‌دهی خودکار، تعداد Podهایی که باید تغییر کنند بر اساس تعداد
رپلیکاهای فعلی دوباره محاسبه می‌شود. هنگامی که تعداد رپلیکاها به کمتر از ۴۰ برسد، سیاست نخست _(Pods)_ اعمال می‌شود
و هر بار ۴ رپلیکا کاهش خواهد یافت.

انتخاب سیاست را می‌توان با مشخص کردن فیلد `selectPolicy` برای یک جهت
مقیاس‌دهی تغییر داد. با تنظیم مقدار آن روی `Min`، سیاستی انتخاب می‌شود که
کمترین تغییر را در تعداد رپلیکاها مجاز می‌داند. تنظیم مقدار روی `Disabled` مقیاس‌دهی
در آن جهت را به‌طور کامل غیرفعال می‌کند.

### پنجره‌ی پایدارسازی

پنجره‌ی پایدارسازی برای محدود کردن [flapping](#flapping) در
تعداد رپلیکاها، هنگامی که متریک‌های مورد استفاده برای مقیاس‌دهی مدام نوسان می‌کنند، به کار می‌رود. الگوریتم مقیاس‌دهی خودکار
از این پنجره برای استنتاج یک وضعیت مطلوب قبلی و جلوگیری از تغییرات ناخواسته در مقیاس
بار کاری استفاده می‌کند.

برای مثال، در قطعه‌کد نمونه‌ی زیر، یک پنجره‌ی پایدارسازی برای `scaleDown` مشخص شده است.

```yaml
behavior:
  scaleDown:
    stabilizationWindowSeconds: 300
```

هنگامی که متریک‌ها نشان می‌دهند که هدف باید کاهش مقیاس یابد، الگوریتم
به وضعیت‌های مطلوبی که پیش‌تر محاسبه شده‌اند نگاه می‌کند و بالاترین مقدار را از بازه‌ی
مشخص‌شده به کار می‌برد. در مثال بالا، همه‌ی وضعیت‌های مطلوب ۵ دقیقه‌ی گذشته در نظر گرفته می‌شوند.

این کار تقریبی از یک بیشینه‌ی غلتان (rolling maximum) است و از این جلوگیری می‌کند که الگوریتم مقیاس‌دهی به‌طور مکرر
Podها را حذف کند، تنها برای آنکه لحظاتی بعد بازسازی یک Pod معادل را آغاز کند.

### رواداری {#tolerance}

{{< feature-state feature_gate_name="HPAConfigurableTolerance" >}}

فیلد `tolerance` یک آستانه برای تغییرات متریک پیکربندی می‌کند و از
مقیاس‌دهی مقیاس‌دهنده‌ی خودکار برای تغییرات کمتر از آن مقدار جلوگیری می‌کند.

این رواداری به‌صورت میزان تغییر در اطراف مقدار مطلوب متریک تعریف می‌شود که در محدوده‌ی آن
هیچ مقیاس‌دهی‌ای رخ نمی‌دهد. برای مثال، یک HorizontalPodAutoscaler را در نظر بگیرید که
با هدف مصرف حافظه‌ی 100MiB و رواداری افزایش مقیاس ۵٪ پیکربندی شده است:

```yaml
behavior:
  scaleUp:
    tolerance: 0.05 # 5% tolerance for scale up
```

با این پیکربندی، الگوریتم HPA تنها در صورتی افزایش مقیاس را در نظر می‌گیرد که مصرف
حافظه بیشتر از 105MiB باشد (یعنی: ۵٪ بالاتر از هدف).

اگر این فیلد را تنظیم نکنید، HPA رواداری پیش‌فرض ۱۰٪ در سطح کل کلاستر را اعمال می‌کند. این
مقدار پیش‌فرض را می‌توان هم برای افزایش مقیاس و هم برای کاهش مقیاس با استفاده از آرگومان خط فرمان
`--horizontal-pod-autoscaler-tolerance` در
[kube-controller-manager](/docs/reference/command-line-tools-reference/kube-controller-manager/)
به‌روزرسانی کرد. (نمی‌توانید از API کوبرنتیز
برای پیکربندی این مقدار پیش‌فرض استفاده کنید.)

### رفتار پیش‌فرض

برای استفاده از مقیاس‌دهی سفارشی، لازم نیست همه‌ی فیلدها مشخص شوند. فقط مقادیری که باید
سفارشی شوند را می‌توان مشخص کرد. این مقادیر سفارشی با مقادیر پیش‌فرض ادغام می‌شوند. مقادیر پیش‌فرض
با رفتار موجود در الگوریتم HPA مطابقت دارند.

```yaml
behavior:
  scaleDown:
    stabilizationWindowSeconds: 300
    policies:
    - type: Percent
      value: 100
      periodSeconds: 15
  scaleUp:
    stabilizationWindowSeconds: 0
    policies:
    - type: Percent
      value: 100
      periodSeconds: 15
    - type: Pods
      value: 4
      periodSeconds: 15
    selectPolicy: Max
```
برای کاهش مقیاس، پنجره‌ی پایدارسازی _300_ ثانیه است (یا مقدار
گزینه‌ی خط فرمان `--horizontal-pod-autoscaler-downscale-stabilization`، در صورتی که ارائه شده باشد). تنها یک سیاست
برای کاهش مقیاس وجود دارد که اجازه می‌دهد ۱۰۰٪ از رپلیکاهای در حال اجرا حذف شوند؛ این
بدان معناست که هدف مقیاس‌دهی می‌تواند تا حداقل تعداد رپلیکای مجاز کاهش یابد.
برای افزایش مقیاس، هیچ پنجره‌ی پایدارسازی‌ای وجود ندارد. هنگامی که متریک‌ها نشان می‌دهند که هدف باید
افزایش مقیاس یابد، هدف بلافاصله افزایش مقیاس می‌یابد. دو سیاست وجود دارد که طبق آن‌ها حداکثر ۴ Pod یا ۱۰۰٪ از
رپلیکاهای در حال اجرا می‌توانند هر ۱۵ ثانیه اضافه شوند تا HPA به وضعیت پایدار خود برسد.

### مثال: تغییر پنجره‌ی پایدارسازی کاهش مقیاس

برای ارائه‌ی یک پنجره‌ی پایدارسازی سفارشی کاهش مقیاس به مدت ۱ دقیقه،
رفتار زیر به HPA افزوده می‌شود:

```yaml
behavior:
  scaleDown:
    stabilizationWindowSeconds: 60
```

### مثال: محدود کردن نرخ کاهش مقیاس

برای محدود کردن نرخ حذف Podها توسط HPA به ۱۰٪ در دقیقه،
رفتار زیر به HPA افزوده می‌شود:

```yaml
behavior:
  scaleDown:
    policies:
    - type: Percent
      value: 10
      periodSeconds: 60
```

برای اطمینان از اینکه بیش از ۵ Pod در دقیقه حذف نشوند، می‌توانید یک سیاست دوم کاهش مقیاس
با اندازه‌ی ثابت ۵ اضافه کنید و `selectPolicy` را روی کمینه تنظیم کنید. تنظیم `selectPolicy` روی `Min` به این معناست
که مقیاس‌دهنده‌ی خودکار سیاستی را انتخاب می‌کند که بر کمترین تعداد Podها اثر می‌گذارد:

```yaml
behavior:
  scaleDown:
    policies:
    - type: Percent
      value: 10
      periodSeconds: 60
    - type: Pods
      value: 5
      periodSeconds: 60
    selectPolicy: Min
```

### مثال: غیرفعال کردن کاهش مقیاس

مقدار `Disabled` برای `selectPolicy` مقیاس‌دهی در جهت داده‌شده را خاموش می‌کند.
بنابراین برای جلوگیری از کاهش مقیاس، از سیاست زیر استفاده می‌شود:

```yaml
behavior:
  scaleDown:
    selectPolicy: Disabled
```

## پشتیبانی از HorizontalPodAutoscaler در kubectl

HorizontalPodAutoscaler، مانند هر منبع API دیگری، به روشی استاندارد توسط `kubectl` پشتیبانی می‌شود.
می‌توانید با استفاده از فرمان `kubectl create` یک مقیاس‌دهنده‌ی خودکار جدید ایجاد کنید.
می‌توانید مقیاس‌دهنده‌های خودکار را با `kubectl get hpa` فهرست کنید یا توضیحات مفصل را با `kubectl describe hpa` دریافت کنید.
در نهایت، می‌توانید یک مقیاس‌دهنده‌ی خودکار را با استفاده از `kubectl delete hpa` حذف کنید.

افزون بر این، یک فرمان ویژه‌ی `kubectl autoscale` برای ایجاد یک آبجکت HorizontalPodAutoscaler وجود دارد.
برای نمونه، اجرای `kubectl autoscale rs foo --min=2 --max=5 --cpu=80%`
یک مقیاس‌دهنده‌ی خودکار برای ReplicaSet _foo_ ایجاد می‌کند که میزان استفاده‌ی هدف از CPU در آن روی `80%`
و تعداد رپلیکاها میان ۲ و ۵ تنظیم شده است.

## مقیاس‌دهی به صفر و از صفر

{{< feature-state feature_gate_name="HPAScaleToZero" >}}

برای HorizontalPodAutoscalerهایی که بر اساس متریک‌های [سفارشی](#scaling-on-custom-metrics) (آبجکت) یا
خارجی مقیاس‌دهی می‌کنند، می‌توانید `spec.minReplicas` را روی `0` تنظیم کنید. در این صورت، بار کاری هنگامی که باری وجود ندارد
تا صفر رپلیکا کاهش مقیاس می‌یابد و هنگامی که متریک نشان دهد دست‌کم
یک رپلیکا لازم است، دوباره افزایش مقیاس می‌یابد. این قابلیت برای بارهای کاری‌ای مفید است که برای مدت‌های طولانی بیکار هستند و
نگه داشتن آن‌ها در حال اجرا پرهزینه است، مانند مصرف‌کنندگان صفی که گاه‌به‌گاه استفاده می‌شود یا Jobهایی که به
سخت‌افزار اختصاصی مانند GPU نیاز دارند.

مقیاس‌دهی به صفر فقط برای متریک‌های آبجکت و متریک‌های خارجی پشتیبانی می‌شود. این قابلیت برای
متریک‌های منابع (مانند میزان استفاده از CPU یا حافظه) در دسترس نیست، زیرا این متریک‌ها را فقط می‌توان روی
Podهای در حال اجرا اندازه‌گیری کرد. تنظیم `minReplicas: 0` مستلزم آن است که دست‌کم یک متریک آبجکت یا متریک خارجی
پیکربندی شده باشد؛ در غیر این صورت سرور API آن HorizontalPodAutoscaler را رد می‌کند.

این رفتار توسط
[feature gate](/docs/reference/command-line-tools-reference/feature-gates/) `HPAScaleToZero` کنترل می‌شود که به‌طور
پیش‌فرض فعال است. این feature gate باید هم روی
{{< glossary_tooltip text="kube-apiserver" term_id="kube-apiserver" >}} (که
`minReplicas: 0` را مجاز می‌کند) و هم روی
{{< glossary_tooltip text="kube-controller-manager" term_id="kube-controller-manager" >}}
(که مقیاس‌دهی را انجام می‌دهد) فعال باشد.

در حالی که HPA یک بار کاری را در صفر رپلیکا نگه داشته است، یک condition به نام `ScaledToZero` با مقدار
`True` در وضعیت HorizontalPodAutoscaler ثبت می‌کند. HPA از این condition برای تمایز میان
بار کاری‌ای که خودش آن را به صفر رسانده است (و هنگام بازگشت متریک دوباره افزایش مقیاس خواهد داد) و بار کاری‌ای که با تنظیم تعداد رپلیکای آن روی
`0` [به‌صورت دستی غیرفعال شده](#implicit-maintenance-mode-deactivation) است استفاده می‌کند. هنگامی که بار کاری دوباره افزایش مقیاس یابد، این condition با دلیل
`NotScaledToZero` روی `False` تنظیم می‌شود.

## غیرفعال‌سازی ضمنی در حالت نگهداری

می‌توانید HPA را برای یک هدف به‌طور ضمنی غیرفعال کنید، بدون
اینکه نیازی به تغییر پیکربندی خود HPA باشد. اگر تعداد رپلیکای مطلوب هدف
روی 0 تنظیم شود و حداقل تعداد رپلیکای HPA بزرگ‌تر از 0 باشد، HPA
تنظیم هدف را متوقف می‌کند (و Condition `ScalingActive` را روی خودش
به `false` تنظیم می‌کند) تا زمانی که آن را با تنظیم دستی تعداد رپلیکای مطلوب هدف
یا حداقل تعداد رپلیکای HPA دوباره فعال کنید.

### مهاجرت Deploymentها و StatefulSetها به مقیاس‌دهی خودکار افقی

هنگامی که یک HPA فعال است، توصیه می‌شود مقدار `spec.replicas` مربوط به
Deployment و / یا StatefulSet از
{{< glossary_tooltip text="مانیفست(های)" term_id="manifest" >}} آن‌ها حذف شود. اگر این کار انجام نشود، هر بار
که تغییری روی آن آبجکت اعمال شود، برای مثال از طریق `kubectl apply -f
deployment.yaml`، این کار به کوبرنتیز دستور می‌دهد که تعداد فعلی Podها را
به مقدار کلید `spec.replicas` مقیاس‌دهی کند. این ممکن است
مطلوب نباشد و هنگامی که یک HPA فعال است دردسرساز شود و به رفتار thrashing یا flapping منجر شود.

به خاطر داشته باشید که حذف `spec.replicas` ممکن است یک‌بار باعث
کاهش تعداد Podها شود، زیرا مقدار پیش‌فرض این کلید 1 است (به
[رپلیکاهای Deployment](/docs/concepts/workloads/controllers/deployment#replicas) مراجعه کنید).
پس از به‌روزرسانی، همه‌ی Podها به‌جز 1 Pod فرایند خاتمه‌ی خود را آغاز می‌کنند. هر
اعمال استقرار پس از آن به‌طور عادی رفتار خواهد کرد و پیکربندی به‌روزرسانی
تدریجی را به‌صورت مطلوب رعایت خواهد کرد. می‌توانید با انتخاب یکی از دو روش زیر،
بسته به نحوه‌ی تغییر استقرارهای خود، از این کاهش جلوگیری کنید:

{{< tabs name="fix_replicas_instructions" >}}
{{% tab name="اعمال سمت کلاینت (Client Side Apply؛ این حالت پیش‌فرض است)" %}}

1. `kubectl apply edit-last-applied deployment/<deployment_name>`
2. در ویرایشگر، `spec.replicas` را حذف کنید. هنگامی که ذخیره می‌کنید و از ویرایشگر خارج می‌شوید، `kubectl`
   به‌روزرسانی را اعمال می‌کند. در این مرحله هیچ تغییری در تعداد Podها رخ نمی‌دهد.
3. اکنون می‌توانید `spec.replicas` را از مانیفست حذف کنید. اگر از سیستم مدیریت کد منبع استفاده می‌کنید،
   تغییرات خود را نیز commit کنید یا هر گام دیگری را که برای بازبینی کد منبع
   متناسب با نحوه‌ی ردیابی به‌روزرسانی‌های شماست انجام دهید.
4. از این پس می‌توانید `kubectl apply -f deployment.yaml` را اجرا کنید

## {{% heading "whatsnext" %}}

اگر مقیاس‌دهی خودکار را در کلاستر خود پیکربندی می‌کنید، ممکن است بخواهید استفاده از
[مقیاس‌دهی خودکار نود](/docs/concepts/cluster-administration/node-autoscaling/)
را نیز در نظر بگیرید تا اطمینان حاصل کنید که تعداد مناسبی نود را اجرا می‌کنید.
همچنین می‌توانید درباره‌ی [مقیاس‌دهی خودکار _عمودی_ Pod](/docs/concepts/workloads/autoscaling/vertical-pod-autoscale/) بیشتر بخوانید.

برای اطلاعات بیشتر درباره‌ی HorizontalPodAutoscaler:

- یک [مثال گام‌به‌گام](/docs/tasks/run-application/horizontal-pod-autoscale-walkthrough/) برای مقیاس‌دهی خودکار افقی Pod را بخوانید.
- مستندات [`kubectl autoscale`](/docs/reference/generated/kubectl/kubectl-commands/#autoscale) را بخوانید.
- اگر می‌خواهید آداپتور متریک سفارشی خود را بنویسید، برای شروع
  [boilerplate](https://github.com/kubernetes-sigs/custom-metrics-apiserver) را بررسی کنید.
- [مرجع API](/docs/reference/kubernetes-api/workload-resources/horizontal-pod-autoscaler-v2/) مربوط به HorizontalPodAutoscaler را بخوانید.
