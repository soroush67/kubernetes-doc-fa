هر {{< glossary_tooltip text="آبجکت" term_id="object" >}} در کلاستر شما یک [_نام_](#names) دارد که در میان منابع هم‌نوع یکتاست.
همچنین هر آبجکت کوبرنتیز یک [_UID_](#uids) دارد که در کل کلاستر یکتاست.

برای مثال، در یک [فضای نام (namespace)](/docs/concepts/overview/working-with-objects/namespaces/) فقط می‌توانید یک Pod با نام `myapp-1234` داشته باشید، اما می‌توانید یک Pod و یک Deployment داشته باشید که نام هر دو `myapp-1234` باشد.

کوبرنتیز برای ویژگی‌های غیریکتایی که کاربر تعیین می‌کند، [برچسب‌ها](/docs/concepts/overview/working-with-objects/labels/) و [حاشیه‌نویسی‌ها (annotations)](/docs/concepts/overview/working-with-objects/annotations/) را فراهم می‌کند.



<!-- body -->

## نام‌ها

{{< glossary_definition term_id="name" length="all" >}}

نام‌ها باید در میان همهٔ [نسخه‌های API](/docs/concepts/overview/kubernetes-api/#api-groups-and-versioning) یک منبع یکتا باشند.

کوبرنتیز آبجکت‌ها را با ترکیبی از چهار ویژگی به‌طور یکتا شناسایی می‌کند:
* **گروه API** (مثلاً `apps`)
* **نوع منبع** (مثلاً `deployments`)
* **فضای نام** (برای منابعی که به فضای نام تعلق دارند)
* **نام**

اگرچه می‌توانید از طریق نسخه‌های مختلف API (مانند `v1` یا `v1beta1`) به یک منبع دسترسی داشته باشید، هر نسخه صرفاً نمایش متفاوتی از همان آبجکت زیربنایی است. از آنجا که نسخه بخشی از شناسهٔ یکتا نیست، نمی‌توانید با استفاده از نسخه‌های مختلف API دو آبجکت با نام و نوع منبع یکسان در یک فضای نام ایجاد کنید.

{{< note >}}
در مواردی که آبجکت‌ها نمایانگر یک موجودیت فیزیکی هستند، مانند Node که نمایانگر یک میزبان فیزیکی است، اگر میزبان بدون حذف و ایجاد دوبارهٔ Node با همان نام از نو ایجاد شود، کوبرنتیز میزبان جدید را همان میزبان قدیمی در نظر می‌گیرد و این ممکن است به ناسازگاری‌هایی منجر شود.
{{< /note >}}

اگر در درخواست ایجاد منبع به‌جای `name` فیلد `generateName` ارائه شود، سرور می‌تواند خودش نامی تولید کند.
هنگام استفاده از `generateName`، مقدار ارائه‌شده به‌عنوان پیشوند نام به کار می‌رود و سرور یک پسوند تولیدشده به آن اضافه می‌کند. با اینکه نام به‌صورت خودکار تولید می‌شود، ممکن است با نام‌های موجود تداخل داشته باشد و پاسخ HTTP 409 برگردانده شود. در کوبرنتیز نسخهٔ 1.31 و بعد از آن، احتمال وقوع این مسئله بسیار کمتر شده است، زیرا سرور پیش از برگرداندن پاسخ HTTP 409 تا ۸ بار برای تولید یک نام یکتا تلاش می‌کند.

در ادامه، چهار نوع از محدودیت‌های رایج برای نام منابع آمده است.

### نام‌های زیردامنهٔ DNS

بیشتر انواع منابع به نامی نیاز دارند که بتوان از آن به‌عنوان نام زیردامنهٔ DNS، مطابق تعریف [RFC 1123](https://tools.ietf.org/html/rfc1123)، استفاده کرد.
یعنی نام باید:

- حداکثر ۲۵۳ نویسه داشته باشد
- فقط شامل نویسه‌های الفبایی-عددی کوچک، '-' یا '.' باشد
- با یک نویسهٔ الفبایی-عددی شروع شود
- با یک نویسهٔ الفبایی-عددی پایان یابد

### نام‌های برچسب RFC 1123 {#dns-label-names}

برخی از انواع منابع نیاز دارند که نامشان از استاندارد برچسب DNS، مطابق تعریف [RFC 1123](https://tools.ietf.org/html/rfc1123)، پیروی کند.
یعنی نام باید:

- حداکثر ۶۳ نویسه داشته باشد
- فقط شامل نویسه‌های الفبایی-عددی کوچک یا '-' باشد
- با یک حرف الفبا شروع شود
- با یک نویسهٔ الفبایی-عددی پایان یابد

{{< note >}}
وقتی feature gate با نام `RelaxedServiceNameValidation` فعال باشد، نام آبجکت‌های Service می‌تواند با یک رقم شروع شود.
{{< /note >}}

### نام‌های برچسب RFC 1035

برخی از انواع منابع نیاز دارند که نامشان از استاندارد برچسب DNS، مطابق تعریف [RFC 1035](https://tools.ietf.org/html/rfc1035)، پیروی کند.
یعنی نام باید:

- حداکثر ۶۳ نویسه داشته باشد
- فقط شامل نویسه‌های الفبایی-عددی کوچک یا '-' باشد
- با یک حرف الفبا شروع شود
- با یک نویسهٔ الفبایی-عددی پایان یابد

{{< note >}}
اگرچه RFC 1123 از نظر فنی اجازه می‌دهد برچسب‌ها با رقم شروع شوند، پیاده‌سازی فعلی کوبرنتیز الزام می‌کند که برچسب‌های RFC 1035 و RFC 1123 هر دو با یک حرف الفبا شروع شوند. تنها استثنا زمانی است که feature gate با نام `RelaxedServiceNameValidation` برای آبجکت‌های Service فعال باشد؛ در این حالت نام Serviceها می‌تواند با رقم شروع شود.
{{< /note >}}

### نام‌های بخش مسیر

برخی از انواع منابع نیاز دارند که نامشان را بتوان به‌طور ایمن به‌عنوان یک بخش مسیر (path segment) کدگذاری کرد. به بیان دیگر، نام نمی‌تواند "." یا ".." باشد و نمی‌تواند شامل "/" یا "%" باشد.

در اینجا نمونه‌ای از مانیفست یک Pod با نام `nginx-demo` آمده است.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx-demo
spec:
  containers:
  - name: nginx
    image: nginx:1.14.2
    ports:
    - containerPort: 80
```


{{< note >}}
برخی از انواع منابع محدودیت‌های بیشتری برای نام خود دارند.
{{< /note >}}

## شناسه‌های UID

{{< glossary_definition term_id="uid" length="all" >}}

شناسه‌های UID در کوبرنتیز، شناسه‌های یکتای جهانی (که با نام UUID نیز شناخته می‌شوند) هستند.
UUIDها در قالب استانداردهای ISO/IEC 9834-8 و ITU-T X.667 استانداردسازی شده‌اند.
