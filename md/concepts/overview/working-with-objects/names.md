<!-- overview -->

هر {{< glossary_tooltip text="آبجکت" term_id="object" >}} در کلاستر شما یک [_نام_](#names) دارد که برای آن نوع منبع یکتاست.
هر آبجکت کوبرنتیز همچنین یک [_UID_](#uids) دارد که در کل کلاستر شما یکتاست.

برای مثال، درون یک [فضای نام](/docs/concepts/overview/working-with-objects/namespaces/) فقط می‌توانید یک Pod با نام `myapp-1234` داشته باشید، اما می‌توانید یک Pod و یک Deployment داشته باشید که هر دو `myapp-1234` نام دارند.

برای ویژگی‌های غیریکتایی که کاربر فراهم می‌کند، کوبرنتیز [برچسب‌ها](/docs/concepts/overview/working-with-objects/labels/) و [حاشیه‌نویسی‌ها](/docs/concepts/overview/working-with-objects/annotations/) را ارائه می‌دهد.



<!-- body -->

## نام‌ها {#names}

{{< glossary_definition term_id="name" length="all" >}}

نام‌ها باید در میان همهٔ [نسخه‌های API](/docs/concepts/overview/kubernetes-api/#api-groups-and-versioning) یک منبع یکسان یکتا باشند. 

کوبرنتیز آبجکت‌ها را با استفاده از ترکیبی از چهار ویژگی به‌طور یکتا شناسایی می‌کند:
* **گروه API** (برای مثال، `apps`)
* **نوع منبع** (برای مثال، `deployments`)
* **فضای نام** (برای منابع وابسته به فضای نام)
* **نام**

اگرچه می‌توانید از طریق نسخه‌های مختلف API (مانند `v1` یا `v1beta1`) به یک منبع دسترسی داشته باشید، نسخه صرفاً بازنمایی متفاوتی از همان آبجکت زیربنایی است. از آنجا که نسخه بخشی از شناسایی یکتا نیست، نمی‌توانید با استفاده از نسخه‌های مختلف API، دو آبجکت با نام و نوع منبع یکسان در یک فضای نام ایجاد کنید.

{{< note >}}
در مواردی که آبجکت‌ها نمایانگر یک موجودیت فیزیکی هستند، مانند Nodeای که نمایانگر یک میزبان فیزیکی است، اگر میزبان بدون حذف و ایجاد دوبارهٔ Node با همان نام دوباره ایجاد شود، کوبرنتیز میزبان جدید را همان میزبان قدیمی تلقی می‌کند که ممکن است به ناسازگاری‌هایی منجر شود.
{{< /note >}}

هنگامی که در یک درخواست ایجاد منبع، به‌جای `name` فیلد `generateName` ارائه شود، سرور ممکن است یک نام تولید کند.
هنگام استفاده از `generateName`، مقدار ارائه‌شده به‌عنوان پیشوند نام استفاده می‌شود و سرور یک پسوند تولیدشده
به آن اضافه می‌کند. با وجود اینکه نام تولید می‌شود، ممکن است با نام‌های موجود تداخل داشته باشد و به پاسخ HTTP 409 منجر شود. این
اتفاق در کوبرنتیز v1.31 و نسخه‌های بعدی بسیار کمتر محتمل شد، زیرا سرور پیش از بازگرداندن پاسخ HTTP 409، تا ۸ بار برای تولید یک
نام یکتا تلاش می‌کند.

در ادامه چهار نوع از محدودیت‌های رایج نام‌گذاری منابع آمده است.

### نام‌های زیردامنهٔ DNS {#dns-subdomain-names}

بیشتر انواع منبع به نامی نیاز دارند که بتوان آن را به‌عنوان نام زیردامنهٔ DNS
مطابق تعریف [RFC 1123](https://tools.ietf.org/html/rfc1123) به کار برد.
این بدان معناست که نام باید:

- حداکثر ۲۵۳ نویسه داشته باشد
- فقط شامل نویسه‌های الفبایی-عددی کوچک، '-' یا '.' باشد
- با یک نویسهٔ الفبایی-عددی آغاز شود
- با یک نویسهٔ الفبایی-عددی پایان یابد

### نام‌های برچسب RFC 1123 {#dns-label-names}

برخی انواع منبع نیاز دارند نامشان از استاندارد برچسب DNS
مطابق تعریف [RFC 1123](https://tools.ietf.org/html/rfc1123) پیروی کند.
این بدان معناست که نام باید:

- حداکثر ۶۳ نویسه داشته باشد
- فقط شامل نویسه‌های الفبایی-عددی کوچک یا '-' باشد
- با یک نویسهٔ الفبایی آغاز شود
- با یک نویسهٔ الفبایی-عددی پایان یابد

{{< note >}}
هنگامی که feature gate با نام `RelaxedServiceNameValidation` فعال باشد،
نام آبجکت‌های Service مجاز است با یک رقم آغاز شود.
{{< /note >}}

### نام‌های برچسب RFC 1035 {#rfc-1035-label-names}

برخی انواع منبع نیاز دارند نامشان از استاندارد برچسب DNS
مطابق تعریف [RFC 1035](https://tools.ietf.org/html/rfc1035) پیروی کند.
این بدان معناست که نام باید:

- حداکثر ۶۳ نویسه داشته باشد
- فقط شامل نویسه‌های الفبایی-عددی کوچک یا '-' باشد
- با یک نویسهٔ الفبایی آغاز شود
- با یک نویسهٔ الفبایی-عددی پایان یابد

{{< note >}}
اگرچه RFC 1123 از نظر فنی اجازه می‌دهد برچسب‌ها با رقم آغاز شوند، پیاده‌سازی فعلی
کوبرنتیز الزام می‌کند که برچسب‌های RFC 1035 و RFC 1123 هر دو با یک نویسهٔ الفبایی
آغاز شوند. استثنا زمانی است که feature gate با نام `RelaxedServiceNameValidation`
برای آبجکت‌های Service فعال باشد که اجازه می‌دهد نام Serviceها با رقم آغاز شود.
{{< /note >}}

### نام‌های بخش مسیر {#path-segment-names}

برخی انواع منبع نیاز دارند نامشان بتواند به‌طور ایمن به‌عنوان یک
بخش مسیر (path segment) کدگذاری شود. به عبارت دیگر، نام نمی‌تواند "." یا ".." باشد و نام نمی‌تواند
شامل "/" یا "%" باشد.

در اینجا یک مانیفست نمونه برای یک Pod با نام `nginx-demo` آمده است.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx-demo
spec:
  containers:
  - name: nginx
    image: nginx:1.14.2
    ports:
    - containerPort: 80
```


{{< note >}}
برخی انواع منبع محدودیت‌های بیشتری بر نام‌های خود دارند.
{{< /note >}}

## UIDها {#uids}

{{< glossary_definition term_id="uid" length="all" >}}

UIDهای کوبرنتیز شناسه‌های یکتای جهانی (که با نام UUID نیز شناخته می‌شوند) هستند.
UUIDها در قالب ISO/IEC 9834-8 و ITU-T X.667 استاندارد شده‌اند.
