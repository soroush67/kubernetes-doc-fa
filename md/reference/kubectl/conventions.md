## استفاده از `kubectl` در اسکریپت‌های قابل استفاده مجدد

برای دریافت خروجی پایدار در یک اسکریپت:

* یکی از قالب‌های خروجی مناسب پردازش ماشینی، مانند `-o name`، `-o json`، `-o yaml`، `-o go-template` یا `-o jsonpath` را درخواست کنید.
* نسخه را به‌طور کامل مشخص کنید. برای مثال، `jobs.v1.batch/myjob`. این کار تضمین می‌کند که kubectl از نسخهٔ پیش‌فرض خود که ممکن است با گذشت زمان تغییر کند، استفاده نکند.
* به context، تنظیمات برگزیده (preferences) یا سایر حالت‌های ضمنی تکیه نکنید.

## Subresourceها

* می‌توانید از آرگومان `--subresource` در زیرفرمان‌های kubectl مانند `get`، `patch`،
`edit`، `apply` و `replace` استفاده کنید تا subresourceهای همهٔ منابعی که از آن‌ها
پشتیبانی می‌کنند را دریافت و به‌روزرسانی کنید. در کوبرنتیز نسخهٔ {{< skew currentVersion >}}، تنها subresourceهای `status`، `scale`
و `resize` پشتیبانی می‌شوند.
  * برای `kubectl edit`، subresource با نام `scale` پشتیبانی نمی‌شود. اگر `--subresource` را
    همراه با `kubectl edit` استفاده کنید و `scale` را به‌عنوان subresource مشخص کنید، فرمان با خطا متوقف می‌شود.
* قرارداد API برای یک subresource با قرارداد API برای یک منبع کامل یکسان است. هنگام به‌روزرسانی
subresource با نام `status` به یک مقدار جدید، به یاد داشته باشید که ممکن است یک کنترل‌کننده
آن subresource را دوباره به مقداری متفاوت همسان‌سازی (reconcile) کند.


## بهترین روش‌ها

### `kubectl run`

برای اینکه `kubectl run` با رویکرد زیرساخت به‌صورت کد (infrastructure as code) سازگار باشد:

* ایمیج را با یک برچسب مختص نسخه علامت‌گذاری کنید و آن برچسب را به نسخهٔ جدید منتقل نکنید. برای مثال، به‌جای `:latest` از `:v1234`، `v1.2.3` یا `r03062016-1-4` استفاده کنید (برای اطلاعات بیشتر، [شیوه‌های خوب پیکربندی در کوبرنتیز](/blog/2025/11/25/configuration-good-practices/) را ببینید).
* اسکریپت مربوط به ایمیجی را که به‌شدت پارامتری شده است، در مخزن کد ثبت (check in) کنید.
* برای قابلیت‌هایی که مورد نیاز هستند اما با فلگ‌های `kubectl run` قابل بیان نیستند، به فایل‌های پیکربندی ثبت‌شده در سیستم کنترل نسخه روی بیاورید.

می‌توانید از فلگ `--dry-run=client` استفاده کنید تا آبجکتی را که به کلاستر شما ارسال می‌شد، بدون ارسال واقعی آن پیش‌نمایش کنید.

### `kubectl proxy`

{{< caution >}}
مرور endpointهای Pod یا Service نامعتبر (untrusted) از طریق `kubectl proxy` خطرناک است،
زیرا محتوای ارائه‌شده با استفاده از اعتبارنامه‌های پروکسی به‌طور ضمنی به API کوبرنتیز دسترسی دارد.
احتیاط کنید و هنگام استفاده از اعتبارنامه‌های دارای سطح دسترسی بالا، از دسترسی به endpointهای نامعتبر خودداری کنید.

برای کاهش خطر:

* از مرور Podها یا Serviceهای نامعتبر از طریق `kubectl proxy` خودداری کنید.
* زمانی که فقط نیاز به مشاهدهٔ منابع دارید، از `--reject-methods='POST,PUT,PATCH,DELETE'` استفاده کنید تا پروکسی
  به عملیات فقط‌خواندنی محدود شود.
* از `--reject-paths` استفاده کنید تا مسیرهای API ای را که پروکسی در دسترس قرار می‌دهد محدود کنید.
* مگر در موارد ضروری، `kubectl proxy` را با اعتبارنامه‌های cluster-admin اجرا نکنید.
{{< /caution >}}

### `kubectl apply`

* می‌توانید از `kubectl apply` برای ایجاد یا به‌روزرسانی منابع استفاده کنید. برای اطلاعات بیشتر دربارهٔ استفاده از kubectl apply برای به‌روزرسانی منابع، [Kubectl Book](https://kubectl.docs.kubernetes.io) را ببینید.
