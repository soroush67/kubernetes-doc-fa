{{< feature-state feature_gate_name="ServerSideApply" >}}

کوبرنتیز از همکاری چند اعمال‌کننده (applier) برای مدیریت فیلدهای یک [آبجکت](/docs/concepts/overview/working-with-objects/) واحد پشتیبانی می‌کند.

قابلیت Server-Side Apply سازوکاری اختیاری فراهم می‌کند تا control plane کلاستر شما بتواند تغییرات فیلدهای یک آبجکت را ردیابی کند. این قابلیت در سطح هر منبع مشخص، اطلاعات مربوط به کنترل بر فیلدهای آن آبجکت را ثبت و ردیابی می‌کند.

قابلیت Server-Side Apply به کاربران و {{< glossary_tooltip text="کنترل‌کننده‌ها" term_id="controller" >}} کمک می‌کند منابع خود را از طریق پیکربندی اعلانی (declarative) مدیریت کنند. کلاینت‌ها می‌توانند با ارسال _قصد کاملاً مشخص‌شده_ (fully specified intent) خود، {{< glossary_tooltip text="آبجکت‌ها" term_id="object" >}} را به‌صورت اعلانی ایجاد و ویرایش کنند.

قصد کاملاً مشخص‌شده، آبجکتی جزئی است که فقط فیلدها و مقادیری را در بر می‌گیرد که کاربر درباره‌ی آن‌ها نظر مشخصی دارد. این قصد یا آبجکت جدیدی ایجاد می‌کند (و برای فیلدهای مشخص‌نشده از مقادیر پیش‌فرض استفاده می‌کند)، یا API server آن را با آبجکت موجود [ترکیب](#merge-strategy) می‌کند.

بخش [مقایسه با اعمال سمت کلاینت](#comparison-with-client-side-apply) توضیح می‌دهد که Server-Side Apply چه تفاوتی با پیاده‌سازی اولیه و سمت کلاینت `kubectl apply` دارد.

## مدیریت فیلدها

سرور API کوبرنتیز _فیلدهای مدیریت‌شده_ (managed fields) را برای همه‌ی آبجکت‌هایی که تازه ایجاد می‌شوند ردیابی می‌کند.

هنگام اعمال یک آبجکت، فیلدهایی که مقدار متفاوتی دارند و مالک آن‌ها [مدیر](#managers) دیگری است، به [تعارض](#conflicts) منجر می‌شوند. هدف از این کار اعلام این نکته است که عملیات ممکن است تغییرات همکار دیگری را خنثی کند. نوشتن در آبجکت‌هایی که فیلدهای مدیریت‌شده دارند را می‌توان اجباری کرد؛ در این صورت مقدار هر فیلد دارای تعارض بازنویسی می‌شود و مالکیت آن منتقل می‌شود.

هر زمان که مقدار یک فیلد واقعاً تغییر کند، مالکیت آن از مدیر فعلی به مدیری منتقل می‌شود که تغییر را انجام داده است.

مدیریت یک فیلد توسط کاربر، به مفهوم Server-Side Apply، به این معناست که کاربر به مقدار آن فیلد متکی است و انتظار دارد این مقدار تغییر نکند. کاربری که آخرین بار درباره‌ی مقدار یک فیلد اظهار نظر کرده است، به‌عنوان مدیر فعلی آن فیلد ثبت می‌شود. این کار با تغییر صریح جزئیات مدیر فیلد از طریق `POST` در HTTP (**create**)، `PUT` (**update**) یا `PATCH` غیر apply (**patch**) انجام‌شدنی است. همچنین می‌توانید با گنجاندن مقداری برای آن فیلد در یک عملیات Server-Side Apply، مدیر فیلد را اعلام و ثبت کنید.

هر درخواست **patch** از نوع Server-Side Apply ایجاب می‌کند که کلاینت هویت خود را به‌عنوان یک [مدیر فیلد](#managers) ارائه دهد. هنگام استفاده از Server-Side Apply، تلاش برای تغییر فیلدی که مدیر دیگری آن را کنترل می‌کند به رد شدن درخواست می‌انجامد، مگر اینکه کلاینت بازنویسی را اجباری کند. برای جزئیات بازنویسی‌ها، بخش [تعارض‌ها](#conflicts) را ببینید.

وقتی دو یا چند اعمال‌کننده یک فیلد را روی مقداری یکسان تنظیم کنند، در مالکیت آن فیلد شریک می‌شوند. پس از آن، هر تلاشی از سوی هر یک از این اعمال‌کننده‌ها برای تغییر مقدار فیلد مشترک به تعارض منجر می‌شود. مالکان مشترک یک فیلد می‌توانند با ارسال یک درخواست **patch** از نوع Server-Side Apply که آن فیلد را شامل نمی‌شود، از مالکیت آن صرف‌نظر کنند.

جزئیات مدیریت فیلدها در فیلدی به نام `managedFields` ذخیره می‌شود که بخشی از [`metadata`](/docs/reference/kubernetes-api/common-definitions/object-meta/) آبجکت است.

اگر فیلدی را از یک مانیفست حذف کنید و آن مانیفست را اعمال کنید، Server-Side Apply بررسی می‌کند که آیا مدیر فیلد دیگری نیز مالک آن فیلد هست یا نه. اگر هیچ مدیر فیلد دیگری مالک آن نباشد، فیلد یا از آبجکت زنده حذف می‌شود یا، در صورت داشتن مقدار پیش‌فرض، به آن مقدار بازنشانی می‌شود. همین قاعده برای آیتم‌های لیست‌های انجمنی (associative list) یا mapها نیز صدق می‌کند.

در مقایسه با حاشیه‌نویسی (annotation) قدیمی [`kubectl.kubernetes.io/last-applied-configuration`](/docs/reference/labels-annotations-taints/#kubectl-kubernetes-io-last-applied-configuration) که `kubectl` آن را مدیریت می‌کند، Server-Side Apply رویکرد اعلانی‌تری دارد و به‌جای آخرین وضعیت اعمال‌شده‌ی کاربر، مدیریت فیلدها توسط کاربر (یا کلاینت) را ردیابی می‌کند. یکی از پیامدهای جانبی استفاده از Server-Side Apply این است که اطلاعات مربوط به اینکه کدام مدیر فیلد هر فیلد از آبجکت را مدیریت می‌کند نیز در دسترس قرار می‌گیرد.

### مثال {#ssa-example-configmap}

یک مثال ساده از آبجکتی که با Server-Side Apply ایجاد شده است می‌تواند به این شکل باشد:

{{< note >}}
دستور `kubectl get` به‌طور پیش‌فرض فیلدهای مدیریت‌شده را نمایش نمی‌دهد.
برای نمایش `managedFields` در حالتی که قالب خروجی `json` یا `yaml` است، `--show-managed-fields` را اضافه کنید.
{{< /note >}}

```yaml
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: test-cm
  namespace: default
  labels:
    test-label: test
  managedFields:
  - manager: kubectl
    operation: Apply # note capitalization: "Apply" (or "Update")
    apiVersion: v1
    time: "2010-10-10T0:00:00Z"
    fieldsType: FieldsV1
    fieldsV1:
      f:metadata:
        f:labels:
          f:test-label: {}
      f:data:
        f:key: {}
data:
  key: some value
```

آبجکت ConfigMap این مثال یک رکورد مدیریت فیلد در `.metadata.managedFields` دارد. این رکورد شامل اطلاعات پایه درباره‌ی خود موجودیت مدیریت‌کننده، به‌علاوه‌ی جزئیات فیلدهای مدیریت‌شده و عملیات مربوط (`Apply` یا `Update`) است. اگر درخواستی که آخرین بار آن فیلد را تغییر داده یک **patch** از نوع Server-Side Apply بوده باشد، مقدار `operation` برابر `Apply` است؛ در غیر این صورت، برابر `Update` است.

نتیجه‌ی ممکن دیگری نیز وجود دارد: کلاینت ممکن است بدنه‌ی درخواست نامعتبری ارسال کند. اگر قصد کاملاً مشخص‌شده به آبجکت معتبری منجر نشود، درخواست با شکست مواجه می‌شود.

با این حال، تغییر `.metadata.managedFields` از طریق یک **update** یا یک عملیات **patch** که از Server-Side Apply استفاده نمی‌کند امکان‌پذیر است. انجام این کار به‌شدت توصیه نمی‌شود، اما ممکن است برای مثال وقتی `.metadata.managedFields` به وضعیتی ناسازگار دچار شده باشد (که در عملیات عادی نباید رخ دهد)، گزینه‌ی معقولی برای امتحان کردن باشد.

قالب `managedFields` در مرجع API کوبرنتیز [شرح داده شده است](/docs/reference/kubernetes-api/common-definitions/object-meta/#System).

{{< caution >}}
فیلد `.metadata.managedFields` را API server مدیریت می‌کند.
باید از به‌روزرسانی دستی آن خودداری کنید.
{{< /caution >}}

### تعارض‌ها

_تعارض_ (conflict) نوع خاصی از خطای وضعیت است که وقتی یک عملیات `Apply` تلاش می‌کند فیلدی را تغییر دهد که مدیر دیگری نیز مدعی مدیریت آن است، رخ می‌دهد. این کار مانع از آن می‌شود که یک اعمال‌کننده ناخواسته مقداری را که کاربر دیگری تنظیم کرده است بازنویسی کند. در این صورت، اعمال‌کننده برای حل تعارض‌ها سه گزینه دارد:

* **بازنویسی مقدار و تبدیل شدن به تنها مدیر:** اگر بازنویسی مقدار عمدی بوده است (یا اگر اعمال‌کننده یک فرایند خودکار مانند یک کنترل‌کننده است)، اعمال‌کننده باید پارامتر کوئری `force` را روی true تنظیم کند (برای `kubectl apply` از پارامتر خط فرمان `--force-conflicts` استفاده می‌کنید) و درخواست را دوباره ارسال کند. این کار عملیات را وادار به موفقیت می‌کند، مقدار فیلد را تغییر می‌دهد و فیلد را از ورودی‌های همه‌ی مدیران دیگر در `managedFields` حذف می‌کند.

* **بازنویسی نکردن مقدار و صرف‌نظر از ادعای مدیریت:** اگر مقدار فیلد دیگر برای اعمال‌کننده اهمیتی ندارد، می‌تواند آن را از مدل محلی خود از منبع حذف کند و درخواست جدیدی بدون آن فیلد ارسال کند. با این کار مقدار بدون تغییر باقی می‌ماند و فیلد از ورودی اعمال‌کننده در `managedFields` حذف می‌شود.

* **بازنویسی نکردن مقدار و تبدیل شدن به مدیر مشترک:** اگر مقدار فیلد همچنان برای اعمال‌کننده مهم است اما نمی‌خواهد آن را بازنویسی کند، می‌تواند مقدار آن فیلد را در مدل محلی خود از منبع طوری تغییر دهد که با مقدار آبجکت روی سرور مطابقت داشته باشد، و سپس درخواست جدیدی ارسال کند که این به‌روزرسانی محلی را در نظر بگیرد. با این کار مقدار بدون تغییر باقی می‌ماند و مدیریت آن فیلد میان اعمال‌کننده و همه‌ی مدیران فیلد دیگری که پیش‌تر مدعی مدیریت آن بوده‌اند به اشتراک گذاشته می‌شود.

### مدیران فیلد {#managers}

مدیران، گردش‌کارهای متمایزی را که آبجکت را تغییر می‌دهند مشخص می‌کنند (که به‌ویژه هنگام بروز تعارض مفید است!) و می‌توان آن‌ها را از طریق پارامتر کوئری [`fieldManager`](/docs/reference/kubernetes-api/common-parameters/common-parameters/#fieldManager) به‌عنوان بخشی از یک درخواست تغییردهنده تعیین کرد. هنگامی که روی یک منبع Apply انجام می‌دهید، پارامتر `fieldManager` الزامی است. برای سایر به‌روزرسانی‌ها، API server هویت مدیر فیلد را از سرآیند HTTP با نام "User-Agent:" (در صورت وجود) استنتاج می‌کند.

وقتی از ابزار `kubectl` برای انجام عملیات Server-Side Apply استفاده می‌کنید، `kubectl` به‌طور پیش‌فرض هویت مدیر را `"kubectl"` تنظیم می‌کند.

## سریال‌سازی

در سطح پروتکل، کوبرنتیز بدنه‌ی پیام‌های Server-Side Apply را به‌صورت [YAML](https://yaml.org/) و با نوع رسانه‌ی `application/apply-patch+yaml` نمایش می‌دهد.

{{< note >}}
چه داده‌ی JSON ارسال کنید و چه داده‌ی YAML، از `application/apply-patch+yaml` به‌عنوان مقدار سرآیند `Content-Type` استفاده کنید.

همه‌ی اسناد JSON، YAML معتبر نیز هستند. با این حال، کوبرنتیز باگی دارد که در آن از تجزیه‌گری برای YAML استفاده می‌کند که مشخصات YAML را به‌طور کامل پیاده‌سازی نمی‌کند. ممکن است برخی از نویسه‌های گریز (escape) در JSON شناسایی نشوند.
{{< /note >}}

سریال‌سازی همانند سریال‌سازی آبجکت‌های کوبرنتیز است، با این تفاوت که کلاینت‌ها ملزم به ارسال آبجکت کامل نیستند.

در ادامه نمونه‌ای از بدنه‌ی پیام Server-Side Apply (قصد کاملاً مشخص‌شده) آمده است:
```yaml
{
  "apiVersion": "v1",
  "kind": "ConfigMap"
}
```

(این پیام، به شرط آنکه به‌عنوان بدنه‌ی یک درخواست **patch** به یک منبع معتبر `v1/configmaps` و با `Content-Type` مناسب ارسال شود، یک به‌روزرسانی بدون تغییر ایجاد می‌کند.)


## عملیات‌هایی که مدیریت فیلدها شامل آن‌ها می‌شود {#apply-and-update}

عملیات‌هایی از API کوبرنتیز که مدیریت فیلدها در آن‌ها لحاظ می‌شود عبارت‌اند از:

1. اعمال سمت سرور (`PATCH` در HTTP با نوع محتوای `application/apply-patch+yaml`)
2. جایگزینی یک آبجکت موجود (**update** در کوبرنتیز؛ `PUT` در سطح HTTP)

هر دو عملیات `.metadata.managedFields` را به‌روزرسانی می‌کنند، اما رفتار کمی متفاوتی دارند.

عملیات apply که با تعارض در سطح فیلد روبه‌رو شود، همیشه با شکست مواجه می‌شود، مگر اینکه بازنویسی اجباری را مشخص کرده باشید. در مقابل، اگر با **update** تغییری ایجاد کنید که بر یک فیلد مدیریت‌شده اثر بگذارد، تعارض هرگز باعث شکست عملیات نمی‌شود.

همه‌ی درخواست‌های **patch** از نوع Server-Side Apply باید با ارائه‌ی پارامتر کوئری `fieldManager` هویت خود را مشخص کنند، در حالی که این پارامتر برای عملیات‌های **update** اختیاری است. در نهایت، هنگام استفاده از عملیات `Apply` نمی‌توانید `managedFields` را در بدنه‌ی درخواستی که ارسال می‌کنید تعریف کنید.

نمونه‌ای از یک آبجکت با چند مدیر می‌تواند به این شکل باشد:

```yaml
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: test-cm
  namespace: default
  labels:
    test-label: test
  managedFields:
  - manager: kubectl
    operation: Apply
    time: '2019-03-30T15:00:00.000Z'
    apiVersion: v1
    fieldsType: FieldsV1
    fieldsV1:
      f:metadata:
        f:labels:
          f:test-label: {}
  - manager: kube-controller-manager
    operation: Update
    apiVersion: v1
    time: '2019-03-30T16:00:00.000Z'
    fieldsType: FieldsV1
    fieldsV1:
      f:data:
        f:key: {}
data:
  key: new value
```

در این مثال، عملیات دوم به‌صورت یک **update** توسط مدیری به نام `kube-controller-manager` اجرا شده است. درخواست به‌روزرسانی موفق بود و مقداری را در فیلد data تغییر داد و همین باعث شد مدیریت آن فیلد به `kube-controller-manager` منتقل شود.

اگر به‌جای آن، این به‌روزرسانی با Server-Side Apply انجام می‌شد، درخواست به دلیل تعارض در مالکیت با شکست مواجه می‌شد.

## راهبرد ادغام

راهبرد ادغامی که با Server-Side Apply پیاده‌سازی شده است، به‌طور کلی چرخه‌ی عمر پایدارتری برای آبجکت فراهم می‌کند. این قابلیت به‌جای چیره شدن بر اساس مقادیر، تلاش می‌کند فیلدها را بر اساس عاملی که آن‌ها را مدیریت می‌کند ادغام کند. به این ترتیب، چند عامل می‌توانند یک آبجکت واحد را بدون ایجاد تداخل غیرمنتظره به‌روزرسانی کنند.

وقتی کاربر یک آبجکت _قصد کاملاً مشخص‌شده_ را به endpoint مربوط به Server-Side Apply ارسال می‌کند، سرور آن را با آبجکت زنده ادغام می‌کند و اگر مقداری در هر دو جا مشخص شده باشد، مقدار موجود در بدنه‌ی درخواست را ترجیح می‌دهد. اگر مجموعه‌ی آیتم‌های موجود در پیکربندی اعمال‌شده ابرمجموعه‌ای از آیتم‌هایی نباشد که همان کاربر دفعه‌ی قبل اعمال کرده بود، هر آیتم غایبی که هیچ اعمال‌کننده‌ی دیگری آن را مدیریت نمی‌کند حذف می‌شود. برای اطلاعات بیشتر درباره‌ی نحوه‌ی استفاده از طرح‌واره‌ی (schema) آبجکت برای تصمیم‌گیری هنگام ادغام، به [sigs.k8s.io/structured-merge-diff](https://sigs.k8s.io/structured-merge-diff) مراجعه کنید.

API کوبرنتیز (و کد Go که این API را برای کوبرنتیز پیاده‌سازی می‌کند) امکان تعریف _نشانگرهای راهبرد ادغام_ (merge strategy markers) را فراهم می‌کند. این نشانگرها راهبرد ادغام پشتیبانی‌شده برای فیلدهای درون آبجکت‌های کوبرنتیز را توصیف می‌کنند. برای یک {{< glossary_tooltip term_id="CustomResourceDefinition" text="CustomResourceDefinition" >}}، می‌توانید این نشانگرها را هنگام تعریف منبع سفارشی تنظیم کنید.

| نشانگر Golang   | افزونه‌ی OpenAPI            | مقادیر ممکن                                  | توضیحات |
| --------------- | ---------------------------- | ------------------------------------------------ | ------- |
| `//+listType`   | `x-kubernetes-list-type`     | `atomic`/`set`/`map`                             | قابل اعمال بر لیست‌ها. مقدار `set` برای لیست‌هایی به کار می‌رود که فقط عناصر اسکالر دارند. این عناصر باید یکتا باشند. مقدار `map` فقط برای لیست‌هایی از انواع تودرتو به کار می‌رود. مقادیر کلید (`listMapKey` را ببینید) باید در لیست یکتا باشند. مقدار `atomic` را می‌توان برای هر لیستی به کار برد. اگر `atomic` پیکربندی شود، کل لیست هنگام ادغام جایگزین می‌شود. در هر لحظه، فقط یک مدیر مالک لیست است. اگر `set` یا `map` باشد، مدیران مختلف می‌توانند ورودی‌ها را جداگانه مدیریت کنند. |
| `//+listMapKey` | `x-kubernetes-list-map-keys` | لیستی از نام فیلدها، مثلاً `["port", "protocol"]` | فقط زمانی قابل اعمال است که `+listType=map` باشد. لیستی از نام فیلدهایی که مقادیرشان ورودی‌های لیست را به‌طور یکتا مشخص می‌کنند. با اینکه ممکن است چند کلید وجود داشته باشد، `listMapKey` مفرد است، زیرا کلیدها باید در نوع Go به‌صورت جداگانه مشخص شوند. فیلدهای کلید باید اسکالر باشند. |
| `//+mapType`    | `x-kubernetes-map-type`      | `atomic`/`granular`                              | قابل اعمال بر mapها. مقدار `atomic` یعنی map فقط می‌تواند به‌طور کامل و توسط یک مدیر واحد جایگزین شود. مقدار `granular` یعنی map از به‌روزرسانی فیلدهای جداگانه توسط مدیران مجزا پشتیبانی می‌کند. |
| `//+structType` | `x-kubernetes-map-type`      | `atomic`/`granular`                              | قابل اعمال بر structها؛ در غیر این صورت، کاربرد و حاشیه‌نویسی OpenAPI آن همانند `//+mapType` است. |

اگر `listType` وجود نداشته باشد، API server نشانگر `patchStrategy=merge` را به‌عنوان `listType=map` و نشانگر `patchMergeKey` متناظر را به‌عنوان `listMapKey` تفسیر می‌کند.

نوع لیست `atomic` بازگشتی است.

(در کد [Go](https://go.dev/) کوبرنتیز، این نشانگرها به‌صورت توضیح (comment) مشخص می‌شوند و نویسندگان کد نیازی ندارند آن‌ها را به‌عنوان برچسب فیلد (field tag) تکرار کنند.)

## منابع سفارشی و Server-Side Apply

به‌طور پیش‌فرض، Server-Side Apply منابع سفارشی را به‌عنوان داده‌ی بدون ساختار در نظر می‌گیرد. با همه‌ی کلیدها همانند فیلدهای struct رفتار می‌شود و همه‌ی لیست‌ها atomic در نظر گرفته می‌شوند.

اگر CustomResourceDefinition یک [طرح‌واره](/docs/reference/generated/kubernetes-api/{{< param "version" >}}#jsonschemaprops-v1-apiextensions-k8s-io) تعریف کند که شامل حاشیه‌نویسی‌هایی باشد که در بخش پیشین [راهبرد ادغام](#merge-strategy) تعریف شدند، این حاشیه‌نویسی‌ها هنگام ادغام آبجکت‌های این نوع به کار می‌روند.


### سازگاری در برابر تغییرات توپولوژی

در موارد نادر، نویسنده‌ی یک CustomResourceDefinition (CRD) یا یک منبع داخلی ممکن است بخواهد توپولوژی مشخص یک فیلد را در منبع خود تغییر دهد، بدون آنکه نسخه‌ی API آن را افزایش دهد. تغییر توپولوژی انواع، چه با ارتقای کلاستر و چه با به‌روزرسانی CRD، هنگام به‌روزرسانی آبجکت‌های موجود پیامدهای متفاوتی دارد. این تغییرات دو دسته‌اند: حالتی که فیلد از `map`/`set`/`granular` به `atomic` تغییر می‌کند، و حالت عکس آن.

وقتی `listType`، `mapType` یا `structType` از `map`/`set`/`granular` به `atomic` تغییر کند، کل لیست، map یا struct آبجکت‌های موجود در نهایت به مالکیت عامل‌هایی درمی‌آید که مالک عنصری از این انواع بوده‌اند. این یعنی هر تغییر بعدی در این آبجکت‌ها به تعارض منجر می‌شود.

وقتی `listType`، `mapType` یا `structType` از `atomic` به `map`/`set`/`granular` تغییر کند، API server نمی‌تواند مالکیت جدید این فیلدها را استنتاج کند. به همین دلیل، هنگام به‌روزرسانی این فیلدها در آبجکت‌ها هیچ تعارضی ایجاد نمی‌شود. از این رو، تغییر یک نوع از `atomic` به `map`/`set`/`granular` توصیه نمی‌شود.

برای مثال، این منبع سفارشی را در نظر بگیرید:

```yaml
---
apiVersion: example.com/v1
kind: Foo
metadata:
  name: foo-sample
  managedFields:
  - manager: "manager-one"
    operation: Apply
    apiVersion: example.com/v1
    fieldsType: FieldsV1
    fieldsV1:
      f:spec:
        f:data: {}
spec:
  data:
    key1: val1
    key2: val2
```

پیش از آنکه `spec.data` از `atomic` به `granular` تغییر کند، `manager-one` مالک فیلد `spec.data` و همه‌ی فیلدهای درون آن (`key1` و `key2`) است. وقتی CRD طوری تغییر کند که `spec.data` به `granular` تبدیل شود، `manager-one` همچنان مالک فیلد سطح بالای `spec.data` باقی می‌ماند (یعنی هیچ مدیر دیگری نمی‌تواند map به نام `data` را بدون تعارض حذف کند)، اما دیگر مالک `key1` و `key2` نیست؛ بنابراین مدیر دیگری می‌تواند این فیلدها را بدون تعارض تغییر دهد یا حذف کند.

## استفاده از اعمال سمت سرور در یک کنترل‌کننده

اگر توسعه‌دهندهٔ یک کنترل‌کننده هستید، می‌توانید از اعمال سمت سرور (Server-Side Apply) برای ساده‌کردن منطق به‌روزرسانی کنترل‌کنندهٔ خود استفاده کنید. تفاوت‌های اصلی این روش با الگوی «خواندن-تغییر-نوشتن» (read-modify-write) و/یا وصله (patch) به شرح زیر است:

* آبجکت اعمال‌شده باید همهٔ فیلدهایی را که برای کنترل‌کننده اهمیت دارند در بر داشته باشد.
* هیچ راهی برای حذف فیلدهایی که کنترل‌کننده پیش‌تر آن‌ها را اعمال نکرده است وجود ندارد (کنترل‌کننده همچنان می‌تواند برای این موارد یک **patch** یا **update** ارسال کند).
* لازم نیست آبجکت از قبل خوانده شود و نیازی به تعیین `resourceVersion` نیست.

اکیداً توصیه می‌شود کنترل‌کننده‌ها همیشه روی آبجکت‌هایی که مالک و مدیر آن‌ها هستند تعارض‌ها را به‌اجبار (force) نادیده بگیرند، زیرا ممکن است نتوانند این تعارض‌ها را حل کنند یا بر اساس آن‌ها اقدامی انجام دهند.

## انتقال مالکیت

اعمال سمت سرور علاوه بر کنترل‌های هم‌روندی که از طریق [حل تعارض](#conflicts) فراهم می‌شود، روش‌هایی برای انتقال هماهنگ مالکیت فیلدها از کاربران به کنترل‌کننده‌ها نیز ارائه می‌دهد.

این موضوع با یک مثال بهتر توضیح داده می‌شود. در ادامه می‌بینیم که چگونه می‌توان هنگام فعال‌کردن مقیاس‌پذیری افقی خودکار برای یک Deployment، با استفاده از منبع HorizontalPodAutoscaler و کنترل‌کنندهٔ همراه آن، مالکیت فیلد `replicas` را به‌طور ایمن از یک کاربر به یک کنترل‌کننده منتقل کرد.

فرض کنید کاربری یک Deployment تعریف کرده و مقدار `replicas` را روی مقدار دلخواه تنظیم کرده است:

{{% code_sample file="application/ssa/nginx-deployment.yaml" %}}

و کاربر این Deployment را با اعمال سمت سرور، به شکل زیر ایجاد کرده است:

```shell
kubectl apply -f https://k8s.io/examples/application/ssa/nginx-deployment.yaml --server-side
```

سپس در زمانی دیگر، مقیاس‌پذیری خودکار برای این Deployment فعال می‌شود؛ برای مثال:

```shell
kubectl autoscale deployment nginx-deployment --cpu=50% --min=1 --max=10
```

اکنون کاربر می‌خواهد `replicas` را از پیکربندی خود حذف کند تا به‌طور ناخواسته با HorizontalPodAutoscaler (HPA) و کنترل‌کنندهٔ آن درگیر نشود. اما در این میان یک وضعیت رقابتی (race) وجود دارد: ممکن است مدتی طول بکشد تا HPA نیاز به تنظیم `.spec.replicas` را تشخیص دهد. اگر کاربر `.spec.replicas` را پیش از آنکه HPA در این فیلد بنویسد و مالک آن شود حذف کند، سرور API مقدار `.spec.replicas` را روی ۱ (تعداد پیش‌فرض رپلیکا برای Deployment) تنظیم می‌کند. کاربر چنین چیزی را، حتی به‌طور موقت، نمی‌خواهد؛ زیرا این وضعیت ممکن است کارایی یک بار کاری در حال اجرا را به‌شدت کاهش دهد.

دو راه‌حل وجود دارد:

- (ساده) فیلد `replicas` را در پیکربندی نگه دارید. هنگامی که HPA سرانجام در این فیلد بنویسد، سیستم برای این فیلد به کاربر تعارض اعلام می‌کند. در این مرحله، حذف آن از پیکربندی ایمن است.

- (پیشرفته‌تر) اما اگر کاربر نخواهد منتظر بماند، برای مثال به این دلیل که می‌خواهد کلاستر برای همکارانش خوانا و قابل‌فهم بماند، می‌تواند گام‌های زیر را انجام دهد تا حذف `replicas` از پیکربندی‌اش ایمن شود:

ابتدا کاربر یک مانیفست جدید تعریف می‌کند که تنها شامل فیلد `replicas` است:

```yaml
# Save this file as 'nginx-deployment-replicas-only.yaml'.
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
spec:
  replicas: 3
```

{{< note >}}
در این حالت، فایل YAML مربوط به اعمال سمت سرور تنها فیلدهایی را در بر دارد که می‌خواهید تغییر دهید. اگر فقط می‌خواهید فیلد `spec.replicas` را با اعمال سمت سرور تغییر دهید، لازم نیست یک مانیفست کامل و معتبر برای Deployment ارائه کنید.
{{< /note >}}

کاربر این مانیفست را با یک نام اختصاصی برای مدیر فیلد (field manager) اعمال می‌کند. در این مثال، کاربر نام `handover-to-hpa` را انتخاب کرده است:

```shell
kubectl apply -f nginx-deployment-replicas-only.yaml \
  --server-side --field-manager=handover-to-hpa \
  --validate=false
```

اگر این اعمال به تعارض با کنترل‌کنندهٔ HPA منجر شد، کاری انجام ندهید. این تعارض نشان می‌دهد که کنترل‌کننده زودتر از آنچه گاهی رخ می‌دهد، مالکیت فیلد را در اختیار گرفته است.

در این مرحله، کاربر می‌تواند فیلد `replicas` را از مانیفست خود حذف کند:

{{% code_sample file="application/ssa/nginx-deployment-no-replicas.yaml" %}}

توجه کنید که هر زمان کنترل‌کنندهٔ HPA مقدار جدیدی برای فیلد `replicas` تنظیم کند، مدیر فیلد موقت دیگر مالک هیچ فیلدی نخواهد بود و به‌طور خودکار حذف می‌شود. هیچ پاک‌سازی دیگری لازم نیست.

### انتقال مالکیت بین مدیرها

مدیرهای فیلد می‌توانند مالکیت یک فیلد را میان یکدیگر منتقل کنند؛ به این صورت که هر دو، آن فیلد را در پیکربندی‌های اعمال‌شدهٔ خود روی مقدار یکسانی تنظیم کنند تا مالکیت فیلد میان آن‌ها مشترک شود. پس از آنکه مالکیت فیلد مشترک شد، یکی از مدیرها می‌تواند فیلد را از پیکربندی اعمال‌شدهٔ خود حذف کند تا از مالکیت آن صرف‌نظر کند و انتقال به مدیر فیلد دیگر کامل شود.

## مقایسه با اعمال سمت کلاینت

اعمال سمت سرور هم به‌عنوان جایگزینی برای پیاده‌سازی اولیهٔ سمت کلاینت زیرفرمان `kubectl apply` طراحی شده است و هم به‌عنوان سازوکاری ساده و کارآمد برای {{< glossary_tooltip term_id="controller" text="کنترل‌کننده‌ها" >}} تا تغییرات خود را اعمال کنند.

در مقایسه با حاشیه‌نویسی (annotation) `last-applied` که `kubectl` آن را مدیریت می‌کند، اعمال سمت سرور رویکرد اعلانی‌تری دارد و به‌جای آخرین وضعیت اعمال‌شدهٔ کاربر، مدیریت فیلدهای آبجکت را ردیابی می‌کند. در نتیجه، یکی از پیامدهای جانبی استفاده از اعمال سمت سرور این است که اطلاعات مربوط به اینکه هر فیلد آبجکت را کدام مدیر فیلد مدیریت می‌کند نیز در دسترس قرار می‌گیرد.

یکی از پیامدهای تشخیص و حل تعارض در اعمال سمت سرور این است که اعمال‌کننده همیشه مقادیر به‌روز فیلدها را در وضعیت محلی خود دارد. اگر چنین نباشد، دفعهٔ بعد که اعمال کند با تعارض روبه‌رو می‌شود. هر یک از سه گزینهٔ حل تعارض باعث می‌شود پیکربندی اعمال‌شده زیرمجموعه‌ای به‌روز از فیلدهای آبجکت روی سرور باشد.

این رفتار با اعمال سمت کلاینت متفاوت است؛ در آن روش، مقادیر قدیمی که کاربران دیگر آن‌ها را بازنویسی کرده‌اند در پیکربندی محلی اعمال‌کننده باقی می‌مانند. این مقادیر تنها زمانی درست می‌شوند که کاربر همان فیلد خاص را به‌روزرسانی کند (اگر اصلاً چنین کند) و اعمال‌کننده هیچ راهی ندارد تا بداند آیا اعمال بعدی‌اش تغییرات کاربران دیگر را بازنویسی خواهد کرد یا نه.

تفاوت دیگر این است که اعمال‌کننده‌ای که از اعمال سمت کلاینت استفاده می‌کند نمی‌تواند نسخهٔ API مورد استفادهٔ خود را تغییر دهد، اما اعمال سمت سرور از این مورد پشتیبانی می‌کند.

## مهاجرت بین اعمال سمت کلاینت و اعمال سمت سرور

### ارتقا از اعمال سمت کلاینت به اعمال سمت سرور

کاربرانی که از اعمال سمت کلاینت استفاده می‌کنند و منبعی را با `kubectl apply` مدیریت می‌کنند، می‌توانند با فلگ زیر استفاده از اعمال سمت سرور را آغاز کنند.

```shell
kubectl apply --server-side [--dry-run=server]
```

به‌طور پیش‌فرض، مدیریت فیلدهای آبجکت بدون بروز تعارض از اعمال سمت کلاینت به اعمال سمت سرور kubectl منتقل می‌شود.

{{< caution >}}
حاشیه‌نویسی `last-applied-configuration` را به‌روز نگه دارید. فیلدهای مدیریت‌شده توسط اعمال سمت کلاینت از روی این حاشیه‌نویسی استنباط می‌شوند. هر فیلدی که اعمال سمت کلاینت آن را مدیریت نکند، باعث بروز تعارض می‌شود.

برای مثال، اگر پس از اعمال سمت کلاینت از `kubectl scale` برای به‌روزرسانی فیلد replicas استفاده کرده باشید، مالک این فیلد اعمال سمت کلاینت نیست و هنگام اجرای `kubectl apply --server-side` تعارض ایجاد می‌کند.
{{< /caution >}}

این رفتار در مورد اعمال سمت سرور با مدیر فیلد `kubectl` صدق می‌کند. به‌عنوان یک استثنا، می‌توانید با تعیین یک مدیر فیلد دیگر و غیرپیش‌فرض، مانند مثال زیر، از این رفتار صرف‌نظر کنید. مدیر فیلد پیش‌فرض برای اعمال سمت سرور در kubectl، `kubectl` است.

```shell
kubectl apply --server-side --field-manager=my-manager [--dry-run=server]
```

### بازگشت از اعمال سمت سرور به اعمال سمت کلاینت

اگر منبعی را با `kubectl apply --server-side` مدیریت می‌کنید، می‌توانید مستقیماً با `kubectl apply` به اعمال سمت کلاینت بازگردید.

این بازگشت ممکن است، زیرا اگر از `kubectl apply` استفاده کنید، اعمال سمت سرور در kubectl حاشیه‌نویسی `last-applied-configuration` را به‌روز نگه می‌دارد.

این رفتار در مورد اعمال سمت سرور با مدیر فیلد `kubectl` صدق می‌کند. به‌عنوان یک استثنا، می‌توانید با تعیین یک مدیر فیلد دیگر و غیرپیش‌فرض، مانند مثال زیر، از این رفتار صرف‌نظر کنید. مدیر فیلد پیش‌فرض برای اعمال سمت سرور در kubectl، `kubectl` است.

```shell
kubectl apply --server-side --field-manager=my-manager [--dry-run=server]
```

## پیاده‌سازی API

فعل `PATCH` (برای آبجکتی که از اعمال سمت سرور پشتیبانی می‌کند) نوع محتوای غیررسمی `application/apply-patch+yaml` را می‌پذیرد. کاربران اعمال سمت سرور می‌توانند آبجکت‌هایی را که به‌طور ناقص مشخص شده‌اند، به‌صورت YAML در بدنهٔ یک درخواست `PATCH` به URI یک منبع ارسال کنند. هنگام اعمال یک پیکربندی، همیشه باید همهٔ فیلدهایی را که برای نتیجهٔ مورد نظرتان (مانند وضعیت مطلوب) اهمیت دارند در آن بگنجانید.

همهٔ پیام‌های JSON، YAML معتبر نیز هستند. بنابراین علاوه بر بدنه‌های درخواست YAML، می‌توانید برای درخواست‌های اعمال سمت سرور از بدنه‌های درخواست JSON نیز استفاده کنید، زیرا آن‌ها هم YAML معتبر به شمار می‌آیند. در هر دو حالت، برای درخواست HTTP از نوع رسانهٔ `application/apply-patch+yaml` استفاده کنید.

### کنترل دسترسی و مجوزها {#rbac-and-permissions}

از آنجا که اعمال سمت سرور نوعی `PATCH` است، یک موجودیت امنیتی (principal)، مانند یک Role در {{< glossary_tooltip text="RBAC" term_id="rbac" >}} کوبرنتیز، برای ویرایش منابع موجود به مجوز **patch** نیاز دارد و برای ایجاد منابع جدید با اعمال سمت سرور نیز به مجوز فعل **create** نیازمند است.

## پاک‌کردن `managedFields`

می‌توان همهٔ `managedFields` را از یک آبجکت حذف کرد؛ به این صورت که آن‌ها را با یک **patch** (JSON Merge Patch، Strategic Merge Patch یا JSON Patch) یا از طریق یک **update** (HTTP `PUT`) بازنویسی کنید؛ به بیان دیگر، با هر عملیات نوشتنی به‌جز **apply**. این کار با بازنویسی فیلد `managedFields` با یک ورودی خالی انجام می‌شود. دو مثال در ادامه آمده است:

```console
PATCH /api/v1/namespaces/default/configmaps/example-cm
Accept: application/json
Content-Type: application/merge-patch+json

{
  "metadata": {
    "managedFields": [
      {}
    ]
  }
}
```

```console
PATCH /api/v1/namespaces/default/configmaps/example-cm
Accept: application/json
Content-Type: application/json-patch+json
If-Match: 1234567890123456789

[{"op": "replace", "path": "/metadata/managedFields", "value": [{}]}]
```

این کار `managedFields` را با فهرستی شامل تنها یک ورودی خالی بازنویسی می‌کند و در نتیجه `managedFields` به‌طور کامل از آبجکت حذف می‌شود. توجه کنید که تنظیم `managedFields` روی یک فهرست خالی، این فیلد را بازنشانی نمی‌کند. این رفتار عمدی است تا کلاینت‌هایی که از وجود این فیلد آگاه نیستند هرگز `managedFields` را حذف نکنند.

در مواردی که عملیات بازنشانی با تغییر فیلدهایی غیر از `managedFields` همراه باشد، ابتدا `managedFields` بازنشانی می‌شود و سپس تغییرات دیگر پردازش می‌شوند. در نتیجه، اعمال‌کننده مالکیت همهٔ فیلدهایی را که در همان درخواست به‌روزرسانی شده‌اند به دست می‌گیرد.

{{< note >}}
اعمال سمت سرور مالکیت را در زیرمنبع‌هایی که نوع آبجکت منبع را دریافت نمی‌کنند به‌درستی ردیابی نمی‌کند. اگر از اعمال سمت سرور با چنین زیرمنبعی استفاده می‌کنید، ممکن است فیلدهای تغییریافته ردیابی نشوند.
{{< /note >}}
