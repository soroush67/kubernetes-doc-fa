توکن‌های راه‌اندازی اولیه (Bootstrap tokens) نوعی توکن حامل (bearer token) ساده هستند که برای ایجاد کلاسترهای جدید یا افزودن نودهای جدید به یک کلاستر موجود طراحی شده‌اند. این توکن‌ها برای پشتیبانی از [kubeadm](/docs/reference/setup-tools/kubeadm/) ساخته شده‌اند، اما کاربرانی که می‌خواهند کلاسترها را بدون `kubeadm` راه‌اندازی کنند نیز می‌توانند در زمینه‌های دیگر از آن‌ها استفاده کنند. همچنین این توکن‌ها طوری ساخته شده‌اند که از طریق سیاست RBAC با سامانهٔ [راه‌اندازی اولیهٔ TLS در kubelet](/docs/reference/access-authn-authz/kubelet-tls-bootstrapping/) کار کنند.


<!-- body -->
## مروری بر توکن‌های راه‌اندازی اولیه

توکن‌های راه‌اندازی اولیه با نوع خاصی از Secretها (`bootstrap.kubernetes.io/token`) تعریف می‌شوند که در فضای نام (namespace) `kube-system` قرار دارند. سپس احرازکنندهٔ هویت راه‌اندازی اولیه (Bootstrap Authenticator) در API Server این Secretها را می‌خواند. کنترل‌کنندهٔ TokenCleaner در Controller Manager توکن‌های منقضی‌شده را حذف می‌کند. علاوه بر این، از طریق کنترل‌کنندهٔ BootstrapSigner از این توکن‌ها برای ایجاد امضا برای ConfigMap خاصی استفاده می‌شود که در فرایند «کشف» (discovery) به کار می‌رود.

## قالب توکن

توکن‌های راه‌اندازی اولیه به شکل `abcdef.0123456789abcdef` هستند. به بیان دقیق‌تر، این توکن‌ها باید با عبارت باقاعدهٔ `[a-z0-9]{6}\.[a-z0-9]{16}` مطابقت داشته باشند.

بخش اول توکن «شناسهٔ توکن» (Token ID) است و اطلاعات عمومی به شمار می‌رود. از این بخش هنگام ارجاع به یک توکن استفاده می‌شود تا بخش محرمانه‌ای که برای احراز هویت به کار می‌رود فاش نشود. بخش دوم «رمز توکن» (Token Secret) است و فقط باید با طرف‌های مورد اعتماد به اشتراک گذاشته شود.

## فعال‌سازی احراز هویت با توکن راه‌اندازی اولیه

احرازکنندهٔ هویت توکن راه‌اندازی اولیه را می‌توان با فلگ زیر روی API server فعال کرد:

```
--enable-bootstrap-token-auth
```

پس از فعال‌سازی، می‌توان از توکن‌های راه‌اندازی اولیه به‌عنوان اعتبارنامهٔ توکن حامل برای احراز هویت درخواست‌ها به API server استفاده کرد.

```http
Authorization: Bearer 07401b.f395accd246ae52d
```

این توکن‌ها با نام کاربری `system:bootstrap:<token id>` احراز هویت می‌شوند و عضو گروه `system:bootstrappers` هستند. 
گروه‌های بیشتری را می‌توان در Secret مربوط به توکن مشخص کرد.

با فعال‌کردن کنترل‌کنندهٔ `tokencleaner` در controller manager، توکن‌های منقضی‌شده به‌طور خودکار حذف می‌شوند.

```
--controllers=*,tokencleaner
```

## قالب Secret توکن راه‌اندازی اولیه

پشتوانهٔ هر توکن معتبر یک Secret در فضای نام `kube-system` است. سند طراحی کامل را می‌توانید [اینجا](https://git.k8s.io/design-proposals-archive/cluster-lifecycle/bootstrap-discovery.md) بیابید.

ظاهر این Secret به شکل زیر است.

```yaml
apiVersion: v1
kind: Secret
metadata:
  # Name MUST be of form "bootstrap-token-<token id>"
  name: bootstrap-token-07401b
  namespace: kube-system

# Type MUST be 'bootstrap.kubernetes.io/token'
type: bootstrap.kubernetes.io/token
stringData:
  # Human readable description. Optional.
  description: "The default bootstrap token generated by 'kubeadm init'."

  # Token ID and secret. Required.
  token-id: 07401b
  token-secret: f395accd246ae52d

  # Expiration. Optional.
  expiration: 2017-03-10T03:22:11Z

  # Allowed usages.
  usage-bootstrap-authentication: "true"
  usage-bootstrap-signing: "true"

  # Extra groups to authenticate the token as. Must start with "system:bootstrappers:"
  auth-extra-groups: system:bootstrappers:worker,system:bootstrappers:ingress
```

نوع این Secret باید `bootstrap.kubernetes.io/token` و نام آن باید `bootstrap-token-<token id>` باشد. همچنین این Secret باید در فضای نام `kube-system` وجود داشته باشد.

اعضای `usage-bootstrap-*` نشان می‌دهند که این Secret برای چه کاربردی در نظر گرفته شده است. برای فعال‌شدن هر کاربرد، مقدار آن باید `true` باشد.

* عضو `usage-bootstrap-authentication` نشان می‌دهد که می‌توان از توکن به‌عنوان توکن حامل برای احراز هویت در API server استفاده کرد.
* عضو `usage-bootstrap-signing` نشان می‌دهد که می‌توان از توکن برای امضای ConfigMap با نام `cluster-info` استفاده کرد؛ این موضوع در ادامه شرح داده شده است.

فیلد `expiration` زمان انقضای توکن را تعیین می‌کند. توکن‌های منقضی‌شده هنگام استفاده برای احراز هویت رد می‌شوند و در امضای ConfigMap نادیده گرفته می‌شوند. مقدار انقضا به‌صورت یک زمان مطلق UTC با قالب [RFC3339](https://datatracker.ietf.org/doc/html/rfc3339) کدگذاری می‌شود. برای حذف خودکار توکن‌های منقضی‌شده، کنترل‌کنندهٔ `tokencleaner` را فعال کنید.

## مدیریت توکن با kubeadm

با ابزار `kubeadm` می‌توانید توکن‌ها را در یک کلاستر در حال اجرا مدیریت کنید. برای جزئیات بیشتر، [مستندات توکن kubeadm](/docs/reference/setup-tools/kubeadm/kubeadm-token/) را ببینید.

## امضای ConfigMap

علاوه بر احراز هویت، می‌توان از توکن‌ها برای امضای یک ConfigMap نیز استفاده کرد. این کار در مراحل ابتدایی فرایند راه‌اندازی اولیهٔ کلاستر و پیش از آنکه کلاینت به API server اعتماد کند انجام می‌شود. ConfigMap امضاشده را می‌توان با توکن مشترک احراز اصالت کرد.

برای فعال‌سازی امضای ConfigMap، کنترل‌کنندهٔ `bootstrapsigner` را در Controller Manager فعال کنید.

```
--controllers=*,bootstrapsigner
```

ConfigMap امضاشده `cluster-info` در فضای نام `kube-public` است. روند معمول این است که کلاینت این ConfigMap را بدون احراز هویت و با نادیده‌گرفتن خطاهای TLS می‌خواند. سپس با بررسی امضای جاسازی‌شده در ConfigMap، محتوای آن را اعتبارسنجی می‌کند.

این ConfigMap ممکن است به شکل زیر باشد:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-info
  namespace: kube-public
data:
  jws-kubeconfig-07401b: eyJhbGciOiJIUzI1NiIsImtpZCI6IjA3NDAxYiJ9..tYEfbo6zDNo40MQE07aZcQX2m3EB2rO3NuXtxVMYm9U
  kubeconfig: |
    apiVersion: v1
    clusters:
    - cluster:
        certificate-authority-data: <really long certificate data>
        server: https://10.138.0.2:6443
      name: ""
    contexts: []
    current-context: ""
    kind: Config
    preferences: {}
    users: []
```

عضو `kubeconfig` در این ConfigMap یک فایل پیکربندی است که فقط اطلاعات کلاستر در آن پر شده است. مهم‌ترین اطلاعاتی که در اینجا منتقل می‌شود `certificate-authority-data` است. ممکن است این اطلاعات در آینده گسترش یابد.

این امضا یک امضای JWS در حالت «جدا» (detached) است. برای اعتبارسنجی امضا، کاربر باید محتوای `kubeconfig` را طبق قواعد JWS کدگذاری کند (یعنی با base64 کدگذاری کند و هر `=` انتهایی را حذف کند). سپس این محتوای کدگذاری‌شده بین دو نقطه قرار می‌گیرد تا یک JWS کامل ساخته شود. می‌توانید این JWS را با طرح `HS256` (HMAC-SHA256) و با استفاده از بخش رمز توکن (برای مثال `f395accd246ae52d`) به‌عنوان رمز مشترک تأیید کنید. کاربران _باید_ اطمینان حاصل کنند که از HS256 استفاده شده است. از آنجا که رمز فقط ۱۶ بایت است، ممکن است لازم باشد برای پذیرفته‌شدن آن در برخی ابزارهای اعتبارسنجی، سمت راست آن را با صفر پر کنید.

{{< warning >}}
هر کسی که یک توکن راه‌اندازی اولیه در اختیار داشته باشد، می‌تواند برای آن توکن امضای معتبر ایجاد کند. هنگام استفاده از امضای ConfigMap، به اشتراک‌گذاشتن یک توکن با کلاینت‌های متعدد توصیه نمی‌شود؛ زیرا یک کلاینت به‌خطرافتاده ممکن است بتواند علیه کلاینت دیگری که برای راه‌اندازی اولیهٔ اعتماد TLS به این امضا متکی است، حملهٔ مرد میانی (man-in-the-middle) انجام دهد.
{{< /warning >}}

برای اطلاعات بیشتر، بخش [جزئیات پیاده‌سازی kubeadm](/docs/reference/setup-tools/kubeadm/implementation-details/) را ببینید.
