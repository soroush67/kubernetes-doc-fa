این صفحه مروری بر مراحلی ارائه می‌دهد که برای ارتقای یک کلاستر کوبرنتیز باید دنبال کنید.

پروژه کوبرنتیز توصیه می‌کند که بی‌درنگ به آخرین نسخه‌های وصله‌ای (patch release) ارتقا دهید و اطمینان حاصل کنید که یک نسخه فرعی (minor release) پشتیبانی‌شده از کوبرنتیز را اجرا می‌کنید. پیروی از این توصیه به حفظ امنیت شما کمک می‌کند.

شیوه ارتقای یک کلاستر به این بستگی دارد که آن را در ابتدا چگونه مستقر کرده‌اید و پس از آن چه تغییراتی در آن داده‌اید.

در سطح کلی، مراحلی که انجام می‌دهید عبارت‌اند از:

- ارتقای {{< glossary_tooltip text="control plane" term_id="control-plane" >}}
- ارتقای نودهای کلاستر
- ارتقای کلاینت‌هایی مانند {{< glossary_tooltip text="kubectl" term_id="kubectl" >}}
- تنظیم مانیفست‌ها و دیگر منابع بر اساس تغییرات API که همراه با نسخه جدید کوبرنتیز ارائه می‌شوند

## {{% heading "prerequisites" %}}

باید یک کلاستر موجود داشته باشید. این صفحه درباره ارتقا از کوبرنتیز {{< skew currentVersionAddMinor -1 >}} به کوبرنتیز {{< skew currentVersion >}} است. اگر کلاستر شما در حال حاضر کوبرنتیز {{< skew currentVersionAddMinor -1 >}} را اجرا نمی‌کند، لطفاً مستندات نسخه‌ای از کوبرنتیز را که قصد ارتقا به آن را دارید بررسی کنید.

{{< note >}}
در نودهای لینوکسی، kubelet به‌طور پیش‌فرض فقط از cgroups v2 پشتیبانی می‌کند.
در کوبرنتیز {{< skew currentVersion >}}، گزینه پیکربندی `FailCgroupV1` در kubelet به‌طور پیش‌فرض روی `true` تنظیم شده است.

برای اطلاعات بیشتر، به [مستندات منسوخ‌شدن cgroup v1 در کوبرنتیز](/docs/concepts/architecture/cgroups/#deprecation-of-cgroup-v1) مراجعه کنید.
{{</ note >}}

## رویکردهای ارتقا

### kubeadm {#upgrade-kubeadm}

اگر کلاستر شما با ابزار `kubeadm` مستقر شده است، برای اطلاعات دقیق درباره نحوه ارتقای کلاستر به [ارتقای کلاسترهای kubeadm](/docs/tasks/administer-cluster/kubeadm/kubeadm-upgrade/) مراجعه کنید.

پس از ارتقای کلاستر، فراموش نکنید که [آخرین نسخه `kubectl` را نصب کنید](/docs/tasks/tools/).

### استقرارهای دستی

{{< caution >}}
این مراحل، افزونه‌های شخص ثالث مانند پلاگین‌های شبکه و ذخیره‌سازی را در نظر نمی‌گیرند.
{{< /caution >}}

باید control plane را به‌صورت دستی و به ترتیب زیر به‌روزرسانی کنید:

- etcd (همه نمونه‌ها)
- kube-apiserver (همه میزبان‌های control plane)
- kube-controller-manager
- kube-scheduler
- cloud controller manager، در صورتی که از آن استفاده می‌کنید

در این مرحله باید [آخرین نسخه `kubectl` را نصب کنید](/docs/tasks/tools/).

برای هر نود در کلاستر، ابتدا آن نود را [تخلیه (drain) کنید](/docs/tasks/administer-cluster/safely-drain-node/) و سپس یا آن را با نود جدیدی که از kubelet نسخه {{< skew currentVersion >}} استفاده می‌کند جایگزین کنید، یا kubelet آن نود را ارتقا دهید و نود را دوباره به چرخه خدمت بازگردانید.

{{< caution >}}
تخلیه نودها پیش از ارتقای kubelet تضمین می‌کند که پادها دوباره پذیرفته شوند و کانتینرها از نو ساخته شوند. این کار ممکن است برای رفع برخی مشکلات امنیتی یا دیگر باگ‌های مهم ضروری باشد.
{{</ caution >}}

### سایر استقرارها {#upgrade-other}

برای آشنایی با مراحل توصیه‌شده برای نگهداری، به مستندات ابزار استقرار کلاستر خود مراجعه کنید.

## کارهای پس از ارتقا

### تغییر نسخه API ذخیره‌سازی کلاستر

آبجکت‌هایی که برای بازنمایی داخلی منابع فعال کوبرنتیز در کلاستر، به‌صورت سریال‌شده در etcd ذخیره می‌شوند، با نسخه مشخصی از API نوشته می‌شوند.

هنگامی که API پشتیبانی‌شده تغییر می‌کند، ممکن است لازم باشد این آبجکت‌ها با API جدیدتر بازنویسی شوند. اگر این کار را انجام ندهید، سرانجام منابعی خواهید داشت که سرور API کوبرنتیز دیگر نمی‌تواند آن‌ها را رمزگشایی یا استفاده کند.

هر آبجکت تحت تأثیر را با استفاده از آخرین API پشتیبانی‌شده دریافت کنید و سپس آن را دوباره با همان آخرین API پشتیبانی‌شده بنویسید.

### به‌روزرسانی مانیفست‌ها

ارتقا به نسخه جدید کوبرنتیز ممکن است APIهای جدیدی را در اختیار شما قرار دهد.

می‌توانید با دستور `kubectl convert` مانیفست‌ها را بین نسخه‌های مختلف API تبدیل کنید.
برای مثال:

```shell
kubectl convert -f pod.yaml --output-version v1
```

ابزار `kubectl` محتوای `pod.yaml` را با مانیفستی جایگزین می‌کند که در آن `kind` همچنان روی Pod تنظیم شده است (بدون تغییر)، اما `apiVersion` آن بازبینی شده است.

### پلاگین‌های دستگاه

اگر در کلاستر شما پلاگین‌های دستگاه (device plugin) اجرا می‌شوند و نود باید به نسخه‌ای از کوبرنتیز ارتقا یابد که نسخه جدیدتری از API پلاگین دستگاه دارد، باید پیش از ارتقای نود، پلاگین‌های دستگاه را طوری ارتقا دهید که از هر دو نسخه پشتیبانی کنند. به این ترتیب تضمین می‌شود که تخصیص دستگاه‌ها در طول ارتقا همچنان با موفقیت انجام شود.

برای جزئیات بیشتر، به [سازگاری API](/docs/concepts/extend-kubernetes/compute-storage-net/device-plugins/#api-compatibility) و [نسخه‌های API مدیر دستگاه kubelet](/docs/reference/node/device-plugin-api-versions/) مراجعه کنید.
