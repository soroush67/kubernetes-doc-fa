## {{% heading "prerequisites" %}}

پیش از آنکه مراحل این صفحه را برای استقرار، مدیریت، پشتیبان‌گیری یا بازیابی etcd دنبال کنید،
باید با انتظارات معمول از بهره‌برداری یک کلاستر etcd آشنا باشید.
برای اطلاعات بیشتر به [مستندات etcd](https://etcd.io/docs/) مراجعه کنید.

نکات کلیدی عبارت‌اند از:

* حداقل نسخه‌های توصیه‌شده etcd برای اجرا در محیط عملیاتی (production)، `3.4.29+` و `3.5.11+` هستند.

* سامانه etcd یک سامانه توزیع‌شده مبتنی بر رهبر (leader-based) است. اطمینان حاصل کنید که رهبر
  به‌طور دوره‌ای و به‌موقع ضربان (heartbeat) را برای همه پیروان ارسال می‌کند تا کلاستر
  پایدار بماند.

* باید etcd را به‌صورت کلاستری با تعداد فردی عضو اجرا کنید.

* تا جای ممکن اطمینان حاصل کنید که هیچ کمبود منبعی (resource starvation) رخ نمی‌دهد.

  کارایی و پایداری کلاستر به ورودی/خروجی شبکه و دیسک حساس است. هرگونه کمبود منبع
  می‌تواند به پایان مهلت ضربان (heartbeat timeout) بینجامد و کلاستر را ناپایدار کند.
  ناپایدار بودن etcd به این معناست که هیچ رهبری انتخاب نشده است. در چنین شرایطی،
  کلاستر نمی‌تواند هیچ تغییری در وضعیت فعلی خود ایجاد کند؛ یعنی هیچ پاد جدیدی
  زمان‌بندی نمی‌شود.

### نیازمندی‌های منابع برای etcd

اجرای etcd با منابع محدود فقط برای اهداف آزمایشی مناسب است.
برای استقرار در محیط عملیاتی، پیکربندی سخت‌افزاری پیشرفته لازم است.
پیش از استقرار etcd در محیط عملیاتی،
[مرجع نیازمندی‌های منابع](https://etcd.io/docs/current/op-guide/hardware/#example-hardware-configurations) را ببینید.

پایدار نگه‌داشتن کلاسترهای etcd برای پایداری کلاسترهای کوبرنتیز حیاتی است.
بنابراین، کلاسترهای etcd را روی ماشین‌های اختصاصی یا در محیط‌های ایزوله اجرا کنید
تا [نیازمندی‌های منابع تضمین‌شده](https://etcd.io/docs/current/op-guide/hardware/) فراهم باشد.

### ابزارها

بسته به نتیجه‌ای که دنبال می‌کنید، به ابزار `etcdctl` یا ابزار `etcdutl` نیاز خواهید داشت
(ممکن است به هر دو نیاز داشته باشید).

## آشنایی با etcdctl و etcdutl

ابزارهای `etcdctl` و `etcdutl` ابزارهای خط فرمانی هستند که برای تعامل با کلاسترهای etcd استفاده می‌شوند، اما هدف‌های متفاوتی دارند:

- ابزار `etcdctl`: این ابزار، کلاینت اصلی خط فرمان برای تعامل با etcd از طریق
شبکه است و برای کارهای روزمره مانند مدیریت کلیدها و مقادیر،
مدیریت کلاستر، بررسی سلامت و موارد دیگر به کار می‌رود.

- ابزار `etcdutl`: این ابزار یک ابزار مدیریتی است که برای کار مستقیم روی فایل‌های داده etcd
طراحی شده است؛ از جمله مهاجرت داده‌ها بین نسخه‌های etcd، یکپارچه‌سازی (defragment) پایگاه داده،
بازیابی اسنپ‌شات‌ها و اعتبارسنجی سازگاری داده‌ها. برای عملیات شبکه‌ای باید از `etcdctl`
استفاده کرد.

برای اطلاعات بیشتر درباره `etcdutl` می‌توانید به [مستندات بازیابی etcd](https://etcd.io/docs/v3.5/op-guide/recovery/) مراجعه کنید.


## راه‌اندازی کلاسترهای etcd

این بخش راه‌اندازی کلاستر etcd تک‌نودی و چندنودی را پوشش می‌دهد.

این راهنما فرض می‌کند که `etcd` از قبل نصب شده است.

### کلاستر etcd تک‌نودی

از کلاستر etcd تک‌نودی فقط برای اهداف آزمایشی استفاده کنید.

1. دستور زیر را اجرا کنید:

   ```sh
   etcd --listen-client-urls=http://$PRIVATE_IP:2379 \
      --advertise-client-urls=http://$PRIVATE_IP:2379
   ```

2. سرور API کوبرنتیز را با فلگ
   `--etcd-servers=$PRIVATE_IP:2379` راه‌اندازی کنید.

   مطمئن شوید که `PRIVATE_IP` روی IP کلاینت etcd شما تنظیم شده است.

### کلاستر etcd چندنودی

برای دوام و دسترس‌پذیری بالا، در محیط عملیاتی etcd را به‌صورت کلاستر چندنودی
اجرا کنید و به‌طور دوره‌ای از آن پشتیبان بگیرید. در محیط عملیاتی، کلاستری با پنج عضو
توصیه می‌شود. برای اطلاعات بیشتر،
[مستندات پرسش‌های متداول](https://etcd.io/docs/current/faq/#what-is-failure-tolerance) را ببینید.

از آنجا که از کوبرنتیز استفاده می‌کنید، می‌توانید etcd را به‌صورت یک کانتینر درون
یک یا چند Pod اجرا کنید. ابزار `kubeadm` به‌طور پیش‌فرض etcd را به‌صورت
{{< glossary_tooltip text="پادهای ایستا" term_id="static-pod" >}} راه‌اندازی می‌کند؛
همچنین می‌توانید یک
[کلاستر جداگانه](/docs/setup/production-environment/tools/kubeadm/setup-ha-etcd-with-kubeadm/)
مستقر کنید و به kubeadm بگویید از آن کلاستر etcd به‌عنوان ذخیره‌ساز پشتیبان control plane استفاده کند.

کلاستر etcd را یا با اطلاعات ایستای اعضا پیکربندی می‌کنید یا با کشف پویا (dynamic discovery).
برای اطلاعات بیشتر درباره خوشه‌بندی،
[مستندات خوشه‌بندی etcd](https://etcd.io/docs/current/op-guide/clustering/) را ببینید.

برای مثال، یک کلاستر etcd پنج‌عضوی را در نظر بگیرید که با URLهای کلاینت زیر اجرا می‌شود:
`http://$IP1:2379`، `http://$IP2:2379`، `http://$IP3:2379`،
`http://$IP4:2379` و `http://$IP5:2379`. برای راه‌اندازی سرور API کوبرنتیز:

1. دستور زیر را اجرا کنید:

   ```shell
   etcd --listen-client-urls=http://$IP1:2379,http://$IP2:2379,http://$IP3:2379,http://$IP4:2379,http://$IP5:2379 --advertise-client-urls=http://$IP1:2379,http://$IP2:2379,http://$IP3:2379,http://$IP4:2379,http://$IP5:2379
   ```

2. سرورهای API کوبرنتیز را با فلگ
   `--etcd-servers=$IP1:2379,$IP2:2379,$IP3:2379,$IP4:2379,$IP5:2379` راه‌اندازی کنید.

   مطمئن شوید که متغیرهای `IP<n>` روی آدرس‌های IP کلاینت شما تنظیم شده‌اند.

### کلاستر etcd چندنودی با متعادل‌کننده بار

برای اجرای یک کلاستر etcd با متعادل‌سازی بار:

1. یک کلاستر etcd راه‌اندازی کنید.
2. یک متعادل‌کننده بار (load balancer) را جلوی کلاستر etcd پیکربندی کنید.
   برای مثال، فرض کنید نشانی متعادل‌کننده بار `$LB` باشد.
3. سرورهای API کوبرنتیز را با فلگ `--etcd-servers=$LB:2379` راه‌اندازی کنید.

## ایمن‌سازی کلاسترهای etcd

دسترسی به etcd معادل دسترسی root در کلاستر است؛ بنابراین در حالت ایده‌آل فقط
سرور API باید به آن دسترسی داشته باشد. با توجه به حساسیت داده‌ها، توصیه می‌شود
فقط به نودهایی مجوز داده شود که به دسترسی به کلاسترهای etcd نیاز دارند.

برای ایمن‌سازی etcd، یا قوانین فایروال تنظیم کنید یا از قابلیت‌های امنیتی
etcd استفاده کنید. قابلیت‌های امنیتی etcd به زیرساخت کلید عمومی (PKI) مبتنی بر
x509 وابسته‌اند. برای شروع، با تولید یک جفت کلید و گواهی، کانال‌های ارتباطی امن
برقرار کنید. برای نمونه، از جفت‌کلید `peer.key` و `peer.cert` برای ایمن‌سازی
ارتباط بین اعضای etcd و از `client.key` و `client.cert` برای ایمن‌سازی ارتباط
بین etcd و کلاینت‌هایش استفاده کنید. برای تولید جفت‌کلیدها و فایل‌های CA جهت
احراز هویت کلاینت، [اسکریپت‌های نمونه](https://github.com/coreos/etcd/tree/master/hack/tls-setup)
ارائه‌شده در پروژه etcd را ببینید.

### ایمن‌سازی ارتباطات

برای پیکربندی etcd با ارتباط امن بین اعضا (peer)، فلگ‌های
`--peer-key-file=peer.key` و `--peer-cert-file=peer.cert` را مشخص کنید و از HTTPS
به‌عنوان طرح (schema) URL استفاده کنید.

به همین ترتیب، برای پیکربندی etcd با ارتباط امن با کلاینت‌ها، فلگ‌های
`--key=k8sclient.key` و `--cert=k8sclient.cert` را مشخص کنید و از HTTPS
به‌عنوان طرح URL استفاده کنید. در ادامه نمونه‌ای از یک دستور کلاینت آمده است که
از ارتباط امن استفاده می‌کند:

```
ETCDCTL_API=3 etcdctl --endpoints 10.2.0.9:2379 \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  member list
```

### محدود کردن دسترسی به کلاسترهای etcd

پس از پیکربندی ارتباط امن، با استفاده از احراز هویت TLS، دسترسی به کلاستر etcd را
فقط به سرورهای API کوبرنتیز محدود کنید.

برای مثال، جفت‌کلید `k8sclient.key` و `k8sclient.cert` را در نظر بگیرید که
CA با نام `etcd.ca` به آن‌ها اعتماد دارد. هنگامی که etcd همراه با TLS با `--client-cert-auth`
پیکربندی شود، گواهی‌های کلاینت‌ها را با استفاده از CAهای سیستم یا CA ارسال‌شده
از طریق فلگ `--trusted-ca-file` تأیید می‌کند. با مشخص کردن فلگ‌های
`--client-cert-auth=true` و `--trusted-ca-file=etcd.ca`، دسترسی فقط به
کلاینت‌هایی که گواهی `k8sclient.cert` دارند محدود می‌شود.

پس از آنکه etcd به‌درستی پیکربندی شد، فقط کلاینت‌هایی که گواهی معتبر دارند
می‌توانند به آن دسترسی داشته باشند. برای دادن دسترسی به سرورهای API کوبرنتیز،
آن‌ها را با فلگ‌های `--etcd-certfile=k8sclient.cert`، `--etcd-keyfile=k8sclient.key` و
`--etcd-cafile=ca.cert` پیکربندی کنید.

احراز هویت etcd برای کوبرنتیز برنامه‌ریزی نشده است.

## جایگزینی عضو ازکارافتاده etcd

کلاستر etcd با تحمل خرابی تعداد اندکی از اعضا به دسترس‌پذیری بالا دست می‌یابد.
با این حال، برای بهبود سلامت کلی کلاستر، اعضای ازکارافتاده را فوراً جایگزین کنید.
اگر چند عضو از کار بیفتند، آن‌ها را یکی‌یکی جایگزین کنید. جایگزینی عضو ازکارافتاده
دو مرحله دارد: حذف عضو ازکارافتاده و افزودن یک عضو جدید.

با اینکه etcd شناسه‌های یکتای اعضا را در داخل خود نگه می‌دارد، توصیه می‌شود برای
جلوگیری از خطای انسانی، برای هر عضو نامی یکتا به کار ببرید. برای مثال، یک کلاستر
etcd سه‌عضوی را در نظر بگیرید و فرض کنید URLها `member1=http://10.0.0.1`،
`member2=http://10.0.0.2` و `member3=http://10.0.0.3` باشند. وقتی `member1` از کار بیفتد،
آن را با `member4=http://10.0.0.4` جایگزین کنید.

1. شناسه عضو ازکارافتاده `member1` را به دست آورید:

   ```shell
   etcdctl --endpoints=http://10.0.0.2,http://10.0.0.3 member list
   ```

   پیام زیر نمایش داده می‌شود:

   ```console
   8211f1d0f64f3269, started, member1, http://10.0.0.1:2380, http://10.0.0.1:2379
   91bc3c398fb3c146, started, member2, http://10.0.0.2:2380, http://10.0.0.2:2379
   fd422379fda50e48, started, member3, http://10.0.0.3:2380, http://10.0.0.3:2379
   ```

1. یکی از کارهای زیر را انجام دهید:

   1. اگر هر سرور API کوبرنتیز برای ارتباط با همه اعضای etcd پیکربندی شده است،
      عضو ازکارافتاده را از فلگ `--etcd-servers` حذف کنید و سپس همه سرورهای
      API کوبرنتیز را دوباره راه‌اندازی کنید.
   1. اگر هر سرور API کوبرنتیز فقط با یک عضو etcd ارتباط دارد، سرور API کوبرنتیزی
      را که با etcd ازکارافتاده ارتباط دارد متوقف کنید.

1. سرور etcd را روی نود خراب متوقف کنید. ممکن است کلاینت‌های دیگری غیر از
   سرور API کوبرنتیز نیز به etcd ترافیک بفرستند؛ بهتر است همه ترافیک را
   متوقف کنید تا از نوشتن در دایرکتوری داده جلوگیری شود.

1. عضو ازکارافتاده را حذف کنید:

   ```shell
   etcdctl member remove 8211f1d0f64f3269
   ```

   پیام زیر نمایش داده می‌شود:

   ```console
   Removed member 8211f1d0f64f3269 from cluster
   ```

1. عضو جدید را اضافه کنید:

   ```shell
   etcdctl member add member4 --peer-urls=http://10.0.0.4:2380
   ```

   پیام زیر نمایش داده می‌شود:

   ```console
   Member 2be1eb8f84b7f63e added to cluster ef37ad9dc622a7c4
   ```

1. عضو تازه‌افزوده را روی ماشینی با IP `10.0.0.4` راه‌اندازی کنید:

   ```shell
   export ETCD_NAME="member4"
   export ETCD_INITIAL_CLUSTER="member2=http://10.0.0.2:2380,member3=http://10.0.0.3:2380,member4=http://10.0.0.4:2380"
   export ETCD_INITIAL_CLUSTER_STATE=existing
   etcd [flags]
   ```

1. یکی از کارهای زیر را انجام دهید:

   1. اگر هر سرور API کوبرنتیز برای ارتباط با همه اعضای etcd پیکربندی شده است،
      عضو تازه‌افزوده را به فلگ `--etcd-servers` اضافه کنید و سپس همه سرورهای
      API کوبرنتیز را دوباره راه‌اندازی کنید.
   1. اگر هر سرور API کوبرنتیز فقط با یک عضو etcd ارتباط دارد، سرور API کوبرنتیزی
      را که در مرحله ۲ متوقف شده بود راه‌اندازی کنید. سپس کلاینت‌های سرور API
      کوبرنتیز را طوری پیکربندی کنید که درخواست‌ها را دوباره به همان سرور API
      کوبرنتیزِ متوقف‌شده هدایت کنند. این کار اغلب با پیکربندی یک متعادل‌کننده بار
      انجام می‌شود.

برای اطلاعات بیشتر درباره پیکربندی مجدد کلاستر،
[مستندات پیکربندی مجدد etcd](https://etcd.io/docs/current/op-guide/runtime-configuration/#remove-a-member) را ببینید.

## پشتیبان‌گیری از کلاستر etcd

همه آبجکت‌های کوبرنتیز در etcd ذخیره می‌شوند. پشتیبان‌گیری دوره‌ای از داده‌های
کلاستر etcd برای بازیابی کلاسترهای کوبرنتیز در سناریوهای فاجعه، مانند از دست رفتن
همه نودهای control plane، اهمیت دارد. فایل اسنپ‌شات تمام وضعیت و اطلاعات حیاتی
کوبرنتیز را در بر دارد. برای حفظ امنیت داده‌های حساس کوبرنتیز، فایل‌های اسنپ‌شات
را رمزنگاری کنید.

پشتیبان‌گیری از کلاستر etcd به دو روش ممکن است: اسنپ‌شات داخلی etcd و
اسنپ‌شات حجم (volume snapshot).

### اسنپ‌شات داخلی

در etcd از اسنپ‌شات داخلی پشتیبانی می‌شود. اسنپ‌شات را می‌توان یا از یک عضو فعال
با دستور `etcdctl snapshot save` ایجاد کرد، یا با کپی کردن فایل
`member/snap/db` از یک
[دایرکتوری داده](https://etcd.io/docs/current/op-guide/configuration/#--data-dir)
etcd که در حال حاضر هیچ فرایند etcd از آن استفاده نمی‌کند. ایجاد اسنپ‌شات
بر کارایی عضو تأثیری نمی‌گذارد.

در ادامه نمونه‌ای از ایجاد اسنپ‌شات از فضای کلیدی که `$ENDPOINT` ارائه می‌دهد،
در فایل `snapshot.db` آمده است:

```shell
ETCDCTL_API=3 etcdctl --endpoints $ENDPOINT snapshot save snapshot.db
```

### اسنپ‌شات حجم

اگر etcd روی یک حجم ذخیره‌سازی اجرا می‌شود که از پشتیبان‌گیری پشتیبانی می‌کند،
مانند Amazon Elastic Block Store، با ایجاد اسنپ‌شات از آن حجم ذخیره‌سازی
از داده‌های etcd پشتیبان بگیرید.

### اسنپ‌شات با استفاده از گزینه‌های etcdctl

همچنین می‌توان اسنپ‌شات را با گزینه‌های مختلفی که etcdctl ارائه می‌دهد ایجاد کرد. برای مثال، دستور

```shell
ETCDCTL_API=3 etcdctl -h 
``` 

گزینه‌های مختلف موجود در etcdctl را فهرست می‌کند. برای نمونه، می‌توانید با مشخص کردن
endpoint، گواهی‌ها و کلید، مطابق زیر یک اسنپ‌شات ایجاد کنید:

```shell
ETCDCTL_API=3 etcdctl --endpoints=https://127.0.0.1:2379 \
  --cacert=<trusted-ca-file> --cert=<cert-file> --key=<key-file> \
  snapshot save <backup-file-location>
```
که در آن `trusted-ca-file`، `cert-file` و `key-file` را می‌توان از توضیحات Pod مربوط به etcd به دست آورد.

## افزایش مقیاس کلاسترهای etcd

افزایش مقیاس کلاسترهای etcd، دسترس‌پذیری را به بهای کاهش کارایی افزایش می‌دهد.
مقیاس‌دهی نه کارایی کلاستر را افزایش می‌دهد و نه توانایی آن را. قاعده کلی این است
که مقیاس کلاسترهای etcd را افزایش یا کاهش ندهید. هیچ گروه مقیاس‌دهی خودکاری
(auto scaling group) برای کلاسترهای etcd پیکربندی نکنید. اکیداً توصیه می‌شود
برای کلاسترهای کوبرنتیز عملیاتی، در هر مقیاسی که به‌طور رسمی پشتیبانی می‌شود،
همیشه یک کلاستر etcd ایستای پنج‌عضوی اجرا کنید.

یک مقیاس‌دهی معقول این است که هرگاه به قابلیت اطمینان بیشتری نیاز باشد، کلاستر
سه‌عضوی را به کلاستر پنج‌عضوی ارتقا دهید. برای آشنایی با نحوه افزودن عضو به یک
کلاستر موجود،
[مستندات پیکربندی مجدد etcd](https://etcd.io/docs/current/op-guide/runtime-configuration/#remove-a-member)
را ببینید.

## بازیابی یک کلاستر etcd

{{< caution >}}
اگر هر یک از API serverها در کلاستر شما در حال اجرا باشد، نباید برای بازیابی نمونه‌های etcd اقدام کنید. در عوض، برای بازیابی etcd این مراحل را دنبال کنید:

- *همه‌ی* نمونه‌های API server را متوقف کنید
- وضعیت را در همه‌ی نمونه‌های etcd بازیابی کنید
- همه‌ی نمونه‌های API server را دوباره راه‌اندازی کنید

پروژه‌ی کوبرنتیز همچنین توصیه می‌کند که مؤلفه‌های کوبرنتیز (`kube-scheduler`، `kube-controller-manager` و `kubelet`) را دوباره راه‌اندازی کنید تا مطمئن شوید به داده‌های کهنه وابسته نیستند. در عمل، بازیابی کمی زمان می‌برد. در طول بازیابی، مؤلفه‌های حیاتی قفل رهبری (leader lock) را از دست می‌دهند و خودشان را دوباره راه‌اندازی می‌کنند.
{{< /caution >}}

ابزار etcd از بازیابی با استفاده از snapshotهایی پشتیبانی می‌کند که از یک فرایند etcd با همان نسخه‌ی [major.minor](https://semver.org/) گرفته شده‌اند. بازیابی از نسخه‌ای با شماره‌ی patch متفاوت etcd نیز پشتیبانی می‌شود. عملیات بازیابی برای بازگرداندن داده‌های یک کلاستر ازکارافتاده به کار می‌رود.

پیش از شروع عملیات بازیابی، باید یک فایل snapshot در دسترس باشد. این فایل می‌تواند یا حاصل یک عملیات پشتیبان‌گیری قبلی باشد یا از یک [دایرکتوری داده](https://etcd.io/docs/current/op-guide/configuration/#--data-dir)ی باقی‌مانده تهیه شود.

{{< tabs name="etcd_restore" >}}
{{% tab name="استفاده از etcdutl" %}}
   هنگام بازیابی کلاستر با استفاده از [`etcdutl`](https://github.com/etcd-io/etcd/blob/main/etcdutl/README.md)،
   با گزینه‌ی `--data-dir` مشخص کنید که کلاستر در کدام پوشه بازیابی شود:

   ```shell
   etcdutl --data-dir <data-dir-location> snapshot restore snapshot.db
   ```
   در این دستور، `<data-dir-location>` دایرکتوری‌ای است که در طول فرایند بازیابی ایجاد می‌شود.

{{% /tab %}}
{{% tab name="استفاده از etcdctl (منسوخ‌شده)" %}}

   {{< note >}}
   استفاده از `etcdctl` برای بازیابی از نسخه‌ی v3.5.x ابزار etcd **منسوخ** شده است و قرار است در etcd v3.6 حذف شود.
   توصیه می‌شود به‌جای آن از [`etcdutl`](https://github.com/etcd-io/etcd/blob/main/etcdutl/README.md) استفاده کنید.
   {{< /note >}}

   مثال زیر نحوه‌ی استفاده از ابزار `etcdctl` را برای عملیات بازیابی نشان می‌دهد:

   ```shell
   export ETCDCTL_API=3
   etcdctl --data-dir <data-dir-location> snapshot restore snapshot.db
   ```

{{% /tab %}}
{{< /tabs >}}

اگر `<data-dir-location>` همان پوشه‌ی قبلی است، پیش از بازیابی کلاستر آن را حذف کنید و فرایند etcd را متوقف کنید.
در غیر این صورت، پس از بازیابی پیکربندی etcd را تغییر دهید و فرایند etcd را دوباره راه‌اندازی کنید تا از دایرکتوری داده‌ی جدید استفاده کند:
ابتدا مقدار `volumes.hostPath.path` مربوط به `name: etcd-data` را در فایل `/etc/kubernetes/manifests/etcd.yaml` به `<data-dir-location>` تغییر دهید،
سپس دستور `kubectl -n kube-system delete pod <name-of-etcd-pod>` یا `systemctl restart kubelet.service` (یا هر دو) را اجرا کنید.
در کلاستری که kubeadm آن را مدیریت می‌کند، مقدار `etcd.local.dataDir` را نیز در ConfigMap با نام `kubeadm-config` برابر `<data-dir-location>` قرار دهید
([پیکربندی مجدد یک کلاستر kubeadm](/docs/tasks/administer-cluster/kubeadm/kubeadm-reconfigure/#updating-the-clusterconfiguration)).
اگر این مقدار همچنان به دایرکتوری قدیمی اشاره کند، اجرای بعدی `kubeadm upgrade` یک مانیفست etcd برای همان دایرکتوری می‌نویسد.

برای اطلاعات بیشتر و مثال‌هایی درباره‌ی بازیابی کلاستر از یک فایل snapshot، به
[مستندات بازیابی از فاجعه‌ی etcd](https://etcd.io/docs/current/op-guide/recovery/#restoring-a-cluster) مراجعه کنید.

اگر نشانی‌های دسترسی (URL) کلاستر بازیابی‌شده با کلاستر قبلی متفاوت باشد، باید API server کوبرنتیز را متناسب با آن دوباره پیکربندی کرد. در این حالت، API serverهای کوبرنتیز را به‌جای فلگ `--etcd-servers=$OLD_ETCD_CLUSTER` با فلگ `--etcd-servers=$NEW_ETCD_CLUSTER` دوباره راه‌اندازی کنید. به‌جای `$NEW_ETCD_CLUSTER` و `$OLD_ETCD_CLUSTER` نشانی‌های IP مربوط را قرار دهید. اگر جلوی کلاستر etcd از یک متعادل‌کننده‌ی بار (load balancer) استفاده می‌شود، ممکن است لازم باشد به‌جای آن، متعادل‌کننده‌ی بار را به‌روزرسانی کنید.

اگر اکثر اعضای etcd برای همیشه از کار افتاده باشند، کلاستر etcd ازکارافتاده در نظر گرفته می‌شود. در این وضعیت، کوبرنتیز نمی‌تواند هیچ تغییری در وضعیت فعلی خود ایجاد کند. هرچند ممکن است پادهای زمان‌بندی‌شده به اجرای خود ادامه دهند، هیچ پاد جدیدی زمان‌بندی نمی‌شود. در چنین مواردی، برای رفع مشکل کلاستر etcd را بازیابی کنید و در صورت نیاز API serverهای کوبرنتیز را دوباره پیکربندی کنید.


## ارتقای کلاسترهای etcd

{{< caution >}}
پیش از شروع ارتقا، ابتدا از کلاستر etcd خود نسخه‌ی پشتیبان تهیه کنید.
{{< /caution >}}

برای جزئیات ارتقای etcd، به مستندات [ارتقاهای etcd](https://etcd.io/docs/latest/upgrades/) مراجعه کنید.

## خواندن جریانی از etcd

{{< feature-state feature_gate_name="EtcdRangeStream" >}}

وقتی feature gate با نام `EtcdRangeStream` فعال باشد و از etcd نسخه‌ی v3.7 یا بالاتر استفاده شود، API server مجموعه‌های بزرگ را به‌جای صفحه‌به‌صفحه، به‌صورت جریانی (stream) از etcd می‌خواند و این کار اوج مصرف حافظه را در هر دو سمت کاهش می‌دهد. اگر backend فراخوانی RPC با نام `RangeStream` را پیاده‌سازی نکرده باشد، API server پاسخ `Unimplemented` در gRPC را تشخیص می‌دهد و به خواندن صفحه‌بندی‌شده بازمی‌گردد. اگر backend یا proxy سازگار با etcd شما به‌درستی به این حالت بازنمی‌گردد، این gate را با `--feature-gates=EtcdRangeStream=false` غیرفعال کنید.

{{< note >}}
خواندن‌های جریانی در متریک `etcd_request_duration_seconds` با مقدار `operation="listStream"` ثبت می‌شوند. هر داشبورد یا هشداری را که با `operation="list"` تطبیق داده می‌شود، به‌روزرسانی کنید.
{{< /note >}}

## نگهداری کلاسترهای etcd

برای جزئیات بیشتر درباره‌ی نگهداری etcd، لطفاً به مستندات [نگهداری etcd](https://etcd.io/docs/latest/op-guide/maintenance/) مراجعه کنید.

### یکپارچه‌سازی (defragmentation) کلاستر

{{% thirdparty-content single="true" %}}

یکپارچه‌سازی عملیاتی پرهزینه است، بنابراین باید تا حد امکان به‌ندرت اجرا شود. از سوی دیگر، لازم است مطمئن شوید که هیچ‌یک از اعضای etcd از سهمیه‌ی ذخیره‌سازی فراتر نمی‌رود. پروژه‌ی کوبرنتیز توصیه می‌کند که برای انجام یکپارچه‌سازی از ابزاری مانند [etcd-defrag](https://github.com/ahrtr/etcd-defrag) استفاده کنید.

همچنین می‌توانید ابزار یکپارچه‌سازی را به‌صورت یک CronJob در کوبرنتیز اجرا کنید تا مطمئن شوید یکپارچه‌سازی به‌طور منظم انجام می‌شود. برای جزئیات، فایل [`etcd-defrag-cronjob.yaml`](https://github.com/ahrtr/etcd-defrag/blob/main/doc/etcd-defrag-cronjob.yaml) را ببینید.
