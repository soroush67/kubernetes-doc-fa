این صفحه نشان می‌دهد که چگونه نودها را به استفاده از به‌روزرسانی‌های مبتنی بر رویداد برای وضعیت کانتینر منتقل کنید. در مقایسه با روش قدیمی که بر نظرسنجی دوره‌ای (polling) تکیه دارد، پیاده‌سازی مبتنی بر رویداد مصرف منابع نود توسط kubelet را کاهش می‌دهد.
ممکن است این قابلیت را با نام _تولیدکنندهٔ رویداد چرخهٔ حیات Pod مبتنی بر رویداد (evented PLEG)_ بشناسید. این نامی است که در داخل پروژهٔ کوبرنتیز برای یکی از جزئیات کلیدی پیاده‌سازی به کار می‌رود.

به روش مبتنی بر نظرسنجی دوره‌ای، _PLEG عمومی (generic PLEG)_ گفته می‌شود.

## {{% heading "prerequisites" %}}

* باید نسخه‌ای از کوبرنتیز را اجرا کنید که این قابلیت را ارائه می‌دهد.
  کوبرنتیز v1.27 پشتیبانی بتا از به‌روزرسانی‌های مبتنی بر رویداد برای وضعیت کانتینر را در بر دارد. این قابلیت در مرحلهٔ بتا است، اما به‌طور پیش‌فرض _غیرفعال_ است، زیرا به پشتیبانی محیط اجرای کانتینر نیاز دارد.
* {{< version-check >}}
  اگر نسخهٔ دیگری از کوبرنتیز را اجرا می‌کنید، مستندات همان نسخه را بررسی کنید.
* محیط اجرای کانتینری که استفاده می‌کنید باید از رویدادهای چرخهٔ حیات کانتینر پشتیبانی کند.
  اگر محیط اجرای کانتینر پشتیبانی از رویدادهای چرخهٔ حیات کانتینر را اعلام نکند، kubelet به‌طور خودکار به سازوکار قدیمی PLEG عمومی بازمی‌گردد، حتی اگر این feature gate را فعال کرده باشید.

## چرا به PLEG مبتنی بر رویداد تغییر دهیم؟

* _PLEG عمومی_ به دلیل نظرسنجی مکرر وضعیت کانتینرها، سربار قابل‌توجهی ایجاد می‌کند.
* نظرسنجی موازی وضعیت کانتینرها در kubelet این سربار را تشدید می‌کند. در نتیجه، مقیاس‌پذیری آن محدود می‌شود و عملکرد ضعیف و مشکلات قابلیت اطمینان پدید می‌آید.
* هدف _PLEG مبتنی بر رویداد_ این است که با جایگزین کردن نظرسنجی دوره‌ای، کارهای غیرضروری را در زمان بی‌کاری کاهش دهد.

## تغییر به PLEG مبتنی بر رویداد

1. kubelet را با [feature gate](/docs/reference/command-line-tools-reference/feature-gates/) `EventedPLEG` فعال‌شده اجرا کنید. برای مدیریت feature gateهای kubelet می‌توانید
   [فایل پیکربندی](/docs/tasks/administer-cluster/kubelet-config-file/) kubelet را ویرایش کنید و سرویس kubelet را دوباره راه‌اندازی کنید.
   این کار را باید روی هر نودی که از این قابلیت استفاده می‌کند انجام دهید.

2. پیش از ادامه، مطمئن شوید که نود [تخلیه](/docs/tasks/administer-cluster/safely-drain-node/) شده است.

3. محیط اجرای کانتینر را با تولید رویداد کانتینر فعال‌شده اجرا کنید.

   {{< tabs name="tab_with_code" >}}
   {{% tab name="Containerd" %}}
   نسخهٔ 1.7 به بالا
   {{% /tab %}}
   {{% tab name="CRI-O" %}}
   نسخهٔ 1.26 به بالا

   با بررسی پیکربندی، مطمئن شوید که CRI-O از قبل برای انتشار رویدادهای CRI پیکربندی شده است:

   ```shell
   crio config | grep enable_pod_events
   ```

   اگر این گزینه فعال باشد، خروجی باید مشابه زیر باشد:

   ```none
   enable_pod_events = true
   ```

   برای فعال کردن آن، دیمن CRI-O را با فلگ `--enable-pod-events=true` اجرا کنید یا از یک فایل پیکربندی تکمیلی (drop-in) با خطوط زیر استفاده کنید:

   ```toml
   [crio.runtime]
   enable_pod_events = true
   ```
   {{% /tab %}}
   {{< /tabs >}}

   {{< version-check >}}

4. بررسی کنید که kubelet از پایش مبتنی بر رویداد برای تغییر مرحلهٔ کانتینر استفاده می‌کند.
   برای این کار، عبارت `EventedPLEG` را در لاگ‌های kubelet جست‌وجو کنید.

   خروجی باید مشابه زیر باشد:

   ```console
   I0314 11:10:13.909915 1105457 feature_gate.go:249] feature gates: &{map[EventedPLEG:true]}
   ```

   اگر مقدار `--v` را روی ۴ یا بیشتر تنظیم کرده باشید، ممکن است ورودی‌های بیشتری ببینید که نشان می‌دهند kubelet از پایش مبتنی بر رویداد برای وضعیت کانتینر استفاده می‌کند.

   ```console
   I0314 11:12:42.009542 1110177 evented.go:238] "Evented PLEG: Generated pod status from the received event" podUID=3b2c6172-b112-447a-ba96-94e7022912dc
   I0314 11:12:44.623326 1110177 evented.go:238] "Evented PLEG: Generated pod status from the received event" podUID=b3fba5ea-a8c5-4b76-8f43-481e17e8ec40
   I0314 11:12:44.714564 1110177 evented.go:238] "Evented PLEG: Generated pod status from the received event" podUID=b3fba5ea-a8c5-4b76-8f43-481e17e8ec40
   ```
