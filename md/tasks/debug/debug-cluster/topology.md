کوبرنتیز بسیاری از جنبه‌های نحوهٔ اجرای پادها روی نودها را از دید کاربر پنهان نگه می‌دارد و این رفتار آگاهانه طراحی شده است. با این حال، برخی بارهای کاری برای آنکه عملکرد قابل‌قبولی داشته باشند، به تضمین‌های قوی‌تری از نظر تأخیر و/یا کارایی نیاز دارند. `kubelet` روش‌هایی فراهم می‌کند که با آن‌ها می‌توان سیاست‌های پیچیده‌تری برای جای‌گذاری بار کاری فعال کرد، بی‌آنکه این لایهٔ انتزاع به دستورهای صریح جای‌گذاری آلوده شود.

می‌توانید توپولوژی را در داخل نودها مدیریت کنید. این کار یعنی کمک به kubelet برای پیکربندی سیستم‌عامل میزبان، به‌گونه‌ای که Podها و کانتینرها در سمت درستِ مرزهای داخلی، مانند _دامنه‌های NUMA_، قرار بگیرند. (NUMA کوتاه‌شدهٔ عبارت _non-uniform memory access_ به معنای «دسترسی ناهمگون به حافظه» است و به این ایده اشاره دارد که پردازنده‌ها ممکن است به‌دلیل چیدمان فیزیکی اجزای سخت‌افزاری و نحوهٔ اتصال آن‌ها به یکدیگر، از نظر توپولوژیک به نواحی مشخصی از حافظه نزدیک‌تر باشند.)

## منابع اطلاعات برای عیب‌یابی

در زمینهٔ مدیریت توپولوژی، برای یافتن علت اینکه چرا یک پاد مستقر نشده یا در یک نود رد شده است، می‌توانید از ابزارهای زیر استفاده کنید:

- _وضعیت پاد_ - خطاهای وابستگی توپولوژی (topology affinity) را نشان می‌دهد
- _لاگ‌های سیستم_ - اطلاعات ارزشمندی برای اشکال‌زدایی دارند؛ برای مثال، دربارهٔ راهنماهای (hints) تولیدشده
- _فایل وضعیت kubelet_ - خروجی وضعیت داخلی Memory Manager است
  (شامل _نقشهٔ نود_ و _نقشه‌های حافظه_)
- می‌توانید از [API منبع افزونهٔ دستگاه](#device-plugin-resource-api)
  برای دریافت اطلاعات مربوط به حافظهٔ رزروشده برای کانتینرها استفاده کنید

## عیب‌یابی `TopologyAffinityError` {#TopologyAffinityError}

این خطا معمولاً در شرایط زیر رخ می‌دهد:

* نود منابع در دسترس کافی برای برآورده کردن درخواست پاد ندارد
* درخواست پاد به‌دلیل محدودیت‌های سیاست خاصی از Topology Manager رد می‌شود

این خطا در وضعیت پاد نمایش داده می‌شود:

```shell
kubectl get pods
```

```none
NAME         READY   STATUS                  RESTARTS   AGE
guaranteed   0/1     TopologyAffinityError   0          113s
```

برای دریافت پیام خطای مفصل، از `kubectl describe pod <id>` یا `kubectl events` استفاده کنید:

```none
Warning  TopologyAffinityError  10m   kubelet, dell8  Resources cannot be allocated with Topology locality
```

## بررسی لاگ‌های سیستم

لاگ‌های سیستم را برای یک پاد مشخص جست‌وجو کنید.

مجموعه راهنماهایی که CPU Manager تولید کرده است باید در لاگ‌ها وجود داشته باشد. همچنین مجموعه راهنماهایی را که Memory Manager برای پاد تولید کرده است نیز می‌توان در لاگ‌ها یافت.

Topology Manager این راهنماها را با هم ادغام می‌کند تا یک راهنمای برتر واحد را محاسبه کند. این راهنمای برتر نیز باید در لاگ‌ها وجود داشته باشد.

راهنمای برتر مشخص می‌کند که همهٔ منابع باید در کجا تخصیص داده شوند. Topology Manager این راهنما را با سیاست فعلی خود می‌سنجد و بر اساس نتیجه، پاد را در نود می‌پذیرد یا آن را رد می‌کند.

همچنین لاگ‌ها را برای رخدادهای مرتبط با Memory Manager جست‌وجو کنید؛ برای مثال، برای یافتن اطلاعاتی دربارهٔ به‌روزرسانی‌های `cgroups` و `cpuset.mems`.

## مثال‌ها

### بررسی وضعیت Memory Manager روی یک نود

ابتدا یک پاد نمونه از نوع `Guaranteed` با مشخصات زیر مستقر می‌کنیم:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: guaranteed
spec:
  containers:
  - name: guaranteed
    image: consumer
    imagePullPolicy: Never
    resources:
      limits:
        cpu: "2"
        memory: 150Gi
      requests:
        cpu: "2"
        memory: 150Gi
    command: ["sleep","infinity"]
```

سپس وارد نودی شوید که پاد روی آن مستقر شده است و فایل وضعیت موجود در
`/var/lib/kubelet/memory_manager_state` را بررسی کنید:


از فایل وضعیت می‌توان نتیجه گرفت که پاد به هر دو نود NUMA سنجاق (pin) شده است، یعنی:

```json
"numaAffinity":[
   0,
   1
],
```

اصطلاح «سنجاق‌شده» به این معناست که مصرف حافظهٔ پاد (از طریق پیکربندی `cgroups`) به این نودهای NUMA محدود شده است.

این موضوع به‌طور خودکار نشان می‌دهد که Memory Manager گروه جدیدی ایجاد کرده که از این دو نود NUMA، یعنی نودهای NUMA با اندیس `0` و `1`، تشکیل شده است.

برای تحلیل منابع حافظهٔ در دسترس در یک گروه، باید مقادیر متناظر نودهای NUMA متعلق به آن گروه را با هم جمع کرد.

برای مثال، کل حافظهٔ «معمولی» آزاد در گروه را می‌توان با جمع کردن حافظهٔ آزاد در دسترس در هر نود NUMA گروه محاسبه کرد؛ یعنی مقادیر بخش `"memory"` در نود NUMA شمارهٔ `0` (`"free":0`) و نود NUMA شمارهٔ `1` (`"free":103739236352`). بنابراین، کل حافظهٔ «معمولی» آزاد در این گروه برابر با `0 + 103739236352` بایت است.

سطر `"systemReserved":3221225472` نشان می‌دهد که مدیر این نود با استفاده از فلگ `--reserved-memory`، مقدار `3221225472` بایت (یعنی `3Gi`) را در نود NUMA شمارهٔ `0` برای سرویس‌دهی به kubelet و فرایندهای سیستمی رزرو کرده است.

## بررسی API منبع افزونهٔ دستگاه {#device-plugin-resource-api}

kubelet یک سرویس gRPC به نام `PodResourceLister` فراهم می‌کند تا کشف منابع و فراداده‌های مرتبط با آن‌ها ممکن شود. با استفاده از [نقطهٔ پایانی List در gRPC](/docs/concepts/extend-kubernetes/compute-storage-net/device-plugins/#grpc-endpoint-list) می‌توان اطلاعات حافظهٔ رزروشده برای هر کانتینر را دریافت کرد؛ این اطلاعات در پیام protobuf با نام `ContainerMemory` قرار دارد.

این اطلاعات را فقط برای پادهایی که در کلاس QoS از نوع Guaranteed قرار دارند می‌توان دریافت کرد.
