این صفحه رهنمودهایی برای سبک نگارش مستندات کوبرنتیز ارائه می‌دهد. این موارد رهنمود هستند، نه قانون. بر اساس بهترین قضاوت خود عمل کنید و در صورت تمایل، تغییراتی را برای این سند در قالب یک pull request پیشنهاد دهید.

برای اطلاعات بیشتر درباره ایجاد محتوای جدید برای مستندات کوبرنتیز، [راهنمای محتوای مستندات](/docs/contribute/style/content-guide/) را بخوانید.

تغییرات راهنمای سبک را گروه SIG Docs به‌صورت جمعی اعمال می‌کند. برای پیشنهاد یک تغییر یا افزودن مطلبی تازه، [آن را به دستور جلسه اضافه کنید](https://bit.ly/sig-docs-agenda) تا در یکی از جلسات آینده SIG Docs مطرح شود، و برای مشارکت در بحث در آن جلسه حاضر شوید.

## زبان

مستندات کوبرنتیز به زبان‌های متعددی ترجمه شده است (به [فایل‌های README بومی‌سازی](https://github.com/kubernetes/website/blob/main/README.md#localization-readmemds) مراجعه کنید).

روش بومی‌سازی مستندات برای زبانی دیگر در [بومی‌سازی مستندات کوبرنتیز](/docs/contribute/localization/) شرح داده شده است.

## استانداردهای قالب‌بندی مستندات

### برای آبجکت‌های API از حالت UpperCamelCase استفاده کنید

هنگامی که مشخصاً به تعامل با یک آبجکت API اشاره می‌کنید، از حالت [UpperCamelCase](https://en.wikipedia.org/wiki/Camel_case) استفاده کنید که با نام Pascal case نیز شناخته می‌شود. ممکن است در [مرجع API](/docs/reference/kubernetes-api/) با شکل‌های دیگری از بزرگ‌نویسی، مانند "configMap"، روبه‌رو شوید. هنگام نوشتن مستندات عمومی، بهتر است از UpperCamelCase استفاده کنید و آن را "ConfigMap" بنامید.

هنگامی که به‌طور کلی درباره یک آبجکت API صحبت می‌کنید، از [بزرگ‌نویسی به سبک جمله](https://docs.microsoft.com/en-us/style-guide/text-formatting/using-type/use-sentence-style-capitalization) استفاده کنید.

مثال‌های زیر بر بزرگ‌نویسی تمرکز دارند. برای اطلاعات بیشتر درباره قالب‌بندی نام آبجکت‌های API، رهنمودهای مرتبط در بخش [سبک کد](#code-style-inline-code) را مرور کنید.

## ارجاع به منابع API کوبرنتیز

این بخش توضیح می‌دهد که در مستندات چگونه به منابع API ارجاع می‌دهیم.

### توضیحی درباره «منبع»

کوبرنتیز از واژه _منبع_ (resource) برای اشاره به منابع API استفاده می‌کند. برای مثال، مسیر URL `/apis/apps/v1/namespaces/default/deployments/my-app` نشان‌دهنده یک Deployment با نام "my-app" در {{< glossary_tooltip text="فضای نام" term_id="namespace" >}} "default" است. در اصطلاحات HTTP، {{< glossary_tooltip text="فضای نام" term_id="namespace" >}} یک منبع است؛ همان‌طور که همه URLهای وب یک منبع را مشخص می‌کنند.

مستندات کوبرنتیز همچنین واژه «منبع» را برای صحبت درباره درخواست‌ها (requests) و محدودیت‌های (limits) CPU و حافظه به کار می‌برد. بسیاری از اوقات بهتر است منابع API را «منابع API» بنامید؛ این کار از اشتباه گرفتن آن‌ها با منابع CPU و حافظه یا انواع دیگر منابع جلوگیری می‌کند.

اگر از شکل جمع و با حروف کوچکِ نام یک منبع، مانند `deployments` یا `configmaps`، استفاده می‌کنید، توضیح نوشتاری بیشتری ارائه دهید تا خوانندگان منظور شما را درک کنند. اگر این اصطلاح را در بافتی به کار می‌برید که نام UpperCamelCase نیز در آن مناسب است و خطر ابهام وجود دارد، استفاده از kind مربوط به API به شکل UpperCamelCase را در نظر بگیرید.

### چه زمانی از اصطلاحات API کوبرنتیز استفاده کنیم

اصطلاحات مختلف API کوبرنتیز عبارت‌اند از:

- _kindهای API_: نامی که در URL مربوط به API به کار می‌رود (مانند `pods`، `namespaces`).
  به kindهای API گاهی _انواع منبع_ (resource types) نیز گفته می‌شود.
- _منبع API_: یک نمونه از یک kind از API (مانند `pod`، `secret`).
- _آبجکت_: منبعی که به‌عنوان یک «ثبت قصد» (record of intent) عمل می‌کند. هر آبجکت وضعیت مطلوب بخش مشخصی از کلاستر شما است که control plane کوبرنتیز تلاش می‌کند آن را حفظ کند.
  همه آبجکت‌های موجود در API کوبرنتیز منبع نیز هستند.

برای وضوح بیشتر، هنگام اشاره به یک منبع API در مستندات کوبرنتیز می‌توانید واژه «منبع» یا «آبجکت» را اضافه کنید.
برای مثال، به‌جای «یک Secret» بنویسید «یک آبجکت Secret».
اگر منظور تنها از روی بزرگ‌نویسی روشن است، نیازی به افزودن واژه اضافی نیست.

هرگاه بازنویسی جمله به جلوگیری از سوءتفاهم کمک می‌کند، آن را بازنویسی کنید. یک موقعیت رایج زمانی است که می‌خواهید جمله‌ای را با یک kind از API، مانند “Secret”، آغاز کنید؛ از آنجا که در زبان انگلیسی و برخی زبان‌های دیگر حرف اول جمله بزرگ نوشته می‌شود، خوانندگان نمی‌توانند تشخیص دهند که منظور شما kind مربوط به API است یا مفهوم کلی. بازنویسی جمله می‌تواند در این موارد کمک کند.

### نام منابع API

نام منابع API را همیشه با قالب [UpperCamelCase](https://en.wikipedia.org/wiki/Camel_case) بنویسید که با نام PascalCase نیز شناخته می‌شود. برای نوشتن kindهای API از قالب کد استفاده نکنید.

نام یک آبجکت API را به واژه‌های جداگانه تقسیم نکنید. برای مثال، از PodTemplateList استفاده کنید، نه Pod Template List.

برای اطلاعات بیشتر درباره PascalCase و قالب‌بندی کد، رهنمودهای مرتبط در [برای آبجکت‌های API از حالت UpperCamelCase استفاده کنید](/docs/contribute/style/style-guide/#use-upper-camel-case-for-api-objects) و [برای کدها، فرمان‌ها و آبجکت‌های API درون‌خطی از سبک کد استفاده کنید](/docs/contribute/style/style-guide/#code-style-inline-code) را مرور کنید.

برای اطلاعات بیشتر درباره اصطلاحات API کوبرنتیز، رهنمودهای مرتبط در [اصطلاحات API کوبرنتیز](/docs/reference/using-api/api-concepts/#standard-api-terminology) را مرور کنید.

بررسی کنید که پاد روی نود انتخاب‌شده شما در حال اجرا است:

```shell
kubectl get pods --output=wide
```

خروجی مشابه زیر است:

```console
NAME     READY     STATUS    RESTARTS   AGE    IP           NODE
nginx    1/1       Running   0          13s    10.200.0.4   worker0
```

### نسخه‌گذاری مثال‌های کوبرنتیز

مثال‌های کد و مثال‌های پیکربندی که اطلاعات نسخه را در بر دارند، باید با متن همراهشان سازگار باشند.

اگر اطلاعات به نسخه خاصی وابسته است، نسخه کوبرنتیز باید در بخش `prerequisites` از [قالب Task](/docs/contribute/style/page-content-types/#task) یا [قالب Tutorial](/docs/contribute/style/page-content-types/#tutorial) تعریف شود.
پس از ذخیره صفحه، بخش `prerequisites` با عنوان **پیش از شروع** (Before you begin) نمایش داده می‌شود.

برای تعیین نسخه کوبرنتیز در صفحه یک وظیفه یا آموزش، `min-kubernetes-server-version` را در سربرگ (front matter) صفحه قرار دهید.

اگر YAML مثال در یک فایل مستقل قرار دارد، مباحثی را که به آن ارجاع می‌دهند پیدا و بررسی کنید.
مطمئن شوید که همه مباحثِ استفاده‌کننده از این YAML مستقل، اطلاعات نسخه مناسب را تعریف کرده‌اند.
اگر هیچ مبحثی به یک فایل YAML مستقل ارجاع نمی‌دهد، به‌جای به‌روزرسانی، حذف آن را در نظر بگیرید.

برای مثال، اگر آموزشی می‌نویسید که به نسخه 1.8 کوبرنتیز مربوط است، سربرگ فایل markdown شما باید چیزی شبیه به این باشد:

```yaml
---
title: <your tutorial title here>
min-kubernetes-server-version: v1.8
---
```

در مثال‌های کد و پیکربندی، توضیحی درباره نسخه‌های جایگزین درج نکنید.
مراقب باشید که گزاره‌های نادرست را به‌صورت توضیح (comment) در مثال‌های خود نیاورید؛ مانند:

```yaml
apiVersion: v1 # earlier versions use...
kind: Pod
...
```

## فرمول‌ها و معادلات

می‌توانید از پشتیبانی Docsy برای [نمودارها و فرمول‌ها](https://www.docsy.dev/docs/adding-content/diagrams-and-formulae/#latex-support-with-katex) استفاده کنید.

برای مثال: `\\(\frac{7}{9} \sqrt{K^8 s}\\)` که به صورت \\(\frac{7}{9} \sqrt{K^8 s}\\) نمایش داده می‌شود.

هر جا که معقول است، فرمول‌های درون‌خطی را ترجیح دهید؛ اما اگر یک بلوک `math` احتمالاً به خوانندگان کمک می‌کند، می‌توانید از آن استفاده کنید.

راهنمای Docsy را بخوانید تا بدانید برای فعال‌سازی این پشتیبانی چه تغییراتی باید در صفحه خود اعمال کنید؛ اگر با مشکلی روبه‌رو شدید، `math: true` را به [سربرگ](https://gohugo.io/content-management/front-matter/) صفحه اضافه کنید (حتی اگر فکر می‌کنید فعال‌سازی خودکار کافی است، می‌توانید این کار را انجام دهید).

## شورت‌کدها

[شورت‌کدهای](https://gohugo.io/content-management/shortcodes) Hugo به ایجاد سطوح مختلفی از تأکید کمک می‌کنند. مستندات ما در این دسته از سه گونه شورت‌کد [`alert`](https://www.docsy.dev/docs/adding-content/shortcodes/#alert) در Docsy پشتیبانی می‌کند: **Note**، **Caution** و **Warning**.

1. متن را میان شورت‌کد آغازین و پایانی `alert` قرار دهید و ویژگی‌های `color` و `title` را متناسب با گونه موردنیاز خود انتخاب کنید.

2. برای اعمال یک سبک، از نحو زیر استفاده کنید:

   ```none
   {{</* alert color="info" title="Note" */>}}
   The shortcode renders the title as a heading, so do not repeat it inside the body.
   {{</* /alert */>}}
   ```

   خروجی به این صورت است:

   {{< alert color="info" title="Note" >}}
   این شورت‌کد عنوان را به‌صورت سرتیتر نمایش می‌دهد؛ بنابراین آن را درون متن تکرار نکنید.
   {{< /alert >}}

بسیاری از صفحه‌های موجود هنوز از شورت‌کدهای قدیمی `{{</* note */>}}`، `{{</* caution */>}}` و `{{</* warning */>}}` استفاده می‌کنند. این شورت‌کدها همچنان کار می‌کنند؛ اما برای محتوای جدید و هنگام ویرایش صفحه‌های موجود، شورت‌کد `alert` را ترجیح دهید.

### یادداشت

از `{{</* alert color="info" title="Note" */>}}` برای برجسته‌کردن یک نکته یا اطلاعاتی استفاده کنید که دانستن آن ممکن است مفید باشد.

برای مثال:

```
{{</* alert color="info" title="Note" */>}}
You can _still_ use Markdown inside these callouts.
{{</* /alert */>}}
```

خروجی به این صورت است:

{{< alert color="info" title="Note" >}}
در این کادرهای توضیحی _همچنان_ می‌توانید از Markdown استفاده کنید.
{{< /alert >}}

می‌توانید کد کوتاه (shortcode) `alert` را درون یک فهرست به کار ببرید:

```
1. Use the alert shortcode in a list

1. A second item with an embedded note

   {{</* alert color="info" title="Note" */>}}
   Warning, Caution, and Note shortcodes, embedded in lists, need to be indented four spaces. See [Common Shortcode Issues](#common-shortcode-issues).
   {{</* /alert */>}}

1. A third item in a list

1. A fourth item in a list
```

خروجی به این صورت است:

1. از کد کوتاه alert درون یک فهرست استفاده کنید

1. مورد دوم، همراه با یک یادداشت درونی

    {{< alert color="info" title="Note" >}}
    کدهای کوتاه Warning، Caution و Note که درون فهرست‌ها قرار می‌گیرند، باید چهار فاصله تورفتگی داشته باشند. به [مشکلات رایج کدهای کوتاه](#common-shortcode-issues) مراجعه کنید.
    {{< /alert >}}

1. مورد سوم فهرست

1. مورد چهارم فهرست

### احتیاط

از `{{</* alert color="caution" title="Caution" */>}}` برای جلب توجه به اطلاعات مهمی استفاده کنید که به پرهیز از اشتباهات رایج کمک می‌کند.

برای مثال:

```
{{</* alert color="caution" title="Caution" */>}}
The callout style only applies to the line directly above the tag.
{{</* /alert */>}}
```

خروجی به این صورت است:

{{< alert color="caution" title="Caution" >}}
سبک کادر توضیحی فقط روی خطی اعمال می‌شود که درست بالای تگ قرار دارد.
{{< /alert >}}

### هشدار

از `{{</* alert color="danger" title="Warning" */>}}` برای نشان‌دادن خطر یا اطلاعاتی استفاده کنید که رعایت آن حیاتی است.

برای مثال:

```
{{</* alert color="danger" title="Warning" */>}}
Beware.
{{</* /alert */>}}
```

خروجی به این صورت است:

{{< alert color="danger" title="Warning" >}}
مراقب باشید.
{{< /alert >}}

## مشکلات رایج کدهای کوتاه

### فهرست‌های مرتب

کدهای کوتاه فهرست‌های شماره‌دار را قطع می‌کنند، مگر اینکه پیش از متن اعلان و تگ، چهار فاصله تورفتگی بگذارید.

برای مثال:

    1. Preheat oven to 350˚F

    1. Prepare the batter, and pour into springform pan.
       {{</* alert color="info" title="Note" */>}}Grease the pan for best results.{{</* /alert */>}}

    1. Bake for 20-25 minutes or until set.

خروجی به این صورت است:

1. فر را از پیش تا دمای 350˚F گرم کنید

1. خمیر را آماده کنید و آن را در قالب کمربندی بریزید.

   {{< alert color="info" title="Note" >}}برای بهترین نتیجه، کف قالب را چرب کنید.{{< /alert >}}

1. به مدت ۲۰ تا ۲۵ دقیقه یا تا زمانی که خمیر سفت شود، بپزید.

### دستورهای include

قرار دادن کدهای کوتاه درون دستورهای include باعث شکست فرایند ساخت (build) می‌شود. باید
آن‌ها را در سند والد، پیش و پس از فراخوانی include، قرار دهید. برای مثال:

```
{{</* alert color="info" title="Note" */>}}
{{</* include "task-tutorial-prereqs.md" */>}}
{{</* /alert */>}}
```

## عناصر Markdown

### شکست خط

برای جدا کردن محتوای سطح بلوک، مانند سرعنوان‌ها، فهرست‌ها، تصاویر، بلوک‌های کد و موارد دیگر،
از یک خط جدید استفاده کنید. استثنای این قاعده سرعنوان‌های سطح دوم هستند که پیش از آن‌ها باید
دو خط جدید بیاید. سرعنوان‌های سطح دوم بدون هیچ پاراگراف یا متنی پس از سرعنوان سطح اول (یا عنوان صفحه)
می‌آیند. فاصلهٔ دوخطی کمک می‌کند ساختار کلی محتوا در ویرایشگر کد بهتر دیده شود.

در صورت لزوم، پاراگراف‌ها را در منبع Markdown به‌صورت دستی بشکنید. از آنجا که ابزار git
و وب‌سایت GitHub تفاوت فایل‌ها را خط‌به‌خط نمایش می‌دهند، شکستن دستی خطوط طولانی
به بازبین‌ها کمک می‌کند تغییرات یک PR را به‌آسانی پیدا کنند و بازخورد بدهند.
این کار به تیم‌های بومی‌سازی پایین‌دستی نیز کمک می‌کند که تغییرات بالادستی را خط‌به‌خط
دنبال می‌کنند. برای مثال، می‌توان خط را در پایان یک جمله یا پس از یک علامت نگارشی شکست.
یک استثنا این است که هر پیوند Markdown یا کد کوتاه باید در یک خط قرار گیرد.

### سرعنوان‌ها و عنوان‌ها {#headings}

ممکن است افرادی که به این مستندات دسترسی دارند از صفحه‌خوان یا دیگر فناوری‌های کمکی (AT) استفاده کنند.
[صفحه‌خوان‌ها](https://en.wikipedia.org/wiki/Screen_reader) دستگاه‌های خروجی خطی هستند؛
یعنی موارد یک صفحه را یکی‌یکی بازگو می‌کنند. اگر صفحه محتوای زیادی دارد، می‌توانید
با سرعنوان‌ها به آن ساختاری درونی بدهید. ساختار خوب صفحه به همهٔ خوانندگان کمک می‌کند
به‌آسانی در صفحه حرکت کنند یا موضوعات موردنظر خود را جدا کنند.

{{< table caption = "Do and Don't - Headings" >}}
انجام دهید | انجام ندهید
:--| :-----
عنوان را در front matter صفحه یا پست وبلاگ به‌روز کنید. | از سرعنوان سطح اول استفاده نکنید، زیرا Hugo عنوان موجود در front matter صفحه را خودکار به سرعنوان سطح اول تبدیل می‌کند.
از سرعنوان‌های مرتب برای ارائهٔ طرح کلی و معنادار محتوا استفاده کنید. | از سرعنوان‌های سطح ۴ تا ۶ استفاده نکنید، مگر اینکه کاملاً ضروری باشد. اگر محتوای شما تا این حد جزئی است، شاید لازم باشد آن را به چند مقالهٔ جداگانه تقسیم کنید.
برای محتوای غیر از پست وبلاگ، از علامت پوند یا هش (`#`) استفاده کنید. | برای مشخص کردن سرعنوان‌های سطح اول از خط زیرین (`---` یا `===`) استفاده نکنید.
برای سرعنوان‌های بدنهٔ صفحه از حالت جمله (sentence case) استفاده کنید. برای مثال، **Extend kubectl with plugins** | برای سرعنوان‌های بدنهٔ صفحه از حالت عنوان (title case) استفاده نکنید. برای مثال، **Extend Kubectl With Plugins**
برای عنوان صفحه در front matter از حالت عنوان استفاده کنید. برای مثال، `title: Kubernetes API Server Bypass Risks` | برای عنوان صفحه در front matter از حالت جمله استفاده نکنید. برای مثال، از `title: Kubernetes API server bypass risks` استفاده نکنید
پیوندهای مرتبط را در متن بدنه قرار دهید. | در سرعنوان‌ها ابرپیوند (`<a href=""></a>`) نگذارید.
برای نشان دادن سرعنوان‌ها از علامت پوند یا هش (`#`) استفاده کنید. | برای جدا کردن پاراگراف‌ها از متن **پررنگ** یا نشانه‌های دیگر استفاده نکنید.
{{< /table >}}

### فهرست‌ها

مواردی را که با یکدیگر مرتبط‌اند و باید به ترتیب مشخصی نمایش داده شوند، یا میان آن‌ها
ارتباطی وجود دارد، در یک فهرست گروه‌بندی کنید. وقتی صفحه‌خوان به یک فهرست می‌رسد،
چه مرتب باشد و چه نامرتب، به کاربر اعلام می‌کند که با گروهی از موارد فهرست روبه‌روست.
کاربر سپس می‌تواند با کلیدهای جهت‌نما میان موارد مختلف فهرست بالا و پایین برود.
پیوندهای ناوبری وب‌سایت را نیز می‌توان به‌صورت موارد فهرست نشانه‌گذاری کرد؛ زیرا آن‌ها
چیزی جز گروهی از پیوندهای مرتبط نیستند.

- اگر یک یا چند مورد از فهرست جملهٔ کامل هستند، هر مورد را با نقطه به پایان برسانید.
  برای یکدستی، معمولاً یا همهٔ موارد باید جملهٔ کامل باشند یا هیچ‌کدام.

  {{< alert color="info" title="Note" >}}
  فهرست‌های مرتبی که بخشی از یک جملهٔ مقدماتی ناتمام هستند، می‌توانند با حروف کوچک نوشته شوند
  و طوری نشانه‌گذاری شوند که گویی هر مورد بخشی از همان جملهٔ مقدماتی است.
  {{< /alert >}}

- برای فهرست‌های مرتب از عدد یک (`1.`) استفاده کنید.

- برای فهرست‌های نامرتب از (`+`)، (`*`) یا (`-`) استفاده کنید.

- پس از هر فهرست یک خط خالی بگذارید.

- فهرست‌های تودرتو را با چهار فاصله تورفتگی دهید (برای مثال، ⋅⋅⋅⋅).

- هر مورد فهرست می‌تواند از چند پاراگراف تشکیل شود. هر پاراگراف بعدی در یک مورد فهرست
  باید با چهار فاصله یا یک تب تورفتگی داشته باشد.

### جدول‌ها

هدف معنایی جدول داده، ارائهٔ داده‌های جدولی است. کاربران بینا می‌توانند جدول را
به‌سرعت مرور کنند، اما صفحه‌خوان آن را سطربه‌سطر می‌خواند. از عنوان جدول (table caption)
برای ایجاد عنوانی توصیفی برای جدول داده استفاده می‌شود. فناوری‌های کمکی از عنصر
caption جدول در HTML استفاده می‌کنند تا محتوای جدول را در ساختار صفحه به کاربر معرفی کنند.

- برای افزودن عنوان به جدول‌ها از [کدهای کوتاه Hugo](/docs/contribute/style/hugo-shortcodes/#table-captions) استفاده کنید.

## بهترین شیوه‌های نگارش محتوا

این بخش بهترین شیوه‌های پیشنهادی برای نوشتن محتوای روشن، موجز و یکدست را در بر دارد.

### از زمان حال استفاده کنید

{{< table caption = "Do and Don't - Use present tense" >}}
انجام دهید | انجام ندهید
:--| :-----
این فرمان یک پراکسی را راه‌اندازی می‌کند. | این فرمان یک پراکسی را راه‌اندازی خواهد کرد.
 {{< /table >}}

استثنا: اگر برای رساندن معنای درست لازم است، از زمان آینده یا گذشته استفاده کنید.

### از وجه معلوم استفاده کنید

{{< table caption = "Do and Don't - Use active voice" >}}
انجام دهید | انجام ندهید
:--| :-----
می‌توانید API را با یک مرورگر بررسی کنید. | API را می‌توان با یک مرورگر بررسی کرد.
فایل YAML تعداد رونوشت‌ها را مشخص می‌کند. | تعداد رونوشت‌ها در فایل YAML مشخص شده است.
{{< /table >}}

استثنا: اگر وجه معلوم به ساختاری نامأنوس منجر می‌شود، از وجه مجهول استفاده کنید.

### از زبان ساده و مستقیم استفاده کنید

از زبان ساده و مستقیم استفاده کنید. از عبارت‌های غیرضروری، مانند «لطفاً»، پرهیز کنید.

{{< table caption = "Do and Don't - Use simple and direct language" >}}
انجام دهید | انجام ندهید
:--| :-----
برای ایجاد یک ReplicaSet، ... | به منظور ایجاد یک ReplicaSet، ...
فایل پیکربندی را ببینید. | لطفاً فایل پیکربندی را ببینید.
پادها را مشاهده کنید. | با فرمان بعدی، پادها را مشاهده خواهیم کرد.
{{< /table >}}

### خواننده را با «شما» خطاب کنید

{{< table caption = "Do and Don't - Addressing the reader" >}}
انجام دهید | انجام ندهید
:--| :-----
می‌توانید یک Deployment را با ... ایجاد کنید | یک Deployment را با ... ایجاد خواهیم کرد
در خروجی پیشین، می‌توانید ... را ببینید | در خروجی پیشین، می‌توانیم ... را ببینیم
{{< /table >}}

### از عبارت‌های لاتین پرهیز کنید

اصطلاحات انگلیسی را به اختصارهای لاتین ترجیح دهید.

{{< table caption = "Do and Don't - Avoid Latin phrases" >}}
انجام دهید | انجام ندهید
:--| :-----
برای مثال، ... | e.g., ...
یعنی، ...| i.e., ...
{{< /table >}}

استثنا: برای et cetera از «etc.» استفاده کنید.

## الگوهایی که باید از آن‌ها پرهیز کرد

### از به‌کاربردن «ما» پرهیز کنید

به‌کاربردن «ما» در جمله می‌تواند گیج‌کننده باشد، زیرا ممکن است خواننده نداند
آیا خودش جزو «ما»یی است که توصیف می‌کنید یا نه.

{{< table caption = "Do and Don't - Patterns to avoid" >}}
انجام دهید | انجام ندهید
:--| :-----
نسخهٔ 1.4 شامل ... است | در نسخهٔ 1.4، ما ... را افزوده‌ایم
کوبرنتیز قابلیت جدیدی برای ... فراهم می‌کند | ما قابلیت جدیدی ... فراهم می‌کنیم
این صفحه نحوهٔ استفاده از پادها را به شما آموزش می‌دهد. | در این صفحه، ما قرار است دربارهٔ پادها یاد بگیریم.
{{< /table >}}

### از اصطلاحات تخصصی نامأنوس و اصطلاحات عامیانه پرهیز کنید

برخی خوانندگان انگلیسی را به‌عنوان زبان دوم صحبت می‌کنند. برای اینکه بهتر متوجه شوند، از اصطلاحات تخصصی نامأنوس و اصطلاحات عامیانه پرهیز کنید.

{{< table caption = "Do and Don't - Avoid jargon and idioms" >}}
انجام دهید | انجام ندهید
:--| :-----
در درون، ... | زیر کاپوت، ...
یک کلاستر جدید ایجاد کنید. | یک کلاستر جدید را بالا بیاورید.
{{< /table >}}

### از گزاره‌هایی دربارهٔ آینده پرهیز کنید

از وعده دادن یا اشاره کردن به آینده پرهیز کنید. اگر لازم است دربارهٔ یک قابلیت آلفا
صحبت کنید، متن را زیر سرعنوانی قرار دهید که آن را به‌عنوان اطلاعات مربوط به نسخهٔ آلفا
مشخص کند.

یک استثنای این قاعده، مستنداتی است که به منسوخ‌شدن‌های اعلام‌شده‌ای می‌پردازند که
قرار است در نسخه‌های آینده حذف شوند. نمونه‌ای از این نوع مستندات
[راهنمای مهاجرت از APIهای منسوخ](/docs/reference/using-api/deprecation-guide/) است.

### از گزاره‌هایی که به‌زودی منسوخ می‌شوند پرهیز کنید

از واژه‌هایی مانند «در حال حاضر» و «جدید» پرهیز کنید. قابلیتی که امروز جدید است،
ممکن است چند ماه بعد دیگر جدید به شمار نیاید.

{{< table caption = "Do and Don't - Avoid statements that will soon be out of date" >}}
انجام دهید | انجام ندهید
:--| :-----
در نسخهٔ 1.4، ... | در نسخهٔ فعلی، ...
قابلیت Federation ... را فراهم می‌کند | قابلیت جدید Federation ... را فراهم می‌کند
{{< /table >}}

### از واژه‌هایی که سطح مشخصی از درک را فرض می‌کنند پرهیز کنید

از واژه‌هایی مانند «فقط»، «به‌سادگی»، «آسان»، «به‌آسانی» یا «ساده» پرهیز کنید. این واژه‌ها ارزشی نمی‌افزایند.

{{< table caption = "Do and Don't - Avoid insensitive words" >}}
انجام دهید | انجام ندهید
:--| :-----
یک فرمان را در ... بگنجانید | فقط یک فرمان را در ... بگنجانید
کانتینر را اجرا کنید ... | به‌سادگی کانتینر را اجرا کنید ...
می‌توانید ... را حذف کنید | می‌توانید به‌آسانی ... را حذف کنید
این مراحل ... | این مراحل ساده ...
{{< /table >}}

### فایل EditorConfig
پروژهٔ کوبرنتیز یک فایل EditorConfig نگهداری می‌کند که ترجیحات سبکی مشترک را در ویرایشگرهای متنی
مانند VS Code تنظیم می‌کند. اگر می‌خواهید مطمئن شوید مشارکت‌هایتان با بقیهٔ پروژه یکدست است،
می‌توانید از این فایل استفاده کنید. برای مشاهدهٔ این فایل، به
[`.editorconfig`](https://github.com/kubernetes/website/blob/main/.editorconfig) در ریشهٔ مخزن مراجعه کنید.
