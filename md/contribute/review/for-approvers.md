[بازبین‌ها](/docs/contribute/participate/#reviewers) و
[تأییدکنندگان](/docs/contribute/participate/#approvers) گروه SIG Docs هنگام بازبینی یک تغییر،
چند کار اضافه نیز انجام می‌دهند.

هر هفته یکی از تأییدکنندگان مستندات داوطلب می‌شود تا درخواست‌های ادغام (pull request) را
اولویت‌بندی و بازبینی کند. این فرد در آن هفته «PR Wrangler» نامیده می‌شود. برای اطلاعات بیشتر،
[برنامهٔ زمانی PR Wranglerها](https://github.com/kubernetes/website/wiki/PR-Wranglers)
را ببینید. برای اینکه PR Wrangler شوید، در جلسهٔ هفتگی SIG Docs شرکت کنید و داوطلب شوید.
حتی اگر در برنامهٔ هفتهٔ جاری نباشید، باز هم می‌توانید درخواست‌های ادغام (PR) را که هنوز
به‌طور فعال در حال بازبینی نیستند، بازبینی کنید.

علاوه بر این چرخش نوبتی، یک ربات نیز بر اساس مالکان فایل‌های تغییریافته، بازبین‌ها و
تأییدکنندگانی را به PR اختصاص می‌دهد.

<!-- body -->

## بازبینی یک PR

مستندات کوبرنتیز از
[فرایند بازبینی کد کوبرنتیز](https://github.com/kubernetes/community/blob/main/contributors/guide/owners.md#the-code-review-process)
پیروی می‌کند.

همهٔ مواردی که در [بازبینی یک درخواست ادغام](/docs/contribute/review/reviewing-prs)
شرح داده شده‌اند در اینجا نیز صدق می‌کنند، اما بازبین‌ها و تأییدکنندگان باید کارهای زیر را هم انجام دهند:

- در صورت نیاز، با دستور `/assign` در Prow یک بازبین مشخص را به PR اختصاص دهند.
  این کار به‌ویژه هنگام درخواست بازبینی فنی از مشارکت‌کنندگان کد اهمیت زیادی دارد.

  {{< note >}}
  برای اینکه ببینید چه کسانی می‌توانند بازبینی فنی انجام دهند، به فیلد `reviewers` در
  front-matter بالای فایل Markdown نگاه کنید.
  {{< /note >}}

- مطمئن شوند که PR از راهنماهای [محتوا](/docs/contribute/style/content-guide/)
  و [سبک نگارش](/docs/contribute/style/style-guide/) پیروی می‌کند و اگر چنین نیست،
  نویسنده را به بخش مربوط در راهنما(ها) ارجاع دهند.
- در صورت لزوم، با گزینهٔ **Request Changes** در GitHub تغییراتی را به نویسندهٔ PR پیشنهاد کنند.
- اگر پیشنهادهایشان اعمال شد، وضعیت بازبینی خود را در GitHub با دستورهای `/approve` یا
  `/lgtm` در Prow تغییر دهند.

## ثبت کامیت در PR شخص دیگر

گذاشتن نظر روی PR مفید است، اما گاهی ممکن است لازم باشد به‌جای آن، مستقیماً در PR شخص دیگری
کامیت ثبت کنید.

کار شخص دیگری را «به دست نگیرید»، مگر اینکه خودش صریحاً از شما بخواهد یا بخواهید یک PR را که
مدت‌ها رها شده است دوباره زنده کنید. هرچند این کار ممکن است در کوتاه‌مدت سریع‌تر باشد، فرصت
مشارکت را از آن شخص می‌گیرد.

روشی که به کار می‌برید به این بستگی دارد که بخواهید فایلی را ویرایش کنید که از قبل در محدودهٔ
PR قرار دارد، یا فایلی را که PR هنوز به آن دست نزده است.

اگر هر یک از شرایط زیر برقرار باشد، نمی‌توانید در PR شخص دیگری کامیت ثبت کنید:

- اگر نویسندهٔ PR شاخهٔ خود را مستقیماً به مخزن
  [https://github.com/kubernetes/website/](https://github.com/kubernetes/website/)
  push کرده باشد. در این حالت فقط بازبینی که دسترسی push دارد می‌تواند در PR کاربر دیگر کامیت ثبت کند.

  {{< note >}}
  نویسنده را تشویق کنید که دفعهٔ بعد، پیش از باز کردن PR، شاخهٔ خود را به fork خودش push کند.
  {{< /note >}}

- نویسندهٔ PR صراحتاً اجازهٔ ویرایش را از تأییدکنندگان گرفته باشد.

## دستورهای Prow برای بازبینی

[Prow](https://github.com/kubernetes/test-infra/blob/master/prow/README.md) یک سامانهٔ
CI/CD مبتنی بر کوبرنتیز است که کارهایی (job) را روی درخواست‌های ادغام اجرا می‌کند. این سامانه
امکان استفاده از دستورهایی به سبک چت‌بات را فراهم می‌کند تا کارهای GitHub در سراسر سازمان کوبرنتیز
انجام شود؛ کارهایی مانند [افزودن و حذف برچسب‌ها](#adding-and-removing-issue-labels)،
بستن issueها و اختصاص دادن تأییدکننده. دستورهای Prow را به‌صورت نظر در GitHub و با قالب
`/<command-name>` وارد کنید.

رایج‌ترین دستورهای Prow که بازبین‌ها و تأییدکنندگان به کار می‌برند عبارت‌اند از:

{{< table caption="دستورهای Prow برای بازبینی" >}}
دستور Prow | محدودیت نقش | توضیحات
:------------|:------------------|:-----------
`/lgtm` | اعضای سازمان | نشان می‌دهد که بازبینی PR را تمام کرده‌اید و از تغییرات راضی هستید.
`/approve` | تأییدکنندگان | PR را برای ادغام تأیید می‌کند.
`/assign` | همه | شخصی را برای بازبینی یا تأیید PR تعیین می‌کند.
`/close` | اعضای سازمان | یک issue یا PR را می‌بندد.
`/hold` | همه | برچسب `do-not-merge/hold` را اضافه می‌کند که نشان می‌دهد PR نمی‌تواند به‌طور خودکار ادغام شود.
`/hold cancel` | همه | برچسب `do-not-merge/hold` را حذف می‌کند.
{{< /table >}}

برای دیدن دستورهایی که می‌توانید در یک PR به کار ببرید، به
[مرجع دستورهای Prow](https://prow.k8s.io/command-help?repo=kubernetes%2Fwebsite) مراجعه کنید.

## اولویت‌بندی و دسته‌بندی issueها

به‌طور کلی، SIG Docs از فرایند
[اولویت‌بندی issueهای کوبرنتیز](https://github.com/kubernetes/community/blob/main/contributors/guide/issue-triage.md)
پیروی می‌کند و همان برچسب‌ها را به کار می‌برد.

این [فیلتر](https://github.com/kubernetes/website/issues?q=is%3Aissue+is%3Aopen+-label%3Apriority%2Fbacklog+-label%3Apriority%2Fimportant-longterm+-label%3Apriority%2Fimportant-soon+-label%3Atriage%2Fneeds-information+-label%3Atriage%2Fsupport+sort%3Acreated-asc)
در GitHub Issues، issueهایی را پیدا می‌کند که ممکن است به اولویت‌بندی نیاز داشته باشند.

### اولویت‌بندی یک issue

1. اعتبار issue را بررسی کنید

   - مطمئن شوید که issue دربارهٔ مستندات وب‌سایت است. برخی issueها را می‌توان با پاسخ دادن به
     یک پرسش یا راهنمایی گزارش‌دهنده به یک منبع، به‌سرعت بست. برای جزئیات، بخش
     [درخواست‌های پشتیبانی یا گزارش‌های باگ کد](#support-requests-or-code-bug-reports) را ببینید.
   - ارزیابی کنید که آیا issue ارزش پیگیری دارد یا نه.
   - اگر issue جزئیات کافی برای اقدام ندارد یا الگوی آن به‌درستی پر نشده است، برچسب
     `triage/needs-information` را اضافه کنید.
   - اگر issue هم برچسب `lifecycle/stale` و هم برچسب `triage/needs-information` را دارد، آن را ببندید.

2. یک برچسب اولویت اضافه کنید (برچسب‌های اولویت در
   [راهنمای اولویت‌بندی issueها](https://github.com/kubernetes/community/blob/main/contributors/guide/issue-triage.md#define-priority)
   به‌تفصیل تعریف شده‌اند)

  {{< table caption="برچسب‌های issue" >}}
  برچسب | توضیحات
  :------------|:------------------
  `priority/critical-urgent` | همین حالا انجام شود.
  `priority/important-soon` | ظرف ۳ ماه انجام شود.
  `priority/important-longterm` | ظرف ۶ ماه انجام شود.
  `priority/backlog` | می‌توان آن را به‌طور نامحدود به تعویق انداخت. هر زمان منابع در دسترس بود انجام شود.
  `priority/awaiting-more-evidence` | جایگاهی موقت برای یک issue بالقوه خوب، تا گم نشود.
  `help` یا `good first issue` | مناسب برای کسی که تجربهٔ بسیار کمی با کوبرنتیز یا SIG Docs دارد. برای اطلاعات بیشتر، [برچسب‌های Help Wanted و Good First Issue](https://kubernetes.dev/docs/guide/help-wanted/) را ببینید.

  {{< /table >}}

  به صلاحدید خود، مسئولیت یک issue را بر عهده بگیرید و برای آن یک PR ارسال کنید
  (به‌ویژه اگر سریع انجام می‌شود یا به کاری مربوط است که از قبل در حال انجامش هستید).

اگر دربارهٔ اولویت‌بندی یک issue پرسشی دارید، آن را در کانال `#sig-docs` در Slack یا
[فهرست پستی kubernetes-sig-docs](https://groups.google.com/forum/#!forum/kubernetes-sig-docs) مطرح کنید.

## افزودن و حذف برچسب‌های issue

برای افزودن یک برچسب، نظری با یکی از قالب‌های زیر بگذارید:

- `/<label-to-add>` (برای مثال، `/good-first-issue`)
- `/<label-category> <label-to-add>` (برای مثال، `/triage needs-information` یا `/language ja`)

برای حذف یک برچسب، نظری با یکی از قالب‌های زیر بگذارید:

- `/remove-<label-to-remove>` (برای مثال، `/remove-help`)
- `/remove-<label-category> <label-to-remove>` (برای مثال، `/remove-triage needs-information`)

در هر دو حالت، برچسب باید از قبل وجود داشته باشد. اگر بخواهید برچسبی را اضافه کنید که وجود ندارد،
دستور بی‌صدا نادیده گرفته می‌شود.

برای دیدن فهرست همهٔ برچسب‌ها، به [بخش Labels مخزن وب‌سایت](https://github.com/kubernetes/website/labels)
مراجعه کنید. SIG Docs همهٔ این برچسب‌ها را به کار نمی‌برد.

### برچسب‌های چرخهٔ عمر issue

issueها معمولاً به‌سرعت باز و بسته می‌شوند.
با این حال، گاهی یک issue پس از باز شدن غیرفعال می‌ماند.
در موارد دیگر، ممکن است لازم باشد یک issue بیش از ۹۰ روز باز بماند.

{{< table caption="برچسب‌های چرخهٔ عمر issue" >}}
برچسب | توضیحات
:------------|:------------------
`lifecycle/stale` | پس از ۹۰ روز بدون فعالیت، issue به‌طور خودکار برچسب stale (کهنه) می‌گیرد. اگر چرخهٔ عمر به‌صورت دستی با دستور `/remove-lifecycle stale` بازگردانده نشود، issue به‌طور خودکار بسته خواهد شد.
`lifecycle/frozen` | issueای که این برچسب را دارد پس از ۹۰ روز عدم فعالیت کهنه نمی‌شود. کاربر این برچسب را به‌صورت دستی به issueهایی اضافه می‌کند که باید بسیار بیش از ۹۰ روز باز بمانند، مانند issueهایی که برچسب `priority/important-longterm` دارند.
{{< /table >}}

## رسیدگی به انواع خاص issue

SIG Docs به‌قدری با انواع زیر از issueها روبه‌رو می‌شود که شیوهٔ رسیدگی به آن‌ها را مستند کرده است.

### issueهای تکراری

اگر برای یک مشکل واحد یک یا چند issue باز وجود دارد، آن‌ها را در یک issue ادغام کنید.
باید تصمیم بگیرید کدام issue باز بماند (یا یک issue جدید باز کنید)، سپس همهٔ اطلاعات مرتبط را
به آن منتقل کنید و issueهای مرتبط را به آن پیوند دهید. در پایان، همهٔ issueهای دیگری را که
همان مشکل را شرح می‌دهند با برچسب `triage/duplicate` علامت‌گذاری کنید و ببندید. داشتن تنها یک
issue برای کار روی یک مشکل، سردرگمی را کاهش می‌دهد و از دوباره‌کاری روی همان مشکل جلوگیری می‌کند.

### issueهای پیوند شکسته

اگر issue مربوط به پیوند شکسته در مستندات API یا `kubectl` است، تا زمانی که مشکل به‌طور کامل
درک نشده، اولویت `/priority critical-urgent` را به آن اختصاص دهید. به همهٔ دیگر issueهای پیوند
شکسته اولویت `/priority important-longterm` بدهید، زیرا باید به‌صورت دستی اصلاح شوند.

### issueهای وبلاگ

انتظار داریم نوشته‌های [وبلاگ کوبرنتیز](/blog/) با گذشت زمان قدیمی شوند. به همین دلیل، فقط
نوشته‌هایی را نگهداری می‌کنیم که کمتر از یک سال از انتشارشان گذشته باشد. اگر یک issue به نوشته‌ای
مربوط است که بیش از یک سال از انتشارش گذشته، معمولاً باید issue را بدون اصلاح ببندید.

می‌توانید پیوندی به [به‌روزرسانی و نگهداری مقاله‌ها](/docs/contribute/blog/#maintenance)
را در پیامی که هنگام بستن PR می‌فرستید قرار دهید.

در مواردی که توجیه مناسبی وجود دارد، اشکالی ندارد استثنا قائل شوید.

### درخواست‌های پشتیبانی یا گزارش‌های باگ کد

برخی issueهای مستندات در واقع مشکلاتی در کد زیربنایی هستند، یا درخواست کمک برای زمانی‌اند که
چیزی، مثلاً یک آموزش، درست کار نمی‌کند. برای issueهایی که به مستندات مربوط نیستند، issue را با
برچسب `kind/support` و نظری ببندید که درخواست‌کننده را به مراکز پشتیبانی (Slack و Stack Overflow)
و در صورت لزوم به مخزنی راهنمایی کند که باید باگ‌های مربوط به قابلیت‌ها را در آن گزارش کند
(`kubernetes/kubernetes` نقطهٔ شروع بسیار خوبی است).

نمونهٔ پاسخ به یک درخواست پشتیبانی:

```none
This issue sounds more like a request for support and less
like an issue specifically for docs. I encourage you to bring
your question to the `#kubernetes-users` channel in
[Kubernetes slack](https://slack.k8s.io/). You can also search
resources like
[Stack Overflow](https://stackoverflow.com/questions/tagged/kubernetes)
for answers to similar questions.

You can also open issues for Kubernetes functionality in
https://github.com/kubernetes/kubernetes.

If this is a documentation issue, please re-open this issue.
```

نمونهٔ پاسخ به گزارش باگ کد:

```none
This sounds more like an issue with the code than an issue with
the documentation. Please open an issue at
https://github.com/kubernetes/kubernetes/issues.

If this is a documentation issue, please re-open this issue.
```

### ادغام کامیت‌ها (Squashing)

شما به‌عنوان تأییدکننده، هنگام بازبینی درخواست‌های ادغام، ممکن است در موقعیت‌های مختلف یکی از
کارهای زیر را انجام دهید:

- به مشارکت‌کننده توصیه کنید کامیت‌هایش را squash کند.
- کامیت‌ها را خودتان برای مشارکت‌کننده squash کنید.
- به مشارکت‌کننده توصیه کنید فعلاً squash نکند.
- از squash کردن جلوگیری کنید.

**توصیه به مشارکت‌کنندگان برای squash کردن**: ممکن است یک مشارکت‌کنندهٔ تازه‌وارد نداند که باید
کامیت‌های درخواست ادغام خود را squash کند. در این صورت، به او توصیه کنید این کار را انجام دهد،
پیوندهایی به اطلاعات مفید در اختیارش بگذارید و اگر به کمک نیاز داشت، پیشنهاد دهید که کمکی برایش
فراهم کنید. چند پیوند مفید:

- [باز کردن درخواست‌های ادغام و squash کردن کامیت‌ها](/docs/contribute/new-content/open-a-pr#squashing-commits)
  برای مشارکت‌کنندگان مستندات.
- [گردش کار GitHub](https://www.k8s.dev/docs/guide/github-workflow/) همراه با نمودارها، برای توسعه‌دهندگان.

**squash کردن کامیت‌ها برای مشارکت‌کنندگان**: اگر مشارکت‌کننده در squash کردن کامیت‌ها با دشواری
روبه‌رو است یا برای ادغام PR محدودیت زمانی وجود دارد، می‌توانید خودتان کامیت‌ها را برایش squash کنید:

- مخزن kubernetes/website
  [طوری پیکربندی شده است که squash کردن را هنگام ادغام درخواست‌ها مجاز می‌داند](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/configuring-commit-squashing-for-pull-requests).
  کافی است دکمهٔ *Squash commits* را انتخاب کنید.
- اگر مشارکت‌کننده در PR به نگهدارندگان اجازهٔ مدیریت PR را داده باشد، می‌توانید کامیت‌هایش را
  squash کنید و fork او را با نتیجه به‌روزرسانی کنید. پیش از squash کردن، به او توصیه کنید آخرین
  تغییراتش را ذخیره و به PR push کند. پس از squash کردن، به او توصیه کنید کامیت squash‌شده را در
  نسخهٔ محلی خود pull کند.
- می‌توانید با استفاده از یک برچسب کاری کنید که GitHub کامیت‌ها را squash کند، به‌طوری که Tide یا
  GitHub این کار را انجام دهد، یا هنگام ادغام PR روی دکمهٔ *Squash commits* کلیک کنید.

**توصیه به مشارکت‌کنندگان برای پرهیز از squash کردن**

- اگر یکی از کامیت‌ها چیزی را خراب می‌کند یا کار نسنجیده‌ای انجام می‌دهد و آخرین کامیت این خطا را
  برمی‌گرداند، کامیت‌ها را squash نکنید. هرچند زبانهٔ «Files changed» در PR در GitHub و پیش‌نمایش
  Netlify هر دو درست به نظر می‌رسند، ادغام این PR ممکن است برای دیگران تعارض‌های rebase یا merge
  ایجاد کند. به هر شکلی که مناسب می‌دانید مداخله کنید تا این خطر متوجه دیگر مشارکت‌کنندگان نشود.

**هرگز squash نکنید**

- اگر در حال راه‌اندازی یک بومی‌سازی یا انتشار مستندات برای نسخه‌ای جدید هستید، شاخه‌ای را ادغام
  می‌کنید که از fork یک کاربر نیامده است؛ در این حالت _هرگز کامیت‌ها را squash نکنید_. squash نکردن
  ضروری است، زیرا باید تاریخچهٔ کامیت‌های آن فایل‌ها را حفظ کنید.
