دو وبلاگ رسمی کوبرنتیز وجود دارد و CNCF نیز وبلاگ خاص خود را دارد که
می‌توانید در آن نیز درباره‌ی کوبرنتیز بنویسید. برای
[وبلاگ اصلی کوبرنتیز](/docs/contribute/blog/)، ما (پروژه‌ی کوبرنتیز) دوست داریم
مقالاتی با دیدگاه‌های گوناگون و تمرکزهای ویژه منتشر کنیم که با
کوبرنتیز ارتباط داشته باشند.

به‌جز چند استثنای ویژه، ما تنها محتوایی را منتشر می‌کنیم که
در هیچ جای دیگری ارسال یا منتشر نشده باشد.

<!-- body -->

## نوشتن برای وبلاگ(های) کوبرنتیز

شما به‌عنوان نویسنده سه مسیر مختلف برای رسیدن به انتشار دارید.

### مسیر توصیه‌شده {#route-1}

رویکردی که پروژه‌ی کوبرنتیز توصیه می‌کند این است: ایده‌ی مقاله‌ی خود را با
تماس با تیم وبلاگ مطرح کنید. می‌توانید این کار را از طریق Slack کوبرنتیز
([#sig-docs-blog](https://kubernetes.slack.com/archives/CJDHVD54J)) انجام دهید. برای
مقالاتی که می‌خواهید تنها در وبلاگ مشارکت‌کنندگان منتشر شوند، می‌توانید
ایده‌ی خود را مستقیماً با
[SIG ContribEx comms](https://kubernetes.slack.com/archives/C03KT3SUJ20) نیز مطرح کنید.

مگر آنکه مشکلی در مطلب ارسالی شما وجود داشته باشد، تیم وبلاگ / SIG ContribEx
شما را با افراد زیر جفت می‌کند:

- یک _ویراستار_ وبلاگ
- _همیار نگارش_ شما (نویسنده‌ی دیگری از وبلاگ)

هنگامی که تیم شما را با نویسنده‌ی دیگری جفت می‌کند، هدف این است که هر دوی شما
با بازبینی پیش‌نویس مقاله‌ی یکدیگر از هم پشتیبانی کنید. لازم نیست
در موضوع مقاله متخصص باشید؛ بیشتر افرادی که مقاله را می‌خوانند نیز
متخصص نخواهند بود. ما، تیم وبلاگ کوبرنتیز، نویسنده‌ی دیگر را همیار
نگارش می‌نامیم.

ویراستار حضور دارد تا در مسیر پیش‌نویس تا انتشار به شما کمک کند.
او یا خودش مستقیماً می‌تواند مقاله‌ی شما را برای انتشار تأیید کند، یا
می‌تواند ترتیبی دهد که این تأیید انجام شود.

برای آشنایی بیشتر با این فرایند، [نگارش یک مقاله‌ی وبلاگ](#authoring) را بخوانید.

### شروع با یک pull request {#route-2}

مسیر دوم برای نوشتن در وبلاگ‌های ما، شروع مستقیم با یک pull
request در GitHub است. تیم وبلاگ در واقع این روش را توصیه نمی‌کند؛ GitHub برای
همکاری روی کد بسیار مفید است، اما برای متن نثر گزینه‌ی ایدئالی نیست.

کاملاً اشکالی ندارد که یک pull request جانگهدار تنها با یک commit خالی
باز کنید و سپس پیش از بازگشت به PR جانگهدار خود، در جای دیگری کار کنید.

همانند [مسیر توصیه‌شده](#route-1)، تلاش می‌کنیم شما را با یک
همیار نگارش و یک ویراستار وبلاگ جفت کنیم. آن‌ها به شما کمک می‌کنند مقاله را برای
انتشار آماده کنید.

### فرایند مقالات وبلاگ پس از انتشار {#route-3-post-release-comms}

مسیر سوم برای مقالات وبلاگ درباره‌ی تغییرات کوبرنتیز مرتبط با یک
انتشار است. هر بار که انتشاری انجام می‌شود، تیم اطلاع‌رسانی انتشار
برنامه‌ی انتشار وبلاگ را در اختیار می‌گیرد. افرادی که قابلیت‌هایی به یک نسخه اضافه می‌کنند، یا
تغییرات دیگری را برنامه‌ریزی می‌کنند که پروژه باید اعلام کند، می‌توانند با
تیم اطلاع‌رسانی انتشار هماهنگ شوند تا مقاله‌شان برنامه‌ریزی، پیش‌نویس، ویرایش و در نهایت
منتشر شود.

## زمان‌بندی مقالات

برای وبلاگ کوبرنتیز، تیم وبلاگ معمولاً مقالات وبلاگ را برای
انتشار در روزهای کاری هفته زمان‌بندی می‌کند (بر اساس تقویم میلادی، آن‌گونه که در ایالات متحده و سایر
کشورها استفاده می‌شود). هنگامی که انتشار در تاریخ مشخصی که به
آخر هفته می‌افتد اهمیت داشته باشد، تیم وبلاگ تلاش می‌کند آن را فراهم کند.

بخش [نگارش یک مقاله‌ی وبلاگ](#authoring) توضیح می‌دهد که چه کاری باید انجام دهید:

- در ابتدا، تاریخی برای مقاله تعیین نکنید
- با این حال، مقاله را به‌عنوان پیش‌نویس تنظیم کنید (`draft: true` را در front matter قرار دهید)

هنگامی که ربات Prow، PRی را که نوشته‌اید ادغام کند، مقاله پیش‌نویس خواهد بود و برای
انتشار تنظیم نخواهد شد. سپس یک مشارکت‌کننده‌ی کوبرنتیز (شما، همیار نگارشتان یا فردی
از تیم وبلاگ) یک PR پیگیری کوچک باز می‌کند که مقاله را برای
انتشار علامت‌گذاری می‌کند. ادغام این PR دوم، مقاله‌ای را که پیش‌تر پیش‌نویس بود آزاد می‌کند تا
بتواند به‌طور خودکار منتشر شود.

در روزی که مقاله برای انتشار زمان‌بندی شده است، خودکارسازی یک ساخت وب‌سایت را
آغاز می‌کند و مقاله‌ی شما قابل مشاهده می‌شود.

## نگارش یک مقاله {#authoring}

پس از آنکه ایده‌ی خود را مطرح کردید، شما را تشویق می‌کنیم از HackMD (یک ویرایشگر
Markdown تحت وب) یا یک Google doc برای به اشتراک گذاشتن نسخه‌ای قابل‌ویرایش از متن مقاله استفاده کنید.
همیار نگارش شما می‌تواند متن پیش‌نویس شما را بخواند و سپس یا مستقیماً پیشنهادهایی ارائه کند
یا بازخورد دیگری بدهد. او همچنین باید به شما اطلاع دهد اگر آنچه پیش‌نویس می‌کنید
با [رهنمودهای وبلاگ](/docs/contribute/blog/guidelines/) همسو نیست.

در همان زمان، شما نیز معمولاً همیار نگارش **او** خواهید بود و می‌توانید از
[راهنمای](/docs/contribute/blog/writing-buddy/) ما درباره‌ی پشتیبانی از کار او پیروی کنید.

### گام‌های اداری اولیه

اگر هنوز [CLA را امضا](/docs/contribute/new-content/#contributing-basics) نکرده‌اید، باید
این کار را انجام دهید. بهتر است این کار را زود آغاز کنید؛ اگر
به‌عنوان بخشی از شغل خود می‌نویسید، ممکن است لازم باشد با تیم حقوقی محل کار
یا با مدیر خود مشورت کنید تا مطمئن شوید که مجاز به امضای آن هستید.

### پیش‌نویس اولیه

تیم وبلاگ توصیه می‌کند از HackMD (یک ویرایشگر Markdown تحت وب) یا یک
Google doc برای آماده‌سازی و به اشتراک گذاشتن نسخه‌ی اولیه و قابل‌ویرایش زنده از
متن مقاله استفاده کنید.

{{< note >}} اگر استفاده از Google Docs را انتخاب کنید، می‌توانید سند خود را در
حالت Markdown قرار دهید. {{< /note >}}

همیار نگارش شما می‌تواند نظرات و/یا بازخوردهایی برای متن پیش‌نویس شما ارائه کند
و بررسی خواهد کرد (یا باید بررسی کند) که با رهنمودها همسو باشد. در همان
زمان، شما همیار نگارش او خواهید بود و می‌توانید از
[راهنمایی](/docs/contribute/blog/writing-buddy/) پیروی کنید که توضیح می‌دهد چگونه
از کار او پشتیبانی کنید.

با این حال، در این مرحله زیاد نگران دقیق بودن قالب‌بندی Markdown
نباشید.

اگر تصاویری دارید، می‌توانید برای دریافت بازخورد اولیه یک نسخه‌ی bitmap از آن‌ها را جایگذاری کنید. تیم وبلاگ
می‌تواند (در مراحل بعدی فرایند) به شما کمک کند تصاویر را برای انتشار نهایی
آماده کنید.

### Markdown برای انتشار

نگاهی به قالب Markdown پست‌های وبلاگ موجود در
[مخزن وب‌سایت](https://github.com/kubernetes/website/tree/master/content/en/blog/_posts)
در GitHub بیندازید.

اگر از قبل با آن آشنا نیستید،
[مبانی مشارکت](/docs/contribute/new-content/#contributing-basics) را بخوانید. این
بخش از صفحه فرض می‌کند که یک کلون محلی از fork خود ندارید
و درون رابط کاربری وب GitHub کار می‌کنید. اگر هنوز یک fork راه دور
از مخزن وب‌سایت ایجاد نکرده‌اید، باید این کار را انجام دهید.

در مخزن GitHub، روی دکمه‌ی **Create new file** کلیک کنید. فایل
پست وبلاگ را با قالب
`/content/en/blog/_posts/YYYY/abbreviated-post-title.md` نام‌گذاری کنید، که در آن
`…/YYYY/…` زیرپوشه‌ای است که پست‌های سال مربوط را در بر دارد. اگر
لازم است تصاویر، نمودارها و موارد دیگری به پست وبلاگ خود اضافه کنید، یک پوشه‌ی
`/content/blog/en/blog/_posts/YYYY/abbreviated-post-title/` همراه با
فایل `index.md` و فایل‌های تکمیلی پست خود ایجاد کنید.

محتوای موجود خود را از HackMD یا Google Docs کپی کنید و سپس آن را در
ویرایشگر جایگذاری کنید. جزئیات بیشتری درباره‌ی محتوای آن فایل در ادامه‌ی همین بخش
آمده است. فایل را مطابق با عنوان پیشنهادی پست وبلاگ نام‌گذاری کنید، اما
تاریخ را در نام فایل قرار ندهید. بازبینان وبلاگ با شما همکاری می‌کنند تا
نام نهایی فایل و تاریخ انتشار مقاله را تعیین کنند.

1. هنگامی که فایل را ذخیره می‌کنید، GitHub شما را در فرایند pull request
   راهنمایی می‌کند.

1. همیار نگارش شما می‌تواند مطلب ارسالی شما را بازبینی کند و در زمینه‌ی بازخوردها
   و جزئیات نهایی با شما همکاری کند. یک ویراستار وبلاگ pull request شما را برای ادغام، به‌عنوان
   پیش‌نویسی که هنوز زمان‌بندی نشده است، تأیید می‌کند.

#### Front matter

فایل Markdown که می‌نویسید باید از
[front matter](https://gohugo.io/content-management/front-matter/) مربوط به Hugo با قالب YAML استفاده کند.

در اینجا یک مثال آمده است:

```yaml
---
layout: blog
title: "Your Title Here"
draft: true # will be changed to date: YYYY-MM-DD before publication
slug: lowercase-text-for-link-goes-here-no-spaces # optional
author: >
  Author-1 (Affiliation),
  Author-2 (Affiliation),
  Author-3 (Affiliation)
---
```

- در ابتدا، تاریخی برای مقاله تعیین نکنید و هیچ جانگهدار تاریخی را
  در front matter قرار ندهید (این‌گونه عمل نکنید ~~`date: XXXX-XX-XX`~~)
- با این حال، مقاله را به‌عنوان پیش‌نویس تنظیم کنید (`draft: true` را در
  [front matter](https://gohugo.io/content-management/front-matter/) مقاله قرار دهید)

#### محتوای مقاله

مطمئن شوید که از عنوان‌های سطح دوم Markdown (`##` نه `#`) به‌عنوان بالاترین
سطح عنوان در مقاله استفاده می‌کنید. `title` که در front matter تنظیم می‌کنید،
عنوان سطح اول آن صفحه می‌شود.

باید از
[راهنمای سبک](https://kubernetes.io/docs/contribute/style/style-guide/) پیروی کنید، اما
با استثناهای زیر:

- مشکلی نداریم که نویسندگان مقاله را با سبک نگارش خودشان بنویسند، به شرط آنکه
  بیشتر خوانندگان بتوانند نکته‌ی مطرح‌شده را دنبال کنند
- استفاده از «ما» در مقاله‌ی وبلاگی که چند نویسنده دارد، یا مقاله‌ای که
  مقدمه‌اش به‌روشنی نشان می‌دهد نویسنده از طرف یک گروه مشخص می‌نویسد،
  اشکالی ندارد. همان‌طور که از همین بخش متوجه خواهید شد، اگرچه ما در
  مستندات خود [از به‌کاربردن «ما» پرهیز می‌کنیم](/docs/contribute/style/style-guide/#avoid-using-we)،
  ایجاد استثناهای موجه اشکالی ندارد.
- از به‌کاربردن shortcodeهای کوبرنتیز برای کادرهای تذکر (مانند
  `{{</* caution */>}}`) پرهیز می‌کنیم. دلیل این است که کادرهای تذکر برای خوانندگان
  مستندات در نظر گرفته شده‌اند و مقالات وبلاگ مستندات نیستند.
- بیان مطالبی درباره‌ی آینده اشکالی ندارد، هرچند در اعلان‌های رسمی
  از طرف کوبرنتیز با احتیاط از آن‌ها استفاده می‌کنیم
- نمونه‌کدهایی که در مقالات وبلاگ استفاده می‌شوند نیازی به استفاده از
  shortcode `{{</* code_sample */>}}` ندارند، و اغلب بهتر است (نگهداری‌شان
  آسان‌تر است) که از آن استفاده نکنند

#### نمودارها و تصاویر {#illustrations}

برای تصاویر، نمودارها یا چارت‌ها، در صورت امکان می‌توان از
[shortcode مربوط به figure](https://gohugo.io/content-management/shortcodes/#figure)
استفاده کرد. برای دسترس‌پذیری باید ویژگی `alt` را تنظیم کنید.

برای تصاویر و نمودارهای فنی، تلاش کنید از گرافیک برداری استفاده کنید. تیم وبلاگ
SVG را بر قالب‌های نمودار شطرنجی (bitmap / pixel) ترجیح می‌دهد و همچنین
SVG را به جای Mermaid توصیه می‌کند (همچنان می‌توانید منبع Mermaid را در یک
توضیح (comment) نگه دارید). ترجیح SVG بر Mermaid به این دلیل است که هنگامی که نگهدارندگان
Mermaid را ارتقا می‌دهند یا تغییراتی در نمایش نمودارها ایجاد می‌کنند، ممکن است راه آسانی
برای تماس با نویسنده‌ی اصلی مقاله‌ی وبلاگ برای بررسی درستی تغییرات
نداشته باشند.

[راهنمای نمودار](/docs/contribute/style/diagram-guide/) برای
مستندات کوبرنتیز در نظر گرفته شده است، نه مقالات وبلاگ. همسویی با آن همچنان خوب است،
اما:

- نیازی به عنوان‌گذاری نمودارها به‌صورت شکل ۱، شکل ۲ و غیره نیست.

الزام به استفاده از تصاویر مقیاس‌پذیر (برداری) فرایند ارسال مقاله را برای افرادی که آشنایی کمتری دارند
دشوارتر می‌کند؛ SIG Docs کوبرنتیز همچنان به دنبال راه‌هایی برای پایین‌آوردن این مانع است.
اگر ایده‌ای برای کاهش این مانع دارید،
لطفاً داوطلبانه کمک کنید.

برای سایر تصاویر (مانند عکس‌ها)، تیم وبلاگ اکیداً استفاده از
ویژگی‌های `alt` را تشویق می‌کند. اگر نرم‌افزارهای دسترس‌پذیری اصلاً نباید به تصویر اشاره کنند، استفاده از ویژگی `alt` خالی
اشکالی ندارد، اما این وضعیتی نادر است.

#### پیام‌های commit

در زمانی که pull request خود را آماده‌ی بازبینی علامت‌گذاری می‌کنید، هر پیام commit
باید خلاصه‌ای کوتاه از کار انجام‌شده باشد. نخستین پیام commit
باید به‌عنوان توضیح کلی پست وبلاگ معنادار باشد.

نمونه‌هایی از پیام commit خوب:

- _Add blog post on the foo kubernetes feature_
- _blog: foobar announcement_

نمونه‌هایی از پیام‌های commit بد:

- _Placeholder commit for announcement about foo_
- _Add blog post_
- _asdf_
- _initial commit_
- _draft post_

#### Squash کردن

هنگامی که فکر می‌کنید مقاله آماده‌ی ادغام است، باید commitهای
pull request خود را [squash](https://www.k8s.dev/docs/guide/pull-requests/#squashing) کنید؛
اگر نمی‌دانید چگونه، اشکالی ندارد که از تیم وبلاگ کمک بخواهید.
