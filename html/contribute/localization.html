بومی‌سازی مستندات کوبرنتیز

این صفحه به شما نشان می‌دهد که چگونه مستندات را برای یک زبان دیگر بومی‌سازی کنید.

مشارکت در یک بومی‌سازی موجود

می‌توانید به افزودن یا بهبود محتوای یک بومی‌سازی موجود کمک کنید. در Slack کوبرنتیز برای هر بومی‌سازی یک کانال وجود دارد. همچنین یک کانال Slack عمومی SIG Docs Localizations نیز وجود دارد که می‌توانید در آن سلام و احوال‌پرسی کنید.

توجه:

برای جزئیات بیشتر درباره نحوه مشارکت در یک بومی‌سازی مشخص، به‌دنبال نسخه بومی‌سازی‌شده این صفحه بگردید.

یافتن کد دوحرفی زبان خود

ابتدا به استاندارد ISO 639-1 مراجعه کنید تا کد دوحرفی زبان بومی‌سازی خود را پیدا کنید. برای مثال، کد دوحرفی زبان کره‌ای ko است.

برخی زبان‌ها در کنار کد زبان خود، از نسخه با حروف کوچک کد کشور بر اساس ISO-3166 نیز استفاده می‌کنند. برای مثال، کد زبان پرتغالی برزیلی pt-br است.

فورک و کلون کردن مخزن

ابتدا فورک شخصی خود را ایجاد کنید از مخزن kubernetes/website.

سپس فورک خود را کلون کنید و با cd وارد آن شوید:

git clone https://github.com/<username>/website
cd website

دایرکتوری محتوای وب‌سایت شامل زیردایرکتوری‌هایی برای هر زبان است. بومی‌سازی‌ای که می‌خواهید در آن کمک کنید در مسیر content/<two-letter-code> قرار دارد.

پیشنهاد تغییرات

صفحه بومی‌سازی‌شده مورد نظر خود را بر اساس نسخه اصلی انگلیسی ایجاد یا به‌روزرسانی کنید. برای جزئیات بیشتر، بومی‌سازی محتوا را ببینید.

اگر متوجه نادرستی فنی یا مشکل دیگری در مستندات بالادستی (انگلیسی) شدید، ابتدا باید مستندات بالادستی را اصلاح کنید و سپس همان اصلاح را با به‌روزرسانی بومی‌سازی‌ای که روی آن کار می‌کنید تکرار نمایید.

تغییرات در هر pull request را به یک بومی‌سازی محدود کنید. بازبینی pull requestهایی که محتوای چند بومی‌سازی را تغییر می‌دهند مشکل‌ساز است.

برای پیشنهاد تغییرات در آن بومی‌سازی، از راهنمای پیشنهاد بهبود محتوا پیروی کنید. این فرایند مشابه پیشنهاد تغییرات برای محتوای بالادستی (انگلیسی) است.

شروع یک بومی‌سازی جدید

اگر می‌خواهید مستندات کوبرنتیز به یک زبان جدید بومی‌سازی شود، کارهایی که باید انجام دهید به شرح زیر است.

از آنجا که مشارکت‌کنندگان نمی‌توانند pull requestهای خود را تأیید کنند، برای آغاز یک بومی‌سازی به حداقل دو مشارکت‌کننده نیاز دارید.

همه تیم‌های بومی‌سازی باید خودکفا باشند. وب‌سایت کوبرنتیز با کمال میل میزبان کار شماست، اما ترجمه آن و به‌روز نگه داشتن محتوای بومی‌سازی‌شده موجود بر عهده شماست.

باید کد دوحرفی زبان خود را بدانید. برای یافتن کد دوحرفی زبان بومی‌سازی خود به استاندارد ISO 639-1 مراجعه کنید. برای مثال، کد دوحرفی زبان کره‌ای ko است.

اگر زبانی که برای آن بومی‌سازی را آغاز می‌کنید در مناطق مختلفی صحبت می‌شود و تفاوت‌های قابل‌توجهی میان گونه‌های آن وجود دارد، ممکن است منطقی باشد که کد کشور ISO-3166 با حروف کوچک را با کد دوحرفی زبان ترکیب کنید. برای مثال، پرتغالی برزیلی با کد pt-br بومی‌سازی می‌شود.

هنگامی که یک بومی‌سازی جدید را آغاز می‌کنید، باید تمام حداقل محتوای موردنیاز را بومی‌سازی کنید، پیش از آنکه پروژه کوبرنتیز بتواند تغییرات شما را در وب‌سایت زنده منتشر کند.

SIG Docs می‌تواند به شما کمک کند روی یک شاخه (branch) جداگانه کار کنید تا بتوانید گام‌به‌گام به آن هدف نزدیک شوید.

یافتن جامعه

به SIG Docs کوبرنتیز اطلاع دهید که علاقه‌مند به ایجاد یک بومی‌سازی هستید! به کانال Slack مربوط به SIG Docs و کانال Slack مربوط به SIG Docs Localizations بپیوندید. سایر تیم‌های بومی‌سازی با کمال میل به شما کمک می‌کنند کار را شروع کنید و به پرسش‌هایتان پاسخ می‌دهند.

همچنین لطفاً در جلسه زیرگروه بومی‌سازی SIG Docs شرکت کنید. مأموریت زیرگروه بومی‌سازی SIG Docs این است که در میان تیم‌های بومی‌سازی SIG Docs همکاری کند تا فرایندهای ایجاد راهنمای مشارکت بومی‌سازی‌شده تعریف و مستند شود. افزون بر این، زیرگروه بومی‌سازی SIG Docs به‌دنبال فرصت‌هایی برای ایجاد و اشتراک‌گذاری ابزارهای مشترک میان تیم‌های بومی‌سازی و شناسایی نیازمندی‌های جدید برای تیم رهبری SIG Docs است. اگر درباره این جلسه پرسشی دارید، لطفاً در کانال Slack مربوط به SIG Docs Localizations بپرسید.

همچنین می‌توانید برای بومی‌سازی خود یک کانال Slack در مخزن kubernetes/community ایجاد کنید. برای نمونه‌ای از افزودن یک کانال Slack، PR مربوط به افزودن یک کانال برای زبان فارسی را ببینید.

پیوستن به سازمان GitHub کوبرنتیز

پس از آنکه یک PR بومی‌سازی باز کردید، می‌توانید به عضویت سازمان GitHub کوبرنتیز درآیید. هر یک از اعضای تیم باید درخواست عضویت در سازمان خود را در مخزن kubernetes/org ایجاد کند.

افزودن تیم بومی‌سازی خود در GitHub

سپس تیم بومی‌سازی کوبرنتیز خود را به sig-docs/teams.yaml اضافه کنید. برای نمونه‌ای از افزودن یک تیم بومی‌سازی، PR مربوط به افزودن تیم بومی‌سازی اسپانیایی را ببینید.

اعضای @kubernetes/sig-docs-**-owners می‌توانند PRهایی را که محتوای درون دایرکتوری بومی‌سازی شما (و فقط درون آن) یعنی /content/**/ را تغییر می‌دهند تأیید کنند. برای هر بومی‌سازی، تیم @kubernetes/sig-docs-**-reviews تخصیص بازبین‌ها به PRهای جدید را خودکار می‌کند. اعضای @kubernetes/website-maintainers می‌توانند شاخه‌های بومی‌سازی جدید برای هماهنگی تلاش‌های ترجمه ایجاد کنند. اعضای @kubernetes/website-milestone-maintainers می‌توانند از دستور Prow با نام /milestone برای اختصاص یک milestone به issueها یا PRها استفاده کنند.

پیکربندی گردش کار

سپس یک برچسب GitHub برای بومی‌سازی خود در مخزن kubernetes/test-infra اضافه کنید. برچسب به شما امکان می‌دهد issueها و pull requestهای مربوط به زبان خود را فیلتر کنید.

برای نمونه‌ای از افزودن یک برچسب، PR مربوط به افزودن برچسب زبان ایتالیایی را ببینید.

تغییر پیکربندی سایت

وب‌سایت کوبرنتیز از Hugo به‌عنوان چارچوب وب خود استفاده می‌کند. پیکربندی Hugo وب‌سایت در فایل hugo.toml قرار دارد. برای پشتیبانی از یک بومی‌سازی جدید باید hugo.toml را تغییر دهید.

یک بلوک پیکربندی برای زبان جدید را به hugo.toml و زیر بلوک [languages] موجود اضافه کنید. برای مثال، بلوک زبان آلمانی به این صورت است:

[languages.de]
title = "Kubernetes"
languageName = "Deutsch (German)"
weight = 5
contentDir = "content/de"
languagedirection = "ltr"

[languages.de.params]
time_format_blog = "02.01.2006"
language_alternatives = ["en"]
description = "Produktionsreife Container-Orchestrierung"
languageNameLatinScript = "Deutsch"

نوار انتخاب زبان، مقدار languageName را فهرست می‌کند. برای languageName مقدار «نام زبان به خط بومی و زبان (نام انگلیسی زبان به خط لاتین)» را تعیین کنید. برای مثال، languageName = "한국어 (Korean)" یا languageName = "Deutsch (German)".

از languageNameLatinScript می‌توان برای دسترسی به نام زبان به خط لاتین و استفاده از آن در پوسته (theme) بهره برد. برای languageNameLatinScript مقدار «نام زبان به خط لاتین» را تعیین کنید. برای مثال، languageNameLatinScript ="Korean" یا languageNameLatinScript = "Deutsch".

پارامتر weight ترتیب زبان‌ها را در نوار انتخاب زبان تعیین می‌کند. وزن کمتر اولویت بیشتری دارد و باعث می‌شود زبان در ابتدا نمایش داده شود. هنگام تعیین پارامتر weight، مهم است که بلوک زبان‌های موجود را بررسی کنید و وزن آن‌ها را چنان تنظیم کنید که نسبت به همه زبان‌ها، از جمله هر زبان تازه‌افزوده‌شده، به‌صورت مرتب باقی بمانند.

برای اطلاعات بیشتر درباره پشتیبانی چندزبانه Hugo، به «Multilingual Mode» مراجعه کنید.

افزودن یک دایرکتوری بومی‌سازی جدید

یک زیردایرکتوری مخصوص زبان را به پوشه content در مخزن اضافه کنید. برای مثال، کد دوحرفی زبان آلمانی de است:

mkdir content/de

همچنین باید یک دایرکتوری درون i18n برای رشته‌های بومی‌سازی‌شده ایجاد کنید؛ برای نمونه به بومی‌سازی‌های موجود نگاه کنید.

برای مثال، برای زبان آلمانی رشته‌ها در i18n/de/de.toml قرار دارند.

بومی‌سازی آیین‌نامه رفتار جامعه

یک PR به مخزن cncf/foundation باز کنید تا آیین‌نامه رفتار (code of conduct) به زبان شما اضافه شود.

تنظیم فایل‌های OWNERS

برای تعیین نقش هر کاربری که در بومی‌سازی مشارکت می‌کند، یک فایل OWNERS درون زیردایرکتوری مخصوص زبان با محتوای زیر ایجاد کنید:

  • reviewers: فهرستی از تیم‌های کوبرنتیز با نقش بازبین، که در اینجا
  • همان تیم sig-docs-**-reviews است که در افزودن تیم بومی‌سازی خود در GitHub ایجاد شد.
  • approvers: فهرستی از تیم‌های کوبرنتیز با نقش تأییدکننده، که در اینجا
  • همان تیم sig-docs-**-owners است که در افزودن تیم بومی‌سازی خود در GitHub ایجاد شد.
  • labels: فهرستی از برچسب‌های GitHub که به‌طور خودکار به یک PR اعمال می‌شوند؛ در اینجا برچسب زبانی است که در پیکربندی گردش کار ایجاد شد.

اطلاعات بیشتر درباره فایل OWNERS در go.k8s.io/owners موجود است.

فایل OWNERS اسپانیایی، با کد زبان es، به این صورت است:

# See the OWNERS docs at https://go.k8s.io/owners

# This is the localization project for Spanish.
# Teams and members are visible at https://github.com/orgs/kubernetes/teams.

reviewers:
- sig-docs-es-reviews

approvers:
- sig-docs-es-owners

labels:
- area/localization
- language/es

پس از افزودن فایل OWNERS مخصوص زبان، فایل OWNERS_ALIASES ریشه را با تیم‌های جدید کوبرنتیز برای بومی‌سازی، یعنی sig-docs-**-owners و sig-docs-**-reviews، به‌روزرسانی کنید.

برای هر تیم، فهرست کاربران GitHub درخواست‌شده در افزودن تیم بومی‌سازی خود در GitHub را به ترتیب حروف الفبا اضافه کنید.

--- a/OWNERS_ALIASES
+++ b/OWNERS_ALIASES
@@ -48,6 +48,14 @@ aliases:

باز کردن یک pull request

سپس یک pull request باز کنید (PR) تا یک بومی‌سازی به مخزن kubernetes/website اضافه شود. PR باید شامل تمام حداقل محتوای موردنیاز باشد تا بتواند تأیید شود.

برای نمونه‌ای از افزودن یک بومی‌سازی جدید، PR مربوط به فعال‌سازی مستندات به زبان فرانسوی را ببینید.

افزودن یک فایل README بومی‌سازی‌شده

برای راهنمایی سایر مشارکت‌کنندگان بومی‌سازی، یک فایل جدید README-**.md را به سطح بالای kubernetes/website اضافه کنید، که در آن ** کد دوحرفی زبان است. برای مثال، فایل README آلمانی README-de.md خواهد بود.

مشارکت‌کنندگان بومی‌سازی را در فایل README-**.md بومی‌سازی‌شده راهنمایی کنید. همان اطلاعات موجود در README.md را به‌علاوه موارد زیر درج کنید:

  • یک نقطه تماس برای پروژه بومی‌سازی
  • هر اطلاعات مختص بومی‌سازی

پس از ایجاد README بومی‌سازی‌شده، پیوندی به این فایل را در README.md اصلی انگلیسی اضافه کنید و اطلاعات تماس را به زبان انگلیسی درج نمایید. می‌توانید یک شناسه GitHub، نشانی ایمیل، کانال Slack یا روش تماس دیگری ارائه دهید. همچنین باید پیوندی به آیین‌نامه رفتار جامعه بومی‌سازی‌شده خود ارائه کنید.

راه‌اندازی بومی‌سازی جدید شما

هنگامی که یک بومی‌سازی الزامات گردش کار و حداقل خروجی را برآورده کند، SIG Docs اقدامات زیر را انجام می‌دهد:

  • انتخاب زبان را در وب‌سایت فعال می‌کند.
  • در دسترس بودن بومی‌سازی را از طریق کانال‌های بنیاد Cloud Native Computing Foundation (CNCF)، از جمله وبلاگ کوبرنتیز، اطلاع‌رسانی می‌کند.

بومی‌سازی محتوا

بومی‌سازی همه مستندات کوبرنتیز کاری عظیم است. اشکالی ندارد که با مقیاس کوچک شروع کنید و به‌مرور آن را گسترش دهید.

حداقل محتوای موردنیاز

همه بومی‌سازی‌ها دست‌کم باید شامل موارد زیر باشند:

شرح نشانی‌ها (URLs)
صفحه اصلی نشانی همه سرفصل‌ها و زیرسرفصل‌ها
راه‌اندازی نشانی همه سرفصل‌ها و زیرسرفصل‌ها
آموزش‌ها مبانی کوبرنتیز، Hello Minikube
رشته‌های سایت همه رشته‌های سایت در یک فایل TOML بومی‌سازی‌شده جدید
نسخه‌ها نشانی همه سرفصل‌ها و زیرسرفصل‌ها

اسناد ترجمه‌شده باید در زیردایرکتوری content/**/ مخصوص خود قرار گیرند، اما در غیر این صورت از همان مسیر URL منبع انگلیسی پیروی کنند. برای مثال، برای آماده‌سازی آموزش مبانی کوبرنتیز جهت ترجمه به آلمانی، یک زیردایرکتوری در دایرکتوری content/de/ ایجاد کنید و منبع یا دایرکتوری انگلیسی را کپی نمایید:

mkdir -p content/de/docs/tutorials
cp -ra content/en/docs/tutorials/kubernetes-basics/ content/de/docs/tutorials/

ابزارهای ترجمه می‌توانند فرایند ترجمه را تسریع کنند. برای مثال، برخی ویرایشگرها افزونه‌هایی برای ترجمه سریع متن ارائه می‌دهند.

احتیاط:

ترجمه ماشینی به‌تنهایی کافی نیست. بومی‌سازی برای رسیدن به حداقل استانداردهای کیفیت به بازبینی گسترده انسانی نیاز دارد.

برای اطمینان از درستی دستور زبان و معنا، اعضای تیم بومی‌سازی شما باید پیش از انتشار، تمام ترجمه‌های ماشینی را با دقت بازبینی کنند.

بومی‌سازی تصاویر SVG

پروژه کوبرنتیز توصیه می‌کند در هر جا که ممکن است از تصاویر برداری (SVG) استفاده شود، زیرا ویرایش آن‌ها برای تیم بومی‌سازی بسیار آسان‌تر است. اگر به یک تصویر شطرنجی (raster) برخوردید که نیاز به بومی‌سازی دارد، ابتدا بازطراحی نسخه انگلیسی به‌صورت تصویر برداری و سپس بومی‌سازی آن را در نظر بگیرید.

هنگام ترجمه متن درون تصاویر SVG (Scalable Vector Graphics)، لازم است از رهنمودهای مشخصی پیروی کنید تا دقت حفظ شود و یکپارچگی میان نسخه‌های زبانی مختلف برقرار بماند. تصاویر SVG معمولاً در مستندات کوبرنتیز برای نمایش مفاهیم، گردش‌های کار و نمودارها استفاده می‌شوند.

  1. شناسایی متن قابل ترجمه: با شناسایی عناصر متنی درون تصویر SVG که باید ترجمه شوند آغاز کنید. این عناصر معمولاً شامل برچسب‌ها، شرح‌ها، حاشیه‌نویسی‌ها (annotation) یا هر متنی هستند که اطلاعاتی را منتقل می‌کند.

  2. ویرایش فایل‌های SVG: فایل‌های SVG مبتنی بر XML هستند، به این معنا که می‌توان آن‌ها را با یک ویرایشگر متن ویرایش کرد. با این حال، باید توجه داشت که بیشتر تصاویر مستندات در کوبرنتیز برای پرهیز از مشکلات سازگاری فونت، متن را از پیش به منحنی تبدیل کرده‌اند. در چنین مواردی توصیه می‌شود برای ویرایش از نرم‌افزار تخصصی ویرایش SVG مانند Inkscape استفاده کنید، فایل SVG را باز کنید و عناصر متنی که نیاز به ترجمه دارند را پیدا نمایید.

  3. ترجمه متن: متن اصلی را با نسخه ترجمه‌شده به زبان موردنظر جایگزین کنید. مطمئن شوید متن ترجمه‌شده معنای موردنظر را به‌درستی منتقل می‌کند و در فضای موجود تصویر جا می‌شود. برای زبان‌هایی که از الفبای لاتین استفاده می‌کنند، باید از خانواده فونت Open Sans استفاده شود. می‌توانید فونت Open Sans را از اینجا دریافت کنید: Open Sans Typeface.

  4. تبدیل متن به منحنی: همان‌طور که پیش‌تر اشاره شد، برای رفع مشکلات سازگاری فونت توصیه می‌شود متن ترجمه‌شده به منحنی یا مسیر (path) تبدیل شود. تبدیل متن به منحنی تضمین می‌کند که تصویر نهایی متن ترجمه‌شده را به‌درستی نمایش دهد، حتی اگر سیستم کاربر فونت دقیقی را که در SVG اصلی استفاده شده است نداشته باشد.

  5. بازبینی و آزمایش: پس از انجام ترجمه‌های لازم و تبدیل متن به منحنی، تصویر SVG به‌روزشده را ذخیره و بازبینی کنید تا مطمئن شوید متن به‌درستی نمایش داده می‌شود و تراز است. بخش پیش‌نمایش محلی تغییرات خود را بررسی کنید.

فایل‌های منبع

بومی‌سازی‌ها باید بر پایه فایل‌های انگلیسیِ یک نسخه مشخص باشند که تیم بومی‌سازی آن را هدف قرار داده است. هر تیم بومی‌سازی می‌تواند تصمیم بگیرد کدام نسخه را هدف قرار دهد؛ این نسخه در ادامه نسخه هدف نامیده می‌شود.

برای یافتن فایل‌های منبع نسخه هدف خود:

  1. به مخزن وب‌سایت کوبرنتیز در نشانی https://github.com/kubernetes/website بروید.

  2. از جدول زیر، شاخه (branch) مربوط به نسخه هدف خود را انتخاب کنید:

نسخه هدف شاخه
آخرین نسخه main
نسخه قبلی release-1.37
نسخه بعدی dev-1.37

شاخه main شامل محتوای نسخه فعلی یعنی v1.37 است. تیم انتشار پیش از نسخه بعدی، یعنی v1.37، یک شاخه `` ایجاد می‌کند.

رشته‌های سایت در i18n

بومی‌سازی‌ها باید محتویات فایل i18n/en/en.toml را در یک فایل جدید مخصوص همان زبان داشته باشند. برای نمونه، برای زبان آلمانی: i18n/de/de.toml.

یک دایرکتوری و فایل بومی‌سازی جدید به i18n/ اضافه کنید. برای مثال، برای زبان آلمانی (de):

mkdir -p i18n/de
cp i18n/en/en.toml i18n/de/de.toml

توضیحات (comments) ابتدای فایل را متناسب با بومی‌سازی خود اصلاح کنید و سپس مقدار هر رشته را ترجمه کنید. برای مثال، متن جایگزین آلمانی‌زبانِ فرم جست‌وجو به این صورت است:

[ui_search]
other = "Suchen"

بومی‌سازی رشته‌های سایت به شما امکان می‌دهد متن‌ها و قابلیت‌های سراسری سایت را سفارشی کنید؛ برای مثال، متن حقوقی کپی‌رایت در پایین هر صفحه.

راهنمای بومی‌سازی مخصوص هر زبان

به عنوان یک تیم بومی‌سازی، می‌توانید با تهیه یک راهنمای بومی‌سازی مخصوص زبان خود، بهترین روش‌هایی را که تیمتان دنبال می‌کند رسمی و مدون کنید.

برای مثال، راهنمای بومی‌سازی کره‌ای را ببینید که شامل محتوایی درباره موضوعات زیر است:

  • ریتم اسپرینت‌ها و انتشارها
  • راهبرد شاخه‌ها
  • گردش کار pull request
  • راهنمای سبک نگارش
  • واژه‌نامه اصطلاحات بومی‌سازی‌شده و بومی‌سازی‌نشده
  • قراردادهای Markdown
  • اصطلاحات مربوط به آبجکت‌های API کوبرنتیز

جلسات Zoom مخصوص هر زبان

اگر پروژه بومی‌سازی به زمان جلسه جداگانه‌ای نیاز دارد، برای ایجاد یک جلسه Zoom تکرارشونده و دعوت‌نامه تقویم جدید با یکی از هم‌رئیس‌های (Co-Chair) SIG Docs یا Tech Lead تماس بگیرید. این کار تنها زمانی لازم است که تیم به‌اندازه کافی بزرگ باشد تا بتواند یک جلسه جداگانه را حفظ کند و به آن نیاز داشته باشد.

طبق سیاست CNCF، تیم‌های بومی‌سازی باید جلسات خود را در پلی‌لیست YouTube مربوط به SIG Docs بارگذاری کنند. تا زمانی که SIG Docs این فرایند را خودکار کند، یکی از هم‌رئیس‌های SIG Docs یا Tech Lead می‌تواند در این زمینه کمک کند.

راهبرد شاخه‌ها {#branch-strategy}

از آنجا که پروژه‌های بومی‌سازی تلاش‌هایی بسیار مشارکتی هستند، به تیم‌ها توصیه می‌کنیم در شاخه‌های بومی‌سازی مشترک کار کنند، به‌ویژه در آغاز کار و تا زمانی که بومی‌سازی هنوز منتشر نشده است.

برای همکاری روی یک شاخه بومی‌سازی:

  1. یکی از اعضای @kubernetes/website-maintainers یک شاخه بومی‌سازی را از یک شاخه منبع در https://github.com/kubernetes/website ایجاد می‌کند.

    تأییدکنندگان (approvers) تیم شما زمانی که تیم بومی‌سازی خود را اضافه کردید در مخزن kubernetes/org، به تیم @kubernetes/website-maintainers پیوستند.

    طرح نام‌گذاری شاخه زیر را پیشنهاد می‌کنیم:

    dev-<source version>-<language code>.<team milestone>

    برای مثال، یک approver در تیم بومی‌سازی آلمانی، شاخه بومی‌سازی dev-1.12-de.1 را بر پایه شاخه منبع مربوط به کوبرنتیز v1.12، مستقیماً در مخزن kubernetes/website ایجاد می‌کند.

  2. مشارکت‌کنندگان به‌صورت فردی شاخه‌های ویژگی (feature branch) را بر پایه شاخه بومی‌سازی ایجاد می‌کنند.

    برای مثال، یک مشارکت‌کننده آلمانی یک pull request با تغییرات برای kubernetes:dev-1.12-de.1 از username:local-branch-name باز می‌کند.

  3. approverها شاخه‌های ویژگی را بررسی می‌کنند و آن‌ها را در شاخه بومی‌سازی ادغام (merge) می‌کنند.

  4. به‌صورت دوره‌ای، یک approver با باز کردن و تأیید یک pull request جدید، شاخه بومی‌سازی را با شاخه منبع آن ادغام می‌کند. پیش از تأیید pull request حتماً کامیت‌ها را squash کنید.

در صورت نیاز، مراحل ۱ تا ۴ را تا زمان تکمیل بومی‌سازی تکرار کنید. برای مثال، شاخه‌های بومی‌سازی بعدیِ آلمانی به این صورت خواهند بود: dev-1.12-de.2، dev-1.12-de.3 و غیره.

تیم‌ها باید محتوای بومی‌سازی‌شده را در همان شاخه‌ای ادغام کنند که محتوا از آن گرفته شده است. برای مثال:

  • یک شاخه بومی‌سازی که از main گرفته شده است باید در main ادغام شود.
  • یک شاخه بومی‌سازی که از release- گرفته شده است باید در release- ادغام شود.
توجه:

اگر شاخه بومی‌سازی شما از شاخه main ایجاد شده است، اما پیش از ایجاد شاخه انتشار جدید در `main` ادغام نشده است، آن را هم در `main` و هم در شاخه انتشار جدید ادغام کنید. برای ادغام شاخه بومی‌سازی خود در شاخه انتشار جدید ، باید شاخه upstream مربوط به شاخه بومی‌سازی خود را به تغییر دهید.

در آغاز هر milestone تیم، مفید است که یک issue برای مقایسه تغییرات upstream میان شاخه بومی‌سازی قبلی و شاخه بومی‌سازی فعلی باز کنید. برای مقایسه تغییرات upstream دو اسکریپت وجود دارد.

  • upstream_changes.py برای بررسی تغییرات اعمال‌شده روی یک فایل مشخص مفید است. و
  • diff_l10n_branches.py برای ایجاد فهرستی از فایل‌های قدیمی‌شده (outdated) در یک شاخه بومی‌سازی مشخص مفید است.

اگرچه تنها approverها می‌توانند یک شاخه بومی‌سازی جدید باز کنند و pull requestها را ادغام کنند، هر کسی می‌تواند برای یک شاخه بومی‌سازی جدید pull request باز کند. هیچ مجوز ویژه‌ای لازم نیست.

برای اطلاعات بیشتر درباره کار با fork یا کار مستقیم از روی مخزن، به "fork و clone کردن مخزن" مراجعه کنید.
