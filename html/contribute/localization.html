بومی‌سازی مستندات کوبرنتیز

این صفحه نشان می‌دهد که چگونه می‌توانید مستندات را برای زبانی دیگر بومی‌سازی کنید.

مشارکت در یک بومی‌سازی موجود

می‌توانید در افزودن یا بهبود محتوای یک بومی‌سازی موجود کمک کنید. در Slack کوبرنتیز برای هر بومی‌سازی یک کانال وجود دارد. همچنین یک کانال عمومی با نام کانال Slack بومی‌سازی‌های SIG Docs نیز هست که می‌توانید در آن خودتان را معرفی کنید.

توجه:

برای جزئیات بیشتر دربارهٔ نحوهٔ مشارکت در یک بومی‌سازی خاص، نسخهٔ بومی‌شدهٔ این صفحه را جست‌وجو کنید.

کد دوحرفی زبان خود را پیدا کنید

ابتدا به استاندارد ISO 639-1 مراجعه کنید تا کد دوحرفی زبان بومی‌سازی خود را بیابید. برای مثال، کد دوحرفی زبان کره‌ای ko است.

برخی زبان‌ها علاوه بر کد زبان، از نسخهٔ حروف کوچکِ کد کشور مطابق استاندارد ISO-3166 نیز استفاده می‌کنند. برای مثال، کد زبان پرتغالی برزیلی pt-br است.

مخزن را فورک و کلون کنید

ابتدا از مخزن kubernetes/website فورک خودتان را بسازید.

سپس فورک خود را کلون کنید و با cd وارد آن شوید:

git clone https://github.com/<username>/website
cd website

پوشهٔ محتوای وب‌سایت برای هر زبان یک زیرپوشه دارد. بومی‌سازی‌ای که می‌خواهید در آن کمک کنید، در مسیر content/<two-letter-code> قرار دارد.

پیشنهاد تغییرات

صفحهٔ بومی‌شدهٔ مورد نظر خود را بر اساس نسخهٔ اصلی انگلیسی ایجاد یا به‌روزرسانی کنید. برای جزئیات بیشتر، بخش بومی‌سازی محتوا را ببینید.

اگر متوجه نادرستی فنی یا مشکل دیگری در مستندات بالادستی (انگلیسی) شدید، ابتدا باید مستندات بالادستی را اصلاح کنید و سپس همان اصلاح را با به‌روزرسانی بومی‌سازی‌ای که روی آن کار می‌کنید تکرار کنید.

تغییرات هر درخواست ادغام (pull request) را به یک بومی‌سازی محدود کنید. بازبینی درخواست‌های ادغامی که محتوای چند بومی‌سازی را تغییر می‌دهند، دشوار و مشکل‌ساز است.

برای پیشنهاد تغییرات در آن بومی‌سازی، از راهنمای پیشنهاد بهبود محتوا پیروی کنید. این فرایند مشابه پیشنهاد تغییرات در محتوای بالادستی (انگلیسی) است.

شروع یک بومی‌سازی جدید

اگر می‌خواهید مستندات کوبرنتیز به زبان جدیدی بومی‌سازی شود، باید کارهای زیر را انجام دهید.

از آنجا که مشارکت‌کنندگان نمی‌توانند درخواست‌های ادغام خودشان را تأیید کنند، برای شروع یک بومی‌سازی دست‌کم به دو مشارکت‌کننده نیاز دارید.

همهٔ تیم‌های بومی‌سازی باید خودکفا باشند. وب‌سایت کوبرنتیز با کمال میل میزبان کار شما خواهد بود، اما ترجمهٔ محتوا و به‌روز نگه داشتن محتوای بومی‌شدهٔ موجود بر عهدهٔ خود شماست.

باید کد دوحرفی زبان خود را بدانید. به استاندارد ISO 639-1 مراجعه کنید تا کد دوحرفی زبان بومی‌سازی خود را بیابید. برای مثال، کد دوحرفی زبان کره‌ای ko است.

اگر زبانی که بومی‌سازی آن را آغاز می‌کنید در مناطق مختلفی صحبت می‌شود و گونه‌های آن تفاوت‌های چشمگیری با هم دارند، شاید منطقی باشد که کد کشور ISO-3166 را با حروف کوچک با کد دوحرفی زبان ترکیب کنید. برای مثال، پرتغالی برزیلی با کد pt-br بومی‌سازی شده است.

هنگامی که بومی‌سازی جدیدی را آغاز می‌کنید، پیش از آنکه پروژهٔ کوبرنتیز بتواند تغییرات شما را در وب‌سایت اصلی منتشر کند، باید تمام حداقل محتوای لازم را بومی‌سازی کنید.

گروه SIG Docs می‌تواند به شما کمک کند تا روی یک شاخهٔ جداگانه کار کنید و به این ترتیب به‌تدریج به این هدف برسید.

جامعه را پیدا کنید

به SIG Docs کوبرنتیز اطلاع دهید که به ایجاد یک بومی‌سازی علاقه دارید! به کانال Slack گروه SIG Docs و کانال Slack بومی‌سازی‌های SIG Docs بپیوندید. سایر تیم‌های بومی‌سازی با کمال میل در شروع کار به شما کمک می‌کنند و به پرسش‌هایتان پاسخ می‌دهند.

همچنین شرکت در جلسهٔ زیرگروه بومی‌سازی SIG Docs را نیز در نظر بگیرید. مأموریت زیرگروه بومی‌سازی SIG Docs، همکاری میان تیم‌های بومی‌سازی SIG Docs برای تعریف و مستندسازی فرایندهای ایجاد راهنماهای مشارکت بومی‌شده است. افزون بر این، زیرگروه بومی‌سازی SIG Docs به دنبال فرصت‌هایی برای ساخت و اشتراک‌گذاری ابزارهای مشترک میان تیم‌های بومی‌سازی و شناسایی نیازمندی‌های جدید برای تیم رهبری SIG Docs است. اگر دربارهٔ این جلسه پرسشی دارید، آن را در کانال Slack بومی‌سازی‌های SIG Docs مطرح کنید.

همچنین می‌توانید در مخزن kubernetes/community یک کانال Slack برای بومی‌سازی خود ایجاد کنید. برای نمونه‌ای از افزودن کانال Slack، درخواست ادغام افزودن کانال برای زبان فارسی را ببینید.

به سازمان GitHub کوبرنتیز بپیوندید

پس از آنکه یک درخواست ادغام بومی‌سازی باز کردید، می‌توانید عضو سازمان GitHub کوبرنتیز شوید. هر یک از اعضای تیم باید در مخزن kubernetes/org درخواست عضویت در سازمان مخصوص به خود را ایجاد کند.

تیم بومی‌سازی خود را در GitHub اضافه کنید

سپس تیم بومی‌سازی کوبرنتیز خود را به فایل sig-docs/teams.yaml اضافه کنید. برای نمونه‌ای از افزودن تیم بومی‌سازی، درخواست ادغام مربوط به افزودن تیم بومی‌سازی اسپانیایی را ببینید.

اعضای @kubernetes/sig-docs-**-owners می‌توانند درخواست‌های ادغامی را تأیید کنند که محتوای داخل پوشهٔ بومی‌سازی شما، یعنی /content/**/، را تغییر می‌دهند (و فقط همین پوشه را). برای هر بومی‌سازی، تیم @kubernetes/sig-docs-**-reviews تخصیص بازبین برای درخواست‌های ادغام جدید را خودکار می‌کند. اعضای @kubernetes/website-maintainers می‌توانند برای هماهنگ کردن کارهای ترجمه، شاخه‌های بومی‌سازی جدید ایجاد کنند. اعضای @kubernetes/website-milestone-maintainers می‌توانند با استفاده از فرمان Prow با نام /milestone، یک نقطهٔ عطف (milestone) را به issueها یا درخواست‌های ادغام اختصاص دهند.

گردش کار را پیکربندی کنید

سپس در مخزن kubernetes/test-infra یک برچسب GitHub برای بومی‌سازی خود اضافه کنید. با این برچسب می‌توانید issueها و درخواست‌های ادغام مربوط به زبان خاص خود را فیلتر کنید.

برای نمونه‌ای از افزودن برچسب، درخواست ادغام مربوط به افزودن برچسب زبان ایتالیایی را ببینید.

پیکربندی سایت را تغییر دهید

وب‌سایت کوبرنتیز از Hugo به‌عنوان چارچوب وب خود استفاده می‌کند. پیکربندی Hugo وب‌سایت در فایل hugo.toml قرار دارد. برای پشتیبانی از بومی‌سازی جدید باید فایل hugo.toml را تغییر دهید.

یک بلوک پیکربندی برای زبان جدید، زیر بلوک موجود [languages] در فایل hugo.toml اضافه کنید. برای مثال، بلوک زبان آلمانی به این شکل است:

[languages.de]
title = "Kubernetes"
languageName = "Deutsch (German)"
weight = 5
contentDir = "content/de"
languagedirection = "ltr"

[languages.de.params]
time_format_blog = "02.01.2006"
language_alternatives = ["en"]
description = "Produktionsreife Container-Orchestrierung"
languageNameLatinScript = "Deutsch"

نوار انتخاب زبان، مقدار languageName را فهرست می‌کند. مقدار «نام زبان به خط بومی و (نام انگلیسی زبان به خط لاتین)» را به languageName اختصاص دهید. برای مثال، languageName = "한국어 (Korean)" یا languageName = "Deutsch (German)".

از languageNameLatinScript می‌توان برای دسترسی به نام زبان به خط لاتین و استفاده از آن در پوسته (theme) بهره برد. مقدار «نام زبان به خط لاتین» را به languageNameLatinScript اختصاص دهید. برای مثال، languageNameLatinScript ="Korean" یا languageNameLatinScript = "Deutsch".

پارامتر weight ترتیب زبان‌ها را در نوار انتخاب زبان تعیین می‌کند. وزن کمتر اولویت بالاتری دارد و باعث می‌شود آن زبان زودتر نمایش داده شود. هنگام تعیین پارامتر weight، مهم است که بلوک زبان‌های موجود را بررسی کنید و وزن آن‌ها را طوری تنظیم کنید که نسبت به همهٔ زبان‌ها، از جمله زبان تازه‌افزوده‌شده، به ترتیب مرتب باشند.

برای اطلاعات بیشتر دربارهٔ پشتیبانی Hugo از چندزبانگی، بخش «Multilingual Mode» را ببینید.

یک پوشهٔ بومی‌سازی جدید اضافه کنید

یک زیرپوشهٔ مخصوص زبان را به پوشهٔ content در مخزن اضافه کنید. برای مثال، کد دوحرفی زبان آلمانی de است:

mkdir content/de

همچنین باید برای رشته‌های بومی‌شده یک پوشه درون i18n ایجاد کنید؛ برای نمونه، به بومی‌سازی‌های موجود نگاه کنید.

برای مثال، رشته‌های زبان آلمانی در i18n/de/de.toml قرار دارند.

آیین‌نامهٔ رفتاری جامعه را بومی‌سازی کنید

یک درخواست ادغام در مخزن cncf/foundation باز کنید تا آیین‌نامهٔ رفتاری به زبان شما اضافه شود.

فایل‌های OWNERS را راه‌اندازی کنید

برای تعیین نقش هر کاربری که در بومی‌سازی مشارکت می‌کند، یک فایل OWNERS درون زیرپوشهٔ مخصوص زبان با محتوای زیر ایجاد کنید:

  • reviewers: فهرستی از تیم‌های کوبرنتیز با نقش بازبین؛ در این مورد،
  • تیم sig-docs-**-reviews که در بخش تیم بومی‌سازی خود را در GitHub اضافه کنید ایجاد شد.
  • approvers: فهرستی از تیم‌های کوبرنتیز با نقش تأییدکننده؛ در این مورد،
  • تیم sig-docs-**-owners که در بخش تیم بومی‌سازی خود را در GitHub اضافه کنید ایجاد شد.
  • labels: فهرستی از برچسب‌های GitHub که به‌طور خودکار روی درخواست ادغام اعمال می‌شوند؛ در این مورد، برچسب زبانی که در بخش گردش کار را پیکربندی کنید ایجاد شد.

اطلاعات بیشتر دربارهٔ فایل OWNERS را می‌توانید در go.k8s.io/owners بیابید.

فایل OWNERS زبان اسپانیایی با کد زبان es به این شکل است:

# See the OWNERS docs at https://go.k8s.io/owners

# This is the localization project for Spanish.
# Teams and members are visible at https://github.com/orgs/kubernetes/teams.

reviewers:
- sig-docs-es-reviews

approvers:
- sig-docs-es-owners

labels:
- area/localization
- language/es

پس از افزودن فایل OWNERS مخصوص زبان، فایل OWNERS_ALIASES در ریشهٔ مخزن را با تیم‌های جدید کوبرنتیز برای بومی‌سازی، یعنی sig-docs-**-owners و sig-docs-**-reviews، به‌روزرسانی کنید.

برای هر تیم، فهرست کاربران GitHub درخواست‌شده در بخش تیم بومی‌سازی خود را در GitHub اضافه کنید را به ترتیب الفبایی اضافه کنید.

+++ b/OWNERS_ALIASES
@@ -48,6 +48,14 @@ aliases:
     - stewart-yu

یک درخواست ادغام باز کنید

سپس برای افزودن بومی‌سازی به مخزن kubernetes/website، یک درخواست ادغام باز کنید (PR). این درخواست ادغام پیش از تأیید باید تمام حداقل محتوای لازم را در بر داشته باشد.

برای نمونه‌ای از افزودن بومی‌سازی جدید، درخواست ادغام مربوط به فعال‌سازی مستندات به زبان فرانسوی را ببینید.

یک فایل README بومی‌شده اضافه کنید

برای راهنمایی سایر مشارکت‌کنندگان بومی‌سازی، یک فایل جدید README-**.md به سطح بالای مخزن kubernetes/website اضافه کنید که در آن ** کد دوحرفی زبان است. برای مثال، فایل README زبان آلمانی README-de.md خواهد بود.

مشارکت‌کنندگان بومی‌سازی را در فایل بومی‌شدهٔ README-**.md راهنمایی کنید. همان اطلاعات موجود در README.md را به همراه موارد زیر در آن بگنجانید:

  • یک فرد رابط برای پروژهٔ بومی‌سازی
  • هرگونه اطلاعات مختص به آن بومی‌سازی

پس از ایجاد فایل README بومی‌شده، از فایل اصلی انگلیسی README.md پیوندی به آن اضافه کنید و اطلاعات تماس را به زبان انگلیسی درج کنید. می‌توانید شناسهٔ GitHub، نشانی ایمیل، کانال Slack یا روش تماس دیگری ارائه دهید. همچنین باید پیوندی به آیین‌نامهٔ رفتاری جامعهٔ بومی‌شدهٔ خود ارائه کنید.

بومی‌سازی جدید خود را راه‌اندازی کنید

هنگامی که یک بومی‌سازی الزامات مربوط به گردش کار و حداقل خروجی را برآورده کند، گروه SIG Docs کارهای زیر را انجام می‌دهد:

  • انتخاب آن زبان را در وب‌سایت فعال می‌کند.
  • در دسترس بودن بومی‌سازی را از طریق کانال‌های بنیاد رایانش ابری بومی (CNCF)، از جمله وبلاگ کوبرنتیز، اطلاع‌رسانی می‌کند.

بومی‌سازی محتوا

بومی‌سازی تمام مستندات کوبرنتیز کاری بسیار بزرگ است. اشکالی ندارد که کار را در مقیاس کوچک آغاز کنید و به مرور زمان گسترش دهید.

حداقل محتوای لازم

همهٔ بومی‌سازی‌ها دست‌کم باید موارد زیر را در بر داشته باشند:

توضیحات نشانی‌ها
صفحهٔ اصلی نشانی همهٔ عنوان‌ها و زیرعنوان‌ها
راه‌اندازی نشانی همهٔ عنوان‌ها و زیرعنوان‌ها
آموزش‌ها مبانی کوبرنتیز، سلام Minikube
رشته‌های سایت همهٔ رشته‌های سایت در یک فایل TOML بومی‌شدهٔ جدید
انتشارها نشانی همهٔ عنوان‌ها و زیرعنوان‌ها

اسناد ترجمه‌شده باید در زیرپوشهٔ content/**/ مخصوص به خود قرار گیرند، اما در سایر موارد از همان مسیر نشانی منبع انگلیسی پیروی کنند. برای مثال، برای آماده کردن آموزش مبانی کوبرنتیز جهت ترجمه به آلمانی، یک زیرپوشه زیر پوشهٔ content/de/ ایجاد کنید و فایل یا پوشهٔ منبع انگلیسی را در آن کپی کنید:

mkdir -p content/de/docs/tutorials
cp -ra content/en/docs/tutorials/kubernetes-basics/ content/de/docs/tutorials/

ابزارهای ترجمه می‌توانند فرایند ترجمه را سرعت ببخشند. برای مثال، برخی ویرایشگرها افزونه‌هایی برای ترجمهٔ سریع متن ارائه می‌کنند.

احتیاط:

ترجمهٔ ماشینی به‌تنهایی کافی نیست. بومی‌سازی برای رسیدن به حداقل استانداردهای کیفیت به بازبینی گستردهٔ انسانی نیاز دارد.

برای اطمینان از درستی دستور زبان و معنا، اعضای تیم بومی‌سازی شما باید پیش از انتشار، همهٔ ترجمه‌های ماشینی را با دقت بازبینی کنند.

بومی‌سازی تصاویر SVG

پروژهٔ کوبرنتیز توصیه می‌کند تا جای ممکن از تصاویر برداری (SVG) استفاده شود، زیرا ویرایش این تصاویر برای تیم بومی‌سازی بسیار آسان‌تر است. اگر به تصویری شطرنجی (raster) برخوردید که نیاز به بومی‌سازی دارد، بهتر است ابتدا نسخهٔ انگلیسی آن را به‌صورت تصویر برداری بازترسیم کنید و سپس آن را بومی‌سازی کنید.

هنگام ترجمهٔ متن درون تصاویر SVG (Scalable Vector Graphics)، پیروی از برخی رهنمودها برای حفظ دقت و یکپارچگی میان نسخه‌های زبانی مختلف ضروری است. تصاویر SVG در مستندات کوبرنتیز معمولاً برای نمایش مفاهیم، گردش‌های کاری و نمودارها به کار می‌روند.

  1. شناسایی متن قابل ترجمه: ابتدا عناصر متنی درون تصویر SVG را که باید ترجمه شوند شناسایی کنید. این عناصر معمولاً شامل برچسب‌ها، زیرنویس‌ها، یادداشت‌ها یا هر متنی است که اطلاعاتی را منتقل می‌کند.

  2. ویرایش فایل‌های SVG: فایل‌های SVG مبتنی بر XML هستند و بنابراین می‌توان آن‌ها را با یک ویرایشگر متن ویرایش کرد. با این حال، باید توجه داشت که در بیشتر تصاویر مستندات کوبرنتیز، متن برای جلوگیری از مشکلات سازگاری فونت از پیش به منحنی تبدیل شده است. در چنین مواردی توصیه می‌شود برای ویرایش از نرم‌افزارهای تخصصی ویرایش SVG مانند Inkscape استفاده کنید؛ فایل SVG را باز کنید و عناصر متنی نیازمند ترجمه را پیدا کنید.

  3. ترجمهٔ متن: متن اصلی را با نسخهٔ ترجمه‌شده به زبان مورد نظر جایگزین کنید. مطمئن شوید که متن ترجمه‌شده معنای مورد نظر را به‌درستی منتقل می‌کند و در فضای موجود در تصویر جا می‌شود. برای زبان‌هایی که از الفبای لاتین استفاده می‌کنند، باید از خانوادهٔ فونت Open Sans بهره گرفت. می‌توانید حروف‌نگاشت Open Sans را از اینجا دریافت کنید: حروف‌نگاشت Open Sans.

  4. تبدیل متن به منحنی: همان‌طور که پیش‌تر اشاره شد، برای رفع مشکلات سازگاری فونت توصیه می‌شود متن ترجمه‌شده را به منحنی یا مسیر (path) تبدیل کنید. تبدیل متن به منحنی تضمین می‌کند که تصویر نهایی، متن ترجمه‌شده را به‌درستی نمایش دهد، حتی اگر فونت دقیقِ استفاده‌شده در فایل SVG اصلی روی سیستم کاربر نصب نباشد.

  5. بازبینی و آزمایش: پس از انجام ترجمه‌های لازم و تبدیل متن به منحنی، تصویر SVG به‌روزشده را ذخیره و بازبینی کنید تا مطمئن شوید متن به‌درستی نمایش داده شده و تراز است. بخش پیش‌نمایش محلی تغییرات را ببینید.

فایل‌های منبع

بومی‌سازی‌ها باید بر پایهٔ فایل‌های انگلیسیِ نسخه‌ای مشخص انجام شوند که تیم بومی‌سازی آن را هدف قرار داده است. هر تیم بومی‌سازی خودش تعیین می‌کند کدام نسخه را هدف قرار دهد. در ادامه از این نسخه با عنوان نسخهٔ هدف یاد می‌شود.

برای یافتن فایل‌های منبع نسخهٔ هدف خود:

  1. به مخزن وب‌سایت کوبرنتیز در نشانی https://github.com/kubernetes/website بروید.

  2. از جدول زیر، شاخهٔ مربوط به نسخهٔ هدف خود را انتخاب کنید:

نسخهٔ هدف شاخه
آخرین نسخه main
نسخهٔ قبلی release-1.37
نسخهٔ بعدی dev-1.37

شاخهٔ main محتوای انتشار فعلی، یعنی v1.37، را در خود دارد. تیم انتشار پیش از انتشار بعدی، یعنی v1.37، شاخهٔ `` را ایجاد می‌کند.

رشته‌های سایت در i18n

هر بومی‌سازی باید محتوای فایل i18n/en/en.toml را در یک فایل جدید و مختص همان زبان داشته باشد. برای نمونه، این فایل برای زبان آلمانی i18n/de/de.toml است.

یک پوشه و فایل جدید برای بومی‌سازی به i18n/ اضافه کنید. برای نمونه، برای زبان آلمانی (de):

mkdir -p i18n/de
cp i18n/en/en.toml i18n/de/de.toml

توضیحات بالای فایل را متناسب با بومی‌سازی خود ویرایش کنید و سپس مقدار هر رشته را ترجمه کنید. برای نمونه، متن جایگزین (placeholder) فرم جستجو به زبان آلمانی چنین است:

[ui_search]
other = "Suchen"

با بومی‌سازی رشته‌های سایت می‌توانید متن‌ها و ویژگی‌هایی را که در سراسر سایت به کار می‌روند سفارشی کنید؛ برای نمونه، متن حقوقی کپی‌رایت در پانویس هر صفحه.

راهنمای بومی‌سازی مختص هر زبان

شما به‌عنوان یک تیم بومی‌سازی می‌توانید با نوشتن یک راهنمای بومی‌سازی مختص زبان خود، بهترین شیوه‌هایی را که تیمتان دنبال می‌کند به‌صورت رسمی مدون کنید.

برای نمونه، راهنمای بومی‌سازی کره‌ای را ببینید که به موضوعات زیر می‌پردازد:

  • آهنگ اسپرینت‌ها و انتشارها
  • راهبرد شاخه‌بندی
  • گردش کار درخواست ادغام (pull request)
  • راهنمای سبک نگارش
  • واژه‌نامهٔ اصطلاحات بومی‌شده و بومی‌نشده
  • قراردادهای نگارش Markdown
  • اصطلاحات مربوط به آبجکت‌های API کوبرنتیز

جلسات Zoom مختص هر زبان

اگر پروژهٔ بومی‌سازی به زمان جلسهٔ جداگانه‌ای نیاز دارد، با یکی از رؤسای مشترک (Co-Chair) یا رهبران فنی (Tech Lead) گروه SIG Docs تماس بگیرید تا یک جلسهٔ تکرارشوندهٔ جدید در Zoom و دعوت‌نامهٔ تقویم برای آن ایجاد کنند. این کار فقط زمانی لازم است که تیم به اندازهٔ کافی بزرگ باشد که هم به جلسهٔ جداگانه نیاز داشته باشد و هم بتواند آن را به‌طور پایدار برگزار کند.

طبق سیاست CNCF، تیم‌های بومی‌سازی باید جلسات خود را در فهرست پخش YouTube گروه SIG Docs بارگذاری کنند. تا زمانی که SIG Docs این فرایند را خودکار نکرده است، یکی از رؤسای مشترک یا رهبران فنی SIG Docs می‌تواند در انجام آن کمک کند.

راهبرد شاخه‌بندی

از آنجا که پروژه‌های بومی‌سازی کارهایی به‌شدت گروهی هستند، به تیم‌ها توصیه می‌کنیم در شاخه‌های بومی‌سازی مشترک کار کنند؛ به‌ویژه در آغاز کار و زمانی که بومی‌سازی هنوز منتشر نشده است.

برای همکاری در یک شاخهٔ بومی‌سازی:

  1. یکی از اعضای تیم @kubernetes/website-maintainers یک شاخهٔ بومی‌سازی را از یکی از شاخه‌های منبع در https://github.com/kubernetes/website ایجاد می‌کند.

    تأییدکنندگان تیم شما هنگامی که تیم بومی‌سازی خود را به مخزن kubernetes/org اضافه کردید، به تیم @kubernetes/website-maintainers پیوسته‌اند.

    الگوی نام‌گذاری زیر را برای شاخه‌ها توصیه می‌کنیم:

    dev-<source version>-<language code>.<team milestone>

    برای نمونه، یکی از تأییدکنندگان تیم بومی‌سازی آلمانی، شاخهٔ بومی‌سازی dev-1.12-de.1 را مستقیماً در مخزن kubernetes/website و بر پایهٔ شاخهٔ منبع کوبرنتیز v1.12 ایجاد می‌کند.

  2. هر یک از مشارکت‌کنندگان، شاخه‌های ویژگی (feature branch) خود را بر پایهٔ شاخهٔ بومی‌سازی ایجاد می‌کند.

    برای نمونه، یک مشارکت‌کنندهٔ آلمانی درخواست ادغامی با تغییرات خود از username:local-branch-name به kubernetes:dev-1.12-de.1 باز می‌کند.

  3. تأییدکنندگان شاخه‌های ویژگی را بازبینی کرده و در شاخهٔ بومی‌سازی ادغام می‌کنند.

  4. یکی از تأییدکنندگان به‌طور دوره‌ای با باز کردن و تأیید یک درخواست ادغام جدید، شاخهٔ بومی‌سازی را با شاخهٔ منبع آن ادغام می‌کند. حتماً پیش از تأیید درخواست ادغام، کامیت‌ها را squash کنید.

مراحل ۱ تا ۴ را تا زمان تکمیل بومی‌سازی، به هر تعداد که لازم است تکرار کنید. برای نمونه، شاخه‌های بعدی بومی‌سازی آلمانی چنین خواهند بود: dev-1.12-de.2، dev-1.12-de.3 و غیره.

تیم‌ها باید محتوای بومی‌شده را در همان شاخه‌ای ادغام کنند که محتوا از آن گرفته شده است. برای نمونه:

  • شاخهٔ بومی‌سازی‌ای که از main گرفته شده است، باید در main ادغام شود.
  • شاخهٔ بومی‌سازی‌ای که از release- گرفته شده است، باید در release- ادغام شود.
توجه:

اگر شاخهٔ بومی‌سازی شما از شاخهٔ main ایجاد شده، اما پیش از ایجاد شاخهٔ انتشار جدید در `main` ادغام نشده است، آن را هم در `main` و هم در شاخهٔ انتشار جدید ادغام کنید. برای ادغام شاخهٔ بومی‌سازی خود در شاخهٔ انتشار جدید ، باید شاخهٔ بالادستی (upstream) شاخهٔ بومی‌سازی خود را به تغییر دهید.

در آغاز هر نقطهٔ عطف (milestone) تیم، بهتر است یک issue باز کنید و در آن تغییرات بالادستی میان شاخهٔ بومی‌سازی قبلی و شاخهٔ بومی‌سازی فعلی را مقایسه کنید. برای مقایسهٔ تغییرات بالادستی دو اسکریپت وجود دارد:

  • اسکریپت upstream_changes.py برای بررسی تغییراتی که در یک فایل مشخص ایجاد شده، مفید است؛ و
  • اسکریپت diff_l10n_branches.py برای تهیهٔ فهرستی از فایل‌های قدیمی‌شده در یک شاخهٔ بومی‌سازی مشخص مفید است.

اگرچه فقط تأییدکنندگان می‌توانند شاخهٔ بومی‌سازی جدیدی ایجاد کنند و درخواست‌های ادغام را ادغام کنند، هر کسی می‌تواند برای یک شاخهٔ بومی‌سازی جدید درخواست ادغام باز کند. این کار به هیچ مجوز ویژه‌ای نیاز ندارد.

برای اطلاعات بیشتر دربارهٔ کار کردن از طریق فورک‌ها یا مستقیماً از خود مخزن، بخش «فورک و کلون کردن مخزن» را ببینید.
