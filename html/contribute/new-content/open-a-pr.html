باز کردن درخواست ادغام (Pull Request)

توجه:

توسعه‌دهندگان کد: اگر برای یکی از نسخه‌های آیندهٔ کوبرنتیز قابلیت جدیدی را مستند می‌کنید، به مستندسازی یک قابلیت جدید مراجعه کنید.

برای افزودن صفحه‌های محتوایی جدید یا بهبود صفحه‌های موجود، یک درخواست ادغام (pull request یا PR) باز کنید. مطمئن شوید که همهٔ الزامات بخش پیش از شروع را رعایت کرده‌اید.

اگر تغییر شما کوچک است یا با git آشنایی ندارید، برای آشنایی با نحوهٔ ویرایش یک صفحه، بخش تغییرات با استفاده از GitHub را بخوانید.

اگر تغییرات شما گسترده است، برای آشنایی با نحوهٔ اعمال تغییرات به‌صورت محلی روی رایانهٔ خود، بخش کار از طریق یک فورک محلی را بخوانید.

تغییرات با استفاده از GitHub

اگر تجربهٔ کمتری با گردش‌کارهای git دارید، روش ساده‌تری برای باز کردن درخواست ادغام وجود دارد. شکل ۱ مراحل کار را به‌طور خلاصه نشان می‌دهد و جزئیات هر مرحله در ادامه آمده است.

شکل ۱. مراحل باز کردن درخواست ادغام با استفاده از GitHub.

  1. در صفحه‌ای که مشکل را در آن مشاهده کرده‌اید، گزینهٔ Edit this page را از پنل پیمایش سمت راست انتخاب کنید.

  2. تغییرات خود را در ویرایشگر مارک‌داون GitHub اعمال کنید.

  3. در سمت راست و بالای ویرایشگر، گزینهٔ Commit changes را انتخاب کنید. در فیلد اول، عنوانی برای پیام کامیت خود بنویسید. در فیلد دوم، توضیحاتی ارائه دهید.

توجه:

در پیام کامیت خود از هیچ‌یک از کلیدواژه‌های GitHub استفاده نکنید. می‌توانید بعداً آن‌ها را به توضیحات درخواست ادغام اضافه کنید.

  1. گزینهٔ Propose changes را انتخاب کنید.

  2. گزینهٔ Create pull request را انتخاب کنید.

  3. صفحهٔ Open a pull request نمایش داده می‌شود. فرم را تکمیل کنید:

    • فیلد Add a title در درخواست ادغام به‌طور پیش‌فرض با خلاصهٔ کامیت پر می‌شود. در صورت نیاز می‌توانید آن را تغییر دهید.
    • فیلد Add a description شامل پیام کامیت تفصیلی شما (در صورت وجود) و مقداری متن قالب است. جزئیاتی را که متن قالب درخواست می‌کند اضافه کنید و سپس متن اضافی قالب را حذف کنید.
    • کادر انتخاب Allow edits from maintainers را در حالت انتخاب‌شده باقی بگذارید.
توجه:

توضیحات درخواست ادغام راه بسیار خوبی برای کمک به بازبین‌ها در درک تغییر شماست. برای اطلاعات بیشتر، به باز کردن درخواست ادغام مراجعه کنید.

  1. گزینهٔ Create pull request را انتخاب کنید.

رسیدگی به بازخوردها در GitHub

پیش از ادغام یک درخواست ادغام، اعضای جامعهٔ کوبرنتیز آن را بازبینی و تأیید می‌کنند. ربات k8s-ci-robot بر اساس نزدیک‌ترین مالکِ ذکرشده در صفحه‌ها، بازبین‌هایی را پیشنهاد می‌کند. اگر فرد خاصی را در نظر دارید، دیدگاهی حاوی نام کاربری GitHub او بگذارید.

اگر بازبینی از شما خواست تغییراتی اعمال کنید:

  1. به زبانهٔ Files changed بروید.
  2. روی نماد مداد (ویرایش) در هر یک از فایل‌هایی که درخواست ادغام تغییرشان داده است، کلیک کنید.
  3. تغییرات درخواست‌شده را اعمال کنید.
  4. تغییرات را کامیت کنید.

اگر منتظر پاسخ یک بازبین هستید، هر ۷ روز یک بار با او تماس بگیرید. همچنین می‌توانید در کانال #sig-docs در Slack پیامی ارسال کنید.

پس از تکمیل بازبینی، یکی از بازبین‌ها درخواست ادغام شما را ادغام می‌کند و تغییرات شما چند دقیقه بعد منتشر می‌شوند.

کار از طریق یک فورک محلی {#fork-the-repo}

اگر تجربهٔ بیشتری با git دارید یا تغییرات شما بیش از چند خط است، از طریق یک فورک محلی کار کنید.

مطمئن شوید که git روی رایانهٔ شما نصب شده است. همچنین می‌توانید از یک برنامهٔ رابط گرافیکی برای git استفاده کنید.

شکل ۲ مراحلی را نشان می‌دهد که هنگام کار از طریق یک فورک محلی باید دنبال کنید. جزئیات هر مرحله در ادامه آمده است.

شکل ۲. کار از طریق یک فورک محلی برای اعمال تغییرات.

فورک کردن مخزن kubernetes/website

  1. به مخزن kubernetes/website بروید.
  2. گزینهٔ Fork را انتخاب کنید.

ایجاد یک کلون محلی و تنظیم upstream

  1. در یک پنجرهٔ ترمینال، فورک خود را کلون کنید و پوستهٔ Docsy Hugo را به‌روزرسانی کنید:

    git clone git@github.com:<github_username>/website
cd website

  2. به پوشهٔ جدید website بروید. مخزن kubernetes/website را به‌عنوان مخزن راه دور upstream تنظیم کنید:

    cd website

git remote add upstream https://github.com/kubernetes/website.git

  3. مخزن‌های origin و upstream خود را بررسی و تأیید کنید:

    git remote -v

    خروجی مشابه زیر است:

    origin	git@github.com:<github_username>/website.git (fetch)
origin	git@github.com:<github_username>/website.git (push)
upstream	https://github.com/kubernetes/website.git (fetch)
upstream	https://github.com/kubernetes/website.git (push)

  4. کامیت‌ها را از شاخهٔ origin/main فورک خود و از شاخهٔ upstream/main مخزن kubernetes/website دریافت کنید:

    git fetch origin
git fetch upstream

    با این کار مطمئن می‌شوید که مخزن محلی شما پیش از شروع اعمال تغییرات به‌روز است.

توجه:

این گردش‌کار با گردش‌کار GitHub جامعهٔ کوبرنتیز تفاوت دارد. لازم نیست پیش از پوش کردن به‌روزرسانی‌ها به فورک خود، نسخهٔ محلی main را با upstream/main ادغام کنید.

ایجاد یک شاخه

  1. تصمیم بگیرید که کار خود را بر پایهٔ کدام شاخه انجام دهید:

    • برای بهبود محتوای موجود، از upstream/main استفاده کنید.
    • برای محتوای جدید دربارهٔ قابلیت‌های موجود، از upstream/main استفاده کنید.
    • برای محتوای بومی‌سازی‌شده، از قراردادهای همان بومی‌سازی پیروی کنید. برای اطلاعات بیشتر، به بومی‌سازی مستندات کوبرنتیز مراجعه کنید.
    • برای قابلیت‌های جدید در نسخهٔ آیندهٔ کوبرنتیز، از شاخهٔ مربوط به آن قابلیت استفاده کنید. برای اطلاعات بیشتر، به مستندسازی برای یک انتشار مراجعه کنید.
    • برای کارهای بلندمدتی که چند مشارکت‌کنندهٔ SIG Docs روی آن‌ها همکاری می‌کنند، مانند سازمان‌دهی مجدد محتوا، از شاخهٔ ویژه‌ای استفاده کنید که برای همان کار ایجاد شده است.

    اگر برای انتخاب شاخه به کمک نیاز دارید، در کانال #sig-docs در Slack بپرسید.

  2. شاخهٔ جدیدی بر پایهٔ شاخه‌ای که در مرحلهٔ ۱ مشخص کردید ایجاد کنید. در این مثال فرض شده است که شاخهٔ پایه upstream/main است:

    git checkout -b <my_new_branch> upstream/main

  3. تغییرات خود را با یک ویرایشگر متن اعمال کنید.

هر زمان که خواستید، می‌توانید با فرمان git status ببینید چه فایل‌هایی را تغییر داده‌اید.

کامیت کردن تغییرات

هنگامی که آمادهٔ ارسال درخواست ادغام شدید، تغییرات خود را کامیت کنید.

  1. در مخزن محلی خود، بررسی کنید که کدام فایل‌ها را باید کامیت کنید:

    git status

    خروجی مشابه زیر است:

    On branch <my_new_branch>
Your branch is up to date with 'origin/<my_new_branch>'.

Changes not staged for commit:
(use "git add <file>..." to update what will be committed)
(use "git checkout -- <file>..." to discard changes in working directory)

modified:   content/en/docs/contribute/new-content/contributing-content.md

no changes added to commit (use "git add" and/or "git commit -a")

  2. فایل‌هایی را که زیر عنوان Changes not staged for commit فهرست شده‌اند به کامیت اضافه کنید:

    git add <your_file_name>

    این کار را برای هر فایل تکرار کنید.

  3. پس از افزودن همهٔ فایل‌ها، یک کامیت ایجاد کنید:

    git commit -m "Your commit message"
توجه:

در پیام کامیت خود از هیچ‌یک از کلیدواژه‌های GitHub استفاده نکنید. می‌توانید بعداً آن‌ها را به توضیحات درخواست ادغام اضافه کنید.

  1. شاخهٔ محلی خود و کامیت جدید آن را به فورک راه دور خود پوش کنید:

    git push origin <my_new_branch>

پیش‌نمایش محلی تغییرات {#preview-locally}

بهتر است پیش از پوش کردن تغییرات یا باز کردن درخواست ادغام، آن‌ها را به‌صورت محلی پیش‌نمایش کنید. مقالهٔ پیش‌نمایش محلی توضیح می‌دهد که چگونه می‌توانید وب‌سایت را به‌صورت محلی اجرا کنید و تغییرات پیشنهادی را پیش‌نمایش کنید.

باز کردن درخواست ادغام از فورک خود به kubernetes/website {#open-a-pr}

شکل ۳. مراحل باز کردن درخواست ادغام از فورک شما به مخزن kubernetes/website.

  1. در مرورگر وب، به مخزن kubernetes/website بروید.

  2. گزینهٔ New Pull Request را انتخاب کنید.

  3. گزینهٔ compare across forks را انتخاب کنید.

  4. از منوی کشویی head repository، فورک خود را انتخاب کنید.

  5. از منوی کشویی compare، شاخهٔ خود را انتخاب کنید.

  6. گزینهٔ Create Pull Request را انتخاب کنید.

  7. توضیحاتی برای درخواست ادغام خود اضافه کنید:

    • عنوان (Title، حداکثر ۵۰ نویسه): هدف تغییر را به‌طور خلاصه بیان کنید.

    • توضیحات (Description): تغییر را با جزئیات بیشتری شرح دهید.

      • اگر issue مرتبطی در GitHub وجود دارد، عبارت Fixes #12345 یا Closes #12345 را در توضیحات بگنجانید. در این صورت، سازوکار خودکار GitHub پس از ادغام درخواست، issue ذکرشده را می‌بندد. اگر درخواست‌های ادغام مرتبط دیگری وجود دارند، پیوند آن‌ها را نیز اضافه کنید.
      • اگر دربارهٔ موضوع خاصی به راهنمایی نیاز دارید، پرسش‌هایی را که می‌خواهید بازبین‌ها درباره‌شان فکر کنند در توضیحات خود بنویسید.

  8. دکمهٔ Create pull request را انتخاب کنید.

تبریک! درخواست ادغام شما اکنون در بخش Pull requests در دسترس است.

پس از باز کردن درخواست ادغام، GitHub آزمون‌های خودکار را اجرا می‌کند و می‌کوشد با استفاده از Netlify یک پیش‌نمایش مستقر کند.

  • اگر ساخت Netlify ناموفق بود، برای اطلاعات بیشتر گزینهٔ Details را انتخاب کنید.
  • اگر ساخت Netlify موفق بود، با انتخاب گزینهٔ Details نسخهٔ آزمایشی وب‌سایت کوبرنتیز همراه با تغییرات اعمال‌شدهٔ شما باز می‌شود. بازبین‌ها تغییرات شما را به همین روش بررسی می‌کنند.

همچنین GitHub برای کمک به بازبین‌ها، به‌طور خودکار برچسب‌هایی به درخواست ادغام اختصاص می‌دهد. در صورت نیاز، شما نیز می‌توانید برچسب اضافه کنید. برای اطلاعات بیشتر، به افزودن و حذف برچسب‌های issue مراجعه کنید.

رسیدگی به بازخوردها به‌صورت محلی

  1. پس از اعمال تغییرات، کامیت قبلی خود را اصلاح (amend) کنید:

    git commit -a --amend
    • گزینهٔ -a: همهٔ تغییرات را کامیت می‌کند
    • گزینهٔ --amend: به‌جای ایجاد کامیت جدید، کامیت قبلی را اصلاح می‌کند

  2. در صورت نیاز، پیام کامیت خود را به‌روزرسانی کنید.

  3. با فرمان git push origin <my_new_branch> تغییرات خود را پوش کنید و آزمون‌های Netlify را دوباره اجرا کنید.

توجه:

اگر به‌جای اصلاح کامیت از git commit -m استفاده کنید، باید پیش از ادغام کامیت‌های خود را یکی (squash) کنید.

تغییرات بازبین‌ها

گاهی بازبین‌ها کامیت‌هایی به درخواست ادغام شما اضافه می‌کنند. پیش از اعمال هر تغییر دیگری، آن کامیت‌ها را دریافت کنید.

  1. کامیت‌ها را از فورک راه دور خود دریافت کنید و شاخهٔ کاری خود را ری‌بیس (rebase) کنید:

    git fetch origin
git rebase origin/<your-branch-name>

  2. پس از ری‌بیس، تغییرات جدید را با force-push به فورک خود ارسال کنید:

    git push --force-with-lease origin <your-branch-name>

تعارض‌های ادغام و ری‌بیس

توجه:

برای اطلاعات بیشتر، به Git Branching - Basic Branching and Merging و Advanced Merging مراجعه کنید یا برای دریافت کمک در کانال #sig-docs در Slack بپرسید.

اگر مشارکت‌کنندهٔ دیگری در یک درخواست ادغام دیگر، تغییراتی را در همان فایل کامیت کند، ممکن است تعارض ادغام (merge conflict) ایجاد شود. شما باید همهٔ تعارض‌های ادغام را در درخواست ادغام خود برطرف کنید.

  1. فورک خود را به‌روزرسانی کنید و شاخهٔ محلی خود را ری‌بیس کنید:

    git fetch origin
git rebase origin/<your-branch-name>

    سپس تغییرات را با force-push به فورک خود ارسال کنید:

    git push --force-with-lease origin <your-branch-name>

  2. تغییرات را از شاخهٔ upstream/main مخزن kubernetes/website دریافت کنید و شاخهٔ خود را ری‌بیس کنید:

    git fetch upstream
git rebase upstream/main

  3. نتایج ری‌بیس را بررسی کنید:

    git status

    در نتیجه، تعدادی از فایل‌ها به‌عنوان دارای تعارض علامت‌گذاری می‌شوند.

  4. هر فایل دارای تعارض را باز کنید و به دنبال نشانگرهای تعارض بگردید: >>>، <<< و ===. تعارض را برطرف کنید و نشانگر تعارض را حذف کنید.

توجه:

برای اطلاعات بیشتر، به How conflicts are presented مراجعه کنید.

  1. فایل‌ها را به مجموعهٔ تغییرات اضافه کنید:

    git add <filename>

  2. ری‌بیس را ادامه دهید:

    git rebase --continue

  3. مراحل ۲ تا ۵ را در صورت نیاز تکرار کنید.

    پس از اعمال همهٔ کامیت‌ها، فرمان git status نشان می‌دهد که ری‌بیس کامل شده است.

  4. شاخه را با force-push به فورک خود ارسال کنید:

    git push --force-with-lease origin <your-branch-name>

    اکنون درخواست ادغام دیگر هیچ تعارضی نشان نمی‌دهد.

ادغام کامیت‌ها (squash)

توجه:

برای اطلاعات بیشتر، به Git Tools - Rewriting History مراجعه کنید یا برای دریافت کمک در کانال Slack با نام #sig-docs سؤال بپرسید.

اگر PR شما چندین کامیت دارد، باید پیش از ادغام PR، آن‌ها را در یک کامیت واحد ادغام کنید. برای بررسی تعداد کامیت‌های PR خود می‌توانید به زبانه Commits آن مراجعه کنید یا دستور git log را به‌صورت محلی اجرا کنید.

توجه:

در این بخش فرض شده است که از vim به‌عنوان ویرایشگر متنی خط فرمان استفاده می‌کنید.

  1. یک rebase تعاملی را آغاز کنید:

    git rebase -i HEAD~<number_of_commits_in_branch>

    ادغام کامیت‌ها نوعی rebase است. سوئیچ -i به git اعلام می‌کند که می‌خواهید rebase را به‌صورت تعاملی انجام دهید. عبارت HEAD~<number_of_commits_in_branch مشخص می‌کند که چه تعداد کامیت برای rebase بررسی شوند.

    خروجی مشابه زیر است:

    pick d875112ca Original commit
pick 4fa167b80 Address feedback 1
pick 7d54e15ee Address feedback 2

# Rebase 3d18sf680..7d54e15ee onto 3d183f680 (3 commands)

...

# These lines can be re-ordered; they are executed from top to bottom.

    بخش اول خروجی، کامیت‌های موجود در rebase را فهرست می‌کند. بخش دوم، گزینه‌های قابل‌استفاده برای هر کامیت را نشان می‌دهد. با تغییر واژه pick، وضعیت آن کامیت پس از پایان rebase تغییر می‌کند.

    برای انجام rebase، روی squash و pick تمرکز کنید.

توجه:

برای اطلاعات بیشتر، به حالت تعاملی مراجعه کنید.

  1. ویرایش فایل را آغاز کنید.

    متن اصلی زیر را:

    pick d875112ca Original commit
pick 4fa167b80 Address feedback 1
pick 7d54e15ee Address feedback 2

    به این صورت تغییر دهید:

    pick d875112ca Original commit
squash 4fa167b80 Address feedback 1
squash 7d54e15ee Address feedback 2

    با این کار، کامیت‌های 4fa167b80 Address feedback 1 و 7d54e15ee Address feedback 2 در کامیت d875112ca Original commit ادغام می‌شوند و تنها d875112ca Original commit در تاریخچه باقی می‌ماند.

  2. فایل را ذخیره کنید و از آن خارج شوید.

  3. کامیت ادغام‌شده خود را push کنید:

    git push --force-with-lease origin <branch_name>

مشارکت در مخزن‌های دیگر

پروژه کوبرنتیز بیش از ۵۰ مخزن دارد. بسیاری از این مخزن‌ها شامل مستنداتی مانند متن‌های راهنمای کاربر، پیام‌های خطا، مرجع‌های API یا توضیحات درون کد هستند.

اگر متنی دیدید که می‌خواهید آن را بهبود دهید، با استفاده از GitHub در همه مخزن‌های سازمان کوبرنتیز جست‌وجو کنید. این کار به شما کمک می‌کند تشخیص دهید issue یا PR خود را کجا ثبت کنید.

هر مخزن فرایندها و رویه‌های خاص خود را دارد. پیش از ثبت issue یا ارسال PR، فایل‌های README.md، CONTRIBUTING.md و code-of-conduct.md آن مخزن را، در صورت وجود، مطالعه کنید.

بیشتر مخزن‌ها از قالب‌های issue و PR استفاده می‌کنند. برای آشنایی با فرایندهای هر تیم، نگاهی به چند issue و PR باز بیندازید. هنگام ثبت issue یا PR، حتماً قالب‌ها را با بیشترین جزئیات ممکن پر کنید.
