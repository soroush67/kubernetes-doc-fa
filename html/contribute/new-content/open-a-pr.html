باز کردن یک pull request

توجه:

توسعه‌دهندگان کد: اگر در حال مستندسازی یک قابلیت جدید برای نسخهٔ آتی کوبرنتیز هستید، به مستندسازی یک قابلیت جدید مراجعه کنید.

برای مشارکت با افزودن صفحات محتوای جدید یا بهبود صفحات موجود، یک pull request (PR) باز کنید. مطمئن شوید که همهٔ الزامات بخش پیش از شروع را رعایت کرده‌اید.

اگر تغییر شما کوچک است یا با git آشنایی ندارید، بخش تغییرات با استفاده از GitHub را بخوانید تا نحوهٔ ویرایش یک صفحه را بیاموزید.

اگر تغییرات شما گسترده است، بخش کار با یک fork محلی را بخوانید تا یاد بگیرید چگونه تغییرات را به‌صورت محلی روی رایانهٔ خود انجام دهید.

شکل ۱. مراحل باز کردن یک PR با استفاده از GitHub.

  1. در صفحه‌ای که مشکل را مشاهده می‌کنید، گزینهٔ Edit this page را در پنل ناوبری سمت راست انتخاب کنید.

  2. تغییرات خود را در ویرایشگر markdown گیت‌هاب اعمال کنید.

  3. در بالای ویرایشگر، سمت راست، Commit changes را انتخاب کنید. در فیلد اول، برای پیام commit خود یک عنوان بنویسید. در فیلد دوم، توضیحات را وارد کنید.

توجه:

از هیچ‌یک از کلیدواژه‌های GitHub در پیام commit خود استفاده نکنید. می‌توانید این کلیدواژه‌ها را بعداً به توضیحات pull request اضافه کنید.

  1. Propose changes را انتخاب کنید.

  2. Create pull request را انتخاب کنید.

  3. صفحهٔ Open a pull request نمایش داده می‌شود. فرم را تکمیل کنید:

    • فیلد Add a title در pull request به‌طور پیش‌فرض برابر با خلاصهٔ commit است. در صورت نیاز می‌توانید آن را تغییر دهید.
    • فیلد Add a description شامل پیام کامل commit شما (در صورت وجود) و مقداری متن قالب است. جزئیاتی را که متن قالب از شما می‌خواهد اضافه کنید و سپس متن اضافی قالب را حذف کنید.
    • کادر انتخاب Allow edits from maintainers را انتخاب‌شده رها کنید.
توجه:

توضیحات PR راه بسیار خوبی برای کمک به بازبین‌ها در درک تغییر شماست. برای اطلاعات بیشتر، به باز کردن یک PR مراجعه کنید.

  1. Create pull request را انتخاب کنید.

رسیدگی به بازخوردها در GitHub

پیش از ادغام یک pull request، اعضای جامعهٔ کوبرنتیز آن را بازبینی و تأیید می‌کنند. k8s-ci-robot بر اساس نزدیک‌ترین مالک ذکرشده در صفحات، بازبین‌هایی را پیشنهاد می‌دهد. اگر شخص مشخصی را در نظر دارید، نظری بگذارید که نام کاربری GitHub او در آن آمده باشد.

اگر بازبین از شما خواست تغییراتی اعمال کنید:

  1. به زبانهٔ Files changed بروید.
  2. روی نماد مداد (ویرایش) در کنار هر فایلی که توسط pull request تغییر کرده است کلیک کنید.
  3. تغییرات درخواست‌شده را اعمال کنید.
  4. تغییرات را commit کنید.

اگر منتظر یک بازبین هستید، هر ۷ روز یک بار با او تماس بگیرید. همچنین می‌توانید در کانال Slack با نام #sig-docs پیام بگذارید.

پس از پایان بازبینی، یک بازبین PR شما را ادغام می‌کند و چند دقیقه بعد تغییرات شما منتشر می‌شود.

مطمئن شوید که git روی رایانهٔ شما نصب شده است. همچنین می‌توانید از یک برنامهٔ رابط کاربری git استفاده کنید.

شکل ۲. کار با یک fork محلی برای اعمال تغییرات.

ایجاد fork از مخزن kubernetes/website

  1. به مخزن kubernetes/website بروید.
  2. Fork را انتخاب کنید.

ایجاد یک کلون محلی و تنظیم upstream

  1. در یک پنجرهٔ ترمینال، fork خود را کلون کنید و تم Docsy Hugo را به‌روزرسانی کنید:

    git clone git@github.com:<github_username>/website
cd website

  2. به دایرکتوری جدید website بروید. مخزن kubernetes/website را به‌عنوان remote با نام upstream تنظیم کنید:

    cd website

git remote add upstream https://github.com/kubernetes/website.git

  3. مخازن origin و upstream خود را بررسی کنید:

    git remote -v

    خروجی مشابه زیر است:

    origin	git@github.com:<github_username>/website.git (fetch)
origin	git@github.com:<github_username>/website.git (push)
upstream	https://github.com/kubernetes/website.git (fetch)
upstream	https://github.com/kubernetes/website.git (push)

  4. commitها را از origin/main در fork خود و upstream/main در kubernetes/website دریافت (fetch) کنید:

    git fetch origin
git fetch upstream

    این کار تضمین می‌کند که پیش از شروع اعمال تغییرات، مخزن محلی شما به‌روز است.

توجه:

این جریان کاری با جریان کاری GitHub جامعهٔ کوبرنتیز متفاوت است. لازم نیست پیش از ارسال (push) به‌روزرسانی‌ها به fork خود، نسخهٔ محلی main را با upstream/main ادغام کنید.

ایجاد یک شاخه (branch)

  1. تصمیم بگیرید کار خود را بر پایهٔ کدام شاخه انجام دهید:

    • برای بهبود محتوای موجود، از upstream/main استفاده کنید.
    • برای محتوای جدید دربارهٔ قابلیت‌های موجود، از upstream/main استفاده کنید.
    • برای محتوای بومی‌سازی‌شده، از قراردادهای همان بومی‌سازی پیروی کنید. برای اطلاعات بیشتر، به بومی‌سازی مستندات کوبرنتیز مراجعه کنید.
    • برای قابلیت‌های جدید در نسخهٔ آتی کوبرنتیز، از شاخهٔ قابلیت (feature branch) استفاده کنید. برای اطلاعات بیشتر، به مستندسازی برای یک نسخه مراجعه کنید.
    • برای تلاش‌های طولانی‌مدت که چند مشارکت‌کنندهٔ SIG Docs در آن همکاری می‌کنند، مانند سازماندهی مجدد محتوا، از یک شاخهٔ قابلیت مخصوص که برای همان تلاش ایجاد شده است استفاده کنید.

    اگر در انتخاب شاخه به کمک نیاز دارید، در کانال Slack با نام #sig-docs بپرسید.

  2. یک شاخهٔ جدید بر پایهٔ شاخه‌ای که در مرحلهٔ ۱ مشخص کردید ایجاد کنید. این مثال فرض می‌کند که شاخهٔ پایه upstream/main است:

    git checkout -b <my_new_branch> upstream/main

  3. تغییرات خود را با یک ویرایشگر متن اعمال کنید.

در هر زمان می‌توانید با دستور git status فایل‌هایی را که تغییر داده‌اید مشاهده کنید.

commit کردن تغییرات

وقتی آمادهٔ ارسال یک pull request هستید، تغییرات خود را commit کنید.

  1. در مخزن محلی خود بررسی کنید کدام فایل‌ها را باید commit کنید:

    git status

    خروجی مشابه زیر است:

    On branch <my_new_branch>
Your branch is up to date with 'origin/<my_new_branch>'.

Changes not staged for commit:
(use "git add <file>..." to update what will be committed)
(use "git checkout -- <file>..." to discard changes in working directory)

modified:   content/en/docs/contribute/new-content/contributing-content.md

no changes added to commit (use "git add" and/or "git commit -a")

  2. فایل‌های فهرست‌شده در بخش Changes not staged for commit را به commit اضافه کنید:

    git add <your_file_name>

    این کار را برای هر فایل تکرار کنید.

  3. پس از افزودن همهٔ فایل‌ها، یک commit ایجاد کنید:

    git commit -m "Your commit message"
توجه:

از هیچ‌یک از کلیدواژه‌های GitHub در پیام commit خود استفاده نکنید. می‌توانید این کلیدواژه‌ها را بعداً به توضیحات pull request اضافه کنید.

  1. شاخهٔ محلی خود و commit جدید آن را به fork راه دور (remote) خود ارسال (push) کنید:

    git push origin <my_new_branch>

پیش‌نمایش محلی تغییرات {#preview-locally}

بهتر است پیش از ارسال تغییرات یا باز کردن یک pull request، آن‌ها را به‌صورت محلی پیش‌نمایش کنید. مقالهٔ پیش‌نمایش محلی توضیح می‌دهد که چگونه می‌توانید وب‌سایت را به‌صورت محلی اجرا کنید و تغییرات پیشنهادی را پیش‌نمایش کنید.

شکل ۳. مراحل باز کردن یک PR از fork شما به kubernetes/website.

  1. در یک مرورگر وب، به مخزن kubernetes/website بروید.

  2. New Pull Request را انتخاب کنید.

  3. compare across forks را انتخاب کنید.

  4. از منوی کشویی head repository، fork خود را انتخاب کنید.

  5. از منوی کشویی compare، شاخهٔ خود را انتخاب کنید.

  6. Create Pull Request را انتخاب کنید.

  7. برای pull request خود توضیحات بنویسید:

    • Title (حداکثر ۵۰ نویسه): هدف تغییر را خلاصه کنید.

    • Description: تغییر را با جزئیات بیشتری شرح دهید.

      • اگر یک issue مرتبط در GitHub وجود دارد، عبارت Fixes #12345 یا Closes #12345 را در توضیحات بیاورید. در صورت استفاده از این عبارت، خودکارسازی GitHub پس از ادغام PR، issue ذکرشده را می‌بندد. اگر PRهای مرتبط دیگری وجود دارد، آن‌ها را نیز پیوند دهید.
      • اگر دربارهٔ موضوع خاصی توصیه می‌خواهید، هر پرسشی را که دوست دارید بازبین‌ها به آن فکر کنند در توضیحات خود بیاورید.

  8. دکمهٔ Create pull request را انتخاب کنید.

تبریک! pull request شما در بخش Pull requests در دسترس است.

پس از باز کردن یک PR، GitHub آزمون‌های خودکار را اجرا می‌کند و تلاش می‌کند با استفاده از Netlify یک پیش‌نمایش مستقر کند.

  • اگر ساخت Netlify شکست بخورد، برای اطلاعات بیشتر Details را انتخاب کنید.
  • اگر ساخت Netlify موفق باشد، انتخاب Details نسخه‌ای آزمایشی (staged) از وب‌سایت کوبرنتیز را با تغییرات اعمال‌شدهٔ شما باز می‌کند. بازبین‌ها از همین طریق تغییرات شما را بررسی می‌کنند.

GitHub همچنین به‌طور خودکار برچسب‌هایی را برای کمک به بازبین‌ها به یک PR اختصاص می‌دهد. در صورت نیاز، شما نیز می‌توانید برچسب اضافه کنید. برای اطلاعات بیشتر، به افزودن و حذف برچسب‌های issue مراجعه کنید.

رسیدگی به بازخوردها به‌صورت محلی

  1. پس از اعمال تغییرات، commit قبلی خود را اصلاح (amend) کنید:

    git commit -a --amend
    • -a: همهٔ تغییرات را commit می‌کند
    • --amend: به‌جای ایجاد یک commit جدید، commit قبلی را اصلاح می‌کند

  2. در صورت نیاز، پیام commit خود را به‌روزرسانی کنید.

  3. با دستور git push origin <my_new_branch> تغییرات خود را ارسال کنید و آزمون‌های Netlify را دوباره اجرا کنید.

توجه:

اگر به‌جای amend از git commit -m استفاده کنید، باید پیش از ادغام، commitهای خود را squash کنید.

تغییرات بازبین‌ها

گاهی بازبین‌ها روی pull request شما commit می‌کنند. پیش از اعمال هر تغییر دیگری، آن commitها را دریافت (fetch) کنید.

  1. commitها را از fork راه دور خود دریافت کنید و شاخهٔ کاری خود را rebase کنید:

    git fetch origin
git rebase origin/<your-branch-name>

  2. پس از rebase، تغییرات جدید را با force-push به fork خود ارسال کنید:

    git push --force-with-lease origin <your-branch-name>

تداخل‌های ادغام و rebase

توجه:

برای اطلاعات بیشتر، به Git Branching - Basic Branching and Merging، Advanced Merging مراجعه کنید یا برای کمک در کانال Slack با نام #sig-docs بپرسید.

اگر مشارکت‌کنندهٔ دیگری در یک PR دیگر تغییراتی را در همان فایل commit کند، ممکن است یک تداخل ادغام (merge conflict) ایجاد شود. شما باید همهٔ تداخل‌های ادغام را در PR خود برطرف کنید.

  1. fork خود را به‌روزرسانی کنید و شاخهٔ محلی خود را rebase کنید:

    git fetch origin
git rebase origin/<your-branch-name>

    سپس تغییرات را با force-push به fork خود ارسال کنید:

    git push --force-with-lease origin <your-branch-name>

  2. تغییرات را از upstream/main در kubernetes/website دریافت (fetch) کنید و شاخهٔ خود را rebase کنید:

    git fetch upstream
git rebase upstream/main

  3. نتایج rebase را بررسی کنید:

    git status

    در نتیجه، تعدادی فایل به‌عنوان دارای تداخل علامت‌گذاری می‌شوند.

  4. هر فایل دارای تداخل را باز کنید و به دنبال نشانگرهای تداخل بگردید: >>>، <<< و ===. تداخل را برطرف کنید و نشانگر تداخل را حذف کنید.

توجه:

برای اطلاعات بیشتر، به How conflicts are presented مراجعه کنید.

  1. فایل‌ها را به مجموعه تغییرات (changeset) اضافه کنید:

    git add <filename>

  2. rebase را ادامه دهید:

    git rebase --continue

  3. در صورت نیاز، مراحل ۲ تا ۵ را تکرار کنید.

    پس از اعمال همهٔ commitها، دستور git status نشان می‌دهد که rebase کامل شده است.

  4. شاخه را با force-push به fork خود ارسال کنید:

    git push --force-with-lease origin <your-branch-name>

    دیگر هیچ تداخلی در pull request نمایش داده نمی‌شود.

ادغام کامیت‌ها (Squashing commits)

توجه:

برای اطلاعات بیشتر، Git Tools - Rewriting History را ببینید، یا در کانال Slack با نام #sig-docs درخواست کمک کنید.

اگر PR شما چند کامیت دارد، پیش از ادغام (merge) PR باید آن‌ها را در یک کامیت واحد ادغام (squash) کنید. می‌توانید تعداد کامیت‌های PR خود را در زبانه‌ی Commits در PR یا با اجرای دستور git log به‌صورت محلی بررسی کنید.

توجه:

این مبحث فرض می‌کند که vim ویرایشگر متن خط فرمان است.

  1. یک rebase تعاملی را آغاز کنید:

    git rebase -i HEAD~<number_of_commits_in_branch>

    ادغام کامیت‌ها نوعی rebase است. سوئیچ -i به git می‌گوید که می‌خواهید rebase را به‌صورت تعاملی انجام دهید. عبارت HEAD~<number_of_commits_in_branch مشخص می‌کند که برای rebase چند کامیت بررسی شود.

    خروجی مشابه زیر است:

    pick d875112ca Original commit
pick 4fa167b80 Address feedback 1
pick 7d54e15ee Address feedback 2

# Rebase 3d18sf680..7d54e15ee onto 3d183f680 (3 commands)

...

# These lines can be re-ordered; they are executed from top to bottom.

    بخش اول خروجی کامیت‌های موجود در rebase را فهرست می‌کند. بخش دوم گزینه‌های هر کامیت را فهرست می‌کند. تغییر واژه‌ی pick پس از اتمام rebase، وضعیت کامیت را تغییر می‌دهد.

    برای اهداف rebase، روی squash و pick تمرکز کنید.

توجه:

برای اطلاعات بیشتر، Interactive Mode را ببینید.

  1. ویرایش فایل را آغاز کنید.

    متن اصلی را تغییر دهید:

    pick d875112ca Original commit
pick 4fa167b80 Address feedback 1
pick 7d54e15ee Address feedback 2

    به:

    pick d875112ca Original commit
squash 4fa167b80 Address feedback 1
squash 7d54e15ee Address feedback 2

    این کار کامیت‌های 4fa167b80 Address feedback 1 و 7d54e15ee Address feedback 2 را در d875112ca Original commit ادغام می‌کند و تنها d875112ca Original commit را به‌عنوان بخشی از تاریخچه باقی می‌گذارد.

  2. فایل را ذخیره کنید و از آن خارج شوید.

  3. کامیت ادغام‌شده‌ی خود را push کنید:

    git push --force-with-lease origin <branch_name>

مشارکت در مخزن‌های دیگر

پروژه‌ی کوبرنتیز بیش از ۵۰ مخزن (repository) دارد. بسیاری از این مخزن‌ها شامل مستندات هستند: متن راهنمای کاربرمحور، پیام‌های خطا، مراجع API یا توضیحات داخل کد.

اگر متنی می‌بینید که مایلید آن را بهبود دهید، از GitHub برای جست‌وجو در تمام مخزن‌های سازمان کوبرنتیز استفاده کنید. این کار می‌تواند به شما کمک کند تشخیص دهید issue یا PR خود را کجا ارسال کنید.

هر مخزن فرایندها و رویه‌های مخصوص به خود را دارد. پیش از ثبت issue یا ارسال PR، فایل‌های README.md، CONTRIBUTING.md و code-of-conduct.md آن مخزن را، در صورت وجود، بخوانید.

بیشتر مخزن‌ها از قالب‌های (template) issue و PR استفاده می‌کنند. چند issue و PR باز را مرور کنید تا با فرایندهای آن تیم آشنا شوید. هنگام ثبت issue یا PR، قالب‌ها را با بیشترین جزئیات ممکن تکمیل کنید.
