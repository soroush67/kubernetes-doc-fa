شکل - آماده‌سازی برای مشارکت با محتوای جدید

شکل بالا اطلاعاتی را نشان می‌دهد که پیش از ارسال محتوای جدید باید بدانید. جزئیات این اطلاعات در ادامه آمده است.

اصول مشارکت {#contributing-basics}

  • مستندات کوبرنتیز را با Markdown بنویسید و سایت کوبرنتیز را با Hugo بسازید.
  • مستندات کوبرنتیز از CommonMark به‌عنوان گونه‌ی Markdown خود استفاده می‌کند.
  • منبع مستندات در GitHub قرار دارد. مستندات کوبرنتیز را می‌توانید در مسیر /content/en/docs/ بیابید. بخشی از مستندات مرجع به‌صورت خودکار از روی اسکریپت‌های موجود در دایرکتوری update-imported-docs/ تولید می‌شود.
  • انواع محتوای صفحه نحوه‌ی ارائه‌ی محتوای مستندات در Hugo را توصیف می‌کنند.
  • برای مشارکت در مستندات کوبرنتیز می‌توانید از shortcodeهای Docsy یا shortcodeهای سفارشی Hugo استفاده کنید.
  • افزون بر shortcodeهای استاندارد Hugo، در مستندات خود شماری shortcode سفارشی Hugo به کار می‌بریم تا نحوه‌ی ارائه‌ی محتوا را کنترل کنیم.
  • منبع مستندات در چندین زبان و در مسیر /content/ در دسترس است. هر زبان پوشه‌ی مخصوص خود را دارد که نام آن یک کد دوحرفی بر پایه‌ی استاندارد ISO 639-1 است. برای مثال، منبع مستندات انگلیسی در /content/en/docs/ ذخیره شده است.
  • برای اطلاعات بیشتر درباره‌ی مشارکت در مستندات به زبان‌های مختلف یا شروع یک ترجمه‌ی جدید، به بومی‌سازی مراجعه کنید.

پیش از شروع {#before-you-begin}

امضای CNCF CLA {#sign-the-cla}

همه‌ی مشارکت‌کنندگان کوبرنتیز باید راهنمای مشارکت‌کنندگان را بخوانند و توافقنامه‌ی مجوز مشارکت‌کننده (CLA) را امضا کنند.

درخواست‌های ادغام (pull request) مشارکت‌کنندگانی که CLA را امضا نکرده‌اند در آزمون‌های خودکار ناموفق می‌شوند. نام و ایمیلی که ارائه می‌کنید باید با مواردی که در git config شما ثبت شده است مطابقت داشته باشد، و نام و ایمیل git شما باید با مواردی که برای CNCF CLA استفاده شده است یکسان باشد.

انتخاب شاخه‌ی Git مناسب {#choose-which-git-branch-to-use}

هنگام باز کردن یک pull request باید از پیش بدانید که کار خود را بر پایه‌ی کدام شاخه (branch) انجام دهید.

سناریو شاخه
محتوای انگلیسی موجود یا جدید برای نسخه‌ی فعلی main
محتوا برای انتشار تغییر یک قابلیت شاخه‌ای که با نسخه‌ی major و minor مربوط به تغییر قابلیت متناظر است و از الگوی dev-<version> پیروی می‌کند. برای مثال، اگر قابلیتی در نسخه‌ی v1.37 تغییر می‌کند، تغییرات مستندات را به شاخه‌ی dev-1.37 اضافه کنید.
محتوا به زبان‌های دیگر (بومی‌سازی‌ها) از قرارداد همان بومی‌سازی پیروی کنید. برای اطلاعات بیشتر به راهبرد شاخه‌بندی بومی‌سازی مراجعه کنید.

اگر هنوز مطمئن نیستید کدام شاخه را انتخاب کنید، در کانال #sig-docs در Slack بپرسید.

توجه:

اگر pull request خود را ارسال کرده‌اید و می‌دانید که شاخه‌ی پایه اشتباه بوده است، شما (و فقط شما، به‌عنوان ارسال‌کننده) می‌توانید آن را تغییر دهید.

زبان‌ها در هر PR {#languages-per-pr}

هر PR را به یک زبان محدود کنید. اگر لازم است یک تغییر یکسان را در نمونه کد مشابه در چند زبان اعمال کنید، برای هر زبان یک PR جداگانه باز کنید.

ابزارهای مشارکت‌کنندگان {#tools-for-contributors}

دایرکتوری ابزارهای مشارکت‌کنندگان مستندات در مخزن kubernetes/website شامل ابزارهایی است که به روان‌تر شدن مسیر مشارکت شما کمک می‌کنند.

گام‌های بعدی

  • درباره‌ی ارسال مقالات وبلاگ مطالعه کنید.
