مستندسازی یک قابلیت برای انتشار

هر انتشار اصلی کوبرنتیز قابلیت‌های جدیدی را معرفی می‌کند که به مستندسازی نیاز دارند. انتشارهای جدید همچنین به‌روزرسانی‌هایی را برای قابلیت‌ها و مستندات موجود به همراه دارند (مانند ارتقای یک قابلیت از آلفا به بتا).

به‌طور کلی، SIG مسئول هر قابلیت، پیش‌نویس مستندات آن قابلیت را به‌صورت یک درخواست ادغام (pull request) به شاخهٔ توسعهٔ مربوط در مخزن kubernetes/website ارسال می‌کند و یکی از اعضای تیم SIG Docs بازخورد ویرایشی می‌دهد یا پیش‌نویس را مستقیماً ویرایش می‌کند. این بخش قراردادهای شاخه‌بندی و فرایندی را که هر دو گروه در طول یک انتشار به کار می‌برند شرح می‌دهد.

برای آشنایی با نحوهٔ اعلام قابلیت‌ها در وبلاگ، صفحهٔ اطلاع‌رسانی پس از انتشار را بخوانید.

برای مشارکت‌کنندگان مستندات

به‌طور کلی، مشارکت‌کنندگان مستندات برای یک انتشار محتوا را از صفر نمی‌نویسند. در عوض، با SIG سازندهٔ قابلیت جدید همکاری می‌کنند تا پیش‌نویس مستندات را بهبود دهند و آن را برای انتشار آماده کنند.

پس از آنکه قابلیتی را برای مستندسازی یا کمک به مستندسازی آن انتخاب کردید، دربارهٔ آن در کانال #sig-docs در Slack، در جلسهٔ هفتگی SIG Docs یا مستقیماً در PR ثبت‌شده از سوی SIG آن قابلیت سؤال کنید. اگر موافقت دریافت کردید، می‌توانید با یکی از روش‌های شرح‌داده‌شده در ثبت commit در PR شخص دیگر آن PR را ویرایش کنید.

آگاهی از قابلیت‌های آینده

برای آگاهی از قابلیت‌های آینده، در جلسهٔ هفتگی SIG Release شرکت کنید (برای اطلاع از جلسات پیش رو، صفحهٔ جامعه را ببینید) و مستندات ویژهٔ هر انتشار را در مخزن kubernetes/sig-release دنبال کنید. هر انتشار یک زیرشاخه در پوشهٔ /sig-release/tree/master/releases/ دارد. این زیرشاخه شامل زمان‌بندی انتشار، پیش‌نویس یادداشت‌های انتشار و سندی است که همهٔ اعضای تیم انتشار را فهرست می‌کند.

زمان‌بندی انتشار شامل پیوند به همهٔ اسناد، جلسات، صورت‌جلسه‌ها و نقاط عطف (milestones) مرتبط با انتشار است. این سند همچنین اطلاعاتی دربارهٔ اهداف و جدول زمانی انتشار و هرگونه فرایند ویژه‌ای که برای این انتشار برقرار است در بر دارد. در نزدیکی انتهای سند، چند اصطلاح مرتبط با انتشار تعریف شده‌اند.

این سند همچنین پیوندی به برگهٔ ردیابی قابلیت‌ها دارد که راه رسمی آگاهی از همهٔ قابلیت‌های جدیدی است که قرار است در انتشار گنجانده شوند.

سند تیم انتشار مشخص می‌کند که مسئولیت هر نقش انتشار با چه کسی است. اگر روشن نیست که دربارهٔ یک قابلیت یا پرسش مشخص باید با چه کسی صحبت کنید، یا در جلسهٔ انتشار شرکت کنید و پرسش خود را مطرح کنید، یا با سرپرست انتشار تماس بگیرید تا شما را به فرد مناسب ارجاع دهد.

پیش‌نویس یادداشت‌های انتشار جای خوبی برای آگاهی از قابلیت‌ها، تغییرات، منسوخ‌شدن‌ها و دیگر جزئیات انتشار است. این محتوا تا اواخر چرخهٔ انتشار نهایی نمی‌شود، بنابراین با احتیاط از آن استفاده کنید.

برگهٔ ردیابی قابلیت‌ها

برگهٔ ردیابی قابلیت‌ها برای هر انتشار کوبرنتیز همهٔ قابلیت‌هایی را فهرست می‌کند که برای آن انتشار برنامه‌ریزی شده‌اند. هر ردیف شامل نام قابلیت، پیوند به issue اصلی آن در GitHub، سطح پایداری آن (آلفا، بتا یا پایدار)، SIG و فرد مسئول پیاده‌سازی آن، نیاز یا عدم نیاز آن به مستندات، پیش‌نویس یادداشت انتشار آن قابلیت و ادغام‌شدن یا نشدن آن است. نکات زیر را در نظر داشته باشید:

  • قابلیت‌های بتا و پایدار معمولاً برای مستندسازی اولویت بیشتری نسبت به قابلیت‌های آلفا دارند.
  • آزمودن (و در نتیجه مستندسازی) قابلیتی که هنوز ادغام نشده یا دست‌کم در PR خود کامل تلقی نمی‌شود، دشوار است.
  • تشخیص اینکه آیا یک قابلیت به مستندات نیاز دارد یا نه، فرایندی دستی است. حتی اگر قابلیتی به‌عنوان نیازمند مستندات علامت‌گذاری نشده باشد، ممکن است لازم باشد آن را مستند کنید.

برای توسعه‌دهندگان یا دیگر اعضای SIG

این بخش شامل اطلاعاتی برای اعضای دیگر SIGهای کوبرنتیز است که قابلیت‌های جدید را برای یک انتشار مستند می‌کنند.

اگر عضو SIGی هستید که قابلیت جدیدی برای کوبرنتیز توسعه می‌دهد، باید با SIG Docs همکاری کنید تا مطمئن شوید قابلیت شما به‌موقع برای انتشار مستند می‌شود. برای اطمینان از جزئیات زمان‌بندی و مهلت‌ها، صفحه‌گسترده ردیابی قابلیت‌ها را بررسی کنید یا در کانال #sig-release در Slack کوبرنتیز پرس‌وجو کنید.

باز کردن یک PR جایگزین موقت

  1. یک درخواست ادغام پیش‌نویس روی شاخهٔ dev-1.37 در مخزن kubernetes/website باز کنید که شامل یک commit کوچک باشد و بعداً آن را اصلاح خواهید کرد. برای ایجاد درخواست ادغام پیش‌نویس، از منوی کشویی Create Pull Request گزینهٔ Create Draft Pull Request را انتخاب کنید و سپس روی Draft Pull Request کلیک کنید.
  2. توضیحات درخواست ادغام را ویرایش کنید تا پیوند به PR(های) kubernetes/kubernetes و issue(های) kubernetes/enhancements را در بر بگیرد.
  3. در issue مرتبط در kubernetes/enhancements دیدگاهی همراه با پیوند به PR بگذارید تا مسئول مستندات این انتشار مطلع شود که مستندات قابلیت در راه است و باید برای انتشار پیگیری شود.

اگر قابلیت شما به هیچ تغییری در مستندات نیاز ندارد، با اعلام این موضوع در کانال #sig-release در Slack، مطمئن شوید که تیم sig-release از آن آگاه است. اگر قابلیت به مستندات نیاز داشته باشد اما PR آن ایجاد نشده باشد، ممکن است قابلیت از نقطهٔ عطف حذف شود.

آماده بودن PR برای بازبینی

هنگامی که آماده شدید، PR جایگزین موقت خود را با مستندات قابلیت تکمیل کنید و وضعیت PR را از پیش‌نویس به ready for review تغییر دهید. برای علامت‌گذاری درخواست ادغام به‌عنوان آمادهٔ بازبینی، به کادر ادغام بروید و روی Ready for review کلیک کنید.

تمام تلاش خود را بکنید تا قابلیت خود و نحوهٔ استفاده از آن را شرح دهید. اگر برای ساختاردهی مستندات خود به کمک نیاز دارید، در کانال #sig-docs در Slack بپرسید.

پس از تکمیل محتوا، مسئول مستنداتی که به قابلیت شما اختصاص یافته است آن را بازبینی می‌کند. برای اطمینان از درستی فنی، ممکن است محتوا به بازبینی فنی از سوی SIG(های) مربوط نیز نیاز داشته باشد. با به‌کارگیری پیشنهادهای آن‌ها، محتوا را به وضعیت آماده برای انتشار برسانید.

اگر قابلیت شما به مستندات نیاز داشته باشد و نخستین پیش‌نویس محتوا دریافت نشود، ممکن است قابلیت از نقطهٔ عطف حذف شود.

Feature gateها {#ready-for-review-feature-gates}

اگر قابلیت شما در مرحلهٔ آلفا یا بتا است و پشت یک feature gate قرار دارد، باید برای آن یک فایل feature gate در مسیر content/en/docs/reference/command-line-tools-reference/feature-gates/ داشته باشید. نام فایل باید همان نام feature gate با پسوند .md باشد. برای اینکه بدانید فایل شما چه شکلی باید داشته باشد، می‌توانید به فایل‌های موجود در همین پوشه نگاه کنید. معمولاً یک پاراگراف کافی است؛ برای توضیحات طولانی‌تر، مستندات را در جای دیگری اضافه کنید و به آن پیوند دهید.

همچنین برای اطمینان از اینکه feature gate شما در جدول Feature gateهای آلفا/بتا نمایش داده می‌شود، جزئیات زیر را در front matter فایل توضیحات Markdown خود بگنجانید:

stages:
  - stage: <alpha/beta/stable/deprecated>  # Specify the development stage of the feature gate
    defaultValue: <true or false>     # Set to true if enabled by default, false otherwise
    fromVersion: <Version>            # Version from which the feature gate is available
    toVersion: <Version>              # (Optional) The version until which the feature gate is available

برای feature gateهای کاملاً جدید، توضیح جداگانه‌ای از feature gate نیز لازم است؛ یک فایل Markdown جدید در مسیر content/en/docs/reference/command-line-tools-reference/feature-gates/ ایجاد کنید (از فایل‌های دیگر به‌عنوان الگو استفاده کنید).

هنگامی که یک feature gate را از حالت «غیرفعال به‌طور پیش‌فرض» به «فعال به‌طور پیش‌فرض» تغییر می‌دهید، ممکن است لازم باشد مستندات دیگری را نیز (نه فقط فهرست feature gateها) تغییر دهید. مراقب عباراتی مانند این باشید: «فیلد exampleSetting یک فیلد بتا است و به‌طور پیش‌فرض غیرفعال است. می‌توانید با فعال کردن feature gate ProcessExampleThings آن را فعال کنید.»

اگر قابلیت شما به مرحلهٔ GA رسیده یا منسوخ شده است، یک مدخل stage اضافی در بلوک stages فایل توضیحات بگنجانید. مطمئن شوید که مراحل آلفا و بتا دست‌نخورده باقی می‌مانند. این کار feature gate را از جدول Feature gateهای آلفا/بتا به جدول Feature gateهای قابلیت‌های ارتقایافته یا منسوخ‌شده منتقل می‌کند. برای نمونه:

stages:

  • stage: alpha defaultValue: false fromVersion: "1.12" toVersion: "1.12"
  • stage: beta defaultValue: true fromVersion: "1.13"

Added a toVersion to the previous stage.

toVersion: "1.18"

Added 'stable' stage block to existing stages.

  • stage: stable defaultValue: true fromVersion: "1.19" toVersion: "1.27"

سرانجام، کوبرنتیز دیگر feature gate را به‌کلی در بر نخواهد داشت. برای نشان دادن حذف یک feature gate، مقدار removed: true را در front matter فایل توضیحات مربوط بگنجانید. با این تغییر، اطلاعات feature gate از بخش Feature gateهای قابلیت‌های ارتقایافته یا منسوخ‌شده به صفحه‌ای اختصاصی با عنوان Feature Gateها (حذف‌شده)، همراه با توضیحات آن، منتقل می‌شود.

بازبینی همهٔ PRها و آمادگی برای ادغام

اگر PR شما تا مهلت انتشار هنوز در شاخهٔ dev-1.37 ادغام نشده است، با مسئول مستندات انتشار همکاری کنید تا پیش از پایان مهلت ادغام شود. اگر قابلیت شما به مستندات نیاز داشته باشد و مستندات آماده نباشد، ممکن است قابلیت از نقطهٔ عطف حذف شود.
