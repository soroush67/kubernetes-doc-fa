رمزگذاری داده‌های محرمانه در حالت ذخیره‌شده

همهٔ APIهای کوبرنتیز که امکان نوشتن داده‌های ماندگار منابع API را فراهم می‌کنند، از رمزگذاری در حالت ذخیره‌شده (at-rest encryption) پشتیبانی می‌کنند. برای نمونه، می‌توانید رمزگذاری در حالت ذخیره‌شده را برای Secretها فعال کنید. این رمزگذاری علاوه بر هرگونه رمزگذاری در سطح سیستم است که برای کلاستر etcd یا برای فایل‌سیستم‌های میزبان‌هایی که kube-apiserver را روی آن‌ها اجرا می‌کنید، به کار رفته باشد.

این صفحه نشان می‌دهد که چگونه رمزگذاری داده‌های API را در حالت ذخیره‌شده فعال و پیکربندی کنید.

توجه:

این راهنما به رمزگذاری داده‌های منابعی می‌پردازد که از طریق API کوبرنتیز ذخیره می‌شوند. برای نمونه، می‌توانید آبجکت‌های Secret را، همراه با داده‌های کلید-مقداری که در خود دارند، رمزگذاری کنید.

اگر می‌خواهید داده‌های موجود در فایل‌سیستم‌هایی را رمزگذاری کنید که در کانتینرها mount می‌شوند، باید یکی از این دو کار را انجام دهید:

  • از یک راهکار یکپارچه‌سازی ذخیره‌سازی استفاده کنید که حجم‌های رمزگذاری‌شده فراهم می‌کند
  • داده‌ها را درون برنامهٔ خودتان رمزگذاری کنید

پیش از شروع

باید یک کلاستر کوبرنتیز داشته باشید و ابزار خط فرمان kubectl باید برای ارتباط با کلاستر شما پیکربندی شده باشد. توصیه می‌شود این آموزش را روی کلاستری اجرا کنید که دست‌کم دو نود داشته باشد که نقش میزبان control plane را ندارند. اگر هنوز کلاستری ندارید، می‌توانید با استفاده از minikube یکی بسازید یا از یکی از این محیط‌های آزمایشی کوبرنتیز استفاده کنید:

  • iximiuz Labs

  • Killercoda

  • KodeKloud

  • در این راهنما فرض شده است که سرور API کوبرنتیز را به‌صورت یک پاد ایستا روی هر نود control plane اجرا می‌کنید.

  • control plane کلاستر شما باید از etcd نسخهٔ v3.x (نسخهٔ اصلی ۳ با هر نسخهٔ فرعی) استفاده کند.

  • برای رمزگذاری یک منبع سفارشی، کلاستر شما باید کوبرنتیز نسخهٔ v1.26 یا جدیدتر را اجرا کند.

  • برای استفاده از نویسهٔ عام (wildcard) در تطبیق منابع، کلاستر شما باید کوبرنتیز نسخهٔ v1.27 یا جدیدتر را اجرا کند.

تشخیص اینکه آیا رمزگذاری در حالت ذخیره‌شده از قبل فعال است {#determining-whether-encryption-at-rest-is-already-enabled}

سرور API به‌طور پیش‌فرض نمایش متن ساده (plain-text) منابع را بدون هیچ رمزگذاری‌ای در etcd ذخیره می‌کند.

فرایند kube-apiserver آرگومانی به نام --encryption-provider-config می‌پذیرد که مسیر یک فایل پیکربندی را مشخص می‌کند. اگر چنین فایلی را مشخص کنید، محتوای آن تعیین می‌کند که داده‌های API کوبرنتیز چگونه در etcd رمزگذاری شوند. اگر kube-apiserver را بدون آرگومان خط فرمان --encryption-provider-config اجرا می‌کنید، رمزگذاری در حالت ذخیره‌شده برای شما فعال نیست. همچنین اگر kube-apiserver را با آرگومان --encryption-provider-config اجرا می‌کنید، ولی فایلی که به آن ارجاع داده شده است فراهم‌کنندهٔ identity را به‌عنوان نخستین فراهم‌کنندهٔ رمزگذاری در فهرست مشخص می‌کند، باز هم رمزگذاری در حالت ذخیره‌شده فعال نیست (فراهم‌کنندهٔ پیش‌فرض identity هیچ‌گونه حفاظتی از محرمانگی داده‌ها فراهم نمی‌کند.)

اگر kube-apiserver را با آرگومان خط فرمان --encryption-provider-config اجرا می‌کنید و فایلی که به آن ارجاع داده شده است، فراهم‌کننده‌ای غیر از identity را به‌عنوان نخستین فراهم‌کنندهٔ رمزگذاری در فهرست مشخص می‌کند، رمزگذاری در حالت ذخیره‌شده از قبل برای شما فعال است. با این حال، این بررسی نشان نمی‌دهد که آیا مهاجرت قبلی به ذخیره‌سازی رمزگذاری‌شده با موفقیت انجام شده است یا نه. اگر مطمئن نیستید، بخش اطمینان از رمزگذاری همهٔ داده‌های مرتبط را ببینید.

آشنایی با پیکربندی رمزگذاری در حالت ذخیره‌شده

---
#
# هشدار: این یک پیکربندی نمونه است.
#        از آن برای کلاستر خودتان استفاده نکنید!
#
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
  - resources:
      - secrets
      - configmaps
      - pandas.awesome.bears.example # یک API منبع سفارشی
    providers:
      # این پیکربندی محرمانگی داده‌ها را تأمین نمی‌کند. نخستین
      # فراهم‌کنندهٔ پیکربندی‌شده سازوکار «identity» را مشخص می‌کند که
      # منابع را به‌صورت متن ساده ذخیره می‌کند.
      #
      - identity: {} # متن ساده؛ به بیان دیگر، بدون هیچ رمزگذاری
      - aesgcm:
          keys:
            - name: key1
              secret: c2VjcmV0IGlzIHNlY3VyZQ==
            - name: key2
              secret: dGhpcyBpcyBwYXNzd29yZA==
      - aescbc:
          keys:
            - name: key1
              secret: c2VjcmV0IGlzIHNlY3VyZQ==
            - name: key2
              secret: dGhpcyBpcyBwYXNzd29yZA==
      - secretbox:
          keys:
            - name: key1
              secret: YWJjZGVmZ2hpamtsbW5vcHFyc3R1dnd4eXoxMjM0NTY=
  - resources:
      - events
    providers:
      - identity: {} # رویدادها رمزگذاری نشوند، هرچند در ادامه *.* مشخص شده است
  - resources:
      - '*.apps' # تطبیق با نویسهٔ عام به کوبرنتیز ۱.۲۷ یا جدیدتر نیاز دارد
    providers:
      - aescbc:
          keys:
          - name: key2
            secret: c2VjcmV0IGlzIHNlY3VyZSwgb3IgaXMgaXQ/Cg==
  - resources:
      - '*.*' # تطبیق با نویسهٔ عام به کوبرنتیز ۱.۲۷ یا جدیدتر نیاز دارد
    providers:
      - aescbc:
          keys:
          - name: key3
            secret: c2VjcmV0IGlzIHNlY3VyZSwgSSB0aGluaw==

هر عضو آرایهٔ resources یک پیکربندی جداگانه و کامل است. فیلد resources.resources آرایه‌ای از نام منابع کوبرنتیز (به شکل resource یا resource.group) است که باید رمزگذاری شوند؛ مانند Secretها، ConfigMapها یا منابع دیگر.

اگر منابع سفارشی به EncryptionConfiguration افزوده شوند و نسخهٔ کلاستر ۱.۲۶ یا جدیدتر باشد، همهٔ منابع سفارشی تازه‌ایجادشده‌ای که در EncryptionConfiguration ذکر شده‌اند رمزگذاری خواهند شد. منابع سفارشی‌ای که پیش از آن نسخه و آن پیکربندی در etcd وجود داشته‌اند، تا زمانی که دوباره در ذخیره‌ساز نوشته نشوند، رمزگذاری‌نشده باقی می‌مانند. این رفتار با رفتار منابع داخلی یکسان است. بخش اطمینان از رمزگذاری همهٔ Secretها را ببینید.

آرایهٔ providers فهرستی مرتب از فراهم‌کننده‌های رمزگذاری ممکن برای APIهایی است که فهرست کرده‌اید. هر فراهم‌کننده از چند کلید پشتیبانی می‌کند. برای رمزگشایی، کلیدها به ترتیب امتحان می‌شوند و اگر این فراهم‌کننده نخستین فراهم‌کنندهٔ فهرست باشد، از نخستین کلید آن برای رمزگذاری استفاده می‌شود.

در هر مدخل فقط یک نوع فراهم‌کننده را می‌توان مشخص کرد (می‌توان identity یا aescbc را تعیین کرد، اما نه هر دو را در یک عضو). نخستین فراهم‌کنندهٔ فهرست برای رمزگذاری منابعی به کار می‌رود که در ذخیره‌ساز نوشته می‌شوند. هنگام خواندن منابع از ذخیره‌ساز، هر فراهم‌کننده‌ای که با داده‌های ذخیره‌شده مطابقت داشته باشد، به ترتیب برای رمزگشایی داده‌ها تلاش می‌کند. اگر هیچ فراهم‌کننده‌ای به‌دلیل ناهمخوانی در قالب یا کلید محرمانه نتواند داده‌های ذخیره‌شده را بخواند، خطایی برگردانده می‌شود که مانع دسترسی کلاینت‌ها به آن منبع می‌شود.

پیکربندی EncryptionConfiguration از نویسه‌های عام برای مشخص کردن منابعی که باید رمزگذاری شوند پشتیبانی می‌کند. برای رمزگذاری همهٔ منابع یک گروه از '*.<group>' استفاده کنید (برای نمونه '*.apps' در مثال بالا) و برای رمزگذاری همهٔ منابع از '*.*'. با '*.' می‌توان همهٔ منابع گروه هسته (core) را رمزگذاری کرد. الگوی '*.*' همهٔ منابع را رمزگذاری می‌کند، حتی منابع سفارشی‌ای که پس از راه‌اندازی سرور API افزوده می‌شوند.

توجه:

استفاده از نویسه‌های عامی که در یک فهرست منابع یا در چند مدخل با یکدیگر هم‌پوشانی دارند مجاز نیست، زیرا بخشی از پیکربندی بی‌اثر خواهد شد. ترتیب پردازش و اولویت فهرست resources بر اساس ترتیبی تعیین می‌شود که در پیکربندی آمده است.

اگر نویسهٔ عامی دارید که منابع را پوشش می‌دهد و می‌خواهید نوع خاصی از منبع را از رمزگذاری در حالت ذخیره‌شده مستثنا کنید، می‌توانید یک عضو جداگانه به آرایهٔ resources با نام منبعی که می‌خواهید مستثنا شود اضافه کنید و پس از آن، یک عضو آرایهٔ providers قرار دهید که در آن فراهم‌کنندهٔ identity را مشخص کرده‌اید. این عضو را طوری به فهرست اضافه کنید که پیش از پیکربندی‌ای قرار گیرد که رمزگذاری را در آن مشخص کرده‌اید (یعنی فراهم‌کننده‌ای غیر از identity).

برای نمونه، اگر '*.*' فعال است و می‌خواهید رویدادها (Events) و ConfigMapها را از رمزگذاری مستثنا کنید، یک عضو جدید را در جایگاهی پیش‌تر به resources اضافه کنید و پس از آن، عضو آرایهٔ providers را با identity به‌عنوان فراهم‌کننده قرار دهید. مدخل خاص‌تر باید پیش از مدخل دارای نویسهٔ عام بیاید.

عضو جدید چیزی شبیه به این خواهد بود:

  ...
  - resources:
      - configmaps. # specifically from the core API group,
                    # because of trailing "."
      - events
    providers:
      - identity: {}
  # and then other entries in resources

اطمینان حاصل کنید که این استثنا پیش از عضو دارای نویسهٔ عام '*.*' در آرایهٔ resources آمده باشد تا بر آن اولویت داشته باشد.

برای اطلاعات بیشتر دربارهٔ ساختار EncryptionConfiguration، به API پیکربندی رمزگذاری مراجعه کنید.

احتیاط:

اگر منبعی با پیکربندی رمزگذاری قابل خواندن نباشد (به‌دلیل تغییر کلیدها) و نتوانید یک پیکربندی سالم را بازیابی کنید، تنها راه چاره این است که آن مدخل را مستقیماً از etcd زیرین حذف کنید.

هر فراخوانی API کوبرنتیز که بخواهد آن منبع را بخواند، تا زمانی که منبع حذف نشود یا یک کلید رمزگشایی معتبر فراهم نشود، با شکست روبه‌رو خواهد شد.

فراهم‌کننده‌های موجود {#providers}

پیش از آنکه رمزگذاری در حالت ذخیره‌شده را برای داده‌های API کوبرنتیز در کلاستر خود پیکربندی کنید، باید مشخص کنید که از کدام فراهم‌کننده یا فراهم‌کننده‌ها استفاده خواهید کرد.

جدول زیر هر یک از فراهم‌کننده‌های موجود را شرح می‌دهد.

kms v1 (منسوخ‌شده از کوبرنتیز v1.28) از طرح رمزگذاری پوششی (envelope encryption) با یک DEK برای هر منبع استفاده می‌کند. قوی‌ترین کند (در مقایسه با kms نسخهٔ ۲) ۳۲ بایت

داده‌ها با کلیدهای رمزگذاری داده (DEK) و با الگوریتم AES-GCM رمزگذاری می‌شوند؛ کلیدهای DEK نیز بر اساس پیکربندی سرویس مدیریت کلید (KMS) با کلیدهای رمزگذاری کلید (KEK) رمزگذاری می‌شوند. کوبرنتیز برای هر رمزگذاری، یک DEK جدید را از یک بذر (seed) محرمانه تولید می‌کند. هر بار که KEK چرخانده شود، این بذر نیز چرخانده می‌شود.
اگر از یک ابزار شخص ثالث برای مدیریت کلید استفاده می‌کنید، گزینهٔ مناسبی است. از کوبرنتیز v1.29 به‌صورت پایدار در دسترس است.
نحوهٔ پیکربندی فراهم‌کنندهٔ KMS V2 را بخوانید.
secretbox XSalsa20 و Poly1305 قوی سریع‌تر ۳۲ بایت
از فناوری‌های رمزگذاری نسبتاً جدیدی استفاده می‌کند که ممکن است در محیط‌هایی که به سطح بالایی از بازبینی نیاز دارند، پذیرفتنی تلقی نشوند. مادهٔ کلید از میزبان control plane قابل دسترسی است.

اگر چیز دیگری مشخص نکنید، فراهم‌کنندهٔ identity پیش‌فرض است. فراهم‌کنندهٔ identity داده‌های ذخیره‌شده را رمزگذاری نمی‌کند و هیچ حفاظت اضافه‌ای از محرمانگی فراهم نمی‌کند.

ذخیره‌سازی کلید

ذخیره‌سازی محلی کلید

رمزگذاری داده‌های محرمانه با کلیدی که به‌صورت محلی مدیریت می‌شود، از داده‌ها در برابر نفوذ به etcd محافظت می‌کند، اما در برابر نفوذ به میزبان محافظتی فراهم نمی‌کند. از آنجا که کلیدهای رمزگذاری در فایل YAML مربوط به EncryptionConfiguration روی میزبان ذخیره می‌شوند، یک مهاجم ماهر می‌تواند به آن فایل دسترسی پیدا کند و کلیدهای رمزگذاری را استخراج کند.

ذخیره‌سازی مدیریت‌شدهٔ کلید (KMS) {#kms-key-storage}

فراهم‌کنندهٔ KMS از رمزگذاری پوششی استفاده می‌کند: کوبرنتیز منابع را با یک کلید داده رمزگذاری می‌کند و سپس آن کلید داده را با سرویس رمزگذاری مدیریت‌شده رمزگذاری می‌کند. کوبرنتیز برای هر منبع یک کلید دادهٔ یکتا تولید می‌کند. سرور API نسخهٔ رمزگذاری‌شدهٔ کلید داده را در کنار متن رمزشده (ciphertext) در etcd ذخیره می‌کند؛ هنگام خواندن منبع، سرور API سرویس رمزگذاری مدیریت‌شده را فراخوانی می‌کند و هم متن رمزشده و هم کلید دادهٔ (رمزگذاری‌شده) را در اختیار آن قرار می‌دهد. درون سرویس رمزگذاری مدیریت‌شده، فراهم‌کننده با استفاده از یک کلید رمزگذاری کلید، کلید داده را رمزگشایی می‌کند و در نهایت متن ساده را بازیابی می‌کند. ارتباط میان control plane و KMS باید در حین انتقال محافظت شود؛ برای نمونه با TLS.

استفاده از رمزگذاری پوششی موجب وابستگی به کلید رمزگذاری کلید می‌شود که در کوبرنتیز ذخیره نمی‌شود. در حالت KMS، مهاجمی که قصد دارد به مقادیر متن ساده دسترسی غیرمجاز پیدا کند، باید هم به etcd و هم به فراهم‌کنندهٔ شخص ثالث KMS نفوذ کند.

محافظت از کلیدهای رمزگذاری

باید تدابیر مناسبی برای محافظت از اطلاعات محرمانه‌ای که امکان رمزگشایی را فراهم می‌کنند بیندیشید؛ چه این اطلاعات یک کلید رمزگذاری محلی باشد و چه توکن احراز هویتی که به سرور API اجازهٔ فراخوانی KMS را می‌دهد.

حتی وقتی مدیریت استفاده و چرخهٔ عمر کلید (یا کلیدهای) اصلی رمزگذاری را به یک فراهم‌کننده می‌سپارید، همچنان مسئولیت دارید اطمینان حاصل کنید که کنترل‌های دسترسی و دیگر تدابیر امنیتی سرویس رمزگذاری مدیریت‌شده با نیازهای امنیتی شما متناسب است.

رمزگذاری داده‌ها {#encrypting-your-data}

تولید کلید رمزگذاری {#generate-key-no-kms}

در مراحل زیر فرض شده است که از KMS استفاده نمی‌کنید و در نتیجه باید یک کلید رمزگذاری تولید کنید. اگر از قبل کلید رمزگذاری دارید، مستقیماً به بخش نوشتن فایل پیکربندی رمزگذاری بروید.

احتیاط:

ذخیره کردن کلید رمزگذاری خام در EncryptionConfig، در مقایسه با نبود رمزگذاری، وضعیت امنیتی شما را تنها به میزان اندکی بهبود می‌بخشد.

برای محرمانگی بیشتر، استفاده از فراهم‌کنندهٔ kms را در نظر بگیرید، زیرا این فراهم‌کننده به کلیدهایی متکی است که بیرون از کلاستر کوبرنتیز شما نگهداری می‌شوند. پیاده‌سازی‌های kms می‌توانند با ماژول‌های امنیتی سخت‌افزاری (HSM) یا با سرویس‌های رمزگذاری‌ای که ارائه‌دهندهٔ ابری شما مدیریت می‌کند کار کنند.

برای آشنایی با راه‌اندازی رمزگذاری در حالت ذخیره‌شده با استفاده از KMS، به استفاده از یک فراهم‌کنندهٔ KMS برای رمزگذاری داده‌ها مراجعه کنید. افزونهٔ فراهم‌کنندهٔ KMS که از آن استفاده می‌کنید نیز ممکن است مستندات اختصاصی بیشتری داشته باشد.

ابتدا یک کلید رمزگذاری جدید تولید کنید و سپس آن را با base64 کدگذاری کنید:

Linux

یک کلید تصادفی ۳۲ بایتی تولید و آن را با base64 کدگذاری کنید. می‌توانید از این دستور استفاده کنید:

head -c 32 /dev/urandom | base64

اگر می‌خواهید از منبع آنتروپی سخت‌افزاری داخلی رایانهٔ خود استفاده کنید، می‌توانید به‌جای /dev/urandom از /dev/hwrng استفاده کنید. همهٔ دستگاه‌های لینوکسی مولد تصادفی سخت‌افزاری ندارند.

macOS

یک کلید تصادفی ۳۲ بایتی تولید و آن را با base64 کدگذاری کنید. می‌توانید از این دستور استفاده کنید:

head -c 32 /dev/urandom | base64
Windows

یک کلید تصادفی ۳۲ بایتی تولید و آن را با base64 کدگذاری کنید. می‌توانید از این دستور استفاده کنید:

# Do not run this in a session where you have set a random number
# generator seed.
[Convert]::ToBase64String((1..32|%{[byte](Get-Random -Max 256)}))
توجه:

کلید رمزگذاری را محرمانه نگه دارید؛ هم در زمان تولید آن و در حالت مطلوب، حتی پس از آنکه دیگر به‌طور فعال از آن استفاده نمی‌کنید.

تکثیر کلید رمزنگاری

با استفاده از یک سازوکار امن برای انتقال فایل، یک نسخه از آن کلید رمزنگاری را در اختیار همه‌ی میزبان‌های دیگر control plane قرار دهید.

دست‌کم از رمزنگاری در حین انتقال، برای نمونه پوسته‌ی امن (SSH)، استفاده کنید. برای امنیت بیشتر، میان میزبان‌ها از رمزنگاری نامتقارن استفاده کنید یا رویکرد خود را تغییر دهید تا به رمزنگاری KMS متکی باشید.

نوشتن فایل پیکربندی رمزنگاری

احتیاط:

فایل پیکربندی رمزنگاری ممکن است کلیدهایی داشته باشد که می‌توانند محتوای etcd را رمزگشایی کنند. اگر این فایل پیکربندی هر نوع داده‌ی کلیدی در خود دارد، باید مجوزهای دسترسی را روی همه‌ی میزبان‌های control plane به‌درستی محدود کنید تا فقط کاربری که kube-apiserver را اجرا می‌کند بتواند این پیکربندی را بخواند.

یک فایل پیکربندی رمزنگاری جدید ایجاد کنید. محتوای آن باید مشابه زیر باشد:

---
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
  - resources:
      - secrets
      - configmaps
      - pandas.awesome.bears.example
    providers:
      - aescbc:
          keys:
            - name: key1
              # See the following text for more details about the secret value
              secret: <BASE 64 ENCODED SECRET>
      - identity: {} # this fallback allows reading unencrypted secrets;
                     # for example, during initial migration

برای ایجاد یک کلید رمزنگاری جدید (که از KMS استفاده نمی‌کند)، بخش تولید کلید رمزنگاری را ببینید.

استفاده از فایل پیکربندی رمزنگاری جدید

باید فایل پیکربندی رمزنگاری جدید را در پاد ایستای kube-apiserver سوار (mount) کنید. در ادامه نمونه‌ای از نحوه‌ی انجام این کار آمده است:

  1. فایل پیکربندی رمزنگاری جدید را در مسیر /etc/kubernetes/enc/enc.yaml روی نود control plane ذخیره کنید.

  2. مانیفست پاد ایستای kube-apiserver را در مسیر /etc/kubernetes/manifests/kube-apiserver.yaml ویرایش کنید تا مشابه زیر شود:

    ---
#
# This is a fragment of a manifest for a static Pod.
# Check whether this is correct for your cluster and for your API server.
#
apiVersion: v1
kind: Pod
metadata:
  annotations:
    kubeadm.kubernetes.io/kube-apiserver.advertise-address.endpoint: 10.20.30.40:443
  creationTimestamp: null
  labels:
    app.kubernetes.io/component: kube-apiserver
    tier: control-plane
  name: kube-apiserver
  namespace: kube-system
spec:
  containers:
  - command:
    - kube-apiserver
    ...
    - --encryption-provider-config=/etc/kubernetes/enc/enc.yaml  # add this line
    volumeMounts:
    ...
    - name: enc                           # add this line
      mountPath: /etc/kubernetes/enc      # add this line
      readOnly: true                      # add this line
    ...
  volumes:
  ...
  - name: enc                             # add this line
    hostPath:                             # add this line
      path: /etc/kubernetes/enc           # add this line
      type: DirectoryOrCreate             # add this line
  ...

  3. سرور API خود را دوباره راه‌اندازی کنید.

احتیاط:

فایل پیکربندی شما کلیدهایی دارد که می‌توانند محتوای etcd را رمزگشایی کنند؛ بنابراین باید مجوزهای دسترسی را روی نودهای control plane به‌درستی محدود کنید تا فقط کاربری که kube-apiserver را اجرا می‌کند بتواند آن را بخواند.

اکنون رمزنگاری برای یک میزبان control plane برقرار شده است. یک کلاستر معمول کوبرنتیز چندین میزبان control plane دارد، پس کارهای بیشتری باقی مانده است.

پیکربندی مجدد سایر میزبان‌های control plane {#api-server-config-update-more}

اگر در کلاستر خود چندین سرور API دارید، باید تغییرات را به‌نوبت روی هر سرور API اعمال کنید.

احتیاط:

در پیکربندی‌هایی از کلاستر که دو یا چند نود control plane دارند، پیکربندی رمزنگاری باید روی همه‌ی نودهای control plane یکسان باشد.

اگر پیکربندی ارائه‌دهنده‌ی رمزنگاری میان نودهای control plane تفاوت داشته باشد، ممکن است kube-apiserver نتواند داده‌ها را رمزگشایی کند.

هنگامی که قصد به‌روزرسانی پیکربندی رمزنگاری کلاستر خود را دارید، طوری برنامه‌ریزی کنید که سرورهای API در control plane همواره بتوانند داده‌های ذخیره‌شده را رمزگشایی کنند (حتی در میانه‌ی اعمال تدریجی تغییر).

اطمینان حاصل کنید که روی هر میزبان control plane از پیکربندی رمزنگاری یکسانی استفاده می‌کنید.

بررسی رمزنگاری داده‌های تازه نوشته‌شده {#verifying-that-data-is-encrypted}

داده‌ها هنگام نوشته شدن در etcd رمزنگاری می‌شوند. پس از راه‌اندازی مجدد kube-apiserver، هر Secret تازه ایجادشده یا به‌روزشده (یا سایر انواع منابعی که در EncryptionConfiguration پیکربندی شده‌اند) باید هنگام ذخیره‌سازی رمزنگاری شود.

برای بررسی این موضوع، می‌توانید با برنامه‌ی خط فرمان etcdctl محتوای داده‌های secret خود را بازیابی کنید.

این مثال نشان می‌دهد که چگونه این موضوع را برای رمزنگاری API مربوط به Secret بررسی کنید.

  1. یک Secret جدید به نام secret1 در فضای نام default ایجاد کنید:

    kubectl create secret generic secret1 -n default --from-literal=mykey=mydata

  2. با ابزار خط فرمان etcdctl، آن Secret را از etcd بخوانید:

    ETCDCTL_API=3 etcdctl get /registry/secrets/default/secret1 [...] | hexdump -C

    در اینجا [...] باید آرگومان‌های اضافی لازم برای اتصال به سرور etcd باشد.

    برای نمونه:

    ETCDCTL_API=3 etcdctl \
   --cacert=/etc/kubernetes/pki/etcd/ca.crt   \
   --cert=/etc/kubernetes/pki/etcd/server.crt \
   --key=/etc/kubernetes/pki/etcd/server.key  \
   get /registry/secrets/default/secret1 | hexdump -C

    خروجی مشابه زیر است (به‌صورت خلاصه):

  3. بررسی کنید که Secret ذخیره‌شده با پیشوند k8s:enc:aescbc:v1: شروع شود؛ این پیشوند نشان می‌دهد که ارائه‌دهنده‌ی aescbc داده‌ی حاصل را رمزنگاری کرده است. مطمئن شوید نام کلیدی که در etcd نمایش داده می‌شود با نام کلید تعیین‌شده در EncryptionConfiguration که پیش‌تر به آن اشاره شد مطابقت دارد. در این مثال می‌بینید که کلید رمزنگاری با نام key1 هم در etcd و هم در EncryptionConfiguration استفاده شده است.

  4. بررسی کنید که Secret هنگام بازیابی از طریق API به‌درستی رمزگشایی شود:

    kubectl get secret secret1 -n default -o yaml

    خروجی باید شامل mykey: bXlkYXRh باشد که همان محتوای mydata است که با base64 کدگذاری شده است. برای آشنایی با نحوه‌ی رمزگشایی کامل Secret، بخش رمزگشایی یک Secret را بخوانید.

اطمینان از رمزنگاری همه‌ی داده‌های مرتبط {#ensure-all-secrets-are-encrypted}

اغلب کافی نیست فقط مطمئن شوید که آبجکت‌های جدید رمزنگاری می‌شوند؛ بلکه می‌خواهید این رمزنگاری روی آبجکت‌هایی که از قبل ذخیره شده‌اند نیز اعمال شود.

در این مثال، کلاستر خود را طوری پیکربندی کرده‌اید که Secretها هنگام نوشته شدن رمزنگاری شوند. اجرای عملیات جایگزینی (replace) برای هر Secret، محتوای آن را در حالت ذخیره (at rest) رمزنگاری می‌کند، در حالی که خود آبجکت‌ها بدون تغییر می‌مانند.

می‌توانید این تغییر را روی همه‌ی Secretهای کلاستر خود اعمال کنید:

# Run this as an administrator that can read and write all Secrets
kubectl get secrets --all-namespaces -o json | kubectl replace -f -

فرمان بالا همه‌ی Secretها را می‌خواند و سپس آن‌ها را با همان داده‌ها به‌روزرسانی می‌کند تا رمزنگاری سمت سرور اعمال شود.

توجه:

اگر به‌دلیل نوشتن متعارض خطایی رخ داد، فرمان را دوباره اجرا کنید. اجرای چندباره‌ی این فرمان بی‌خطر است.

در کلاسترهای بزرگ‌تر، ممکن است بخواهید Secretها را بر اساس فضای نام تقسیم کنید یا به‌روزرسانی را با یک اسکریپت انجام دهید.

جلوگیری از بازیابی به‌صورت متن ساده {#cleanup-all-secrets-encrypted}

اگر می‌خواهید مطمئن شوید که دسترسی به یک نوع API خاص فقط به‌صورت رمزنگاری‌شده انجام می‌شود، می‌توانید توانایی سرور API در خواندن داده‌های پشتیبان آن API به‌صورت متن ساده را حذف کنید.

هشدار:

اعمال این تغییر مانع از آن می‌شود که سرور API منابعی را بازیابی کند که به‌عنوان رمزنگاری‌شده در حالت ذخیره علامت‌گذاری شده‌اند، اما در واقع به‌صورت رمزنگاری‌نشده ذخیره شده‌اند.

هنگامی که رمزنگاری در حالت ذخیره را برای یک API پیکربندی کرده‌اید (برای نمونه، نوع API به نام Secret که نماینده‌ی منابع secrets در گروه API هسته است)، باید اطمینان حاصل کنید که همه‌ی آن منابع در این کلاستر واقعاً در حالت ذخیره رمزنگاری شده‌اند. پیش از ادامه‌ی گام‌های بعدی این موضوع را بررسی کنید.

پس از آنکه همه‌ی Secretهای کلاستر شما رمزنگاری شدند، می‌توانید بخش identity را از پیکربندی رمزنگاری حذف کنید. برای نمونه:

---
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
  - resources:
      - secrets
    providers:
      - aescbc:
          keys:
            - name: key1
              secret: <BASE 64 ENCODED SECRET>
      - identity: {} # REMOVE THIS LINE

…و سپس هر سرور API را به‌نوبت دوباره راه‌اندازی کنید. این تغییر مانع از آن می‌شود که سرور API، حتی به‌طور تصادفی، به یک Secret ذخیره‌شده به‌صورت متن ساده دسترسی پیدا کند.

چرخش کلید رمزگشایی {#rotating-a-decryption-key}

تغییر کلید رمزنگاری در کوبرنتیز بدون ایجاد وقفه در سرویس به یک عملیات چندمرحله‌ای نیاز دارد، به‌ویژه در یک استقرار با دسترس‌پذیری بالا که در آن چندین فرایند kube-apiserver در حال اجرا هستند.

  1. یک کلید جدید تولید کنید و آن را به‌عنوان دومین ورودی کلید برای ارائه‌دهنده‌ی فعلی، روی همه‌ی نودهای control plane اضافه کنید.
  2. همه‌ی فرایندهای kube-apiserver را دوباره راه‌اندازی کنید تا مطمئن شوید هر سرور می‌تواند هر داده‌ای را که با کلید جدید رمزنگاری شده است رمزگشایی کند.
  3. از کلید رمزنگاری جدید یک نسخه‌ی پشتیبان امن تهیه کنید. اگر همه‌ی نسخه‌های این کلید را از دست بدهید، باید همه‌ی منابعی را که با کلید ازدست‌رفته رمزنگاری شده‌اند حذف کنید و ممکن است بارهای کاری در مدتی که رمزنگاری در حالت ذخیره مختل است، آن‌طور که انتظار می‌رود کار نکنند.
  4. کلید جدید را به اولین ورودی آرایه‌ی keys تبدیل کنید تا برای رمزنگاری در حالت ذخیره‌ی نوشتن‌های جدید استفاده شود.
  5. همه‌ی فرایندهای kube-apiserver را دوباره راه‌اندازی کنید تا مطمئن شوید هر میزبان control plane اکنون با کلید جدید رمزنگاری می‌کند.
  6. به‌عنوان یک کاربر دارای دسترسی ویژه، فرمان kubectl get secrets --all-namespaces -o json | kubectl replace -f - را اجرا کنید تا همه‌ی Secretهای موجود با کلید جدید رمزنگاری شوند.
  7. پس از آنکه همه‌ی Secretهای موجود را برای استفاده از کلید جدید به‌روزرسانی کردید و از کلید جدید یک نسخه‌ی پشتیبان امن تهیه کردید، کلید رمزگشایی قدیمی را از پیکربندی حذف کنید.

رمزگشایی همه‌ی داده‌ها {#decrypting-all-data}

این مثال نشان می‌دهد که چگونه رمزنگاری API مربوط به Secret را در حالت ذخیره متوقف کنید. اگر انواع دیگری از API را رمزنگاری می‌کنید، گام‌ها را متناسب با آن‌ها تنظیم کنید.

برای غیرفعال کردن رمزنگاری در حالت ذخیره، ارائه‌دهنده‌ی identity را به‌عنوان اولین ورودی در فایل پیکربندی رمزنگاری خود قرار دهید:

---
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
  - resources:
      - secrets
      # list any other resources here that you previously were
      # encrypting at rest
    providers:
      - identity: {} # add this line
      - aescbc:
          keys:
            - name: key1
              secret: <BASE 64 ENCODED SECRET> # keep this in place
                                               # make sure it comes after "identity"

سپس فرمان زیر را اجرا کنید تا رمزگشایی همه‌ی Secretها اجباری شود:

kubectl get secrets --all-namespaces -o json | kubectl replace -f -

پس از آنکه همه‌ی منابع رمزنگاری‌شده‌ی موجود را با داده‌های پشتیبانی جایگزین کردید که از رمزنگاری استفاده نمی‌کنند، می‌توانید تنظیمات رمزنگاری را از kube-apiserver حذف کنید.

پیکربندی بارگذاری مجدد خودکار

می‌توانید بارگذاری مجدد خودکار پیکربندی ارائه‌دهنده‌ی رمزنگاری را پیکربندی کنید. این تنظیم تعیین می‌کند که سرور API فایلی را که برای --encryption-provider-config مشخص می‌کنید فقط یک بار هنگام راه‌اندازی بارگذاری کند، یا هر بار که آن فایل را تغییر می‌دهید به‌طور خودکار آن را بارگذاری کند. با فعال کردن این گزینه می‌توانید کلیدهای رمزنگاری در حالت ذخیره را بدون راه‌اندازی مجدد سرور API تغییر دهید.

برای فعال کردن بارگذاری مجدد خودکار، سرور API را طوری پیکربندی کنید که با --encryption-provider-config-automatic-reload=true اجرا شود. در صورت فعال بودن این گزینه، تغییرات فایل هر دقیقه یک بار بررسی می‌شوند تا اصلاحات شناسایی شوند. سنجه‌ی apiserver_encryption_config_controller_automatic_reload_last_timestamp_seconds زمانی را که پیکربندی جدید اعمال می‌شود مشخص می‌کند. به این ترتیب می‌توان کلیدهای رمزنگاری را بدون راه‌اندازی مجدد سرور API چرخش داد.

گام‌های بعدی

  • درباره‌ی رمزگشایی داده‌هایی که از قبل در حالت ذخیره نگهداری شده‌اند بخوانید.
  • درباره‌ی API پیکربندی EncryptionConfiguration (v1) بیشتر بیاموزید.
