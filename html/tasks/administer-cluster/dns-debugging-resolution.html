اشکال‌زدایی تفکیک نام DNS

این صفحه راهنمایی‌هایی برای تشخیص مشکلات DNS ارائه می‌دهد.

پیش از شروع

باید یک کلاستر کوبرنتیز داشته باشید و ابزار خط فرمان kubectl باید برای ارتباط با کلاستر شما پیکربندی شده باشد. توصیه می‌شود این آموزش را روی کلاستری اجرا کنید که دست‌کم دو نود داشته باشد که نقش میزبان control plane را ندارند. اگر هنوز کلاستری ندارید، می‌توانید با استفاده از minikube یکی بسازید یا از یکی از این محیط‌های آزمایشی کوبرنتیز استفاده کنید:

  • iximiuz Labs
  • Killercoda
  • KodeKloud

کلاستر شما باید طوری پیکربندی شده باشد که از افزونهی CoreDNS استفاده کند.

یک Pod ساده به‌عنوان محیط آزمایشی بسازید

admin/dns/dnsutils.yaml
apiVersion: v1
kind: Pod
metadata:
  name: dnsutils
  namespace: default
spec:
  containers:
  - name: dnsutils
    image: registry.k8s.io/e2e-test-images/agnhost:2.39
    imagePullPolicy: IfNotPresent
  restartPolicy: Always
توجه:

این مثال یک Pod در فضای نام (namespace) default می‌سازد. تفکیک نام DNS برای سرویس‌ها به فضای نام Pod بستگی دارد. برای اطلاعات بیشتر، صفحهٔ DNS برای سرویس‌ها و Podها را ببینید.

با استفاده از این مانیفست یک Pod بسازید:

kubectl apply -f https://k8s.io/examples/admin/dns/dnsutils.yaml

pod/dnsutils created

…و وضعیت آن را بررسی کنید:

kubectl get pods dnsutils

NAME       READY     STATUS    RESTARTS   AGE
dnsutils   1/1       Running   0          <some-time>

پس از اجرای این Pod، می‌توانید دستور nslookup را در این محیط اجرا کنید. اگر خروجی‌ای مشابه نمونهٔ زیر می‌بینید، DNS به‌درستی کار می‌کند.

kubectl exec -i -t dnsutils -- nslookup kubernetes.default

Server:    10.0.0.10
Address 1: 10.0.0.10

Name:      kubernetes.default
Address 1: 10.0.0.1

اگر دستور nslookup با شکست مواجه شد، موارد زیر را بررسی کنید:

ابتدا پیکربندی محلی DNS را بررسی کنید

محتوای فایل resolv.conf را بررسی کنید. (برای اطلاعات بیشتر، سفارشی‌سازی سرویس DNS و بخش مشکلات شناخته‌شده را در ادامه ببینید.)

kubectl exec -ti dnsutils -- cat /etc/resolv.conf

بررسی کنید که مسیر جست‌وجو (search path) و سرور نام (name server) مانند نمونهٔ زیر تنظیم شده باشند (توجه کنید که مسیر جست‌وجو ممکن است در ارائه‌دهندگان ابری مختلف متفاوت باشد):

search default.svc.cluster.local svc.cluster.local cluster.local google.internal c.gce_project_id.internal
nameserver 10.0.0.10
options ndots:5

خطاهایی مانند نمونه‌های زیر نشان‌دهندهٔ مشکلی در افزونهٔ CoreDNS یا سرویس‌های مرتبط با آن هستند:

kubectl exec -i -t dnsutils -- nslookup kubernetes.default

Server:    10.0.0.10
Address 1: 10.0.0.10

nslookup: can't resolve 'kubernetes.default'

یا

kubectl exec -i -t dnsutils -- nslookup kubernetes.default

Server:    10.0.0.10
Address 1: 10.0.0.10 kube-dns.kube-system.svc.cluster.local

nslookup: can't resolve 'kubernetes.default'

بررسی کنید که Pod مربوط به DNS در حال اجرا باشد

با دستور kubectl get pods بررسی کنید که Pod مربوط به DNS در حال اجرا باشد.

kubectl get pods --namespace=kube-system -l k8s-app=kube-dns

NAME                       READY     STATUS    RESTARTS   AGE
...
coredns-7b96bf9f76-5hsxb   1/1       Running   0           1h
coredns-7b96bf9f76-mvmmt   1/1       Running   0           1h
...
توجه:

مقدار برچسب k8s-app برای CoreDNS، به‌منظور سازگاری با نسخه‌های قبلی و kube-dns اصلی، برابر با kube-dns است.

اگر می‌بینید که هیچ Pod مربوط به CoreDNS در حال اجرا نیست یا وضعیت Pod شکست‌خورده یا تکمیل‌شده است، احتمالاً افزونهٔ DNS به‌طور پیش‌فرض در محیط فعلی شما مستقر نشده است و باید آن را به‌صورت دستی مستقر کنید.

خطاهای Pod مربوط به DNS را بررسی کنید

با دستور kubectl logs لاگ‌های کانتینرهای DNS را ببینید.

برای CoreDNS:

kubectl logs --namespace=kube-system -l k8s-app=kube-dns

نمونه‌ای از لاگ یک CoreDNS سالم در ادامه آمده است:

.:53
2018/08/15 14:37:17 [INFO] CoreDNS-1.2.2
2018/08/15 14:37:17 [INFO] linux/amd64, go1.10.3, 2e322f6
CoreDNS-1.2.2
linux/amd64, go1.10.3, 2e322f6
2018/08/15 14:37:17 [INFO] plugin/reload: Running configuration MD5 = 24e6c59e83ce706f07bcc82c31b1ea1c

بررسی کنید که آیا پیام مشکوک یا غیرمنتظره‌ای در لاگ‌ها وجود دارد یا نه.

آیا سرویس DNS فعال است؟

با دستور kubectl get service بررسی کنید که سرویس DNS فعال باشد.

kubectl get svc --namespace=kube-system

NAME         TYPE        CLUSTER-IP     EXTERNAL-IP   PORT(S)             AGE
...
kube-dns     ClusterIP   10.0.0.10      <none>        53/UDP,53/TCP        1h
...
توجه:

نام Service مربوط به CoreDNS، به‌منظور سازگاری با نسخه‌های قبلی و kube-dns اصلی، kube-dns است.

اگر Service را ساخته‌اید، یا قرار بوده به‌طور پیش‌فرض ساخته شود اما نمایش داده نمی‌شود، برای اطلاعات بیشتر صفحهٔ اشکال‌زدایی سرویس‌ها را ببینید.

آیا endpointهای DNS در دسترس قرار گرفته‌اند؟

با دستور kubectl get endpointslice می‌توانید بررسی کنید که endpointهای DNS در دسترس قرار گرفته باشند.

kubectl get endpointslice -l kubernetes.io/service-name=kube-dns --namespace=kube-system

NAME             ADDRESSTYPE   PORTS   ENDPOINTS                  AGE
coredns-zxoja    IPv4          53      10.180.3.17,10.180.3.17    1h

اگر endpointها را نمی‌بینید، بخش endpointها را در مستندات اشکال‌زدایی سرویس‌ها ببینید.

آیا پرس‌وجوهای DNS دریافت و پردازش می‌شوند؟

برای بررسی اینکه CoreDNS پرس‌وجوها را دریافت می‌کند یا نه، می‌توانید افزونهٔ log را به پیکربندی CoreDNS (که Corefile نیز نامیده می‌شود) اضافه کنید. فایل Corefile مربوط به CoreDNS در یک ConfigMap با نام coredns نگهداری می‌شود. برای ویرایش آن از دستور زیر استفاده کنید:

kubectl -n kube-system edit configmap coredns

سپس مطابق نمونهٔ زیر، log را به بخش Corefile اضافه کنید:

apiVersion: v1
kind: ConfigMap
metadata:
  name: coredns
  namespace: kube-system
data:
  Corefile: |
    .:53 {
        log
        errors
        health
        kubernetes cluster.local in-addr.arpa ip6.arpa {
          pods insecure
          upstream
          fallthrough in-addr.arpa ip6.arpa
        }
        prometheus :9153
        forward . /etc/resolv.conf
        cache 30
        loop
        reload
        loadbalance
    }

پس از ذخیرهٔ تغییرات، ممکن است یک تا دو دقیقه طول بکشد تا کوبرنتیز این تغییرات را به Podهای CoreDNS منتقل کند.

سپس چند پرس‌وجو انجام دهید و مطابق بخش‌های قبلی این سند، لاگ‌ها را ببینید. اگر Podهای CoreDNS پرس‌وجوها را دریافت کنند، باید آن‌ها را در لاگ‌ها ببینید.

نمونه‌ای از یک پرس‌وجو در لاگ در ادامه آمده است:

CoreDNS-1.2.0

آیا CoreDNS مجوزهای کافی دارد؟

برای تفکیک درست نام سرویس‌ها، CoreDNS باید بتواند منابع مرتبط با سرویس و endpointslice را فهرست کند.

نمونهٔ پیام خطا:

2022-03-18T07:12:15.699431183Z [INFO] 10.96.144.227:52299 - 3686 "A IN serverproxy.contoso.net.cluster.local. udp 52 false 512" SERVFAIL qr,aa,rd 145 0.000091221s

ابتدا ClusterRole فعلی system:coredns را دریافت کنید:

kubectl describe clusterrole system:coredns -n kube-system

خروجی مورد انتظار:

PolicyRule:
  Resources                        Non-Resource URLs  Resource Names  Verbs
  ---------                        -----------------  --------------  -----
  endpoints                        []                 []              [list watch]
  namespaces                       []                 []              [list watch]
  pods                             []                 []              [list watch]
  services                         []                 []              [list watch]
  endpointslices.discovery.k8s.io  []                 []              [list watch]

اگر مجوزی وجود ندارد، ClusterRole را ویرایش کنید و آن را اضافه کنید:

kubectl edit clusterrole system:coredns -n kube-system

نمونه‌ای از افزودن مجوزهای EndpointSlice:

...
- apiGroups:
  - discovery.k8s.io
  resources:
  - endpointslices
  verbs:
  - list
  - watch
...

آیا در فضای نام درست سرویس هستید؟

دامنهٔ پرس‌وجوهای DNS که فضای نامی در آن‌ها مشخص نشده است، به فضای نام Pod محدود می‌شود.

اگر فضای نام Pod و سرویس متفاوت باشد، پرس‌وجوی DNS باید فضای نام سرویس را نیز در بر داشته باشد.

این پرس‌وجو به فضای نام Pod محدود است:

kubectl exec -i -t dnsutils -- nslookup <service-name>

این پرس‌وجو فضای نام را مشخص می‌کند:

kubectl exec -i -t dnsutils -- nslookup <service-name>.<namespace>

برای آشنایی بیشتر با تفکیک نام، صفحهٔ DNS برای سرویس‌ها و Podها را ببینید.

مشکلات شناخته‌شده

برخی توزیع‌های لینوکس (مانند Ubuntu) به‌طور پیش‌فرض از یک تفکیک‌کنندهٔ DNS محلی (systemd-resolved) استفاده می‌کنند. سرویس systemd-resolved فایل /etc/resolv.conf را جابه‌جا می‌کند و یک فایل stub را جایگزین آن می‌کند که ممکن است هنگام تفکیک نام‌ها در سرورهای بالادستی، یک حلقهٔ ارسال (forwarding loop) مخرب ایجاد کند. می‌توان این مشکل را به‌صورت دستی برطرف کرد؛ کافی است با فلگ --resolv-conf در kubelet به فایل resolv.conf درست اشاره کنید (در صورت استفاده از systemd-resolved، این فایل /run/systemd/resolve/resolv.conf است). ابزار kubeadm وجود systemd-resolved را به‌طور خودکار تشخیص می‌دهد و فلگ‌های kubelet را متناسب با آن تنظیم می‌کند.

نصب‌های کوبرنتیز به‌طور پیش‌فرض فایل‌های resolv.conf نودها را برای استفاده از DNS کلاستر پیکربندی نمی‌کنند، زیرا این فرایند ذاتاً به توزیع وابسته است. احتمالاً این قابلیت در آینده پیاده‌سازی خواهد شد.

کتابخانهٔ libc لینوکس (یا همان glibc) به‌طور پیش‌فرض تعداد رکوردهای nameserver در DNS را به ۳ محدود می‌کند و کوبرنتیز به یک رکورد nameserver نیاز دارد. بنابراین اگر یک نصب محلی از قبل از ۳ رکورد nameserver استفاده کند، برخی از این مدخل‌ها از دست می‌روند. برای دور زدن این محدودیت، نود می‌تواند dnsmasq را اجرا کند که مدخل‌های nameserver بیشتری فراهم می‌کند. همچنین می‌توانید از فلگ --resolv-conf در kubelet استفاده کنید.

اگر از نسخهٔ 3.17 یا قدیمی‌تر Alpine به‌عنوان ایمیج پایه استفاده می‌کنید، ممکن است به‌دلیل یک مشکل طراحی در Alpine، DNS به‌درستی کار نکند. تا پیش از نسخهٔ 1.24 کتابخانهٔ musl، امکان بازگشت به TCP (TCP fallback) در تفکیک‌کنندهٔ stub مربوط به DNS وجود نداشت؛ به این معنا که هر فراخوانی DNS بزرگ‌تر از ۵۱۲ بایت با شکست مواجه می‌شد. لطفاً ایمیج‌های خود را به نسخهٔ 3.18 یا بالاتر Alpine ارتقا دهید.

گام‌های بعدی

  • صفحهٔ مقیاس‌دهی خودکار سرویس DNS در یک کلاستر را ببینید.
  • صفحهٔ DNS برای سرویس‌ها و Podها را بخوانید.
