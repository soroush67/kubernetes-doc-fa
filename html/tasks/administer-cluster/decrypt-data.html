رمزگشایی داده‌های محرمانه‌ای که در حالت سکون رمزگذاری شده‌اند

همهٔ APIهایی در کوبرنتیز که امکان نوشتن داده‌های ماندگار منابع API را فراهم می‌کنند، از رمزگذاری در حالت سکون (at-rest encryption) پشتیبانی می‌کنند. برای مثال، می‌توانید رمزگذاری در حالت سکون را برای Secretها فعال کنید. این رمزگذاری در حالت سکون، علاوه بر هر نوع رمزگذاری در سطح سیستم است که برای کلاستر etcd یا برای فایل‌سیستم(های) میزبان‌هایی که kube-apiserver را روی آن‌ها اجرا می‌کنید اعمال شده باشد.

این صفحه نشان می‌دهد چگونه رمزگذاری داده‌های API در حالت سکون را کنار بگذارید تا داده‌های API به‌صورت رمزگذاری‌نشده ذخیره شوند. ممکن است بخواهید این کار را برای بهبود کارایی انجام دهید؛ با این حال، معمولاً اگر رمزگذاری برخی داده‌ها ایدهٔ خوبی بوده است، رمزگذاری‌شده نگه‌داشتن آن‌ها نیز ایدهٔ خوبی است.

توجه:

این تکلیف به رمزگذاری داده‌های منابعی می‌پردازد که با استفاده از API کوبرنتیز ذخیره می‌شوند. برای مثال، می‌توانید آبجکت‌های Secret را همراه با داده‌های کلید-مقداری که در خود دارند رمزگذاری کنید.

اگر می‌خواهید رمزگذاری داده‌ها را در فایل‌سیستم‌هایی مدیریت کنید که در کانتینرها مانت می‌شوند، باید به‌جای آن یکی از این کارها را انجام دهید:

  • از یک یکپارچه‌سازی ذخیره‌سازی استفاده کنید که حجم‌های (volume) رمزگذاری‌شده فراهم می‌کند
  • داده‌ها را درون برنامهٔ خودتان رمزگذاری کنید

پیش از شروع

باید یک کلاستر کوبرنتیز داشته باشید و ابزار خط فرمان kubectl باید برای ارتباط با کلاستر شما پیکربندی شده باشد. توصیه می‌شود این آموزش را روی کلاستری اجرا کنید که دست‌کم دو نود داشته باشد که نقش میزبان control plane را ندارند. اگر هنوز کلاستری ندارید، می‌توانید با استفاده از minikube یکی بسازید یا از یکی از این محیط‌های آزمایشی کوبرنتیز استفاده کنید:

  • iximiuz Labs

  • Killercoda

  • KodeKloud

  • در این تکلیف فرض بر این است که سرور API کوبرنتیز را به‌صورت یک پاد ایستا (static pod) روی هر نود control plane اجرا می‌کنید.

  • control plane کلاستر شما باید از etcd نسخهٔ v3.x (نسخهٔ اصلی ۳ با هر نسخهٔ فرعی) استفاده کند.

  • برای رمزگذاری یک منبع سفارشی (custom resource)، کلاستر شما باید کوبرنتیز v1.26 یا جدیدتر را اجرا کند.

  • باید مقداری دادهٔ API داشته باشید که از قبل رمزگذاری شده باشد.

تشخیص اینکه آیا رمزگذاری در حالت سکون از قبل فعال است

سرور API به‌طور پیش‌فرض از فراهم‌کننده‌ای (provider) به نام identity استفاده می‌کند که نمایش متن سادهٔ منابع را ذخیره می‌کند. فراهم‌کنندهٔ پیش‌فرض identity هیچ حفاظتی از محرمانگی ارائه نمی‌دهد.

فرایند kube-apiserver آرگومانی به نام --encryption-provider-config می‌پذیرد که مسیر یک فایل پیکربندی را مشخص می‌کند. اگر چنین فایلی را مشخص کنید، محتوای آن تعیین می‌کند که داده‌های API کوبرنتیز در etcd چگونه رمزگذاری شوند. اگر این آرگومان مشخص نشده باشد، رمزگذاری در حالت سکون فعال نیست.

قالب این فایل پیکربندی YAML است و یک نوع (kind) از API پیکربندی به نام EncryptionConfiguration را نمایش می‌دهد. می‌توانید نمونه‌ای از این پیکربندی را در پیکربندی رمزگذاری در حالت سکون ببینید.

اگر --encryption-provider-config تنظیم شده باشد، بررسی کنید که کدام منابع (مانند secrets) برای رمزگذاری پیکربندی شده‌اند و از کدام فراهم‌کننده استفاده می‌شود. مطمئن شوید که فراهم‌کنندهٔ ترجیحی برای آن نوع منبع، identity نیست؛ فقط زمانی identity (بدون رمزگذاری) را به‌عنوان پیش‌فرض تنظیم می‌کنید که بخواهید رمزگذاری در حالت سکون را غیرفعال کنید. بررسی کنید که نخستین فراهم‌کنندهٔ فهرست‌شده برای یک منبع، چیزی غیر از identity باشد؛ این یعنی هر اطلاعات جدیدی که در منابع آن نوع نوشته شود، طبق پیکربندی رمزگذاری خواهد شد. اگر برای منبعی، identity را به‌عنوان نخستین فراهم‌کنندهٔ فهرست‌شده می‌بینید، یعنی آن منابع بدون رمزگذاری در etcd نوشته می‌شوند.

رمزگشایی همهٔ داده‌ها {#decrypting-all-data}

این مثال نشان می‌دهد چگونه رمزگذاری API مربوط به Secret را در حالت سکون متوقف کنید. اگر انواع دیگری از API را رمزگذاری می‌کنید، مراحل را متناسب با آن‌ها تنظیم کنید.

یافتن فایل پیکربندی رمزگذاری

ابتدا فایل‌های پیکربندی سرور API را پیدا کنید. روی هر نود control plane، مانیفست Pod ایستای kube-apiserver یک آرگومان خط فرمان به نام --encryption-provider-config را مشخص می‌کند. احتمالاً این فایل با استفاده از یک مانت حجم از نوع hostPath در Pod ایستا مانت شده است. پس از یافتن حجم، می‌توانید فایل را در فایل‌سیستم نود پیدا و بررسی کنید.

پیکربندی سرور API برای رمزگشایی آبجکت‌ها

برای غیرفعال‌کردن رمزگذاری در حالت سکون، فراهم‌کنندهٔ identity را به‌عنوان نخستین مدخل در فایل پیکربندی رمزگذاری قرار دهید.

برای مثال، اگر فایل EncryptionConfiguration فعلی شما به این صورت است:

---
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
  - resources:
      - secrets
    providers:
      - aescbc:
          keys:
            # Do not use this (invalid) example key for encryption
            - name: example
              secret: 2KfZgdiq2K0g2YrYpyDYs9mF2LPZhQ==

آن را به این صورت تغییر دهید:

---
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
  - resources:
      - secrets
    providers:
      - identity: {} # add this line
      - aescbc:
          keys:
            - name: example
              secret: 2KfZgdiq2K0g2YrYpyDYs9mF2LPZhQ==

و Pod مربوط به kube-apiserver را روی این نود دوباره راه‌اندازی کنید.

پیکربندی دوبارهٔ دیگر میزبان‌های control plane {#api-server-config-update-more-1}

اگر چند سرور API در کلاستر خود دارید، باید تغییرات را به‌ترتیب روی هر سرور API اعمال کنید.

مطمئن شوید که روی همهٔ میزبان‌های control plane از پیکربندی رمزگذاری یکسانی استفاده می‌کنید.

اجبار به رمزگشایی

سپس فرمان زیر را اجرا کنید تا همهٔ Secretها به‌اجبار رمزگشایی شوند:

# If you are decrypting a different kind of object, change "secrets" to match.
kubectl get secrets --all-namespaces -o json | kubectl replace -f -

پس از آنکه همهٔ منابع رمزگذاری‌شدهٔ موجود را با داده‌های پشتیبانی جایگزین کردید که از رمزگذاری استفاده نمی‌کنند، می‌توانید تنظیمات رمزگذاری را از kube-apiserver حذف کنید.

گزینه‌های خط فرمانی که باید حذف شوند عبارت‌اند از:

  • --encryption-provider-config
  • --encryption-provider-config-automatic-reload

برای اعمال پیکربندی جدید، Pod مربوط به kube-apiserver را دوباره راه‌اندازی کنید.
