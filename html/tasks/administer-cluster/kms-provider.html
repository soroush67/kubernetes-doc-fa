استفاده از ارائه‌دهندهٔ KMS برای رمزنگاری داده‌ها

این صفحه نشان می‌دهد چگونه یک ارائه‌دهنده (provider) و افزونهٔ (plugin) سرویس مدیریت کلید (Key Management Service یا KMS) را پیکربندی کنید تا رمزنگاری داده‌های محرمانه فعال شود. در کوبرنتیز 1.37 دو نسخه از رمزنگاری داده‌های ذخیره‌شده (at-rest) با KMS وجود دارد. در صورت امکان از KMS v2 استفاده کنید، زیرا KMS v1 منسوخ شده است (از کوبرنتیز v1.28) و به‌طور پیش‌فرض غیرفعال است (از کوبرنتیز v1.29). کارایی KMS v2 به‌مراتب بهتر از KMS v1 است.

احتیاط:

این مستندات مربوط به پیاده‌سازی KMS v2 در وضعیت عرضهٔ عمومی (generally available) است (و همچنین پیاده‌سازی منسوخ‌شدهٔ نسخهٔ ۱). اگر از هر یک از مؤلفه‌های control plane قدیمی‌تر از کوبرنتیز v1.29 استفاده می‌کنید، لطفاً صفحهٔ معادل را در مستندات همان نسخه‌ای از کوبرنتیز که کلاستر شما اجرا می‌کند بررسی کنید. نسخه‌های پیشین کوبرنتیز رفتار متفاوتی داشتند که ممکن است از نظر امنیت اطلاعات اهمیت داشته باشد.

پیش از شروع

باید یک کلاستر کوبرنتیز داشته باشید و ابزار خط فرمان kubectl باید برای ارتباط با کلاستر شما پیکربندی شده باشد. توصیه می‌شود این آموزش را روی کلاستری اجرا کنید که دست‌کم دو نود داشته باشد که نقش میزبان control plane را ندارند. اگر هنوز کلاستری ندارید، می‌توانید با استفاده از minikube یکی بسازید یا از یکی از این محیط‌های آزمایشی کوبرنتیز استفاده کنید:

  • iximiuz Labs
  • Killercoda
  • KodeKloud

نسخهٔ موردنیاز کوبرنتیز به نسخه‌ای از API ِ KMS بستگی دارد که انتخاب کرده‌اید. کوبرنتیز استفاده از KMS v2 را توصیه می‌کند.

  • اگر KMS API v1 را برای پشتیبانی از کلاسترهای پیش از نسخهٔ v1.27 انتخاب کرده‌اید، یا افزونهٔ KMS قدیمی‌ای دارید که فقط از KMS v1 پشتیبانی می‌کند، هر نسخهٔ پشتیبانی‌شدهٔ کوبرنتیز کار خواهد کرد. این API از کوبرنتیز v1.28 منسوخ شده است و کوبرنتیز استفاده از آن را توصیه نمی‌کند.

KMS v1

وضعیت ویژگی: Kubernetes v1.28 [deprecated] (منسوخ)

  • به کوبرنتیز نسخهٔ 1.10.0 یا بالاتر نیاز است.

  • در نسخهٔ 1.29 و بالاتر، پیاده‌سازی v1 ِ KMS به‌طور پیش‌فرض غیرفعال است. برای فعال‌کردن این قابلیت و پیکربندی یک ارائه‌دهندهٔ KMS v1، مقدار --feature-gates=KMSv1=true را تنظیم کنید.

  • کلاستر شما باید از etcd نسخهٔ v3 یا بالاتر استفاده کند.

KMS v2

وضعیت ویژگی: Kubernetes v1.29 [stable] (پایدار)
  • کلاستر شما باید از etcd نسخهٔ v3 یا بالاتر استفاده کند.

رمزنگاری KMS و کلیدهای رمزنگاری مختص هر آبجکت

ارائه‌دهندهٔ رمزنگاری KMS برای رمزنگاری داده‌ها در etcd از طرح رمزنگاری پاکتی (envelope encryption) استفاده می‌کند. داده‌ها با یک کلید رمزنگاری داده (data encryption key یا DEK) رمزنگاری می‌شوند. خود DEKها نیز با یک کلید رمزنگاری کلید (key encryption key یا KEK) رمزنگاری می‌شوند که در یک KMS راه‌دور ذخیره و مدیریت می‌شود.

اگر از پیاده‌سازی (منسوخ‌شدهٔ) v1 ِ KMS استفاده کنید، برای هر عملیات رمزنگاری یک DEK جدید تولید می‌شود.

در KMS v2، یک DEK جدید برای هر رمزنگاری تولید می‌شود: سرور API با استفاده از یک تابع استخراج کلید (key derivation function)، از ترکیب یک بذر (seed) محرمانه با مقداری دادهٔ تصادفی، کلیدهای رمزنگاری دادهٔ یک‌بارمصرف تولید می‌کند. هر بار که KEK چرخش (rotate) داده شود، این بذر نیز چرخانده می‌شود (برای جزئیات بیشتر، بخش درک key_id و چرخش کلید را در ادامه ببینید).

ارائه‌دهندهٔ KMS از gRPC برای ارتباط با یک افزونهٔ KMS مشخص از طریق یک سوکت دامنهٔ UNIX استفاده می‌کند. افزونهٔ KMS که به‌صورت یک سرور gRPC پیاده‌سازی شده و روی همان میزبان (یا میزبان‌هایی) مستقر می‌شود که control plane کوبرنتیز روی آن قرار دارد، مسئول تمام ارتباطات با KMS راه‌دور است.

پیکربندی ارائه‌دهندهٔ KMS

برای پیکربندی یک ارائه‌دهندهٔ KMS روی سرور API، یک ارائه‌دهنده از نوع kms را در آرایهٔ providers در فایل پیکربندی رمزنگاری قرار دهید و ویژگی‌های زیر را تنظیم کنید:

KMS v1 {#configuring-the-kms-provider-kms-v1}

  • apiVersion: نسخهٔ API برای ارائه‌دهندهٔ KMS. این مقدار را خالی بگذارید یا آن را v1 قرار دهید.
  • name: نام نمایشی افزونهٔ KMS. پس از تنظیم، قابل تغییر نیست.
  • endpoint: نشانی شنود سرور gRPC (افزونهٔ KMS). این نقطهٔ پایانی (endpoint) یک سوکت دامنهٔ UNIX است.
  • cachesize: تعداد کلیدهای رمزنگاری داده (DEK) که به‌صورت رمزنگاری‌نشده در حافظهٔ نهان (cache) نگهداری می‌شوند. DEKهایی که در حافظهٔ نهان هستند بدون فراخوانی دوبارهٔ KMS قابل استفاده‌اند؛ در حالی که برای باز کردن (unwrap) DEKهایی که در حافظهٔ نهان نیستند باید KMS فراخوانی شود.
  • timeout: مدت‌زمانی که kube-apiserver پیش از برگرداندن خطا منتظر پاسخ kms-plugin می‌ماند (مقدار پیش‌فرض ۳ ثانیه است).

KMS v2 {#configuring-the-kms-provider-kms-v2}

  • apiVersion: نسخهٔ API برای ارائه‌دهندهٔ KMS. این مقدار را v2 قرار دهید.
  • name: نام نمایشی افزونهٔ KMS. پس از تنظیم، قابل تغییر نیست.
  • endpoint: نشانی شنود سرور gRPC (افزونهٔ KMS). این نقطهٔ پایانی یک سوکت دامنهٔ UNIX است.
  • timeout: مدت‌زمانی که kube-apiserver پیش از برگرداندن خطا منتظر پاسخ kms-plugin می‌ماند (مقدار پیش‌فرض ۳ ثانیه است).

ویژگی cachesize در KMS v2 پشتیبانی نمی‌شود. همهٔ کلیدهای رمزنگاری داده (DEK)، پس از آنکه سرور آن‌ها را با فراخوانی KMS باز کرد، به‌صورت رمزنگاری‌نشده در حافظهٔ نهان نگهداری می‌شوند. پس از قرار گرفتن در حافظهٔ نهان، می‌توان از DEKها بدون فراخوانی KMS و برای مدت نامحدود جهت رمزگشایی استفاده کرد.

درک پیکربندی رمزنگاری داده‌های ذخیره‌شده را ببینید.

پیاده‌سازی یک افزونهٔ KMS

برای پیاده‌سازی یک افزونهٔ KMS، می‌توانید یک سرور gRPC جدید برای افزونه توسعه دهید یا افزونهٔ KMS ارائه‌شده از سوی ارائه‌دهندهٔ ابری خود را فعال کنید. سپس افزونه را با KMS راه‌دور یکپارچه می‌کنید و آن را روی control plane کوبرنتیز مستقر می‌کنید.

فعال‌کردن KMS پشتیبانی‌شده از سوی ارائه‌دهندهٔ ابری

برای دستورالعمل‌های فعال‌کردن افزونهٔ KMS مختص ارائه‌دهندهٔ ابری، به مستندات ارائه‌دهندهٔ ابری خود مراجعه کنید.

توسعهٔ سرور gRPC برای افزونهٔ KMS

می‌توانید سرور gRPC افزونهٔ KMS را با استفاده از یک فایل stub که برای Go در دسترس است توسعه دهید. برای زبان‌های دیگر، با استفاده از یک فایل proto یک فایل stub ایجاد می‌کنید و از آن برای توسعهٔ کد سرور gRPC بهره می‌گیرید.

KMS v1 {#developing-a-kms-plugin-gRPC-server-kms-v1}

  • با استفاده از Go: برای توسعهٔ کد سرور gRPC، از توابع و ساختارهای دادهٔ موجود در فایل stub api.pb.go استفاده کنید.

  • با استفاده از زبان‌هایی غیر از Go: برای تولید فایل stub مخصوص آن زبان، از کامپایلر protoc همراه با فایل proto api.proto استفاده کنید.

KMS v2 {#developing-a-kms-plugin-gRPC-server-kms-v2}

  • با استفاده از Go: یک کتابخانهٔ سطح بالا برای ساده‌ترکردن این فرایند فراهم شده است. پیاده‌سازی‌های سطح پایین می‌توانند برای توسعهٔ کد سرور gRPC از توابع و ساختارهای دادهٔ موجود در فایل stub api.pb.go استفاده کنند.

  • با استفاده از زبان‌هایی غیر از Go: برای تولید فایل stub مخصوص آن زبان، از کامپایلر protoc همراه با فایل proto api.proto استفاده کنید.

سپس با استفاده از توابع و ساختارهای دادهٔ موجود در فایل stub، کد سرور را توسعه دهید.

نکات

KMS v1 {#developing-a-kms-plugin-gRPC-server-notes-kms-v1}

  • نسخهٔ افزونهٔ kms: v1beta1

    یک افزونهٔ KMS سازگار باید در پاسخ به فراخوانی رویهٔ Version، مقدار v1beta1 را به‌عنوان VersionResponse.version برگرداند.

  • نسخهٔ پیام: v1beta1

    فیلد version در همهٔ پیام‌های ارسالی از ارائه‌دهندهٔ KMS برابر v1beta1 است.

  • پروتکل: سوکت دامنهٔ UNIX (unix)

    این افزونه به‌صورت یک سرور gRPC پیاده‌سازی شده است که روی یک سوکت دامنهٔ UNIX گوش می‌دهد. هنگام استقرار افزونه باید یک فایل روی سیستم فایل ایجاد شود تا اتصال سوکت دامنهٔ unix ِ gRPC برقرار شود. سرور API (کلاینت gRPC) با نقطهٔ پایانی سوکت دامنهٔ unix ِ ارائه‌دهندهٔ KMS (سرور gRPC) پیکربندی می‌شود تا بتواند با آن ارتباط برقرار کند. با آغاز کردن نقطهٔ پایانی با /@، یعنی unix:///@foo، می‌توان از یک سوکت انتزاعی (abstract) لینوکس استفاده کرد. هنگام استفاده از این نوع سوکت باید احتیاط کرد، زیرا (برخلاف سوکت‌های سنتی مبتنی بر فایل) مفهوم ACL در آن‌ها وجود ندارد. با این حال، این سوکت‌ها تابع فضای نام شبکهٔ لینوکس هستند و بنابراین، مگر آنکه از شبکهٔ میزبان استفاده شود، فقط برای کانتینرهای درون همان پاد در دسترس خواهند بود.

KMS v2 {#developing-a-kms-plugin-gRPC-server-notes-kms-v2}

  • نسخهٔ افزونهٔ KMS: v2

    یک افزونهٔ KMS سازگار باید در پاسخ به فراخوانی رویهٔ راه‌دور Status، نسخهٔ سازگاری KMS خود را به‌عنوان StatusResponse.version برگرداند. این پاسخ وضعیت باید همچنین مقدار "ok" را به‌عنوان StatusResponse.healthz و یک key_id (شناسهٔ KEK در KMS راه‌دور) را به‌عنوان StatusResponse.key_id در بر داشته باشد. پروژهٔ کوبرنتیز توصیه می‌کند افزونهٔ خود را با API پایدار v2 ِ KMS سازگار کنید. کوبرنتیز 1.37 از API ِ v2beta1 برای KMS نیز پشتیبانی می‌کند؛ احتمالاً نسخه‌های آیندهٔ کوبرنتیز نیز همچنان از این نسخهٔ بتا پشتیبانی خواهند کرد.

    سرور API، وقتی همه‌چیز سالم است، تقریباً هر دقیقه یک بار و وقتی افزونه سالم نیست، هر ۱۰ ثانیه یک بار رویهٔ Status را فراخوانی (poll) می‌کند. افزونه‌ها باید این فراخوانی را بهینه کنند، زیرا همواره زیر بار خواهد بود.

  • رمزنگاری

    فراخوانی رویهٔ EncryptRequest متن آشکار (plaintext) و یک UID را برای مقاصد ثبت لاگ فراهم می‌کند. پاسخ باید شامل متن رمزشده (ciphertext)، key_id ِ KEK استفاده‌شده و در صورت نیاز، هرگونه فراداده‌ای باشد که افزونهٔ KMS برای کمک به فراخوانی‌های آتی DecryptRequest به آن نیاز دارد (از طریق فیلد annotations). افزونه باید تضمین کند که هر متن آشکار متمایز، به پاسخ (ciphertext, key_id, annotations) متمایزی منجر شود.

    اگر افزونه یک نگاشت annotations غیرخالی برگرداند، همهٔ کلیدهای این نگاشت باید نام دامنهٔ کاملاً مشخص (fully qualified domain name) باشند، مانند example.com. نمونه‌ای از کاربرد annotation چنین است: {"kms.example.io/remote-kms-auditid":"<audit ID used by the remote KMS>"}

    سرور API فراخوانی رویهٔ EncryptRequest را با نرخ بالا انجام نمی‌دهد. با این حال، پیاده‌سازی‌های افزونه باید بکوشند تأخیر هر درخواست را زیر ۱۰۰ میلی‌ثانیه نگه دارند.

  • رمزگشایی

    فراخوانی رویهٔ DecryptRequest مقدار (ciphertext, key_id, annotations) حاصل از EncryptRequest و یک UID را برای مقاصد ثبت لاگ فراهم می‌کند. همان‌طور که انتظار می‌رود، این فراخوانی عکس فراخوانی EncryptRequest است. افزونه‌ها باید بررسی کنند که key_id برایشان شناخته‌شده باشد؛ آن‌ها نباید برای رمزگشایی داده‌ای تلاش کنند، مگر آنکه مطمئن باشند آن داده پیش‌تر به دست خودشان رمزنگاری شده است.

    سرور API ممکن است هنگام راه‌اندازی، برای پرکردن حافظهٔ نهان watch خود، هزاران فراخوانی رویهٔ DecryptRequest انجام دهد. بنابراین پیاده‌سازی‌های افزونه باید این فراخوانی‌ها را با بیشترین سرعت ممکن انجام دهند و بکوشند تأخیر هر درخواست را زیر ۱۰ میلی‌ثانیه نگه دارند.

  • درک key_id و چرخش کلید

    مقدار key_id نام عمومی و غیرمحرمانهٔ KEK ِ KMS راه‌دوری است که در حال حاضر استفاده می‌شود. این مقدار ممکن است در جریان کار عادی سرور API در لاگ‌ها ثبت شود و بنابراین نباید هیچ دادهٔ خصوصی‌ای در بر داشته باشد. به پیاده‌سازی‌های افزونه توصیه می‌شود برای جلوگیری از نشت هرگونه داده، از هش استفاده کنند. متریک‌های KMS v2 این مقدار را پیش از ارائه از طریق نقطهٔ پایانی /metrics هش می‌کنند.

    سرور API مقدار key_id ِ برگشتی از فراخوانی رویهٔ Status را مرجع معتبر می‌داند. بنابراین تغییر این مقدار به سرور API اعلام می‌کند که KEK راه‌دور تغییر کرده است و داده‌هایی که با KEK قدیمی رمزنگاری شده‌اند، هنگام انجام یک نوشتن بی‌اثر (no-op write)، باید کهنه (stale) علامت‌گذاری شوند (همان‌طور که در ادامه توضیح داده می‌شود). اگر فراخوانی رویهٔ EncryptRequest مقدار key_id ای متفاوت با Status برگرداند، پاسخ دور ریخته می‌شود و افزونه ناسالم در نظر گرفته می‌شود. بنابراین پیاده‌سازی‌ها باید تضمین کنند که key_id برگشتی از Status با مقدار برگشتی از EncryptRequest یکسان باشد. افزون بر این، افزونه‌ها باید اطمینان حاصل کنند که key_id پایدار است و میان مقادیر مختلف نوسان نمی‌کند (برای مثال، در حین چرخش KEK راه‌دور).

    افزونه‌ها نباید از key_idها دوباره استفاده کنند، حتی در شرایطی که یک KEK راه‌دور که پیش‌تر استفاده شده بود دوباره به کار گرفته شود. برای مثال، اگر افزونه‌ای از key_id=A استفاده می‌کرد، سپس به key_id=B تغییر کرد و دوباره به key_id=A بازگشت، به‌جای گزارش key_id=A باید مقداری مشتق‌شده مانند key_id=A_001 را گزارش کند یا از مقداری جدید مانند key_id=C استفاده کند.

    از آنجا که سرور API تقریباً هر دقیقه یک بار Status را فراخوانی می‌کند، چرخش key_id فوری نیست. افزون بر این، سرور API حدود سه دقیقه بر پایهٔ آخرین وضعیت معتبر به کار خود ادامه می‌دهد. بنابراین اگر کاربری بخواهد رویکردی منفعل در مهاجرت ذخیره‌سازی در پیش بگیرد (یعنی با صبر کردن)، باید مهاجرت را طوری زمان‌بندی کند که 3 + N + M دقیقه پس از چرخش KEK راه‌دور انجام شود (N مدت‌زمانی است که طول می‌کشد تا افزونه تغییر key_id را مشاهده کند و M حاشیهٔ زمانی دلخواه برای پردازش تغییرات پیکربندی است؛ حداقل مقدار توصیه‌شده برای M پنج دقیقه است). توجه کنید که برای انجام چرخش KEK نیازی به راه‌اندازی مجدد سرور API نیست.

احتیاط:

از آنجا که تعداد نوشتن‌هایی که با DEK انجام می‌شود در کنترل شما نیست، پروژهٔ کوبرنتیز توصیه می‌کند KEK را دست‌کم هر ۹۰ روز یک بار بچرخانید.

  • پروتکل: سوکت دامنهٔ UNIX (unix)

    این افزونه به‌صورت یک سرور gRPC پیاده‌سازی شده است که روی یک سوکت دامنهٔ UNIX گوش می‌دهد. هنگام استقرار افزونه باید یک فایل روی سیستم فایل ایجاد شود تا اتصال سوکت دامنهٔ unix ِ gRPC برقرار شود. سرور API (کلاینت gRPC) با نقطهٔ پایانی سوکت دامنهٔ unix ِ ارائه‌دهندهٔ KMS (سرور gRPC) پیکربندی می‌شود تا بتواند با آن ارتباط برقرار کند. با آغاز کردن نقطهٔ پایانی با /@، یعنی unix:///@foo، می‌توان از یک سوکت انتزاعی لینوکس استفاده کرد. هنگام استفاده از این نوع سوکت باید احتیاط کرد، زیرا (برخلاف سوکت‌های سنتی مبتنی بر فایل) مفهوم ACL در آن‌ها وجود ندارد. با این حال، این سوکت‌ها تابع فضای نام شبکهٔ لینوکس هستند و بنابراین، مگر آنکه از شبکهٔ میزبان استفاده شود، فقط برای کانتینرهای درون همان پاد در دسترس خواهند بود.

یکپارچه‌سازی افزونهٔ KMS با KMS راه‌دور

افزونهٔ KMS می‌تواند با هر پروتکلی که KMS از آن پشتیبانی می‌کند با KMS راه‌دور ارتباط برقرار کند. همهٔ داده‌های پیکربندی، از جمله اعتبارنامه‌های احراز هویتی که افزونهٔ KMS برای ارتباط با KMS راه‌دور به کار می‌برد، به‌طور مستقل در خود افزونهٔ KMS ذخیره و مدیریت می‌شوند. افزونهٔ KMS می‌تواند متن رمزشده را پیش از ارسال به KMS برای رمزگشایی، همراه با فراداده‌های اضافی موردنیاز کدگذاری کند (KMS v2 با فراهم‌کردن فیلد اختصاصی annotations این فرایند را ساده‌تر کرده است).

استقرار افزونهٔ KMS

اطمینان حاصل کنید که افزونهٔ KMS روی همان میزبان (یا میزبان‌هایی) اجرا می‌شود که سرور (یا سرورهای) API کوبرنتیز روی آن قرار دارند.

رمزنگاری داده‌ها با ارائه‌دهندهٔ KMS

برای رمزنگاری داده‌ها:

  1. یک فایل EncryptionConfiguration جدید با ویژگی‌های مناسب برای ارائه‌دهندهٔ kms ایجاد کنید تا منابعی مانند Secretها و ConfigMapها رمزنگاری شوند. اگر می‌خواهید یک API افزونه (extension API) را که در یک CustomResourceDefinition تعریف شده است رمزنگاری کنید، کلاستر شما باید کوبرنتیز v1.26 یا جدیدتر را اجرا کند.

  2. فلگ --encryption-provider-config را روی kube-apiserver طوری تنظیم کنید که به محل فایل پیکربندی اشاره کند.

  3. آرگومان بولی --encryption-provider-config-automatic-reload تعیین می‌کند که آیا فایل تعیین‌شده با --encryption-provider-config، در صورت تغییر محتوای آن روی دیسک، به‌طور خودکار دوباره بارگذاری شود یا نه.

  4. سرور API خود را مجدداً راه‌اندازی کنید.

KMS v1 {#encrypting-your-data-with-the-kms-provider-kms-v1}

apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
  - resources:
      - secrets
      - configmaps
      - pandas.awesome.bears.example
    providers:
      - kms:
          name: myKmsPluginFoo
          endpoint: unix:///tmp/socketfile-foo.sock
          cachesize: 100
          timeout: 3s
      - kms:
          name: myKmsPluginBar
          endpoint: unix:///tmp/socketfile-bar.sock
          cachesize: 100
          timeout: 3s

KMS v2 {#encrypting-your-data-with-the-kms-provider-kms-v2}

apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
  - resources:
      - secrets
      - configmaps
      - pandas.awesome.bears.example
    providers:
      - kms:
          apiVersion: v2
          name: myKmsPluginFoo
          endpoint: unix:///tmp/socketfile-foo.sock
          timeout: 3s
      - kms:
          apiVersion: v2
          name: myKmsPluginBar
          endpoint: unix:///tmp/socketfile-bar.sock
          timeout: 3s

اگر مقدار --encryption-provider-config-automatic-reload را true قرار دهید، همهٔ بررسی‌های سلامت (health check) در یک endpoint واحد بررسی سلامت ادغام می‌شوند. بررسی‌های سلامت جداگانه فقط زمانی در دسترس هستند که از ارائه‌دهندگان KMS v1 استفاده شود و پیکربندی رمزنگاری به‌طور خودکار دوباره بارگذاری نشود.

جدول زیر endpointهای بررسی سلامت را برای هر نسخهٔ KMS خلاصه می‌کند:

پیکربندی‌های KMS بدون بارگذاری مجدد خودکار با بارگذاری مجدد خودکار
فقط KMS v1 بررسی‌های سلامت جداگانه بررسی سلامت واحد
فقط KMS v2 بررسی سلامت واحد بررسی سلامت واحد
هر دو KMS v1 و v2 بررسی‌های سلامت جداگانه بررسی سلامت واحد
بدون KMS هیچ‌کدام بررسی سلامت واحد

منظور از «بررسی سلامت واحد» (Single Healthcheck) این است که تنها endpoint بررسی سلامت، /healthz/kms-providers است.

منظور از «بررسی‌های سلامت جداگانه» (Individual Healthchecks) این است که هر افزونهٔ KMS، بر اساس جایگاهش در پیکربندی رمزنگاری، endpoint بررسی سلامت مخصوص به خود را دارد: /healthz/kms-provider-0، /healthz/kms-provider-1 و غیره.

مسیرهای این endpointهای بررسی سلامت به‌صورت ثابت در کد تعریف شده‌اند و سرور آن‌ها را تولید و کنترل می‌کند. اندیس‌های بررسی‌های سلامت جداگانه با ترتیب پردازش پیکربندی رمزنگاری KMS مطابقت دارند.

تا زمانی که مراحل بخش اطمینان از رمزنگاری همهٔ Secretها انجام نشده است، فهرست providers باید به ارائه‌دهندهٔ identity: {} ختم شود تا داده‌های رمزنگاری‌نشده نیز قابل خواندن باشند. پس از رمزنگاری همهٔ منابع، باید ارائه‌دهندهٔ identity را حذف کنید تا API server دیگر داده‌های رمزنگاری‌نشده را نپذیرد.

برای جزئیات بیشتر دربارهٔ قالب EncryptionConfiguration، به مرجع API رمزنگاری API server مراجعه کنید.

بررسی رمزنگاری داده‌ها

هنگامی که رمزنگاری داده‌های ذخیره‌شده (encryption at rest) به‌درستی پیکربندی شده باشد، منابع هنگام نوشتن رمزنگاری می‌شوند. پس از راه‌اندازی مجدد kube-apiserver، هر Secret یا هر نوع منبع دیگری که در EncryptionConfiguration پیکربندی شده است، اگر تازه ایجاد یا به‌روزرسانی شود، باید هنگام ذخیره‌سازی رمزنگاری شود. برای بررسی این موضوع، می‌توانید با برنامهٔ خط فرمان etcdctl محتوای داده‌های Secret خود را بازیابی کنید.

  1. یک Secret جدید به نام secret1 در فضای نام default ایجاد کنید:

    kubectl create secret generic secret1 -n default --from-literal=mykey=mydata

  2. با استفاده از خط فرمان etcdctl، آن Secret را از etcd بخوانید:

    ETCDCTL_API=3 etcdctl get /kubernetes.io/secrets/default/secret1 [...] | hexdump -C

    در این دستور، [...] شامل آرگومان‌های اضافی برای اتصال به سرور etcd است.

  3. بررسی کنید که Secret ذخیره‌شده در KMS v1 با پیشوند k8s:enc:kms:v1: و در KMS v2 با پیشوند k8s:enc:kms:v2: آغاز شود؛ این پیشوند نشان می‌دهد که ارائه‌دهندهٔ kms داده‌های حاصل را رمزنگاری کرده است.

  4. بررسی کنید که Secret هنگام بازیابی از طریق API به‌درستی رمزگشایی شود:

    kubectl describe secret secret1 -n default

    این Secret باید شامل mykey: mydata باشد.

اطمینان از رمزنگاری همهٔ Secretها

هنگامی که رمزنگاری داده‌های ذخیره‌شده به‌درستی پیکربندی شده باشد، منابع هنگام نوشتن رمزنگاری می‌شوند. بنابراین می‌توان با یک به‌روزرسانی درجا و بدون تغییر (no-op)، از رمزنگاری داده‌ها اطمینان حاصل کرد.

دستور زیر همهٔ Secretها را می‌خواند و سپس آن‌ها را به‌روزرسانی می‌کند تا رمزنگاری سمت سرور روی آن‌ها اعمال شود. اگر به دلیل نوشتن هم‌زمان و متعارض خطایی رخ داد، دستور را دوباره اجرا کنید. در کلاسترهای بزرگ‌تر، ممکن است بخواهید Secretها را بر اساس فضای نام تقسیم کنید یا فرایند به‌روزرسانی را با یک اسکریپت انجام دهید.

kubectl get secrets --all-namespaces -o json | kubectl replace -f -

تغییر از ارائه‌دهندهٔ رمزنگاری محلی به ارائه‌دهندهٔ KMS

برای تغییر از یک ارائه‌دهندهٔ رمزنگاری محلی به ارائه‌دهندهٔ kms و رمزنگاری دوبارهٔ همهٔ Secretها:

  1. مطابق مثال زیر، ارائه‌دهندهٔ kms را به‌عنوان نخستین مورد در فایل پیکربندی اضافه کنید.

    apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
  - resources:
      - secrets
    providers:
      - kms:
          apiVersion: v2
          name : myKmsPlugin
          endpoint: unix:///tmp/socketfile.sock
      - aescbc:
          keys:
            - name: key1
              secret: <BASE 64 ENCODED SECRET>

  2. همهٔ فرایندهای kube-apiserver را دوباره راه‌اندازی کنید.

  3. دستور زیر را اجرا کنید تا همهٔ Secretها به‌اجبار با ارائه‌دهندهٔ kms دوباره رمزنگاری شوند.

    kubectl get secrets --all-namespaces -o json | kubectl replace -f -

گام‌های بعدی

اگر دیگر نمی‌خواهید داده‌هایی را که در API کوبرنتیز ذخیره می‌شوند رمزنگاری کنید، رمزگشایی داده‌هایی که پیش‌تر به‌صورت ذخیره‌شده رمزنگاری شده‌اند را مطالعه کنید.
