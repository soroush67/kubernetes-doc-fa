مدیریت Cloud Controller Manager

وضعیت ویژگی: Kubernetes v1.11 [beta] (بتا)

ارائه‌دهندگان ابری با سرعتی متفاوت از پروژهٔ کوبرنتیز توسعه می‌یابند و نسخه منتشر می‌کنند. به همین دلیل، جدا کردن کدهای مختص هر ارائه‌دهنده و انتقال آن‌ها به فایل اجرایی <span class="term" title="cloud-controller-manager">cloud-controller-manager</span> به فروشندگان ابری امکان می‌دهد مستقل از کد هستهٔ کوبرنتیز پیشرفت کنند.

می‌توان cloud-controller-manager را به هر ارائه‌دهندهٔ ابری که رابط cloudprovider.Interface را پیاده‌سازی کرده باشد پیوند داد. برای حفظ سازگاری با نسخه‌های قبلی، cloud-controller-manager ارائه‌شده در هستهٔ پروژهٔ کوبرنتیز از همان کتابخانه‌های ابری kube-controller-manager استفاده می‌کند. انتظار می‌رود ارائه‌دهندگان ابری‌ای که هم‌اکنون در هستهٔ کوبرنتیز پشتیبانی می‌شوند، برای خروج از هستهٔ کوبرنتیز از cloud-controller-manager درون‌درختی (in-tree) استفاده کنند.

مدیریت

الزامات

هر ابر مجموعه الزامات خاص خود را برای اجرای یکپارچه‌سازی ارائه‌دهندهٔ ابری‌اش دارد، اما این الزامات نباید تفاوت چندانی با الزامات اجرای kube-controller-manager داشته باشند. به‌عنوان یک قاعدهٔ کلی، به موارد زیر نیاز خواهید داشت:

  • احراز هویت و مجوزدهی ابری: ممکن است ابر شما برای دسترسی به APIهایش به یک توکن یا قواعد IAM نیاز داشته باشد.
  • احراز هویت و مجوزدهی کوبرنتیز: ممکن است cloud-controller-manager برای ارتباط با apiserver کوبرنتیز به قواعد RBAC نیاز داشته باشد.
  • دسترس‌پذیری بالا: مانند kube-controller-manager، ممکن است بخواهید با استفاده از انتخاب رهبر (leader election) که به‌طور پیش‌فرض فعال است، یک راه‌اندازی با دسترس‌پذیری بالا برای cloud controller manager داشته باشید.

اجرای cloud-controller-manager

اجرای موفق cloud-controller-manager مستلزم اعمال چند تغییر در پیکربندی کلاستر شماست.

  • باید kubelet و kube-controller-manager را متناسب با استفادهٔ کاربر از CCM خارجی تنظیم کرد. اگر کاربر یک CCM خارجی دارد (و نه حلقه‌های کنترل ابری داخلی در Kubernetes Controller Manager)، باید --cloud-provider=external مشخص شود. در غیر این صورت، نباید این گزینه مشخص شود.

توجه داشته باشید که راه‌اندازی کلاستر برای استفاده از cloud controller manager، رفتار کلاستر شما را از چند جهت تغییر می‌دهد:

  • مؤلفه‌هایی که --cloud-provider=external را مشخص می‌کنند، در حین مقداردهی اولیه یک taint با نام node.cloudprovider.kubernetes.io/uninitialized و اثر NoSchedule اضافه می‌کنند. این taint نشان می‌دهد که نود پیش از آنکه بتوان کاری روی آن زمان‌بندی کرد، به مقداردهی اولیهٔ دوم از سوی یک کنترل‌کنندهٔ خارجی نیاز دارد. توجه کنید که اگر cloud controller manager در دسترس نباشد، نودهای جدید کلاستر زمان‌بندی‌ناپذیر باقی می‌مانند. این taint اهمیت دارد، زیرا ممکن است زمان‌بند به اطلاعات مختص ابر دربارهٔ نودها، مانند منطقه یا نوع آن‌ها (پردازندهٔ قوی، GPU، حافظهٔ زیاد، نمونهٔ spot و غیره) نیاز داشته باشد.
  • اطلاعات ابری مربوط به نودهای کلاستر دیگر از فراداده‌های محلی دریافت نمی‌شود، بلکه همهٔ فراخوانی‌های API برای دریافت اطلاعات نودها از طریق cloud controller manager انجام می‌شود. در نتیجه ممکن است بتوانید برای امنیت بیشتر، دسترسی به API ابر را روی kubeletها محدود کنید. در کلاسترهای بزرگ‌تر، بهتر است بررسی کنید که آیا cloud controller manager به محدودیت‌های نرخ (rate limits) برخورد می‌کند یا نه، زیرا اکنون تقریباً همهٔ فراخوانی‌های API از درون کلاستر به ابر شما بر عهدهٔ آن است.

cloud controller manager می‌تواند موارد زیر را پیاده‌سازی کند:

  • کنترل‌کنندهٔ نود: مسئول به‌روزرسانی نودهای کوبرنتیز با استفاده از APIهای ابری و حذف نودهایی از کوبرنتیز است که در ابر شما حذف شده‌اند.
  • کنترل‌کنندهٔ سرویس: مسئول متعادل‌کننده‌های بار (load balancer) در ابر شما برای سرویس‌هایی از نوع LoadBalancer است.
  • کنترل‌کنندهٔ مسیر: مسئول برپایی مسیرهای شبکه در ابر شماست.
  • هر قابلیت دیگری که در صورت اجرای یک ارائه‌دهندهٔ بیرون‌درختی (out-of-tree) بخواهید پیاده‌سازی کنید.

نمونه‌ها

اگر از ابری استفاده می‌کنید که در حال حاضر در هستهٔ کوبرنتیز پشتیبانی می‌شود و می‌خواهید cloud controller manager را به کار بگیرید، به cloud controller manager در هستهٔ کوبرنتیز مراجعه کنید.

برای cloud controller managerهایی که در هستهٔ کوبرنتیز نیستند، می‌توانید پروژه‌های مربوط را در مخزن‌هایی بیابید که فروشندگان ابری یا SIGها نگهداری می‌کنند.

برای ارائه‌دهندگانی که هم‌اکنون در هستهٔ کوبرنتیز هستند، می‌توانید cloud controller manager درون‌درختی را به‌صورت یک DaemonSet در کلاستر خود اجرا کنید. از نمونهٔ زیر به‌عنوان راهنما استفاده کنید:

admin/cloud/ccm-example.yaml
# This is an example of how to set up cloud-controller-manager as a Daemonset in your cluster.
# It assumes that your masters can run pods and has the role node-role.kubernetes.io/master
# Note that this Daemonset will not work straight out of the box for your cloud, this is
# meant to be a guideline.

---
apiVersion: v1
kind: ServiceAccount
metadata:
  name: cloud-controller-manager
  namespace: kube-system
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: system:cloud-controller-manager
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: cluster-admin
subjects:
- kind: ServiceAccount
  name: cloud-controller-manager
  namespace: kube-system
---
apiVersion: apps/v1
kind: DaemonSet
metadata:
  labels:
    k8s-app: cloud-controller-manager
  name: cloud-controller-manager
  namespace: kube-system
spec:
  selector:
    matchLabels:
      k8s-app: cloud-controller-manager
  template:
    metadata:
      labels:
        k8s-app: cloud-controller-manager
    spec:
      serviceAccountName: cloud-controller-manager
      containers:
      - name: cloud-controller-manager
        # for in-tree providers we use registry.k8s.io/cloud-controller-manager
        # this can be replaced with any other image for out-of-tree providers
        image: registry.k8s.io/cloud-controller-manager:v1.8.0
        command:
        - /usr/local/bin/cloud-controller-manager
        - --cloud-provider=[YOUR_CLOUD_PROVIDER]  # Add your own cloud provider here!
        - --leader-elect=true
        - --use-service-account-credentials
        # these flags will vary for every cloud provider
        - --allocate-node-cidrs=true
        - --configure-cloud-routes=true
        - --cluster-cidr=172.17.0.0/16
      tolerations:
      # this is required so CCM can bootstrap itself
      - key: node.cloudprovider.kubernetes.io/uninitialized
        value: "true"
        effect: NoSchedule
      # these tolerations are to have the daemonset runnable on control plane nodes
      # remove them if your control plane nodes should not run pods
      - key: node-role.kubernetes.io/control-plane
        operator: Exists
        effect: NoSchedule
      - key: node-role.kubernetes.io/master
        operator: Exists
        effect: NoSchedule
      # this is to restrict CCM to only run on master nodes
      # the node selector may vary depending on your cluster setup
      nodeSelector:
        node-role.kubernetes.io/master: ""

محدودیت‌ها

اجرای cloud controller manager با چند محدودیت احتمالی همراه است. اگرچه این محدودیت‌ها در نسخه‌های آینده برطرف می‌شوند، مهم است که برای بارهای کاری محیط عملیاتی از آن‌ها آگاه باشید.

پشتیبانی از حجم‌ها

cloud controller manager هیچ‌یک از کنترل‌کننده‌های حجم (volume) موجود در kube-controller-manager را پیاده‌سازی نمی‌کند، زیرا یکپارچه‌سازی‌های حجم به هماهنگی با kubeletها نیز نیاز دارند. با تکامل CSI (رابط ذخیره‌سازی کانتینر) و افزودن پشتیبانی قوی‌تر از افزونه‌های flex volume، پشتیبانی لازم به cloud controller manager افزوده خواهد شد تا ابرها بتوانند به‌طور کامل با حجم‌ها یکپارچه شوند. دربارهٔ افزونه‌های حجم CSI بیرون‌درختی اینجا بیشتر بخوانید.

مقیاس‌پذیری

cloud-controller-manager برای دریافت اطلاعات همهٔ نودها، APIهای ارائه‌دهندهٔ ابری شما را پرس‌وجو می‌کند. در کلاسترهای بسیار بزرگ، گلوگاه‌های احتمالی مانند نیازمندی‌های منابع و محدودیت نرخ API را در نظر بگیرید.

مسئلهٔ مرغ و تخم‌مرغ

هدف پروژهٔ cloud controller manager جدا کردن توسعهٔ قابلیت‌های ابری از هستهٔ پروژهٔ کوبرنتیز است. متأسفانه، بسیاری از بخش‌های پروژهٔ کوبرنتیز بر این فرض بنا شده‌اند که قابلیت‌های ارائه‌دهندهٔ ابری به‌طور تنگاتنگ با پروژه یکپارچه هستند. در نتیجه، به‌کارگیری این معماری جدید ممکن است موقعیت‌هایی پدید آورد که در آن‌ها درخواستی برای دریافت اطلاعات از ارائه‌دهندهٔ ابری ارسال می‌شود، اما cloud controller manager نمی‌تواند پیش از تکمیل درخواست اولیه آن اطلاعات را بازگرداند.

نمونهٔ خوبی از این وضعیت، قابلیت راه‌اندازی TLS (TLS bootstrapping) در Kubelet است. در راه‌اندازی TLS فرض می‌شود که Kubelet می‌تواند همهٔ انواع نشانی‌های خود (خصوصی، عمومی و غیره) را از ارائه‌دهندهٔ ابری (یا یک سرویس فرادادهٔ محلی) درخواست کند. اما cloud controller manager نمی‌تواند انواع نشانی‌های یک نود را تنظیم کند، مگر آنکه ابتدا مقداردهی اولیه شده باشد، و این کار مستلزم آن است که kubelet برای ارتباط با apiserver گواهی‌های TLS داشته باشد.

با پیشرفت این طرح، در نسخه‌های آینده تغییراتی برای رفع این مشکلات اعمال خواهد شد.

گام‌های بعدی
