بررسی اینکه آیا حذف dockershim روی شما اثر می‌گذارد

مؤلفهٔ dockershim در کوبرنتیز امکان استفاده از Docker را به‌عنوان محیط اجرای کانتینر کوبرنتیز فراهم می‌کند. مؤلفهٔ داخلی dockershim کوبرنتیز در نسخهٔ v1.24 حذف شد.

این صفحه توضیح می‌دهد که کلاستر شما چگونه ممکن است از Docker به‌عنوان محیط اجرای کانتینر استفاده کند، جزئیاتی دربارهٔ نقش dockershim در هنگام استفاده ارائه می‌دهد و گام‌هایی را نشان می‌دهد که با آن‌ها می‌توانید بررسی کنید آیا بارهای کاری شما ممکن است از حذف dockershim تأثیر بپذیرند یا نه.

بررسی وابستگی برنامهٔ شما به Docker {#find-docker-dependencies}

اگر از Docker برای ساختن کانتینرهای برنامهٔ خود استفاده می‌کنید، همچنان می‌توانید این کانتینرها را روی هر محیط اجرای کانتینری اجرا کنید. این نوع استفاده از Docker وابستگی به Docker به‌عنوان محیط اجرای کانتینر به شمار نمی‌آید.

هنگامی که از یک محیط اجرای کانتینر جایگزین استفاده می‌شود، اجرای دستورهای Docker ممکن است کار نکند یا خروجی غیرمنتظره‌ای تولید کند. با روش زیر می‌توانید بفهمید که آیا به Docker وابستگی دارید یا نه:

  1. مطمئن شوید که هیچ Pod دارای دسترسی ممتاز (privileged) دستورهای Docker (مانند docker ps) را اجرا نمی‌کند، سرویس Docker را مجدداً راه‌اندازی نمی‌کند (با دستورهایی مانند systemctl restart docker.service) و فایل‌های مختص Docker مانند /etc/docker/daemon.json را تغییر نمی‌دهد.
  2. وجود هرگونه رجیستری خصوصی یا تنظیمات آینهٔ ایمیج (image mirror) را در فایل پیکربندی Docker (مانند /etc/docker/daemon.json) بررسی کنید. این تنظیمات معمولاً باید برای محیط اجرای کانتینر دیگر دوباره پیکربندی شوند.
  3. بررسی کنید که اسکریپت‌ها و برنامه‌هایی که بیرون از زیرساخت کوبرنتیز شما روی نودها اجرا می‌شوند، دستورهای Docker را اجرا نکنند. این موارد ممکن است شامل این‌ها باشند:
    • اتصال SSH به نودها برای عیب‌یابی؛
    • اسکریپت‌های راه‌اندازی نود؛
    • عامل‌های پایش و امنیتی که مستقیماً روی نودها نصب شده‌اند.
  4. ابزارهای شخص ثالثی که عملیات ممتاز ذکرشده در بالا را انجام می‌دهند. برای اطلاعات بیشتر، مهاجرت عامل‌های تله‌متری و امنیتی از dockershim را ببینید.
  5. مطمئن شوید که هیچ وابستگی غیرمستقیمی به رفتار dockershim وجود ندارد. این یک حالت حاشیه‌ای است و بعید است روی برنامهٔ شما اثر بگذارد. برخی ابزارها ممکن است طوری پیکربندی شده باشند که به رفتارهای مختص Docker واکنش نشان دهند؛ برای مثال، بر اساس متریک‌های خاصی هشدار دهند یا به‌عنوان بخشی از دستورالعمل‌های عیب‌یابی، به‌دنبال پیام لاگ خاصی بگردند. اگر چنین ابزارهایی را پیکربندی کرده‌اید، پیش از مهاجرت، رفتار آن‌ها را روی یک کلاستر آزمایشی بیازمایید.

توضیح وابستگی به Docker {#role-of-dockershim}

محیط اجرای کانتینر نرم‌افزاری است که کانتینرهای تشکیل‌دهندهٔ یک Pod کوبرنتیز را اجرا می‌کند. کوبرنتیز مسئول هماهنگ‌سازی (orchestration) و زمان‌بندی Podها است؛ روی هر نود، kubelet از رابط محیط اجرای کانتینر (CRI) به‌عنوان یک لایهٔ انتزاعی استفاده می‌کند تا بتوانید از هر محیط اجرای کانتینر سازگاری استفاده کنید.

کوبرنتیز در نخستین نسخه‌های خود تنها با یک محیط اجرای کانتینر سازگار بود: Docker. در ادامهٔ تاریخچهٔ پروژهٔ کوبرنتیز، گردانندگان کلاستر خواستار به‌کارگیری محیط‌های اجرای کانتینر دیگری شدند. CRI برای فراهم کردن چنین انعطاف‌پذیری‌ای طراحی شد و kubelet نیز پشتیبانی از CRI را آغاز کرد. با این حال، چون Docker پیش از ابداع مشخصات CRI وجود داشت، پروژهٔ کوبرنتیز یک مؤلفهٔ مبدل (adapter) به نام dockershim ایجاد کرد. مبدل dockershim به kubelet امکان می‌دهد با Docker طوری تعامل کند که گویی Docker یک محیط اجرای سازگار با CRI است.

می‌توانید در پست وبلاگ Kubernetes Containerd integration goes GA دربارهٔ آن بخوانید.

با تغییر محیط اجرای کانتینر به Containerd، واسطه حذف می‌شود. همهٔ همان کانتینرها را می‌توان مانند گذشته با محیط‌های اجرای کانتینری مانند Containerd اجرا کرد. اما اکنون، چون کانتینرها مستقیماً از طریق محیط اجرای کانتینر زمان‌بندی می‌شوند، برای Docker قابل مشاهده نیستند. بنابراین هر ابزار Docker یا رابط کاربری پیشرفته‌ای که پیش‌تر برای بررسی این کانتینرها استفاده می‌کردید، دیگر در دسترس نیست.

نمی‌توانید با دستورهای docker ps یا docker inspect اطلاعات کانتینرها را به دست آورید. از آنجا که نمی‌توانید کانتینرها را فهرست کنید، نمی‌توانید لاگ‌ها را دریافت کنید، کانتینرها را متوقف کنید یا با docker exec چیزی را درون یک کانتینر اجرا کنید.

توجه:

اگر بارهای کاری را از طریق کوبرنتیز اجرا می‌کنید، بهترین راه برای متوقف کردن یک کانتینر استفاده از API کوبرنتیز است، نه استفادهٔ مستقیم از محیط اجرای کانتینر (این توصیه برای همهٔ محیط‌های اجرای کانتینر صدق می‌کند، نه فقط Docker).

همچنان می‌توانید ایمیج‌ها را pull کنید یا با دستور docker build آن‌ها را بسازید. اما ایمیج‌هایی که Docker ساخته یا pull کرده است، برای محیط اجرای کانتینر و کوبرنتیز قابل مشاهده نیستند. برای اینکه کوبرنتیز بتواند از آن‌ها استفاده کند، باید آن‌ها را در یک رجیستری push کرد.

مشکلات شناخته‌شده

برخی متریک‌های فایل‌سیستم وجود ندارند و قالب متریک‌ها متفاوت است

نقطهٔ پایانی (endpoint) /metrics/cadvisor در kubelet متریک‌های Prometheus را ارائه می‌کند؛ همان‌طور که در متریک‌های مؤلفه‌های سیستمی کوبرنتیز مستند شده است. اگر یک گردآورندهٔ متریک نصب کنید که به این نقطهٔ پایانی وابسته باشد، ممکن است با مشکلات زیر روبه‌رو شوید:

  • قالب متریک‌ها روی نود Docker به صورت k8s_<container-name>_<pod-name>_<namespace>_<pod-uid>_<restart-count> است، اما این قالب در محیط‌های اجرای دیگر متفاوت است. برای مثال، روی نود containerd به صورت <container-id> است.
  • برخی متریک‌های فایل‌سیستم به شرح زیر وجود ندارند:
    container_fs_inodes_free
container_fs_inodes_total
container_fs_io_current
container_fs_io_time_seconds_total
container_fs_io_time_weighted_seconds_total
container_fs_limit_bytes
container_fs_read_seconds_total
container_fs_reads_merged_total
container_fs_sector_reads_total
container_fs_sector_writes_total
container_fs_usage_bytes

راه‌حل موقت

می‌توانید با استفاده از cAdvisor به‌صورت یک daemonset مستقل، این مشکل را کاهش دهید.

  1. آخرین نسخهٔ منتشرشدهٔ cAdvisor را با الگوی نام vX.Y.Z-containerd-cri (برای مثال v0.42.0-containerd-cri) پیدا کنید.
  2. برای ایجاد daemonset، گام‌های cAdvisor Kubernetes Daemonset را دنبال کنید.
  3. گردآورندهٔ متریک نصب‌شده را طوری تنظیم کنید که از نقطهٔ پایانی /metrics در cAdvisor استفاده کند؛ این نقطهٔ پایانی مجموعهٔ کامل متریک‌های کانتینر Prometheus را ارائه می‌کند.

راه‌حل‌های جایگزین:

  • از یک راهکار جایگزین شخص ثالث برای گردآوری متریک‌ها استفاده کنید.
  • متریک‌ها را از API خلاصهٔ kubelet که در /stats/summary ارائه می‌شود، گردآوری کنید.

گام‌های بعدی

  • برای آشنایی با گام‌های بعدی، مهاجرت از dockershim را بخوانید.
  • برای اطلاعات بیشتر، مقالهٔ پرسش‌های متداول دربارهٔ منسوخ شدن dockershim را بخوانید.
