این سند نحوهٔ پیکربندی مجدد محدوده‌ (یا محدوده‌های) پیش‌فرض IP سرویس را که به یک کلاستر اختصاص داده شده است، شرح می‌دهد.

پیش از شروع

باید یک کلاستر کوبرنتیز داشته باشید و ابزار خط فرمان kubectl باید برای ارتباط با کلاستر شما پیکربندی شده باشد. توصیه می‌شود این آموزش را روی کلاستری اجرا کنید که دست‌کم دو نود داشته باشد که نقش میزبان control plane را ندارند. اگر هنوز کلاستری ندارید، می‌توانید با استفاده از minikube یکی بسازید یا از یکی از این محیط‌های آزمایشی کوبرنتیز استفاده کنید:

  • iximiuz Labs
  • Killercoda
  • KodeKloud

پیکربندی مجدد ServiceCIDR پیش‌فرض کوبرنتیز

این سند توضیح می‌دهد که چگونه محدودهٔ نشانی‌های IP سرویس را در یک کلاستر کوبرنتیز مدیریت کنید. این محدوده بر خانواده‌های IP پشتیبانی‌شده برای Serviceها در کلاستر نیز اثر می‌گذارد.

خانواده‌های IP در دسترس برای ClusterIPهای Service با فلگ --service-cluster-ip-range در kube-apiserver تعیین می‌شوند. برای درک بهتر نحوهٔ تخصیص نشانی IP به Serviceها، به مستندات ردیابی تخصیص نشانی IP به Serviceها مراجعه کنید.

از نسخهٔ ۱.۳۳ کوبرنتیز، خانواده‌های IP سرویس که برای کلاستر پیکربندی شده‌اند، در آبجکت ServiceCIDR با نام kubernetes منعکس می‌شوند. نخستین نمونهٔ kube-apiserver که راه‌اندازی می‌شود، آبجکت ServiceCIDR با نام kubernetes را بر اساس مقدار پیکربندی‌شدهٔ فلگ --service-cluster-ip-range خود ایجاد می‌کند. برای اطمینان از رفتار یکنواخت کلاستر، همهٔ نمونه‌های kube-apiserver باید با مقادیر یکسانی برای --service-cluster-ip-range پیکربندی شوند و این مقادیر باید با آبجکت ServiceCIDR پیش‌فرض kubernetes مطابقت داشته باشند.

دسته‌بندی‌های پیکربندی مجدد ServiceCIDR در کوبرنتیز

پیکربندی مجدد ServiceCIDR معمولاً در یکی از دسته‌های زیر قرار می‌گیرد:

  • گسترش ServiceCIDRهای موجود: این کار را می‌توان به‌صورت پویا و با افزودن آبجکت‌های ServiceCIDR جدید، بدون نیاز به پیکربندی مجدد kube-apiserver انجام داد. لطفاً به مستندات اختصاصی گسترش محدوده‌های IP سرویس مراجعه کنید.

  • تبدیل تک‌پشته به دوپشته با حفظ ServiceCIDR اصلی: در این حالت، یک خانوادهٔ IP ثانویه (IPv6 به کلاستری که فقط IPv4 دارد، یا IPv4 به کلاستری که فقط IPv6 دارد) اضافه می‌شود و خانوادهٔ IP اولیه همچنان به‌عنوان خانوادهٔ اصلی باقی می‌ماند. این کار مستلزم به‌روزرسانی پیکربندی kube-apiserver و تغییر متناظر در مؤلفه‌های مختلفی از کلاستر است که باید این خانوادهٔ IP اضافی را مدیریت کنند. این مؤلفه‌ها شامل kube-proxy، افزونهٔ CNI یا شبکه، پیاده‌سازی‌های سرویس‌مش (service mesh) و سرویس‌های DNS هستند، اما به این موارد محدود نمی‌شوند.

  • تبدیل دوپشته به تک‌پشته با حفظ ServiceCIDR اصلی: در این حالت، خانوادهٔ IP ثانویه از یک کلاستر دوپشته حذف می‌شود و کلاستر با حفظ خانوادهٔ IP اصلی اولیه به یک خانوادهٔ IP واحد بازمی‌گردد. علاوه بر پیکربندی مجدد مؤلفه‌ها برای تطابق با خانوادهٔ IP جدید، ممکن است لازم باشد Serviceهایی را که صراحتاً برای استفاده از خانوادهٔ IP حذف‌شده پیکربندی شده‌اند نیز رسیدگی کنید.

  • هر تغییری که به تغییر ServiceCIDR اصلی منجر شود: جایگزینی کامل ServiceCIDR پیش‌فرض عملیاتی پیچیده است. اگر ServiceCIDR جدید با ServiceCIDR موجود هم‌پوشانی نداشته باشد، لازم است همهٔ Serviceهای موجود از نو شماره‌گذاری شوند و Service با نام kubernetes.default تغییر کند. حالتی که خانوادهٔ IP اصلی نیز تغییر می‌کند حتی پیچیده‌تر است و ممکن است نیاز باشد چندین مؤلفهٔ کلاستر (kubelet، افزونه‌های شبکه و غیره) برای تطابق با خانوادهٔ IP اصلی جدید تغییر کنند.

عملیات دستی برای جایگزینی ServiceCIDR پیش‌فرض

پیکربندی مجدد ServiceCIDR پیش‌فرض مستلزم گام‌هایی دستی است که اپراتور کلاستر، مدیر آن یا نرم‌افزاری که چرخهٔ عمر کلاستر را مدیریت می‌کند باید انجام دهد. این گام‌ها معمولاً عبارت‌اند از:

  1. به‌روزرسانی پیکربندی kube-apiserver: فلگ --service-cluster-ip-range را با محدوده (یا محدوده‌های) IP جدید تغییر دهید.
  2. پیکربندی مجدد مؤلفه‌های شبکه: این گامی حیاتی است و روال دقیق آن به مؤلفه‌های شبکهٔ مورد استفاده بستگی دارد. این کار ممکن است شامل به‌روزرسانی فایل‌های پیکربندی، راه‌اندازی مجدد Podهای عامل (agent) یا به‌روزرسانی مؤلفه‌ها باشد تا ServiceCIDR(های) جدید و پیکربندی خانوادهٔ IP مطلوب برای Podها را مدیریت کنند. مؤلفه‌های رایج می‌توانند پیاده‌سازی Serviceهای کوبرنتیز مانند kube-proxy، افزونهٔ شبکهٔ پیکربندی‌شده و احتمالاً دیگر مؤلفه‌های شبکه مانند کنترل‌کننده‌های سرویس‌مش و سرورهای DNS باشند. هدف این است که این مؤلفه‌ها بتوانند ترافیک را به‌درستی مدیریت کنند و کشف سرویس (service discovery) را با پیکربندی جدید خانوادهٔ IP انجام دهند.
  3. مدیریت Serviceهای موجود: Serviceهایی که IP آن‌ها از CIDR قدیمی است و در محدوده‌های پیکربندی‌شدهٔ جدید قرار نمی‌گیرند، باید رسیدگی شوند. گزینه‌ها شامل ایجاد دوبارهٔ آن‌ها (که به قطعی سرویس و تخصیص IPهای جدید منجر می‌شود) یا راهبردهای احتمالاً پیچیده‌تر پیکربندی مجدد است.
  4. ایجاد دوبارهٔ سرویس‌های داخلی کوبرنتیز: اگر خانوادهٔ IP اصلی تغییر کند یا با شبکهٔ دیگری جایگزین شود، Service با نام kubernetes.default باید حذف و دوباره ایجاد شود تا نشانی IP خود را از ServiceCIDR جدید دریافت کند.

گام‌های نمونه برای پیکربندی مجدد

گام‌های زیر یک پیکربندی مجدد کنترل‌شده را شرح می‌دهند که بر جایگزینی کامل ServiceCIDR پیش‌فرض و ایجاد دوبارهٔ Service با نام kubernetes.default تمرکز دارد:

  1. kube-apiserver را با مقدار اولیهٔ --service-cluster-ip-range راه‌اندازی کنید.
  2. Serviceهای اولیه‌ای ایجاد کنید که IP خود را از این محدوده دریافت می‌کنند.
  3. یک ServiceCIDR جدید را به‌عنوان مقصد موقت برای پیکربندی مجدد اضافه کنید.
  4. ServiceCIDR پیش‌فرض kubernetes را برای حذف علامت‌گذاری کنید (به دلیل وجود IPهای موجود و finalizerها، این آبجکت در وضعیت معلق باقی می‌ماند). این کار از تخصیص‌های جدید از محدودهٔ قدیمی جلوگیری می‌کند.
  5. Serviceهای موجود را دوباره ایجاد کنید. اکنون باید IPها از ServiceCIDR موقت جدید به آن‌ها تخصیص داده شود.
  6. kube-apiserver را با ServiceCIDR(های) جدید پیکربندی‌شده دوباره راه‌اندازی کنید و نمونهٔ قدیمی را خاموش کنید.
  7. Service با نام kubernetes.default را حذف کنید. kube-apiserver جدید آن را در ServiceCIDR جدید دوباره ایجاد می‌کند.

گام‌های بعدی

  • مفاهیم شبکه در کوبرنتیز
  • Serviceهای دوپشته در کوبرنتیز
  • گسترش محدوده‌های IP سرویس در کوبرنتیز
