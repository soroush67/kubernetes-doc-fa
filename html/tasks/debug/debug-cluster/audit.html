ممیزی

ممیزی (auditing) در کوبرنتیز مجموعه‌ای از سوابق مرتبط با امنیت و مرتب بر اساس زمان فراهم می‌کند که توالی رویدادهای یک کلاستر را مستند می‌کند. کلاستر فعالیت‌هایی را ممیزی می‌کند که کاربران، برنامه‌های کاربردی استفاده‌کننده از API کوبرنتیز و خودِ control plane ایجاد می‌کنند.

ممیزی به مدیران کلاستر امکان می‌دهد به پرسش‌های زیر پاسخ دهند:

  • چه اتفاقی افتاد؟
  • چه زمانی رخ داد؟
  • چه کسی آن را آغاز کرد؟
  • روی چه چیزی رخ داد؟
  • کجا مشاهده شد؟
  • از کجا آغاز شد؟
  • به کجا می‌رفت؟

چرخهٔ عمر سوابق ممیزی درون مؤلفهٔ kube-apiserver آغاز می‌شود. هر درخواست در هر مرحله از اجرای خود یک رویداد ممیزی تولید می‌کند. این رویداد سپس طبق یک سیاست مشخص پیش‌پردازش می‌شود و در یک بک‌اند (backend) نوشته می‌شود. سیاست تعیین می‌کند چه چیزی ثبت شود و بک‌اندها سوابق را به‌طور ماندگار نگه می‌دارند. پیاده‌سازی‌های کنونی بک‌اند شامل فایل‌های لاگ و وب‌هوک‌ها (webhooks) هستند.

هر درخواست را می‌توان همراه با یک مرحله (stage) مرتبط ثبت کرد. مراحل تعریف‌شده عبارت‌اند از:

  • RequestReceived - مرحلهٔ رویدادهایی که بلافاصله پس از دریافت درخواست به‌دست handler ممیزی و پیش از واگذاری آن به ادامهٔ زنجیرهٔ handlerها تولید می‌شوند.
  • ResponseStarted - پس از ارسال سرآیندهای پاسخ و پیش از ارسال بدنهٔ پاسخ. این مرحله فقط برای درخواست‌های طولانی‌مدت (مثلاً watch) تولید می‌شود.
  • ResponseComplete - بدنهٔ پاسخ کامل شده است و بایت دیگری ارسال نخواهد شد.
  • Panic - رویدادهایی که هنگام وقوع panic تولید می‌شوند.
توجه:

پیکربندی یک رویداد ممیزی (Audit Event) با آبجکت API Event متفاوت است.

قابلیت ثبت لاگ ممیزی مصرف حافظهٔ API server را افزایش می‌دهد، زیرا بخشی از اطلاعات زمینه‌ای لازم برای ممیزی به ازای هر درخواست ذخیره می‌شود. میزان مصرف حافظه به پیکربندی لاگ ممیزی بستگی دارد.

سیاست ممیزی

سیاست ممیزی قواعدی را تعریف می‌کند که مشخص می‌کنند کدام رویدادها باید ثبت شوند و چه داده‌هایی باید در آن‌ها گنجانده شود. ساختار آبجکت سیاست ممیزی در گروه API audit.k8s.io تعریف شده است. هنگام پردازش یک رویداد، آن رویداد به‌ترتیب با فهرست قواعد مقایسه می‌شود. نخستین قاعدهٔ منطبق، سطح ممیزی (audit level) رویداد را تعیین می‌کند. سطوح ممیزی تعریف‌شده عبارت‌اند از:

  • None - رویدادهای منطبق با این قاعده لاگ نشوند.
  • Metadata - رویدادها همراه با فراداده (کاربر درخواست‌دهنده، مُهر زمانی، منبع، فعل و غیره) لاگ شوند، اما بدنهٔ درخواست یا پاسخ لاگ نشود.
  • Request - رویدادها همراه با فراداده و بدنهٔ درخواست لاگ شوند، اما بدنهٔ پاسخ لاگ نشود. این سطح برای درخواست‌های غیرمنبعی اعمال نمی‌شود.
  • RequestResponse - رویدادها همراه با فرادادهٔ درخواست، بدنهٔ درخواست و بدنهٔ پاسخ لاگ شوند. این سطح برای درخواست‌های غیرمنبعی اعمال نمی‌شود.

می‌توانید فایل سیاست را با فلگ --audit-policy-file به kube-apiserver بدهید. اگر این فلگ حذف شود، هیچ رویدادی لاگ نمی‌شود. توجه کنید که فیلد rules باید در فایل سیاست ممیزی وجود داشته باشد. سیاستی که هیچ قاعده‌ای (صفر قاعده) نداشته باشد نامعتبر شمرده می‌شود.

در ادامه نمونه‌ای از فایل سیاست ممیزی آمده است:

audit/audit-policy.yaml
apiVersion: audit.k8s.io/v1 # This is required.
kind: Policy
# Don't generate audit events for all requests in RequestReceived stage.
omitStages:
  - "RequestReceived"
rules:
  # Log pod changes at RequestResponse level
  - level: RequestResponse
    resources:
    - group: ""
      # Resource "pods" doesn't match requests to any subresource of pods,
      # which is consistent with the RBAC policy.
      resources: ["pods"]
  # Log "pods/log", "pods/status" at Metadata level
  - level: Metadata
    resources:
    - group: ""
      resources: ["pods/log", "pods/status"]

  # Don't log requests to a configmap called "controller-leader"
  - level: None
    resources:
    - group: ""
      resources: ["configmaps"]
      resourceNames: ["controller-leader"]

  # Don't log watch requests by the "system:kube-proxy" on endpoints or services
  - level: None
    users: ["system:kube-proxy"]
    verbs: ["watch"]
    resources:
    - group: "" # core API group
      resources: ["endpoints", "services"]

  # Don't log authenticated requests to certain non-resource URL paths.
  - level: None
    userGroups: ["system:authenticated"]
    nonResourceURLs:
    - "/api*" # Wildcard matching.
    - "/version"

  # Log the request body of configmap changes in kube-system.
  - level: Request
    resources:
    - group: "" # core API group
      resources: ["configmaps"]
    # This rule only applies to resources in the "kube-system" namespace.
    # The empty string "" can be used to select non-namespaced resources.
    namespaces: ["kube-system"]

  # Log configmap and secret changes in all other namespaces at the Metadata level.
  - level: Metadata
    resources:
    - group: "" # core API group
      resources: ["secrets", "configmaps"]

  # Log all other resources in core and extensions at the Request level.
  - level: Request
    resources:
    - group: "" # core API group
    - group: "extensions" # Version of group should NOT be included.

  # A catch-all rule to log all other requests at the Metadata level.
  - level: Metadata
    # Long-running requests like watches that fall under this rule will not
    # generate an audit event in RequestReceived.
    omitStages:
      - "RequestReceived"

برای لاگ کردن همهٔ درخواست‌ها در سطح Metadata می‌توانید از یک فایل سیاست ممیزی حداقلی استفاده کنید:

# Log all requests at the Metadata level.
apiVersion: audit.k8s.io/v1
kind: Policy
rules:
- level: Metadata

اگر نمایهٔ ممیزی خودتان را می‌سازید، می‌توانید نمایهٔ ممیزی Google Container-Optimized OS را نقطهٔ شروع قرار دهید. می‌توانید اسکریپت configure-helper.sh را بررسی کنید که یک فایل سیاست ممیزی تولید می‌کند. با نگاه مستقیم به این اسکریپت، بیشتر محتوای فایل سیاست ممیزی را می‌توانید ببینید.

برای جزئیات فیلدهای تعریف‌شده می‌توانید به مرجع پیکربندی Policy نیز مراجعه کنید.

بک‌اندهای ممیزی

بک‌اندهای ممیزی رویدادهای ممیزی را در یک ذخیره‌سازی خارجی به‌طور ماندگار نگه می‌دارند. kube-apiserver به‌طور پیش‌فرض دو بک‌اند ارائه می‌کند:

  • بک‌اند لاگ، که رویدادها را در سیستم فایل می‌نویسد
  • بک‌اند وب‌هوک، که رویدادها را به یک HTTP API خارجی می‌فرستد

در همهٔ حالت‌ها، رویدادهای ممیزی از ساختاری پیروی می‌کنند که API کوبرنتیز در گروه API audit.k8s.io تعریف کرده است.

توجه:

در مورد patchها، بدنهٔ درخواست یک آرایهٔ JSON شامل عملیات patch است، نه یک آبجکت JSON حاوی آبجکت API مناسب کوبرنتیز. برای مثال، بدنهٔ درخواست زیر یک درخواست patch معتبر به /apis/batch/v1/namespaces/some-namespace/jobs/some-job-name است:

[
  {
    "op": "replace",
    "path": "/spec/parallelism",
    "value": 0
  },
  {
    "op": "remove",
    "path": "/spec/template/spec/containers/0/terminationMessagePolicy"
  }
]

بک‌اند لاگ

بک‌اند لاگ رویدادهای ممیزی را با قالب JSONlines در یک فایل می‌نویسد. بک‌اند لاگ ممیزی را می‌توانید با فلگ‌های زیرِ kube-apiserver پیکربندی کنید:

  • فلگ --audit-log-path مسیر فایل لاگی را مشخص می‌کند که بک‌اند لاگ رویدادهای ممیزی را در آن می‌نویسد. اگر این فلگ مشخص نشود، بک‌اند لاگ غیرفعال می‌شود. مقدار - به معنای خروجی استاندارد است
  • فلگ --audit-log-maxage حداکثر تعداد روزهای نگهداری فایل‌های لاگ ممیزی قدیمی را تعیین می‌کند
  • فلگ --audit-log-maxbackup حداکثر تعداد فایل‌های لاگ ممیزی نگهداری‌شده را تعیین می‌کند
  • فلگ --audit-log-maxsize حداکثر اندازهٔ فایل لاگ ممیزی را بر حسب مگابایت، پیش از چرخش (rotation) آن، تعیین می‌کند

اگر control plane کلاستر شما kube-apiserver را به‌صورت یک Pod اجرا می‌کند، به یاد داشته باشید که hostPath را به محل فایل سیاست و فایل لاگ mount کنید تا سوابق ممیزی ماندگار بمانند. برای مثال:

  - --audit-policy-file=/etc/kubernetes/audit-policy.yaml
  - --audit-log-path=/var/log/kubernetes/audit/audit.log

سپس حجم‌ها را mount کنید:

...
volumeMounts:
  - mountPath: /etc/kubernetes/audit-policy.yaml
    name: audit
    readOnly: true
  - mountPath: /var/log/kubernetes/audit/
    name: audit-log
    readOnly: false

و در پایان hostPath را پیکربندی کنید:

...
volumes:
- name: audit
  hostPath:
    path: /etc/kubernetes/audit-policy.yaml
    type: File

- name: audit-log
  hostPath:
    path: /var/log/kubernetes/audit/
    type: DirectoryOrCreate

بک‌اند وب‌هوک

بک‌اند ممیزی وب‌هوک رویدادهای ممیزی را به یک وب API راه دور می‌فرستد که فرض می‌شود گونه‌ای از API کوبرنتیز، همراه با سازوکارهای احراز هویت، است. بک‌اند ممیزی وب‌هوک را می‌توانید با فلگ‌های زیرِ kube-apiserver پیکربندی کنید:

  • فلگ --audit-webhook-config-file مسیر فایلی را مشخص می‌کند که پیکربندی وب‌هوک در آن قرار دارد. پیکربندی وب‌هوک در عمل یک kubeconfig تخصصی است.
  • فلگ --audit-webhook-initial-backoff مدت زمان انتظار پس از نخستین درخواست ناموفق و پیش از تلاش دوباره را مشخص می‌کند. درخواست‌های بعدی با عقب‌نشینی نمایی (exponential backoff) دوباره تلاش می‌شوند.

فایل پیکربندی وب‌هوک از قالب kubeconfig برای مشخص کردن نشانی راه دور سرویس و اعتبارنامه‌های لازم برای اتصال به آن استفاده می‌کند.

دسته‌بندی رویدادها {#batching}

هر دو بک‌اند log و webhook از دسته‌بندی (batching) پشتیبانی می‌کنند. در ادامه فهرست فلگ‌های موجود برای هر بک‌اند آمده است. به‌طور پیش‌فرض، دسته‌بندی و محدودسازی نرخ (throttling) برای بک‌اند webhook فعال و برای بک‌اند log غیرفعال است.

webhook
  • فلگ --audit-webhook-mode راهبرد بافر کردن را تعیین می‌کند و یکی از مقادیر زیر را می‌پذیرد:
    • batch - رویدادها بافر می‌شوند و به‌صورت ناهمگام در دسته‌ها پردازش می‌شوند. این حالت پیش‌فرض بک‌اند webhook است.
    • blocking - پاسخ‌های API server تا پردازش هر رویداد مسدود می‌شوند.
    • blocking-strict - همانند blocking است، با این تفاوت که اگر هنگام ثبت لاگ ممیزی در مرحلهٔ RequestReceived خطایی رخ دهد، کل درخواست به kube-apiserver ناموفق می‌شود.

فلگ‌های زیر فقط در حالت batch استفاده می‌شوند:

  • فلگ --audit-webhook-batch-buffer-size تعداد رویدادهایی را که پیش از دسته‌بندی بافر می‌شوند تعیین می‌کند. اگر نرخ رویدادهای ورودی از ظرفیت بافر فراتر رود، رویدادها دور ریخته می‌شوند. مقدار پیش‌فرض ۱۰۰۰۰ است.
  • فلگ --audit-webhook-batch-max-size حداکثر تعداد رویدادهای یک دسته را تعیین می‌کند. مقدار پیش‌فرض ۴۰۰ است.
  • فلگ --audit-webhook-batch-max-wait حداکثر مدت انتظار پیش از دسته‌بندی بی‌قیدوشرط رویدادهای صف را تعیین می‌کند. مقدار پیش‌فرض ۳۰ ثانیه است.
  • فلگ --audit-webhook-batch-throttle-enable تعیین می‌کند که محدودسازی نرخ دسته‌بندی فعال باشد یا نه. محدودسازی نرخ به‌طور پیش‌فرض فعال است.
  • فلگ --audit-webhook-batch-throttle-qps حداکثر میانگین تعداد دسته‌های تولیدشده در هر ثانیه را تعیین می‌کند. مقدار پیش‌فرض ۱۰ است.
  • فلگ --audit-webhook-batch-throttle-burst حداکثر تعداد دسته‌هایی را تعیین می‌کند که اگر پیش‌تر از QPS مجاز به‌طور کامل استفاده نشده باشد، می‌توانند در یک لحظه تولید شوند. مقدار پیش‌فرض ۱۵ است.
log
  • فلگ --audit-log-mode راهبرد بافر کردن را تعیین می‌کند و یکی از مقادیر زیر را می‌پذیرد:
    • batch - رویدادها بافر می‌شوند و به‌صورت ناهمگام در دسته‌ها پردازش می‌شوند. دسته‌بندی برای بک‌اند log توصیه نمی‌شود.
    • blocking - پاسخ‌های API server تا پردازش هر رویداد مسدود می‌شوند. این حالت پیش‌فرض بک‌اند log است.
    • blocking-strict - همانند blocking است، با این تفاوت که اگر هنگام ثبت لاگ ممیزی در مرحلهٔ RequestReceived خطایی رخ دهد، کل درخواست به kube-apiserver ناموفق می‌شود.

فلگ‌های زیر فقط در حالت batch استفاده می‌شوند (دسته‌بندی برای بک‌اند log به‌طور پیش‌فرض غیرفعال است و وقتی دسته‌بندی غیرفعال باشد، همهٔ فلگ‌های مرتبط با آن نادیده گرفته می‌شوند):

  • فلگ --audit-log-batch-buffer-size تعداد رویدادهایی را که پیش از دسته‌بندی بافر می‌شوند تعیین می‌کند. اگر نرخ رویدادهای ورودی از ظرفیت بافر فراتر رود، رویدادها دور ریخته می‌شوند.
  • فلگ --audit-log-batch-max-size حداکثر تعداد رویدادهای یک دسته را تعیین می‌کند.
  • فلگ --audit-log-batch-max-wait حداکثر مدت انتظار پیش از دسته‌بندی بی‌قیدوشرط رویدادهای صف را تعیین می‌کند.
  • فلگ --audit-log-batch-throttle-enable تعیین می‌کند که محدودسازی نرخ دسته‌بندی فعال باشد یا نه.
  • فلگ --audit-log-batch-throttle-qps حداکثر میانگین تعداد دسته‌های تولیدشده در هر ثانیه را تعیین می‌کند.
  • فلگ --audit-log-batch-throttle-burst حداکثر تعداد دسته‌هایی را تعیین می‌کند که اگر پیش‌تر از QPS مجاز به‌طور کامل استفاده نشده باشد، می‌توانند در یک لحظه تولید شوند.

تنظیم پارامترها

پارامترها باید متناسب با بار وارد بر API server تنظیم شوند.

برای مثال، اگر kube-apiserver در هر ثانیه ۱۰۰ درخواست دریافت کند و هر درخواست فقط در مراحل ResponseStarted و ResponseComplete ممیزی شود، باید تولید حدود ۲۰۰ رویداد ممیزی در هر ثانیه را در نظر بگیرید. با فرض اینکه هر دسته حداکثر ۱۰۰ رویداد داشته باشد، باید سطح محدودسازی نرخ را دست‌کم ۲ درخواست در ثانیه تنظیم کنید. با فرض اینکه نوشتن رویدادها در بک‌اند تا ۵ ثانیه طول بکشد، باید اندازهٔ بافر را طوری تنظیم کنید که رویدادهای ۵ ثانیه را در خود جای دهد؛ یعنی ۱۰ دسته یا ۱۰۰۰ رویداد.

با این حال، در بیشتر موارد پارامترهای پیش‌فرض کافی هستند و نیازی به تنظیم دستی آن‌ها ندارید. برای پایش وضعیت زیرسیستم ممیزی، می‌توانید متریک‌های Prometheus زیر را که kube-apiserver ارائه می‌کند و همچنین لاگ‌ها را بررسی کنید.

  • متریک apiserver_audit_event_total شامل تعداد کل رویدادهای ممیزی صادرشده است.
  • متریک apiserver_audit_error_total شامل تعداد کل رویدادهایی است که به‌دلیل خطا در هنگام صدور دور ریخته شده‌اند.

کوتاه‌سازی مدخل‌های لاگ {#truncate}

هر دو بک‌اند لاگ و وب‌هوک از محدود کردن اندازهٔ رویدادهای لاگ‌شده پشتیبانی می‌کنند. برای نمونه، فهرست فلگ‌های موجود برای بک‌اند لاگ به این شرح است:

  • فلگ audit-log-truncate-enabled تعیین می‌کند که کوتاه‌سازی رویدادها و دسته‌ها فعال باشد یا نه.
  • فلگ audit-log-truncate-max-batch-size حداکثر اندازهٔ دستهٔ ارسالی به بک‌اند زیرین را بر حسب بایت تعیین می‌کند.
  • فلگ audit-log-truncate-max-event-size حداکثر اندازهٔ رویداد ممیزی ارسالی به بک‌اند زیرین را بر حسب بایت تعیین می‌کند.

کوتاه‌سازی به‌طور پیش‌فرض در هر دو بک‌اند webhook و log غیرفعال است؛ مدیر کلاستر برای فعال کردن این قابلیت باید audit-log-truncate-enabled یا audit-webhook-truncate-enabled را تنظیم کند.

گام‌های بعدی

  • دربارهٔ حاشیه‌نویسی‌های (annotations) ممیزی وب‌هوک‌های تغییردهنده بیاموزید.
  • با مطالعهٔ مرجع پیکربندی ممیزی، دربارهٔ انواع منبع Event و Policy بیشتر بیاموزید.
