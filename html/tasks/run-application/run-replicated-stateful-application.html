اجرای یک برنامهٔ حالت‌مند تکثیرشده

این صفحه نشان می‌دهد چگونه می‌توان یک برنامهٔ حالت‌مند (stateful) تکثیرشده را با استفاده از یک statefulset اجرا کرد. این برنامه یک پایگاه دادهٔ MySQL تکثیرشده است. توپولوژی این مثال از یک سرور اصلی (primary) و چند رونوشت (replica) تشکیل شده و از تکثیر ناهمگام مبتنی بر سطر (asynchronous row-based replication) استفاده می‌کند.

توجه:

این پیکربندی برای محیط عملیاتی مناسب نیست. تنظیمات MySQL روی مقادیر پیش‌فرض ناامن باقی مانده‌اند تا تمرکز بر الگوهای کلی اجرای برنامه‌های حالت‌مند در کوبرنتیز حفظ شود.

پیش از شروع

باید یک کلاستر کوبرنتیز داشته باشید و ابزار خط فرمان kubectl باید برای ارتباط با کلاستر شما پیکربندی شده باشد. توصیه می‌شود این آموزش را روی کلاستری اجرا کنید که دست‌کم دو نود داشته باشد که نقش میزبان control plane را ندارند. اگر هنوز کلاستری ندارید، می‌توانید با استفاده از minikube یکی بسازید یا از یکی از این محیط‌های آزمایشی کوبرنتیز استفاده کنید:

  • iximiuz Labs
  • Killercoda
  • KodeKloud

برای تأمین PersistentVolumeClaim‌هایی که در اینجا استفاده می‌شوند، باید یا یک تأمین‌کننده پویای PersistentVolume با یک StorageClass پیش‌فرض داشته باشید، یا خودتان PersistentVolume‌ها را به‌صورت ایستا تأمین کنید.

  • این آموزش فرض می‌کند که با PersistentVolumeها و StatefulSetها و همچنین با سایر مفاهیم اصلی مانند Podها، Serviceها و ConfigMapها آشنا هستید.
  • آشنایی نسبی با MySQL مفید است، اما هدف این آموزش ارائهٔ الگوهای کلی‌ای است که برای سیستم‌های دیگر نیز سودمند باشند.
  • از فضای نام (namespace) پیش‌فرض یا فضای نام دیگری استفاده می‌کنید که هیچ آبجکت متعارضی در آن وجود ندارد.
  • به یک پردازندهٔ سازگار با AMD64 نیاز دارید.

اهداف

  • یک توپولوژی MySQL تکثیرشده را با یک StatefulSet مستقر کنید.
  • ترافیک کلاینت MySQL ارسال کنید.
  • مقاومت در برابر از دسترس خارج شدن را مشاهده کنید.
  • مقیاس StatefulSet را افزایش و کاهش دهید.

استقرار MySQL

استقرار نمونهٔ MySQL از یک ConfigMap، دو Service و یک StatefulSet تشکیل شده است.

ایجاد یک ConfigMap {#configmap}

ConfigMap را از فایل پیکربندی YAML زیر ایجاد کنید:

application/mysql/mysql-configmap.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: mysql
  labels:
    app: mysql
    app.kubernetes.io/name: mysql
data:
  primary.cnf: |
    # Apply this config only on the primary.
    [mysqld]
    log-bin
  replica.cnf: |
    # Apply this config only on replicas.
    [mysqld]
    super-read-only

kubectl apply -f https://k8s.io/examples/application/mysql/mysql-configmap.yaml

این ConfigMap مقادیری برای بازنویسی فایل my.cnf فراهم می‌کند تا بتوانید پیکربندی سرور اصلی MySQL و رونوشت‌های آن را به‌طور مستقل کنترل کنید. در این مثال، می‌خواهید سرور اصلی بتواند لاگ‌های تکثیر را در اختیار رونوشت‌ها قرار دهد و رونوشت‌ها هر عملیات نوشتنی را که از طریق تکثیر نرسیده است رد کنند.

خود ConfigMap ویژگی خاصی ندارد که باعث شود بخش‌های مختلف آن روی Podهای مختلف اعمال شوند. هر Pod هنگام راه‌اندازی، بر اساس اطلاعاتی که کنترل‌کنندهٔ StatefulSet در اختیارش می‌گذارد، تصمیم می‌گیرد کدام بخش را بخواند.

ایجاد Serviceها {#services}

Serviceها را از فایل پیکربندی YAML زیر ایجاد کنید:

application/mysql/mysql-services.yaml
# Headless service for stable DNS entries of StatefulSet members.
apiVersion: v1
kind: Service
metadata:
  name: mysql
  labels:
    app: mysql
    app.kubernetes.io/name: mysql
spec:
  ports:
  - name: mysql
    port: 3306
  clusterIP: None
  selector:
    app: mysql
---
# Client service for connecting to any MySQL instance for reads.
# For writes, you must instead connect to the primary: mysql-0.mysql.
apiVersion: v1
kind: Service
metadata:
  name: mysql-read
  labels:
    app: mysql
    app.kubernetes.io/name: mysql
    readonly: "true"
spec:
  ports:
  - name: mysql
    port: 3306
  selector:
    app: mysql

kubectl apply -f https://k8s.io/examples/application/mysql/mysql-services.yaml

Service بدون سر (headless) محلی برای رکوردهای DNS فراهم می‌کند که کنترل‌کننده‌های StatefulSet برای هر Pod عضو این مجموعه ایجاد می‌کنند. از آنجا که نام این Service بدون سر mysql است، می‌توان از درون هر Pod دیگری در همان کلاستر و فضای نام کوبرنتیز، با resolve کردن <pod-name>.mysql به Podها دسترسی داشت.

Service کلاینت با نام mysql-read یک Service معمولی است که cluster IP مخصوص به خود را دارد و اتصال‌ها را بین همهٔ Podهای MySQL که وضعیت Ready گزارش می‌کنند توزیع می‌کند. مجموعهٔ endpointهای احتمالی شامل سرور اصلی MySQL و همهٔ رونوشت‌ها است.

توجه کنید که فقط کوئری‌های خواندنی می‌توانند از Service کلاینت با توازن بار استفاده کنند. از آنجا که تنها یک سرور اصلی MySQL وجود دارد، کلاینت‌ها برای انجام عملیات نوشتن باید مستقیماً (از طریق رکورد DNS آن در Service بدون سر) به Pod اصلی MySQL متصل شوند.

ایجاد StatefulSet {#statefulset}

در پایان، StatefulSet را از فایل پیکربندی YAML زیر ایجاد کنید:

application/mysql/mysql-statefulset.yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mysql
spec:
  selector:
    matchLabels:
      app: mysql
      app.kubernetes.io/name: mysql
  serviceName: mysql
  replicas: 3
  template:
    metadata:
      labels:
        app: mysql
        app.kubernetes.io/name: mysql
    spec:
      initContainers:
      - name: init-mysql
        image: mysql:5.7
        command:
        - bash
        - "-c"
        - |
          set -ex
          # Generate mysql server-id from pod ordinal index.
          [[ $HOSTNAME =~ -([0-9]+)$ ]] || exit 1
          ordinal=${BASH_REMATCH[1]}
          echo [mysqld] > /mnt/conf.d/server-id.cnf
          # Add an offset to avoid reserved server-id=0 value.
          echo server-id=$((100 + $ordinal)) >> /mnt/conf.d/server-id.cnf
          # Copy appropriate conf.d files from config-map to emptyDir.
          if [[ $ordinal -eq 0 ]]; then
            cp /mnt/config-map/primary.cnf /mnt/conf.d/
          else
            cp /mnt/config-map/replica.cnf /mnt/conf.d/
          fi
        volumeMounts:
        - name: conf
          mountPath: /mnt/conf.d
        - name: config-map
          mountPath: /mnt/config-map
      - name: clone-mysql
        image: gcr.io/google-samples/xtrabackup:1.0
        command:
        - bash
        - "-c"
        - |
          set -ex
          # Skip the clone if data already exists.
          [[ -d /var/lib/mysql/mysql ]] && exit 0
          # Skip the clone on primary (ordinal index 0).
          [[ `hostname` =~ -([0-9]+)$ ]] || exit 1
          ordinal=${BASH_REMATCH[1]}
          [[ $ordinal -eq 0 ]] && exit 0
          # Clone data from previous peer.
          ncat --recv-only mysql-$(($ordinal-1)).mysql 3307 | xbstream -x -C /var/lib/mysql
          # Prepare the backup.
          xtrabackup --prepare --target-dir=/var/lib/mysql
        volumeMounts:
        - name: data
          mountPath: /var/lib/mysql
          subPath: mysql
        - name: conf
          mountPath: /etc/mysql/conf.d
      containers:
      - name: mysql
        image: mysql:5.7
        env:
        - name: MYSQL_ALLOW_EMPTY_PASSWORD
          value: "1"
        ports:
        - name: mysql
          containerPort: 3306
        volumeMounts:
        - name: data
          mountPath: /var/lib/mysql
          subPath: mysql
        - name: conf
          mountPath: /etc/mysql/conf.d
        resources:
          requests:
            cpu: 500m
            memory: 1Gi
        livenessProbe:
          exec:
            command: ["mysqladmin", "ping"]
          initialDelaySeconds: 30
          periodSeconds: 10
          timeoutSeconds: 5
        readinessProbe:
          exec:
            # Check we can execute queries over TCP (skip-networking is off).
            command: ["mysql", "-h", "127.0.0.1", "-e", "SELECT 1"]
          initialDelaySeconds: 5
          periodSeconds: 2
          timeoutSeconds: 1
      - name: xtrabackup
        image: gcr.io/google-samples/xtrabackup:1.0
        ports:
        - name: xtrabackup
          containerPort: 3307
        command:
        - bash
        - "-c"
        - |
          set -ex
          cd /var/lib/mysql

          # Determine binlog position of cloned data, if any.
          if [[ -f xtrabackup_slave_info && "x$(<xtrabackup_slave_info)" != "x" ]]; then
            # XtraBackup already generated a partial "CHANGE MASTER TO" query
            # because we're cloning from an existing replica. (Need to remove the tailing semicolon!)
            cat xtrabackup_slave_info | sed -E 's/;$//g' > change_master_to.sql.in
            # Ignore xtrabackup_binlog_info in this case (it's useless).
            rm -f xtrabackup_slave_info xtrabackup_binlog_info
          elif [[ -f xtrabackup_binlog_info ]]; then
            # We're cloning directly from primary. Parse binlog position.
            [[ `cat xtrabackup_binlog_info` =~ ^(.*?)[[:space:]]+(.*?)$ ]] || exit 1
            rm -f xtrabackup_binlog_info xtrabackup_slave_info
            echo "CHANGE MASTER TO MASTER_LOG_FILE='${BASH_REMATCH[1]}',\
                  MASTER_LOG_POS=${BASH_REMATCH[2]}" > change_master_to.sql.in
          fi

          # Check if we need to complete a clone by starting replication.
          if [[ -f change_master_to.sql.in ]]; then
            echo "Waiting for mysqld to be ready (accepting connections)"
            until mysql -h 127.0.0.1 -e "SELECT 1"; do sleep 1; done

            echo "Initializing replication from clone position"
            mysql -h 127.0.0.1 \
                  -e "$(<change_master_to.sql.in), \
                          MASTER_HOST='mysql-0.mysql', \
                          MASTER_USER='root', \
                          MASTER_PASSWORD='', \
                          MASTER_CONNECT_RETRY=10; \
                        START SLAVE;" || exit 1
            # In case of container restart, attempt this at-most-once.
            mv change_master_to.sql.in change_master_to.sql.orig
          fi

          # Start a server to send backups when requested by peers.
          exec ncat --listen --keep-open --send-only --max-conns=1 3307 -c \
            "xtrabackup --backup --slave-info --stream=xbstream --host=127.0.0.1 --user=root"
        volumeMounts:
        - name: data
          mountPath: /var/lib/mysql
          subPath: mysql
        - name: conf
          mountPath: /etc/mysql/conf.d
        resources:
          requests:
            cpu: 100m
            memory: 100Mi
      volumes:
      - name: conf
        emptyDir: {}
      - name: config-map
        configMap:
          name: mysql
  volumeClaimTemplates:
  - metadata:
      name: data
    spec:
      accessModes: ["ReadWriteOnce"]
      resources:
        requests:
          storage: 10Gi

kubectl apply -f https://k8s.io/examples/application/mysql/mysql-statefulset.yaml

با اجرای دستور زیر می‌توانید روند راه‌اندازی را دنبال کنید:

kubectl get pods -l app=mysql --watch

پس از مدتی، باید ببینید که هر ۳ Pod به وضعیت Running رسیده‌اند:

NAME      READY     STATUS    RESTARTS   AGE
mysql-0   2/2       Running   0          2m
mysql-1   2/2       Running   0          1m
mysql-2   2/2       Running   0          1m

برای لغو دنبال کردن، کلیدهای Ctrl+C را فشار دهید.

توجه:

اگر هیچ پیشرفتی مشاهده نمی‌کنید، مطمئن شوید که یک تأمین‌کنندهٔ پویای PersistentVolume (dynamic provisioner) فعال دارید؛ همان‌طور که در پیش‌نیازها ذکر شده است.

این مانیفست از روش‌های گوناگونی برای مدیریت Podهای حالت‌مند به‌عنوان بخشی از یک StatefulSet استفاده می‌کند. بخش بعدی برخی از این روش‌ها را برجسته می‌کند تا توضیح دهد هنگام ایجاد Podها به‌دست StatefulSet چه اتفاقی می‌افتد.

آشنایی با راه‌اندازی اولیهٔ Podهای حالت‌مند

کنترل‌کنندهٔ StatefulSet، Podها را یکی‌یکی و به ترتیب اندیس ترتیبی (ordinal index) آن‌ها راه‌اندازی می‌کند. این کنترل‌کننده پیش از راه‌اندازی هر Pod، منتظر می‌ماند تا Pod قبلی وضعیت Ready را گزارش کند.

افزون بر این، کنترل‌کننده به هر Pod نامی یکتا و پایدار به شکل <statefulset-name>-<ordinal-index> اختصاص می‌دهد؛ در نتیجه Podها با نام‌های mysql-0، mysql-1 و mysql-2 ایجاد می‌شوند.

الگوی Pod در مانیفست StatefulSet بالا از این ویژگی‌ها بهره می‌گیرد تا راه‌اندازی تکثیر MySQL را به‌صورت منظم انجام دهد.

تولید پیکربندی

پیش از راه‌اندازی هر یک از کانتینرهای تعریف‌شده در مشخصات Pod، ابتدا همهٔ کانتینرهای init به ترتیب تعریف‌شده اجرا می‌شوند.

نخستین کانتینر init با نام init-mysql، فایل‌های پیکربندی ویژهٔ MySQL را بر اساس اندیس ترتیبی تولید می‌کند.

این اسکریپت اندیس ترتیبی خود را از انتهای نام Pod استخراج می‌کند؛ نامی که دستور hostname برمی‌گرداند. سپس این عدد ترتیبی را (با یک جابه‌جایی عددی برای پرهیز از مقادیر رزروشده) در فایلی به نام server-id.cnf در پوشهٔ conf.d مربوط به MySQL ذخیره می‌کند. به این ترتیب، هویت یکتا و پایداری که StatefulSet فراهم می‌کند به حوزهٔ شناسه‌های سرور MySQL منتقل می‌شود که به همین ویژگی‌ها نیاز دارند.

اسکریپت موجود در کانتینر init-mysql همچنین یکی از فایل‌های primary.cnf یا replica.cnf را از ConfigMap، با کپی کردن محتوای آن در conf.d، اعمال می‌کند. از آنجا که توپولوژی این مثال از یک سرور اصلی MySQL و تعداد دلخواهی رونوشت تشکیل شده است، اسکریپت Pod با عدد ترتیبی 0 را سرور اصلی و بقیه را رونوشت در نظر می‌گیرد. این کار، همراه با تضمین ترتیب استقرار کنترل‌کنندهٔ StatefulSet، تضمین می‌کند که سرور اصلی MySQL پیش از ایجاد رونوشت‌ها Ready باشد تا رونوشت‌ها بتوانند تکثیر را آغاز کنند.

کلون کردن داده‌های موجود

به‌طور کلی، وقتی یک Pod جدید به‌عنوان رونوشت به مجموعه می‌پیوندد، باید فرض کند که سرور اصلی MySQL ممکن است از قبل داده داشته باشد. همچنین باید فرض کند که لاگ‌های تکثیر ممکن است تا ابتدای زمان به عقب نرسند. این فرض‌های محافظه‌کارانه کلید این هستند که یک StatefulSet در حال اجرا بتواند در طول زمان مقیاس خود را افزایش و کاهش دهد، به جای آنکه در اندازهٔ اولیه‌اش ثابت بماند.

دومین کانتینر init با نام clone-mysql، نخستین باری که یک Pod رونوشت روی یک PersistentVolume خالی راه‌اندازی می‌شود، عملیات کلون را روی آن انجام می‌دهد. یعنی همهٔ داده‌های موجود را از یک Pod در حال اجرای دیگر کپی می‌کند تا وضعیت محلی آن به اندازهٔ کافی سازگار باشد و بتواند تکثیر از سرور اصلی را آغاز کند.

خود MySQL سازوکاری برای این کار فراهم نمی‌کند؛ بنابراین این مثال از ابزار متن‌باز و پرکاربردی به نام Percona XtraBackup استفاده می‌کند. در حین کلون، ممکن است کارایی سرور MySQL مبدأ کاهش یابد. برای به حداقل رساندن تأثیر بر سرور اصلی MySQL، اسکریپت به هر Pod دستور می‌دهد از Podی کلون کند که اندیس ترتیبی آن یک واحد کمتر است. این روش کار می‌کند، زیرا کنترل‌کنندهٔ StatefulSet همیشه تضمین می‌کند که Pod شمارهٔ N پیش از راه‌اندازی Pod شمارهٔ N+1 در وضعیت Ready باشد.

آغاز تکثیر

پس از اینکه کانتینرهای init با موفقیت به پایان رسیدند، کانتینرهای عادی اجرا می‌شوند. Podهای MySQL از یک کانتینر mysql که سرور اصلی mysqld را اجرا می‌کند، و یک کانتینر xtrabackup تشکیل شده‌اند که نقش یک sidecar را دارد.

کانتینر جانبی xtrabackup فایل‌های دادهٔ کلون‌شده را بررسی می‌کند و تشخیص می‌دهد که آیا لازم است تکثیر MySQL روی رونوشت راه‌اندازی شود یا نه. اگر لازم باشد، منتظر می‌ماند تا mysqld آماده شود و سپس دستورهای CHANGE MASTER TO و START SLAVE را با پارامترهای تکثیری اجرا می‌کند که از فایل‌های کلون XtraBackup استخراج شده‌اند.

هنگامی که یک رونوشت تکثیر را آغاز می‌کند، سرور اصلی MySQL خود را به خاطر می‌سپارد و اگر سرور راه‌اندازی مجدد شود یا اتصال قطع شود، به‌طور خودکار دوباره متصل می‌شود. همچنین، از آنجا که رونوشت‌ها سرور اصلی را با نام DNS پایدار آن (mysql-0.mysql) جست‌وجو می‌کنند، حتی اگر سرور اصلی به دلیل زمان‌بندی مجدد IP جدیدی برای Pod بگیرد، رونوشت‌ها به‌طور خودکار آن را پیدا می‌کنند.

در پایان، پس از آغاز تکثیر، کانتینر xtrabackup به اتصال‌های Podهای دیگری گوش می‌دهد که درخواست کلون داده دارند. این سرور برای مدت نامحدود فعال می‌ماند تا اگر مقیاس StatefulSet افزایش یافت، یا Pod بعدی PersistentVolumeClaim خود را از دست داد و نیاز به انجام دوبارهٔ کلون داشت، پاسخ‌گو باشد.

ارسال ترافیک کلاینت

می‌توانید با اجرای یک کانتینر موقت با ایمیج mysql:5.7 و اجرای فایل اجرایی کلاینت mysql، کوئری‌های آزمایشی را به سرور اصلی MySQL (با نام میزبان mysql-0.mysql) ارسال کنید.

kubectl run mysql-client --image=mysql:5.7 -i --rm --restart=Never --\
  mysql -h mysql-0.mysql <<EOF
CREATE DATABASE test;
CREATE TABLE test.messages (message VARCHAR(250));
INSERT INTO test.messages VALUES ('hello');
EOF

برای ارسال کوئری‌های آزمایشی به هر سروری که وضعیت Ready را گزارش می‌کند، از نام میزبان mysql-read استفاده کنید:

kubectl run mysql-client --image=mysql:5.7 -i -t --rm --restart=Never --\
  mysql -h mysql-read -e "SELECT * FROM test.messages"

باید خروجی‌ای مانند این دریافت کنید:

Waiting for pod default/mysql-client to be running, status is Pending, pod ready: false
+---------+
| message |
+---------+
| hello   |
+---------+
pod "mysql-client" deleted

برای اینکه نشان دهید Service mysql-read اتصال‌ها را بین سرورها توزیع می‌کند، می‌توانید SELECT @@server_id را در یک حلقه اجرا کنید:

kubectl run mysql-client-loop --image=mysql:5.7 -i -t --rm --restart=Never --\
  bash -ic "while sleep 1; do mysql -h mysql-read -e 'SELECT @@server_id,NOW()'; done"

باید ببینید که مقدار گزارش‌شدهٔ @@server_id به‌طور تصادفی تغییر می‌کند، زیرا ممکن است در هر تلاش برای اتصال، endpoint متفاوتی انتخاب شود:

+-------------+---------------------+
| @@server_id | NOW()               |
+-------------+---------------------+
|         100 | 2006-01-02 15:04:05 |
+-------------+---------------------+
+-------------+---------------------+
| @@server_id | NOW()               |
+-------------+---------------------+
|         102 | 2006-01-02 15:04:06 |
+-------------+---------------------+
+-------------+---------------------+
| @@server_id | NOW()               |
+-------------+---------------------+
|         101 | 2006-01-02 15:04:07 |
+-------------+---------------------+

هر زمان خواستید حلقه را متوقف کنید، می‌توانید Ctrl+C را فشار دهید، اما بهتر است آن را در پنجرهٔ دیگری در حال اجرا نگه دارید تا تأثیر مراحل بعدی را ببینید.

شبیه‌سازی خرابی Pod و نود {#simulate-pod-and-node-downtime}

برای نشان دادن افزایش دسترس‌پذیری در خواندن از مجموعهٔ رونوشت‌ها به جای یک سرور واحد، حلقهٔ SELECT @@server_id بالا را در حال اجرا نگه دارید و در همین حال یک Pod را به‌اجبار از وضعیت Ready خارج کنید.

از کار انداختن Readiness probe

کاوشگر آمادگی (readiness probe) کانتینر mysql دستور mysql -h 127.0.0.1 -e 'SELECT 1' را اجرا می‌کند تا مطمئن شود سرور بالا آمده و می‌تواند کوئری‌ها را اجرا کند.

یکی از راه‌های وادار کردن این کاوشگر آمادگی به شکست، از کار انداختن همین دستور است:

kubectl exec mysql-2 -c mysql -- mv /usr/bin/mysql /usr/bin/mysql.off

این دستور به فایل‌سیستم کانتینر واقعی Pod mysql-2 دسترسی پیدا می‌کند و نام دستور mysql را تغییر می‌دهد تا کاوشگر آمادگی نتواند آن را پیدا کند. پس از چند ثانیه، Pod باید یکی از کانتینرهای خود را در وضعیت غیر Ready گزارش کند؛ این موضوع را می‌توانید با اجرای دستور زیر بررسی کنید:

kubectl get pod mysql-2

به دنبال مقدار 1/2 در ستون READY بگردید:

NAME      READY     STATUS    RESTARTS   AGE
mysql-2   1/2       Running   0          3m

در این مرحله، باید ببینید که حلقهٔ SELECT @@server_id همچنان اجرا می‌شود، هرچند دیگر هرگز مقدار 102 را گزارش نمی‌کند. به یاد داشته باشید که اسکریپت init-mysql مقدار server-id را برابر با 100 + $ordinal تعریف کرده بود؛ بنابراین شناسهٔ سرور 102 متعلق به Pod mysql-2 است.

اکنون Pod را تعمیر کنید؛ پس از چند ثانیه باید دوباره در خروجی حلقه ظاهر شود:

kubectl exec mysql-2 -c mysql -- mv /usr/bin/mysql.off /usr/bin/mysql

حذف Podها

StatefulSet نیز، مشابه کاری که ReplicaSet برای Podهای بدون حالت انجام می‌دهد، Podهای حذف‌شده را دوباره ایجاد می‌کند.

kubectl delete pod mysql-2

کنترل‌کنندهٔ StatefulSet متوجه می‌شود که دیگر Podی با نام mysql-2 وجود ندارد و Pod جدیدی با همان نام ایجاد می‌کند که به همان PersistentVolumeClaim متصل است. باید ببینید که شناسهٔ سرور 102 برای مدتی از خروجی حلقه ناپدید می‌شود و سپس خودبه‌خود بازمی‌گردد.

تخلیهٔ یک نود

اگر کلاستر کوبرنتیز شما چند نود دارد، می‌توانید با اجرای drain از کار افتادن نود را (مانند زمانی که نودها ارتقا داده می‌شوند) شبیه‌سازی کنید.

ابتدا مشخص کنید که یکی از Podهای MySQL روی کدام نود قرار دارد:

kubectl get pod mysql-2 -o wide

نام نود باید در ستون آخر نمایش داده شود:

NAME      READY     STATUS    RESTARTS   AGE       IP            NODE
mysql-2   2/2       Running   0          15m       10.244.5.27   kubernetes-node-9l2t

سپس با اجرای دستور زیر نود را تخلیه کنید. این دستور ابتدا نود را cordon می‌کند تا هیچ Pod جدیدی روی آن زمان‌بندی نشود، و سپس همهٔ Podهای موجود را بیرون می‌کند. به جای <node-name> نام نودی را قرار دهید که در مرحلهٔ قبل پیدا کردید.

احتیاط:

تخلیهٔ یک نود ممکن است بر سایر بارهای کاری و برنامه‌هایی که روی همان نود اجرا می‌شوند تأثیر بگذارد. مرحلهٔ زیر را فقط در یک کلاستر آزمایشی انجام دهید.

# See above advice about impact on other workloads
kubectl drain <node-name> --force --delete-emptydir-data --ignore-daemonsets

اکنون می‌توانید زمان‌بندی مجدد Pod روی نود دیگری را دنبال کنید:

kubectl get pod mysql-2 -o wide --watch

خروجی باید چیزی شبیه به این باشد:

NAME      READY   STATUS          RESTARTS   AGE       IP            NODE
mysql-2   2/2     Terminating     0          15m       10.244.1.56   kubernetes-node-9l2t
[...]
mysql-2   0/2     Pending         0          0s        <none>        kubernetes-node-fjlm
mysql-2   0/2     Init:0/2        0          0s        <none>        kubernetes-node-fjlm
mysql-2   0/2     Init:1/2        0          20s       10.244.5.32   kubernetes-node-fjlm
mysql-2   0/2     PodInitializing 0          21s       10.244.5.32   kubernetes-node-fjlm
mysql-2   1/2     Running         0          22s       10.244.5.32   kubernetes-node-fjlm
mysql-2   2/2     Running         0          30s       10.244.5.32   kubernetes-node-fjlm

باز هم باید ببینید که شناسهٔ سرور 102 برای مدتی از خروجی حلقهٔ SELECT @@server_id ناپدید می‌شود و سپس بازمی‌گردد.

اکنون cordon نود را بردارید تا به وضعیت عادی بازگردد:

kubectl uncordon <node-name>

تغییر مقیاس تعداد رونوشت‌ها

هنگام استفاده از تکثیر MySQL، می‌توانید با افزودن رونوشت‌ها ظرفیت پاسخ‌گویی به کوئری‌های خواندنی را افزایش دهید. در یک StatefulSet، این کار با یک دستور ساده انجام می‌شود:

kubectl scale statefulset mysql  --replicas=5

با اجرای دستور زیر، بالا آمدن Podهای جدید را دنبال کنید:

kubectl get pods -l app=mysql --watch

پس از بالا آمدن آن‌ها، باید ببینید که شناسه‌های سرور 103 و 104 در خروجی حلقهٔ SELECT @@server_id ظاهر می‌شوند.

همچنین می‌توانید بررسی کنید که این سرورهای جدید، داده‌هایی را که پیش از ایجادشان اضافه کرده بودید در اختیار دارند:

kubectl run mysql-client --image=mysql:5.7 -i -t --rm --restart=Never --\
  mysql -h mysql-3.mysql -e "SELECT * FROM test.messages"

Waiting for pod default/mysql-client to be running, status is Pending, pod ready: false
+---------+
| message |
+---------+
| hello   |
+---------+
pod "mysql-client" deleted

کاهش دوبارهٔ مقیاس نیز بدون هیچ مشکلی انجام می‌شود:

kubectl scale statefulset mysql --replicas=3
توجه:

اگرچه افزایش مقیاس به‌طور خودکار PersistentVolumeClaimهای جدیدی ایجاد می‌کند، کاهش مقیاس این PVCها را به‌طور خودکار حذف نمی‌کند.

به این ترتیب می‌توانید انتخاب کنید که این PVCهای راه‌اندازی‌شده را نگه دارید تا افزایش دوبارهٔ مقیاس سریع‌تر انجام شود، یا پیش از حذف آن‌ها داده‌هایشان را استخراج کنید.

این موضوع را می‌توانید با اجرای دستور زیر ببینید:

kubectl get pvc -l app=mysql

خروجی نشان می‌دهد که با وجود کاهش مقیاس StatefulSet به ۳، هر ۵ PVC همچنان وجود دارند:

NAME           STATUS    VOLUME                                     CAPACITY   ACCESSMODES   AGE
data-mysql-0   Bound     pvc-8acbf5dc-b103-11e6-93fa-42010a800002   10Gi       RWO           20m
data-mysql-1   Bound     pvc-8ad39820-b103-11e6-93fa-42010a800002   10Gi       RWO           20m
data-mysql-2   Bound     pvc-8ad69a6d-b103-11e6-93fa-42010a800002   10Gi       RWO           20m
data-mysql-3   Bound     pvc-50043c45-b1c5-11e6-93fa-42010a800002   10Gi       RWO           2m
data-mysql-4   Bound     pvc-500a9957-b1c5-11e6-93fa-42010a800002   10Gi       RWO           2m

اگر قصد ندارید از PVCهای اضافی دوباره استفاده کنید، می‌توانید آن‌ها را حذف کنید:

kubectl delete pvc data-mysql-3
kubectl delete pvc data-mysql-4

پاکسازی

  1. حلقهٔ SELECT @@server_id را با فشار دادن Ctrl+C در ترمینال مربوط به آن لغو کنید، یا دستور زیر را از ترمینال دیگری اجرا کنید:

    kubectl delete pod mysql-client-loop --now

  2. StatefulSet را حذف کنید. با این کار، خاتمهٔ Podها نیز آغاز می‌شود.

    kubectl delete statefulset mysql

  3. بررسی کنید که Podها ناپدید شوند. ممکن است خاتمهٔ کامل آن‌ها مدتی طول بکشد.

    kubectl get pods -l app=mysql

    زمانی متوجه می‌شوید Podها خاتمه یافته‌اند که دستور بالا این خروجی را برگرداند:

    No resources found.

  4. ConfigMap، Serviceها و PersistentVolumeClaimها را حذف کنید.

    kubectl delete configmap,service,pvc -l app=mysql

  5. اگر PersistentVolumeها را به‌صورت دستی تأمین کرده‌اید، باید آن‌ها را نیز به‌صورت دستی حذف کنید و منابع زیرساختی مربوط را آزاد کنید. اگر از یک تأمین‌کنندهٔ پویا استفاده کرده‌اید، این تأمین‌کننده با مشاهدهٔ حذف PersistentVolumeClaimها، PersistentVolumeها را به‌طور خودکار حذف می‌کند. برخی تأمین‌کننده‌های پویا (مانند تأمین‌کننده‌های EBS و PD) پس از حذف PersistentVolumeها، منابع زیرساختی را نیز آزاد می‌کنند.

گام‌های بعدی

  • درباره‌ی مقیاس‌دهی یک StatefulSet بیشتر بیاموزید.
  • درباره‌ی اشکال‌زدایی یک StatefulSet بیشتر بیاموزید.
  • درباره‌ی حذف یک StatefulSet بیشتر بیاموزید.
  • درباره‌ی حذف اجباری Podهای یک StatefulSet بیشتر بیاموزید.
  • برای یافتن نمونه‌های دیگری از برنامه‌های حالت‌مند (stateful)، به مخزن Helm Charts مراجعه کنید.
