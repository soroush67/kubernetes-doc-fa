چارچوب زمان‌بندی

وضعیت ویژگی: Kubernetes v1.19 [stable] (پایدار)

چارچوب زمان‌بندی (scheduling framework) معماری افزونه‌پذیری برای زمان‌بند کوبرنتیز است. این چارچوب از مجموعه‌ای از APIهای «افزونه» (plugin) تشکیل شده است که مستقیماً درون زمان‌بند کامپایل می‌شوند. با این APIها می‌توان بیشتر قابلیت‌های زمان‌بندی را به شکل افزونه پیاده‌سازی کرد و در عین حال «هسته» زمان‌بندی را سبک و نگهداری‌پذیر نگه داشت. برای اطلاعات فنی بیشتر درباره طراحی این چارچوب، به پیشنهاد طراحی چارچوب زمان‌بندی مراجعه کنید.

گردش کار چارچوب

چارچوب زمان‌بندی چند نقطه توسعه (extension point) تعریف می‌کند. افزونه‌های زمان‌بند ثبت می‌شوند تا در یک یا چند نقطه توسعه فراخوانی شوند. برخی از این افزونه‌ها می‌توانند تصمیم‌های زمان‌بندی را تغییر دهند و برخی دیگر صرفاً جنبه اطلاع‌رسانی دارند.

هر تلاش برای زمان‌بندی یک Pod به دو مرحله تقسیم می‌شود: چرخه زمان‌بندی (scheduling cycle) و چرخه اتصال (binding cycle).

چرخه زمان‌بندی و چرخه اتصال

چرخه زمان‌بندی یک نود را برای Pod انتخاب می‌کند و چرخه اتصال آن تصمیم را روی کلاستر اعمال می‌کند. به مجموع یک چرخه زمان‌بندی و یک چرخه اتصال «زمینه زمان‌بندی» (scheduling context) گفته می‌شود.

چرخه‌های زمان‌بندی به‌صورت پشت سر هم اجرا می‌شوند، اما چرخه‌های اتصال ممکن است به‌طور همزمان اجرا شوند.

اگر مشخص شود که Pod زمان‌بندی‌پذیر نیست یا خطای داخلی رخ دهد، چرخه زمان‌بندی یا اتصال ممکن است لغو شود. در این صورت Pod به صف بازگردانده می‌شود و دوباره تلاش می‌شود.

واسط‌ها

تصویر زیر زمینه زمان‌بندی یک Pod و واسط‌هایی (interface) را نشان می‌دهد که چارچوب زمان‌بندی در اختیار قرار می‌دهد.

هر افزونه می‌تواند چند واسط را پیاده‌سازی کند تا کارهای پیچیده‌تر یا حالت‌دار انجام دهد.

برخی از واسط‌ها با نقاط توسعه زمان‌بند مطابقت دارند که می‌توان آن‌ها را از طریق پیکربندی زمان‌بند پیکربندی کرد.

PreEnqueue {#pre-enqueue}

این افزونه‌ها پیش از افزوده‌شدن Podها به صف فعال داخلی فراخوانی می‌شوند؛ صفی که Podها در آن آماده زمان‌بندی علامت‌گذاری می‌شوند.

یک Pod تنها زمانی اجازه ورود به صف فعال را دارد که همه افزونه‌های PreEnqueue مقدار Success را برگردانند. در غیر این صورت، Pod در فهرست داخلی Podهای زمان‌بندی‌ناپذیر قرار می‌گیرد و وضعیت Unschedulable نیز برای آن ثبت نمی‌شود.

برای جزئیات بیشتر درباره نحوه کار صف‌های داخلی زمان‌بند، صف زمان‌بندی در kube-scheduler را مطالعه کنید.

EnqueueExtension

واسط EnqueueExtension به افزونه امکان می‌دهد بر اساس تغییرات کلاستر تعیین کند که آیا زمان‌بندی Podهایی که این افزونه رد کرده است دوباره امتحان شود یا خیر. افزونه‌هایی که PreEnqueue، PreFilter، Filter، Reserve یا Permit را پیاده‌سازی می‌کنند باید این واسط را نیز پیاده‌سازی کنند.

QueueingHint

وضعیت ویژگی: Kubernetes [] ()

تابع QueueingHint یک تابع بازفراخوانی (callback) است که تعیین می‌کند آیا یک Pod می‌تواند دوباره به صف فعال یا صف عقب‌نشینی (backoff queue) بازگردد یا خیر. این تابع هر بار که نوع خاصی از رویداد یا تغییر در کلاستر رخ می‌دهد اجرا می‌شود. هنگامی که QueueingHint تشخیص دهد که آن رویداد ممکن است Pod را زمان‌بندی‌پذیر کند، Pod در صف فعال یا صف عقب‌نشینی قرار می‌گیرد تا زمان‌بند دوباره زمان‌بندی آن را امتحان کند.

QueueSort {#queue-sort}

این افزونه‌ها برای مرتب‌سازی Podها در صف زمان‌بندی استفاده می‌شوند. هر افزونه مرتب‌سازی صف اساساً یک تابع Less(Pod1, Pod2) فراهم می‌کند. در هر زمان تنها یک افزونه مرتب‌سازی صف می‌تواند فعال باشد.

PreFilter {#pre-filter}

این افزونه‌ها برای پیش‌پردازش اطلاعات Pod یا بررسی شرایط معینی که کلاستر یا Pod باید برآورده کنند استفاده می‌شوند. اگر یک افزونه PreFilter خطا برگرداند، چرخه زمان‌بندی لغو می‌شود.

Filter

این افزونه‌ها برای کنار گذاشتن نودهایی استفاده می‌شوند که نمی‌توانند Pod را اجرا کنند. زمان‌بند برای هر نود، افزونه‌های فیلتر را به ترتیبی که پیکربندی شده‌اند فراخوانی می‌کند. اگر هر یک از افزونه‌های فیلتر نود را نامناسب علامت‌گذاری کند، افزونه‌های باقی‌مانده برای آن نود فراخوانی نمی‌شوند. ارزیابی نودها ممکن است به‌طور همزمان انجام شود.

PostFilter {#post-filter}

این افزونه‌ها پس از مرحله Filter فراخوانی می‌شوند، اما فقط زمانی که هیچ نود مناسبی برای Pod پیدا نشده باشد. افزونه‌ها به ترتیبی که پیکربندی شده‌اند فراخوانی می‌شوند. اگر هر یک از افزونه‌های PostFilter نود را Schedulable علامت‌گذاری کند، افزونه‌های باقی‌مانده فراخوانی نمی‌شوند. یک پیاده‌سازی رایج PostFilter، پس‌گیری (preemption) است که می‌کوشد با بیرون راندن Podهای دیگر، Pod را زمان‌بندی‌پذیر کند.

PreScore {#pre-score}

این افزونه‌ها برای انجام کارهای «پیش از امتیازدهی» استفاده می‌شوند که وضعیتی اشتراک‌پذیر برای استفاده افزونه‌های Score تولید می‌کند. اگر یک افزونه PreScore خطا برگرداند، چرخه زمان‌بندی لغو می‌شود.

Score {#scoring}

این افزونه‌ها برای رتبه‌بندی نودهایی استفاده می‌شوند که از مرحله فیلتر عبور کرده‌اند. زمان‌بند هر افزونه امتیازدهی را برای هر نود فراخوانی می‌کند. بازه مشخصی از اعداد صحیح، کمترین و بیشترین امتیاز را تعیین می‌کند. پس از مرحله NormalizeScore، زمان‌بند امتیازهای نودها را از همه افزونه‌ها بر اساس وزن‌های پیکربندی‌شده افزونه‌ها با هم ترکیب می‌کند.

امتیازدهی بر اساس ظرفیت {#scoring-capacity}

وضعیت ویژگی: Kubernetes [] ()

در نسخه v1.32 از feature gate با نام VolumeCapacityPriority برای پشتیبانی از ذخیره‌سازی‌هایی استفاده می‌شد که به‌صورت ایستا تأمین شده بودند. از نسخه v1.33، feature gate جدید StorageCapacityScoring جایگزین VolumeCapacityPriority قدیمی شده و پشتیبانی از ذخیره‌سازی تأمین‌شده به‌صورت پویا را نیز اضافه کرده است. هنگامی که StorageCapacityScoring فعال باشد، افزونه VolumeBinding در kube-scheduler گسترش می‌یابد تا نودها را بر اساس ظرفیت ذخیره‌سازی هر یک از آن‌ها امتیازدهی کند. این قابلیت برای حجم‌های (volume) CSI که از ظرفیت ذخیره‌سازی پشتیبانی می‌کنند، از جمله ذخیره‌سازی محلی مبتنی بر درایور CSI، قابل استفاده است.

NormalizeScore {#normalize-scoring}

این افزونه‌ها برای تغییر امتیازها پیش از آنکه زمان‌بند رتبه‌بندی نهایی نودها را محاسبه کند استفاده می‌شوند. افزونه‌ای که برای این نقطه توسعه ثبت می‌شود، با نتایج Score همان افزونه فراخوانی می‌شود. این فراخوانی در هر چرخه زمان‌بندی، برای هر افزونه یک بار انجام می‌شود.

برای مثال، فرض کنید افزونه‌ای به نام BlinkingLightScorer نودها را بر اساس تعداد چراغ‌های چشمک‌زنشان رتبه‌بندی می‌کند.

func ScoreNode(_ *v1.pod, n *v1.Node) (int, error) {
    return getBlinkingLightCount(n)
}

با این حال، بیشترین تعداد چراغ‌های چشمک‌زن ممکن است در مقایسه با NodeScoreMax کوچک باشد. برای رفع این مشکل، BlinkingLightScorer باید برای این نقطه توسعه نیز ثبت شود.

func NormalizeScores(scores map[string]int) {
    highest := 0
    for _, score := range scores {
        highest = max(highest, score)
    }
    for node, score := range scores {
        scores[node] = score*NodeScoreMax/highest
    }
}

اگر هر یک از افزونه‌های NormalizeScore خطا برگرداند، چرخه زمان‌بندی لغو می‌شود.

توجه:

افزونه‌هایی که می‌خواهند کارهای «پیش از رزرو» انجام دهند، باید از نقطه توسعه NormalizeScore استفاده کنند.

Reserve {#reserve}

افزونه‌ای که واسط Reserve را پیاده‌سازی می‌کند دو متد به نام‌های Reserve و Unreserve دارد که به ترتیب پشتیبان دو مرحله اطلاع‌رسانی زمان‌بندی به نام‌های Reserve و Unreserve هستند. افزونه‌هایی که وضعیت زمان اجرا را نگهداری می‌کنند (یا همان «افزونه‌های حالت‌دار») باید از این مراحل استفاده کنند تا هنگام رزرو شدن و آزاد شدن منابع یک نود برای یک Pod مشخص، از زمان‌بند اطلاع دریافت کنند.

مرحله Reserve پیش از آنکه زمان‌بند واقعاً یک Pod را به نود تعیین‌شده‌اش متصل کند رخ می‌دهد. هدف این مرحله جلوگیری از شرایط رقابتی (race condition) در مدتی است که زمان‌بند منتظر موفقیت اتصال است. متد Reserve هر افزونه Reserve ممکن است موفق یا ناموفق باشد؛ اگر یکی از فراخوانی‌های متد Reserve ناموفق باشد، افزونه‌های بعدی اجرا نمی‌شوند و مرحله Reserve ناموفق در نظر گرفته می‌شود. اگر متد Reserve همه افزونه‌ها موفق باشد، مرحله Reserve موفق در نظر گرفته می‌شود و بقیه چرخه زمان‌بندی و چرخه اتصال اجرا می‌شوند.

اگر مرحله Reserve یا مرحله‌ای پس از آن ناموفق باشد، مرحله Unreserve آغاز می‌شود. در این حالت، متد Unreserve همه افزونه‌های Reserve به ترتیب معکوس فراخوانی‌های متد Reserve اجرا می‌شود. هدف این مرحله پاک‌سازی وضعیت مرتبط با Pod رزروشده است.

احتیاط:

پیاده‌سازی متد Unreserve در افزونه‌های Reserve باید خودتوان (idempotent) باشد و نباید با شکست مواجه شود.

Permit

افزونه‌های Permit در پایان چرخه زمان‌بندی هر Pod فراخوانی می‌شوند تا از اتصال به نود نامزد جلوگیری کنند یا آن را به تأخیر بیندازند. هر افزونه Permit می‌تواند یکی از سه کار زیر را انجام دهد:

  1. تأیید (approve)
    هنگامی که همه افزونه‌های Permit یک Pod را تأیید کنند، Pod برای اتصال فرستاده می‌شود.

  2. رد (deny)
    اگر هر یک از افزونه‌های Permit یک Pod را رد کند، Pod به صف زمان‌بندی بازگردانده می‌شود. این کار مرحله Unreserve را در افزونه‌های Reserve آغاز می‌کند.

  3. انتظار (wait، همراه با مهلت زمانی)
    اگر یک افزونه Permit مقدار «wait» را برگرداند، Pod در فهرست داخلی Podهای «در انتظار» نگه داشته می‌شود و چرخه اتصال این Pod آغاز می‌شود، اما بلافاصله تا زمان تأیید شدن مسدود می‌ماند. اگر مهلت زمانی به پایان برسد، انتظار به رد تبدیل می‌شود و Pod به صف زمان‌بندی بازگردانده می‌شود و مرحله Unreserve در افزونه‌های Reserve آغاز می‌شود.

توجه:

با اینکه هر افزونه‌ای می‌تواند به فهرست Podهای «در انتظار» دسترسی داشته باشد و آن‌ها را تأیید کند (به FrameworkHandle مراجعه کنید)، انتظار می‌رود تنها افزونه‌های Permit اتصال Podهای رزروشده‌ای را که در وضعیت «در انتظار» هستند تأیید کنند. پس از تأیید یک Pod، آن Pod به مرحله PreBind فرستاده می‌شود.

PreBind {#pre-bind}

این افزونه‌ها برای انجام هر کاری استفاده می‌شوند که پیش از اتصال یک Pod لازم است. برای مثال، یک افزونه PreBind ممکن است پیش از آنکه اجازه دهد Pod روی نود مقصد اجرا شود، یک حجم شبکه‌ای تأمین کند و آن را روی آن نود سوار (mount) کند.

اگر هر یک از افزونه‌های PreBind خطا برگرداند، Pod رد می‌شود و به صف زمان‌بندی بازمی‌گردد.

Bind

این افزونه‌ها برای اتصال یک Pod به یک نود استفاده می‌شوند. افزونه‌های Bind تا زمانی که همه افزونه‌های PreBind کارشان را تمام نکرده باشند فراخوانی نمی‌شوند. هر افزونه Bind به ترتیب پیکربندی‌شده فراخوانی می‌شود. هر افزونه Bind می‌تواند انتخاب کند که Pod داده‌شده را مدیریت کند یا خیر. اگر یک افزونه Bind مدیریت یک Pod را بپذیرد، از افزونه‌های Bind باقی‌مانده صرف‌نظر می‌شود.

PostBind {#post-bind}

این یک واسط اطلاع‌رسانی است. افزونه‌های PostBind پس از اتصال موفق یک Pod فراخوانی می‌شوند. این مرحله پایان چرخه اتصال است و می‌توان از آن برای پاک‌سازی منابع مرتبط استفاده کرد.

API افزونه

استفاده از API افزونه دو گام دارد. نخست، افزونه‌ها باید ثبت و پیکربندی شوند و سپس از واسط‌های نقاط توسعه استفاده می‌کنند. واسط‌های نقاط توسعه به شکل زیر هستند.

type Plugin interface {
    Name() string
}

type QueueSortPlugin interface {
    Plugin
    Less(*v1.pod, *v1.pod) bool
}

type PreFilterPlugin interface {
    Plugin
    PreFilter(context.Context, *framework.CycleState, *v1.pod) error
}

پیکربندی افزونه

می‌توانید افزونه‌ها را در پیکربندی زمان‌بند فعال یا غیرفعال کنید. اگر از کوبرنتیز نسخه v1.18 یا بالاتر استفاده می‌کنید، بیشتر افزونه‌های زمان‌بندی به‌طور پیش‌فرض در حال استفاده و فعال هستند.

علاوه بر افزونه‌های پیش‌فرض، می‌توانید افزونه‌های زمان‌بندی خودتان را نیز پیاده‌سازی کنید و آن‌ها را در کنار افزونه‌های پیش‌فرض پیکربندی کنید. برای جزئیات بیشتر می‌توانید به scheduler-plugins مراجعه کنید.

اگر از کوبرنتیز نسخه v1.18 یا بالاتر استفاده می‌کنید، می‌توانید مجموعه‌ای از افزونه‌ها را به‌عنوان یک پروفایل زمان‌بند پیکربندی کنید و سپس چندین پروفایل تعریف کنید تا با انواع مختلف بار کاری سازگار باشند. برای اطلاعات بیشتر، پروفایل‌های چندگانه را ببینید.
