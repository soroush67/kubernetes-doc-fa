مدیریت منابع برای Podها و کانتینرها

هنگامی که یک pod را تعریف می‌کنید، می‌توانید به‌صورت اختیاری مشخص کنید که هر کانتینر به چه مقدار از هر منبع نیاز دارد. رایج‌ترین منابعی که مشخص می‌شوند CPU و حافظه (RAM) هستند؛ منابع دیگری نیز وجود دارند.

هنگامی که درخواست (request) منبع را برای کانتینرهای یک Pod مشخص می‌کنید، kube-scheduler از این اطلاعات برای تصمیم‌گیری دربارهٔ اینکه Pod روی کدام نود قرار گیرد استفاده می‌کند. هنگامی که حد (limit) منبع را برای یک کانتینر مشخص می‌کنید، kubelet آن حدها را اعمال می‌کند تا کانتینر در حال اجرا اجازه نداشته باشد بیش از حدی که تعیین کرده‌اید از آن منبع استفاده کند. kubelet همچنین دست‌کم به اندازهٔ درخواست از آن منبع سیستمی را به‌طور خاص برای استفادهٔ آن کانتینر رزرو می‌کند.

درخواست‌ها و حدها

اگر نودی که Pod روی آن اجرا می‌شود به مقدار کافی از یک منبع در دسترس داشته باشد، ممکن (و مجاز) است که یک کانتینر بیش از مقداری که request آن برای آن منبع مشخص می‌کند از آن منبع استفاده کند.

برای نمونه، اگر درخواست memory به میزان 256 MiB را برای یک کانتینر تنظیم کنید و آن کانتینر در Podی باشد که روی یک Node با 8GiB حافظه و بدون هیچ Pod دیگری زمان‌بندی شده است، آن‌گاه کانتینر می‌تواند تلاش کند از RAM بیشتری استفاده کند.

حدها داستان دیگری دارند. هر دو حد cpu و memory توسط kubelet (و زمان اجرای کانتینر) اعمال می‌شوند و در نهایت توسط کرنل به اجرا درمی‌آیند. روی نودهای لینوکسی، کرنل لینوکس حدها را با cgroupها اعمال می‌کند. رفتار اعمال حدهای cpu و memory اندکی متفاوت است.

حدهای cpu با محدودسازی (throttling) CPU اعمال می‌شوند. هنگامی که یک کانتینر به حد cpu خود نزدیک می‌شود، کرنل دسترسی به CPU را متناسب با حد کانتینر محدود می‌کند. بنابراین، حد cpu یک حد سخت است که کرنل اعمال می‌کند. کانتینرها نمی‌توانند بیش از مقدار مشخص‌شده در حد cpu خود از CPU استفاده کنند.

حدهای memory توسط کرنل با کشتن‌های ناشی از کمبود حافظه (OOM kill) اعمال می‌شوند. هنگامی که یک کانتینر بیش از حد memory خود استفاده کند، کرنل ممکن است آن را خاتمه دهد. با این حال، خاتمه‌دادن‌ها تنها زمانی رخ می‌دهند که کرنل فشار حافظه را تشخیص دهد. بنابراین، کانتینری که بیش از حد حافظه تخصیص دهد ممکن است بی‌درنگ کشته نشود. این بدان معناست که حدهای memory به‌صورت واکنشی اعمال می‌شوند. یک کانتینر ممکن است بیش از حد memory خود از حافظه استفاده کند، اما اگر چنین کند، ممکن است کشته شود.

توجه:

قابلیتی به نام MemoryQoS وجود دارد که محدودسازی حافظه و رزرو اختیاری لایه‌بندی‌شدهٔ حافظه را روی نودهای لینوکسی با استفاده از cgroup v2 اضافه می‌کند. برای جزئیات، Memory QoS با cgroup v2 را ببینید.

توجه:

اگر برای یک منبع حدی تعیین کنید اما هیچ درخواستی مشخص نکنید، و هیچ سازوکاری در زمان پذیرش (admission) درخواست پیش‌فرضی برای آن منبع اعمال نکرده باشد، کوبرنتیز حدی را که مشخص کرده‌اید کپی می‌کند و آن را به‌عنوان مقدار درخواستی برای آن منبع به کار می‌برد.

انواع منابع

یک نوع منبع دارای یک واحد پایه است و می‌تواند درخواست شود، محدود شود یا هر دو. کوبرنتیز انواع منابع داخلی زیر را دارد:

نوع منبع توضیح واحد پایه
cpu پردازش محاسباتی cpu (هسته)
memory RAM بایت
ephemeral-storage ذخیره‌سازی موقت محلی بایت
hugepages-<size> صفحه‌های بزرگ (Huge pages) (فقط لینوکس) بایت

کلاسترها همچنین می‌توانند منابع توسعه‌یافته (extended resources) (منابعی با نام سفارشی که معمولاً توسط device pluginها ارائه می‌شوند) فراهم کنند.

صفحه‌های بزرگ (Huge pages)

برای بارهای کاری لینوکسی، می‌توانید منابع صفحهٔ بزرگ را مشخص کنید. صفحه‌های بزرگ قابلیتی خاص لینوکس هستند که در آن کرنل نود بلوک‌هایی از حافظه را تخصیص می‌دهد که بسیار بزرگ‌تر از اندازهٔ پیش‌فرض صفحه‌اند.

برای نمونه، روی سیستمی که اندازهٔ پیش‌فرض صفحه 4KiB است، می‌توانید حد hugepages-2Mi: 80Mi را مشخص کنید. اگر کانتینر تلاش کند بیش از ۴۰ صفحهٔ بزرگ 2MiB (در مجموع 80 MiB) تخصیص دهد، آن تخصیص با شکست مواجه می‌شود.

توجه:

نمی‌توانید منابع hugepages-* را بیش از ظرفیت متعهد (overcommit) کنید. این با منابع memory و cpu متفاوت است.

CPU و حافظه در مجموع منابع محاسباتی یا منابع نامیده می‌شوند. منابع محاسباتی کمیت‌های قابل اندازه‌گیری‌ای هستند که می‌توانند درخواست، تخصیص و مصرف شوند. این منابع از منابع API متمایزند. منابع API، مانند Podها و Serviceها، آبجکت‌هایی هستند که می‌توان آن‌ها را از طریق سرور API کوبرنتیز خواند و تغییر داد.

درخواست‌ها و حدهای منابع Pod و کانتینر

برای هر کانتینر، می‌توانید حدها و درخواست‌های منابع را مشخص کنید، از جمله موارد زیر:

  • spec.containers[].resources.limits.cpu
  • spec.containers[].resources.limits.memory
  • spec.containers[].resources.limits.ephemeral-storage
  • spec.containers[].resources.limits.hugepages-<size>
  • spec.containers[].resources.requests.cpu
  • spec.containers[].resources.requests.memory
  • spec.containers[].resources.requests.ephemeral-storage
  • spec.containers[].resources.requests.hugepages-<size>

اگرچه تنها می‌توانید درخواست‌ها و حدها را برای کانتینرهای منفرد مشخص کنید، اندیشیدن به درخواست‌ها و حدهای کلی منابع برای یک Pod نیز سودمند است. برای یک منبع مشخص، درخواست/حد منبع Pod برابر با مجموع درخواست‌ها/حدهای منبع از آن نوع برای همهٔ کانتینرهای Pod است.

مشخص کردن منابع در سطح Pod

وضعیت ویژگی: Kubernetes [] ()

به شرط آنکه feature gate با نام PodLevelResources در کلاستر شما فعال باشد، می‌توانید درخواست‌ها و حدهای منابع را در سطح Pod مشخص کنید. در سطح Pod، کوبرنتیز 1.37 تنها از درخواست‌ها یا حدهای منابع برای انواع مشخصی از منابع پشتیبانی می‌کند: cpu و/ یا memory و/یا hugepages. با این قابلیت، کوبرنتیز به شما امکان می‌دهد بودجهٔ کلی منابع را برای Pod اعلام کنید، که به‌ویژه هنگام کار با تعداد زیادی کانتینر که سنجش دقیق نیازهای منابع تک‌تک آن‌ها دشوار است، سودمند است. افزون بر این، این قابلیت به کانتینرهای درون یک Pod امکان می‌دهد منابع بیکار را با یکدیگر به اشتراک بگذارند و در نتیجه بهره‌وری منابع بهبود یابد.

برای یک Pod، می‌توانید حدها و درخواست‌های منابع را برای CPU و حافظه با افزودن موارد زیر مشخص کنید:

  • spec.resources.limits.cpu
  • spec.resources.limits.memory
  • spec.resources.limits.hugepages-<size>
  • spec.resources.requests.cpu
  • spec.resources.requests.memory
  • spec.resources.requests.hugepages-<size>

واحدهای منابع در کوبرنتیز

واحدهای منبع CPU {#meaning-of-cpu}

حدها و درخواست‌های منابع CPU با واحد cpu اندازه‌گیری می‌شوند. در کوبرنتیز، ۱ واحد CPU معادل ۱ هستهٔ فیزیکی CPU یا ۱ هستهٔ مجازی است، بسته به اینکه نود یک میزبان فیزیکی باشد یا یک ماشین مجازی که درون یک ماشین فیزیکی اجرا می‌شود.

درخواست‌های کسری مجازند. هنگامی که کانتینری را با spec.containers[].resources.requests.cpu برابر با 0.5 تعریف می‌کنید، در مقایسه با حالتی که 1.0 CPU درخواست کنید، نصف زمان CPU را درخواست می‌کنید. برای واحدهای منبع CPU، عبارت کمیت (quantity) 0.1 معادل عبارت 100m است که می‌توان آن را «صد میلی‌cpu» خواند. برخی افراد می‌گویند «صد میلی‌هسته» و این نیز به همان معنا درک می‌شود.

منبع CPU همیشه به‌صورت مقدار مطلق منبع مشخص می‌شود، نه هرگز به‌صورت مقدار نسبی. برای نمونه، 500m CPU تقریباً همان مقدار توان محاسباتی را نشان می‌دهد، چه آن کانتینر روی ماشینی تک‌هسته‌ای، دوهسته‌ای یا ۴۸ هسته‌ای اجرا شود.

توجه:

کوبرنتیز اجازه نمی‌دهد منابع CPU را با دقتی ریزتر از 1m یا 0.001 CPU مشخص کنید. برای اجتناب از استفادهٔ تصادفی از یک کمیت CPU نامعتبر، سودمند است که هنگام استفاده از کمتر از ۱ واحد CPU، واحدهای CPU را به‌جای شکل اعشاری با شکل milliCPU مشخص کنید.

برای نمونه، Podی دارید که از 5m یا 0.005 CPU استفاده می‌کند و می‌خواهید منابع CPU آن را کاهش دهید. با استفاده از شکل اعشاری، تشخیص اینکه 0.0005 CPU مقداری نامعتبر است دشوارتر است، در حالی که با استفاده از شکل milliCPU، تشخیص اینکه 0.5m مقداری نامعتبر است آسان‌تر است.

واحدهای منبع حافظه {#meaning-of-memory}

حدها و درخواست‌های memory بر حسب بایت اندازه‌گیری می‌شوند. می‌توانید حافظه را به‌صورت یک عدد صحیح ساده یا یک عدد ممیز ثابت با استفاده از یکی از این پسوندهای کمیت بیان کنید: E، P، T، G، M، k. همچنین می‌توانید از معادل‌های توانی از دو استفاده کنید: Ei، Pi، Ti، Gi، Mi، Ki. API کوبرنتیز همچنین m را به‌عنوان پسوند می‌پذیرد (برای میلی‌بایت: ۱/۱۰۰۰ بایت)، اما مشخص کردن آن سودمند نیست: همیشه باید تعداد صحیحی بایت، یا گاهی بخش‌های بزرگ‌تر مانند مضارب ۱ گیبی‌بایت، تخصیص دهید.

در اینجا چند نمونه از کمیت‌های حافظه آمده است که تقریباً مقدار یکسانی را نشان می‌دهند:

128974848, 129e6, 129M,  128974848000m, 123Mi

به بزرگی و کوچکی حروف پسوندها توجه کنید. "M" به معنای مگابایت است، در حالی که "m" به معنای میلی‌بایت است. اگر 400m حافظه درخواست کنید، این درخواستی برای 0.4 بایت است. کسی که این را تایپ می‌کند احتمالاً قصد داشته 400 مبی‌بایت (400Mi) یا 400 مگابایت (400M) درخواست کند.

نمونهٔ منابع کانتینر {#example-1}

Pod زیر دو کانتینر دارد. هر دو کانتینر با درخواستی برای 0.25 CPU و 64MiB (226 بایت) حافظه تعریف شده‌اند. هر کانتینر حدی برابر با 0.5 CPU و 128MiB حافظه دارد. می‌توان گفت Pod درخواستی برابر با 0.5 CPU و 128 MiB حافظه، و حدی برابر با 1 CPU و 256MiB حافظه دارد.

---
apiVersion: v1
kind: Pod
metadata:
  name: frontend
spec:
  containers:
  - name: app
    image: images.my-company.example/app:v4
    resources:
      requests:
        memory: "64Mi"
        cpu: "250m"
      limits:
        memory: "128Mi"
        cpu: "500m"
  - name: log-aggregator
    image: images.my-company.example/log-aggregator:v6
    resources:
      requests:
        memory: "64Mi"
        cpu: "250m"
      limits:
        memory: "128Mi"
        cpu: "500m"

نمونهٔ منابع Pod {#example-2}

وضعیت ویژگی: Kubernetes [] ()

این قابلیت را می‌توان با تنظیم feature gate با نام PodLevelResources فعال کرد. Pod زیر درخواست صریحی برابر با 1 CPU و 100 MiB حافظه، و حد صریحی برابر با 1 CPU و 200 MiB حافظه دارد. کانتینر pod-resources-demo-ctr-1 درخواست‌ها و حدهای صریحی دارد. با این حال، کانتینر pod-resources-demo-ctr-2 صرفاً منابع در دسترس را در محدودهٔ منابع Pod به اشتراک می‌گذارد، زیرا درخواست‌ها و حدهای صریحی برای آن تنظیم نشده است.

pods/resource/pod-level-resources.yaml
apiVersion: v1
kind: Pod
metadata:
  name: pod-resources-demo
  namespace: pod-resources-example
spec:
  resources:
    limits:
      cpu: "1"
      memory: "200Mi"
    requests:
      cpu: "1"
      memory: "100Mi"
  containers:
  - name: pod-resources-demo-ctr-1
    image: nginx
    resources:
      limits:
        cpu: "0.5"
        memory: "100Mi"
      requests:
        cpu: "0.5"
        memory: "50Mi"
  - name: pod-resources-demo-ctr-2
    image: fedora
    command:
    - sleep
    - inf

Podهای دارای درخواست منابع چگونه زمان‌بندی می‌شوند

هنگامی که یک Pod ایجاد می‌کنید، زمان‌بند کوبرنتیز نودی را برای اجرای Pod انتخاب می‌کند. هر نود برای هر یک از انواع منابع ظرفیت بیشینه‌ای دارد: مقدار CPU و حافظه‌ای که می‌تواند برای Podها فراهم کند. زمان‌بند اطمینان حاصل می‌کند که برای هر نوع منبع، مجموع درخواست‌های منابع کانتینرهای زمان‌بندی‌شده کمتر از ظرفیت نود باشد. توجه داشته باشید که حتی اگر مصرف واقعی حافظه یا CPU روی نودها بسیار پایین باشد، اگر بررسی ظرفیت ناموفق باشد، زمان‌بند همچنان از قرار دادن Pod روی آن نود خودداری می‌کند. این کار از کمبود منابع روی یک نود در زمانی که مصرف منابع بعداً افزایش یابد، برای نمونه در اوج روزانهٔ نرخ درخواست‌ها، جلوگیری می‌کند.

کوبرنتیز درخواست‌ها و حدهای منابع را چگونه اعمال می‌کند {#how-pods-with-resource-limits-are-run}

هنگامی که kubelet یک کانتینر را به‌عنوان بخشی از یک Pod آغاز می‌کند، درخواست‌ها و حدهای حافظه و CPU آن کانتینر را به زمان اجرای کانتینر ارسال می‌کند.

در لینوکس، زمان اجرای کانتینر معمولاً cgroupهای کرنل را پیکربندی می‌کند که حدهایی را که تعریف کرده‌اید اعمال و اجرا می‌کنند.

  • حد CPU سقف سختی را برای مقدار زمان CPU که کانتینر می‌تواند استفاده کند تعریف می‌کند. در هر بازهٔ زمان‌بندی (برش زمانی)، کرنل لینوکس بررسی می‌کند که آیا از این حد فراتر رفته است یا نه؛ اگر چنین باشد، کرنل پیش از اجازه دادن به ادامهٔ اجرای آن cgroup صبر می‌کند.
  • درخواست CPU معمولاً یک وزن‌دهی را تعریف می‌کند. اگر چندین کانتینر (cgroup) مختلف بخواهند روی سیستمی که بر سر منابع آن رقابت وجود دارد اجرا شوند، به بارهای کاری با درخواست‌های CPU بزرگ‌تر زمان CPU بیشتری نسبت به بارهای کاری با درخواست‌های کوچک تخصیص داده می‌شود.
  • درخواست حافظه عمدتاً در زمان زمان‌بندی Pod (کوبرنتیز) استفاده می‌شود. روی نودی که از cgroups v2 استفاده می‌کند، زمان اجرای کانتینر ممکن است از درخواست حافظه به‌عنوان راهنمایی برای تنظیم memory.min و memory.low استفاده کند.
  • حد حافظه یک حد حافظه برای آن cgroup تعریف می‌کند. اگر کانتینر تلاش کند بیش از این حد حافظه تخصیص دهد، زیرسیستم کمبود حافظهٔ (out-of-memory) کرنل لینوکس فعال می‌شود و معمولاً با متوقف کردن یکی از فرایندهای درون کانتینر که تلاش کرده حافظه تخصیص دهد مداخله می‌کند. اگر آن فرایند PID 1 کانتینر باشد و کانتینر به‌عنوان قابل راه‌اندازی مجدد علامت‌گذاری شده باشد، کوبرنتیز کانتینر را دوباره راه‌اندازی می‌کند.
  • حد حافظهٔ Pod یا کانتینر می‌تواند به صفحه‌های موجود در حجم‌های مبتنی بر حافظه، مانند یک emptyDir، نیز اعمال شود. kubelet حجم‌های emptyDir از نوع tmpfs را به‌عنوان مصرف حافظهٔ کانتینر ردگیری می‌کند، نه به‌عنوان ذخیره‌سازی موقت محلی. هنگام استفاده از emptyDir مبتنی بر حافظه، حتماً نکات زیر را بررسی کنید.

اگر یک کانتینر از درخواست حافظهٔ خود فراتر رود و نودی که روی آن اجرا می‌شود در مجموع با کمبود حافظه مواجه شود، احتمالاً Podی که کانتینر به آن تعلق دارد بیرون رانده خواهد شد.

ممکن است به یک کانتینر اجازه داده شود یا داده نشود که برای مدت طولانی از حد CPU خود فراتر رود. با این حال، زمان‌های اجرای کانتینر، Podها یا کانتینرها را به دلیل مصرف بیش از حد CPU خاتمه نمی‌دهند.

برای تعیین اینکه آیا یک کانتینر به دلیل حدهای منابع قابل زمان‌بندی نیست یا در حال کشته شدن است، بخش عیب‌یابی را ببینید.

تغییر اندازهٔ منابع کانتینر

پس از ایجاد یک Pod، ممکن است لازم باشد منابع CPU یا حافظهٔ آن را بر اساس الگوهای مصرف واقعی تنظیم کنید. کوبرنتیز دو رویکرد برای تغییر اندازهٔ منابع Pod فراهم می‌کند:

می‌توانید requests و limits مربوط به CPU و حافظهٔ کانتینرها را در یک Pod در حال اجرا بدون ایجاد مجدد آن تغییر دهید. این کار مقیاس‌پذیری عمودی درجای Pod یا تغییر اندازهٔ درجای Pod نامیده می‌شود. برای انجام تغییر اندازهٔ درجا، مشخصات منابع کانتینر را با استفاده از زیرمنبع /resize در Pod به‌روزرسانی کنید. می‌توانید با تنظیم فیلد resizePolicy در مشخصات کانتینر کنترل کنید که آیا راه‌اندازی مجدد کانتینر لازم است یا نه.

تغییر اندازه با راه‌اندازی Podهای جایگزین

رویکرد بومی ابر برای تغییر منابع یک Pod، به‌روزرسانی قالب Pod در آبجکت بار کاری (مانند یک Deployment یا StatefulSet) و سپردن کار به کنترل‌کنندهٔ بار کاری است تا Podها را با Podهای جدیدی که منابع به‌روزشده دارند جایگزین کند. این رویکرد با هر نسخه‌ای از کوبرنتیز کار می‌کند و می‌تواند هر مشخصه‌ای از Pod را تغییر دهد.

برای جزئیات بیشتر دربارهٔ تغییر اندازهٔ Pod، تغییر اندازهٔ Podها را ببینید. برای دستورالعمل‌های تفصیلی دربارهٔ تغییر اندازهٔ درجا، تغییر اندازهٔ منابع CPU و حافظهٔ تخصیص‌یافته به کانتینرها را ببینید. همچنین می‌توانید از Vertical Pod Autoscaler برای مدیریت خودکار توصیه‌های منابع Pod استفاده کنید.

پایش مصرف منابع محاسباتی و حافظه

kubelet مصرف منابع یک Pod را به‌عنوان بخشی از status آن Pod گزارش می‌کند.

اگر ابزارهای پایش اختیاری در کلاستر شما در دسترس باشند، مصرف منابع Pod را می‌توان یا مستقیماً از Metrics API یا از ابزارهای پایش خود بازیابی کرد.

ملاحظات مربوط به حجم‌های emptyDir مبتنی بر حافظه {#memory-backed-emptydir}

توجه:
وضعیت ویژگی: Kubernetes [] ()

هنگامی که feature gate با نام InPlacePodVerticalScalingMemoryBackedVolumes فعال باشد، می‌توانید sizeLimit یک حجم emptyDir مبتنی بر حافظه (medium: Memory) را روی یک Pod در حال اجرا به‌صورت پویا تنظیم کنید، بدون آنکه نیازی به ایجاد مجدد Pod یا راه‌اندازی مجدد کانتینرها باشد. برای دستورالعمل‌های گام‌به‌گام، تغییر اندازهٔ منابع CPU و حافظهٔ تخصیص‌یافته به کانتینرها را ببینید.

احتیاط:

اگر برای یک حجم emptyDir مقدار sizeLimit را مشخص نکنید، آن حجم ممکن است تا سقف حد حافظهٔ آن Pod (Pod.spec.containers[].resources.limits.memory) مصرف کند. اگر حد حافظه تعیین نکنید، Pod هیچ سقفی برای مصرف حافظه ندارد و می‌تواند تمام حافظهٔ در دسترس روی نود را مصرف کند. کوبرنتیز Podها را بر اساس درخواست‌های منابع (Pod.spec.containers[].resources.requests) زمان‌بندی می‌کند و هنگام تصمیم‌گیری دربارهٔ اینکه آیا Pod دیگری روی یک نود مشخص جا می‌شود، مصرف حافظهٔ بیش از درخواست را در نظر نمی‌گیرد. این امر می‌تواند به منع سرویس (denial of service) منجر شود و سیستم‌عامل را وادار به رسیدگی به کمبود حافظه (OOM) کند. می‌توان هر تعداد emptyDir ایجاد کرد که به‌طور بالقوه تمام حافظهٔ در دسترس روی نود را مصرف کنند و احتمال OOM را افزایش دهند.

از منظر مدیریت حافظه، شباهت‌هایی میان حالتی که یک فرایند از حافظه به‌عنوان فضای کاری استفاده می‌کند و حالت استفاده از emptyDir مبتنی بر حافظه وجود دارد. اما هنگام استفاده از حافظه به‌عنوان حجم، مانند emptyDir مبتنی بر حافظه، نکات اضافی زیر وجود دارد که باید مراقب آن‌ها باشید:

  • فایل‌های ذخیره‌شده روی یک حجم مبتنی بر حافظه تقریباً به‌طور کامل توسط برنامهٔ کاربر مدیریت می‌شوند. برخلاف زمانی که حافظه به‌عنوان فضای کاری یک فرایند استفاده می‌شود، نمی‌توانید به مواردی مانند زباله‌روبی در سطح زبان برنامه‌نویسی تکیه کنید.
  • هدف از نوشتن فایل‌ها روی یک حجم، ذخیرهٔ داده‌ها یا انتقال آن‌ها میان برنامه‌هاست. نه کوبرنتیز و نه سیستم‌عامل فایل‌ها را به‌طور خودکار از یک حجم حذف نمی‌کنند، بنابراین حافظهٔ مصرف‌شده توسط آن فایل‌ها هنگامی که سیستم یا Pod تحت فشار حافظه است قابل بازپس‌گیری نیست.
  • emptyDir مبتنی بر حافظه به دلیل کارایی‌اش سودمند است، اما حافظه معمولاً از نظر اندازه بسیار کوچک‌تر و از نظر هزینه بسیار گران‌تر از سایر رسانه‌های ذخیره‌سازی، مانند دیسک‌ها یا SSDها، است. استفاده از مقادیر زیاد حافظه برای حجم‌های emptyDir ممکن است بر عملکرد عادی Pod شما یا کل نود تأثیر بگذارد، بنابراین باید با احتیاط از آن استفاده شود.

اگر مدیر یک کلاستر یا فضای نام هستید، می‌توانید ResourceQuotaای نیز تنظیم کنید که مصرف حافظه را محدود کند؛ همچنین ممکن است بخواهید برای اعمال محدودیت بیشتر یک LimitRange تعریف کنید. اگر برای هر Pod مقدار spec.containers[].resources.limits.memory را مشخص کنید، بیشینهٔ اندازهٔ یک حجم emptyDir برابر با حد حافظهٔ Pod خواهد بود.

به‌عنوان جایگزین، مدیر کلاستر می‌تواند با استفاده از سازوکار سیاستی مانند ValidatingAdmissionPolicy حدهای اندازه را برای حجم‌های emptyDir در Podهای جدید اعمال کند.

ذخیره‌سازی موقت محلی

برای مفاهیم کلی دربارهٔ ذخیره‌سازی موقت محلی و نکاتی دربارهٔ پیکربندی درخواست‌ها و/یا حدهای ذخیره‌سازی موقت برای یک کانتینر، لطفاً صفحهٔ ذخیره‌سازی موقت محلی را بررسی کنید.

پایش منابع برای ذخیره‌سازی موقت محلی

kubelet می‌تواند اندازه بگیرد که چه مقدار از ذخیره‌سازی موقت محلی در حال استفاده است. این کار را تا زمانی انجام می‌دهد که جداسازی ظرفیت ذخیره‌سازی موقت محلی را فعال کرده باشید.

کوبرنتیز مقدار ذخیره‌سازی موقتی را که یک Pod استفاده می‌کند از موارد زیر ردگیری می‌کند:

  • نوشتن در لایهٔ قابل نوشتن کانتینر (rootfs)، ایمیج‌های کانتینر یا هر دو.
  • نوشتن در حجم‌های emptyDir محلی.
  • لاگ‌های خود Pod (که معمولاً زیر /var/log/pods ذخیره می‌شوند).
  • فایل‌های سیستمی مدیریت‌شده توسط کوبرنتیز که در Pod نگاشت می‌شوند، مانند /etc/hosts.

منابع توسعه‌یافته (Extended resources)

منابع توسعه‌یافته نام‌های کاملاً واجد شرایط (fully-qualified) منابعی هستند که بیرون از دامنهٔ kubernetes.io قرار دارند. این منابع به گردانندگان کلاستر امکان می‌دهند منابعی را که جزو منابع داخلی کوبرنتیز نیستند اعلام کنند و به کاربران امکان می‌دهند آن‌ها را مصرف کنند.

برای استفاده از منابع توسعه‌یافته دو گام لازم است. نخست، گردانندهٔ کلاستر باید یک منبع توسعه‌یافته را اعلام کند. دوم، کاربران باید منبع توسعه‌یافته را در Podها درخواست کنند.

مدیریت منابع توسعه‌یافته

منابع توسعه‌یافته در سطح نود

منابع توسعه‌یافته در سطح نود به نودها وابسته‌اند.

منابع مدیریت‌شده توسط device plugin

برای چگونگی اعلام منابع مدیریت‌شده توسط device plugin روی هر نود، Device Plugin را ببینید.

سایر منابع

برای اعلام یک منبع توسعه‌یافتهٔ جدید در سطح نود، گردانندهٔ کلاستر می‌تواند یک درخواست HTTP از نوع PATCH به سرور API ارسال کند تا مقدار در دسترس را در status.capacity برای یکی از نودهای کلاستر مشخص کند. پس از این عملیات، status.capacity نود شامل منبع جدیدی خواهد بود. فیلد status.allocatable به‌طور خودکار و ناهمگام توسط kubelet با منبع جدید به‌روزرسانی می‌شود.

از آنجا که زمان‌بند هنگام ارزیابی تناسب Pod از مقدار status.allocatable نود استفاده می‌کند، زمان‌بند تنها پس از آن به‌روزرسانی ناهمگام، مقدار جدید را در نظر می‌گیرد. ممکن است میان patch کردن ظرفیت نود با یک منبع جدید و زمانی که نخستین Pod درخواست‌کنندهٔ آن منبع بتواند روی آن نود زمان‌بندی شود، تأخیر کوتاهی وجود داشته باشد.

مثال:

در اینجا نمونه‌ای آمده است که نشان می‌دهد چگونه با استفاده از curl یک درخواست HTTP بسازید که پنج منبع "example.com/foo" را روی نود k8s-node-1 که master آن k8s-master است اعلام کند.

curl --header "Content-Type: application/json-patch+json" \
--request PATCH \
--data '[{"op": "add", "path": "/status/capacity/example.com~1foo", "value": "5"}]' \
http://k8s-master:8080/api/v1/nodes/k8s-node-1/status
توجه:

در درخواست پیشین، ~1 کدگذاری نویسهٔ / در مسیر patch است. مقدار مسیر عملیات در JSON-Patch به‌عنوان یک JSON-Pointer تفسیر می‌شود. برای جزئیات بیشتر، IETF RFC 6901، بخش 3 را ببینید.

منابع توسعه‌یافته در سطح کلاستر

منابع توسعه‌یافته در سطح کلاستر به نودها وابسته نیستند. این منابع معمولاً توسط گسترش‌دهنده‌های زمان‌بند (scheduler extenders) مدیریت می‌شوند که مصرف منابع و سهمیهٔ منابع را مدیریت می‌کنند.

می‌توانید منابع توسعه‌یافته‌ای را که توسط گسترش‌دهنده‌های زمان‌بند مدیریت می‌شوند در پیکربندی زمان‌بند مشخص کنید.

مثال:

پیکربندی زیر برای یک سیاست زمان‌بند نشان می‌دهد که منبع توسعه‌یافتهٔ سطح کلاستر "example.com/foo" توسط گسترش‌دهندهٔ زمان‌بند مدیریت می‌شود.

  • زمان‌بند تنها در صورتی یک Pod را به گسترش‌دهندهٔ زمان‌بند ارسال می‌کند که Pod منبع "example.com/foo" را درخواست کرده باشد.
  • فیلد ignoredByScheduler مشخص می‌کند که زمان‌بند منبع "example.com/foo" را در گزارهٔ (predicate) PodFitsResources خود بررسی نکند.
{
  "kind": "Policy",
  "apiVersion": "v1",
  "extenders": [
    {
      "urlPrefix":"<extender-endpoint>",
      "bindVerb": "bind",
      "managedResources": [
        {
          "name": "example.com/foo",
          "ignoredByScheduler": true
        }
      ]
    }
  ]
}

تخصیص منابع توسعه‌یافته توسط DRA

تخصیص منابع توسعه‌یافته توسط DRA به مدیران کلاستر امکان می‌دهد یک extendedResourceName را در DeviceClass مشخص کنند؛ سپس دستگاه‌هایی که با DeviceClass مطابقت دارند را می‌توان از طریق درخواست‌های منابع توسعه‌یافتهٔ یک Pod درخواست کرد. دربارهٔ تخصیص منابع توسعه‌یافته توسط DRA بیشتر بخوانید.

مصرف منابع توسعه‌یافته

کاربران می‌توانند منابع توسعه‌یافته را مانند CPU و حافظه در مشخصات Pod مصرف کنند. زمان‌بند حسابداری منابع را بر عهده می‌گیرد تا بیش از مقدار در دسترس به‌طور هم‌زمان به Podها تخصیص داده نشود.

سرور API کمیت‌های منابع توسعه‌یافته را به اعداد صحیح محدود می‌کند. نمونه‌هایی از کمیت‌های معتبر عبارت‌اند از 3، 3000m و 3Ki. نمونه‌هایی از کمیت‌های نامعتبر عبارت‌اند از 0.5 و 1500m (زیرا 1500m به 1.5 منجر می‌شود).

توجه:

منابع توسعه‌یافته جایگزین Opaque Integer Resources شده‌اند. کاربران می‌توانند از هر پیشوند نام دامنه‌ای به‌جز kubernetes.io که رزرو شده است استفاده کنند.

برای مصرف یک منبع توسعه‌یافته در یک Pod، نام منبع را به‌عنوان یک کلید در نگاشت spec.containers[].resources.limits در مشخصات کانتینر قرار دهید.

توجه:

منابع توسعه‌یافته را نمی‌توان بیش از ظرفیت متعهد کرد، بنابراین اگر درخواست و حد هر دو در مشخصات کانتینر وجود داشته باشند، باید برابر باشند.

یک Pod تنها در صورتی زمان‌بندی می‌شود که همهٔ درخواست‌های منابع آن، از جمله CPU، حافظه و هر منبع توسعه‌یافته، برآورده شوند. تا زمانی که درخواست منبع قابل برآورده‌شدن نباشد، Pod در وضعیت PENDING باقی می‌ماند.

مثال:

Pod زیر ۲ CPU و ۱ "example.com/foo" (یک منبع توسعه‌یافته) درخواست می‌کند.

apiVersion: v1
kind: Pod
metadata:
  name: my-pod
spec:
  containers:
  - name: my-container
    image: myimage
    resources:
      requests:
        cpu: 2
        example.com/foo: 1
      limits:
        example.com/foo: 1

محدودسازی PID

حدهای شناسهٔ فرایند (PID) امکان پیکربندی kubelet را فراهم می‌کنند تا تعداد PIDهایی که یک Pod مشخص می‌تواند مصرف کند محدود شود. برای اطلاعات بیشتر محدودسازی PID را ببینید.

عیب‌یابی

Podهای من با پیام رویداد FailedScheduling در وضعیت pending هستند

اگر زمان‌بند نتواند نودی بیابد که Pod روی آن جا شود، Pod تا زمانی که جایی پیدا شود زمان‌بندی‌نشده باقی می‌ماند. هر بار که زمان‌بند نتواند جایی برای Pod بیابد، یک Event تولید می‌شود. می‌توانید از kubectl برای مشاهدهٔ رویدادهای یک Pod استفاده کنید؛ برای نمونه:

kubectl describe pod frontend | grep -A 9999999999 Events

Events:
  Type     Reason            Age   From               Message
  ----     ------            ----  ----               -------
  Warning  FailedScheduling  23s   default-scheduler  0/42 nodes available: insufficient cpu

در مثال پیشین، زمان‌بندی Pod با نام "frontend" به دلیل کمبود منبع CPU روی همهٔ نودها ناموفق است. پیام‌های خطای مشابه ممکن است نشان‌دهندهٔ شکست به دلیل کمبود حافظه (PodExceedsFreeMemory) نیز باشند. به‌طور کلی، اگر یک Pod با پیامی از این نوع در وضعیت pending باشد، چند کار را می‌توان امتحان کرد:

  • نودهای بیشتری به کلاستر اضافه کنید.
  • Podهای غیرضروری را خاتمه دهید تا برای Podهای در انتظار جا باز شود.
  • بررسی کنید که Pod از همهٔ نودها بزرگ‌تر نباشد. برای نمونه، اگر ظرفیت همهٔ نودها cpu: 1 باشد، Podی با درخواست cpu: 1.1 هرگز زمان‌بندی نخواهد شد.
  • taintهای نود را بررسی کنید. اگر بیشتر نودهای شما taint شده باشند و Pod جدید آن taint را تحمل نکند، زمان‌بند تنها جای‌گذاری روی نودهای باقی‌مانده‌ای را در نظر می‌گیرد که آن taint را ندارند.

در خروجی پیشین می‌بینید که اگر یک Pod بیش از 1.120 CPU یا بیش از 6.23Gi حافظه درخواست کند، آن Pod روی این نود جا نخواهد شد.

با نگاه به بخش “Pods” می‌توانید ببینید کدام Podها روی نود فضا اشغال کرده‌اند.

مقدار منابع در دسترس برای Podها کمتر از ظرفیت نود است، زیرا daemonهای سیستم بخشی از منابع در دسترس را استفاده می‌کنند. در API کوبرنتیز، هر Node یک فیلد .status.allocatable دارد (برای جزئیات NodeStatus را ببینید).

فیلد .status.allocatable مقدار منابعی را که برای Podها روی آن نود در دسترس است توصیف می‌کند (برای نمونه: ۱۵ CPU مجازی و 7538 MiB حافظه). برای اطلاعات بیشتر دربارهٔ منابع قابل تخصیص نود در کوبرنتیز، رزرو منابع محاسباتی برای daemonهای سیستم را ببینید.

می‌توانید سهمیه‌های منابع را پیکربندی کنید تا کل مقدار منابعی را که یک فضای نام می‌تواند مصرف کند محدود کنید. کوبرنتیز هنگامی که یک ResourceQuota در یک فضای نام مشخص وجود داشته باشد، سهمیه‌ها را برای آبجکت‌های آن فضای نام اعمال می‌کند. برای نمونه، اگر فضاهای نام مشخصی را به تیم‌های مختلف اختصاص دهید، می‌توانید ResourceQuotaهایی را در آن فضاهای نام اضافه کنید. تنظیم سهمیه‌های منابع کمک می‌کند از اینکه یک تیم آن‌قدر از یک منبع استفاده کند که این مصرف بیش از حد بر تیم‌های دیگر تأثیر بگذارد جلوگیری شود.

همچنین باید در نظر بگیرید که چه دسترسی‌ای به آن فضای نام اعطا می‌کنید: دسترسی نوشتن کامل به یک فضای نام به کسی که آن دسترسی را دارد اجازه می‌دهد هر منبعی، از جمله یک ResourceQuota پیکربندی‌شده، را حذف کند.

گام بعدی شما ممکن است بررسی کد برنامه برای یافتن نشت حافظه باشد. اگر دریافتید که برنامه همان‌طور که انتظار دارید رفتار می‌کند، تنظیم حد حافظهٔ بالاتر (و احتمالاً درخواست بالاتر) را برای آن کانتینر در نظر بگیرید.

گام‌های بعدی

  • تجربهٔ عملی تخصیص منابع حافظه به کانتینرها و Podها را کسب کنید.
  • تجربهٔ عملی تخصیص منابع CPU به کانتینرها و Podها را کسب کنید.
  • بخوانید که مرجع API چگونه یک کانتینر و نیازمندی‌های منابع آن را تعریف می‌کند
  • دربارهٔ ذخیره‌سازی موقت محلی بیشتر بخوانید
  • دربارهٔ مرجع پیکربندی kube-scheduler (v1) بیشتر بخوانید
  • دربارهٔ کلاس‌های کیفیت سرویس (QoS) برای Podها بیشتر بخوانید
  • دربارهٔ تخصیص منابع توسعه‌یافته توسط DRA بیشتر بخوانید
