Downward API

دو روش برای در دسترس قرار دادن فیلدهای Pod و کانتینر برای یک کانتینر در حال اجرا وجود دارد: متغیرهای محیطی، و فایل‌هایی که یک نوع خاص از حجم (volume) آن‌ها را پر می‌کند. این دو روش برای در دسترس قرار دادن فیلدهای Pod و کانتینر، روی هم downward API نامیده می‌شوند.

گاهی مفید است که یک کانتینر بدون وابستگی بیش از حد به کوبرنتیز، اطلاعاتی درباره‌ی خودش داشته باشد. به کمک downward API، کانتینرها می‌توانند بدون استفاده از کلاینت کوبرنتیز یا API server، اطلاعاتی درباره‌ی خود یا کلاستر به دست آورند.

برای نمونه، برنامه‌ای موجود را در نظر بگیرید که فرض می‌کند یک متغیر محیطی شناخته‌شده‌ی مشخص، شناسه‌ای یکتا را در خود نگه می‌دارد. یک راه این است که برنامه را درون پوششی (wrapper) قرار دهید، اما این کار خسته‌کننده و مستعد خطاست و با هدف کاهش وابستگی نیز در تضاد است. راه بهتر این است که از نام Pod به‌عنوان شناسه استفاده کنید و نام Pod را در همان متغیر محیطی شناخته‌شده تزریق کنید.

در کوبرنتیز، دو روش برای در دسترس قرار دادن فیلدهای Pod و کانتینر برای یک کانتینر در حال اجرا وجود دارد:

  • به‌صورت متغیرهای محیطی
  • به‌صورت فایل‌هایی در یک حجم downwardAPI

این دو روش برای در دسترس قرار دادن فیلدهای Pod و کانتینر، روی هم downward API نامیده می‌شوند.

فیلدهای در دسترس

تنها برخی از فیلدهای API کوبرنتیز از طریق downward API در دسترس هستند. این بخش فهرست فیلدهایی را که می‌توانید در دسترس قرار دهید ارائه می‌کند.

می‌توانید اطلاعات فیلدهای در دسترس در سطح Pod را با استفاده از fieldRef منتقل کنید. در سطح API، بخش spec هر Pod همواره دست‌کم یک Container را تعریف می‌کند. اطلاعات فیلدهای در دسترس در سطح Container را نیز می‌توانید با استفاده از resourceFieldRef منتقل کنید.

اطلاعات در دسترس از طریق fieldRef {#downwardapi-fieldRef}

برخی از فیلدهای سطح Pod را می‌توانید یا به‌صورت متغیر محیطی یا با استفاده از یک حجم downwardAPI در اختیار کانتینر قرار دهید. فیلدهایی که از طریق هر دو سازوکار در دسترس هستند عبارت‌اند از:

metadata.name
نام پاد
metadata.namespace
فضای نام پاد
metadata.uid
شناسه‌ی یکتای پاد
metadata.annotations['<KEY>']
مقدار حاشیه‌نویسی پاد با نام <KEY> (برای مثال، metadata.annotations['myannotation'])
metadata.labels['<KEY>']
مقدار متنی برچسب پاد با نام <KEY> (برای مثال، metadata.labels['mylabel'])

اطلاعات زیر از طریق متغیرهای محیطی در دسترس هستند، اما نه به‌صورت fieldRef در حجم downwardAPI:

spec.serviceAccountName
نام حساب سرویس پاد
spec.nodeName
نام نودی که پاد روی آن اجرا می‌شود
status.hostIP
نشانی IP اصلی نودی که پاد به آن اختصاص داده شده است
status.hostIPs
نشانی‌های IP که نسخه‌ی دوپشته‌ای (dual-stack) از status.hostIP هستند؛ نخستین نشانی همواره با status.hostIP یکسان است.
status.podIP
نشانی IP اصلی پاد (معمولاً نشانی IPv4 آن)
status.podIPs
نشانی‌های IP که نسخه‌ی دوپشته‌ای از status.podIP هستند؛ نخستین نشانی همواره با status.podIP یکسان است

اطلاعات زیر از طریق fieldRef در یک حجم downwardAPI در دسترس هستند، اما نه به‌صورت متغیرهای محیطی:

metadata.labels
همه‌ی برچسب‌های پاد، با قالب label-key="escaped-label-value" و هر برچسب در یک خط
metadata.annotations
همه‌ی حاشیه‌نویسی‌های پاد، با قالب annotation-key="escaped-annotation-value" و هر حاشیه‌نویسی در یک خط

اطلاعات در دسترس از طریق resourceFieldRef {#downwardapi-resourceFieldRef}

با این فیلدهای سطح کانتینر می‌توانید اطلاعاتی درباره‌ی درخواست‌ها و محدودیت‌ها برای منابعی مانند CPU و حافظه فراهم کنید.

توجه:
وضعیت ویژگی: Kubernetes [] ()

منابع CPU و حافظه‌ی کانتینر را می‌توان در حین اجرای کانتینر تغییر اندازه داد. در این صورت، حجم downward API به‌روزرسانی می‌شود، اما متغیرهای محیطی تا زمانی که کانتینر دوباره راه‌اندازی نشود به‌روزرسانی نمی‌شوند. برای جزئیات بیشتر، تغییر اندازه‌ی منابع CPU و حافظه‌ی اختصاص‌یافته به کانتینرها را ببینید.

resource: limits.cpu
محدودیت CPU کانتینر
resource: requests.cpu
درخواست CPU کانتینر
resource: limits.memory
محدودیت حافظه‌ی کانتینر
resource: requests.memory
درخواست حافظه‌ی کانتینر
resource: limits.hugepages-*
محدودیت hugepages کانتینر
resource: requests.hugepages-*
درخواست hugepages کانتینر
resource: limits.ephemeral-storage
محدودیت ذخیره‌سازی موقت (ephemeral-storage) کانتینر
resource: requests.ephemeral-storage
درخواست ذخیره‌سازی موقت کانتینر

اطلاعات جایگزین برای محدودیت‌های منابع

اگر محدودیت‌های CPU و حافظه برای یک کانتینر مشخص نشده باشند و شما بکوشید این اطلاعات را با downward API در دسترس قرار دهید، kubelet به‌طور پیش‌فرض بیشینه‌ی مقدار قابل تخصیص CPU و حافظه را بر پایه‌ی محاسبه‌ی منابع قابل تخصیص نود در دسترس قرار می‌دهد.

گام‌های بعدی

می‌توانید درباره‌ی حجم‌های downwardAPI مطالعه کنید.

می‌توانید استفاده از downward API را برای در دسترس قرار دادن اطلاعات سطح کانتینر یا Pod امتحان کنید:

  • به‌صورت متغیرهای محیطی
  • به‌صورت فایل‌هایی در حجم downwardAPI
