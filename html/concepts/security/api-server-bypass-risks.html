خطرات دور زدن API Server کوبرنتیز

اطلاعات معماری امنیتی مرتبط با API server و سایر مؤلفه‌ها

API server کوبرنتیز نقطهٔ ورود اصلی به یک کلاستر برای طرف‌های خارجی (کاربران و سرویس‌ها) است که با آن تعامل دارند.

API server به‌عنوان بخشی از این نقش، چندین کنترل امنیتی کلیدی داخلی دارد، مانند ثبت لاگ ممیزی و کنترل‌کننده‌های پذیرش. با این حال، روش‌هایی برای تغییر پیکربندی یا محتوای کلاستر وجود دارد که این کنترل‌ها را دور می‌زنند.

این صفحه روش‌هایی را توصیف می‌کند که از طریق آن‌ها می‌توان کنترل‌های امنیتی داخلی API server کوبرنتیز را دور زد، تا اپراتورهای کلاستر و معماران امنیت بتوانند اطمینان حاصل کنند که این راه‌های دور زدن به‌طور مناسب محدود شده‌اند.

پادهای ایستا (Static Pods) {#static-pods}

kubelet روی هر نود، هر مانیفستی را که در یک دایرکتوری مشخص ذخیره شده یا از یک URL مشخص دریافت شده باشد، به‌عنوان پادهای ایستا در کلاستر شما بارگذاری کرده و مستقیماً مدیریت می‌کند. API server این پادهای ایستا را مدیریت نمی‌کند. مهاجمی که دسترسی نوشتن به این مکان داشته باشد، می‌تواند پیکربندی پادهای ایستای بارگذاری‌شده از آن منبع را تغییر دهد، یا پادهای ایستای جدیدی وارد کند.

دسترسی پادهای ایستا به سایر آبجکت‌ها در API کوبرنتیز محدود است. برای مثال، نمی‌توانید یک Pod ایستا را طوری پیکربندی کنید که یک Secret را از کلاستر mount کند. با این حال، این پادها می‌توانند اقدامات حساس امنیتی دیگری انجام دهند، مانند استفاده از mountهای hostPath از نود زیربنایی.

به‌طور پیش‌فرض، kubelet یک پاد آینه‌ای (mirror pod) ایجاد می‌کند تا پادهای ایستا در API کوبرنتیز قابل مشاهده باشند. با این حال، اگر مهاجم هنگام ایجاد Pod از نام فضای نام نامعتبری استفاده کند، Pod در API کوبرنتیز قابل مشاهده نخواهد بود و تنها توسط ابزارهایی که به میزبان(های) متأثر دسترسی دارند قابل کشف است.

اگر یک Pod ایستا در کنترل پذیرش رد شود، kubelet آن Pod را در API server ثبت نمی‌کند. با این حال، Pod همچنان روی نود اجرا می‌شود. برای اطلاعات بیشتر، به kubeadm issue #1541 مراجعه کنید.

راهکارهای کاهش خطر {#static-pods-mitigations}

  • قابلیت مانیفست Pod ایستای kubelet را فعال کنید فقط در صورتی که نود به آن نیاز داشته باشد.
  • اگر نودی از قابلیت Pod ایستا استفاده می‌کند، دسترسی فایل‌سیستمی به دایرکتوری یا URL مانیفست‌های Pod ایستا را به کاربرانی که به این دسترسی نیاز دارند محدود کنید.
  • دسترسی به پارامترها و فایل‌های پیکربندی kubelet را محدود کنید تا از تنظیم مسیر یا URL مربوط به Pod ایستا توسط مهاجم جلوگیری شود.
  • همهٔ دسترسی‌ها به دایرکتوری‌ها یا مکان‌های ذخیره‌سازی وبی که میزبان مانیفست‌های Pod ایستا و فایل‌های پیکربندی kubelet هستند را به‌طور منظم ممیزی کرده و به‌صورت متمرکز گزارش کنید.

API مربوط به kubelet {#kubelet-api}

kubelet یک API از نوع HTTP فراهم می‌کند که معمولاً روی پورت TCP 10250 در نودهای کارگر کلاستر در معرض دسترسی قرار می‌گیرد. بسته به توزیع کوبرنتیز مورد استفاده، این API ممکن است روی نودهای control plane نیز در معرض دسترسی باشد. دسترسی مستقیم به این API امکان افشای اطلاعات دربارهٔ پادهای در حال اجرا روی یک نود، لاگ‌های آن پادها، و اجرای دستورات در هر کانتینر در حال اجرا روی نود را فراهم می‌کند.

برخی از این endpointها از پروتکل‌های Websocket از طریق درخواست‌های HTTP GET پشتیبانی می‌کنند که با فعل get مجوزدهی می‌شوند. این به آن معناست که مجوز get روی nodes/proxy یک مجوز فقط‌خواندنی نیست، و دسترسی به endpointهایی را مجاز می‌کند که می‌توان از آن‌ها برای اجرای دستورات در هر کانتینر در حال اجرا روی نود استفاده کرد.

هنگامی که کاربران کلاستر کوبرنتیز دسترسی RBAC به زیرمنابع آبجکت Node دارند، این دسترسی به‌عنوان مجوزی برای تعامل با API مربوط به kubelet عمل می‌کند. دسترسی دقیق بستگی به این دارد که دسترسی به کدام زیرمنبع اعطا شده است، همان‌طور که در مجوزدهی kubelet به تفصیل آمده است.

دسترسی مستقیم به API مربوط به kubelet مشمول کنترل پذیرش نیست و توسط ثبت لاگ ممیزی کوبرنتیز ثبت نمی‌شود. مهاجمی که دسترسی مستقیم به این API داشته باشد ممکن است بتواند کنترل‌هایی را که اقدامات خاصی را تشخیص می‌دهند یا از آن‌ها جلوگیری می‌کنند دور بزند.

API مربوط به kubelet را می‌توان طوری پیکربندی کرد که درخواست‌ها را به روش‌های گوناگونی احراز هویت کند. به‌طور پیش‌فرض، پیکربندی kubelet اجازهٔ دسترسی ناشناس را می‌دهد. بیشتر ارائه‌دهندگان کوبرنتیز این پیش‌فرض را تغییر می‌دهند تا از احراز هویت webhook و گواهی‌نامه استفاده شود. این کار به control plane امکان می‌دهد اطمینان حاصل کند که فراخواننده مجوز دسترسی به منبع API nodes یا زیرمنابع آن را دارد. دسترسی ناشناس پیش‌فرض این بررسی را با control plane انجام نمی‌دهد.

راهکارهای کاهش خطر

  • دسترسی به زیرمنابع آبجکت API nodes را با استفاده از سازوکارهایی مانند RBAC محدود کنید. این دسترسی را فقط در صورت نیاز اعطا کنید، مانند نیاز سرویس‌های پایش.
  • از اعطای مجوز همه‌جانبهٔ nodes/proxy، حتی فقط با فعل get، خودداری کنید. به‌جای آن، مجوزهای جزئی اعطا کنید.
  • دسترسی به پورت kubelet را محدود کنید. فقط به محدوده‌های نشانی IP مشخص و مورد اعتماد اجازهٔ دسترسی به این پورت را بدهید.
  • اطمینان حاصل کنید که احراز هویت kubelet. روی حالت webhook یا گواهی‌نامه تنظیم شده است.
  • اطمینان حاصل کنید که پورت «فقط‌خواندنی» و بدون احراز هویت Kubelet در کلاستر فعال نیست.

API مربوط به etcd

کلاسترهای کوبرنتیز از etcd به‌عنوان مخزن داده استفاده می‌کنند. سرویس etcd روی پورت TCP 2379 گوش می‌دهد. تنها کلاینت‌هایی که به دسترسی نیاز دارند، API server کوبرنتیز و هر ابزار پشتیبان‌گیری‌ای است که استفاده می‌کنید. دسترسی مستقیم به این API امکان افشا یا تغییر هر داده‌ای را که در کلاستر نگهداری می‌شود فراهم می‌کند.

دسترسی به API مربوط به etcd معمولاً از طریق احراز هویت با گواهی‌نامهٔ کلاینت مدیریت می‌شود. هر گواهی‌نامه‌ای که توسط یک مرجع صدور گواهی‌نامهٔ مورد اعتماد etcd صادر شده باشد، دسترسی کامل به داده‌های ذخیره‌شده در etcd را فراهم می‌کند.

دسترسی مستقیم به etcd مشمول کنترل پذیرش کوبرنتیز نیست و توسط ثبت لاگ ممیزی کوبرنتیز ثبت نمی‌شود. مهاجمی که به کلید خصوصی گواهی‌نامهٔ کلاینت etcd مربوط به API server دسترسی خواندن داشته باشد (یا بتواند یک گواهی‌نامهٔ کلاینت مورد اعتماد جدید ایجاد کند)، می‌تواند با دسترسی به secretهای کلاستر یا تغییر قواعد دسترسی، حقوق مدیر کلاستر را به دست آورد. حتی بدون ارتقای امتیازات RBAC کوبرنتیز، مهاجمی که بتواند etcd را تغییر دهد می‌تواند هر آبجکت API را بازیابی کند یا بارهای کاری جدیدی درون کلاستر ایجاد کند.

بسیاری از ارائه‌دهندگان کوبرنتیز etcd را طوری پیکربندی می‌کنند که از TLS متقابل (mutual TLS) استفاده کند (هم کلاینت و هم سرور گواهی‌نامهٔ یکدیگر را برای احراز هویت بررسی می‌کنند). هیچ پیاده‌سازی مجوزدهی پذیرفته‌شده و گسترده‌ای برای API مربوط به etcd وجود ندارد، هرچند این قابلیت وجود دارد. از آنجا که هیچ مدل مجوزدهی‌ای وجود ندارد، هر گواهی‌نامه‌ای که دسترسی کلاینت به etcd داشته باشد می‌تواند برای کسب دسترسی کامل به etcd استفاده شود. معمولاً گواهی‌نامه‌های کلاینت etcd که فقط برای بررسی سلامت استفاده می‌شوند نیز می‌توانند دسترسی کامل خواندن و نوشتن اعطا کنند.

راهکارهای کاهش خطر {#etcd-api-mitigations}

  • اطمینان حاصل کنید که مرجع صدور گواهی‌نامهٔ مورد اعتماد etcd فقط برای اهداف احراز هویت در آن سرویس استفاده می‌شود.
  • دسترسی به کلید خصوصی گواهی‌نامهٔ سرور etcd، و به گواهی‌نامه و کلید کلاینت API server را کنترل کنید.
  • محدود کردن دسترسی به پورت etcd در سطح شبکه را در نظر بگیرید تا فقط دسترسی از محدوده‌های نشانی IP مشخص و مورد اعتماد مجاز باشد.

سوکت محیط اجرای کانتینر {#runtime-socket}

روی هر نود در یک کلاستر کوبرنتیز، دسترسی برای تعامل با کانتینرها توسط محیط اجرای کانتینر (container runtime) کنترل می‌شود (یا محیط‌های اجرا، اگر بیش از یکی پیکربندی کرده باشید). معمولاً محیط اجرای کانتینر یک سوکت Unix در معرض دسترسی قرار می‌دهد که kubelet می‌تواند به آن دسترسی داشته باشد. مهاجمی که به این سوکت دسترسی داشته باشد می‌تواند کانتینرهای جدیدی راه‌اندازی کند یا با کانتینرهای در حال اجرا تعامل داشته باشد.

در سطح کلاستر، تأثیر این دسترسی به این بستگی دارد که آیا کانتینرهایی که روی نود آسیب‌دیده اجرا می‌شوند به Secretها یا سایر داده‌های محرمانه‌ای دسترسی دارند که مهاجم بتواند از آن‌ها برای ارتقای امتیازات به سایر نودهای کارگر یا به مؤلفه‌های control plane استفاده کند.

راهکارهای کاهش خطر {#runtime-socket-mitigations}

  • اطمینان حاصل کنید که دسترسی فایل‌سیستمی به سوکت‌های محیط اجرای کانتینر را به‌دقت کنترل می‌کنید. در صورت امکان، این دسترسی را به کاربر root محدود کنید.
  • kubelet را با استفاده از سازوکارهایی مانند فضاهای نام هستهٔ لینوکس، از سایر مؤلفه‌های در حال اجرا روی نود ایزوله کنید.
  • اطمینان حاصل کنید که استفاده از mountهای hostPath را که شامل سوکت محیط اجرای کانتینر هستند، چه به‌طور مستقیم و چه با mount کردن یک دایرکتوری والد، محدود یا ممنوع می‌کنید. همچنین mountهای hostPath باید به‌صورت فقط‌خواندنی تنظیم شوند تا خطرات دور زدن محدودیت‌های دایرکتوری توسط مهاجمان کاهش یابد.
  • دسترسی کاربران به نودها را محدود کنید، و به‌ویژه دسترسی ابرکاربر به نودها را محدود کنید.
