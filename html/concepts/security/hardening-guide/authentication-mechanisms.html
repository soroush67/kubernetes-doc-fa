راهنمای سخت‌سازی - سازوکارهای احراز هویت

اطلاعاتی دربارهٔ گزینه‌های احراز هویت در کوبرنتیز و ویژگی‌های امنیتی آن‌ها.

انتخاب سازوکار(های) احراز هویت مناسب جنبه‌ای حیاتی از ایمن‌سازی کلاستر شماست. کوبرنتیز چندین سازوکار داخلی فراهم می‌کند که هر یک نقاط قوت و ضعف خود را دارد و هنگام انتخاب بهترین سازوکار احراز هویت برای کلاستر باید به‌دقت در نظر گرفته شوند.

به‌طور کلی، توصیه می‌شود تا حد امکان سازوکارهای احراز هویت کمتری فعال کنید تا مدیریت کاربران ساده‌تر شود و از مواردی جلوگیری شود که کاربران دسترسی‌ای به کلاستر را حفظ می‌کنند که دیگر به آن نیازی ندارند.

توجه به این نکته اهمیت دارد که کوبرنتیز پایگاه دادهٔ کاربری داخلی درون کلاستر ندارد. در عوض، اطلاعات کاربران را از سیستم احراز هویت پیکربندی‌شده دریافت می‌کند و از آن برای اتخاذ تصمیم‌های مجوزدهی استفاده می‌کند. بنابراین، برای ممیزی دسترسی کاربران، باید اعتبارنامه‌ها را از هر منبع احراز هویت پیکربندی‌شده بازبینی کنید.

برای کلاسترهای تولیدی که چندین کاربر به‌طور مستقیم به API کوبرنتیز دسترسی دارند، توصیه می‌شود از منابع احراز هویت خارجی مانند OIDC استفاده شود. سازوکارهای احراز هویت داخلی، مانند گواهی‌نامه‌های کلاینت و توکن‌های حساب سرویس که در ادامه توصیف شده‌اند، برای این مورد استفاده مناسب نیستند.

احراز هویت با گواهی‌نامهٔ کلاینت X.509 {#x509-client-certificate-authentication}

کوبرنتیز از احراز هویت با گواهی‌نامهٔ کلاینت X.509 برای مؤلفه‌های سیستمی استفاده می‌کند، مانند زمانی که kubelet در API Server احراز هویت می‌شود. اگرچه این سازوکار را می‌توان برای احراز هویت کاربران نیز به کار برد، ممکن است به دلیل چندین محدودیت برای استفادهٔ تولیدی مناسب نباشد:

  • گواهی‌نامه‌های کلاینت را نمی‌توان به‌صورت تکی باطل کرد. هنگامی که یک گواهی‌نامه افشا شود، مهاجم می‌تواند تا زمان انقضای آن از آن استفاده کند. برای کاهش این خطر، توصیه می‌شود طول عمر کوتاهی برای اعتبارنامه‌های احراز هویت کاربر که با استفاده از گواهی‌نامه‌های کلاینت ایجاد می‌شوند پیکربندی شود.
  • اگر لازم باشد گواهی‌نامه‌ای بی‌اعتبار شود، کلید مرجع صدور گواهی‌نامه باید از نو تولید شود که این کار می‌تواند خطرات دسترس‌پذیری را برای کلاستر به همراه داشته باشد.
  • هیچ سابقهٔ دائمی‌ای از گواهی‌نامه‌های کلاینت ایجادشده در کلاستر وجود ندارد. بنابراین، اگر نیاز به پیگیری گواهی‌نامه‌های صادرشده دارید، همهٔ آن‌ها باید ثبت شوند.
  • کلیدهای خصوصی مورد استفاده برای احراز هویت با گواهی‌نامهٔ کلاینت را نمی‌توان با گذرواژه محافظت کرد. هر کسی که بتواند فایل حاوی کلید را بخواند، قادر به استفاده از آن خواهد بود.
  • استفاده از احراز هویت با گواهی‌نامهٔ کلاینت مستلزم اتصال مستقیم از کلاینت به API server بدون هیچ نقطهٔ خاتمهٔ TLS میانی است که می‌تواند معماری‌های شبکه را پیچیده کند.
  • داده‌های گروه در مقدار O گواهی‌نامهٔ کلاینت جاسازی شده‌اند، به این معنا که عضویت‌های گروهی کاربر در طول عمر گواهی‌نامه قابل تغییر نیستند.

فایل توکن ایستا {#static-token-file}

اگرچه کوبرنتیز به شما اجازه می‌دهد اعتبارنامه‌ها را از یک فایل توکن ایستا واقع روی دیسک‌های نودهای control plane بارگذاری کنید، این رویکرد به دلایل متعددی برای سرورهای تولیدی توصیه نمی‌شود:

  • اعتبارنامه‌ها به‌صورت متن ساده روی دیسک‌های نودهای control plane ذخیره می‌شوند که می‌تواند یک خطر امنیتی باشد.
  • تغییر هر اعتبارنامه برای اعمال شدن مستلزم راه‌اندازی مجدد فرایند API server است که می‌تواند بر دسترس‌پذیری تأثیر بگذارد.
  • هیچ سازوکاری برای اینکه کاربران بتوانند اعتبارنامه‌های خود را چرخش دهند وجود ندارد. برای چرخش یک اعتبارنامه، مدیر کلاستر باید توکن را روی دیسک تغییر داده و آن را میان کاربران توزیع کند.
  • هیچ سازوکار قفل‌کردنی برای جلوگیری از حملات brute-force وجود ندارد.

توکن‌های راه‌اندازی {#bootstrap-tokens}

توکن‌های راه‌اندازی (Bootstrap tokens) برای پیوستن نودها به کلاسترها استفاده می‌شوند و به دلایل متعددی برای احراز هویت کاربران توصیه نمی‌شوند:

  • آن‌ها عضویت‌های گروهی ثابت و ازپیش‌تعیین‌شده‌ای دارند که برای استفادهٔ عمومی مناسب نیست و این امر آن‌ها را برای اهداف احراز هویت نامناسب می‌سازد.
  • تولید دستی توکن‌های راه‌اندازی می‌تواند به توکن‌های ضعیفی منجر شود که مهاجم بتواند آن‌ها را حدس بزند و این می‌تواند یک خطر امنیتی باشد.
  • هیچ سازوکار قفل‌کردنی برای جلوگیری از حملات brute-force وجود ندارد و این امر حدس زدن یا شکستن توکن را برای مهاجمان آسان‌تر می‌کند.

توکن‌های secret مربوط به ServiceAccount {#serviceaccount-secret-tokens}

Secretهای حساب سرویس به‌عنوان گزینه‌ای در دسترس هستند تا بارهای کاری در حال اجرا در کلاستر بتوانند در API server احراز هویت شوند. در کوبرنتیز < 1.23، این‌ها گزینهٔ پیش‌فرض بودند، اما در حال جایگزین شدن با توکن‌های TokenRequest API هستند. اگرچه می‌توان از این secretها برای احراز هویت کاربران استفاده کرد، به دلایل متعددی عموماً نامناسب هستند:

  • نمی‌توان برای آن‌ها تاریخ انقضا تعیین کرد و تا زمان حذف حساب سرویس مرتبط معتبر باقی می‌مانند.
  • توکن‌های احراز هویت برای هر کاربر کلاستری که بتواند secretها را در فضای نامی که در آن تعریف شده‌اند بخواند قابل مشاهده هستند.
  • حساب‌های سرویس را نمی‌توان به گروه‌های دلخواه اضافه کرد و این امر مدیریت RBAC را در جاهایی که استفاده می‌شوند پیچیده می‌کند.

توکن‌های TokenRequest API {#tokenrequest-api-tokens}

TokenRequest API ابزاری مفید برای تولید اعتبارنامه‌های کوتاه‌عمر برای احراز هویت سرویس‌ها در API server یا سیستم‌های شخص ثالث است. با این حال، عموماً برای احراز هویت کاربران توصیه نمی‌شود، زیرا هیچ روشی برای ابطال وجود ندارد و توزیع ایمن اعتبارنامه‌ها میان کاربران می‌تواند چالش‌برانگیز باشد.

هنگام استفاده از توکن‌های TokenRequest برای احراز هویت سرویس، توصیه می‌شود طول عمر کوتاهی برای آن‌ها پیاده‌سازی شود تا تأثیر توکن‌های افشاشده کاهش یابد.

احراز هویت با توکن OpenID Connect {#openid-connect-token-authentication}

کوبرنتیز از یکپارچه‌سازی سرویس‌های احراز هویت خارجی با API کوبرنتیز با استفاده از OpenID Connect (OIDC) پشتیبانی می‌کند. طیف گسترده‌ای از نرم‌افزارها وجود دارد که می‌توان از آن‌ها برای یکپارچه‌سازی کوبرنتیز با یک ارائه‌دهندهٔ هویت استفاده کرد. با این حال، هنگام استفاده از احراز هویت OIDC در کوبرنتیز، در نظر گرفتن اقدامات سخت‌سازی زیر اهمیت دارد:

  • نرم‌افزاری که برای پشتیبانی از احراز هویت OIDC در کلاستر نصب می‌شود باید از بارهای کاری عمومی ایزوله شود، زیرا با امتیازات بالا اجرا خواهد شد.
  • برخی از سرویس‌های مدیریت‌شدهٔ کوبرنتیز از نظر ارائه‌دهندگان OIDC قابل استفاده محدودیت دارند.
  • همانند توکن‌های TokenRequest، توکن‌های OIDC باید طول عمر کوتاهی داشته باشند تا تأثیر توکن‌های افشاشده کاهش یابد.

احراز هویت با توکن Webhook {#webhook-token-authentication}

احراز هویت با توکن Webhook گزینهٔ دیگری برای یکپارچه‌سازی ارائه‌دهندگان احراز هویت خارجی با کوبرنتیز است. این سازوکار اجازه می‌دهد برای اتخاذ تصمیم احراز هویت، از طریق یک webhook با یک سرویس احراز هویت، که یا درون کلاستر یا به‌صورت خارجی اجرا می‌شود، ارتباط برقرار شود. توجه به این نکته اهمیت دارد که مناسب بودن این سازوکار احتمالاً به نرم‌افزار مورد استفاده برای سرویس احراز هویت بستگی دارد و ملاحظات خاص کوبرنتیز نیز وجود دارد که باید در نظر گرفته شوند.

برای پیکربندی احراز هویت Webhook، دسترسی به فایل‌سیستم‌های سرورهای control plane لازم است. این به آن معناست که این کار با کوبرنتیز مدیریت‌شده ممکن نخواهد بود، مگر اینکه ارائه‌دهنده به‌طور خاص آن را در دسترس قرار دهد. علاوه بر این، هر نرم‌افزاری که برای پشتیبانی از این دسترسی در کلاستر نصب می‌شود باید از بارهای کاری عمومی ایزوله شود، زیرا با امتیازات بالا اجرا خواهد شد.

پراکسی احراز هویت‌کننده {#authenticating-proxy}

گزینهٔ دیگر برای یکپارچه‌سازی سیستم‌های احراز هویت خارجی با کوبرنتیز، استفاده از یک پراکسی احراز هویت‌کننده است. با این سازوکار، کوبرنتیز انتظار دارد درخواست‌هایی را از پراکسی دریافت کند که مقادیر سرآیند مشخصی در آن‌ها تنظیم شده است و نام کاربری و عضویت‌های گروهی‌ای را که باید برای اهداف مجوزدهی اختصاص یابند نشان می‌دهند. توجه به این نکته اهمیت دارد که هنگام استفاده از این سازوکار، ملاحظات مشخصی وجود دارد که باید در نظر گرفته شوند.

نخست، باید از TLS با پیکربندی ایمن میان پراکسی و API server کوبرنتیز استفاده شود تا خطر رهگیری ترافیک یا حملات شنود کاهش یابد. این کار تضمین می‌کند که ارتباط میان پراکسی و API server کوبرنتیز ایمن است.

دوم، باید آگاه بود که مهاجمی که بتواند سرآیندهای درخواست را تغییر دهد ممکن است بتواند به منابع کوبرنتیز دسترسی غیرمجاز پیدا کند. از این رو، اهمیت دارد اطمینان حاصل شود که سرآیندها به‌درستی ایمن شده‌اند و قابل دستکاری نیستند.
