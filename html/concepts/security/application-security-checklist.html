چک‌لیست امنیت برنامه

رهنمودهای پایه برای تضمین امنیت برنامه‌ها روی کوبرنتیز، با مخاطب قرار دادن توسعه‌دهندگان برنامه

هدف این چک‌لیست ارائهٔ رهنمودهای پایه برای ایمن‌سازی برنامه‌های در حال اجرا در کوبرنتیز از دیدگاه یک توسعه‌دهنده است. این فهرست قرار نیست جامع باشد و قرار است در طول زمان تکامل یابد.

دربارهٔ نحوهٔ خواندن و استفاده از این سند:

  • ترتیب موضوعات بازتاب‌دهندهٔ ترتیب اولویت نیست.
  • برخی از موارد چک‌لیست در پاراگراف زیر فهرست هر بخش به تفصیل آمده‌اند.
  • این چک‌لیست فرض می‌کند که یک developer کاربری از کلاستر کوبرنتیز است که با آبجکت‌هایی با دامنهٔ فضای نام تعامل دارد.
احتیاط:

چک‌لیست‌ها به‌تنهایی برای دستیابی به وضعیت امنیتی خوب کافی نیستند. وضعیت امنیتی خوب نیازمند توجه و بهبود مداوم است، اما یک چک‌لیست می‌تواند نخستین گام در مسیر بی‌پایان آمادگی امنیتی باشد. برخی از توصیه‌های این چک‌لیست ممکن است برای نیازهای امنیتی خاص شما بیش از حد سخت‌گیرانه یا بیش از حد آسان‌گیرانه باشند. از آنجا که امنیت کوبرنتیز «یک نسخه برای همه» نیست، هر دسته از موارد چک‌لیست باید بر اساس شایستگی‌های خود ارزیابی شود.

سخت‌سازی امنیتی پایه

چک‌لیست زیر توصیه‌های سخت‌سازی امنیتی پایه‌ای را ارائه می‌دهد که برای بیشتر برنامه‌هایی که روی کوبرنتیز مستقر می‌شوند کاربرد دارد.

طراحی برنامه

  • [ ] هنگام طراحی برنامه‌ها، از اصول امنیتی درست پیروی کنید.
  • [ ] برنامه از طریق درخواست و محدودیت منابع با کلاس QoS مناسب پیکربندی شده باشد.
    • [ ] محدودیت حافظه برای بارهای کاری با مقداری برابر یا بیشتر از درخواست تنظیم شده باشد.
    • [ ] ممکن است محدودیت CPU روی بارهای کاری حساس تنظیم شود.

حساب سرویس

  • [ ] از استفاده از ServiceAccount با نام default خودداری کنید. به‌جای آن، برای هر بار کاری یا میکروسرویس ServiceAccountهای جداگانه ایجاد کنید.
  • [ ] automountServiceAccountToken باید روی false تنظیم شود، مگر اینکه پاد برای کار کردن به‌طور خاص به دسترسی به API کوبرنتیز نیاز داشته باشد.

توصیه‌های securityContext در سطح Pod {#security-context-pod}

  • [ ] runAsNonRoot: true را تنظیم کنید.
  • [ ] کانتینر را طوری پیکربندی کنید که به‌عنوان کاربری با امتیازات کمتر اجرا شود (برای مثال، با استفاده از runAsUser و runAsGroup) و مجوزهای مناسب را روی فایل‌ها یا دایرکتوری‌های درون ایمیج کانتینر پیکربندی کنید.
  • [ ] به‌صورت اختیاری یک گروه تکمیلی با fsGroup برای دسترسی به حجم‌های پایدار اضافه کنید.
  • [ ] برنامه در فضای نامی مستقر شود که یک استاندارد امنیتی Pod مناسب را اعمال می‌کند. اگر نمی‌توانید این اعمال را برای کلاستر(هایی) که برنامه در آن‌ها مستقر می‌شود کنترل کنید، این موضوع را یا از طریق مستندسازی یا از طریق دفاع در عمق اضافی در نظر بگیرید.

توصیه‌های securityContext در سطح کانتینر {#security-context-container}

  • [ ] ارتقای امتیاز را با استفاده از allowPrivilegeEscalation: false غیرفعال کنید.
  • [ ] فایل‌سیستم ریشه را با readOnlyRootFilesystem: true به‌صورت فقط‌خواندنی پیکربندی کنید.
  • [ ] از اجرای کانتینرهای privileged خودداری کنید (privileged: false را تنظیم کنید).
  • [ ] همهٔ capabilityها را از کانتینرها حذف کنید و فقط capabilityهای مشخصی را که برای عملکرد کانتینر لازم هستند دوباره اضافه کنید.

کنترل دسترسی مبتنی بر نقش (RBAC) {#rbac}

  • [ ] مجوزهایی مانند create، patch، update و delete فقط در صورت لزوم اعطا شوند.
  • [ ] از ایجاد مجوزهای RBAC برای ایجاد یا به‌روزرسانی نقش‌ها خودداری کنید، زیرا این کار می‌تواند به ارتقای امتیاز منجر شود.
  • [ ] اتصال‌ها (binding) برای گروه system:unauthenticated را بازبینی کرده و در صورت امکان آن‌ها را حذف کنید، زیرا این کار به هر کسی که بتواند در سطح شبکه با API server ارتباط برقرار کند دسترسی می‌دهد.

افعال create، update و delete باید با احتیاط مجاز شوند. فعل patch اگر روی یک Namespace مجاز باشد، می‌تواند به کاربران اجازه دهد برچسب‌های فضای نام یا deploymentها را به‌روزرسانی کنند که می‌تواند سطح حمله را افزایش دهد.

برای بارهای کاری حساس، ارائهٔ یک ValidatingAdmissionPolicy توصیه‌شده را در نظر بگیرید که اقدامات نوشتنی مجاز را بیشتر محدود می‌کند.

امنیت ایمیج

  • [ ] استفاده از یک ابزار اسکن ایمیج برای اسکن ایمیج پیش از استقرار کانتینرها در کلاستر کوبرنتیز.
  • [ ] از امضای کانتینر برای اعتبارسنجی امضای ایمیج کانتینر پیش از استقرار در کلاستر کوبرنتیز استفاده کنید.

سیاست‌های شبکه

  • [ ] NetworkPolicyها را طوری پیکربندی کنید که فقط ترافیک ورودی و خروجی مورد انتظار از پادها مجاز باشد.

اطمینان حاصل کنید که کلاستر شما NetworkPolicy را فراهم کرده و اعمال می‌کند. اگر برنامه‌ای می‌نویسید که کاربران آن را در کلاسترهای مختلف مستقر خواهند کرد، بررسی کنید که آیا می‌توانید فرض کنید NetworkPolicy در دسترس است و اعمال می‌شود یا خیر.

سخت‌سازی امنیتی پیشرفته {#advanced}

این بخش از راهنما برخی نکات پیشرفتهٔ سخت‌سازی امنیتی را پوشش می‌دهد که بسته به تنظیمات مختلف محیط کوبرنتیز ممکن است ارزشمند باشند.

امنیت کانتینرهای لینوکس

Security Context را برای کانتینر پاد پیکربندی کنید.

  • [ ] تنظیم پروفایل Seccomp برای یک کانتینر.
  • [ ] محدود کردن دسترسی یک کانتینر به منابع با AppArmor.
  • [ ] اختصاص برچسب‌های SELinux به یک کانتینر.

کلاس‌های محیط اجرا

  • [ ] کلاس‌های محیط اجرای (runtime class) مناسب را برای کانتینرها پیکربندی کنید.

برخی کانتینرها ممکن است به سطح ایزوله‌سازی متفاوتی از آنچه محیط اجرای پیش‌فرض کلاستر فراهم می‌کند نیاز داشته باشند. می‌توان از runtimeClassName در یک podspec برای تعریف کلاس محیط اجرای متفاوت استفاده کرد.

برای بارهای کاری حساس، استفاده از ابزارهای شبیه‌سازی هسته مانند gVisor، یا ایزوله‌سازی مجازی‌سازی‌شده با استفاده از سازوکاری مانند kata-containers را در نظر بگیرید.

در محیط‌های با اعتماد بالا، استفاده از ماشین‌های مجازی محرمانه را برای بهبود هرچه بیشتر امنیت کلاستر در نظر بگیرید.
