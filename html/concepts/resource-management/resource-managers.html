مدیران منابع

کوبرنتیز برای پشتیبانی از بارهای کاری حساس به تأخیر و با توان عملیاتی بالا، مجموعه‌ای از مدیران منابع (Resource Managers) را ارائه می‌دهد. هدف این مدیران، هماهنگ‌سازی و بهینه‌سازی هم‌ترازی منابع نود برای Podهایی است که با الزامات مشخصی برای منابع CPU، دستگاه‌ها و حافظه (hugepages) پیکربندی شده‌اند.

Topology manager

وضعیت ویژگی: Kubernetes [] ()

Topology Manager یکی از اجزای kubelet است که هدف آن هماهنگ‌سازی مجموعهٔ اجزایی است که مسئول این بهینه‌سازی‌ها هستند. برای آگاهی بیشتر، کنترل سیاست‌های مدیریت توپولوژی روی یک نود را بخوانید.

CPU manager

وضعیت ویژگی: Kubernetes [] ()

CPU Manager یکی از اجزای kubelet است که تخصیص انحصاری منابع را برای منابع CPU فراهم می‌کند. این جزء برای گرفتن تصمیم‌های اختصاص منابع با Topology Manager مشورت می‌کند. برای آگاهی بیشتر، کنترل سیاست‌های مدیریت CPU روی نود را بخوانید.

سیاست‌های اختصاص CPU به Podها

پس از اینکه یک Pod به یک نود متصل شد، kubelet روی آن نود ممکن است لازم باشد یا سخت‌افزار موجود را چندگانه‌سازی (multiplex) کند (برای مثال، CPUها را بین چند Pod به اشتراک بگذارد) یا با اختصاص دادن بخشی از منابع، سخت‌افزار را تخصیص دهد (برای مثال، یک یا چند CPU را برای استفادهٔ انحصاری یک Pod اختصاص دهد).

به‌طور پیش‌فرض، kubelet از سهمیهٔ CFS برای اعمال محدودیت‌های CPU مربوط به Pod استفاده می‌کند. هنگامی که نود تعداد زیادی Pod وابسته به CPU را اجرا می‌کند، بار کاری ممکن است بسته به اینکه Pod محدودسازی (throttle) شده باشد یا نه و اینکه کدام هسته‌های CPU در زمان زمان‌بندی در دسترس باشند، به هسته‌های CPU متفاوتی منتقل شود. بسیاری از بارهای کاری به این جابه‌جایی حساس نیستند و بنابراین بدون هیچ مداخله‌ای به‌خوبی کار می‌کنند.

با این حال، در بارهای کاری که وابستگی (affinity) به حافظهٔ نهان CPU و تأخیر زمان‌بندی به‌طور چشمگیری بر کارایی بار کاری اثر می‌گذارند، kubelet اجازه می‌دهد سیاست‌های جایگزینی برای مدیریت CPU به کار روند تا برخی ترجیحات جای‌گذاری روی نود تعیین شوند. این کار با استفاده از CPU Manager و سیاست آن پیاده‌سازی شده است. دو سیاست در دسترس است:

  • none: سیاست none به‌طور صریح طرح پیش‌فرض موجود برای وابستگی CPU را فعال می‌کند و هیچ وابستگی‌ای فراتر از آنچه زمان‌بند سیستم‌عامل به‌طور خودکار انجام می‌دهد، فراهم نمی‌کند. محدودیت‌های مصرف CPU برای Podهای Guaranteed و Podهای Burstable با استفاده از سهمیهٔ CFS اعمال می‌شوند.
  • static: سیاست static به کانتینرهای Podهای Guaranteed که requests صحیح برای CPU دارند، اجازهٔ دسترسی به CPUهای انحصاری روی نود را می‌دهد. این انحصار با استفاده از کنترل‌کنندهٔ cgroup با نام cpuset اعمال می‌شود.
توجه:

سرویس‌های سیستمی مانند container runtime و خود kubelet می‌توانند همچنان روی این CPUهای انحصاری اجرا شوند. این انحصار تنها شامل Podهای دیگر می‌شود.

CPU Manager از آفلاین و آنلاین کردن CPUها در زمان اجرا پشتیبانی نمی‌کند.

سیاست Static

سیاست static مدیریت دقیق‌تر CPU و اختصاص انحصاری CPU را ممکن می‌سازد. این سیاست یک مخزن مشترک از CPUها را مدیریت می‌کند که در ابتدا شامل همهٔ CPUهای نود است. تعداد CPUهای قابل تخصیص انحصاری برابر است با تعداد کل CPUهای نود منهای هرگونه رزرو CPU که در پیکربندی kubelet تعیین شده است. CPUهایی که با این گزینه‌ها رزرو می‌شوند، به مقدار صحیح و به ترتیب صعودی شناسهٔ هستهٔ فیزیکی از مخزن مشترک اولیه برداشته می‌شوند. این مخزن مشترک مجموعه‌ای از CPUهاست که همهٔ کانتینرهای Podهای BestEffort و Burstable روی آن اجرا می‌شوند. کانتینرهای Podهای Guaranteed که requests کسری برای CPU دارند نیز روی CPUهای مخزن مشترک اجرا می‌شوند. تنها کانتینرهایی که بخشی از یک Pod Guaranteed هستند و requests صحیح برای CPU دارند، CPUهای انحصاری دریافت می‌کنند.

توجه:

هنگامی که سیاست static فعال است، kubelet به رزرو CPU بزرگ‌تر از صفر نیاز دارد. دلیل این امر آن است که رزرو صفر CPU اجازه می‌دهد مخزن مشترک خالی شود.

همزمان با زمان‌بندی Podهای Guaranteed که کانتینرهایشان الزامات اختصاص ایستا را برآورده می‌کنند روی نود، CPUها از مخزن مشترک حذف و در cpuset کانتینر قرار داده می‌شوند. از سهمیهٔ CFS برای محدود کردن مصرف CPU این کانتینرها استفاده نمی‌شود، زیرا مصرف آن‌ها توسط خود دامنهٔ زمان‌بندی محدود می‌شود. به عبارت دیگر، تعداد CPUها در cpuset کانتینر برابر با limit صحیح CPU است که در مشخصات Pod تعیین شده است. این اختصاص ایستا وابستگی CPU را افزایش می‌دهد و تعویض‌های زمینه (context switch) ناشی از محدودسازی را برای بار کاری وابسته به CPU کاهش می‌دهد.

کانتینرهای موجود در مشخصات Podهای زیر را در نظر بگیرید:

spec:
  containers:
  - name: nginx
    image: nginx

Pod بالا در کلاس QoS از نوع BestEffort اجرا می‌شود، زیرا هیچ requests یا limits منبعی مشخص نشده است. این Pod در مخزن مشترک اجرا می‌شود.

spec:
  containers:
  - name: nginx
    image: nginx
    resources:
      limits:
        memory: "200Mi"
      requests:
        memory: "100Mi"

Pod بالا در کلاس QoS از نوع Burstable اجرا می‌شود، زیرا requests منبع با limits برابر نیستند و مقدار cpu مشخص نشده است. این Pod در مخزن مشترک اجرا می‌شود.

spec:
  containers:
  - name: nginx
    image: nginx
    resources:
      limits:
        memory: "200Mi"
        cpu: "2"
      requests:
        memory: "100Mi"
        cpu: "1"

Pod بالا در کلاس QoS از نوع Burstable اجرا می‌شود، زیرا requests منبع با limits برابر نیستند. این Pod در مخزن مشترک اجرا می‌شود.

spec:
  containers:
  - name: nginx
    image: nginx
    resources:
      limits:
        memory: "200Mi"
        cpu: "2"
      requests:
        memory: "200Mi"
        cpu: "2"

Pod بالا در کلاس QoS از نوع Guaranteed اجرا می‌شود، زیرا requests با limits برابرند. همچنین محدودیت منبع کانتینر برای منبع CPU یک عدد صحیح بزرگ‌تر از یا مساوی یک است. به کانتینر nginx دو CPU انحصاری داده می‌شود.

spec:
  containers:
  - name: nginx
    image: nginx
    resources:
      limits:
        memory: "200Mi"
        cpu: "1.5"
      requests:
        memory: "200Mi"
        cpu: "1.5"

Pod بالا در کلاس QoS از نوع Guaranteed اجرا می‌شود، زیرا requests با limits برابرند. اما محدودیت منبع کانتینر برای منبع CPU یک عدد کسری است. این Pod در مخزن مشترک اجرا می‌شود.

spec:
  containers:
  - name: nginx
    image: nginx
    resources:
      limits:
        memory: "200Mi"
        cpu: "2"

Pod بالا در کلاس QoS از نوع Guaranteed اجرا می‌شود، زیرا تنها limits مشخص شده‌اند و requests در صورتی که به‌طور صریح مشخص نشوند، برابر با limits تنظیم می‌شوند. همچنین محدودیت منبع کانتینر برای منبع CPU یک عدد صحیح بزرگ‌تر از یا مساوی یک است. به کانتینر nginx دو CPU انحصاری داده می‌شود.

گزینه‌های سیاست Static {#cpu-policy-static--options}

گزینه‌های در دسترس برای سیاست مدیریت CPU از نوع static در ادامه آمده‌اند که به ترتیب الفبایی فهرست شده‌اند:

align-by-socket (آلفا، به‌طور پیش‌فرض پنهان)
CPUها را بر اساس مرز بستهٔ فیزیکی / سوکت، به‌جای مرزهای منطقی NUMA، هم‌تراز می‌کند (در دسترس از کوبرنتیز v1.25)
distribute-cpus-across-cores (آلفا، به‌طور پیش‌فرض پنهان)
هسته‌های مجازی را که گاهی رشته‌های سخت‌افزاری (hardware threads) نامیده می‌شوند، در میان هسته‌های فیزیکی مختلف تخصیص می‌دهد (در دسترس از کوبرنتیز v1.31)
distribute-cpus-across-numa (بتا، به‌طور پیش‌فرض قابل مشاهده)
CPUها را در میان دامنه‌های مختلف NUMA پخش می‌کند و هدف آن توازن یکنواخت بین دامنه‌های انتخاب‌شده است (در دسترس از کوبرنتیز v1.23)
full-pcpus-only (GA، به‌طور پیش‌فرض قابل مشاهده)
همیشه هسته‌های فیزیکی کامل را تخصیص می‌دهد (در دسترس از کوبرنتیز v1.22، GA از کوبرنتیز v1.33)
strict-cpu-reservation (GA، به‌طور پیش‌فرض قابل مشاهده)
از اجرای همهٔ Podها، صرف‌نظر از کلاس کیفیت سرویس (Quality of Service) آن‌ها، روی CPUهای رزروشده جلوگیری می‌کند (در دسترس از کوبرنتیز v1.32، GA از کوبرنتیز v1.35)
prefer-align-cpus-by-uncorecache (GA، به‌طور پیش‌فرض قابل مشاهده)
CPUها را به شیوهٔ بهترین تلاش (best-effort) بر اساس مرز حافظهٔ نهان uncore (سطح آخر) هم‌تراز می‌کند (در دسترس از کوبرنتیز v1.32)

می‌توانید گروه‌هایی از گزینه‌ها را بر اساس سطح بلوغشان با استفاده از feature gateهای زیر روشن و خاموش کنید:

  • CPUManagerPolicyBetaOptions (به‌طور پیش‌فرض فعال). برای پنهان کردن گزینه‌های سطح بتا، آن را غیرفعال کنید.
  • CPUManagerPolicyAlphaOptions (به‌طور پیش‌فرض غیرفعال). برای نمایش گزینه‌های سطح آلفا، آن را فعال کنید.

همچنان باید هر گزینه را با استفاده از فیلد cpuManagerPolicyOptions در فایل پیکربندی kubelet فعال کنید.

برای جزئیات بیشتر دربارهٔ تک‌تک گزینه‌هایی که می‌توانید پیکربندی کنید، ادامه را بخوانید.

full-pcpus-only

اگر گزینهٔ سیاست full-pcpus-only مشخص شود، سیاست static همیشه هسته‌های فیزیکی کامل را تخصیص می‌دهد. به‌طور پیش‌فرض و بدون این گزینه، سیاست static با استفاده از تخصیص بهترین تطابق (best-fit) آگاه از توپولوژی، CPUها را تخصیص می‌دهد. در سیستم‌هایی که SMT در آن‌ها فعال است، این سیاست می‌تواند هسته‌های مجازی منفرد را که متناظر با رشته‌های سخت‌افزاری هستند، تخصیص دهد. این امر می‌تواند باعث شود کانتینرهای مختلف از هسته‌های فیزیکی یکسانی استفاده کنند؛ این رفتار نیز به نوبهٔ خود به مشکل همسایه‌های پرسروصدا دامن می‌زند. با فعال بودن این گزینه، Pod تنها در صورتی توسط kubelet پذیرفته می‌شود که درخواست CPU همهٔ کانتینرهای آن بتواند با تخصیص هسته‌های فیزیکی کامل برآورده شود. اگر Pod از مرحلهٔ پذیرش عبور نکند، با پیام SMTAlignmentError در وضعیت Failed قرار می‌گیرد.

distribute-cpus-across-numa

اگر گزینهٔ سیاست distribute-cpus-across-numa مشخص شود، سیاست static در مواردی که برای برآوردن تخصیص به بیش از یک نود NUMA نیاز باشد، CPUها را به‌طور یکنواخت در میان نودهای NUMA توزیع می‌کند. به‌طور پیش‌فرض، CPUManager CPUها را روی یک نود NUMA فشرده می‌کند تا پر شود و CPUهای باقی‌مانده به‌سادگی به نود NUMA بعدی سرریز می‌شوند. این امر می‌تواند در کدهای موازی که به barrierها (و ابزارهای همگام‌سازی مشابه) متکی هستند، گلوگاه‌های ناخواسته‌ای ایجاد کند، زیرا این نوع کد معمولاً تنها به سرعت کندترین کارگر خود اجرا می‌شود (کارگری که به این دلیل کند می‌شود که CPUهای کمتری دست‌کم روی یکی از نودهای NUMA در دسترس هستند). با توزیع یکنواخت CPUها در میان نودهای NUMA، توسعه‌دهندگان برنامه می‌توانند آسان‌تر اطمینان حاصل کنند که هیچ کارگری بیش از دیگران از اثرات NUMA آسیب نمی‌بیند و در نتیجه کارایی کلی این نوع برنامه‌ها بهبود می‌یابد.

align-by-socket

اگر گزینهٔ سیاست align-by-socket مشخص شود، هنگام تصمیم‌گیری دربارهٔ نحوهٔ تخصیص CPUها به یک کانتینر، CPUها در مرز سوکت هم‌تراز در نظر گرفته می‌شوند. به‌طور پیش‌فرض، CPUManager تخصیص‌های CPU را در مرز NUMA هم‌تراز می‌کند؛ این کار در صورتی که برای برآوردن تخصیص لازم باشد CPUها از بیش از یک نود NUMA برداشته شوند، ممکن است به افت کارایی منجر شود. هرچند CPUManager می‌کوشد اطمینان حاصل کند که همهٔ CPUها از کمترین تعداد ممکن نودهای NUMA تخصیص یابند، هیچ تضمینی وجود ندارد که آن نودهای NUMA روی یک سوکت باشند. با هدایت CPUManager به هم‌تراز کردن صریح CPUها در مرز سوکت به‌جای مرز NUMA، می‌توانیم از چنین مشکلاتی جلوگیری کنیم. توجه داشته باشید که این گزینهٔ سیاست با سیاست single-numa-node در TopologyManager سازگار نیست و برای سخت‌افزاری که تعداد سوکت‌های آن بیشتر از تعداد نودهای NUMA است، اعمال نمی‌شود.

distribute-cpus-across-cores

اگر گزینهٔ سیاست distribute-cpus-across-cores مشخص شود، سیاست static می‌کوشد هسته‌های مجازی (رشته‌های سخت‌افزاری) را در میان هسته‌های فیزیکی مختلف تخصیص دهد. به‌طور پیش‌فرض، CPUManager تمایل دارد CPUها را روی کمترین تعداد ممکن هستهٔ فیزیکی فشرده کند؛ این کار می‌تواند به رقابت میان CPUهای یک هستهٔ فیزیکی منجر شود و گلوگاه‌های کارایی ایجاد کند. با فعال کردن سیاست distribute-cpus-across-cores، سیاست static اطمینان حاصل می‌کند که CPUها در میان بیشترین تعداد ممکن هستهٔ فیزیکی توزیع شوند و بدین ترتیب رقابت روی یک هستهٔ فیزیکی کاهش یابد و کارایی کلی بهبود پیدا کند. با این حال، باید توجه داشت که این راهبرد ممکن است هنگامی که سیستم زیر بار سنگین است، کارایی کمتری داشته باشد. در چنین شرایطی، مزیت کاهش رقابت کم می‌شود. در مقابل، رفتار پیش‌فرض می‌تواند به کاهش سربار ارتباط میان هسته‌ها کمک کند و احتمالاً در شرایط بار بالا کارایی بهتری فراهم آورد.

strict-cpu-reservation

پارامتر reservedSystemCPUs در KubeletConfiguration، یا گزینهٔ منسوخ‌شدهٔ خط فرمان kubelet یعنی --reserved-cpus، یک مجموعهٔ CPU صریح را برای daemonهای سیستمی سیستم‌عامل و daemonهای سیستمی کوبرنتیز تعریف می‌کند. جزئیات بیشتر دربارهٔ این پارامتر را می‌توانید در صفحهٔ فهرست CPUهای رزروشدهٔ صریح بیابید. به‌طور پیش‌فرض، این ایزوله‌سازی تنها برای Podهای guaranteed با درخواست‌های CPU صحیح پیاده‌سازی شده است و برای Podهای burstable و best-effort (و Podهای guaranteed با درخواست‌های CPU کسری) اعمال نمی‌شود. مرحلهٔ پذیرش تنها درخواست‌های CPU را با CPUهای قابل تخصیص مقایسه می‌کند. از آنجا که محدودیت CPU بالاتر از درخواست است، رفتار پیش‌فرض به Podهای burstable و best-effort اجازه می‌دهد ظرفیت reservedSystemCPUs را مصرف کنند و در استقرارهای واقعی باعث گرسنگی سرویس‌های سیستم‌عامل میزبان شوند. اگر گزینهٔ سیاست strict-cpu-reservation فعال باشد، سیاست static اجازه نمی‌دهد هیچ بار کاری‌ای از هسته‌های CPU مشخص‌شده در reservedSystemCPUs استفاده کند.

prefer-align-cpus-by-uncorecache

اگر سیاست prefer-align-cpus-by-uncorecache مشخص شود، سیاست static منابع CPU را برای کانتینرهای منفرد به گونه‌ای تخصیص می‌دهد که همهٔ CPUهای اختصاص‌یافته به یک کانتینر، بلوک حافظهٔ نهان uncore یکسانی (که حافظهٔ نهان سطح آخر یا LLC نیز نامیده می‌شود) را به اشتراک بگذارند. به‌طور پیش‌فرض، CPUManager اختصاص‌های CPU را به‌صورت فشرده انجام می‌دهد که ممکن است باعث شود به کانتینرها CPUهایی از چند حافظهٔ نهان uncore اختصاص یابد. این گزینه CPUManager را قادر می‌سازد CPUها را به گونه‌ای تخصیص دهد که استفادهٔ کارآمد از حافظهٔ نهان uncore به حداکثر برسد. تخصیص به شیوهٔ بهترین تلاش انجام می‌شود و هدف آن قرار دادن هرچه بیشتر CPUها درون یک حافظهٔ نهان uncore یکسان است. اگر نیاز CPU کانتینر از ظرفیت CPU یک حافظهٔ نهان uncore بیشتر باشد، CPUManager تعداد حافظه‌های نهان uncore مورد استفاده را به حداقل می‌رساند تا هم‌ترازی بهینهٔ حافظهٔ نهان uncore حفظ شود. بارهای کاری خاص می‌توانند از کاهش تأخیر میان حافظه‌های نهان و کاهش همسایه‌های پرسروصدا در سطح حافظهٔ نهان، از نظر کارایی بهره ببرند. اگر CPUManager نتواند در حالی که نود منابع کافی دارد هم‌ترازی بهینه را انجام دهد، کانتینر همچنان با استفاده از رفتار فشردهٔ پیش‌فرض پذیرفته می‌شود.

Memory manager

وضعیت ویژگی: Kubernetes [] ()

Memory Manager یکی از اجزای kubelet است که تخصیص انحصاری منابع را برای منابع حافظه فراهم می‌کند. این جزء برای گرفتن تصمیم‌های اختصاص منابع با Topology Manager مشورت می‌کند. برای آگاهی بیشتر، کنترل سیاست‌های مدیریت حافظه روی یک نود را بخوانید.

سیاست‌های اختصاص حافظه به Podها {#memory-management-policies}

Memory Manager کوبرنتیز منابع RAM (حافظه و به‌طور اختیاری huge pageهای لینوکس) را برای Podهای دارای کلاس QoS از نوع Guaranteed تخصیص می‌دهد.

Memory Manager از پروتکل تولید راهنما (hint) برای به دست آوردن مناسب‌ترین وابستگی NUMA برای یک Pod استفاده می‌کند. Memory Manager این راهنماهای وابستگی را در اختیار مدیر مرکزی (Topology Manager) قرار می‌دهد. بر اساس این راهنماها و سیاست Topology Manager، Pod رد یا در نود پذیرفته می‌شود.

افزون بر این، Memory Manager اطمینان حاصل می‌کند که حافظه‌ای که یک Pod درخواست می‌کند از کمترین تعداد ممکن نودهای NUMA تخصیص یابد.

برای آگاهی بیشتر، کنترل سیاست‌های مدیریت حافظه روی یک نود را بخوانید.

Device manager

وضعیت ویژگی: Kubernetes v1.26 [stable] (پایدار)

Device Manager یکی از اجزای kubelet است که دستگاه‌های سخت‌افزاری را با استفاده از API مربوط به device plugin به Podها تخصیص می‌دهد. این جزء برای گرفتن تصمیم‌های اختصاص منابع، با استفاده از اطلاعات توپولوژی‌ای که device pluginها فراهم می‌کنند، با Topology Manager مشورت می‌کند. برای آگاهی بیشتر، یکپارچگی device plugin با Topology Manager را بخوانید.

مدیران منابع سطح Pod {#pod-level-resource-managers}

وضعیت ویژگی: Kubernetes [] ()

پشتیبانی از منابع سطح Pod برای مدیران منابع kubelet (Topology، CPU و Memory) به مدیران منابع اجازه می‌دهد مستقیماً از .spec.resources برای تصمیم‌های هم‌ترازی NUMA و تخصیص انحصاری استفاده کنند.

برای آگاهی بیشتر، صفحهٔ مفهومی اختصاصی مدیران منابع سطح Pod را ببینید، یا بخوانید که چگونه منابع CPU و حافظهٔ سطح Pod را اختصاص دهید.
