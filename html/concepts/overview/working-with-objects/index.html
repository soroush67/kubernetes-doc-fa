آبجکت‌ها در کوبرنتیز

آبجکت‌های کوبرنتیز موجودیت‌های ماندگاری در سیستم کوبرنتیز هستند. کوبرنتیز از این موجودیت‌ها برای بازنمایی وضعیت کلاستر شما استفاده می‌کند. با مدل آبجکت کوبرنتیز و نحوه‌ی کار با این آبجکت‌ها آشنا شوید.

این صفحه توضیح می‌دهد که آبجکت‌های کوبرنتیز چگونه در API کوبرنتیز بازنمایی می‌شوند و چگونه می‌توانید آن‌ها را در قالب .yaml بیان کنید.

آشنایی با آبجکت‌های کوبرنتیز {#kubernetes-objects}

آبجکت‌های کوبرنتیز موجودیت‌های ماندگاری در سیستم کوبرنتیز هستند. کوبرنتیز از این موجودیت‌ها برای بازنمایی وضعیت کلاستر شما استفاده می‌کند. به‌طور مشخص، این آبجکت‌ها می‌توانند موارد زیر را توصیف کنند:

  • چه برنامه‌های کانتینری‌شده‌ای در حال اجرا هستند (و روی کدام نودها)
  • منابعی که در اختیار آن برنامه‌ها قرار دارد
  • سیاست‌های حاکم بر رفتار آن برنامه‌ها، مانند سیاست‌های راه‌اندازی مجدد، ارتقا و تحمل خطا

یک آبجکت کوبرنتیز «ثبتی از قصد» (record of intent) است؛ هنگامی که آبجکت را ایجاد می‌کنید، سیستم کوبرنتیز پیوسته تلاش می‌کند تا از وجود آن آبجکت اطمینان حاصل کند. با ایجاد یک آبجکت، در واقع به سیستم کوبرنتیز می‌گویید که می‌خواهید بار کاری کلاستر شما چه شکلی داشته باشد؛ این همان وضعیت مطلوب کلاستر شما است.

برای کار با آبجکت‌های کوبرنتیز، چه برای ایجاد، چه تغییر و چه حذف آن‌ها، باید از API کوبرنتیز استفاده کنید. برای مثال، هنگامی که از رابط خط فرمان kubectl استفاده می‌کنید، این رابط خط فرمان فراخوانی‌های لازم API کوبرنتیز را برای شما انجام می‌دهد. همچنین می‌توانید با استفاده از یکی از کتابخانه‌های کلاینت، API کوبرنتیز را مستقیماً در برنامه‌های خود به کار ببرید.

spec و status آبجکت

تقریباً هر آبجکت کوبرنتیز دو فیلد آبجکتیِ تودرتو دارد که پیکربندی آبجکت را تعیین می‌کنند: spec آبجکت و status آبجکت. برای آبجکت‌هایی که spec دارند، باید هنگام ایجاد آبجکت این فیلد را تنظیم کنید و توصیفی از ویژگی‌هایی که می‌خواهید منبع داشته باشد، یعنی وضعیت مطلوب آن را، ارائه دهید.

status وضعیت فعلی آبجکت را توصیف می‌کند که سیستم کوبرنتیز و مؤلفه‌های آن آن را فراهم و به‌روزرسانی می‌کنند. control plane کوبرنتیز به‌طور پیوسته و فعالانه وضعیت واقعی هر آبجکت را مدیریت می‌کند تا با وضعیت مطلوبی که شما تعیین کرده‌اید مطابقت داشته باشد.

برای مثال: در کوبرنتیز، Deployment آبجکتی است که می‌تواند یک برنامه‌ی در حال اجرا روی کلاستر شما را بازنمایی کند. هنگامی که Deployment را ایجاد می‌کنید، ممکن است spec آن Deployment را طوری تنظیم کنید که مشخص کند می‌خواهید سه رونوشت (replica) از برنامه در حال اجرا باشد. سیستم کوبرنتیز spec مربوط به Deployment را می‌خواند و سه نمونه از برنامه‌ی مطلوب شما را راه‌اندازی می‌کند و status را به‌روزرسانی می‌کند تا با spec شما مطابقت داشته باشد. اگر هر یک از آن نمونه‌ها با شکست مواجه شود (یک تغییر در status)، سیستم کوبرنتیز با انجام یک اصلاح به تفاوت میان spec و status واکنش نشان می‌دهد؛ در این مورد، با راه‌اندازی یک نمونه‌ی جایگزین.

برای اطلاعات بیشتر درباره‌ی spec، status و metadata آبجکت، به قراردادهای API کوبرنتیز مراجعه کنید.

توصیف یک آبجکت کوبرنتیز

هنگامی که آبجکتی را در کوبرنتیز ایجاد می‌کنید، باید spec آبجکت را که وضعیت مطلوب آن را توصیف می‌کند، همراه با برخی اطلاعات پایه درباره‌ی آبجکت (مانند نام) ارائه دهید. هنگامی که از API کوبرنتیز برای ایجاد آبجکت استفاده می‌کنید (چه مستقیماً و چه از طریق kubectl)، آن درخواست API باید این اطلاعات را به‌صورت JSON در بدنه‌ی درخواست در بر داشته باشد. در بیشتر موارد، اطلاعات را در فایلی که مانیفست نامیده می‌شود در اختیار kubectl قرار می‌دهید. طبق قرارداد، مانیفست‌ها در قالب YAML هستند (می‌توانید از قالب JSON نیز استفاده کنید). ابزارهایی مانند kubectl هنگام ارسال درخواست API از طریق HTTP، اطلاعات مانیفست را به JSON یا قالب سریال‌سازی پشتیبانی‌شده‌ی دیگری تبدیل می‌کنند.

در اینجا نمونه‌ای از یک مانیفست آمده است که فیلدهای الزامی و spec آبجکت را برای یک Deployment کوبرنتیز نشان می‌دهد:

application/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
spec:
  selector:
    matchLabels:
      app: nginx
  replicas: 2 # tells deployment to run 2 pods matching the template
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
      - name: nginx
        image: nginx:1.14.2
        ports:
        - containerPort: 80

یکی از راه‌های ایجاد یک Deployment با استفاده از فایل مانیفستی مانند نمونه‌ی بالا، استفاده از فرمان kubectl apply در رابط خط فرمان kubectl و ارسال فایل .yaml به‌عنوان آرگومان است. در اینجا یک نمونه آمده است:

kubectl apply -f https://k8s.io/examples/application/deployment.yaml

خروجی مشابه زیر است:

deployment.apps/nginx-deployment created

فیلدهای الزامی

در مانیفست (فایل YAML یا JSON) آبجکت کوبرنتیزی که می‌خواهید ایجاد کنید، باید مقادیر فیلدهای زیر را تنظیم کنید:

  • apiVersion - از کدام نسخه‌ی API کوبرنتیز برای ایجاد این آبجکت استفاده می‌کنید
  • kind - چه نوع آبجکتی می‌خواهید ایجاد کنید
  • metadata - داده‌هایی که به شناسایی یکتای آبجکت کمک می‌کنند، از جمله رشته‌ی name، UID و namespace اختیاری
  • spec - چه وضعیتی را برای آبجکت می‌خواهید

قالب دقیق spec آبجکت برای هر آبجکت کوبرنتیز متفاوت است و فیلدهای تودرتوی مختص آن آبجکت را در بر می‌گیرد. مرجع API کوبرنتیز می‌تواند به شما کمک کند قالب spec را برای همه‌ی آبجکت‌هایی که می‌توانید با کوبرنتیز ایجاد کنید بیابید.

برای مثال، فیلد spec را در مرجع API مربوط به Pod ببینید. برای هر Pod، فیلد .spec آن Pod و وضعیت مطلوب آن را مشخص می‌کند (مانند نام ایمیج کانتینر برای هر کانتینر درون آن Pod). نمونه‌ی دیگری از مشخصات یک آبجکت، فیلد spec در API مربوط به StatefulSet است. برای StatefulSet، فیلد .spec آن StatefulSet و وضعیت مطلوب آن را مشخص می‌کند. درون .spec یک StatefulSet، یک الگو (template) برای آبجکت‌های Pod قرار دارد. این الگو Podهایی را توصیف می‌کند که کنترل‌کننده‌ی StatefulSet برای برآورده‌کردن مشخصات StatefulSet ایجاد خواهد کرد. انواع مختلف آبجکت‌ها می‌توانند .status متفاوتی نیز داشته باشند؛ باز هم صفحات مرجع API ساختار فیلد .status و محتوای آن را برای هر نوع آبجکت به تفصیل شرح می‌دهند.

برای اطلاعات بیشتر درباره‌ی نوشتن فایل‌های پیکربندی YAML، به بهترین رویه‌های پیکربندی کوبرنتیز مراجعه کنید.

اعتبارسنجی فیلد در سمت سرور

از نسخه‌ی v1.25 کوبرنتیز به بعد، API server اعتبارسنجی فیلد را در سمت سرور ارائه می‌دهد که فیلدهای ناشناخته یا تکراری را در یک آبجکت تشخیص می‌دهد. این قابلیت همه‌ی کارکردهای kubectl --validate را در سمت سرور فراهم می‌کند.

ابزار kubectl از فلگ --validate برای تنظیم سطح اعتبارسنجی فیلد استفاده می‌کند. این فلگ مقادیر ignore، warn و strict را می‌پذیرد و همچنین مقادیر true (معادل strict) و false (معادل ignore) را نیز قبول می‌کند. تنظیم پیش‌فرض اعتبارسنجی برای kubectl، --validate=true است.

Strict
اعتبارسنجی سخت‌گیرانه‌ی فیلد؛ در صورت شکست اعتبارسنجی، خطا رخ می‌دهد
Warn
اعتبارسنجی فیلد انجام می‌شود، اما خطاها به‌جای شکست درخواست، به‌صورت هشدار نمایش داده می‌شوند
Ignore
هیچ اعتبارسنجی فیلدی در سمت سرور انجام نمی‌شود

هنگامی که kubectl نتواند به API serverای متصل شود که از اعتبارسنجی فیلد پشتیبانی می‌کند، به استفاده از اعتبارسنجی سمت کلاینت بازمی‌گردد. کوبرنتیز 1.27 و نسخه‌های بعدی همیشه اعتبارسنجی فیلد را ارائه می‌دهند؛ نسخه‌های قدیمی‌تر کوبرنتیز ممکن است این قابلیت را نداشته باشند. اگر کلاستر شما قدیمی‌تر از v1.27 است، مستندات نسخه‌ی کوبرنتیز خود را بررسی کنید.

گام‌های بعدی

اگر با کوبرنتیز تازه آشنا شده‌اید، درباره‌ی موارد زیر بیشتر بخوانید:

  • Podها که مهم‌ترین آبجکت‌های پایه‌ی کوبرنتیز هستند.
  • آبجکت‌های Deployment.
  • کنترل‌کننده‌ها در کوبرنتیز.
  • kubectl و فرمان‌های kubectl.

مدیریت آبجکت‌های کوبرنتیز توضیح می‌دهد که چگونه از kubectl برای مدیریت آبجکت‌ها استفاده کنید. اگر kubectl را هنوز در اختیار ندارید، ممکن است لازم باشد kubectl را نصب کنید.
