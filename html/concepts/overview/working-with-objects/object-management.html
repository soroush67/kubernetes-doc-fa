مدیریت آبجکت‌های کوبرنتیز

ابزار خط فرمان kubectl از چند روش مختلف برای ایجاد و مدیریت آبجکت‌های کوبرنتیز پشتیبانی می‌کند. این سند مروری بر رویکردهای مختلف ارائه می‌دهد. برای جزئیات مدیریت آبجکت‌ها با Kubectl، کتاب Kubectl را بخوانید.

روش‌های مدیریت

هشدار:

یک آبجکت کوبرنتیز باید فقط با یک روش مدیریت شود. ترکیب و آمیختن روش‌ها برای یک آبجکت یکسان به رفتار تعریف‌نشده منجر می‌شود.

روش مدیریت بر روی چه چیزی عمل می‌کند محیط توصیه‌شده تعداد نویسندگان پشتیبانی‌شده منحنی یادگیری
دستورهای دستوری (imperative) آبجکت‌های زنده پروژه‌های توسعه 1+ کمترین
پیکربندی دستوری آبجکت فایل‌های منفرد پروژه‌های عملیاتی 1 متوسط
پیکربندی اعلانی (declarative) آبجکت دایرکتوری‌هایی از فایل‌ها پروژه‌های عملیاتی 1+ بیشترین

دستورهای دستوری

هنگام استفاده از دستورهای دستوری، کاربر مستقیماً روی آبجکت‌های زنده در یک کلاستر عمل می‌کند. کاربر عملیات را به‌صورت آرگومان یا پرچم به دستور kubectl ارائه می‌دهد.

این روش توصیه‌شده برای شروع کار یا اجرای یک کار یک‌باره در یک کلاستر است. از آنجا که این روش مستقیماً روی آبجکت‌های زنده عمل می‌کند، هیچ سابقه‌ای از پیکربندی‌های قبلی فراهم نمی‌کند.

مثال‌ها

با ایجاد یک آبجکت Deployment، یک نمونه از کانتینر nginx را اجرا کنید:

kubectl create deployment nginx --image nginx

مزایا و معایب

مزایا در مقایسه با پیکربندی آبجکت:

  • دستورها در قالب یک واژهٔ عملیاتی واحد بیان می‌شوند.
  • دستورها برای اعمال تغییرات در کلاستر فقط به یک مرحله نیاز دارند.

معایب در مقایسه با پیکربندی آبجکت:

  • دستورها با فرایندهای بازبینی تغییرات یکپارچه نمی‌شوند.
  • دستورها سابقهٔ ممیزی مرتبط با تغییرات فراهم نمی‌کنند.
  • دستورها جز آنچه به‌صورت زنده وجود دارد، منبعی برای سوابق فراهم نمی‌کنند.
  • دستورها قالبی برای ایجاد آبجکت‌های جدید فراهم نمی‌کنند.

پیکربندی دستوری آبجکت

در پیکربندی دستوری آبجکت، دستور kubectl عملیات (create، replace و غیره)، پرچم‌های اختیاری و دست‌کم یک نام فایل را مشخص می‌کند. فایل مشخص‌شده باید شامل تعریف کامل آبجکت در قالب YAML یا JSON باشد.

برای جزئیات بیشتر دربارهٔ تعاریف آبجکت‌ها، به مرجع API مراجعه کنید.

هشدار:

دستور دستوری replace مشخصات (spec) موجود را با مشخصات تازه ارائه‌شده جایگزین می‌کند و همهٔ تغییراتی را که در آبجکت اعمال شده اما در فایل پیکربندی وجود ندارند کنار می‌گذارد. این رویکرد نباید با انواع منبعی استفاده شود که مشخصات آن‌ها مستقل از فایل پیکربندی به‌روزرسانی می‌شود. برای مثال، فیلد externalIPs در Serviceهایی از نوع LoadBalancer توسط کلاستر و مستقل از پیکربندی به‌روزرسانی می‌شود.

مثال‌ها

آبجکت‌های تعریف‌شده در یک فایل پیکربندی را ایجاد کنید:

kubectl create -f nginx.yaml

آبجکت‌های تعریف‌شده در دو فایل پیکربندی را حذف کنید:

kubectl delete -f nginx.yaml -f redis.yaml

آبجکت‌های تعریف‌شده در یک فایل پیکربندی را با بازنویسی پیکربندی زنده به‌روزرسانی کنید:

kubectl replace -f nginx.yaml

مزایا و معایب

مزایا در مقایسه با دستورهای دستوری:

  • پیکربندی آبجکت را می‌توان در یک سیستم کنترل نسخه مانند Git ذخیره کرد.
  • پیکربندی آبجکت می‌تواند با فرایندهایی مانند بازبینی تغییرات پیش از push و سوابق ممیزی یکپارچه شود.
  • پیکربندی آبجکت قالبی برای ایجاد آبجکت‌های جدید فراهم می‌کند.

معایب در مقایسه با دستورهای دستوری:

  • پیکربندی آبجکت به درک پایه‌ای از طرح‌وارهٔ آبجکت نیاز دارد.
  • پیکربندی آبجکت به مرحلهٔ اضافی نوشتن یک فایل YAML نیاز دارد.

مزایا در مقایسه با پیکربندی اعلانی آبجکت:

  • رفتار پیکربندی دستوری آبجکت ساده‌تر و درک آن آسان‌تر است.
  • از نسخهٔ 1.5 کوبرنتیز، پیکربندی دستوری آبجکت بالغ‌تر است.

معایب در مقایسه با پیکربندی اعلانی آبجکت:

  • پیکربندی دستوری آبجکت روی فایل‌ها بهترین عملکرد را دارد، نه روی دایرکتوری‌ها.
  • به‌روزرسانی‌های آبجکت‌های زنده باید در فایل‌های پیکربندی منعکس شوند، در غیر این صورت در جایگزینی بعدی از دست خواهند رفت.

پیکربندی اعلانی آبجکت

هنگام استفاده از پیکربندی اعلانی آبجکت، کاربر روی فایل‌های پیکربندی آبجکت که به‌صورت محلی ذخیره شده‌اند عمل می‌کند، اما عملیاتی را که باید روی فایل‌ها انجام شود تعریف نمی‌کند. عملیات ایجاد، به‌روزرسانی و حذف به‌طور خودکار و برای هر آبجکت توسط kubectl تشخیص داده می‌شوند. این امر کار روی دایرکتوری‌ها را ممکن می‌سازد، جایی که ممکن است برای آبجکت‌های مختلف به عملیات متفاوتی نیاز باشد.

توجه:

پیکربندی اعلانی آبجکت تغییراتی را که نویسندگان دیگر اعمال کرده‌اند حفظ می‌کند، حتی اگر این تغییرات در فایل پیکربندی آبجکت ادغام نشده باشند. این امر با استفاده از عملیات API ‏patch برای نوشتن فقط تفاوت‌های مشاهده‌شده، به‌جای استفاده از عملیات API ‏replace برای جایگزینی کل پیکربندی آبجکت، امکان‌پذیر است.

مثال‌ها

همهٔ فایل‌های پیکربندی آبجکت در دایرکتوری configs را پردازش کنید و آبجکت‌های زنده را ایجاد یا patch کنید. می‌توانید ابتدا با diff ببینید چه تغییراتی قرار است اعمال شود و سپس apply کنید:

kubectl diff -f configs/
kubectl apply -f configs/

دایرکتوری‌ها را به‌صورت بازگشتی پردازش کنید:

kubectl diff -R -f configs/
kubectl apply -R -f configs/

مزایا و معایب

مزایا در مقایسه با پیکربندی دستوری آبجکت:

  • تغییراتی که مستقیماً روی آبجکت‌های زنده اعمال شده‌اند حفظ می‌شوند، حتی اگر در فایل‌های پیکربندی ادغام نشده باشند.
  • پیکربندی اعلانی آبجکت پشتیبانی بهتری از کار روی دایرکتوری‌ها و تشخیص خودکار نوع عملیات (create، patch، delete) برای هر آبجکت دارد.

معایب در مقایسه با پیکربندی دستوری آبجکت:

  • اشکال‌زدایی پیکربندی اعلانی آبجکت و درک نتایج آن، هنگامی که غیرمنتظره باشند، دشوارتر است.
  • به‌روزرسانی‌های جزئی با استفاده از diffها، عملیات ادغام و patch پیچیده‌ای ایجاد می‌کنند.

گام‌های بعدی

  • مدیریت آبجکت‌های کوبرنتیز با استفاده از دستورهای دستوری
  • مدیریت دستوری آبجکت‌های کوبرنتیز با استفاده از فایل‌های پیکربندی
  • مدیریت اعلانی آبجکت‌های کوبرنتیز با استفاده از فایل‌های پیکربندی
  • مدیریت اعلانی آبجکت‌های کوبرنتیز با استفاده از Kustomize
