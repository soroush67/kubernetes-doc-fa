نسخه‌های ذخیره‌سازی

سرور API کوبرنتیز آبجکت‌ها را با تکیه بر یک ذخیره‌ساز پشتیبان سازگار با etcd ذخیره می‌کند (اغلب، ذخیره‌ساز پشتیبان خود etcd است). هر آبجکت با استفاده از نسخهٔ مشخصی از آن نوع API سریال‌سازی می‌شود؛ برای مثال، بازنمایی v1 یک ConfigMap. کوبرنتیز از اصطلاح نسخهٔ ذخیره‌سازی (storage version) برای توصیف نحوهٔ ذخیره‌شدن یک آبجکت در کلاستر شما استفاده می‌کند.

API کوبرنتیز همچنین بر تبدیل خودکار تکیه دارد؛ برای مثال، اگر یک HorizontalPodAutoscaler داشته باشید، می‌توانید با آن HorizontalPodAutoscaler با استفاده از هر ترکیبی از نسخه‌های v1 و v2 از API ‏HorizontalPodAutoscaler تعامل داشته باشید. کوبرنتیز مسئول تبدیل هر فراخوانی API است تا کلاینت‌ها نبینند که در واقع کدام نسخه سریال‌سازی شده است.

برای مدیران کلاستر، نسخهٔ ذخیره‌سازی آبجکت مفهوم مهمی برای درک است، زیرا همین مفهوم بازنمایی API آبجکت را به کدگذاری واقعی در پشتوانهٔ ذخیره‌سازی پیوند می‌دهد. این موضوع می‌تواند زمانی اهمیت داشته باشد که کدگذاری‌های باینری زیربنایی آبجکت مهم باشند، مانند رمزنگاری در حالت سکون (encryption at rest) یا منسوخ‌شدن API.

یک API یکسان ممکن است چند نسخهٔ ذخیره‌سازی داشته باشد که سرور API می‌تواند آن‌ها را به یک طرح‌وارهٔ آبجکت تبدیل کند. یک آبجکت منفرد که بخشی از آن منبع است، باید در هر زمان فقط یک نسخهٔ ذخیره‌سازی داشته باشد. این بدان معناست که سرور API از کدگذاری‌های باینری آبجکت‌ها آگاه است و می‌تواند همهٔ نسخه‌های ذخیره‌شده را به‌صورت پویا به بازنمایی API آبجکت تبدیل کند.

نسخهٔ یک آبجکت کاملاً از نسخهٔ ذخیره‌سازی جداست. برای مثال، یک آبجکت API با نسخهٔ v1alpha1 و یک آبجکت با نسخهٔ v1beta1 برای یک منبع یکسان، تا زمانی که نسخهٔ ذخیره‌سازی میان این دو آبجکت به‌روزرسانی نشده باشد، در ذخیره‌ساز به شکل یکسانی کدگذاری می‌شوند.

نگاشت نسخهٔ ذخیره‌سازی به منبع

هر منبع در هر لحظه یک نسخهٔ ذخیره‌سازی فعال دارد، به این معنا که هر نوشتنی روی یک آبجکت، آبجکت را با آن نسخهٔ ذخیره‌سازی ذخیره می‌کند. با این حال، نسخهٔ ذخیره‌سازی را می‌توان به‌روزرسانی کرد و در نتیجه آبجکت‌ها می‌توانند با نسخه‌های متفاوتی ذخیره شوند. یک آبجکت در هر زمان فقط با یک نسخهٔ ذخیره‌سازی ذخیره می‌شود.

خواندن از سرور API داده‌های ذخیره‌شده را به بازنمایی API آبجکت تبدیل می‌کند. به این ترتیب، نسخه‌های ذخیره‌سازی قدیمی می‌توانند تا زمانی که هیچ به‌روزرسانی‌ای روی آبجکت رخ ندهد، برای مدت نامحدود باقی بمانند. از سوی دیگر، نوشتن‌ها آبجکت ذخیره‌شده را هنگام به‌روزرسانی به بازنمایی جدید تبدیل می‌کنند.

نسخه‌های ذخیره‌سازی برای منابع سفارشی {#CustomResourceDefinition-storage-version}

منابع سفارشی به‌صورت پویا تعریف می‌شوند و از این رو از نظر نسخهٔ ذخیره‌سازی با انواع داخلی کوبرنتیز تفاوت دارند. کدگذاری ذخیره‌سازی آبجکت‌های داخلی معمولاً جدا از انواع API آن‌ها تعریف می‌شود، به‌طوری که آبجکت ذخیره‌شده نقش یک هاب (hub) را ایفا می‌کند و نسخهٔ مشخص منبع، جز اینکه فیلدی در طرح‌وارهٔ آبجکت است، اهمیتی ندارد.

اما برای منابع سفارشی، نسخهٔ مشخصی از منبع باید به‌عنوان نسخهٔ ذخیره‌سازی تنظیم شود. طرح‌واره‌ای که آن نسخهٔ مشخص از منبع سفارشی تعریف می‌کند، به‌عنوان کدگذاری منبع در لایهٔ ذخیره‌سازی استفاده خواهد شد. برای اطلاعات دقیق‌تر دربارهٔ راه‌اندازی API و نسخه‌گذاری، به مجموعه قابلیت‌های پیشرفتهٔ CRD مراجعه کنید.

برای مثال، این CustomResourceDefinition برای crontabs را ببینید:

apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: crontabs.example.com
spec:
  group: example.com
  # list of versions supported by this CustomResourceDefinition
  versions:
  - name: v1beta1
    # Each version can be enabled/disabled by Served flag.
    served: true
    # One and only one version must be marked as the storage version.
    storage: true
    schema:
      openAPIV3Schema:
        type: object
        properties:
          host:
            type: string
          port:
            type: string
  - name: v1
    served: true
    storage: false
    schema:
      openAPIV3Schema:
        type: object
        properties:
          host:
            type: string
          port:
            type: string
          time:
            type: string
  conversion:
    strategy: None
  scope: Namespaced
  names:
    plural: crontabs
    singular: crontab
    kind: CronTab
    shortNames:
    - ct

تعریف API ‏v1beta1 به‌عنوان نسخهٔ ذخیره‌سازی استفاده می‌شود، به این معنا که هرگونه به‌روزرسانی یا ایجاد crontabs با طرح‌وارهٔ آبجکت API v1beta1 ذخیره خواهد شد. در این مورد، این در واقع به آن معناست که آبجکت API ‏v1 هرگز نخواهد توانست فیلد time را ذخیره کند، زیرا این فیلد بخشی از تعریف ذخیره‌سازی نیست. این طرح‌واره در لایهٔ ذخیره‌سازی به‌عنوان کدگذاری باینری خود آبجکت استفاده می‌شود. تلاش برای تنظیم هم‌زمان دو نسخه به‌عنوان نسخهٔ ذخیره‌شده نامعتبر تلقی می‌شود، زیرا به این معنا خواهد بود که دو طرح دادهٔ مختلف هم‌زمان روش‌های معتبری برای ذخیرهٔ آبجکت‌ها محسوب شوند.

پس از تغییر نسخه‌ای که برای ذخیره‌سازی استفاده می‌شود، آن نسخه از API برای ذخیرهٔ هر CR جدید یا به‌روزرسانی‌شده استفاده خواهد شد. watch کردن یا دریافت آبجکت باعث می‌شود آبجکت مورد استفاده قرار گیرد، اما فقط آبجکت را از نسخهٔ ذخیره‌سازی قدیمی تبدیل می‌کند و بر آبجکت تأثیری نمی‌گذارد. فقط به‌روزرسانی یا ایجاد تأثیر خواهد داشت و از نسخهٔ ذخیره‌سازی تازه تعریف‌شده استفاده خواهد کرد.

ارتباط نسخه‌های ذخیره‌سازی با رمزنگاری در حالت سکون

ابزارهایی برای رمزنگاری ذخیره‌سازی در حالت سکون یک کلاستر وجود دارد، به‌ویژه برای secretهای کلاستر. این کار لایهٔ حفاظتی بیشتری در برابر نشت داده‌ها اضافه می‌کند، زیرا داده‌های واقعی ذخیره‌شده در کلاستر رمزنگاری شده‌اند. این بدان معناست که سرور API در واقع داده‌ها را هنگام بازیابی از ذخیره‌ساز رمزگشایی می‌کند. APIServer برای رمزگشایی صحیح آبجکت، باید کلید آن نسخهٔ ذخیره‌سازی را در اختیار داشته باشد.

در این مورد، نسخهٔ ذخیره‌سازی چیزی بیش از کدگذاری باینری آبجکت است. تا زمانی که آنچه ذخیره شده است به نحوی قابل تبدیل به آبجکت API باشد، می‌توان از آن به‌عنوان نسخهٔ ذخیره‌سازی استفاده کرد.

مهاجرت به نسخهٔ ذخیره‌سازی متفاوت

وجود چند نسخهٔ ذخیره‌سازی برای یک منبع واحد می‌تواند برای مدیران کلاستر مشکلاتی ایجاد کند. یک مدیر کلاستر ممکن است نتواند نسخه‌های قدیمی یک API را برای CRDهایی که ممکن است دیگر پشتیبانی نشوند حذف کند، تا زمانی که مطمئن شود هیچ آبجکتی دیگر از نسخهٔ ذخیره‌سازی مرتبط با آن استفاده نمی‌کند. با وجود تعداد زیادی آبجکت و دیدی مبهم نسبت به اینکه کدام‌یک جدید هستند و کدام‌یک هنوز بر نسخه‌های ذخیره‌سازی قدیمی تکیه دارند، تشخیص اینکه چه زمانی می‌توان یک نسخه را به‌طور ایمن حذف کرد دشوار می‌شود. اگر نسخه‌ای زودتر از موعد حذف شود، ممکن است به ناتوانی کامل در خواندن آبجکت منجر شود.

مسئلهٔ مهم دیگر، استفاده از کلیدهای رمزنگاری است که در بخش بالا تعریف شد. از آنجا که برای به‌روزرسانی نسخهٔ ذخیره‌سازی، منبع باید به‌طور فعال مورد استفاده باشد، هنگام چرخش کلید، هم کلید رمزنگاری قدیمی و هم کلید رمزنگاری جدید باید تا زمانی که مدیر مطمئن شود همهٔ آبجکت‌ها دست‌کم یک بار نوشته شده‌اند، در حال استفاده باقی بمانند. این امر هم خطرات امنیتی و هم مشکلات کاربردپذیری ایجاد می‌کند، زیرا تا آن زمان نمی‌توان کلید را به‌طور کامل از استفاده خارج کرد.

برای نمونه‌هایی از نحوهٔ اجرای یک مهاجرت که تضمین کند همهٔ آبجکت‌ها بدون دخالت دستی از نسخهٔ ذخیره‌سازی جدیدتری استفاده می‌کنند، به مهاجرت نسخهٔ ذخیره‌سازی مراجعه کنید.
