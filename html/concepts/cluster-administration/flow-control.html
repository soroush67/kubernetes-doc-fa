اولویت و انصاف API

وضعیت ویژگی: Kubernetes v1.29 [stable] (پایدار)

کنترل رفتار سرور API کوبرنتیز در شرایط اضافه‌بار یکی از وظایف کلیدی مدیران کلاستر است. kube-apiserver چند کنترل در اختیار می‌گذارد (یعنی فلگ‌های خط فرمان --max-requests-inflight و --max-mutating-requests-inflight) که میزان کار معوقِ پذیرفته‌شده را محدود می‌کنند. این کنترل‌ها مانع می‌شوند که سیل درخواست‌های ورودی سرور API را دچار اضافه‌بار کند و احتمالاً از کار بیندازد. با این حال، این فلگ‌ها برای اطمینان از اینکه مهم‌ترین درخواست‌ها در دوره‌های پرترافیک پردازش شوند کافی نیستند.

ویژگی اولویت و انصاف API (API Priority and Fairness یا APF) جایگزینی است که محدودیت‌های max-inflight پیش‌گفته را بهبود می‌دهد. این ویژگی درخواست‌ها را با دقت و جزئیات بیشتری دسته‌بندی و از یکدیگر جدا می‌کند. همچنین مقدار محدودی صف‌بندی (queuing) را معرفی می‌کند تا در موارد افزایش‌های بسیار کوتاه‌مدت ترافیک، هیچ درخواستی رد نشود. درخواست‌ها با استفاده از یک روش صف‌بندی منصفانه از صف‌ها ارسال می‌شوند؛ برای مثال، یک کنترل‌کننده بدرفتار نباید باعث گرسنگی (starvation) دیگران شود (حتی در همان سطح اولویت).

این ویژگی به گونه‌ای طراحی شده است که با کنترل‌کننده‌های استاندارد به‌خوبی کار کند. این کنترل‌کننده‌ها از informerها استفاده می‌کنند و به شکست درخواست‌های API با عقب‌نشینی نمایی (exponential back-off) واکنش نشان می‌دهند. همین موضوع درباره‌ی سایر کلاینت‌هایی که به همین شیوه کار می‌کنند نیز صادق است.

احتیاط:

برخی درخواست‌ها که «طولانی‌مدت» دسته‌بندی می‌شوند—مانند اجرای فرمان از راه دور یا دنبال کردن لاگ‌ها—مشمول فیلتر اولویت و انصاف API نیستند. این موضوع درباره‌ی فلگ --max-requests-inflight نیز، زمانی که ویژگی اولویت و انصاف API فعال نیست، صادق است. اولویت و انصاف API بر درخواست‌های watch اعمال می‌شود. وقتی اولویت و انصاف API غیرفعال است، درخواست‌های watch مشمول محدودیت --max-requests-inflight نیستند.

فعال‌سازی/غیرفعال‌سازی اولویت و انصاف API

ویژگی اولویت و انصاف API با یک فلگ خط فرمان کنترل می‌شود و به‌طور پیش‌فرض فعال است. برای توضیحی کلی درباره‌ی گزینه‌های خط فرمان موجود برای kube-apiserver و نحوه‌ی فعال و غیرفعال کردن آن‌ها، بخش گزینه‌ها را ببینید. نام گزینه‌ی خط فرمان برای APF، "--enable-priority-and-fairness" است. این ویژگی همچنین یک گروه API را در بر می‌گیرد که شامل این نسخه‌هاست: (الف) نسخه‌ی پایدار v1 که در 1.29 معرفی شده و به‌طور پیش‌فرض فعال است، و (ب) نسخه‌ی v1beta3 که به‌طور پیش‌فرض فعال است و در v1.29 منسوخ شده است. می‌توانید نسخه‌ی بتای v1beta3 این گروه API را با افزودن فلگ‌های خط فرمان زیر به فراخوانی kube-apiserver غیرفعال کنید:

kube-apiserver \
--runtime-config=flowcontrol.apiserver.k8s.io/v1beta3=false \
 # …and other flags as usual

فلگ خط فرمان --enable-priority-and-fairness=false ویژگی اولویت و انصاف API را غیرفعال می‌کند.

سناریوهای سرور بازگشتی

در سناریوهای سرور بازگشتی باید با احتیاط از اولویت و انصاف API استفاده کرد. در این سناریوها، سروری مانند A هنگام رسیدگی به یک درخواست، یک درخواست فرعی به سرور دیگری مانند B می‌فرستد. حتی ممکن است سرور B نیز به نوبه‌ی خود یک فراخوانی فرعی دیگر به سرور A برگرداند. در شرایطی که کنترل اولویت و انصاف هم بر درخواست اصلی و هم بر یک یا چند درخواست فرعی اعمال شود، فارغ از عمق بازگشت، خطر وارونگی اولویت (priority inversion) و/یا بن‌بست (deadlock) وجود دارد.

یک نمونه از بازگشت زمانی است که kube-apiserver یک فراخوانی admission webhook به سرور B می‌فرستد و سرور B هنگام رسیدگی به آن فراخوانی، یک درخواست فرعی دیگر به kube-apiserver برمی‌گرداند. نمونه‌ی دیگر زمانی است که یک آبجکت APIService به kube-apiserver دستور می‌دهد درخواست‌های مربوط به یک گروه API مشخص را به یک سرور خارجی سفارشی B واگذار کند (این یکی از مواردی است که «تجمیع» (aggregation) نامیده می‌شود).

وقتی مشخص است که درخواست اصلی به یک سطح اولویت معین تعلق دارد، یکی از راه‌حل‌های ممکن این است که درخواست‌های فرعیِ کنترل‌شده در سطوح اولویت بالاتری دسته‌بندی شوند. وقتی درخواست‌های اصلی ممکن است به هر سطح اولویتی تعلق داشته باشند، درخواست‌های فرعیِ کنترل‌شده باید از محدودیت اولویت و انصاف معاف شوند. یک راه برای این کار استفاده از آبجکت‌هایی است که دسته‌بندی و رسیدگی را پیکربندی می‌کنند و در ادامه شرح داده می‌شوند. راه دیگر، غیرفعال کردن کامل اولویت و انصاف در سرور B با روش‌هایی است که در بالا توضیح داده شد. راه سوم، که وقتی سرور B همان kube-apiserver نیست ساده‌ترین راه است، ساختن سرور B به گونه‌ای است که اولویت و انصاف در کد آن غیرفعال باشد.

مفاهیم

ویژگی اولویت و انصاف API از چند قابلیت متمایز تشکیل شده است. درخواست‌های ورودی بر اساس ویژگی‌هایشان و با استفاده از FlowSchemaها دسته‌بندی می‌شوند و به سطوح اولویت اختصاص می‌یابند. سطوح اولویت با نگه‌داشتن محدودیت‌های همروندی (concurrency) جداگانه، درجه‌ای از جداسازی فراهم می‌کنند تا درخواست‌هایی که به سطوح اولویت مختلف اختصاص یافته‌اند نتوانند باعث گرسنگی یکدیگر شوند. در داخل هر سطح اولویت، یک الگوریتم صف‌بندی منصفانه مانع می‌شود که درخواست‌های جریان‌های (flows) مختلف باعث گرسنگی یکدیگر شوند. این الگوریتم همچنین امکان صف‌بندی درخواست‌ها را فراهم می‌کند تا وقتی میانگین بار به‌طور قابل‌قبولی پایین است، ترافیک انفجاری باعث شکست درخواست‌ها نشود.

سطوح اولویت

بدون فعال بودن APF، همروندی کلی در سرور API با فلگ‌های --max-requests-inflight و --max-mutating-requests-inflight در kube-apiserver محدود می‌شود. با فعال بودن APF، محدودیت‌های همروندی تعریف‌شده با این فلگ‌ها با هم جمع می‌شوند و سپس این مجموع میان مجموعه‌ای قابل پیکربندی از سطوح اولویت تقسیم می‌شود. هر درخواست ورودی به یک سطح اولویت واحد اختصاص می‌یابد و هر سطح اولویت تنها به تعدادی که محدودیت خاص آن اجازه می‌دهد، درخواست همروند ارسال می‌کند.

برای مثال، پیکربندی پیش‌فرض شامل سطوح اولویت جداگانه برای درخواست‌های انتخاب رهبر (leader election)، درخواست‌های کنترل‌کننده‌های داخلی و درخواست‌های Podها است. بنابراین یک Pod بدرفتار که سرور API را با درخواست‌ها غرق می‌کند، نمی‌تواند مانع موفقیت انتخاب رهبر یا اقدامات کنترل‌کننده‌های داخلی شود.

محدودیت‌های همروندی سطوح اولویت به‌صورت دوره‌ای تنظیم می‌شوند تا سطوح اولویتی که کمتر استفاده می‌شوند بتوانند به‌طور موقت همروندی را به سطوحی که بیشتر استفاده می‌شوند قرض دهند. این محدودیت‌ها بر پایه‌ی محدودیت‌های اسمی و نیز حدودی هستند که مشخص می‌کنند یک سطح اولویت چه مقدار همروندی می‌تواند قرض بدهد و چه مقدار می‌تواند قرض بگیرد. همه‌ی این مقادیر از آبجکت‌های پیکربندی‌ای به دست می‌آیند که در ادامه به آن‌ها اشاره می‌شود.

صندلی‌های اشغال‌شده توسط یک درخواست

توضیح بالا درباره‌ی مدیریت همروندی، روایت پایه است. درخواست‌ها مدت‌زمان‌های متفاوتی دارند، اما هنگام مقایسه با محدودیت همروندی یک سطح اولویت، در هر لحظه به‌طور یکسان شمرده می‌شوند. در روایت پایه، هر درخواست یک واحد همروندی را اشغال می‌کند. واژه‌ی «صندلی» (seat) به معنای یک واحد همروندی به کار می‌رود؛ این تعبیر از آنجا الهام گرفته شده است که هر مسافر در قطار یا هواپیما یکی از صندلی‌های محدود و ثابت را اشغال می‌کند.

اما برخی درخواست‌ها بیش از یک صندلی اشغال می‌کنند. بخشی از این‌ها درخواست‌های list هستند که سرور تخمین می‌زند تعداد زیادی آبجکت برمی‌گردانند. مشخص شده است که این درخواست‌ها بار فوق‌العاده سنگینی بر سرور تحمیل می‌کنند. به همین دلیل، سرور تعداد آبجکت‌هایی را که برگردانده خواهند شد تخمین می‌زند و برای درخواست، تعدادی صندلی متناسب با همین عدد تخمینی در نظر می‌گیرد.

تنظیمات زمان اجرا برای درخواست‌های watch

اولویت و انصاف API درخواست‌های watch را نیز مدیریت می‌کند، اما این کار با چند انحراف دیگر از رفتار پایه همراه است. نخستین مورد به این مربوط است که یک درخواست watch تا چه مدت صندلی خود را اشغال‌شده در نظر گرفته می‌شود. بسته به پارامترهای درخواست، پاسخ به یک درخواست watch ممکن است با اعلان‌های create برای همه‌ی آبجکت‌های مرتبطِ از پیش موجود آغاز شود یا نشود. اولویت و انصاف API درخواست watch را زمانی با صندلی خود تمام‌شده در نظر می‌گیرد که آن انفجار اولیه‌ی اعلان‌ها، در صورت وجود، به پایان رسیده باشد.

هر بار که سرور از ایجاد، به‌روزرسانی یا حذف یک آبجکت مطلع می‌شود، اعلان‌های معمول به‌صورت یک انفجار همروند به همه‌ی جریان‌های پاسخ watch مرتبط فرستاده می‌شوند. برای به حساب آوردن این کار، اولویت و انصاف API فرض می‌کند که هر درخواست نوشتن، پس از پایان نوشتن واقعی، مدتی اضافه نیز صندلی‌ها را اشغال می‌کند. سرور تعداد اعلان‌هایی را که باید فرستاده شوند تخمین می‌زند و تعداد صندلی‌ها و مدت اشغال صندلی درخواست نوشتن را طوری تنظیم می‌کند که این کار اضافه را نیز در بر بگیرد.

صف‌بندی

حتی در داخل یک سطح اولویت نیز ممکن است تعداد زیادی منبع ترافیک متمایز وجود داشته باشد. در شرایط اضافه‌بار، ارزشمند است که از گرسنگی دیگر جریان‌های درخواست به دست یک جریان جلوگیری شود (به‌ویژه در حالت نسبتاً رایجی که یک کلاینت معیوب، kube-apiserver را با درخواست‌ها غرق می‌کند؛ در حالت ایده‌آل، آن کلاینت معیوب نباید اصلاً تأثیر قابل‌اندازه‌گیری چندانی بر دیگر کلاینت‌ها داشته باشد). این موضوع با استفاده از یک الگوریتم صف‌بندی منصفانه برای پردازش درخواست‌هایی که به یک سطح اولویت یکسان اختصاص یافته‌اند مدیریت می‌شود. هر درخواست به یک جریان اختصاص می‌یابد که با نام FlowSchema منطبق به‌علاوه‌ی یک متمایزکننده‌ی جریان (flow distinguisher) شناسایی می‌شود. این متمایزکننده یا کاربر درخواست‌دهنده است، یا فضای نام (namespace) منبع هدف، یا هیچ‌کدام. سیستم تلاش می‌کند به درخواست‌های جریان‌های مختلفِ یک سطح اولویت وزن تقریباً یکسانی بدهد. برای اینکه نمونه‌های متمایز به‌طور متمایز رسیدگی شوند، کنترل‌کننده‌هایی که نمونه‌های زیادی دارند باید با نام‌های کاربری متمایز احراز هویت کنند.

پس از دسته‌بندی یک درخواست در یک جریان، ویژگی اولویت و انصاف API ممکن است درخواست را به یک صف اختصاص دهد. این تخصیص از روشی به نام شاردینگ درهم (shuffle sharding) استفاده می‌کند که با بهره‌گیری نسبتاً کارآمد از صف‌ها، جریان‌های کم‌شدت را از جریان‌های پرشدت جدا نگه می‌دارد.

جزئیات الگوریتم صف‌بندی برای هر سطح اولویت قابل تنظیم است و به مدیران امکان می‌دهد میان این موارد توازن برقرار کنند: مصرف حافظه، انصاف (این ویژگی که وقتی کل ترافیک از ظرفیت فراتر می‌رود، همه‌ی جریان‌های مستقل پیشرفت کنند)، تحمل ترافیک انفجاری، و تأخیر اضافه‌ای که صف‌بندی ایجاد می‌کند.

درخواست‌های معاف

برخی درخواست‌ها به اندازه‌ای مهم تلقی می‌شوند که مشمول هیچ‌یک از محدودیت‌های اعمال‌شده توسط این ویژگی نیستند. این معافیت‌ها مانع می‌شوند که یک پیکربندی نادرست کنترل جریان، سرور API را به‌کلی از کار بیندازد.

منابع

API کنترل جریان شامل دو نوع منبع است. PriorityLevelConfigurationها سطوح اولویت موجود و سهمی از بودجه‌ی همروندی موجود را که هر سطح می‌تواند به عهده بگیرد تعریف می‌کنند و امکان تنظیم دقیق رفتار صف‌بندی را فراهم می‌کنند. FlowSchemaها برای دسته‌بندی تک‌تک درخواست‌های ورودی استفاده می‌شوند و هر درخواست را با یک PriorityLevelConfiguration واحد منطبق می‌کنند.

PriorityLevelConfiguration

هر PriorityLevelConfiguration نماینده‌ی یک سطح اولویت واحد است. هر PriorityLevelConfiguration یک محدودیت مستقل بر تعداد درخواست‌های معوق و نیز محدودیت‌هایی بر تعداد درخواست‌های در صف دارد.

محدودیت همروندی اسمی یک PriorityLevelConfiguration نه به‌صورت تعداد مطلق صندلی‌ها، بلکه به‌صورت «سهم‌های همروندی اسمی» (nominal concurrency shares) مشخص می‌شود. کل محدودیت همروندی سرور API به نسبت این سهم‌ها میان PriorityLevelConfigurationهای موجود تقسیم می‌شود تا محدودیت اسمی هر سطح بر حسب صندلی به دست آید. به این ترتیب، مدیر کلاستر می‌تواند با راه‌اندازی مجدد kube-apiserver با مقدار متفاوتی برای --max-requests-inflight (یا --max-mutating-requests-inflight)، کل ترافیک یک سرور را افزایش یا کاهش دهد و حداکثر همروندی مجاز همه‌ی PriorityLevelConfigurationها نیز به همان نسبت بالا (یا پایین) می‌رود.

احتیاط:

در نسخه‌های پیش از v1beta3، فیلد مربوط در PriorityLevelConfiguration به جای «سهم‌های همروندی اسمی»، «سهم‌های همروندی تضمین‌شده» (assured concurrency shares) نام دارد. همچنین در نسخه‌ی 1.25 کوبرنتیز و نسخه‌های پیش از آن، هیچ تنظیم دوره‌ای وجود نداشت و محدودیت‌های اسمی/تضمین‌شده همیشه بدون تنظیم اعمال می‌شدند.

حدودی که مشخص می‌کنند یک سطح اولویت چه مقدار همروندی می‌تواند قرض بدهد و چه مقدار می‌تواند قرض بگیرد، در PriorityLevelConfiguration به‌صورت درصدی از محدودیت اسمی آن سطح بیان می‌شوند. این مقادیر با ضرب در حاصل تقسیم محدودیت اسمی بر 100.0 و گرد کردن، به تعداد مطلق صندلی‌ها تبدیل می‌شوند. محدودیت همروندیِ پویا‌تنظیم‌شده‌ی یک سطح اولویت محدود است به اینکه میان (الف) کرانی پایین برابر با محدودیت اسمی منهای صندلی‌های قابل قرض دادن آن، و (ب) کرانی بالا برابر با محدودیت اسمی به‌علاوه‌ی صندلی‌هایی که می‌تواند قرض بگیرد، قرار گیرد. در هر تنظیم، محدودیت‌های پویا به این صورت به دست می‌آیند که هر سطح اولویت، صندلی‌های قرض‌داده‌شده‌ای را که اخیراً برایشان تقاضا ایجاد شده است پس می‌گیرد و سپس همه‌ی سطوح اولویت به‌طور مشترک و منصفانه، در محدوده‌ی همان حدودی که شرح داده شد، به تقاضای اخیر صندلی پاسخ می‌دهند.

احتیاط:

با فعال بودن ویژگی اولویت و انصاف، کل محدودیت همروندی سرور برابر با مجموع --max-requests-inflight و --max-mutating-requests-inflight تنظیم می‌شود. دیگر هیچ تمایزی میان درخواست‌های تغییردهنده (mutating) و غیرتغییردهنده گذاشته نمی‌شود؛ اگر می‌خواهید برای یک منبع مشخص با آن‌ها به‌طور جداگانه رفتار کنید، FlowSchemaهای جداگانه‌ای بسازید که به ترتیب با فعل‌های تغییردهنده و غیرتغییردهنده منطبق شوند.

وقتی حجم درخواست‌های ورودی اختصاص‌یافته به یک PriorityLevelConfiguration واحد از سطح همروندی مجاز آن بیشتر شود، فیلد type در مشخصات آن تعیین می‌کند که با درخواست‌های اضافه چه رخ دهد. نوع Reject به این معناست که ترافیک اضافه بلافاصله با خطای HTTP 429 (Too Many Requests) رد می‌شود. نوع Queue به این معناست که درخواست‌های بیش از آستانه در صف قرار می‌گیرند و برای متوازن کردن پیشرفت میان جریان‌های درخواست، از روش‌های شاردینگ درهم و صف‌بندی منصفانه استفاده می‌شود.

پیکربندی صف‌بندی امکان تنظیم الگوریتم صف‌بندی منصفانه را برای یک سطح اولویت فراهم می‌کند. جزئیات این الگوریتم را می‌توانید در پیشنهاد بهبود بخوانید، اما به‌طور خلاصه:

  • افزایش queues نرخ برخورد میان جریان‌های مختلف را به بهای افزایش مصرف حافظه کاهش می‌دهد. مقدار 1 در اینجا عملاً منطق صف‌بندی منصفانه را غیرفعال می‌کند، اما همچنان امکان صف‌بندی درخواست‌ها را حفظ می‌کند.

  • افزایش queueLengthLimit باعث می‌شود انفجارهای بزرگ‌تر ترافیک بدون کنار گذاشتن هیچ درخواستی تحمل شوند، اما به بهای افزایش تأخیر و مصرف حافظه.

  • با تغییر handSize می‌توانید احتمال برخورد میان جریان‌های مختلف و نیز کل همروندی در دسترس یک جریان واحد را در شرایط اضافه‌بار تنظیم کنید.

توجه:

مقدار بزرگ‌تر handSize احتمال برخورد دو جریان مجزا (و در نتیجه توانایی یکی برای ایجاد گرسنگی در دیگری) را کمتر می‌کند، اما احتمال اینکه تعداد اندکی جریان بر apiserver مسلط شوند را بیشتر می‌کند. مقدار بزرگ‌تر handSize همچنین ممکن است میزان تأخیری را که یک جریان پرترافیک واحد می‌تواند ایجاد کند افزایش دهد. حداکثر تعداد درخواست‌های در صفِ ممکن از یک جریان واحد برابر با handSize * queueLengthLimit است.

در ادامه جدولی آمده است که مجموعه‌ای جالب از پیکربندی‌های شاردینگ درهم را نشان می‌دهد. این جدول برای هر پیکربندی، احتمال اینکه یک موش مشخص (جریان کم‌شدت) زیر دست‌وپای فیل‌ها (جریان‌های پرشدت) له شود را برای مجموعه‌ای نمونه از تعداد فیل‌ها نشان می‌دهد. برای دیدن برنامه‌ای که این جدول را محاسبه می‌کند، به https://play.golang.org/p/Gi0PLgVHiUg مراجعه کنید.

آبجکت FlowSchema

هر FlowSchema با برخی از درخواست‌های ورودی تطبیق می‌یابد و آن‌ها را به یک سطح اولویت اختصاص می‌دهد. هر درخواست ورودی با FlowSchemaها سنجیده می‌شود. این سنجش از FlowSchemaهایی آغاز می‌شود که matchingPrecedence آن‌ها از نظر عددی کمترین مقدار را دارد و به‌ترتیب به سمت مقادیر بزرگ‌تر پیش می‌رود. نخستین تطبیق، تعیین‌کننده است.

احتیاط:

برای هر درخواست، تنها نخستین FlowSchema منطبق اهمیت دارد. اگر چند FlowSchema با یک درخواست ورودی منطبق باشند، درخواست بر اساس FlowSchemaای اختصاص داده می‌شود که بالاترین matchingPrecedence را دارد. اگر چند FlowSchema با matchingPrecedence برابر با یک درخواست منطبق باشند، FlowSchemaای انتخاب می‌شود که name آن از نظر ترتیب واژگانی کوچک‌تر است. با این حال، بهتر است به این رفتار تکیه نکنید و در عوض اطمینان حاصل کنید که هیچ دو FlowSchemaای matchingPrecedence یکسانی ندارند.

یک FlowSchema زمانی با درخواستی منطبق است که دست‌کم یکی از rules آن منطبق باشد. یک قاعده زمانی منطبق است که دست‌کم یکی از subjects آن و دست‌کم یکی از resourceRules یا nonResourceRules آن (بسته به اینکه درخواست ورودی مربوط به یک منبع باشد یا یک URL غیرمنبعی) با درخواست منطبق باشند.

برای فیلد name در subjectها، و نیز فیلدهای verbs، apiGroups، resources، namespaces و nonResourceURLs در قواعد منبعی و غیرمنبعی، می‌توان نویسهٔ عام (wildcard) * را تعیین کرد تا با همهٔ مقادیر آن فیلد منطبق شود؛ در عمل، این کار آن فیلد را از فرایند سنجش کنار می‌گذارد.

فیلد distinguisherMethod.type در هر FlowSchema تعیین می‌کند که درخواست‌های منطبق با آن طرح‌واره چگونه به جریان‌ها (flows) تفکیک شوند. مقدار آن می‌تواند ByUser باشد که در این حالت یک کاربر درخواست‌دهنده نمی‌تواند ظرفیت را از دیگر کاربران بگیرد و آن‌ها را دچار گرسنگی کند؛ یا ByNamespace باشد که در این حالت درخواست‌های مربوط به منابع یک فضای نام (namespace) نمی‌توانند ظرفیت را از درخواست‌های مربوط به منابع دیگر فضاهای نام بگیرند؛ یا خالی باشد (یا distinguisherMethod به‌طور کامل حذف شود) که در این حالت همهٔ درخواست‌های منطبق با این FlowSchema بخشی از یک جریان واحد در نظر گرفته می‌شوند. انتخاب درست برای هر FlowSchema به منبع موردنظر و محیط خاص شما بستگی دارد.

پیش‌فرض‌ها

هر kube-apiserver دو نوع آبجکت پیکربندی APF را نگهداری می‌کند: اجباری و پیشنهادی.

آبجکت‌های پیکربندی اجباری

چهار آبجکت پیکربندی اجباری، رفتار محافظتی (guardrail) ثابت و درونی سرور را بازتاب می‌دهند. این همان رفتاری است که سرورها پیش از وجود این آبجکت‌ها دارند، و هنگامی که این آبجکت‌ها وجود دارند، spec آن‌ها همین رفتار را بازتاب می‌دهد. چهار آبجکت اجباری به شرح زیر هستند.

  • سطح اولویت اجباری exempt برای درخواست‌هایی استفاده می‌شود که اصلاً مشمول کنترل جریان نیستند: این درخواست‌ها همواره بی‌درنگ ارسال می‌شوند. آبجکت FlowSchema اجباری exempt همهٔ درخواست‌های گروه system:masters را در این سطح اولویت دسته‌بندی می‌کند. در صورت لزوم، می‌توانید FlowSchemaهای دیگری تعریف کنید که درخواست‌های دیگری را به این سطح اولویت هدایت کنند.

  • سطح اولویت اجباری catch-all همراه با FlowSchema اجباری catch-all استفاده می‌شود تا اطمینان حاصل شود که هر درخواست به نوعی دسته‌بندی می‌شود. معمولاً نباید به این پیکربندی فراگیر تکیه کنید و بهتر است در صورت لزوم، FlowSchema و PriorityLevelConfiguration فراگیر خودتان را ایجاد کنید (یا از سطح اولویت پیشنهادی global-default استفاده کنید که به‌طور پیش‌فرض نصب می‌شود). از آنجا که انتظار نمی‌رود این سطح اولویت در حالت عادی استفاده شود، سطح اولویت اجباری catch-all سهم هم‌روندی بسیار کوچکی دارد و درخواست‌ها را در صف قرار نمی‌دهد.

آبجکت‌های پیکربندی پیشنهادی

مجموعهٔ FlowSchemaها و PriorityLevelConfigurationهای پیشنهادی، پیکربندی پیش‌فرض معقولی را تشکیل می‌دهند. در صورت تمایل می‌توانید این آبجکت‌ها را تغییر دهید و/یا آبجکت‌های پیکربندی دیگری ایجاد کنید. اگر احتمال دارد کلاستر شما با بار سنگینی روبه‌رو شود، باید بررسی کنید که کدام پیکربندی بهترین عملکرد را خواهد داشت.

پیکربندی پیشنهادی، درخواست‌ها را در شش سطح اولویت دسته‌بندی می‌کند:

  • سطح اولویت node-high برای به‌روزرسانی‌های سلامت (health) ارسال‌شده از نودها است.

  • سطح اولویت system برای درخواست‌های غیرمرتبط با سلامت از گروه system:nodes، یعنی kubeletها، است. این اجزا باید بتوانند با سرور API ارتباط برقرار کنند تا بارهای کاری بتوانند روی آن‌ها زمان‌بندی شوند.

  • سطح اولویت leader-election برای درخواست‌های انتخاب رهبر (leader election) از کنترل‌کننده‌های درونی است (به‌ویژه درخواست‌های مربوط به endpoints، configmaps یا leases که از کاربران system:kube-controller-manager یا system:kube-scheduler و حساب‌های سرویس در فضای نام kube-system ارسال می‌شوند). جداسازی این درخواست‌ها از دیگر ترافیک‌ها اهمیت دارد، زیرا شکست در انتخاب رهبر باعث از کار افتادن و راه‌اندازی دوبارهٔ کنترل‌کننده‌ها می‌شود و این امر نیز به‌نوبهٔ خود ترافیک پرهزینه‌تری ایجاد می‌کند، چون کنترل‌کننده‌های جدید باید informerهای خود را همگام‌سازی کنند.

  • سطح اولویت workload-high برای دیگر درخواست‌های کنترل‌کننده‌های درونی است.

  • سطح اولویت workload-low برای درخواست‌های هر حساب سرویس دیگری است که معمولاً همهٔ درخواست‌های کنترل‌کننده‌هایی را که در Podها اجرا می‌شوند، در بر می‌گیرد.

  • سطح اولویت global-default همهٔ ترافیک‌های دیگر را مدیریت می‌کند؛ برای نمونه، فرمان‌های تعاملی kubectl که کاربران فاقد امتیاز ویژه اجرا می‌کنند.

وظیفهٔ FlowSchemaهای پیشنهادی هدایت درخواست‌ها به سطوح اولویت بالا است و در اینجا فهرست نشده‌اند.

نگهداری آبجکت‌های پیکربندی اجباری و پیشنهادی

هر kube-apiserver به‌طور مستقل، آبجکت‌های پیکربندی اجباری و پیشنهادی را با یک رفتار اولیه و یک رفتار دوره‌ای نگهداری می‌کند. از این رو، در شرایطی که سرورهایی با نسخه‌های متفاوت در کنار هم وجود دارند، تا زمانی که سرورها دربارهٔ محتوای درست این آبجکت‌ها دیدگاه‌های متفاوتی داشته باشند، ممکن است این آبجکت‌ها مدام بین حالت‌های مختلف تغییر کنند (thrashing).

هر kube-apiserver ابتدا یک دور نگهداری اولیه روی آبجکت‌های پیکربندی اجباری و پیشنهادی انجام می‌دهد و پس از آن، نگهداری دوره‌ای این آبجکت‌ها را (هر دقیقه یک بار) انجام می‌دهد.

برای آبجکت‌های پیکربندی اجباری، نگهداری شامل اطمینان از وجود آبجکت و، در صورت وجود، داشتن spec درست است. سرور اجازهٔ ایجاد یا به‌روزرسانی با specی را که با رفتار محافظتی سرور ناسازگار باشد، نمی‌دهد.

نگهداری آبجکت‌های پیکربندی پیشنهادی به گونه‌ای طراحی شده است که بتوان spec آن‌ها را بازنویسی کرد. اما حذف این آبجکت‌ها پذیرفته نمی‌شود و فرایند نگهداری، آبجکت را بازمی‌گرداند. اگر به یک آبجکت پیکربندی پیشنهادی نیاز ندارید، باید آن را نگه دارید ولی spec آن را طوری تنظیم کنید که کمترین اثر را داشته باشد. نگهداری آبجکت‌های پیشنهادی همچنین به گونه‌ای طراحی شده است که هنگام عرضهٔ نسخهٔ جدیدی از kube-apiserver، مهاجرت خودکار را پشتیبانی کند، هرچند ممکن است در مدتی که سرورهایی با نسخه‌های مختلف در کنار هم هستند، این آبجکت‌ها مدام بین حالت‌های مختلف تغییر کنند.

نگهداری یک آبجکت پیکربندی پیشنهادی، در صورتی که آبجکت وجود نداشته باشد، شامل ایجاد آن با spec پیشنهادی سرور است. از سوی دیگر، اگر آبجکت از پیش وجود داشته باشد، رفتار نگهداری به این بستگی دارد که کنترل آبجکت در دست kube-apiservers باشد یا کاربران. در حالت نخست، سرور اطمینان حاصل می‌کند که spec آبجکت همان چیزی باشد که سرور پیشنهاد می‌کند؛ در حالت دوم، spec دست‌نخورده باقی می‌ماند.

برای پاسخ به این پرسش که کنترل آبجکت در دست چه کسی است، ابتدا به دنبال یک حاشیه‌نویسی (annotation) با کلید apf.kubernetes.io/autoupdate-spec گشته می‌شود. اگر چنین حاشیه‌نویسی‌ای وجود داشته باشد و مقدار آن true باشد، کنترل آبجکت در دست kube-apiserverها است. اگر چنین حاشیه‌نویسی‌ای وجود داشته باشد و مقدار آن false باشد، کنترل آبجکت در دست کاربران است. اگر هیچ‌یک از این دو شرط برقرار نباشد، فیلد metadata.generation آبجکت بررسی می‌شود. اگر مقدار آن ۱ باشد، کنترل آبجکت در دست kube-apiserverها است؛ در غیر این صورت، کنترل آن در دست کاربران است. این قواعد در نسخهٔ 1.22 معرفی شدند و بررسی metadata.generation در آن‌ها برای مهاجرت از رفتار ساده‌تر پیشین است. کاربرانی که می‌خواهند کنترل یک آبجکت پیکربندی پیشنهادی را در دست داشته باشند، باید حاشیه‌نویسی apf.kubernetes.io/autoupdate-spec آن را روی false تنظیم کنند.

نگهداری یک آبجکت پیکربندی اجباری یا پیشنهادی همچنین شامل اطمینان از این است که آبجکت یک حاشیه‌نویسی apf.kubernetes.io/autoupdate-spec داشته باشد که به‌درستی نشان دهد آیا کنترل آبجکت در دست kube-apiserverها است یا نه.

نگهداری همچنین شامل حذف آبجکت‌هایی است که نه اجباری‌اند و نه پیشنهادی، اما حاشیه‌نویسی apf.kubernetes.io/autoupdate-spec=true دارند.

معافیت درخواست‌های بررسی سلامت از محدودیت هم‌روندی

پیکربندی پیشنهادی هیچ رفتار ویژه‌ای برای درخواست‌های بررسی سلامت که kubeletهای محلی به kube-apiserverها ارسال می‌کنند، در نظر نمی‌گیرد؛ این درخواست‌ها معمولاً از پورت امن استفاده می‌کنند اما هیچ اعتبارنامه‌ای ارائه نمی‌دهند. با پیکربندی پیشنهادی، این درخواست‌ها به FlowSchema global-default و سطح اولویت متناظر آن، یعنی global-default، اختصاص داده می‌شوند؛ جایی که ترافیک‌های دیگر می‌توانند آن‌ها را کنار بزنند.

اگر FlowSchema اضافی زیر را بیفزایید، این درخواست‌ها از محدودسازی نرخ معاف می‌شوند.

احتیاط:

با اعمال این تغییر، هر طرف مهاجمی نیز می‌تواند درخواست‌های بررسی سلامتی را که با این FlowSchema منطبق هستند، با هر حجمی که بخواهد ارسال کند. اگر برای محافظت از سرور API کلاستر خود در برابر ترافیک عمومی اینترنت، از یک فیلتر ترافیک وب یا سازوکار امنیتی خارجی مشابهی استفاده می‌کنید، می‌توانید قواعدی پیکربندی کنید تا هر درخواست بررسی سلامتی را که از بیرون کلاستر شما سرچشمه می‌گیرد، مسدود کنند.

priority-and-fairness/health-for-strangers.yaml
apiVersion: flowcontrol.apiserver.k8s.io/v1
kind: FlowSchema
metadata:
  name: health-for-strangers
spec:
  matchingPrecedence: 1000
  priorityLevelConfiguration:
    name: exempt
  rules:
    - nonResourceRules:
      - nonResourceURLs:
          - "/healthz"
          - "/livez"
          - "/readyz"
        verbs:
          - "*"
      subjects:
        - kind: Group
          group:
            name: "system:unauthenticated"

مشاهده‌پذیری

متریک‌ها

توجه:

در نسخه‌های کوبرنتیز پیش از v1.20، برچسب‌های flow_schema و priority_level به‌طور ناهمگون به ترتیب flowSchema و priorityLevel نام‌گذاری شده بودند. اگر از کوبرنتیز نسخه‌ی v1.19 یا قدیمی‌تر استفاده می‌کنید، به مستندات همان نسخه مراجعه کنید.

وقتی قابلیت اولویت و انصاف API (API Priority and Fairness) را فعال می‌کنید، kube-apiserver متریک‌های بیشتری منتشر می‌کند. با پایش این متریک‌ها می‌توانید بفهمید که آیا پیکربندی شما ترافیک مهم را به‌شکل نامناسبی محدود می‌کند یا نه. همچنین می‌توانید بارهای کاری بدرفتاری را پیدا کنید که ممکن است به سلامت سامانه آسیب بزنند.

سطح بلوغ بتا

  • متریک apiserver_flowcontrol_rejected_requests_total یک بردار شمارنده (counter vector) است که تعداد درخواست‌های ردشده را (به‌صورت تجمعی از زمان راه‌اندازی سرور) نگه می‌دارد. این شمارش بر اساس برچسب‌های flow_schema (که نشان می‌دهد درخواست با کدام FlowSchema تطبیق یافته است)، priority_level (که نشان می‌دهد درخواست به کدام سطح اولویت تخصیص یافته است) و reason تفکیک می‌شود. برچسب reason یکی از مقادیر زیر را دارد:

    • مقدار queue-full، به این معنا که پیش از این، درخواست‌های بسیار زیادی در صف قرار گرفته بودند.
    • مقدار concurrency-limit، به این معنا که PriorityLevelConfiguration طوری پیکربندی شده است که درخواست‌های مازاد را به‌جای قرار دادن در صف، رد کند.
    • مقدار time-out، به این معنا که درخواست هنگام پایان مهلت صف‌نشینی‌اش هنوز در صف بوده است.
    • مقدار cancelled، به این معنا که درخواست قفل پاک‌سازی (purge lock) نداشته و از صف بیرون انداخته شده است.

  • متریک apiserver_flowcontrol_dispatched_requests_total یک بردار شمارنده است که تعداد درخواست‌هایی را که اجرایشان آغاز شده است (به‌صورت تجمعی از زمان راه‌اندازی سرور) نگه می‌دارد و بر اساس flow_schema و priority_level تفکیک می‌شود.

  • متریک apiserver_flowcontrol_current_inqueue_requests یک بردار سنجه (gauge vector) است که تعداد لحظه‌ای درخواست‌های درون صف (و نه در حال اجرا) را نگه می‌دارد و بر اساس priority_level و flow_schema تفکیک می‌شود.

  • متریک apiserver_flowcontrol_current_executing_requests یک بردار سنجه است که تعداد لحظه‌ای درخواست‌های در حال اجرا (و نه منتظر در صف) را نگه می‌دارد و بر اساس priority_level و flow_schema تفکیک می‌شود.

  • متریک apiserver_flowcontrol_current_executing_seats یک بردار سنجه است که تعداد لحظه‌ای صندلی‌های (seat) اشغال‌شده را نگه می‌دارد و بر اساس priority_level و flow_schema تفکیک می‌شود.

  • متریک apiserver_flowcontrol_request_wait_duration_seconds یک بردار هیستوگرام است که مدت زمان ماندن درخواست‌ها در صف را نشان می‌دهد و بر اساس برچسب‌های flow_schema، priority_level و execute تفکیک می‌شود. برچسب execute نشان می‌دهد که آیا اجرای درخواست آغاز شده است یا نه.

توجه:

از آنجا که هر FlowSchema همیشه درخواست‌ها را به یک PriorityLevelConfiguration واحد تخصیص می‌دهد، می‌توانید هیستوگرام‌های همه‌ی FlowSchemaهای مربوط به یک سطح اولویت را با هم جمع کنید تا هیستوگرام مؤثر درخواست‌های تخصیص‌یافته به آن سطح اولویت به دست آید.

  • متریک apiserver_flowcontrol_nominal_limit_seats یک بردار سنجه است که حد هم‌روندی اسمی هر سطح اولویت را نگه می‌دارد. این حد از روی حد هم‌روندی کل سرور API و سهم‌های هم‌روندی اسمی پیکربندی‌شده برای آن سطح اولویت محاسبه می‌شود.

سطح بلوغ آلفا

  • متریک apiserver_current_inqueue_requests یک بردار سنجه است که بیشینه‌های اخیر (high water mark) تعداد درخواست‌های درون صف را نگه می‌دارد و بر اساس برچسبی به نام request_kind گروه‌بندی می‌شود که مقدارش mutating یا readOnly است. این بیشینه‌ها بزرگ‌ترین عدد مشاهده‌شده در آخرین بازه‌ی یک‌ثانیه‌ای کامل‌شده را توصیف می‌کنند. این متریک مکمل بردار سنجه‌ی قدیمی‌تر apiserver_current_inflight_requests است که بیشینه‌ی تعداد درخواست‌های در حال سرویس‌دهی فعال را در آخرین بازه نگه می‌دارد.

  • متریک apiserver_current_inqueue_seats یک بردار سنجه است که برای درخواست‌های درون صف، مجموع بیشترین تعداد صندلی‌ای را که هر درخواست اشغال خواهد کرد نگه می‌دارد و بر اساس برچسب‌هایی به نام flow_schema و priority_level گروه‌بندی می‌شود.

  • متریک apiserver_flowcontrol_read_vs_write_current_requests یک بردار هیستوگرام از مشاهداتی است که در پایان هر نانوثانیه از تعداد درخواست‌ها انجام می‌شود. این مشاهدات بر اساس برچسب‌های phase (با مقادیر waiting و executing) و request_kind (با مقادیر mutating و readOnly) تفکیک می‌شوند. هر مقدار مشاهده‌شده نسبتی بین ۰ و ۱ است که از تقسیم تعداد درخواست‌ها بر حد متناظر تعداد درخواست‌ها به دست می‌آید (حد حجم صف برای حالت انتظار و حد هم‌روندی برای حالت اجرا).

  • متریک apiserver_flowcontrol_request_concurrency_in_use یک بردار سنجه است که تعداد لحظه‌ای صندلی‌های اشغال‌شده را نگه می‌دارد و بر اساس priority_level و flow_schema تفکیک می‌شود.

  • متریک apiserver_flowcontrol_priority_level_request_utilization یک بردار هیستوگرام از مشاهداتی است که در پایان هر نانوثانیه از تعداد درخواست‌ها انجام می‌شود. این مشاهدات بر اساس برچسب‌های phase (با مقادیر waiting و executing) و priority_level تفکیک می‌شوند. هر مقدار مشاهده‌شده نسبتی بین ۰ و ۱ است که از تقسیم تعداد درخواست‌ها بر حد متناظر تعداد درخواست‌ها به دست می‌آید (حد حجم صف برای حالت انتظار و حد هم‌روندی برای حالت اجرا).

  • متریک apiserver_flowcontrol_priority_level_seat_utilization یک بردار هیستوگرام از مشاهداتی است که در پایان هر نانوثانیه از میزان بهره‌برداری از حد هم‌روندی یک سطح اولویت انجام می‌شود و بر اساس priority_level تفکیک می‌شود. این میزان بهره‌برداری برابر با کسر (تعداد صندلی‌های اشغال‌شده) / (حد هم‌روندی) است. این متریک همه‌ی مراحل اجرای همه‌ی درخواست‌ها را در نظر می‌گیرد (هم مرحله‌ی عادی و هم تأخیر اضافه در پایان یک عملیات نوشتن که برای پوشش کار اطلاع‌رسانی متناظر آن است)، به‌جز درخواست‌های WATCH؛ برای این درخواست‌ها فقط مرحله‌ی آغازین در نظر گرفته می‌شود که اعلان‌های مربوط به آبجکت‌های ازپیش‌موجود را ارسال می‌کند. هر هیستوگرام در این بردار برچسب phase: executing را نیز دارد (برای مرحله‌ی انتظار هیچ حدی برای صندلی‌ها وجود ندارد).

  • متریک apiserver_flowcontrol_request_queue_length_after_enqueue یک بردار هیستوگرام از طول صف‌هاست که بر اساس priority_level و flow_schema تفکیک می‌شود و نمونه‌برداری آن به‌وسیله‌ی درخواست‌های واردشده به صف انجام می‌شود. هر درخواستی که وارد صف می‌شود، یک نمونه به هیستوگرام مربوط به خود اضافه می‌کند که طول صف را بلافاصله پس از افزوده شدن آن درخواست گزارش می‌دهد. توجه کنید که آماری که به این روش به دست می‌آید با آمار یک نمونه‌گیری بی‌طرفانه متفاوت است.

  • متریک apiserver_flowcontrol_work_estimated_seats یک بردار هیستوگرام از تعداد صندلی‌های تخمینی مرتبط با درخواست‌هاست (بیشینه‌ی مرحله‌ی آغازین و پایانی اجرا) و بر اساس flow_schema و priority_level تفکیک می‌شود.

  • متریک apiserver_flowcontrol_request_dispatch_no_accommodation_total یک بردار شمارنده است که تعداد رویدادهایی را می‌شمارد که در اصل می‌توانستند به ارسال یک درخواست برای اجرا بینجامند، اما به دلیل کمبود هم‌روندی در دسترس چنین نشده است. این شمارش بر اساس flow_schema و priority_level تفکیک می‌شود.

  • متریک apiserver_flowcontrol_epoch_advance_total یک بردار شمارنده است که تعداد تلاش‌ها برای عقب بردن شاخص پیشرفت یک سطح اولویت به‌منظور جلوگیری از سرریز عددی را می‌شمارد و بر اساس priority_level و success گروه‌بندی می‌شود.

روش‌های خوب برای استفاده از اولویت و انصاف API

وقتی یک سطح اولویت از هم‌روندی مجاز خود فراتر می‌رود، ممکن است تأخیر درخواست‌ها افزایش یابد یا درخواست‌ها با خطای HTTP 429 (Too Many Requests) کنار گذاشته شوند. برای جلوگیری از این پیامدهای جانبی APF، می‌توانید بار کاری خود را تغییر دهید یا تنظیمات APF را طوری اصلاح کنید که صندلی‌های کافی برای سرویس‌دهی به درخواست‌هایتان در دسترس باشد.

برای اینکه بفهمید آیا درخواست‌ها به دلیل APF رد می‌شوند یا نه، متریک‌های زیر را بررسی کنید:

  • متریک apiserver_flowcontrol_rejected_requests_total: تعداد کل درخواست‌های ردشده به تفکیک هر FlowSchema و PriorityLevelConfiguration.
  • متریک apiserver_flowcontrol_current_inqueue_requests: تعداد فعلی درخواست‌های درون صف به تفکیک هر FlowSchema و PriorityLevelConfiguration.
  • متریک apiserver_flowcontrol_request_wait_duration_seconds: تأخیری که به درخواست‌های منتظر در صف‌ها افزوده می‌شود.
  • متریک apiserver_flowcontrol_priority_level_seat_utilization: میزان بهره‌برداری از صندلی‌ها به تفکیک هر PriorityLevelConfiguration.

تغییرات بار کاری {#good-practice-workload-modifications}

برای جلوگیری از اینکه درخواست‌ها به دلیل APF در صف بمانند و تأخیرشان افزایش یابد یا کنار گذاشته شوند، می‌توانید درخواست‌های خود را به روش‌های زیر بهینه کنید:

  • کاهش نرخ اجرای درخواست‌ها. هرچه تعداد درخواست‌ها در یک بازه‌ی زمانی ثابت کمتر باشد، در هر لحظه به صندلی‌های کمتری نیاز خواهد بود.
  • پرهیز از ارسال هم‌زمان تعداد زیادی درخواست پرهزینه. می‌توان درخواست‌ها را طوری بهینه کرد که صندلی‌های کمتری مصرف کنند یا تأخیر کمتری داشته باشند تا این صندلی‌ها را مدت کوتاه‌تری در اختیار بگیرند. درخواست‌های list بسته به تعداد آبجکت‌هایی که در طول درخواست واکشی می‌شوند، ممکن است بیش از ۱ صندلی اشغال کنند. اگر تعداد آبجکت‌های بازیابی‌شده در یک درخواست list را محدود کنید (برای مثال با صفحه‌بندی)، در مجموع صندلی‌های کمتری در مدت کوتاه‌تری مصرف می‌شود. افزون بر این، جایگزین کردن درخواست‌های list با درخواست‌های watch به سهم‌های هم‌روندی کل کمتری نیاز دارد، زیرا درخواست‌های watch در طول موج آغازین اعلان‌هایشان فقط ۱ صندلی اشغال می‌کنند. اگر در نسخه‌ی 1.27 و بعد از آن از فهرست‌های جریانی (streaming list) استفاده کنید، درخواست‌های watch در موج آغازین اعلان‌هایشان به همان تعداد صندلیِ یک درخواست list را اشغال می‌کنند، زیرا کل وضعیت مجموعه باید به‌صورت جریانی ارسال شود. توجه کنید که در هر دو حالت، یک درخواست watch پس از این مرحله‌ی آغازین هیچ صندلی‌ای در اختیار نمی‌گیرد.

به خاطر داشته باشید که درخواست‌های در صف مانده یا ردشده به دست APF ممکن است یا ناشی از افزایش تعداد درخواست‌ها باشند یا ناشی از افزایش تأخیر درخواست‌های موجود. برای مثال، اگر اجرای درخواست‌هایی که معمولاً ۱ ثانیه طول می‌کشند به ۶۰ ثانیه برسد، ممکن است APF شروع به رد کردن درخواست‌ها کند، چون این افزایش تأخیر باعث می‌شود درخواست‌ها صندلی‌ها را مدتی طولانی‌تر از حد معمول اشغال کنند. اگر APF بدون تغییر محسوسی در بار کاری، درخواست‌ها را در چند سطح اولویت رد کند، ممکن است مشکلی بنیادی در کارایی control plane وجود داشته باشد، نه در بار کاری یا تنظیمات APF.

تنظیمات اولویت و انصاف {#good-practice-apf-settings}

همچنین می‌توانید آبجکت‌های پیش‌فرض FlowSchema و PriorityLevelConfiguration را تغییر دهید یا آبجکت‌های جدیدی از این نوع‌ها بسازید تا با بار کاری شما سازگاری بیشتری داشته باشند.

تنظیمات APF را می‌توان برای اهداف زیر تغییر داد:

  • اختصاص صندلی‌های بیشتر به درخواست‌های با اولویت بالا.
  • جداسازی درخواست‌های غیرضروری یا پرهزینه‌ای که اگر یک سطح هم‌روندی با جریان‌های دیگر مشترک باشد، آن را با کمبود منبع مواجه می‌کنند.

اختصاص صندلی‌های بیشتر به درخواست‌های با اولویت بالا

  1. در صورت امکان، می‌توانید با افزایش مقادیر فلگ‌های max-requests-inflight و max-mutating-requests-inflight، تعداد صندلی‌های در دسترس در همه‌ی سطوح اولویت را برای یک kube-apiserver مشخص افزایش دهید. راه دیگر، مقیاس‌دهی افقی تعداد نمونه‌های kube-apiserver است. به شرط آنکه توزیع بار درخواست‌ها به‌اندازه‌ی کافی انجام شود، این کار هم‌روندی کل هر سطح اولویت را در سراسر کلاستر افزایش می‌دهد.
  2. می‌توانید یک FlowSchema جدید بسازید که به یک PriorityLevelConfiguration با سطح هم‌روندی بالاتر ارجاع دهد. این PriorityLevelConfiguration جدید می‌تواند یکی از سطوح موجود باشد یا سطحی تازه با مجموعه‌ی سهم‌های هم‌روندی اسمی خودش. برای مثال، می‌توان یک FlowSchema جدید تعریف کرد تا PriorityLevelConfiguration درخواست‌های شما را از global-default به workload-low تغییر دهد و تعداد صندلی‌های در دسترس کاربرتان افزایش یابد. ساختن یک PriorityLevelConfiguration جدید، تعداد صندلی‌های اختصاص‌یافته به سطوح موجود را کاهش می‌دهد. به یاد داشته باشید که برای ویرایش یک FlowSchema یا PriorityLevelConfiguration پیش‌فرض، باید حاشیه‌نویسی (annotation) apf.kubernetes.io/autoupdate-spec را روی false تنظیم کنید.
  3. همچنین می‌توانید مقدار NominalConcurrencyShares را برای PriorityLevelConfiguration‌ای که به درخواست‌های با اولویت بالای شما سرویس می‌دهد افزایش دهید. راه دیگر این است که در نسخه‌ی 1.26 و بعد از آن، مقدار LendablePercent را برای سطوح اولویت رقیب افزایش دهید تا سطح اولویت موردنظر، مخزن بزرگ‌تری از صندلی‌ها برای قرض گرفتن در اختیار داشته باشد.

جلوگیری از اینکه درخواست‌های غیرضروری جریان‌های دیگر را با کمبود منبع مواجه کنند

برای جداسازی درخواست‌ها، می‌توانید یک FlowSchema بسازید که subject آن با کاربری که این درخواست‌ها را ارسال می‌کند تطبیق یابد، یا FlowSchema‌ای بسازید که با ماهیت خود درخواست (متناظر با resourceRules) تطبیق یابد. سپس می‌توانید این FlowSchema را به یک PriorityLevelConfiguration با سهم کمی از صندلی‌ها نگاشت کنید.

برای مثال، فرض کنید درخواست‌های list رویدادها از سوی Podهایی که در فضای نام default اجرا می‌شوند، هر کدام ۱۰ صندلی مصرف می‌کنند و اجرایشان ۱ دقیقه طول می‌کشد. برای جلوگیری از اینکه این درخواست‌های پرهزینه بر درخواست‌های Podهای دیگری که از FlowSchema موجود service-accounts استفاده می‌کنند اثر بگذارند، می‌توانید FlowSchema زیر را اعمال کنید تا این فراخوانی‌های list از درخواست‌های دیگر جدا شوند.

نمونه‌ای از آبجکت FlowSchema برای جداسازی درخواست‌های list رویدادها:

priority-and-fairness/list-events-default-service-account.yaml
apiVersion: flowcontrol.apiserver.k8s.io/v1
kind: FlowSchema
metadata:
  name: list-events-default-service-account
spec:
  distinguisherMethod:
    type: ByUser
  matchingPrecedence: 8000
  priorityLevelConfiguration:
    name: catch-all
  rules:
    - resourceRules:
      - apiGroups:
          - '*'
        namespaces:
          - default
        resources:
          - events
        verbs:
          - list
      subjects:
        - kind: ServiceAccount
          serviceAccount:
            name: default
            namespace: default
  • این FlowSchema همه‌ی فراخوانی‌های list رویدادها را که حساب سرویس default در فضای نام default انجام می‌دهد دربرمی‌گیرد. مقدار تقدم تطبیق ۸۰۰۰ کمتر از مقدار ۹۰۰۰ است که FlowSchema موجود service-accounts از آن استفاده می‌کند؛ بنابراین این فراخوانی‌های list رویدادها به‌جای service-accounts با list-events-default-service-account تطبیق می‌یابند.
  • برای جداسازی این درخواست‌ها از PriorityLevelConfiguration با نام catch-all استفاده می‌شود. سطح اولویت catch-all سهم هم‌روندی بسیار کوچکی دارد و درخواست‌ها را در صف قرار نمی‌دهد.

گام‌های بعدی

  • برای آشنایی بیشتر با عیب‌یابی، می‌توانید مستند مرجع کنترل جریان را ببینید.
  • برای اطلاعات پیش‌زمینه درباره‌ی جزئیات طراحی اولویت و انصاف API، پیشنهاد بهبود را ببینید.
  • می‌توانید پیشنهادها و درخواست‌های قابلیت خود را از طریق SIG API Machinery یا کانال اسلک این قابلیت مطرح کنید.
