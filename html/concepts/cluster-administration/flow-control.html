اولویت و انصاف API

وضعیت ویژگی: Kubernetes v1.29 [stable] (پایدار)

کنترل رفتار سرور API کوبرنتیز در شرایط بار بیش‌ازحد، یکی از وظایف کلیدی مدیران کلاستر است. kube-apiserver چند سازوکار کنترلی در اختیار دارد (مانند فلگ‌های خط فرمان --max-requests-inflight و --max-mutating-requests-inflight) تا میزان کار در حال انجامی را که پذیرفته می‌شود محدود کند و از سرریز شدن درخواست‌های ورودی و در نتیجه overload شدن و حتی از کار افتادن احتمالی سرور API جلوگیری نماید؛ اما این فلگ‌ها برای اطمینان از عبور مهم‌ترین درخواست‌ها در دوره‌های ترافیک بالا کافی نیستند.

ویژگی اولویت و انصاف API (API Priority and Fairness یا APF) جایگزینی است که محدودیت‌های max-inflight یادشده را بهبود می‌بخشد. APF درخواست‌ها را با دقت بیشتری دسته‌بندی و ایزوله می‌کند. همچنین مقدار محدودی صف‌بندی را معرفی می‌کند تا در موارد افزایش ناگهانی و بسیار کوتاه‌مدت ترافیک، هیچ درخواستی رد نشود. درخواست‌ها با استفاده از یک تکنیک صف‌بندی منصفانه از صف‌ها ارسال می‌شوند تا برای مثال یک کنترل‌کننده بدرفتار نتواند سایرین را (حتی در همان سطح اولویت) دچار قحطی منابع (starvation) کند.

این ویژگی طوری طراحی شده است که با کنترل‌کننده‌های استاندارد که از informerها استفاده می‌کنند و به شکست درخواست‌های API با exponential back-off واکنش نشان می‌دهند، و همچنین با سایر کلاینت‌هایی که به همین شیوه عمل می‌کنند، به خوبی کار کند.

احتیاط:

برخی درخواست‌ها که «طولانی‌مدت» دسته‌بندی می‌شوند—مانند اجرای دستور از راه دور یا دنبال کردن لاگ‌ها—مشمول فیلتر اولویت و انصاف API نمی‌شوند. این موضوع درباره فلگ --max-requests-inflight نیز در حالتی که ویژگی اولویت و انصاف API فعال نباشد صادق است. اولویت و انصاف API بر درخواست‌های watch اعمال می‌شود. وقتی اولویت و انصاف API غیرفعال باشد، درخواست‌های watch مشمول محدودیت --max-requests-inflight نمی‌شوند.

فعال/غیرفعال کردن اولویت و انصاف API {#enabling-disabling-api-priority-and-fairness}

ویژگی اولویت و انصاف API با یک فلگ خط فرمان کنترل می‌شود و به‌طور پیش‌فرض فعال است. برای توضیح کلی گزینه‌های خط فرمان موجود در kube-apiserver و نحوه فعال و غیرفعال کردن آن‌ها، گزینه‌ها را ببینید. نام گزینه خط فرمان برای APF برابر "--enable-priority-and-fairness" است. این ویژگی همچنین شامل یک گروه API است که دارای این موارد است: (الف) نسخه پایدار v1 که در 1.29 معرفی شد و به‌طور پیش‌فرض فعال است؛ (ب) نسخه v1beta3 که به‌طور پیش‌فرض فعال است و در v1.29 منسوخ شد. می‌توانید نسخه بتای گروه API یعنی v1beta3 را با افزودن فلگ‌های خط فرمان زیر به فراخوانی kube-apiserver غیرفعال کنید:

kube-apiserver \
--runtime-config=flowcontrol.apiserver.k8s.io/v1beta3=false \
 # …and other flags as usual

فلگ خط فرمان --enable-priority-and-fairness=false ویژگی اولویت و انصاف API را غیرفعال می‌کند.

سناریوهای بازگشتی سرور {#recursive-server-scenarios}

اولویت و انصاف API باید در سناریوهای بازگشتی سرور با دقت به کار گرفته شود. این‌ها سناریوهایی هستند که در آن‌ها یک سرور A هنگام پاسخ‌دهی به یک درخواست، یک درخواست فرعی به سرور B ارسال می‌کند. ممکن است سرور B نیز خود یک فراخوانی فرعی دیگر را به سرور A بازگرداند. در شرایطی که کنترل اولویت و انصاف هم بر درخواست اصلی و هم بر برخی درخواست‌های فرعی اعمال شود، صرف‌نظر از اینکه بازگشت تا چه عمقی پیش برود، خطر وارونگی اولویت (priority inversion) و/یا بن‌بست (deadlock) وجود دارد.

یک نمونه از بازگشت زمانی است که kube-apiserver یک فراخوانی admission webhook به سرور B ارسال می‌کند و سرور B هنگام پاسخ به آن فراخوانی، یک درخواست فرعی دیگر را به kube-apiserver ارسال می‌کند. نمونه دیگر بازگشت زمانی است که یک آبجکت APIService به kube-apiserver دستور می‌دهد درخواست‌های مربوط به یک گروه API مشخص را به یک سرور خارجی سفارشی B واگذار کند (این یکی از مواردی است که «aggregation» نامیده می‌شود).

وقتی بدانیم درخواست اصلی به یک سطح اولویت مشخص تعلق دارد و درخواست‌های فرعی تحت کنترل در سطوح اولویت بالاتر دسته‌بندی شوند، این یک راه‌حل ممکن است. وقتی درخواست‌های اصلی می‌توانند به هر سطح اولویتی تعلق داشته باشند، درخواست‌های فرعی تحت کنترل باید از محدودیت اولویت و انصاف معاف شوند. یک روش برای این کار استفاده از آبجکت‌هایی است که دسته‌بندی و نحوه رسیدگی را پیکربندی می‌کنند و در ادامه بحث می‌شوند. روش دیگر غیرفعال کردن کامل اولویت و انصاف روی سرور B با استفاده از تکنیک‌هایی است که در بالا گفته شد. روش سوم، که وقتی سرور B همان kube-apiserver نیست ساده‌ترین روش است، ساخت سرور B با اولویت و انصاف غیرفعال در سطح کد است.

مفاهیم {#concepts}

چند ویژگی متمایز در ویژگی اولویت و انصاف API نقش دارند. درخواست‌های ورودی با استفاده از FlowSchemaها بر اساس ویژگی‌های درخواست دسته‌بندی می‌شوند و به سطوح اولویت اختصاص می‌یابند. سطوح اولویت با حفظ محدودیت‌های همروندی (concurrency) مجزا، درجه‌ای از ایزولگی ایجاد می‌کنند، به‌طوری که درخواست‌های اختصاص‌یافته به سطوح اولویت مختلف نمی‌توانند یکدیگر را دچار قحطی منابع کنند. در داخل یک سطح اولویت، یک الگوریتم صف‌بندی منصفانه مانع از آن می‌شود که درخواست‌های جریان‌های (flows) مختلف یکدیگر را دچار قحطی منابع کنند، و اجازه می‌دهد درخواست‌ها صف‌بندی شوند تا ترافیک ناگهانی (bursty) وقتی میانگین بار به‌طور قابل قبولی پایین است، باعث شکست درخواست‌ها نشود.

سطوح اولویت {#priority-levels}

بدون فعال بودن APF، همروندی کلی در سرور API با فلگ‌های kube-apiserver یعنی --max-requests-inflight و --max-mutating-requests-inflight محدود می‌شود. با فعال بودن APF، محدودیت‌های همروندی تعریف‌شده توسط این فلگ‌ها با هم جمع می‌شوند و سپس حاصل‌جمع میان مجموعه‌ای پیکربندی‌پذیر از سطوح اولویت تقسیم می‌شود. هر درخواست ورودی به یک سطح اولویت اختصاص می‌یابد و هر سطح اولویت فقط به تعداد درخواست‌های همزمانی را ارسال می‌کند که محدودیت خاص خودش اجازه می‌دهد.

برای مثال، پیکربندی پیش‌فرض شامل سطوح اولویت جداگانه برای درخواست‌های انتخاب رهبر (leader election)، درخواست‌های کنترل‌کننده‌های داخلی و درخواست‌های Podها است. این بدان معناست که یک Pod بدرفتار که سرور API را با درخواست‌ها سیل‌آسا پر می‌کند، نمی‌تواند مانع موفقیت انتخاب رهبر یا اقدامات کنترل‌کننده‌های داخلی شود.

محدودیت‌های همروندی سطوح اولویت به‌صورت دوره‌ای تنظیم می‌شوند، تا سطوح اولویتی که کم‌استفاده‌اند بتوانند به‌طور موقت همروندی را به سطوح پرمصرف قرض دهند. این محدودیت‌ها بر پایه محدودیت‌های اسمی (nominal) و کران‌هایی هستند که تعیین می‌کنند یک سطح اولویت چه مقدار همروندی را می‌تواند قرض دهد و چه مقدار می‌تواند قرض بگیرد، و همه آن‌ها از آبجکت‌های پیکربندی که در ادامه ذکر می‌شوند به دست می‌آیند.

صندلی‌های اشغال‌شده توسط یک درخواست {#seats-occupied-by-a-request}

توضیح بالا درباره مدیریت همروندی، روایت پایه است. درخواست‌ها مدت‌زمان‌های متفاوتی دارند اما هنگام مقایسه با محدودیت همروندی یک سطح اولویت، در هر لحظه یکسان شمرده می‌شوند. در روایت پایه، هر درخواست یک واحد همروندی را اشغال می‌کند. واژه «صندلی» (seat) برای اشاره به یک واحد همروندی به کار می‌رود و الهام‌گرفته از این است که هر مسافر قطار یا هواپیما یکی از تعداد ثابت صندلی‌ها را اشغال می‌کند.

اما برخی درخواست‌ها بیش از یک صندلی را اشغال می‌کنند. برخی از این‌ها درخواست‌های list هستند که سرور برآورد می‌کند تعداد زیادی آبجکت برمی‌گردانند. مشخص شده است که این درخواست‌ها بار فوق‌العاده سنگینی بر سرور وارد می‌کنند. به همین دلیل، سرور تعداد آبجکت‌هایی را که برگردانده خواهند شد برآورد می‌کند و درخواست را اشغال‌کننده تعداد صندلی‌هایی متناسب با آن عدد برآوردشده در نظر می‌گیرد.

تنظیمات زمان اجرا برای درخواست‌های watch {#execution-time-tweaks-for-watch-requests}

اولویت و انصاف API درخواست‌های watch را مدیریت می‌کند، اما این کار شامل چند انحراف دیگر از رفتار پایه است. مورد اول به این مربوط است که یک درخواست watch تا چه مدتی صندلی خود را اشغال‌شده در نظر گرفته می‌شود. بسته به پارامترهای درخواست، پاسخ به یک درخواست watch ممکن است با اعلان‌های create برای همه آبجکت‌های از پیش موجود مرتبط آغاز شود یا نشود. اولویت و انصاف API یک درخواست watch را پس از پایان آن موج اولیه اعلان‌ها، در صورت وجود، از صندلی خود فارغ می‌داند.

اعلان‌های عادی هر بار که سرور از ایجاد/به‌روزرسانی/حذف یک آبجکت مطلع می‌شود، در یک موج همروند به همه جریان‌های پاسخ watch مرتبط ارسال می‌شوند. برای محاسبه این کار، اولویت و انصاف API فرض می‌کند هر درخواست نوشتن پس از پایان نوشتن واقعی، مدت زمان اضافی‌ای را نیز صندلی‌ها را اشغال می‌کند. سرور تعداد اعلان‌هایی را که باید ارسال شوند برآورد می‌کند و تعداد صندلی‌ها و مدت اشغال صندلی درخواست نوشتن را طوری تنظیم می‌کند که این کار اضافی را نیز در بر بگیرد.

صف‌بندی {#queuing}

حتی در داخل یک سطح اولویت نیز ممکن است تعداد زیادی منبع متمایز ترافیک وجود داشته باشد. در شرایط بار بیش‌ازحد، جلوگیری از اینکه یک جریان از درخواست‌ها سایرین را دچار قحطی منابع کند ارزشمند است (به‌ویژه در حالت نسبتاً رایج یک کلاینت معیوب که kube-apiserver را با درخواست‌ها پر می‌کند؛ در حالت ایده‌آل آن کلاینت معیوب تأثیر قابل‌اندازه‌گیری چندانی بر سایر کلاینت‌ها نخواهد داشت). این موضوع با استفاده از یک الگوریتم صف‌بندی منصفانه برای پردازش درخواست‌هایی که به همان سطح اولویت اختصاص یافته‌اند مدیریت می‌شود. هر درخواست به یک جریان (flow) اختصاص می‌یابد که با نام FlowSchema منطبق به‌علاوه یک شناسه‌ی تمایز جریان (flow distinguisher) مشخص می‌شود — که یا کاربر درخواست‌کننده است، یا فضای نام منبع هدف، یا هیچ‌چیز — و سیستم تلاش می‌کند وزن تقریباً برابری به درخواست‌های جریان‌های مختلف در یک سطح اولویت بدهد. برای فعال کردن رسیدگی متمایز به نمونه‌های متمایز، کنترل‌کننده‌هایی که نمونه‌های متعدد دارند باید با نام‌های کاربری متمایز احراز هویت شوند

پس از دسته‌بندی یک درخواست در یک جریان، ویژگی اولویت و انصاف API ممکن است درخواست را به یک صف اختصاص دهد. این اختصاص از تکنیکی به نام shuffle sharding استفاده می‌کند که استفاده نسبتاً کارآمدی از صف‌ها می‌کند تا جریان‌های کم‌شدت را از جریان‌های پرشدت مجزا کند.

جزئیات الگوریتم صف‌بندی برای هر سطح اولویت قابل تنظیم است و به مدیران اجازه می‌دهد میان مصرف حافظه، انصاف (ویژگی‌ای که بر اساس آن جریان‌های مستقل همگی وقتی ترافیک کل از ظرفیت فراتر می‌رود پیشرفت می‌کنند)، تحمل ترافیک ناگهانی و تأخیر اضافی ناشی از صف‌بندی، موازنه برقرار کنند.

درخواست‌های معاف {#exempt-requests}

برخی درخواست‌ها آن‌قدر مهم تلقی می‌شوند که مشمول هیچ‌یک از محدودیت‌های اعمال‌شده توسط این ویژگی نمی‌شوند. این معافیت‌ها مانع از آن می‌شوند که یک پیکربندی کنترل جریان نادرست، سرور API را به‌طور کامل از کار بیندازد.

منابع {#resources}

API کنترل جریان شامل دو نوع منبع است. PriorityLevelConfigurationها سطوح اولویت موجود، سهم هر یک از بودجه همروندی در دسترس که می‌تواند مدیریت کند را تعریف می‌کنند و امکان تنظیم دقیق رفتار صف‌بندی را فراهم می‌آورند. FlowSchemaها برای دسته‌بندی درخواست‌های ورودی منفرد به کار می‌روند و هر یک را با یک PriorityLevelConfiguration منطبق می‌کنند.

PriorityLevelConfiguration {#prioritylevelconfiguration}

یک PriorityLevelConfiguration نمایانگر یک سطح اولویت است. هر PriorityLevelConfiguration یک محدودیت مستقل بر تعداد درخواست‌های در حال انجام و محدودیت‌هایی بر تعداد درخواست‌های صف‌شده دارد.

محدودیت همروندی اسمی برای یک PriorityLevelConfiguration بر حسب تعداد مطلق صندلی‌ها مشخص نمی‌شود، بلکه بر حسب «سهم‌های همروندی اسمی» (nominal concurrency shares) بیان می‌شود. محدودیت کل همروندی برای سرور API متناسب با این سهم‌ها میان PriorityLevelConfigurationهای موجود توزیع می‌شود تا محدودیت اسمی هر سطح بر حسب صندلی به دست آید. این امر به مدیر کلاستر اجازه می‌دهد با راه‌اندازی مجدد kube-apiserver با مقدار متفاوتی برای --max-requests-inflight (یا --max-mutating-requests-inflight)، مقدار کل ترافیک به سمت یک سرور را افزایش یا کاهش دهد، و همه PriorityLevelConfigurationها شاهد افزایش (یا کاهش) حداکثر همروندی مجاز خود به یک نسبت یکسان خواهند بود.

احتیاط:

در نسخه‌های پیش از v1beta3، فیلد مرتبط در PriorityLevelConfiguration به‌جای "nominal concurrency shares" با نام "assured concurrency shares" شناخته می‌شود. همچنین در نسخه 1.25 کوبرنتیز و نسخه‌های قبل از آن، تنظیم دوره‌ای وجود نداشت: محدودیت‌های اسمی/تضمین‌شده همواره بدون تنظیم اعمال می‌شدند.

کران‌های مربوط به اینکه یک سطح اولویت چه مقدار همروندی را می‌تواند قرض دهد و چه مقدار می‌تواند قرض بگیرد، در PriorityLevelConfiguration به‌صورت درصدی از محدودیت اسمی آن سطح بیان می‌شوند. این مقادیر با ضرب در محدودیت اسمی تقسیم بر 100.0 و گرد کردن، به تعداد مطلق صندلی‌ها تبدیل می‌شوند. محدودیت همروندی تنظیم‌شده‌ی پویای یک سطح اولویت چنان محدود می‌شود که میان (الف) یک کران پایین برابر با محدودیت اسمی آن منهای صندلی‌های قابل قرض‌دادن آن و (ب) یک کران بالا برابر با محدودیت اسمی آن به‌علاوه صندلی‌هایی که می‌تواند قرض بگیرد قرار گیرد. در هر تنظیم، محدودیت‌های پویا به این صورت به دست می‌آیند که هر سطح اولویت صندلی‌های قرض‌داده‌شده‌ای را که اخیراً برایشان تقاضا پدید آمده بازپس می‌گیرد و سپس به‌طور مشترک و منصفانه به تقاضای اخیر صندلی در سطوح اولویت، در چارچوب کران‌هایی که توضیح داده شد، پاسخ می‌دهد.

احتیاط:

با فعال بودن ویژگی اولویت و انصاف، محدودیت کل همروندی برای سرور برابر با مجموع --max-requests-inflight و --max-mutating-requests-inflight تعیین می‌شود. دیگر هیچ تمایزی میان درخواست‌های تغییردهنده و غیرتغییردهنده قائل نمی‌شود؛ اگر می‌خواهید برای یک منبع مشخص با آن‌ها به‌طور جداگانه رفتار کنید، FlowSchemaهای جداگانه‌ای بسازید که به‌ترتیب با فعل‌های (verbs) تغییردهنده و غیرتغییردهنده تطبیق داشته باشند.

وقتی حجم درخواست‌های ورودی اختصاص‌یافته به یک PriorityLevelConfiguration بیش از سطح همروندی مجاز آن باشد، فیلد type در مشخصات آن تعیین می‌کند با درخواست‌های اضافی چه اتفاقی می‌افتد. نوع Reject به این معناست که ترافیک مازاد بلافاصله با خطای HTTP 429 (Too Many Requests) رد می‌شود. نوع Queue به این معناست که درخواست‌های بالاتر از آستانه صف‌بندی می‌شوند و از تکنیک‌های shuffle sharding و صف‌بندی منصفانه برای ایجاد توازن در پیشرفت میان جریان‌های درخواست استفاده می‌شود.

پیکربندی صف‌بندی امکان تنظیم الگوریتم صف‌بندی منصفانه را برای یک سطح اولویت فراهم می‌کند. جزئیات الگوریتم را می‌توانید در پیشنهاد بهبود (enhancement proposal) مطالعه کنید، اما به‌طور خلاصه:

  • افزایش queues نرخ برخورد میان جریان‌های مختلف را کاهش می‌دهد، به بهای افزایش مصرف حافظه. مقدار 1 در اینجا عملاً منطق صف‌بندی منصفانه را غیرفعال می‌کند، اما همچنان اجازه می‌دهد درخواست‌ها صف‌بندی شوند.

  • افزایش queueLengthLimit امکان تحمل موج‌های بزرگ‌تر ترافیک را بدون حذف هیچ درخواستی فراهم می‌کند، به بهای افزایش تأخیر و مصرف حافظه.

  • تغییر handSize به شما اجازه می‌دهد احتمال برخورد میان جریان‌های مختلف و همروندی کلی در دسترس یک جریان واحد را در شرایط بار بیش‌ازحد تنظیم کنید.

توجه:

handSize بزرگ‌تر احتمال برخورد دو جریان منفرد را کمتر می‌کند (و در نتیجه احتمال اینکه یکی بتواند دیگری را دچار قحطی منابع کند)، اما احتمال اینکه تعداد اندکی از جریان‌ها بتوانند بر apiserver مسلط شوند را بیشتر می‌کند. handSize بزرگ‌تر همچنین به‌طور بالقوه میزان تأخیری را که یک جریان پرترافیک واحد می‌تواند ایجاد کند افزایش می‌دهد. حداکثر تعداد درخواست‌های صف‌شده ممکن از یک جریان واحد برابر handSize * queueLengthLimit است.

FlowSchema

یک FlowSchema بخشی از درخواست‌های ورودی را تطبیق می‌دهد و آن‌ها را به یک سطح اولویت (priority level) اختصاص می‌دهد. هر درخواست ورودی با FlowSchemaها سنجیده می‌شود؛ این کار از FlowSchemaهایی که matchingPrecedence عددی کمتری دارند آغاز می‌شود و به‌تدریج به سمت مقادیر بالاتر ادامه می‌یابد. نخستین تطبیق برنده است.

احتیاط:

برای هر درخواست فقط نخستین FlowSchema منطبق اهمیت دارد. اگر چند FlowSchema با یک درخواست ورودی تطبیق پیدا کنند، درخواست بر اساس همان FlowSchema‌ای اختصاص می‌یابد که بیشترین matchingPrecedence را دارد. اگر چند FlowSchema با matchingPrecedence برابر با یک درخواست منطبق باشند، FlowSchema‌ای که name آن از نظر ترتیب الفبایی (lexicographic) کوچک‌تر است برنده می‌شود؛ اما بهتر است به این رفتار تکیه نکنید و در عوض مطمئن شوید که هیچ دو FlowSchema‌ای matchingPrecedence یکسان ندارند.

یک FlowSchema با یک درخواست مفروض تطبیق دارد اگر دست‌کم یکی از rules آن با درخواست تطبیق داشته باشد. یک rule زمانی تطبیق دارد که دست‌کم یکی از subjects آن و دست‌کم یکی از resourceRules یا nonResourceRules آن (بسته به اینکه درخواست ورودی برای یک URL منبع یا غیرمنبع است) با درخواست تطبیق داشته باشد.

برای فیلد name در subjects و همچنین فیلدهای verbs، apiGroups، resources، namespaces و nonResourceURLs در قواعد منبع و غیرمنبع، می‌توان از نویسه‌ی عام * استفاده کرد تا با همه‌ی مقادیر آن فیلد تطبیق یابد؛ این کار در عمل آن فیلد را از ارزیابی خارج می‌کند.

مقدار distinguisherMethod.type در یک FlowSchema تعیین می‌کند که درخواست‌های منطبق با آن schema چگونه به جریان‌ها (flows) تفکیک شوند. این مقدار می‌تواند ByUser باشد که در آن یک کاربر درخواست‌دهنده نمی‌تواند سایر کاربران را از ظرفیت محروم کند؛ ByNamespace باشد که در آن درخواست‌ها برای منابع یک فضای نام (namespace) نمی‌توانند درخواست‌ها برای منابع فضاهای نام دیگر را از ظرفیت محروم کنند؛ یا خالی باشد (یا فیلد distinguisherMethod به‌طور کامل حذف شود) که در این حالت همه‌ی درخواست‌هایی که با این FlowSchema تطبیق می‌یابند بخشی از یک جریان واحد در نظر گرفته می‌شوند. انتخاب درست برای یک FlowSchema مشخص به منبع موردنظر و محیط خاص شما بستگی دارد.

مقادیر پیش‌فرض {#defaults}

هر kube-apiserver دو نوع آبجکت پیکربندی APF را نگهداری می‌کند: اجباری (mandatory) و پیشنهادی (suggested).

آبجکت‌های پیکربندی اجباری

چهار آبجکت پیکربندی اجباری بیانگر رفتار حفاظتی (guardrail) ثابت و درونی هستند. این رفتار همان چیزی است که سرورها پیش از وجود این آبجکت‌ها دارند، و هنگامی که این آبجکت‌ها وجود دارند، spec آن‌ها این رفتار را منعکس می‌کند. چهار آبجکت اجباری به شرح زیر هستند.

  • سطح اولویت اجباری exempt برای درخواست‌هایی استفاده می‌شود که اصلاً مشمول کنترل جریان نیستند: این درخواست‌ها همیشه بی‌درنگ توزیع می‌شوند. FlowSchema اجباری exempt همه‌ی درخواست‌های گروه system:masters را در این سطح اولویت طبقه‌بندی می‌کند. در صورت لزوم می‌توانید FlowSchemaهای دیگری تعریف کنید که درخواست‌های دیگر را به این سطح اولویت هدایت کنند.

  • سطح اولویت اجباری catch-all در ترکیب با FlowSchema اجباری catch-all به کار می‌رود تا اطمینان حاصل شود که هر درخواست به‌نوعی طبقه‌بندی می‌شود. معمولاً نباید به این پیکربندی فراگیر تکیه کنید و بسته به نیاز باید FlowSchema و PriorityLevelConfiguration فراگیر خودتان را ایجاد کنید (یا از سطح اولویت پیشنهادی global-default که به‌صورت پیش‌فرض نصب می‌شود استفاده کنید). از آنجا که انتظار نمی‌رود این سطح در حالت عادی استفاده شود، سطح اولویت اجباری catch-all سهم هم‌زمانی (concurrency share) بسیار کوچکی دارد و درخواست‌ها را در صف قرار نمی‌دهد.

آبجکت‌های پیکربندی پیشنهادی

FlowSchemaها و PriorityLevelConfigurationهای پیشنهادی یک پیکربندی پیش‌فرض معقول را تشکیل می‌دهند. در صورت تمایل می‌توانید این‌ها را تغییر دهید و/یا آبجکت‌های پیکربندی اضافی ایجاد کنید. اگر احتمال می‌رود کلاستر شما بار سنگینی را تجربه کند، باید بررسی کنید چه پیکربندی بهترین کارکرد را خواهد داشت.

پیکربندی پیشنهادی درخواست‌ها را در شش سطح اولویت گروه‌بندی می‌کند:

  • سطح اولویت node-high برای به‌روزرسانی‌های سلامت از سوی نودها است.

  • سطح اولویت system برای درخواست‌های غیرمرتبط با سلامت از سوی گروه system:nodes است، یعنی Kubeletها، که باید بتوانند با API server ارتباط برقرار کنند تا بارهای کاری بتوانند روی آن‌ها زمان‌بندی شوند.

  • سطح اولویت leader-election برای درخواست‌های انتخاب رهبر (leader election) از سوی کنترل‌کننده‌های داخلی است (به‌طور مشخص، درخواست‌های مربوط به endpoints، configmaps یا leases که از سوی کاربران system:kube-controller-manager یا system:kube-scheduler و حساب‌های سرویس در فضای نام kube-system می‌آیند). جدا نگه داشتن این ترافیک از ترافیک‌های دیگر اهمیت دارد، زیرا خطا در انتخاب رهبر باعث می‌شود کنترل‌کننده‌های مربوطه با شکست مواجه شوند و دوباره راه‌اندازی شوند، و این به نوبه‌ی خود ترافیک پرهزینه‌تری ایجاد می‌کند، چون کنترل‌کننده‌های جدید informerهای خود را همگام‌سازی می‌کنند.

  • سطح اولویت workload-high برای سایر درخواست‌های کنترل‌کننده‌های داخلی است.

  • سطح اولویت workload-low برای درخواست‌های هر حساب سرویس دیگر است که معمولاً شامل همه‌ی درخواست‌های کنترل‌کننده‌هایی می‌شود که در Podها اجرا می‌شوند.

  • سطح اولویت global-default همه‌ی ترافیک‌های دیگر را مدیریت می‌کند، مانند دستورهای تعاملی kubectl که کاربران بدون دسترسی ویژه اجرا می‌کنند.

FlowSchemaهای پیشنهادی برای هدایت درخواست‌ها به سطوح اولویت بالا به کار می‌روند و در اینجا فهرست نشده‌اند.

نگهداری آبجکت‌های پیکربندی اجباری و پیشنهادی

هر kube-apiserver آبجکت‌های پیکربندی اجباری و پیشنهادی را به‌طور مستقل و با رفتار اولیه و دوره‌ای نگهداری می‌کند. بنابراین، در شرایطی که ترکیبی از سرورهایی با نسخه‌های مختلف وجود دارد، تا زمانی که سرورهای مختلف دیدگاه‌های متفاوتی درباره‌ی محتوای صحیح این آبجکت‌ها داشته باشند، ممکن است نوسان (thrashing) رخ دهد.

هر kube-apiserver یک مرحله‌ی نگهداری اولیه روی آبجکت‌های پیکربندی اجباری و پیشنهادی انجام می‌دهد و پس از آن به‌طور دوره‌ای (هر دقیقه یک‌بار) این آبجکت‌ها را نگهداری می‌کند.

برای آبجکت‌های پیکربندی اجباری، نگهداری شامل اطمینان از وجود آبجکت و در صورت وجود، داشتن spec صحیح است. سرور اجازه‌ی ایجاد یا به‌روزرسانی با specی را که با رفتار حفاظتی سرور ناسازگار باشد نمی‌دهد.

نگهداری آبجکت‌های پیکربندی پیشنهادی به‌گونه‌ای طراحی شده است که امکان بازنویسی specهای آن‌ها را فراهم کند. در مقابل، حذف آن‌ها پذیرفته نمی‌شود: فرایند نگهداری آبجکت را بازمی‌گرداند. اگر یک آبجکت پیکربندی پیشنهادی را نمی‌خواهید، باید آن را نگه دارید اما spec آن را طوری تنظیم کنید که کمترین پیامد را داشته باشد. نگهداری آبجکت‌های پیشنهادی همچنین برای پشتیبانی از مهاجرت خودکار هنگام عرضه‌ی نسخه‌ی جدید kube-apiserver طراحی شده است، هرچند ممکن است تا زمانی که جمعیتی ترکیبی از سرورها وجود دارد، با نوسان همراه باشد.

نگهداری یک آبجکت پیکربندی پیشنهادی شامل ایجاد آن --- با spec پیشنهادی سرور --- در صورت عدم وجود آبجکت است. از سوی دیگر، اگر آبجکت از قبل وجود داشته باشد، رفتار نگهداری به این بستگی دارد که kube-apiserverها آبجکت را کنترل می‌کنند یا کاربران. در حالت اول، سرور اطمینان حاصل می‌کند که spec آبجکت همان چیزی است که سرور پیشنهاد می‌کند؛ در حالت دوم، spec دست‌نخورده باقی می‌ماند.

پاسخ به اینکه چه کسی آبجکت را کنترل می‌کند، ابتدا با جست‌وجوی یک annotation با کلید apf.kubernetes.io/autoupdate-spec به‌دست می‌آید. اگر چنین annotation ای وجود داشته باشد و مقدار آن true باشد، kube-apiserverها آبجکت را کنترل می‌کنند. اگر چنین annotation ای وجود داشته باشد و مقدار آن false باشد، کاربران آبجکت را کنترل می‌کنند. اگر هیچ‌یک از این دو شرط برقرار نباشد، metadata.generation آبجکت بررسی می‌شود. اگر مقدار آن 1 باشد، kube-apiserverها آبجکت را کنترل می‌کنند. در غیر این صورت، کاربران آبجکت را کنترل می‌کنند. این قواعد در نسخه‌ی 1.22 معرفی شدند و درنظر گرفتن metadata.generation برای مهاجرت از رفتار ساده‌تر پیشین است. کاربرانی که می‌خواهند یک آبجکت پیکربندی پیشنهادی را کنترل کنند، باید annotation با کلید apf.kubernetes.io/autoupdate-spec آن را روی false تنظیم کنند.

نگهداری یک آبجکت پیکربندی اجباری یا پیشنهادی همچنین شامل اطمینان از این است که آبجکت یک annotation با کلید apf.kubernetes.io/autoupdate-spec دارد که به‌درستی نشان می‌دهد آیا kube-apiserverها آبجکت را کنترل می‌کنند یا خیر.

نگهداری همچنین شامل حذف آبجکت‌هایی است که نه اجباری هستند و نه پیشنهادی، اما با apf.kubernetes.io/autoupdate-spec=true annotate شده‌اند.

معافیت درخواست‌های بررسی سلامت از محدودیت هم‌زمانی {#health-check-concurrency-exemption}

پیکربندی پیشنهادی هیچ رفتار ویژه‌ای برای درخواست‌های بررسی سلامت (health check) روی kube-apiserverها از سوی kubeletهای محلی آن‌ها در نظر نمی‌گیرد --- درخواست‌هایی که معمولاً از پورت امن استفاده می‌کنند اما هیچ اعتبارنامه‌ای ارائه نمی‌دهند. با پیکربندی پیشنهادی، این درخواست‌ها به FlowSchema با نام global-default و سطح اولویت متناظر global-default اختصاص می‌یابند، جایی که ترافیک‌های دیگر می‌توانند آن‌ها را از میدان به در کنند.

اگر FlowSchema اضافی زیر را اضافه کنید، این درخواست‌ها از محدودسازی نرخ معاف می‌شوند.

احتیاط:

اعمال این تغییر همچنین به هر طرف مخربی اجازه می‌دهد درخواست‌های بررسی سلامتی ارسال کند که با این FlowSchema تطبیق دارند، آن هم با هر حجمی که بخواهد. اگر برای محافظت از API server کلاستر خود در برابر ترافیک عمومی اینترنت از یک فیلتر ترافیک وب یا سازوکار امنیتی خارجی مشابه استفاده می‌کنید، می‌توانید قواعدی پیکربندی کنید که هر درخواست بررسی سلامتی را که از خارج کلاستر شما می‌آید مسدود کند.

priority-and-fairness/health-for-strangers.yaml
apiVersion: flowcontrol.apiserver.k8s.io/v1
kind: FlowSchema
metadata:
  name: health-for-strangers
spec:
  matchingPrecedence: 1000
  priorityLevelConfiguration:
    name: exempt
  rules:
    - nonResourceRules:
      - nonResourceURLs:
          - "/healthz"
          - "/livez"
          - "/readyz"
        verbs:
          - "*"
      subjects:
        - kind: Group
          group:
            name: "system:unauthenticated"

متریک‌ها {#metrics}

توجه:

در نسخه‌های کوبرنتیز پیش از v1.20، برچسب‌های flow_schema و priority_level به‌صورت ناهماهنگ به ترتیب با نام‌های flowSchema و priorityLevel نام‌گذاری شده بودند. اگر از کوبرنتیز نسخه v1.19 یا قدیمی‌تر استفاده می‌کنید، باید به مستندات نسخه خود مراجعه کنید.

هنگامی که قابلیت API Priority and Fairness را فعال می‌کنید، kube-apiserver متریک‌های اضافی را ارائه می‌کند. پایش این متریک‌ها می‌تواند به شما کمک کند تشخیص دهید که آیا پیکربندی شما به‌طور نامناسب ترافیک مهم را محدود (throttle) می‌کند، یا بارهای کاری بدرفتاری را که ممکن است به سلامت سیستم آسیب بزنند پیدا کنید.

سطح بلوغ بتا

  • apiserver_flowcontrol_rejected_requests_total یک counter vector (تجمعی از زمان شروع سرور) از درخواست‌های ردشده است که بر اساس برچسب‌های flow_schema (نشان‌دهنده FlowSchema منطبق با درخواست)، priority_level (نشان‌دهنده سطح اولویتی که درخواست به آن تخصیص یافته) و reason تفکیک شده است. برچسب reason یکی از مقادیر زیر را خواهد داشت:

    • queue-full: نشان می‌دهد که تعداد زیادی درخواست از قبل در صف قرار گرفته بود.
    • concurrency-limit: نشان می‌دهد که PriorityLevelConfiguration به‌گونه‌ای پیکربندی شده که درخواست‌های مازاد را به‌جای صف‌بندی، رد کند.
    • time-out: نشان می‌دهد که درخواست هنگام پایان یافتن محدودیت زمان صف‌بندی‌اش همچنان در صف بود.
    • cancelled: نشان می‌دهد که درخواست purge locked نیست و از صف بیرون انداخته شده است.

  • apiserver_flowcontrol_dispatched_requests_total یک counter vector (تجمعی از زمان شروع سرور) از درخواست‌هایی است که اجرایشان آغاز شده و بر اساس flow_schema و priority_level تفکیک شده است.

  • apiserver_flowcontrol_current_inqueue_requests یک gauge vector است که تعداد لحظه‌ای درخواست‌های صف‌شده (که در حال اجرا نیستند) را نگه می‌دارد و بر اساس priority_level و flow_schema تفکیک شده است.

  • apiserver_flowcontrol_current_executing_requests یک gauge vector است که تعداد لحظه‌ای درخواست‌های در حال اجرا (که در صف منتظر نیستند) را نگه می‌دارد و بر اساس priority_level و flow_schema تفکیک شده است.

  • apiserver_flowcontrol_current_executing_seats یک gauge vector است که تعداد لحظه‌ای seatهای اشغال‌شده را نگه می‌دارد و بر اساس priority_level و flow_schema تفکیک شده است.

  • apiserver_flowcontrol_request_wait_duration_seconds یک histogram vector از مدت زمانی است که درخواست‌ها در صف سپری کرده‌اند و بر اساس برچسب‌های flow_schema، priority_level و execute تفکیک شده است. برچسب execute نشان می‌دهد که آیا اجرای درخواست آغاز شده است یا خیر.

توجه:

از آنجا که هر FlowSchema همواره درخواست‌ها را به یک PriorityLevelConfiguration واحد تخصیص می‌دهد، می‌توانید هیستوگرام‌های همه FlowSchemaهای مربوط به یک سطح اولویت را با هم جمع کنید تا هیستوگرام مؤثر برای درخواست‌های تخصیص‌یافته به آن سطح اولویت به دست آید.

  • apiserver_flowcontrol_nominal_limit_seats یک gauge vector است که حد همزمانی اسمی هر سطح اولویت را نگه می‌دارد؛ این مقدار از حد همزمانی کل API server و سهم‌های همزمانی اسمی پیکربندی‌شده برای سطح اولویت محاسبه می‌شود.

سطح بلوغ آلفا

  • apiserver_current_inqueue_requests یک gauge vector از بیشینه‌های اخیر (high water mark) تعداد درخواست‌های صف‌شده است که بر اساس برچسبی به نام request_kind با مقدار mutating یا readOnly گروه‌بندی می‌شود. این بیشینه‌ها بزرگ‌ترین عددی را توصیف می‌کنند که در آخرین بازه یک‌ثانیه‌ای کامل‌شده دیده شده است. این متریک‌ها مکمل gauge vector قدیمی‌تر apiserver_current_inflight_requests هستند که بیشینه تعداد درخواست‌هایی را که در آخرین بازه به‌طور فعال سرویس‌دهی می‌شدند نگه می‌دارد.

  • apiserver_current_inqueue_seats یک gauge vector از مجموع بزرگ‌ترین تعداد seat که هر یک از درخواست‌های صف‌شده اشغال خواهند کرد است و بر اساس برچسب‌های flow_schema و priority_level گروه‌بندی می‌شود.

  • apiserver_flowcontrol_read_vs_write_current_requests یک histogram vector از مشاهداتی است که در پایان هر نانوثانیه از تعداد درخواست‌ها انجام می‌شود و بر اساس برچسب‌های phase (با مقادیر waiting و executing) و request_kind (با مقادیر mutating و readOnly) تفکیک شده است. هر مقدار مشاهده‌شده نسبتی بین 0 و 1 است که از تقسیم تعداد درخواست‌ها بر حد متناظر تعداد درخواست‌ها به دست می‌آید (حد حجم صف برای وضعیت انتظار و حد همزمانی برای وضعیت اجرا).

  • apiserver_flowcontrol_request_concurrency_in_use یک gauge vector است که تعداد لحظه‌ای seatهای اشغال‌شده را نگه می‌دارد و بر اساس priority_level و flow_schema تفکیک شده است.

  • apiserver_flowcontrol_priority_level_request_utilization یک histogram vector از مشاهداتی است که در پایان هر نانوثانیه از تعداد درخواست‌ها انجام می‌شود و بر اساس برچسب‌های phase (با مقادیر waiting و executing) و priority_level تفکیک شده است. هر مقدار مشاهده‌شده نسبتی بین 0 و 1 است که از تقسیم تعداد درخواست‌ها بر حد متناظر تعداد درخواست‌ها به دست می‌آید (حد حجم صف برای وضعیت انتظار و حد همزمانی برای وضعیت اجرا).

  • apiserver_flowcontrol_priority_level_seat_utilization یک histogram vector از مشاهداتی است که در پایان هر نانوثانیه از میزان بهره‌برداری از حد همزمانی یک سطح اولویت انجام می‌شود و بر اساس priority_level تفکیک شده است. این بهره‌برداری برابر با کسر (تعداد seatهای اشغال‌شده) / (حد همزمانی) است. این متریک همه مراحل اجرا (هم مرحله عادی و هم تأخیر اضافی در پایان یک نوشتن برای پوشش کار اعلان متناظر) را برای همه درخواست‌ها به‌جز WATCHها در نظر می‌گیرد؛ برای WATCHها فقط مرحله اولیه‌ای را در نظر می‌گیرد که اعلان‌های مربوط به آبجکت‌های از پیش موجود را تحویل می‌دهد. هر هیستوگرام در این vector همچنین با phase: executing برچسب‌گذاری شده است (برای وضعیت انتظار هیچ حد seat وجود ندارد).

  • apiserver_flowcontrol_request_queue_length_after_enqueue یک histogram vector از طول صف‌ها است که بر اساس priority_level و flow_schema تفکیک شده و توسط درخواست‌های صف‌شده نمونه‌برداری می‌شود. هر درخواستی که در صف قرار می‌گیرد یک نمونه به هیستوگرام خود می‌افزاید که طول صف را بلافاصله پس از افزوده شدن درخواست گزارش می‌کند. توجه کنید که این روش آمارهایی متفاوت از یک بررسی نااریب تولید می‌کند.

توجه:

وجود یک مقدار پرت (outlier) در یکی از هیستوگرام‌ها نشان می‌دهد که احتمالاً یک جریان واحد (یعنی درخواست‌های یک کاربر یا برای یک فضای نام، بسته به پیکربندی) API server را مورد هجوم قرار داده و محدود (throttle) می‌شود. در مقابل، اگر هیستوگرام یک سطح اولویت نشان دهد که همه صف‌های آن سطح اولویت از صف‌های سایر سطوح اولویت بلندتر هستند، ممکن است افزایش سهم‌های همزمانی آن PriorityLevelConfiguration مناسب باشد.

  • apiserver_flowcontrol_request_concurrency_limit همان apiserver_flowcontrol_nominal_limit_seats است. پیش از معرفی قرض‌گیری همزمانی میان سطوح اولویت، این مقدار همواره برابر با apiserver_flowcontrol_current_limit_seats بود (که به‌عنوان یک متریک مجزا وجود نداشت).

  • apiserver_flowcontrol_lower_limit_seats یک gauge vector است که کران پایین حد همزمانی پویای هر سطح اولویت را نگه می‌دارد.

  • apiserver_flowcontrol_upper_limit_seats یک gauge vector است که کران بالای حد همزمانی پویای هر سطح اولویت را نگه می‌دارد.

  • apiserver_flowcontrol_demand_seats یک histogram vector است که مشاهدات را در پایان هر نانوثانیه برای نسبت (تقاضای seat) / (حد همزمانی اسمی) هر سطح اولویت می‌شمارد. تقاضای seat یک سطح اولویت برابر است با مجموع، روی درخواست‌های صف‌شده و درخواست‌های موجود در مرحله اولیه اجرا، بیشینه تعداد seatهای اشغال‌شده در مراحل اجرای اولیه و نهایی درخواست.

  • apiserver_flowcontrol_demand_seats_high_watermark یک gauge vector است که برای هر سطح اولویت، بیشینه تقاضای seat دیده‌شده در طول آخرین بازه تنظیم قرض‌گیری همزمانی را نگه می‌دارد.

  • apiserver_flowcontrol_demand_seats_average یک gauge vector است که برای هر سطح اولویت، میانگین وزن‌دار زمانی تقاضای seat دیده‌شده در طول آخرین بازه تنظیم قرض‌گیری همزمانی را نگه می‌دارد.

  • apiserver_flowcontrol_demand_seats_stdev یک gauge vector است که برای هر سطح اولویت، انحراف معیار جامعه با وزن زمانی تقاضای seat دیده‌شده در طول آخرین بازه تنظیم قرض‌گیری همزمانی را نگه می‌دارد.

  • apiserver_flowcontrol_demand_seats_smoothed یک gauge vector است که برای هر سطح اولویت، تقاضای seat هموارشده و پوششی (enveloped) را که در آخرین تنظیم همزمانی تعیین شده است نگه می‌دارد.

  • apiserver_flowcontrol_target_seats یک gauge vector است که برای هر سطح اولویت، هدف همزمانی را که وارد مسئله تخصیص قرض‌گیری می‌شود نگه می‌دارد.

  • apiserver_flowcontrol_seat_fair_frac یک gauge است که کسر تخصیص منصفانه تعیین‌شده در آخرین تنظیم قرض‌گیری را نگه می‌دارد.

  • apiserver_flowcontrol_current_limit_seats یک gauge vector است که برای هر سطح اولویت، حد همزمانی پویای به‌دست‌آمده در آخرین تنظیم را نگه می‌دارد.

  • apiserver_flowcontrol_request_execution_seconds یک histogram vector از مدت زمانی است که اجرای واقعی درخواست‌ها طول کشیده و بر اساس flow_schema و priority_level تفکیک شده است.

  • apiserver_flowcontrol_watch_count_samples یک histogram vector از تعداد درخواست‌های WATCH فعالِ مرتبط با یک نوشتن مشخص است که بر اساس flow_schema و priority_level تفکیک شده است.

  • apiserver_flowcontrol_work_estimated_seats یک histogram vector از تعداد seatهای تخمینی (بیشینه مراحل اولیه و نهایی اجرا) مرتبط با درخواست‌ها است که بر اساس flow_schema و priority_level تفکیک شده است.

  • apiserver_flowcontrol_request_dispatch_no_accommodation_total یک counter vector از تعداد رویدادهایی است که در principle می‌توانستند منجر به dispatch شدن یک درخواست شوند اما به دلیل نبود همزمانی در دسترس این اتفاق نیفتاد و بر اساس flow_schema و priority_level تفکیک شده است.

  • apiserver_flowcontrol_epoch_advance_total یک counter vector از تعداد تلاش‌ها برای جهش دادن پیشرفت‌سنج (progress meter) یک سطح اولویت به عقب، به‌منظور جلوگیری از سرریز عددی است که بر اساس priority_level و success گروه‌بندی می‌شود.

روش‌های توصیه‌شده برای استفاده از API Priority and Fairness {#good-practices-for-using-api-priority-and-fairness}

هنگامی که یک سطح اولویت از همزمانی مجاز خود فراتر می‌رود، درخواست‌ها ممکن است با افزایش تأخیر روبه‌رو شوند یا با خطای HTTP 429 (Too Many Requests) حذف شوند. برای جلوگیری از این پیامدهای جانبی APF، می‌توانید بار کاری خود را تغییر دهید یا تنظیمات APF را اصلاح کنید تا اطمینان یابید seatهای کافی برای سرویس‌دهی به درخواست‌های شما در دسترس است.

برای تشخیص اینکه آیا درخواست‌ها به دلیل APF رد می‌شوند، متریک‌های زیر را بررسی کنید:

  • apiserver_flowcontrol_rejected_requests_total: تعداد کل درخواست‌های ردشده به تفکیک FlowSchema و PriorityLevelConfiguration.
  • apiserver_flowcontrol_current_inqueue_requests: تعداد فعلی درخواست‌های صف‌شده به تفکیک FlowSchema و PriorityLevelConfiguration.
  • apiserver_flowcontrol_request_wait_duration_seconds: تأخیری که به درخواست‌های منتظر در صف اضافه می‌شود.
  • apiserver_flowcontrol_priority_level_seat_utilization: میزان بهره‌برداری از seat به ازای هر PriorityLevelConfiguration.

تغییرات بار کاری {#good-practice-workload-modifications}

برای جلوگیری از صف‌بندی درخواست‌ها و افزودن تأخیر یا حذف آن‌ها به دلیل APF، می‌توانید درخواست‌های خود را با روش‌های زیر بهینه کنید:

  • کاهش نرخ اجرای درخواست‌ها. تعداد کمتر درخواست در یک بازه زمانی ثابت باعث می‌شود در هر لحظه به تعداد کمتری seat نیاز باشد.
  • از ارسال همزمان تعداد زیادی درخواست پرهزینه خودداری کنید. درخواست‌ها را می‌توان طوری بهینه کرد که از seat کمتری استفاده کنند یا تأخیر کمتری داشته باشند تا این درخواست‌ها seatها را برای مدت کوتاه‌تری نگه دارند. درخواست‌های list بسته به تعداد آبجکت‌های واکشی‌شده در طول درخواست می‌توانند بیش از 1 seat را اشغال کنند. محدود کردن تعداد آبجکت‌های بازیابی‌شده در یک درخواست list، برای مثال با استفاده از صفحه‌بندی (pagination)، در بازه زمانی کوتاه‌تری از seatهای کل کمتری استفاده می‌کند. افزون بر این، جایگزین کردن درخواست‌های list با درخواست‌های watch به سهم‌های همزمانی کل کمتری نیاز دارد، زیرا درخواست‌های watch در طول انفجار اولیه اعلان‌ها فقط 1 seat را اشغال می‌کنند. اگر در نسخه‌های 1.27 و بالاتر از streaming list استفاده کنید، درخواست‌های watch برای انفجار اولیه اعلان‌های خود به همان تعداد seat که یک درخواست list اشغال می‌کند نیاز دارند، زیرا کل وضعیت مجموعه باید به‌صورت جریانی ارسال شود. توجه کنید که در هر دو حالت، یک درخواست watch پس از این مرحله اولیه هیچ seat‌ای را نگه نمی‌دارد.

به خاطر داشته باشید که صف‌بندی یا ردشدن درخواست‌ها توسط APF می‌تواند ناشی از افزایش تعداد درخواست‌ها یا افزایش تأخیر درخواست‌های موجود باشد. برای مثال، اگر درخواست‌هایی که معمولاً 1 ثانیه برای اجرا طول می‌کشند شروع به صرف 60 ثانیه کنند، ممکن است APF شروع به رد درخواست‌ها کند، زیرا درخواست‌ها به دلیل این افزایش تأخیر، seatها را برای مدتی طولانی‌تر از حد معمول اشغال کرده‌اند. اگر APF شروع به رد درخواست‌ها در چندین سطح اولویت کند، بدون آنکه تغییر چشمگیری در بار کاری رخ داده باشد، ممکن است مشکلی زیربنایی در عملکرد control plane وجود داشته باشد، نه در بار کاری یا تنظیمات APF.

تنظیمات اولویت و انصاف {#good-practice-apf-settings}

همچنین می‌توانید آبجکت‌های پیش‌فرض FlowSchema و PriorityLevelConfiguration را تغییر دهید یا آبجکت‌های جدیدی از این نوع‌ها ایجاد کنید تا بهتر با بار کاری شما سازگار شوند.

تنظیمات APF را می‌توان برای اهداف زیر تغییر داد:

  • اختصاص seatهای بیشتر به درخواست‌های با اولویت بالا.
  • جداسازی درخواست‌های غیرضروری یا پرهزینه‌ای که اگر یک سطح همزمانی را با سایر جریان‌ها به اشتراک بگذارند، آن را دچار قحطی (starvation) می‌کنند.

اختصاص seatهای بیشتر به درخواست‌های با اولویت بالا {#give-more-seats-to-high-priority-requests}

  1. در صورت امکان، تعداد seatهای در دسترس در همه سطوح اولویت برای یک kube-apiserver مشخص را می‌توان با افزایش مقادیر فلگ‌های max-requests-inflight و max-mutating-requests-inflight افزایش داد. به‌طور جایگزین، مقیاس‌دهی افقی تعداد نمونه‌های kube-apiserver همزمانی کل هر سطح اولویت را در سراسر کلاستر افزایش می‌دهد، مشروط بر اینکه توزیع بار (load balancing) درخواست‌ها به‌اندازه کافی انجام شود.
  2. می‌توانید یک FlowSchema جدید ایجاد کنید که به یک PriorityLevelConfiguration با سطح همزمانی بزرگ‌تر ارجاع دهد. این PriorityLevelConfiguration جدید می‌تواند یک سطح موجود یا یک سطح جدید با مجموعه سهم‌های همزمانی اسمی مخصوص به خود باشد. برای مثال، می‌توان یک FlowSchema جدید معرفی کرد تا PriorityLevelConfiguration درخواست‌های شما را از global-default به workload-low تغییر دهد و تعداد seatهای در دسترس کاربر شما را افزایش دهد. ایجاد یک PriorityLevelConfiguration جدید تعداد seatهای اختصاص‌یافته به سطوح موجود را کاهش می‌دهد. به یاد داشته باشید که ویرایش یک FlowSchema یا PriorityLevelConfiguration پیش‌فرض مستلزم تنظیم حاشیه‌نویسی (annotation) با نام apf.kubernetes.io/autoupdate-spec روی false است.
  3. همچنین می‌توانید NominalConcurrencyShares را برای PriorityLevelConfiguration‌ای که به درخواست‌های با اولویت بالای شما سرویس می‌دهد افزایش دهید. به‌طور جایگزین، در نسخه‌های 1.26 و بالاتر، می‌توانید LendablePercent را برای سطوح اولویت رقیب افزایش دهید تا سطح اولویت مورد نظر استخر بزرگ‌تری از seatها برای قرض‌گرفتن داشته باشد.

جداسازی درخواست‌های غیرضروری برای جلوگیری از قحطی سایر جریان‌ها {#isolate-non-essential-requests-from-starving-other-flows}

برای جداسازی درخواست‌ها، می‌توانید یک FlowSchema ایجاد کنید که subject آن با کاربری که این درخواست‌ها را ارسال می‌کند مطابقت داشته باشد، یا یک FlowSchema ایجاد کنید که با ماهیت درخواست (متناظر با resourceRules) مطابقت داشته باشد. سپس می‌توانید این FlowSchema را به یک PriorityLevelConfiguration با سهم کمی از seatها نگاشت کنید.

برای مثال، فرض کنید درخواست‌های list رویدادها از Podهای در حال اجرا در فضای نام default هر کدام 10 seat استفاده می‌کنند و به مدت 1 دقیقه اجرا می‌شوند. برای جلوگیری از تأثیر این درخواست‌های پرهزینه بر درخواست‌های سایر Podها که از FlowSchema موجود service-accounts استفاده می‌کنند، می‌توانید FlowSchema زیر را اعمال کنید تا این فراخوانی‌های list از سایر درخواست‌ها جدا شوند.

نمونه آبجکت FlowSchema برای جداسازی درخواست‌های list رویدادها:

priority-and-fairness/list-events-default-service-account.yaml
apiVersion: flowcontrol.apiserver.k8s.io/v1
kind: FlowSchema
metadata:
  name: list-events-default-service-account
spec:
  distinguisherMethod:
    type: ByUser
  matchingPrecedence: 8000
  priorityLevelConfiguration:
    name: catch-all
  rules:
    - resourceRules:
      - apiGroups:
          - '*'
        namespaces:
          - default
        resources:
          - events
        verbs:
          - list
      subjects:
        - kind: ServiceAccount
          serviceAccount:
            name: default
            namespace: default
  • این FlowSchema همه فراخوانی‌های list رویدادها را که توسط service account پیش‌فرض در فضای نام default انجام می‌شوند دربرمی‌گیرد. اولویت تطبیق 8000 کمتر از مقدار 9000 است که FlowSchema موجود service-accounts استفاده می‌کند، بنابراین این فراخوانی‌های list رویدادها با list-events-default-service-account مطابقت خواهند یافت، نه با service-accounts.
  • از PriorityLevelConfiguration با نام catch-all برای جداسازی این درخواست‌ها استفاده می‌شود. سطح اولویت catch-all سهم همزمانی بسیار کوچکی دارد و درخواست‌ها را صف‌بندی نمی‌کند.

گام‌های بعدی

  • برای کسب اطلاعات بیشتر درباره عیب‌یابی می‌توانید مستند مرجع کنترل جریان را مطالعه کنید.
  • برای اطلاعات پیش‌زمینه درباره جزئیات طراحی API Priority and Fairness، به پیشنهاد بهبود (enhancement proposal) مراجعه کنید.
  • می‌توانید پیشنهادها و درخواست‌های قابلیت خود را از طریق SIG API Machinery یا کانال slack این قابلیت مطرح کنید.
