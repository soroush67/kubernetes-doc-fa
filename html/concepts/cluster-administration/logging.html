معماری لاگ‌گیری

لاگ‌های برنامه می‌توانند به شما کمک کنند بفهمید در درون برنامه‌تان چه می‌گذرد. لاگ‌ها به‌ویژه برای اشکال‌زدایی مشکلات و پایش فعالیت کلاستر مفیدند. بیشتر برنامه‌های مدرن نوعی سازوکار لاگ‌گیری دارند. همچنین موتورهای کانتینر برای پشتیبانی از لاگ‌گیری طراحی شده‌اند. ساده‌ترین و پرکاربردترین روش لاگ‌گیری برای برنامه‌های کانتینری‌شده، نوشتن در جریان‌های خروجی استاندارد (standard output) و خطای استاندارد (standard error) است.

با این حال، قابلیت بومی ارائه‌شده توسط موتور کانتینر یا runtime معمولاً برای یک راهکار کامل لاگ‌گیری کافی نیست.

برای مثال، ممکن است بخواهید در صورتی که یک کانتینر از کار بیفتد، یک Pod اخراج (evict) شود یا یک نود از بین برود، به لاگ‌های برنامه‌تان دسترسی داشته باشید.

در یک کلاستر، لاگ‌ها باید ذخیره‌سازی و چرخه عمر جداگانه‌ای مستقل از نودها، Podها یا کانتینرها داشته باشند. این مفهوم لاگ‌گیری در سطح کلاستر نامیده می‌شود.

معماری‌های لاگ‌گیری در سطح کلاستر به یک backend جداگانه برای ذخیره، تحلیل و پرس‌وجوی لاگ‌ها نیاز دارند. کوبرنتیز راهکار ذخیره‌سازی بومی برای داده‌های لاگ ارائه نمی‌دهد. در عوض، راهکارهای لاگ‌گیری بسیاری وجود دارند که با کوبرنتیز یکپارچه می‌شوند. بخش‌های زیر نحوه مدیریت و ذخیره لاگ‌ها روی نودها را شرح می‌دهند.

لاگ‌های Pod و کانتینر {#basic-logging-in-kubernetes}

کوبرنتیز لاگ‌های هر کانتینر را در یک Pod در حال اجرا ثبت می‌کند.

این مثال از مانیفست یک Pod استفاده می‌کند که در آن کانتینری هر ثانیه یک‌بار متنی را در جریان خروجی استاندارد می‌نویسد.

debug/counter-pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: counter
spec:
  containers:
  - name: count
    image: busybox:1.28
    args: [/bin/sh, -c,
            'i=0; while true; do echo "$i: $(date)"; i=$((i+1)); sleep 1; done']

برای اجرای این Pod از دستور زیر استفاده کنید:

kubectl apply -f https://k8s.io/examples/debug/counter-pod.yaml

خروجی به این صورت است:

pod/counter created

برای دریافت لاگ‌ها، از دستور kubectl logs به‌صورت زیر استفاده کنید:

kubectl logs counter

خروجی مشابه زیر است:

0: Fri Apr  1 11:42:23 UTC 2022
1: Fri Apr  1 11:42:24 UTC 2022
2: Fri Apr  1 11:42:25 UTC 2022

می‌توانید از kubectl logs --previous برای بازیابی لاگ‌های نمونه قبلی یک کانتینر استفاده کنید. اگر Pod شما چند کانتینر دارد، با افزودن نام کانتینر به دستور و با استفاده از فلگ -c مشخص کنید به لاگ‌های کدام کانتینر می‌خواهید دسترسی پیدا کنید، مانند زیر:

kubectl logs counter -c count

جریان‌های لاگ کانتینر

وضعیت ویژگی: Kubernetes [] ()

به‌عنوان یک قابلیت آلفا، kubelet می‌تواند لاگ‌های دو جریان استاندارد تولیدشده توسط یک کانتینر را از یکدیگر جدا کند: خروجی استاندارد و خطای استاندارد. برای استفاده از این رفتار، باید feature gate با نام PodLogsQuerySplitStreams را فعال کنید. با فعال بودن این feature gate، کوبرنتیز 1.37 امکان دسترسی مستقیم به این جریان‌های لاگ را از طریق API مربوط به Pod فراهم می‌کند. می‌توانید با مشخص کردن نام جریان (Stdout یا Stderr) از طریق query string با نام stream، یک جریان مشخص را دریافت کنید. باید به خواندن زیرمنبع log آن Pod دسترسی داشته باشید.

برای نمایش این قابلیت، می‌توانید یک Pod ایجاد کنید که به‌صورت دوره‌ای متنی را هم در جریان خروجی استاندارد و هم در جریان خطای استاندارد می‌نویسد.

debug/counter-pod-err.yaml
apiVersion: v1
kind: Pod
metadata:
  name: counter-err
spec:
  containers:
  - name: count
    image: busybox:1.28
    args: [/bin/sh, -c,
            'i=0; while true; do echo "$i: $(date)"; echo "$i: err" >&2 ; i=$((i+1)); sleep 1; done']

برای اجرای این Pod از دستور زیر استفاده کنید:

kubectl apply -f https://k8s.io/examples/debug/counter-pod-err.yaml

برای دریافت تنها جریان لاگ stderr می‌توانید دستور زیر را اجرا کنید:

kubectl get --raw "/api/v1/namespaces/default/pods/counter-err/log?stream=Stderr"

برای جزئیات بیشتر به مستندات kubectl logs مراجعه کنید.

نحوه مدیریت لاگ‌های کانتینر توسط نودها

یک container runtime هر خروجی تولیدشده به جریان‌های stdout و stderr یک برنامه کانتینری‌شده را مدیریت و هدایت می‌کند. container runtimeهای مختلف این کار را به شیوه‌های متفاوتی پیاده‌سازی می‌کنند؛ با این حال، یکپارچگی با kubelet به‌صورت قالب لاگ‌گیری CRI استانداردسازی شده است.

به‌طور پیش‌فرض، اگر یک کانتینر راه‌اندازی مجدد شود، kubelet یک کانتینر خاتمه‌یافته را به‌همراه لاگ‌هایش نگه می‌دارد. اگر یک Pod از نود اخراج شود، تمام کانتینرهای متناظر آن نیز به‌همراه لاگ‌هایشان اخراج می‌شوند.

kubelet لاگ‌ها را از طریق یک قابلیت ویژه API کوبرنتیز در دسترس کلاینت‌ها قرار می‌دهد. روش معمول دسترسی به آن اجرای kubectl logs است.

چرخش لاگ (Log rotation)

وضعیت ویژگی: Kubernetes v1.21 [stable] (پایدار)

kubelet مسئول چرخش لاگ‌های کانتینر و مدیریت ساختار دایرکتوری لاگ‌ها است. kubelet این اطلاعات را (با استفاده از CRI) به container runtime ارسال می‌کند و runtime لاگ‌های کانتینر را در مکان داده‌شده می‌نویسد.

می‌توانید دو تنظیم پیکربندی kubelet را (configuration settings) یعنی containerLogMaxSize (پیش‌فرض 10Mi) و containerLogMaxFiles (پیش‌فرض 5) با استفاده از فایل پیکربندی kubelet تنظیم کنید. این تنظیمات به شما امکان می‌دهند به‌ترتیب بیشینه اندازه هر فایل لاگ و بیشینه تعداد فایل‌های مجاز برای هر کانتینر را پیکربندی کنید.

برای انجام چرخش کارآمد لاگ در کلاسترهایی که حجم لاگ‌های تولیدشده توسط بار کاری در آن‌ها زیاد است، kubelet سازوکاری نیز برای تنظیم نحوه چرخش لاگ‌ها فراهم می‌کند؛ از جمله اینکه چند چرخش هم‌زمان لاگ می‌تواند انجام شود و لاگ‌ها در چه بازه‌ای پایش و در صورت نیاز چرخانده شوند. می‌توانید دو تنظیم پیکربندی kubelet را (configuration settings) یعنی containerLogMaxWorkers و containerLogMonitorInterval را با استفاده از فایل پیکربندی kubelet تنظیم کنید.

وقتی kubectl logs را مانند مثال لاگ‌گیری پایه اجرا می‌کنید، kubelet روی نود درخواست را مدیریت می‌کند و مستقیماً از فایل لاگ می‌خواند. kubelet محتوای فایل لاگ را برمی‌گرداند.

توجه:

تنها محتوای آخرین فایل لاگ از طریق kubectl logs در دسترس است.

برای مثال، اگر یک Pod ‏40 MiB لاگ بنویسد و kubelet لاگ‌ها را پس از هر 10 MiB بچرخاند، اجرای kubectl logs حداکثر 10MiB داده برمی‌گرداند.

لاگ‌های اجزای سیستم

دو نوع جزء سیستمی وجود دارد: اجزایی که معمولاً درون یک کانتینر اجرا می‌شوند، و اجزایی که مستقیماً در اجرای کانتینرها نقش دارند. برای مثال:

  • kubelet و container runtime درون کانتینر اجرا نمی‌شوند. kubelet کانتینرهای شما را (که در Podها گروه‌بندی شده‌اند) اجرا می‌کند.
  • زمان‌بند کوبرنتیز، controller manager و سرور API درون Podها اجرا می‌شوند (معمولاً به‌صورت Podهای ایستا). جزء etcd در control plane اجرا می‌شود و بیشتر اوقات نیز به‌صورت یک Pod ایستا اجرا می‌شود. اگر کلاستر شما از kube-proxy استفاده می‌کند، معمولاً آن را به‌صورت یک DaemonSet اجرا می‌کنید.

مکان‌های لاگ {#log-location-node}

نحوه نوشتن لاگ‌ها توسط kubelet و container runtime به سیستم‌عاملی که نود استفاده می‌کند بستگی دارد:

Linux

در نودهای لینوکسی که از systemd استفاده می‌کنند، kubelet و container runtime به‌طور پیش‌فرض در journald می‌نویسند. برای خواندن ژورنال systemd از journalctl استفاده می‌کنید؛ برای مثال: journalctl -u kubelet.

اگر systemd وجود نداشته باشد، kubelet و container runtime در فایل‌های .log در دایرکتوری /var/log می‌نویسند. اگر می‌خواهید لاگ‌ها در جای دیگری نوشته شوند، می‌توانید kubelet را به‌طور غیرمستقیم از طریق ابزار کمکی kube-log-runner اجرا کنید و از آن ابزار برای هدایت لاگ‌های kubelet به دایرکتوری دلخواه خود استفاده کنید.

به‌طور پیش‌فرض، kubelet به container runtime شما دستور می‌دهد لاگ‌ها را در دایرکتوری‌هایی درون /var/log/pods بنویسد.

برای اطلاعات بیشتر درباره kube-log-runner، لاگ‌های سیستم را بخوانید.

Windows

به‌طور پیش‌فرض، kubelet لاگ‌ها را در فایل‌هایی درون دایرکتوری C:\var\logs می‌نویسد (توجه کنید که این C:\var\log نیست).

اگرچه C:\var\log مکان پیش‌فرض کوبرنتیز برای این لاگ‌ها است، چند ابزار استقرار کلاستر نودهای ویندوزی را طوری تنظیم می‌کنند که به‌جای آن در C:\var\log\kubelet لاگ بنویسند.

اگر می‌خواهید لاگ‌ها در جای دیگری نوشته شوند، می‌توانید kubelet را به‌طور غیرمستقیم از طریق ابزار کمکی kube-log-runner اجرا کنید و از آن ابزار برای هدایت لاگ‌های kubelet به دایرکتوری دلخواه خود استفاده کنید.

با این حال، به‌طور پیش‌فرض، kubelet به container runtime شما دستور می‌دهد لاگ‌ها را درون دایرکتوری C:\var\log\pods بنویسد.

برای اطلاعات بیشتر درباره kube-log-runner، لاگ‌های سیستم را بخوانید.


اجزای کلاستر کوبرنتیز که درون Podها اجرا می‌شوند، در فایل‌هایی درون دایرکتوری /var/log می‌نویسند و سازوکار پیش‌فرض لاگ‌گیری را دور می‌زنند (این اجزا در ژورنال systemd نمی‌نویسند). می‌توانید از سازوکارهای ذخیره‌سازی کوبرنتیز استفاده کنید تا ذخیره‌سازی پایدار را به کانتینری که جزء را اجرا می‌کند نگاشت کنید.

kubelet امکان تغییر دایرکتوری لاگ‌های Pod را از مسیر پیش‌فرض /var/log/pods به یک مسیر سفارشی فراهم می‌کند. این تنظیم با پیکربندی پارامتر podLogsDir در فایل پیکربندی kubelet انجام می‌شود.

احتیاط:

توجه به این نکته مهم است که مکان پیش‌فرض /var/log/pods مدت زمان طولانی مورد استفاده بوده است و برخی فرایندها ممکن است به‌طور ضمنی این مسیر را فرض کنند. بنابراین، تغییر این پارامتر باید با احتیاط و با مسئولیت خود شما انجام شود.

نکته دیگری که باید در نظر داشت این است که kubelet از قرار گرفتن این مکان روی همان دیسک /var پشتیبانی می‌کند. در غیر این صورت، اگر لاگ‌ها روی سیستم فایلی جدا از /var باشند، kubelet میزان استفاده از آن سیستم فایل را ردیابی نخواهد کرد و در صورت پر شدن آن ممکن است مشکلاتی پیش بیاید.

برای جزئیات درباره etcd و لاگ‌های آن، مستندات etcd را ببینید. در اینجا نیز می‌توانید از سازوکارهای ذخیره‌سازی کوبرنتیز استفاده کنید تا ذخیره‌سازی پایدار را به کانتینری که جزء را اجرا می‌کند نگاشت کنید.

توجه:

اگر اجزای کلاستر کوبرنتیز (مانند زمان‌بند) را طوری مستقر کنید که در یک حجم (volume) مشترک از نود والد لاگ بنویسند، باید بررسی کنید و اطمینان یابید که چرخش این لاگ‌ها انجام می‌شود. کوبرنتیز چرخش این لاگ‌ها را مدیریت نمی‌کند.

ممکن است سیستم‌عامل شما به‌طور خودکار نوعی چرخش لاگ را پیاده‌سازی کند؛ برای مثال، اگر دایرکتوری /var/log را به یک Pod ایستا برای یک جزء به اشتراک بگذارید، چرخش لاگ در سطح نود با فایل موجود در آن دایرکتوری همانند فایلی رفتار می‌کند که یک جزء خارج از کوبرنتیز نوشته است.

برخی ابزارهای استقرار این چرخش لاگ را در نظر می‌گیرند و آن را خودکار می‌کنند؛ برخی دیگر این کار را بر عهده شما می‌گذارند.

معماری‌های لاگ‌گیری در سطح کلاستر {#cluster-level-logging-architectures}

اگرچه کوبرنتیز راهکار بومی برای لاگ‌گیری در سطح کلاستر ارائه نمی‌دهد، چند رویکرد رایج وجود دارد که می‌توانید در نظر بگیرید. گزینه‌ها عبارت‌اند از:

  • استفاده از یک عامل لاگ‌گیری در سطح نود که روی هر نود اجرا می‌شود.
  • افزودن یک کانتینر sidecar اختصاصی برای لاگ‌گیری در Pod برنامه.
  • ارسال مستقیم لاگ‌ها از درون برنامه به یک backend.

استفاده از عامل لاگ‌گیری نود

می‌توانید با قرار دادن یک عامل لاگ‌گیری در سطح نود روی هر نود، لاگ‌گیری در سطح کلاستر را پیاده‌سازی کنید. عامل لاگ‌گیری ابزاری اختصاصی است که لاگ‌ها را در دسترس قرار می‌دهد یا آن‌ها را به یک backend ارسال می‌کند. معمولاً عامل لاگ‌گیری کانتینری است که به دایرکتوری حاوی فایل‌های لاگ همه کانتینرهای برنامه روی آن نود دسترسی دارد.

از آنجا که عامل لاگ‌گیری باید روی هر نود اجرا شود، توصیه می‌شود عامل به‌صورت یک DaemonSet اجرا شود.

لاگ‌گیری در سطح نود فقط یک عامل برای هر نود ایجاد می‌کند و به هیچ تغییری در برنامه‌هایی که روی نود اجرا می‌شوند نیاز ندارد.

کانتینرها در stdout و stderr می‌نویسند، اما قالب مورد توافقی وجود ندارد. یک عامل در سطح نود این لاگ‌ها را جمع‌آوری می‌کند و برای تجمیع ارسال می‌کند.

استفاده از کانتینر sidecar همراه با عامل لاگ‌گیری {#sidecar-container-with-logging-agent}

می‌توانید از کانتینر sidecar به یکی از روش‌های زیر استفاده کنید:

  • کانتینر sidecar لاگ‌های برنامه را به stdout خودش استریم می‌کند.
  • کانتینر sidecar یک عامل لاگ‌گیری اجرا می‌کند که برای برداشت لاگ‌ها از یک کانتینر برنامه پیکربندی شده است.

کانتینر sidecar استریم‌کننده

با اینکه کانتینرهای sidecar را وادار کنید در جریان‌های stdout و stderr خودشان بنویسند، می‌توانید از kubelet و عامل لاگ‌گیری‌ای که از قبل روی هر نود اجرا می‌شود بهره ببرید. کانتینرهای sidecar لاگ‌ها را از یک فایل، یک سوکت یا journald می‌خوانند. هر کانتینر sidecar لاگ را در جریان stdout یا stderr خودش چاپ می‌کند.

این رویکرد به شما امکان می‌دهد چند جریان لاگ را از بخش‌های مختلف برنامه‌تان جدا کنید؛ بخش‌هایی که ممکن است از نوشتن در stdout یا stderr پشتیبانی نکنند. منطق هدایت لاگ‌ها حداقلی است، بنابراین سربار قابل‌توجهی ندارد. افزون بر این، چون stdout و stderr توسط kubelet مدیریت می‌شوند، می‌توانید از ابزارهای داخلی مانند kubectl logs استفاده کنید.

برای مثال، یک Pod یک کانتینر واحد اجرا می‌کند و آن کانتینر با دو قالب متفاوت در دو فایل لاگ مجزا می‌نویسد. مانیفست این Pod به‌صورت زیر است:

admin/logging/two-files-counter-pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: counter
spec:
  containers:
  - name: count
    image: busybox:1.28
    args:
    - /bin/sh
    - -c
    - >
      i=0;
      while true;
      do
        echo "$i: $(date)" >> /var/log/1.log;
        echo "$(date) INFO $i" >> /var/log/2.log;
        i=$((i+1));
        sleep 1;
      done
    volumeMounts:
    - name: varlog
      mountPath: /var/log
  volumes:
  - name: varlog
    emptyDir: {}

توصیه نمی‌شود ورودی‌های لاگ با قالب‌های مختلف در یک جریان لاگ نوشته شوند، حتی اگر موفق شده باشید هر دو جزء را به جریان stdout کانتینر هدایت کنید. در عوض، می‌توانید دو کانتینر sidecar ایجاد کنید. هر کانتینر sidecar می‌تواند یک فایل لاگ مشخص را از یک حجم (volume) مشترک دنبال (tail) کند و سپس لاگ‌ها را به جریان stdout خودش هدایت کند.

مانیفست یک Pod که دو کانتینر sidecar دارد به‌صورت زیر است:

admin/logging/two-files-counter-pod-streaming-sidecar.yaml
apiVersion: v1
kind: Pod
metadata:
  name: counter
spec:
  containers:
  - name: count
    image: busybox:1.28
    args:
    - /bin/sh
    - -c
    - >
      i=0;
      while true;
      do
        echo "$i: $(date)" >> /var/log/1.log;
        echo "$(date) INFO $i" >> /var/log/2.log;
        i=$((i+1));
        sleep 1;
      done
    volumeMounts:
    - name: varlog
      mountPath: /var/log
  - name: count-log-1
    image: busybox:1.28
    args: [/bin/sh, -c, 'tail -n+1 -F /var/log/1.log']
    volumeMounts:
    - name: varlog
      mountPath: /var/log
  - name: count-log-2
    image: busybox:1.28
    args: [/bin/sh, -c, 'tail -n+1 -F /var/log/2.log']
    volumeMounts:
    - name: varlog
      mountPath: /var/log
  volumes:
  - name: varlog
    emptyDir: {}

اکنون وقتی این Pod را اجرا می‌کنید، می‌توانید با اجرای دستورات زیر به هر جریان لاگ به‌صورت جداگانه دسترسی پیدا کنید:

kubectl logs counter count-log-1

خروجی مشابه زیر است:

0: Fri Apr  1 11:42:26 UTC 2022
1: Fri Apr  1 11:42:27 UTC 2022
2: Fri Apr  1 11:42:28 UTC 2022
...

kubectl logs counter count-log-2

خروجی مشابه زیر است:

Fri Apr  1 11:42:29 UTC 2022 INFO 0
Fri Apr  1 11:42:30 UTC 2022 INFO 0
Fri Apr  1 11:42:31 UTC 2022 INFO 0
...

اگر در کلاستر خود یک عامل در سطح نود نصب کرده باشید، آن عامل این جریان‌های لاگ را بدون هیچ پیکربندی بیشتری به‌طور خودکار برمی‌دارد. در صورت تمایل، می‌توانید عامل را طوری پیکربندی کنید که خطوط لاگ را بسته به کانتینر مبدأ تجزیه (parse) کند.

حتی برای Podهایی که مصرف CPU و حافظه پایینی دارند (در حد چند میلی‌کور برای CPU و چند مگابایت برای حافظه)، نوشتن لاگ‌ها در یک فایل و سپس استریم آن‌ها به stdout می‌تواند میزان ذخیره‌سازی موردنیاز شما روی نود را دو برابر کند. اگر برنامه‌ای دارید که در یک فایل واحد می‌نویسد، توصیه می‌شود به‌جای پیاده‌سازی رویکرد کانتینر sidecar استریم‌کننده، /dev/stdout را به‌عنوان مقصد تنظیم کنید.

از کانتینرهای sidecar همچنین می‌توان برای چرخش فایل‌های لاگی استفاده کرد که خود برنامه نمی‌تواند آن‌ها را بچرخاند. نمونه‌ای از این رویکرد، یک کانتینر کوچک است که به‌صورت دوره‌ای logrotate را اجرا می‌کند. با این حال، استفاده مستقیم از stdout و stderr و واگذار کردن سیاست‌های چرخش و نگهداری به kubelet ساده‌تر است.

کانتینر sidecar همراه با عامل لاگ‌گیری

اگر عامل لاگ‌گیری در سطح نود برای شرایط شما به‌اندازه کافی انعطاف‌پذیر نیست، می‌توانید یک کانتینر sidecar با یک عامل لاگ‌گیری جداگانه ایجاد کنید که به‌طور مشخص برای اجرا همراه با برنامه شما پیکربندی کرده‌اید.

توجه:

استفاده از عامل لاگ‌گیری در یک کانتینر sidecar می‌تواند به مصرف قابل‌توجه منابع منجر شود. علاوه بر این، نمی‌توانید با kubectl logs به آن لاگ‌ها دسترسی پیدا کنید، زیرا توسط kubelet کنترل نمی‌شوند.

در اینجا دو مانیفست نمونه آمده است که می‌توانید برای پیاده‌سازی یک کانتینر sidecar همراه با عامل لاگ‌گیری از آن‌ها استفاده کنید. مانیفست اول شامل یک ConfigMap برای پیکربندی fluentd است.

admin/logging/fluentd-sidecar-config.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: fluentd-config
data:
  fluentd.conf: |
    <source>
      type tail
      format none
      path /var/log/1.log
      pos_file /var/log/1.log.pos
      tag count.format1
    </source>

    <source>
      type tail
      format none
      path /var/log/2.log
      pos_file /var/log/2.log.pos
      tag count.format2
    </source>

    <match **>
      type google_cloud
    </match>
توجه:

در پیکربندی‌های نمونه، می‌توانید fluentd را با هر عامل لاگ‌گیری دیگری جایگزین کنید که از هر منبعی درون یک کانتینر برنامه می‌خواند.

مانیفست دوم یک Pod را توصیف می‌کند که یک کانتینر sidecar دارد و fluentd را اجرا می‌کند. این Pod حجمی (volume) را mount می‌کند که fluentd می‌تواند داده‌های پیکربندی خود را از آن برداشت کند.

admin/logging/two-files-counter-pod-agent-sidecar.yaml
apiVersion: v1
kind: Pod
metadata:
  name: counter
spec:
  containers:
  - name: count
    image: busybox:1.28
    args:
    - /bin/sh
    - -c
    - >
      i=0;
      while true;
      do
        echo "$i: $(date)" >> /var/log/1.log;
        echo "$(date) INFO $i" >> /var/log/2.log;
        i=$((i+1));
        sleep 1;
      done
    volumeMounts:
    - name: varlog
      mountPath: /var/log
  - name: count-agent
    image: registry.k8s.io/fluentd-gcp:1.30
    env:
    - name: FLUENTD_ARGS
      value: -c /etc/fluentd-config/fluentd.conf
    volumeMounts:
    - name: varlog
      mountPath: /var/log
    - name: config-volume
      mountPath: /etc/fluentd-config
  volumes:
  - name: varlog
    emptyDir: {}
  - name: config-volume
    configMap:
      name: fluentd-config

در دسترس قرار دادن مستقیم لاگ‌ها از برنامه

لاگ‌گیری در سطح کلاستر که لاگ‌ها را مستقیماً از هر برنامه در دسترس قرار می‌دهد یا ارسال می‌کند، خارج از محدوده کوبرنتیز است.

گام‌های بعدی

  • درباره لاگ‌های سیستمی کوبرنتیز مطالعه کنید
  • درباره ردیابی (Trace) برای اجزای سیستمی کوبرنتیز بیاموزید
  • یاد بگیرید چگونه پیام خاتمه را سفارشی‌سازی کنید که کوبرنتیز هنگام شکست‌خوردن یک Pod ثبت می‌کند
