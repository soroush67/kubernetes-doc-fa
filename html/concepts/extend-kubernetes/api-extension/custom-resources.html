منابع سفارشی

منابع سفارشی (custom resources) نمونه‌هایی از انواع منبع هستند که از طریق افزونه‌های API به کوبرنتیز اضافه می‌شوند. این صفحه توضیح می‌دهد که چه زمانی باید یک منبع سفارشی به کلاستر کوبرنتیز خود اضافه کنید و چه زمانی از یک سرویس مستقل استفاده کنید. همچنین دو روش افزودن منابع سفارشی و چگونگی انتخاب میان آن‌ها را شرح می‌دهد.

منابع سفارشی

یک منبع نقطهٔ پایانی (endpoint) در API کوبرنتیز است که مجموعه‌ای از آبجکت‌های API از یک نوع مشخص را ذخیره می‌کند؛ برای مثال، منبع داخلی pods شامل مجموعه‌ای از آبجکت‌های Pod است.

یک منبع سفارشی افزونه‌ای بر API کوبرنتیز است که لزوماً در یک نصب پیش‌فرض کوبرنتیز در دسترس نیست. این منبع نمایانگر سفارشی‌سازی یک نصب مشخص از کوبرنتیز است. با این حال، اکنون بسیاری از قابلیت‌های اصلی کوبرنتیز با استفاده از منابع سفارشی ساخته می‌شوند و همین امر کوبرنتیز را ماژولارتر می‌کند.

منابع سفارشی می‌توانند از طریق ثبت پویا در یک کلاستر در حال اجرا ظاهر یا ناپدید شوند، و مدیران کلاستر می‌توانند منابع سفارشی را مستقل از خود کلاستر به‌روزرسانی کنند. پس از نصب یک منبع سفارشی، کاربران می‌توانند با استفاده از kubectl آبجکت‌های آن را ایجاد کنند و به آن‌ها دسترسی داشته باشند، درست همان‌طور که برای منابع داخلی مانند Pods این کار را انجام می‌دهند.

کنترل‌کننده‌های سفارشی

منابع سفارشی به‌تنهایی به شما امکان می‌دهند داده‌های ساخت‌یافته را ذخیره و بازیابی کنید. هنگامی که یک منبع سفارشی را با یک کنترل‌کنندهٔ سفارشی ترکیب می‌کنید، منابع سفارشی یک API اعلانی (declarative API) واقعی فراهم می‌کنند.

API اعلانی کوبرنتیز تفکیک مسئولیت‌ها را الزامی می‌کند. شما وضعیت مطلوب منبع خود را اعلام می‌کنید. کنترل‌کنندهٔ کوبرنتیز وضعیت فعلی آبجکت‌های کوبرنتیز را با وضعیت مطلوبی که اعلام کرده‌اید همگام نگه می‌دارد. این رویکرد در تقابل با یک API دستوری (imperative) است که در آن به سرور دستور می‌دهید چه کاری انجام دهد.

می‌توانید یک کنترل‌کنندهٔ سفارشی را روی یک کلاستر در حال اجرا، مستقل از چرخهٔ عمر کلاستر، مستقر و به‌روزرسانی کنید. کنترل‌کننده‌های سفارشی می‌توانند با هر نوع منبعی کار کنند، اما به‌ویژه هنگامی که با منابع سفارشی ترکیب شوند مؤثر هستند. الگوی Operator منابع سفارشی و کنترل‌کننده‌های سفارشی را با هم ترکیب می‌کند. می‌توانید از کنترل‌کننده‌های سفارشی برای رمزگذاری دانش دامنه برای برنامه‌های مشخص در قالب افزونه‌ای بر API کوبرنتیز استفاده کنید.

آیا باید یک منبع سفارشی به کلاستر کوبرنتیز خود اضافه کنم؟

هنگام ایجاد یک API جدید، بررسی کنید که آیا API خود را با APIهای کلاستر کوبرنتیز تجمیع کنید یا اجازه دهید API شما مستقل باقی بماند.

تجمیع API را در نظر بگیرید اگر: API مستقل را ترجیح دهید اگر:
API شما اعلانی است. API شما با مدل اعلانی سازگار نیست.
می‌خواهید انواع جدید شما با استفاده از kubectl قابل خواندن و نوشتن باشند. پشتیبانی kubectl لازم نیست
می‌خواهید انواع جدید خود را در کنار انواع داخلی، در یک رابط کاربری کوبرنتیز مانند داشبورد مشاهده کنید. پشتیبانی رابط کاربری کوبرنتیز لازم نیست.
در حال توسعهٔ یک API جدید هستید. از قبل برنامه‌ای دارید که API شما را ارائه می‌دهد و به‌خوبی کار می‌کند.
حاضرید محدودیت قالبی را که کوبرنتیز بر مسیرهای منابع REST اعمال می‌کند، مانند API Groupها و Namespaceها، بپذیرید. (به مرور کلی API مراجعه کنید.) برای سازگاری با یک REST API از پیش تعریف‌شده، به مسیرهای REST مشخصی نیاز دارید.
منابع شما به‌طور طبیعی در محدودهٔ یک کلاستر یا فضاهای نام یک کلاستر قرار می‌گیرند. منابع با محدودهٔ کلاستر یا فضای نام مناسب نیستند؛ به کنترل بر جزئیات مسیرهای منابع نیاز دارید.
می‌خواهید از قابلیت‌های پشتیبانی API کوبرنتیز دوباره استفاده کنید. به آن قابلیت‌ها نیاز ندارید.

APIهای اعلانی {#declarative-apis}

در یک API اعلانی، معمولاً:

  • API شما از تعداد نسبتاً کمی آبجکت (منبع) نسبتاً کوچک تشکیل شده است.
  • آبجکت‌ها پیکربندی برنامه‌ها یا زیرساخت را تعریف می‌کنند.
  • آبجکت‌ها نسبتاً به‌ندرت به‌روزرسانی می‌شوند.
  • انسان‌ها اغلب نیاز دارند آبجکت‌ها را بخوانند و بنویسند.
  • عملیات اصلی روی آبجکت‌ها از نوع CRUD (ایجاد، خواندن، به‌روزرسانی و حذف) است.
  • تراکنش‌های میان آبجکت‌ها لازم نیست: API نمایانگر یک وضعیت مطلوب است، نه یک وضعیت دقیق.

APIهای دستوری اعلانی نیستند. نشانه‌هایی که ممکن است API شما اعلانی نباشد عبارت‌اند از:

  • کلاینت می‌گوید «این کار را انجام بده» و سپس پس از اتمام کار، یک پاسخ همگام دریافت می‌کند.
  • کلاینت می‌گوید «این کار را انجام بده» و سپس یک شناسهٔ عملیات دریافت می‌کند و باید یک آبجکت Operation جداگانه را بررسی کند تا از تکمیل درخواست مطمئن شود.
  • دربارهٔ فراخوانی رویه از راه دور (RPC) صحبت می‌کنید.
  • ذخیره‌سازی مستقیم حجم زیادی از داده؛ برای مثال، بیش از چند کیلوبایت برای هر آبجکت، یا بیش از هزاران آبجکت.
  • به دسترسی با پهنای باند بالا (ده‌ها درخواست پایدار در ثانیه) نیاز است.
  • ذخیرهٔ داده‌های کاربر نهایی (مانند تصاویر، اطلاعات هویتی شخصی و غیره) یا سایر داده‌های بزرگ‌مقیاس که برنامه‌ها پردازش می‌کنند.
  • عملیات طبیعی روی آبجکت‌ها از نوع CRUD نیست.
  • API را نمی‌توان به‌آسانی در قالب آبجکت‌ها مدل‌سازی کرد.
  • تصمیم گرفته‌اید عملیات در انتظار را با یک شناسهٔ عملیات یا یک آبجکت عملیات نمایش دهید.

آیا باید از ConfigMap استفاده کنم یا از یک منبع سفارشی؟

اگر هر یک از موارد زیر صدق می‌کند، از ConfigMap استفاده کنید:

  • یک قالب فایل پیکربندی موجود و به‌خوبی مستندشده وجود دارد، مانند mysql.cnf یا pom.xml.
  • می‌خواهید کل پیکربندی را در یک کلید از ConfigMap قرار دهید.
  • کاربرد اصلی فایل پیکربندی این است که برنامه‌ای که در یک Pod روی کلاستر شما اجرا می‌شود فایل را مصرف کند تا خود را پیکربندی نماید.
  • مصرف‌کنندگان فایل ترجیح می‌دهند آن را از طریق فایلی در یک Pod یا متغیر محیطی در یک پاد مصرف کنند، نه از طریق API کوبرنتیز.
  • می‌خواهید هنگام به‌روزرسانی فایل، به‌روزرسانی‌های تدریجی (rolling update) را از طریق Deployment و موارد مشابه انجام دهید.
توجه:

برای داده‌های حساس از یک Secret استفاده کنید که مشابه ConfigMap اما امن‌تر است.

اگر بیشتر موارد زیر صدق می‌کند، از یک منبع سفارشی (CRD یا API تجمیع‌شده) استفاده کنید:

  • می‌خواهید از کتابخانه‌های کلاینت و CLIهای کوبرنتیز برای ایجاد و به‌روزرسانی منبع جدید استفاده کنید.
  • پشتیبانی سطح بالا از kubectl می‌خواهید؛ برای مثال، kubectl get my-object object-name.
  • می‌خواهید خودکارسازی جدیدی بسازید که به‌روزرسانی‌های آبجکت جدید را زیر نظر بگیرد و سپس عملیات CRUD را روی آبجکت‌های دیگر انجام دهد، یا برعکس.
  • می‌خواهید خودکارسازی‌ای بنویسید که به‌روزرسانی‌های آبجکت را مدیریت کند.
  • می‌خواهید از قراردادهای API کوبرنتیز مانند .spec، .status و .metadata استفاده کنید.
  • می‌خواهید آبجکت یک انتزاع بر روی مجموعه‌ای از منابع کنترل‌شده، یا خلاصه‌ای از منابع دیگر باشد.

افزودن منابع سفارشی

کوبرنتیز دو روش برای افزودن منابع سفارشی به کلاستر شما فراهم می‌کند:

  • CRDها ساده هستند و می‌توان آن‌ها را بدون هیچ برنامه‌نویسی ایجاد کرد.
  • تجمیع API به برنامه‌نویسی نیاز دارد، اما کنترل بیشتری بر رفتارهای API، مانند نحوهٔ ذخیره‌سازی داده‌ها و تبدیل میان نسخه‌های API، فراهم می‌کند.

کوبرنتیز این دو گزینه را برای برآوردن نیازهای کاربران مختلف ارائه می‌دهد تا نه سهولت استفاده و نه انعطاف‌پذیری فدا نشود.

APIهای تجمیع‌شده سرورهای API فرعی هستند که پشت سرور API اصلی قرار می‌گیرند و سرور اصلی نقش پروکسی را ایفا می‌کند. این ترتیب تجمیع API(AA) نامیده می‌شود. از دید کاربران، API کوبرنتیز گسترش‌یافته به نظر می‌رسد.

CRDها به کاربران اجازه می‌دهند بدون افزودن سرور API دیگری، انواع جدیدی از منابع ایجاد کنند. برای استفاده از CRDها لازم نیست تجمیع API را درک کنید.

صرف‌نظر از نحوهٔ نصب، منابع جدید «منابع سفارشی» نامیده می‌شوند تا از منابع داخلی کوبرنتیز (مانند پادها) متمایز شوند.

توجه:

از به‌کارگیری یک منبع سفارشی به‌عنوان محل ذخیره‌سازی داده‌های برنامه، کاربر نهایی یا پایش خودداری کنید: طراحی‌های معماری که داده‌های برنامه را درون API کوبرنتیز ذخیره می‌کنند، معمولاً نشان‌دهندهٔ طراحی‌ای با وابستگی بیش از حد تنگاتنگ هستند.

از نظر معماری، معماری‌های برنامه‌های ابرزاد (cloud native) وابستگی سست میان اجزا را ترجیح می‌دهند. اگر بخشی از بار کاری شما برای عملکرد روزمرهٔ خود به یک سرویس پشتیبان نیاز دارد، آن سرویس پشتیبان را به‌عنوان یک جزء اجرا کنید یا آن را به‌صورت یک سرویس خارجی مصرف کنید. به این ترتیب، بار کاری شما برای عملکرد عادی خود به API کوبرنتیز وابسته نخواهد بود.

CustomResourceDefinitionها

منبع API CustomResourceDefinition به شما امکان می‌دهد منابع سفارشی تعریف کنید. تعریف یک آبجکت CRD، منبع سفارشی جدیدی با نام و طرح‌واره‌ای (schema) که مشخص می‌کنید ایجاد می‌کند. API کوبرنتیز منبع سفارشی شما را ارائه می‌دهد و ذخیره‌سازی آن را مدیریت می‌کند. نام خود آبجکت CRD باید یک نام زیردامنهٔ DNS معتبر باشد که از نام منبع تعریف‌شده و گروه API آن مشتق می‌شود؛ برای جزئیات بیشتر به چگونگی ایجاد یک CRD مراجعه کنید. افزون بر این، نام آبجکتی که kind/منبع آن توسط یک CRD تعریف شده است نیز باید یک نام زیردامنهٔ DNS معتبر باشد.

این کار شما را از نوشتن سرور API اختصاصی برای مدیریت منبع سفارشی بی‌نیاز می‌کند، اما ماهیت عمومی این پیاده‌سازی به این معناست که انعطاف‌پذیری کمتری نسبت به تجمیع سرور API دارید.

برای نمونه‌ای از نحوهٔ ثبت یک منبع سفارشی جدید، کار با نمونه‌های نوع منبع جدید خود و استفاده از یک کنترل‌کننده برای مدیریت رویدادها، به نمونهٔ کنترل‌کنندهٔ سفارشی مراجعه کنید.

تجمیع سرور API {#api-server-aggregation}

معمولاً هر منبع در API کوبرنتیز به کدی نیاز دارد که درخواست‌های REST را مدیریت کند و ذخیره‌سازی پایدار آبجکت‌ها را بر عهده بگیرد. سرور API اصلی کوبرنتیز منابع داخلی مانند pods و services را مدیریت می‌کند و همچنین می‌تواند منابع سفارشی را به‌صورت عمومی از طریق CRDها مدیریت کند.

لایهٔ تجمیع به شما اجازه می‌دهد با نوشتن و استقرار سرور API اختصاصی خود، پیاده‌سازی‌های تخصصی برای منابع سفارشی‌تان ارائه دهید. سرور API اصلی درخواست‌های مربوط به منابع سفارشی‌ای را که شما مدیریت می‌کنید به سرور API شما واگذار می‌کند و به این ترتیب آن‌ها را در اختیار همهٔ کلاینت‌های خود قرار می‌دهد.

انتخاب روشی برای افزودن منابع سفارشی

استفاده از CRDها آسان‌تر است. APIهای تجمیع‌شده انعطاف‌پذیرتر هستند. روشی را انتخاب کنید که به بهترین شکل نیازهای شما را برآورده می‌کند.

معمولاً CRDها در موارد زیر انتخاب مناسبی هستند:

  • تعداد انگشت‌شماری فیلد دارید
  • از منبع درون شرکت خود یا به‌عنوان بخشی از یک پروژهٔ متن‌باز کوچک (در مقابل یک محصول تجاری) استفاده می‌کنید

مقایسهٔ سهولت استفاده

ایجاد CRDها از APIهای تجمیع‌شده آسان‌تر است.

CRDها API تجمیع‌شده
به برنامه‌نویسی نیاز ندارند. کاربران می‌توانند هر زبانی را برای یک کنترل‌کنندهٔ CRD انتخاب کنند. به برنامه‌نویسی و ساخت فایل باینری و ایمیج نیاز دارد.
سرویس اضافه‌ای برای اجرا وجود ندارد؛ CRDها توسط سرور API مدیریت می‌شوند. سرویسی اضافه که باید ایجاد شود و ممکن است دچار خرابی شود.
پس از ایجاد CRD، به پشتیبانی مستمر نیازی نیست. هر رفع اشکالی به‌عنوان بخشی از ارتقاهای عادی Master کوبرنتیز اعمال می‌شود. ممکن است لازم باشد به‌طور دوره‌ای رفع اشکال‌ها را از upstream دریافت کنید و سرور API تجمیع‌شده را دوباره بسازید و به‌روزرسانی کنید.
نیازی به مدیریت چند نسخه از API خود ندارید؛ برای مثال، هنگامی که کلاینت این منبع را در اختیار دارید، می‌توانید آن را همگام با API ارتقا دهید. باید چند نسخه از API خود را مدیریت کنید؛ برای مثال، هنگام توسعهٔ افزونه‌ای برای اشتراک‌گذاری با همگان.

قابلیت‌های پیشرفته و انعطاف‌پذیری

APIهای تجمیع‌شده قابلیت‌های پیشرفته‌تر API و امکان سفارشی‌سازی سایر قابلیت‌ها را ارائه می‌دهند؛ برای مثال، لایهٔ ذخیره‌سازی.

اعتبارسنجی به کاربران کمک می‌کند از خطاها جلوگیری کنند و به شما اجازه می‌دهد API خود را مستقل از کلاینت‌هایتان تکامل دهید. این قابلیت‌ها زمانی بیشترین کاربرد را دارند که کلاینت‌های زیادی وجود داشته باشند که نتوانند همگی هم‌زمان به‌روزرسانی شوند. بله. بیشتر اعتبارسنجی‌ها را می‌توان در CRD با استفاده از اعتبارسنجی OpenAPI v3.0 مشخص کرد. feature gate با نام CRDValidationRatcheting اجازه می‌دهد اعتبارسنجی‌های ناموفقی که با OpenAPI مشخص شده‌اند نادیده گرفته شوند، به شرطی که بخش ناموفق منبع تغییر نکرده باشد. هر اعتبارسنجی دیگری با افزودن یک Validating Webhook پشتیبانی می‌شود. بله، بررسی‌های اعتبارسنجی دلخواه
مقداردهی پیش‌فرض به بالا مراجعه کنید بله، یا از طریق کلیدواژهٔ default در اعتبارسنجی OpenAPI v3.0 (GA در نسخهٔ 1.17)، یا از طریق یک Mutating Webhook (هرچند این مورد هنگام خواندن آبجکت‌های قدیمی از etcd اجرا نمی‌شود). بله
چندنسخه‌ای امکان ارائهٔ یک آبجکت یکسان از طریق دو نسخهٔ API را فراهم می‌کند. می‌تواند تغییرات API مانند تغییر نام فیلدها را آسان‌تر کند. اگر نسخه‌های کلاینت خود را در اختیار دارید، اهمیت کمتری دارد. بله بله
ذخیره‌سازی سفارشی اگر به ذخیره‌سازی با حالت کارایی متفاوت (برای مثال، یک پایگاه دادهٔ سری زمانی به‌جای ذخیره‌ساز کلید-مقدار) یا جداسازی برای امنیت (برای مثال، رمزنگاری اطلاعات حساس و غیره) نیاز دارید خیر بله
منطق کسب‌وکار سفارشی انجام بررسی‌ها یا اقدامات دلخواه هنگام ایجاد، خواندن، به‌روزرسانی یا حذف یک آبجکت بله، با استفاده از Webhookها. بله
زیرمنبع Scale به سیستم‌هایی مانند HorizontalPodAutoscaler و PodDisruptionBudget اجازه می‌دهد با منبع جدید شما تعامل داشته باشند بله بله
زیرمنبع Status کنترل دسترسی دقیقی را فراهم می‌کند که در آن کاربر بخش spec را می‌نویسد و کنترل‌کننده بخش status را. امکان افزایش Generation آبجکت را هنگام تغییر داده‌های منبع سفارشی فراهم می‌کند (به بخش‌های spec و status جداگانه در منبع نیاز دارد) بله بله
سایر زیرمنابع افزودن عملیاتی غیر از CRUD، مانند «logs» یا «exec». خیر بله
strategic-merge-patch نقاط پایانی جدید از PATCH با Content-Type: application/strategic-merge-patch+json پشتیبانی می‌کنند. برای به‌روزرسانی آبجکت‌هایی مفید است که ممکن است هم به‌صورت محلی و هم توسط سرور تغییر کنند. برای اطلاعات بیشتر، به «به‌روزرسانی درجای آبجکت‌های API با استفاده از kubectl patch» مراجعه کنید خیر بله
Protocol Buffers منبع جدید از کلاینت‌هایی که می‌خواهند از Protocol Buffers استفاده کنند پشتیبانی می‌کند خیر بله
طرح‌وارهٔ OpenAPI آیا طرح‌وارهٔ OpenAPI (swagger) برای انواعی وجود دارد که بتوان آن را به‌صورت پویا از سرور دریافت کرد؟ آیا با اطمینان از اینکه فقط فیلدهای مجاز تنظیم می‌شوند، کاربر در برابر غلط املایی در نام فیلدها محافظت می‌شود؟ آیا انواع داده الزامی می‌شوند (به عبارت دیگر، یک int را در یک فیلد string قرار ندهید)؟ بله، بر اساس طرح‌وارهٔ اعتبارسنجی OpenAPI v3.0 (GA در نسخهٔ 1.16). بله
نام نمونه آیا این سازوکار توسعه محدودیتی بر نام آبجکت‌هایی که kind/منبع آن‌ها به این روش تعریف شده است اعمال می‌کند؟ بله، نام چنین آبجکتی باید یک نام زیردامنهٔ DNS معتبر باشد. خیر

قابلیت‌های مشترک {#common-features}

هنگامی که یک منبع سفارشی را، چه از طریق CRD و چه از طریق AA، ایجاد می‌کنید، در مقایسه با پیاده‌سازی آن بیرون از پلتفرم کوبرنتیز، قابلیت‌های فراوانی برای API خود به دست می‌آورید:

قابلیت کارکرد
CRUD نقاط پایانی جدید از عملیات پایهٔ CRUD از طریق HTTP و kubectl پشتیبانی می‌کنند
Watch نقاط پایانی جدید از عملیات Watch کوبرنتیز از طریق HTTP پشتیبانی می‌کنند
کشف (Discovery) کلاینت‌هایی مانند kubectl و داشبورد به‌طور خودکار عملیات فهرست‌کردن، نمایش و ویرایش فیلد را روی منابع شما ارائه می‌دهند
json-patch نقاط پایانی جدید از PATCH با Content-Type: application/json-patch+json پشتیبانی می‌کنند
merge-patch نقاط پایانی جدید از PATCH با Content-Type: application/merge-patch+json پشتیبانی می‌کنند
HTTPS نقاط پایانی جدید از HTTPS استفاده می‌کنند
احراز هویت داخلی دسترسی به افزونه برای احراز هویت از سرور API اصلی (لایهٔ تجمیع) استفاده می‌کند
مجوزدهی داخلی دسترسی به افزونه می‌تواند از همان مجوزدهی مورد استفادهٔ سرور API اصلی دوباره استفاده کند؛ برای مثال، RBAC.
Finalizerها حذف منابع افزونه را تا زمان انجام پاک‌سازی خارجی مسدود می‌کنند.
Admission Webhookها در هر عملیات ایجاد/به‌روزرسانی/حذف، مقادیر پیش‌فرض را تنظیم و منابع افزونه را اعتبارسنجی می‌کنند.
نمایش در UI/CLI Kubectl و داشبورد می‌توانند منابع افزونه را نمایش دهند.
تنظیم‌نشده در برابر خالی کلاینت‌ها می‌توانند فیلدهای تنظیم‌نشده را از فیلدهای با مقدار صفر تشخیص دهند.
تولید کتابخانه‌های کلاینت کوبرنتیز کتابخانه‌های کلاینت عمومی و همچنین ابزارهایی برای تولید کتابخانه‌های کلاینت مخصوص هر نوع فراهم می‌کند.
برچسب‌ها و حاشیه‌نویسی‌ها فرادادهٔ مشترک میان آبجکت‌ها که ابزارها می‌دانند چگونه آن را برای منابع اصلی و سفارشی ویرایش کنند.

آماده‌سازی برای نصب یک منبع سفارشی

پیش از افزودن یک منبع سفارشی به کلاستر خود، باید از چند نکته آگاه باشید.

کد شخص ثالث و نقاط خرابی جدید

اگرچه ایجاد یک CRD به‌طور خودکار هیچ نقطهٔ خرابی جدیدی اضافه نمی‌کند (برای مثال، از طریق اجرای کد شخص ثالث روی سرور API شما)، اما بسته‌ها (برای مثال، Chartها) یا سایر بسته‌های نصب اغلب علاوه بر CRDها، یک Deployment از کد شخص ثالث را نیز شامل می‌شوند که منطق کسب‌وکار یک منبع سفارشی جدید را پیاده‌سازی می‌کند.

نصب یک سرور API تجمیع‌شده همواره مستلزم اجرای یک Deployment جدید است.

ذخیره‌سازی

منابع سفارشی به همان شیوهٔ ConfigMapها فضای ذخیره‌سازی مصرف می‌کنند. ایجاد تعداد بسیار زیادی منبع سفارشی ممکن است فضای ذخیره‌سازی سرور API شما را بیش از حد بارگذاری کند.

منابع سفارشی بر اساس نسخهٔ ذخیره‌سازی فعلی منبع که در spec مربوط به CRD تعریف شده است، در ذخیره‌ساز قرار می‌گیرند. هر به‌روزرسانی یک منبع سفارشی از نسخهٔ ذخیره‌سازی تعریف‌شدهٔ فعلی برای ذخیرهٔ منبع استفاده خواهد کرد. همهٔ نسخه‌های دیگر برای عملکرد صحیح یا باید همهٔ فیلدهای آن نسخه را داشته باشند یا تبدیل‌هایی را تعریف کنند.

سرورهای API تجمیع‌شده ممکن است از همان ذخیره‌ساز سرور API اصلی استفاده کنند که در این صورت همان هشدار صدق می‌کند.

احراز هویت، مجوزدهی و ممیزی

CRDها همواره از همان احراز هویت، مجوزدهی و ثبت گزارش ممیزی استفاده می‌کنند که منابع داخلی سرور API شما به کار می‌برند.

اگر برای مجوزدهی از RBAC استفاده می‌کنید، بیشتر نقش‌های RBAC دسترسی به منابع جدید را اعطا نمی‌کنند (به‌جز نقش cluster-admin یا هر نقشی که با قواعد wildcard ایجاد شده باشد). باید دسترسی به منابع جدید را به‌طور صریح اعطا کنید. CRDها و APIهای تجمیع‌شده اغلب همراه با تعاریف نقش جدید برای انواعی که اضافه می‌کنند عرضه می‌شوند.

سرورهای API تجمیع‌شده ممکن است از همان احراز هویت، مجوزدهی و ممیزی سرور API اصلی استفاده کنند یا نکنند.

دسترسی به یک منبع سفارشی

برای دسترسی به منابع سفارشی می‌توان از کتابخانه‌های کلاینت کوبرنتیز استفاده کرد. همهٔ کتابخانه‌های کلاینت از منابع سفارشی پشتیبانی نمی‌کنند. کتابخانه‌های کلاینت Go و Python از آن‌ها پشتیبانی می‌کنند.

هنگامی که یک منبع سفارشی اضافه می‌کنید، می‌توانید با استفاده از موارد زیر به آن دسترسی داشته باشید:

  • kubectl
  • کلاینت پویای کوبرنتیز.
  • یک کلاینت REST که خودتان می‌نویسید.
  • کلاینتی که با استفاده از ابزارهای تولید کلاینت کوبرنتیز تولید شده است (تولید چنین کلاینتی کاری پیشرفته است، اما برخی پروژه‌ها ممکن است کلاینتی را همراه با CRD یا AA ارائه دهند).

انتخابگرهای فیلد منابع سفارشی

انتخابگرهای فیلد به کلاینت‌ها اجازه می‌دهند منابع سفارشی را بر اساس مقدار یک یا چند فیلد منبع انتخاب کنند.

همهٔ منابع سفارشی از انتخابگرهای فیلد metadata.name و metadata.namespace پشتیبانی می‌کنند.

فیلدهای اعلام‌شده در یک CustomResourceDefinition نیز در صورتی که در فیلد spec.versions[*].selectableFields آن CustomResourceDefinition گنجانده شده باشند، می‌توانند همراه با انتخابگرهای فیلد استفاده شوند.

فیلدهای قابل انتخاب برای منابع سفارشی {#crd-selectable-fields}

وضعیت ویژگی: Kubernetes [] ()

فیلد spec.versions[*].selectableFields در یک CustomResourceDefinition را می‌توان برای اعلام اینکه کدام فیلدهای دیگر در یک منبع سفارشی می‌توانند در انتخابگرهای فیلد استفاده شوند به کار برد.

مثال زیر فیلدهای .spec.color و .spec.size را به‌عنوان فیلدهای قابل انتخاب اضافه می‌کند.

customresourcedefinition/shirt-resource-definition.yaml
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: shirts.stable.example.com
spec:
  group: stable.example.com
  scope: Namespaced
  names:
    plural: shirts
    singular: shirt
    kind: Shirt
  versions:
  - name: v1
    served: true
    storage: true
    schema:
      openAPIV3Schema:
        type: object
        properties:
          spec:
            type: object
            properties:
              color:
                type: string
              size:
                type: string
    selectableFields:
    - jsonPath: .spec.color
    - jsonPath: .spec.size
    additionalPrinterColumns:
    - jsonPath: .spec.color
      name: Color
      type: string
    - jsonPath: .spec.size
      name: Size
      type: string

سپس می‌توان از انتخابگرهای فیلد برای دریافت فقط منابعی با color برابر blue استفاده کرد:

kubectl get shirts.stable.example.com --field-selector spec.color=blue

خروجی باید به این صورت باشد:

NAME       COLOR  SIZE
example1   blue   S
example2   blue   M
