گسترش کوبرنتیز

روش‌های گوناگون برای تغییر رفتار کلاستر کوبرنتیز شما.

کوبرنتیز بسیار پیکربندی‌پذیر و گسترش‌پذیر است. به همین دلیل، به‌ندرت پیش می‌آید که لازم باشد از کد پروژه کوبرنتیز انشعاب (fork) بگیرید یا برای آن وصله (patch) ارسال کنید.

این راهنما گزینه‌های سفارشی‌سازی کلاستر کوبرنتیز را شرح می‌دهد. مخاطب آن اپراتورهای کلاستر هستند که می‌خواهند بدانند چگونه کلاستر کوبرنتیز خود را با نیازهای محیط کاری‌شان سازگار کنند. توسعه‌دهندگانی که قصد دارند توسعه‌دهنده پلتفرم یا مشارکت‌کننده پروژه کوبرنتیز شوند نیز می‌توانند از این راهنما به‌عنوان مقدمه‌ای بر نقاط و الگوهای گسترش موجود، و نیز مزایا، معایب و محدودیت‌های آن‌ها بهره ببرند.

رویکردهای سفارشی‌سازی را می‌توان به‌طور کلی به دو دسته تقسیم کرد: پیکربندی که تنها شامل تغییر آرگومان‌های خط فرمان، فایل‌های پیکربندی محلی یا منابع API است؛ و افزونه‌ها که اجرای برنامه‌های اضافی، سرویس‌های شبکه‌ای اضافی یا هر دو را در بر می‌گیرند. موضوع اصلی این سند افزونه‌ها است.

پیکربندی

فایل‌های پیکربندی و آرگومان‌های فرمان در بخش مرجع مستندات آنلاین شرح داده شده‌اند و برای هر فایل اجرایی صفحه‌ای جداگانه وجود دارد:

  • kube-apiserver
  • kube-controller-manager
  • kube-scheduler
  • kubelet
  • kube-proxy

در سرویس‌های میزبانی‌شده کوبرنتیز یا توزیع‌هایی با نصب مدیریت‌شده، همیشه نمی‌توان آرگومان‌های فرمان و فایل‌های پیکربندی را تغییر داد. هنگامی هم که تغییرپذیر باشند، معمولاً فقط اپراتور کلاستر می‌تواند آن‌ها را تغییر دهد. افزون بر این، ممکن است در نسخه‌های آینده کوبرنتیز تغییر کنند و تنظیم آن‌ها ممکن است به راه‌اندازی مجدد فرایندها نیاز داشته باشد. به همین دلایل، تنها زمانی باید از آن‌ها استفاده کرد که گزینه دیگری وجود نداشته باشد.

APIهای سیاست داخلی، مانند ResourceQuota، NetworkPolicy و کنترل دسترسی مبتنی بر نقش (RBAC)، APIهای داخلی کوبرنتیز هستند که تنظیمات سیاست را به‌صورت اعلانی (declarative) فراهم می‌کنند. این APIها معمولاً حتی در سرویس‌های میزبانی‌شده کوبرنتیز و نصب‌های مدیریت‌شده نیز قابل استفاده‌اند. APIهای سیاست داخلی از همان قراردادهای سایر منابع کوبرنتیز، مانند Podها، پیروی می‌کنند. هنگامی که از یک API سیاست پایدار استفاده می‌کنید، مانند سایر APIهای کوبرنتیز از یک سیاست پشتیبانی مشخص بهره‌مند می‌شوید. به همین دلایل، هر جا مناسب باشد، استفاده از APIهای سیاست بر فایل‌های پیکربندی و آرگومان‌های فرمان ترجیح داده می‌شود.

افزونه‌ها

افزونه‌ها مؤلفه‌های نرم‌افزاری هستند که کوبرنتیز را گسترش می‌دهند و عمیقاً با آن یکپارچه می‌شوند. این مؤلفه‌ها کوبرنتیز را برای پشتیبانی از انواع جدید و گونه‌های تازه‌ای از سخت‌افزار سازگار می‌کنند.

بسیاری از مدیران کلاستر از نمونه‌ای میزبانی‌شده یا یک توزیع از کوبرنتیز استفاده می‌کنند. این کلاسترها با افزونه‌های از پیش نصب‌شده عرضه می‌شوند. در نتیجه، بیشتر کاربران کوبرنتیز نیازی به نصب افزونه ندارند و تعداد کاربرانی که باید افزونه جدیدی بنویسند از این هم کمتر است.

الگوهای گسترش

کوبرنتیز طوری طراحی شده است که بتوان آن را با نوشتن برنامه‌های کلاینت خودکار کرد. هر برنامه‌ای که از API کوبرنتیز بخواند و/یا در آن بنویسد، می‌تواند خودکارسازی مفیدی فراهم کند. خودکارسازی می‌تواند درون کلاستر یا بیرون از آن اجرا شود. با پیروی از راهنمایی‌های این سند می‌توانید خودکارسازی‌هایی با دسترس‌پذیری بالا و مقاوم بنویسید. خودکارسازی معمولاً با هر کلاستر کوبرنتیزی، از جمله کلاسترهای میزبانی‌شده و نصب‌های مدیریت‌شده، کار می‌کند.

برای نوشتن برنامه‌های کلاینتی که به‌خوبی با کوبرنتیز کار کنند، الگوی مشخصی به نام الگوی کنترل‌کننده وجود دارد. کنترل‌کننده‌ها معمولاً فیلد .spec یک آبجکت را می‌خوانند، در صورت لزوم کارهایی انجام می‌دهند و سپس فیلد .status آن آبجکت را به‌روزرسانی می‌کنند.

هر کنترل‌کننده یک کلاینت API کوبرنتیز است. هنگامی که خود کوبرنتیز نقش کلاینت را دارد و یک سرویس راه دور را فراخوانی می‌کند، کوبرنتیز این را وب‌هوک (webhook) می‌نامد. به آن سرویس راه دور بک‌اند وب‌هوک گفته می‌شود. وب‌هوک‌ها نیز، مانند کنترل‌کننده‌های سفارشی، یک نقطه شکست اضافه می‌کنند.

توجه:

بیرون از کوبرنتیز، اصطلاح «وب‌هوک» معمولاً به سازوکاری برای اعلان‌های ناهمگام اشاره دارد که در آن، فراخوانی وب‌هوک به‌عنوان اعلانی یک‌طرفه به سیستم یا مؤلفه‌ای دیگر عمل می‌کند. در اکوسیستم کوبرنتیز، حتی فراخوانی‌های همگام HTTP نیز اغلب «وب‌هوک» نامیده می‌شوند.

در مدل وب‌هوک، کوبرنتیز یک درخواست شبکه‌ای به سرویسی راه دور ارسال می‌کند. در مدل جایگزین، یعنی پلاگین باینری، کوبرنتیز یک فایل اجرایی (برنامه) را اجرا می‌کند. پلاگین‌های باینری را kubelet (برای نمونه پلاگین‌های ذخیره‌سازی CSI و پلاگین‌های شبکه CNI) و kubectl (به گسترش kubectl با پلاگین‌ها مراجعه کنید) به کار می‌برند.

نقاط گسترش

این نمودار نقاط گسترش یک کلاستر کوبرنتیز و کلاینت‌هایی را که به آن دسترسی دارند نشان می‌دهد.

راهنمای شکل

  1. کاربران اغلب با استفاده از kubectl با API کوبرنتیز تعامل دارند. پلاگین‌ها رفتار کلاینت‌ها را سفارشی می‌کنند. افزونه‌های عمومی‌ای وجود دارند که می‌توانند روی کلاینت‌های مختلف اعمال شوند، و روش‌های مشخصی نیز برای گسترش kubectl وجود دارد.

  2. سرور API همه درخواست‌ها را پردازش می‌کند. چندین نوع نقطه گسترش در سرور API امکان احراز هویت درخواست‌ها، مسدود کردن آن‌ها بر اساس محتوایشان، ویرایش محتوا و مدیریت حذف را فراهم می‌کنند. این موارد در بخش افزونه‌های دسترسی به API شرح داده شده‌اند.

  3. سرور API انواع گوناگونی از منابع را ارائه می‌کند. انواع منابع داخلی، مانند pods، را پروژه کوبرنتیز تعریف کرده است و نمی‌توان آن‌ها را تغییر داد. برای آشنایی با گسترش API کوبرنتیز، بخش افزونه‌های API را بخوانید.

  4. زمان‌بند کوبرنتیز تصمیم می‌گیرد که podها روی کدام نودها قرار گیرند. چندین روش برای گسترش زمان‌بندی وجود دارد که در بخش افزونه‌های زمان‌بندی شرح داده شده‌اند.

  5. بخش بزرگی از رفتار کوبرنتیز را برنامه‌هایی به نام کنترل‌کننده‌ها پیاده‌سازی می‌کنند که کلاینت‌های سرور API هستند. کنترل‌کننده‌ها اغلب همراه با منابع سفارشی به کار می‌روند. برای اطلاعات بیشتر، بخش‌های ترکیب APIهای جدید با خودکارسازی و تغییر منابع داخلی را بخوانید.

  6. ‏kubelet روی سرورها (نودها) اجرا می‌شود و کمک می‌کند podها مانند سرورهای مجازی با IP مختص خود در شبکه کلاستر ظاهر شوند. پلاگین‌های شبکه امکان پیاده‌سازی‌های مختلفی از شبکه pod را فراهم می‌کنند.

  7. می‌توانید از پلاگین‌های دستگاه برای یکپارچه‌سازی سخت‌افزار سفارشی یا سایر امکانات ویژه محلیِ نود استفاده کنید و آن‌ها را در اختیار Podهایی بگذارید که در کلاستر شما اجرا می‌شوند. ‏kubelet از کار با پلاگین‌های دستگاه پشتیبانی می‌کند.

    همچنین kubelet حجم‌ها را برای podها و کانتینرهایشان سوار (mount) و پیاده (unmount) می‌کند. با استفاده از پلاگین‌های ذخیره‌سازی می‌توانید پشتیبانی از انواع جدید ذخیره‌سازی و سایر انواع حجم را اضافه کنید.

فلوچارت انتخاب نقطه گسترش {#extension-flowchart}

اگر نمی‌دانید از کجا شروع کنید، این فلوچارت می‌تواند کمک کند. توجه کنید که برخی راه‌حل‌ها ممکن است چند نوع افزونه را در بر گیرند.

افزونه‌های کلاینت

پلاگین‌های kubectl فایل‌های اجرایی جداگانه‌ای هستند که رفتار زیرفرمان‌های مشخصی را اضافه یا جایگزین می‌کنند. ابزار kubectl همچنین می‌تواند با پلاگین‌های اعتبارنامه یکپارچه شود. این افزونه‌ها تنها بر محیط محلی هر کاربر اثر می‌گذارند و از این رو نمی‌توانند سیاست‌هایی را در سطح کل سازمان اعمال کنند.

اگر می‌خواهید ابزار kubectl را گسترش دهید، گسترش kubectl با پلاگین‌ها را بخوانید.

افزونه‌های API

تعریف‌های منبع سفارشی

اگر می‌خواهید کنترل‌کننده‌های جدید، آبجکت‌های پیکربندی برنامه یا سایر APIهای اعلانی تعریف کنید و آن‌ها را با ابزارهای کوبرنتیز مانند kubectl مدیریت کنید، افزودن یک منبع سفارشی (Custom Resource) به کوبرنتیز را در نظر بگیرید.

برای اطلاعات بیشتر درباره منابع سفارشی، راهنمای مفهومی منابع سفارشی را ببینید.

لایه تجمیع API

می‌توانید از لایه تجمیع API کوبرنتیز برای یکپارچه‌سازی API کوبرنتیز با سرویس‌های اضافی مانند Metrics API استفاده کنید.

ترکیب APIهای جدید با خودکارسازی

ترکیب یک API منبع سفارشی با یک حلقه کنترل، الگوی کنترل‌کننده‌ها نامیده می‌شود. اگر کنترل‌کننده شما جای یک اپراتور انسانی را بگیرد که زیرساخت را بر اساس وضعیت مطلوب مستقر می‌کند، آن کنترل‌کننده ممکن است از الگوی اپراتور نیز پیروی کند. الگوی اپراتور برای مدیریت برنامه‌های مشخصی به کار می‌رود؛ معمولاً این‌ها برنامه‌هایی هستند که وضعیت را نگه می‌دارند و مدیریتشان به دقت و مراقبت نیاز دارد.

همچنین می‌توانید APIها و حلقه‌های کنترل سفارشی خود را بسازید تا منابع دیگری مانند ذخیره‌سازی را مدیریت کنند یا سیاست‌هایی (مانند یک محدودیت کنترل دسترسی) تعریف کنند.

تغییر منابع داخلی

هنگامی که API کوبرنتیز را با افزودن منابع سفارشی گسترش می‌دهید، منابع افزوده‌شده همیشه در گروه‌های API جدیدی قرار می‌گیرند. نمی‌توانید گروه‌های API موجود را جایگزین یا تغییر دهید. افزودن یک API به‌طور مستقیم امکان اثرگذاری بر رفتار APIهای موجود (مانند Podها) را به شما نمی‌دهد، اما افزونه‌های دسترسی به API این امکان را فراهم می‌کنند.

افزونه‌های دسترسی به API

هنگامی که درخواستی به سرور API کوبرنتیز می‌رسد، ابتدا احراز هویت و سپس مجوزدهی می‌شود و پس از آن تحت انواع گوناگون کنترل پذیرش (admission control) قرار می‌گیرد (برخی درخواست‌ها در واقع احراز هویت نمی‌شوند و رفتار ویژه‌ای با آن‌ها می‌شود). برای اطلاعات بیشتر درباره این روند، کنترل دسترسی به API کوبرنتیز را ببینید.

هر یک از مراحل روند احراز هویت/مجوزدهی کوبرنتیز نقاط گسترشی ارائه می‌کند.

احراز هویت

احراز هویت سرآیندها یا گواهی‌های موجود در همه درخواست‌ها را به نام کاربریِ کلاینتی که درخواست را ارسال کرده است نگاشت می‌کند.

کوبرنتیز از چندین روش احراز هویت داخلی پشتیبانی می‌کند. اگر این روش‌ها نیازهای شما را برآورده نکنند، کوبرنتیز می‌تواند پشت یک پراکسی احراز هویت قرار گیرد و همچنین می‌تواند توکن موجود در سرآیند Authorization: را برای راستی‌آزمایی به یک سرویس راه دور بفرستد (یک وب‌هوک احراز هویت).

مجوزدهی

مجوزدهی تعیین می‌کند که آیا کاربران مشخصی می‌توانند منابع API را بخوانند، در آن‌ها بنویسند و عملیات دیگری روی آن‌ها انجام دهند یا نه. مجوزدهی در سطح کل منابع عمل می‌کند و بر اساس فیلدهای دلخواه آبجکت‌ها تمایزی قائل نمی‌شود.

اگر گزینه‌های مجوزدهی داخلی نیازهای شما را برآورده نکنند، یک وب‌هوک مجوزدهی امکان فراخوانی کد سفارشی‌ای را فراهم می‌کند که درباره مجوزدهی تصمیم می‌گیرد.

کنترل پذیرش پویا

پس از آنکه درخواستی مجوز گرفت، اگر عملیات نوشتن باشد، از مراحل کنترل پذیرش نیز عبور می‌کند. افزون بر مراحل داخلی، چندین افزونه نیز وجود دارد:

  • وب‌هوک سیاست ایمیج محدود می‌کند که چه ایمیج‌هایی را می‌توان در کانتینرها اجرا کرد.
  • برای گرفتن تصمیم‌های دلخواه در کنترل پذیرش، می‌توان از یک وب‌هوک پذیرش عمومی استفاده کرد. وب‌هوک‌های پذیرش می‌توانند ایجاد یا به‌روزرسانی‌ها را رد کنند. برخی وب‌هوک‌های پذیرش، داده‌های درخواست ورودی را پیش از پردازش بیشتر به دست کوبرنتیز تغییر می‌دهند.

افزونه‌های زیرساخت

پلاگین‌های دستگاه

پلاگین‌های دستگاه به نود امکان می‌دهند منابع جدیدی برای نود (افزون بر منابع داخلی مانند cpu و حافظه) را از طریق یک پلاگین دستگاه کشف کند.

پلاگین‌های ذخیره‌سازی

پلاگین‌های رابط ذخیره‌سازی کانتینر (CSI) راهی برای گسترش کوبرنتیز با پشتیبانی از انواع جدید حجم‌ها فراهم می‌کنند. این حجم‌ها می‌توانند بر پایه ذخیره‌سازی خارجی پایدار باشند، ذخیره‌سازی موقت (ephemeral) فراهم کنند، یا با الگوی سیستم فایل، رابطی فقط‌خواندنی به اطلاعات ارائه دهند.

کوبرنتیز همچنین از پلاگین‌های FlexVolume پشتیبانی می‌کند که از نسخه v1.23 کوبرنتیز منسوخ شده‌اند (و CSI جایگزین آن‌ها شده است).

پلاگین‌های FlexVolume به کاربران امکان می‌دهند انواعی از حجم را سوار کنند که کوبرنتیز به‌طور بومی از آن‌ها پشتیبانی نمی‌کند. هنگامی که Podای را اجرا می‌کنید که به ذخیره‌سازی FlexVolume وابسته است، kubelet یک پلاگین باینری را برای سوار کردن حجم فراخوانی می‌کند. پیشنهاد طراحی بایگانی‌شده FlexVolume جزئیات بیشتری درباره این رویکرد ارائه می‌دهد.

سند پرسش‌های متداول پلاگین‌های حجم کوبرنتیز برای فروشندگان ذخیره‌سازی اطلاعات کلی درباره پلاگین‌های ذخیره‌سازی را در بر دارد.

پلاگین‌های شبکه

کلاستر کوبرنتیز شما برای داشتن یک شبکه Pod کارآمد و پشتیبانی از سایر جنبه‌های مدل شبکه کوبرنتیز، به یک پلاگین شبکه نیاز دارد.

پلاگین‌های شبکه به کوبرنتیز امکان می‌دهند با توپولوژی‌ها و فناوری‌های شبکه گوناگون کار کند.

پلاگین‌های ارائه‌دهنده اعتبارنامه ایمیج kubelet

وضعیت ویژگی: Kubernetes v1.26 [stable] (پایدار)

ارائه‌دهندگان اعتبارنامه ایمیج kubelet پلاگین‌هایی برای kubelet هستند که اعتبارنامه‌های رجیستری ایمیج را به‌صورت پویا بازیابی می‌کنند. سپس این اعتبارنامه‌ها هنگام دریافت ایمیج از رجیستری‌های ایمیج کانتینری که با پیکربندی مطابقت دارند، به کار می‌روند.

این پلاگین‌ها می‌توانند برای به دست آوردن اعتبارنامه‌ها با سرویس‌های خارجی ارتباط برقرار کنند یا از فایل‌های محلی استفاده کنند. به این ترتیب، kubelet نیازی ندارد برای هر رجیستری اعتبارنامه ایستا داشته باشد و می‌تواند از روش‌ها و پروتکل‌های احراز هویت گوناگون پشتیبانی کند.

برای جزئیات پیکربندی پلاگین، پیکربندی ارائه‌دهنده اعتبارنامه ایمیج kubelet را ببینید.

افزونه‌های زمان‌بندی

زمان‌بند نوع ویژه‌ای از کنترل‌کننده است که podها را زیر نظر دارد و آن‌ها را به نودها تخصیص می‌دهد. می‌توان زمان‌بند پیش‌فرض را به‌طور کامل جایگزین کرد و همچنان از سایر مؤلفه‌های کوبرنتیز استفاده کرد، یا چندین زمان‌بند را هم‌زمان اجرا کرد.

این کار بسیار پرزحمت است و تقریباً همه کاربران کوبرنتیز درمی‌یابند که نیازی به تغییر زمان‌بند ندارند.

می‌توانید تعیین کنید کدام پلاگین‌های زمان‌بندی فعال باشند، یا مجموعه‌هایی از پلاگین‌ها را به پروفایل‌های زمان‌بند نام‌گذاری‌شده مختلف مرتبط کنید. همچنین می‌توانید پلاگین خود را بنویسید که با یک یا چند نقطه گسترش kube-scheduler یکپارچه شود.

در نهایت، مؤلفه داخلی kube-scheduler از یک وب‌هوک پشتیبانی می‌کند که به یک بک‌اند HTTP راه دور (افزونه زمان‌بند) اجازه می‌دهد نودهایی را که kube-scheduler برای یک pod انتخاب می‌کند فیلتر کند و/یا اولویت‌بندی کند.

توجه:

با وب‌هوک گسترش‌دهنده زمان‌بند (scheduler extender) تنها می‌توانید بر فیلتر کردن و اولویت‌بندی نودها اثر بگذارید؛ سایر نقاط گسترش از طریق یکپارچه‌سازی وب‌هوک در دسترس نیستند.
