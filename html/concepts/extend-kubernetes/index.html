گسترش کوبرنتیز

روش‌های مختلف برای تغییر رفتار کلاستر کوبرنتیز شما.

کوبرنتیز بسیار پیکربندی‌پذیر و توسعه‌پذیر است. در نتیجه، به‌ندرت نیازی به فورک کردن کد پروژه کوبرنتیز یا ارسال وصله (patch) به آن وجود دارد.

این راهنما گزینه‌های سفارشی‌سازی یک کلاستر کوبرنتیز را شرح می‌دهد. مخاطب آن اپراتورهای کلاستر هستند که می‌خواهند بدانند چگونه کلاستر کوبرنتیز خود را با نیازهای محیط کاری‌شان تطبیق دهند. توسعه‌دهندگانی که قصد دارند توسعه‌دهنده پلتفرم شوند یا مشارکت‌کنندگان پروژه کوبرنتیز نیز این راهنما را به‌عنوان مقدمه‌ای بر نقاط توسعه و الگوهای موجود، به همراه مزایا و محدودیت‌های آن‌ها مفید خواهند یافت.

رویکردهای سفارشی‌سازی را می‌توان به‌طور کلی به دو دسته تقسیم کرد: پیکربندی که فقط شامل تغییر آرگومان‌های خط فرمان، فایل‌های پیکربندی محلی یا منابع API است؛ و افزونه‌ها که شامل اجرای برنامه‌های اضافی، سرویس‌های شبکه‌ای اضافی یا هر دو است. تمرکز اصلی این سند بر افزونه‌ها است.

پیکربندی {#configuration}

فایل‌های پیکربندی و آرگومان‌های خط فرمان در بخش مرجع مستندات آنلاین و با یک صفحه برای هر فایل اجرایی توضیح داده شده‌اند:

  • kube-apiserver
  • kube-controller-manager
  • kube-scheduler
  • kubelet
  • kube-proxy

ممکن است آرگومان‌های خط فرمان و فایل‌های پیکربندی همیشه در یک سرویس کوبرنتیز میزبانی‌شده یا در یک توزیع با نصب مدیریت‌شده قابل تغییر نباشند. در صورتی که قابل تغییر باشند، معمولاً فقط اپراتور کلاستر می‌تواند آن‌ها را تغییر دهد. علاوه بر این، آن‌ها ممکن است در نسخه‌های آتی کوبرنتیز تغییر کنند و تنظیم‌شان ممکن است نیازمند راه‌اندازی مجدد پردازه‌ها باشد. به همین دلایل، باید فقط زمانی از آن‌ها استفاده کرد که گزینه دیگری وجود ندارد.

APIهای سیاست‌گذاری داخلی، مانند ResourceQuota، NetworkPolicy و کنترل دسترسی مبتنی بر نقش (RBAC)، APIهای داخلی کوبرنتیز هستند که تنظیمات سیاست‌گذاری را به‌صورت اعلانی (declarative) فراهم می‌کنند. این APIها معمولاً حتی با سرویس‌های کوبرنتیز میزبانی‌شده و نصب‌های مدیریت‌شده کوبرنتیز نیز قابل استفاده‌اند. APIهای سیاست‌گذاری داخلی از همان قراردادهای سایر منابع کوبرنتیز، مانند Pod، پیروی می‌کنند. وقتی از یک API سیاست‌گذاری پایدار استفاده می‌کنید، مانند سایر APIهای کوبرنتیز از یک سیاست پشتیبانی تعریف‌شده بهره‌مند می‌شوید. به این دلایل، در موارد مناسب، APIهای سیاست‌گذاری بر فایل‌های پیکربندی و آرگومان‌های خط فرمان ترجیح داده می‌شوند.

افزونه‌ها {#extensions}

افزونه‌ها اجزای نرم‌افزاری‌ای هستند که کوبرنتیز را گسترش می‌دهند و به‌طور عمیق با آن یکپارچه می‌شوند. آن‌ها کوبرنتیز را برای پشتیبانی از انواع جدید و انواع تازه‌ای از سخت‌افزار تطبیق می‌دهند.

بسیاری از مدیران کلاستر از یک نمونه کوبرنتیز میزبانی‌شده یا توزیعی استفاده می‌کنند. این کلاسترها با افزونه‌های از پیش نصب‌شده عرضه می‌شوند. در نتیجه، بیشتر کاربران کوبرنتیز نیازی به نصب افزونه نخواهند داشت و شمار کاربرانی که نیاز به نوشتن افزونه‌های جدید دارند حتی کمتر است.

الگوهای افزونه {#extension-patterns}

کوبرنتیز طوری طراحی شده است که با نوشتن برنامه‌های کلاینت خودکارسازی شود. هر برنامه‌ای که از API کوبرنتیز بخواند و/یا در آن بنویسد می‌تواند خودکارسازی مفیدی فراهم کند. خودکارسازی می‌تواند روی کلاستر یا خارج از آن اجرا شود. با پیروی از راهنمایی‌های این سند می‌توانید خودکارسازی‌های بسیار در دسترس و مقاوم بنویسید. خودکارسازی معمولاً با هر کلاستر کوبرنتیز، از جمله کلاسترهای میزبانی‌شده و نصب‌های مدیریت‌شده، کار می‌کند.

الگوی مشخصی برای نوشتن برنامه‌های کلاینت وجود دارد که به‌خوبی با کوبرنتیز کار می‌کند و الگوی کنترل‌کننده نامیده می‌شود. کنترل‌کننده‌ها معمولاً .spec یک آبجکت را می‌خوانند، احتمالاً اقداماتی انجام می‌دهند و سپس .status آبجکت را به‌روزرسانی می‌کنند.

یک کنترل‌کننده کلاینتی برای API کوبرنتیز است. وقتی کوبرنتیز خودش کلاینت باشد و یک سرویس راه دور را فراخوانی کند، کوبرنتیز این را webhook می‌نامد. سرویس راه دور webhook backend نامیده می‌شود. همانند کنترل‌کننده‌های سفارشی، webhookها نیز یک نقطه شکست (point of failure) اضافه می‌کنند.

توجه:

خارج از کوبرنتیز، اصطلاح «webhook» معمولاً به سازوکاری برای اعلان‌های ناهمگام اشاره دارد، که در آن فراخوانی webhook نقش یک اعلان یک‌طرفه به سیستم یا مؤلفه‌ای دیگر را دارد. در اکوسیستم کوبرنتیز، حتی فراخوانی‌های HTTP همگام نیز اغلب «webhook» نامیده می‌شوند.

در مدل webhook، کوبرنتیز یک درخواست شبکه‌ای به یک سرویس راه دور ارسال می‌کند. در مدل جایگزین Plugin باینری، کوبرنتیز یک فایل باینری (برنامه) را اجرا می‌کند. پلاگین‌های باینری توسط kubelet (برای مثال پلاگین‌های ذخیره‌سازی CSI و پلاگین‌های شبکه CNI) و توسط kubectl (به گسترش kubectl با پلاگین‌ها مراجعه کنید) استفاده می‌شوند.

نقاط توسعه {#extension-points}

این نمودار نقاط توسعه در یک کلاستر کوبرنتیز و کلاینت‌هایی را که به آن دسترسی دارند نشان می‌دهد.

راهنمای شکل

  1. کاربران اغلب با استفاده از kubectl با API کوبرنتیز تعامل می‌کنند. پلاگین‌ها رفتار کلاینت‌ها را سفارشی می‌کنند. افزونه‌های عمومی‌ای وجود دارند که می‌توانند برای کلاینت‌های مختلف به‌کار روند، و همچنین روش‌های خاصی برای گسترش kubectl وجود دارد.

  2. سرور API همه درخواست‌ها را مدیریت می‌کند. چند نوع نقطه توسعه در سرور API امکان احراز هویت درخواست‌ها، یا مسدود کردن آن‌ها بر اساس محتوایشان، ویرایش محتوا و مدیریت حذف را فراهم می‌کنند. این موارد در بخش افزونه‌های دسترسی به API شرح داده شده‌اند.

  3. سرور API انواع مختلفی از منابع را ارائه می‌دهد. انواع منابع داخلی، مانند pods، توسط پروژه کوبرنتیز تعریف می‌شوند و قابل تغییر نیستند. برای آشنایی با گسترش API کوبرنتیز، افزونه‌های API را بخوانید.

  4. زمان‌بند کوبرنتیز تصمیم می‌گیرد پادها روی کدام نودها قرار گیرند. راه‌های متعددی برای گسترش زمان‌بندی وجود دارد که در بخش افزونه‌های زمان‌بندی شرح داده شده‌اند.

  5. بخش زیادی از رفتار کوبرنتیز توسط برنامه‌هایی به نام کنترل‌کننده‌ها پیاده‌سازی می‌شود که کلاینت سرور API هستند. کنترل‌کننده‌ها اغلب همراه با منابع سفارشی به‌کار می‌روند. برای اطلاعات بیشتر، ترکیب APIهای جدید با خودکارسازی و تغییر منابع داخلی را بخوانید.

  6. kubelet روی سرورها (نودها) اجرا می‌شود و کمک می‌کند پادها مانند سرورهای مجازی با IPهای مخصوص خود در شبکه کلاستر ظاهر شوند. پلاگین‌های شبکه امکان پیاده‌سازی‌های مختلف شبکه پادها را فراهم می‌کنند.

  7. می‌توانید از پلاگین‌های دستگاه برای یکپارچه‌سازی سخت‌افزار سفارشی یا سایر امکانات ویژه محلی نود استفاده کنید و آن‌ها را در اختیار Podهایی که در کلاستر شما اجرا می‌شوند قرار دهید. kubelet از کار با پلاگین‌های دستگاه پشتیبانی می‌کند.

    kubelet همچنین حجم‌ها (volume) را برای پادها و کانتینرهایشان mount و unmount می‌کند. می‌توانید از پلاگین‌های ذخیره‌سازی برای افزودن پشتیبانی از انواع جدید ذخیره‌سازی و سایر انواع حجم استفاده کنید.

نمودار انتخاب نقطه توسعه {#extension-flowchart}

اگر مطمئن نیستید از کجا شروع کنید، این نمودار می‌تواند کمک کند. توجه داشته باشید که برخی راه‌حل‌ها ممکن است شامل چند نوع افزونه باشند.

افزونه‌های کلاینت {#client-extensions}

پلاگین‌های kubectl فایل‌های باینری جداگانه‌ای هستند که رفتار زیرفرمان‌های مشخصی را اضافه یا جایگزین می‌کنند. ابزار kubectl همچنین می‌تواند با پلاگین‌های اعتبارنامه یکپارچه شود. این افزونه‌ها فقط بر محیط محلی هر کاربر تأثیر می‌گذارند و بنابراین نمی‌توانند سیاست‌های سراسری سایت را اعمال کنند.

اگر می‌خواهید ابزار kubectl را گسترش دهید، گسترش kubectl با پلاگین‌ها را بخوانید.

افزونه‌های API {#api-extensions}

تعریف‌های منبع سفارشی {#custom-resource-definitions}

اگر می‌خواهید کنترل‌کننده‌های جدید، آبجکت‌های پیکربندی برنامه یا سایر APIهای اعلانی تعریف کنید و آن‌ها را با ابزارهای کوبرنتیز مانند kubectl مدیریت کنید، افزودن یک منبع سفارشی (Custom Resource) به کوبرنتیز را در نظر بگیرید.

برای اطلاعات بیشتر درباره منابع سفارشی، راهنمای مفهومی منابع سفارشی را ببینید.

لایه تجمیع API {#api-aggregation-layer}

می‌توانید از لایه تجمیع API کوبرنتیز استفاده کنید تا API کوبرنتیز را با سرویس‌های اضافی مانند Metrics API یکپارچه کنید.

ترکیب APIهای جدید با خودکارسازی {#combining-new-apis-with-automation}

ترکیب یک API منبع سفارشی و یک حلقه کنترل، الگوی کنترل‌کننده‌ها نامیده می‌شود. اگر کنترل‌کننده شما جای یک اپراتور انسانی را می‌گیرد که زیرساخت را بر اساس یک وضعیت مطلوب مستقر می‌کند، آنگاه ممکن است کنترل‌کننده از الگوی اپراتور نیز پیروی کند. الگوی اپراتور برای مدیریت برنامه‌های خاص به‌کار می‌رود؛ معمولاً این‌ها برنامه‌هایی هستند که وضعیت (state) را نگهداری می‌کنند و مدیریت آن‌ها نیازمند دقت است.

همچنین می‌توانید APIهای سفارشی و حلقه‌های کنترل خودتان را برای مدیریت سایر منابع، مانند ذخیره‌سازی، یا برای تعریف سیاست‌ها (مانند محدودیت کنترل دسترسی) بسازید.

تغییر منابع داخلی {#changing-built-in-resources}

وقتی API کوبرنتیز را با افزودن منابع سفارشی گسترش می‌دهید، منابع افزوده‌شده همیشه در گروه‌های API جدید قرار می‌گیرند. نمی‌توانید گروه‌های API موجود را جایگزین یا تغییر دهید. افزودن یک API به‌طور مستقیم به شما اجازه نمی‌دهد رفتار APIهای موجود (مانند Pod) را تحت تأثیر قرار دهید، در حالی که افزونه‌های دسترسی به API چنین امکانی را فراهم می‌کنند.

افزونه‌های دسترسی به API {#api-access-extensions}

وقتی درخواستی به سرور API کوبرنتیز می‌رسد، ابتدا احراز هویت می‌شود، سپس مجوزدهی می‌شود، و پس از آن مشمول انواع مختلفی از کنترل پذیرش (admission control) قرار می‌گیرد (برخی درخواست‌ها در واقع احراز هویت نمی‌شوند و با آن‌ها رفتار ویژه‌ای می‌شود). برای اطلاعات بیشتر درباره این جریان، کنترل دسترسی به API کوبرنتیز را ببینید.

هر یک از مراحل جریان احراز هویت / مجوزدهی در کوبرنتیز نقاط توسعه‌ای ارائه می‌دهد.

احراز هویت {#authentication}

احراز هویت سرصفحه‌ها (headers) یا گواهی‌های موجود در همه درخواست‌ها را به نام کاربری کلاینتی که درخواست را ارسال می‌کند نگاشت می‌کند.

کوبرنتیز چند روش احراز هویت داخلی را پشتیبانی می‌کند. همچنین می‌تواند پشت یک پروکسی احراز هویت قرار گیرد، و در صورتی که این روش‌ها نیازهای شما را برآورده نکنند، می‌تواند توکن موجود در سرصفحه Authorization: را برای تأیید به یک سرویس راه دور ارسال کند (یک webhook احراز هویت).

مجوزدهی {#authorization}

مجوزدهی تعیین می‌کند که کاربران مشخص بتوانند منابع API را بخوانند، بنویسند و عملیات دیگری روی آن‌ها انجام دهند. این فرایند در سطح کل منابع عمل می‌کند -- و بر اساس فیلدهای دلخواه آبجکت تمایز قائل نمی‌شود.

اگر گزینه‌های مجوزدهی داخلی نیازهای شما را برآورده نکنند، یک webhook مجوزدهی امکان فراخوانی کدی سفارشی را فراهم می‌کند که تصمیم مجوزدهی را می‌گیرد.

کنترل پذیرش پویا {#dynamic-admission-control}

پس از مجاز شدن یک درخواست، اگر عملیات نوشتن باشد، از مراحل کنترل پذیرش (Admission Control) نیز عبور می‌کند. علاوه بر مراحل داخلی، چند افزونه وجود دارد:

  • webhook سیاست ایمیج (Image Policy) محدود می‌کند که چه ایمیج‌هایی می‌توانند در کانتینرها اجرا شوند.
  • برای اتخاذ تصمیم‌های دلخواه کنترل پذیرش، می‌توان از یک webhook پذیرش (Admission webhook) عمومی استفاده کرد. webhookهای پذیرش می‌توانند ایجاد یا به‌روزرسانی را رد کنند. برخی webhookهای پذیرش داده‌های درخواست ورودی را پیش از آنکه کوبرنتیز آن را بیشتر پردازش کند، تغییر می‌دهند.

افزونه‌های زیرساخت {#infrastructure-extensions}

پلاگین‌های دستگاه {#device-plugins}

پلاگین‌های دستگاه به یک نود اجازه می‌دهند از طریق یک Device Plugin منابع جدید نود را (علاوه بر منابع داخلی مانند cpu و memory) کشف کند.

پلاگین‌های ذخیره‌سازی {#storage-plugins}

پلاگین‌های Container Storage Interface (CSI) راهی برای گسترش کوبرنتیز با پشتیبانی از انواع جدید حجم فراهم می‌کنند. حجم‌ها می‌توانند توسط ذخیره‌سازی خارجی پایدار پشتیبانی شوند، یا ذخیره‌سازی موقت ارائه دهند، یا یک رابط فقط‌خواندنی برای اطلاعات با استفاده از الگوی سیستم فایل عرضه کنند.

کوبرنتیز همچنین از پلاگین‌های FlexVolume پشتیبانی می‌کند که از کوبرنتیز نسخه v1.23 منسوخ شده‌اند (به نفع CSI).

پلاگین‌های FlexVolume به کاربران اجازه می‌دهند انواع حجمی را که به‌طور بومی توسط کوبرنتیز پشتیبانی نمی‌شوند mount کنند. وقتی Podی را اجرا می‌کنید که به ذخیره‌سازی FlexVolume متکی است، kubelet یک پلاگین باینری را برای mount کردن حجم فراخوانی می‌کند. پیشنهاد طراحی بایگانی‌شده FlexVolume جزئیات بیشتری درباره این رویکرد دارد.

پرسش‌های متداول پلاگین حجم کوبرنتیز برای فروشندگان ذخیره‌سازی شامل اطلاعات عمومی درباره پلاگین‌های ذخیره‌سازی است.

پلاگین‌های شبکه {#network-plugins}

کلاستر کوبرنتیز شما برای داشتن یک شبکه Pod فعال و پشتیبانی از سایر جنبه‌های مدل شبکه کوبرنتیز به یک پلاگین شبکه نیاز دارد.

پلاگین‌های شبکه به کوبرنتیز اجازه می‌دهند با توپولوژی‌ها و فناوری‌های شبکه‌ای مختلف کار کند.

پلاگین‌های ارائه‌دهنده اعتبارنامه ایمیج در kubelet {#kubelet-image-credential-provider-plugins}

وضعیت ویژگی: Kubernetes v1.26 [stable] (پایدار)

ارائه‌دهنده‌های اعتبارنامه ایمیج در kubelet پلاگین‌هایی برای kubelet هستند که اعتبارنامه‌های رجیستری ایمیج را به‌صورت پویا دریافت می‌کنند. سپس این اعتبارنامه‌ها هنگام pull کردن ایمیج‌ها از رجیستری‌های ایمیج کانتینر که با پیکربندی مطابقت دارند، استفاده می‌شوند.

این پلاگین‌ها می‌توانند با سرویس‌های خارجی ارتباط برقرار کنند یا برای دریافت اعتبارنامه‌ها از فایل‌های محلی استفاده کنند. به این ترتیب، kubelet نیازی ندارد برای هر رجیستری اعتبارنامه‌های ثابت داشته باشد و می‌تواند از روش‌ها و پروتکل‌های احراز هویت مختلف پشتیبانی کند.

برای جزئیات پیکربندی پلاگین، به پیکربندی یک ارائه‌دهنده اعتبارنامه ایمیج در kubelet مراجعه کنید.

افزونه‌های زمان‌بندی {#scheduling-extensions}

زمان‌بند نوع ویژه‌ای از کنترل‌کننده است که پادها را مشاهده می‌کند و آن‌ها را به نودها اختصاص می‌دهد. زمان‌بند پیش‌فرض را می‌توان به‌طور کامل جایگزین کرد، در حالی که از سایر مؤلفه‌های کوبرنتیز همچنان استفاده می‌شود، یا چند زمان‌بند می‌توانند هم‌زمان اجرا شوند.

این کار مستلزم تلاش قابل‌توجهی است و تقریباً همه کاربران کوبرنتیز درمی‌یابند که نیازی به تغییر زمان‌بند ندارند.

می‌توانید کنترل کنید کدام پلاگین‌های زمان‌بندی فعال باشند، یا مجموعه‌هایی از پلاگین‌ها را با پروفایل‌های زمان‌بند نام‌دار مختلف مرتبط کنید. همچنین می‌توانید پلاگین خودتان را بنویسید که با یک یا چند مورد از نقاط توسعه kube-scheduler یکپارچه شود.

در نهایت، مؤلفه داخلی kube-scheduler از یک webhook پشتیبانی می‌کند که به یک backend راه دور HTTP (افزونه زمان‌بند) اجازه می‌دهد نودهایی را که kube-scheduler برای یک Pod انتخاب می‌کند فیلتر و/یا اولویت‌بندی کند.

توجه:

با webhook افزونه زمان‌بند (scheduler extender) فقط می‌توانید بر فیلتر کردن نودها و اولویت‌بندی نودها تأثیر بگذارید؛ سایر نقاط توسعه از طریق یکپارچه‌سازی webhook در دسترس نیستند.

گام‌های بعدی

  • درباره افزونه‌های زیرساخت بیشتر بیاموزید
    • پلاگین‌های دستگاه
    • پلاگین‌های شبکه
    • پلاگین‌های ذخیره‌سازی CSI
  • درباره پلاگین‌های kubectl بیاموزید
  • درباره منابع سفارشی بیشتر بیاموزید
  • درباره سرورهای API افزونه بیشتر بیاموزید
  • درباره کنترل پذیرش پویا بیاموزید
  • درباره الگوی اپراتور بیاموزید
