مفاهیم و منابع پشت شبکه‌سازی در کوبرنتیز.

مدل شبکه کوبرنتیز

مدل شبکه کوبرنتیز از چند بخش تشکیل شده است:

  • هر pod در یک کلاستر یک آدرس IP یکتا در سطح کل کلاستر دریافت می‌کند.

    • هر pod فضای نام شبکه (network namespace) خصوصی خود را دارد که میان همه کانتینرهای درون آن pod مشترک است. فرایندهایی که در کانتینرهای مختلفِ یک pod اجرا می‌شوند، می‌توانند از طریق localhost با یکدیگر ارتباط برقرار کنند.

  • شبکه pod (که شبکه کلاستر نیز نامیده می‌شود) ارتباط میان pod‌ها را مدیریت می‌کند. این شبکه تضمین می‌کند که (به‌جز در صورت قطعه‌بندی عمدی شبکه):

    • همه pod‌ها می‌توانند با همه pod‌های دیگر ارتباط برقرار کنند، چه روی یک نود باشند و چه روی نودهای مختلف. pod‌ها می‌توانند مستقیماً و بدون استفاده از پراکسی یا ترجمه آدرس (NAT) با یکدیگر ارتباط برقرار کنند.

      در ویندوز، این قاعده برای pod‌هایی که از شبکه میزبان (host-network) استفاده می‌کنند صدق نمی‌کند.

    • عامل‌های (agents) روی یک نود (مانند daemonهای سیستمی یا kubelet) می‌توانند با همه pod‌های همان نود ارتباط برقرار کنند.

  • API مربوط به Service به شما امکان می‌دهد برای یک سرویس که توسط یک یا چند pod پشتیبان پیاده‌سازی شده است، یک آدرس IP یا نام میزبان پایدار (بلندمدت) فراهم کنید، در حالی که pod‌های تشکیل‌دهنده آن سرویس می‌توانند در طول زمان تغییر کنند.

    • کوبرنتیز آبجکت‌های EndpointSlice را به‌طور خودکار مدیریت می‌کند تا اطلاعاتی درباره pod‌هایی که در حال حاضر پشتیبان یک Service هستند فراهم کند.

    • یک پیاده‌سازی پراکسی سرویس (service proxy)، مجموعه آبجکت‌های Service و EndpointSlice را پایش می‌کند و با استفاده از API‌های سیستم‌عامل یا ارائه‌دهنده ابری برای رهگیری یا بازنویسی بسته‌ها، data plane را برای مسیریابی ترافیک سرویس به backendهای آن برنامه‌ریزی می‌کند.

  • API مربوط به Gateway (یا پیشینِ آن، Ingress) به شما امکان می‌دهد Serviceها را برای کلاینت‌هایی که خارج از کلاستر قرار دارند در دسترس قرار دهید.

    • هنگام استفاده از یک ارائه‌دهنده ابری پشتیبانی‌شده، سازوکار ساده‌تر اما با قابلیت پیکربندی کمتر برای ورود ترافیک به کلاستر از طریق type: LoadBalancer در API مربوط به Service در دسترس است.

  • NetworkPolicy یک API داخلی کوبرنتیز است که به شما امکان می‌دهد ترافیک میان pod‌ها، یا میان pod‌ها و دنیای بیرون را کنترل کنید.

در سامانه‌های کانتینری قدیمی‌تر، میان کانتینرهای روی میزبان‌های مختلف اتصال خودکار وجود نداشت و به همین دلیل اغلب لازم بود میان کانتینرها صریحاً پیوند (link) ایجاد شود یا پورت‌های کانتینر به پورت‌های میزبان نگاشت شوند تا کانتینرهای روی میزبان‌های دیگر بتوانند به آن‌ها دسترسی داشته باشند. در کوبرنتیز به این کارها نیازی نیست؛ مدل کوبرنتیز این است که از نظر تخصیص پورت، نام‌گذاری، کشف سرویس (service discovery)، توزیع بار، پیکربندی برنامه و مهاجرت، با pod‌ها می‌توان تقریباً مانند ماشین‌های مجازی یا میزبان‌های فیزیکی رفتار کرد.

تنها بخش اندکی از این مدل توسط خود کوبرنتیز پیاده‌سازی می‌شود. برای بخش‌های دیگر، کوبرنتیز API‌ها را تعریف می‌کند، اما قابلیت متناظر را مؤلفه‌های خارجی فراهم می‌کنند که برخی از آن‌ها اختیاری هستند:

  • راه‌اندازی فضای نام شبکه pod توسط نرم‌افزار سطح سیستم که Container Runtime Interface را پیاده‌سازی می‌کند انجام می‌شود.

  • خود شبکه pod توسط یک پیاده‌سازی شبکه pod مدیریت می‌شود. در لینوکس، بیشتر container runtimeها برای تعامل با پیاده‌سازی شبکه pod از Container Networking Interface (CNI) استفاده می‌کنند، به همین دلیل این پیاده‌سازی‌ها اغلب افزونه‌های CNI نامیده می‌شوند.

  • کوبرنتیز یک پیاده‌سازی پیش‌فرض برای پراکسی‌سازی سرویس به نام kube proxy ارائه می‌کند، اما برخی پیاده‌سازی‌های شبکه pod به‌جای آن از پراکسی سرویس مخصوص به خود استفاده می‌کنند که یکپارچگی بیشتری با سایر بخش‌های آن پیاده‌سازی دارد.

  • NetworkPolicy نیز معمولاً توسط پیاده‌سازی شبکه pod پیاده‌سازی می‌شود. (برخی پیاده‌سازی‌های ساده‌تر شبکه pod، NetworkPolicy را پیاده‌سازی نمی‌کنند، یا ممکن است مدیر سیستم تصمیم بگیرد شبکه pod را بدون پشتیبانی از NetworkPolicy پیکربندی کند. در این موارد، API همچنان وجود دارد اما هیچ تأثیری نخواهد داشت.)

  • پیاده‌سازی‌های متعددی از Gateway API وجود دارد؛ برخی مختص محیط‌های ابری خاص هستند، برخی بیشتر بر محیط‌های «bare metal» تمرکز دارند و برخی دیگر عمومی‌تر هستند.

گام‌های بعدی

آموزش اتصال برنامه‌ها به Serviceها با یک مثال عملی، شما را با Serviceها و شبکه‌سازی در کوبرنتیز آشنا می‌کند.

شبکه‌سازی کلاستر توضیح می‌دهد که چگونه شبکه کلاستر خود را راه‌اندازی کنید و همچنین مروری بر فناوری‌های دخیل ارائه می‌دهد.

برای آشنایی با مفاهیم خاص شبکه‌سازی، به موارد زیر مراجعه کنید:

  • Service - در دسترس قرار دادن یک برنامه پشت یک endpoint واحد رو به بیرون
  • Ingress - مسیریابی HTTP/HTTPS آگاه از پروتکل با استفاده از URIها، نام‌های میزبان و مسیرها
  • Gateway API - آماده‌سازی پویای زیرساخت و مسیریابی پیشرفته ترافیک
  • Network Policies - کنترل جریان ترافیک در سطح آدرس IP یا پورت (لایه ۳ یا ۴ مدل OSI)
  • DNS برای Serviceها و Pod‌ها - کشف سرویس‌ها در درون کلاستر با استفاده از DNS
