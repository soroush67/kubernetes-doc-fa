استفاده از kubectl برای ایجاد یک Deployment

اهداف

  • با Deploymentهای برنامه آشنا شوید.
  • نخستین برنامهٔ خود را با kubectl روی کوبرنتیز مستقر کنید.

پیش از شروع

دستورهای پوسته در این آموزش از نحو پوستهٔ POSIX استفاده می‌کنند. این نحو را پوسته‌های پیش‌فرض بیشتر سیستم‌های لینوکس و macOS (برای نمونه bash، zsh یا sh) پشتیبانی می‌کنند. کاربران ویندوز برای اجرای دستورها به همان شکلی که نوشته شده‌اند، باید از یک پوستهٔ سازگار با POSIX مانند زیرسیستم ویندوز برای لینوکس (WSL) یا Git Bash استفاده کنند. دستورهایی که از export، $() و ساختارهای مشابه استفاده می‌کنند، با PowerShell یا Command Prompt ویندوز سازگار نیستند.

Deploymentهای کوبرنتیز

هر Deployment مسئول ایجاد و به‌روزرسانی نمونه‌های برنامهٔ شماست.

Note

این آموزش از کانتینری استفاده می‌کند که به معماری AMD64 نیاز دارد. اگر از minikube روی رایانه‌ای با معماری پردازندهٔ دیگری استفاده می‌کنید، می‌توانید minikube را با درایوری امتحان کنید که توانایی شبیه‌سازی AMD64 را دارد؛ برای نمونه، درایور Docker Desktop چنین قابلیتی دارد.

پس از آنکه یک کلاستر کوبرنتیز در حال اجرا در اختیار داشتید، می‌توانید برنامه‌های کانتینری‌شدهٔ خود را روی آن مستقر کنید. برای این کار، یک Deployment کوبرنتیز ایجاد می‌کنید. این Deployment به کوبرنتیز می‌گوید که نمونه‌های برنامهٔ شما را چگونه ایجاد و به‌روزرسانی کند. پس از ایجاد Deployment، ‏control plane کوبرنتیز نمونه‌های برنامهٔ موجود در آن را برای اجرا روی نودهای مختلف کلاستر زمان‌بندی می‌کند.

پس از ایجاد نمونه‌های برنامه، یک کنترل‌کنندهٔ Deployment در کوبرنتیز به‌طور پیوسته بر این نمونه‌ها نظارت می‌کند. اگر نودی که میزبان یک نمونه است از کار بیفتد یا حذف شود، کنترل‌کنندهٔ Deployment آن نمونه را با نمونه‌ای روی نود دیگری از کلاستر جایگزین می‌کند. این کار سازوکاری خودترمیم (self-healing) برای مقابله با خرابی یا نگهداری ماشین‌ها فراهم می‌کند.

در دوران پیش از هماهنگ‌سازی (orchestration)، معمولاً از اسکریپت‌های نصب برای راه‌اندازی برنامه‌ها استفاده می‌شد، اما این اسکریپت‌ها امکان بازیابی پس از خرابی ماشین را فراهم نمی‌کردند. Deploymentهای کوبرنتیز هم نمونه‌های برنامهٔ شما را ایجاد می‌کنند و هم آن‌ها را روی نودها در حال اجرا نگه می‌دارند؛ به این ترتیب، رویکردی بنیادین متفاوت برای مدیریت برنامه‌ها ارائه می‌دهند.

استقرار نخستین برنامه روی کوبرنتیز

برای استقرار برنامه‌ها روی کوبرنتیز، باید آن‌ها را در یکی از قالب‌های کانتینری پشتیبانی‌شده بسته‌بندی کرد.

می‌توانید با استفاده از رابط خط فرمان کوبرنتیز، یعنی kubectl، یک Deployment ایجاد و مدیریت کنید. ابزار kubectl برای تعامل با کلاستر از API کوبرنتیز استفاده می‌کند. در این بخش، رایج‌ترین دستورهای kubectl را که برای ایجاد Deploymentهای اجراکنندهٔ برنامه‌هایتان روی کلاستر کوبرنتیز لازم است، یاد می‌گیرید.

هنگام ایجاد یک Deployment، باید ایمیج کانتینر برنامه و تعداد رپلیکاهایی را که می‌خواهید اجرا شوند مشخص کنید. بعداً می‌توانید با به‌روزرسانی Deployment این اطلاعات را تغییر دهید؛ بخش ۵ و بخش ۶ این دورهٔ آموزشی به چگونگی مقیاس‌دهی و به‌روزرسانی Deploymentها می‌پردازند.

برای نخستین Deployment، از برنامهٔ hello-node استفاده می‌کنید که در یک کانتینر Docker بسته‌بندی شده است و با NGINX همهٔ درخواست‌ها را بازتاب می‌دهد. (اگر تاکنون ایجاد برنامهٔ hello-node و استقرار آن با یک کانتینر را امتحان نکرده‌اید، می‌توانید ابتدا دستورالعمل‌های آموزش Hello Minikube را دنبال کنید.)

همچنین باید kubectl را نصب کرده باشید. اگر به نصب آن نیاز دارید، به صفحهٔ نصب ابزارها مراجعه کنید.

اکنون که می‌دانید Deploymentها چه هستند، بیایید نخستین برنامهٔ خود را مستقر کنیم!

مبانی kubectl

قالب رایج یک دستور kubectl چنین است: kubectl action resource.

این دستور عمل مشخص‌شده (مانند create، describe یا delete) را روی منبع مشخص‌شده (مانند node یا deployment) انجام می‌دهد. برای دریافت اطلاعات بیشتر دربارهٔ پارامترهای ممکن، می‌توانید پس از زیردستور از --help استفاده کنید (برای نمونه: kubectl get nodes --help).

با اجرای دستور kubectl version بررسی کنید که kubectl برای ارتباط با کلاستر شما پیکربندی شده باشد.

بررسی کنید که kubectl نصب شده باشد و بتوانید نسخهٔ کلاینت و نسخهٔ سرور را ببینید.

برای مشاهدهٔ نودهای کلاستر، دستور kubectl get nodes را اجرا کنید.

نودهای در دسترس را می‌بینید. بعداً کوبرنتیز بر اساس منابع در دسترس نودها تصمیم می‌گیرد که برنامهٔ ما را کجا مستقر کند.

استقرار یک برنامه

بیایید نخستین برنامهٔ خود را با دستور kubectl create deployment روی کوبرنتیز مستقر کنیم. باید نام Deployment و محل ایمیج برنامه را مشخص کنیم (برای ایمیج‌هایی که خارج از Docker Hub میزبانی می‌شوند، نشانی کامل مخزن را وارد کنید).

kubectl create deployment kubernetes-bootcamp --image=gcr.io/google-samples/kubernetes-bootcamp:v1

عالی است! با ایجاد یک Deployment، نخستین برنامهٔ خود را مستقر کردید. این کار چند عمل را برای شما انجام داد:

  • نود مناسبی را جست‌وجو کرد که بتوان نمونه‌ای از برنامه را روی آن اجرا کرد (ما تنها ۱ نود در دسترس داریم)
  • برنامه را برای اجرا روی آن نود زمان‌بندی کرد
  • کلاستر را طوری پیکربندی کرد که در صورت نیاز، نمونه را دوباره روی نود جدیدی زمان‌بندی کند

برای فهرست کردن Deploymentها از دستور kubectl get deployments استفاده کنید:

kubectl get deployments

می‌بینیم که ۱ Deployment وجود دارد که یک نمونه از برنامهٔ شما را اجرا می‌کند. این نمونه درون یک کانتینر روی نود شما در حال اجراست.

مشاهدهٔ برنامه

Podهایی که درون کوبرنتیز اجرا می‌شوند، روی شبکه‌ای خصوصی و ایزوله اجرا می‌شوند. این Podها به‌طور پیش‌فرض از سوی Podها و Serviceهای دیگرِ همان کلاستر کوبرنتیز قابل مشاهده‌اند، اما از بیرون آن شبکه دیده نمی‌شوند. هنگامی که از kubectl استفاده می‌کنیم، از طریق یک نقطهٔ پایانی (endpoint) API با برنامهٔ خود ارتباط برقرار می‌کنیم.

گزینه‌های دیگر برای در دسترس قرار دادن برنامه بیرون از کلاستر کوبرنتیز را بعداً در بخش ۴ بررسی خواهیم کرد. همچنین از آنجا که این یک آموزش مقدماتی است، در اینجا جزئیات Pods را توضیح نمی‌دهیم؛ این موضوع در مباحث بعدی پوشش داده خواهد شد.

دستور kubectl proxy می‌تواند پراکسی‌ای ایجاد کند که ارتباطات را به شبکهٔ خصوصی سراسری کلاستر هدایت می‌کند. می‌توان با فشردن control-C پراکسی را متوقف کرد و این پراکسی در طول اجرا هیچ خروجی‌ای نمایش نمی‌دهد.

برای اجرای پراکسی باید یک پنجرهٔ ترمینال دوم باز کنید.

kubectl proxy

پراکسی میزبان شما را به کلاستر کوبرنتیز متصل می‌کند. این پراکسی در ترمینال دوم همچنان در حال اجرا می‌ماند، پس دستورهای زیر را در ترمینال اصلی خود اجرا کنید.

می‌توانید همهٔ آن APIها را که از طریق نقطهٔ پایانی پراکسی میزبانی می‌شوند ببینید. برای نمونه، می‌توانیم با دستور curl نسخه را مستقیماً از طریق API پرس‌وجو کنیم:

curl http://localhost:8001/version
Note

اگر درگاه 8001 در دسترس نیست، مطمئن شوید که kubectl proxyای که پیش‌تر راه‌اندازی کردید، در ترمینال دوم در حال اجراست.

سرور API به‌طور خودکار برای هر Pod، بر اساس نام آن، یک نقطهٔ پایانی ایجاد می‌کند که از طریق پراکسی نیز در دسترس است.

ابتدا باید نام Pod را به دست آوریم و آن را در متغیر محیطی POD_NAME ذخیره کنیم.

export POD_NAME=$(kubectl get pods -o go-template --template '{{range .items}}{{.metadata.name}}{{"\n"}}{{end}}')
echo Name of the Pod: $POD_NAME

با اجرای دستور زیر می‌توانید از طریق API پراکسی‌شده به Pod دسترسی پیدا کنید:

curl http://localhost:8001/api/v1/namespaces/default/pods/$POD_NAME:8080/proxy/

برای آنکه Deployment جدید بدون استفاده از پراکسی در دسترس باشد، به یک Service نیاز است که در بخش ۴ توضیح داده خواهد شد.
