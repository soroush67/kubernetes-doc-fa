نصب درایورها و تخصیص دستگاه‌ها با DRA

وضعیت ویژگی: Kubernetes [] ()

این آموزش نشان می‌دهد که چگونه درایورهای تخصیص پویای منابع (DRA) را در کلاستر خود نصب کنید و چگونه از آن‌ها همراه با APIهای DRA برای تخصیص دستگاه‌ها به Podها استفاده کنید. مخاطب این صفحه مدیران کلاستر هستند.

با تخصیص پویای منابع (DRA)، کلاستر می‌تواند در دسترس بودن و تخصیص منابع سخت‌افزاری را مدیریت کند تا درخواست‌های مبتنی بر Pod برای نیازمندی‌ها و ترجیحات سخت‌افزاری برآورده شوند. برای پشتیبانی از این قابلیت، ترکیبی از مؤلفه‌های داخلی کوبرنتیز (مانند زمان‌بند کوبرنتیز، kubelet و kube-controller-manager) و درایورهای شخص ثالثی که مالکان دستگاه‌ها ارائه می‌کنند (و درایورهای DRA نامیده می‌شوند)، مسئولیت اعلام، تخصیص، آماده‌سازی، اتصال (mount)، بررسی سلامت، لغو آماده‌سازی و پاک‌سازی منابع را در سراسر چرخه عمر Pod به‌طور مشترک بر عهده دارند. این مؤلفه‌ها از طریق مجموعه‌ای از APIهای مخصوص DRA در گروه API resource.k8s.io اطلاعات را با یکدیگر به اشتراک می‌گذارند. این APIها شامل DeviceClassها، ResourceSliceها و ResourceClaimها و همچنین فیلدهای جدیدی در خودِ spec مربوط به Pod هستند.

اهداف

  • استقرار یک درایور DRA نمونه
  • استقرار یک Pod که با استفاده از APIهای DRA یک درخواست سخت‌افزاری (claim) ثبت می‌کند
  • حذف Podای که درخواست دارد

پیش از شروع

کلاستر شما باید از RBAC پشتیبانی کند. می‌توانید این آموزش را روی کلاستری با سازوکار مجوزدهی دیگری نیز امتحان کنید، اما در آن صورت باید مراحل مربوط به تعریف نقش‌ها و مجوزها را با آن سازوکار تطبیق دهید.

باید یک کلاستر کوبرنتیز داشته باشید و ابزار خط فرمان kubectl باید برای ارتباط با کلاستر شما پیکربندی شده باشد. توصیه می‌شود این آموزش را روی کلاستری اجرا کنید که دست‌کم دو نود داشته باشد که نقش میزبان control plane را ندارند. اگر هنوز کلاستری ندارید، می‌توانید با استفاده از minikube یکی بسازید یا از یکی از این محیط‌های آزمایشی کوبرنتیز استفاده کنید:

  • iximiuz Labs
  • Killercoda
  • KodeKloud

این آموزش روی نودهای لینوکسی آزموده شده است، هرچند ممکن است روی انواع دیگر نودها نیز کار کند.

اگر کلاستر شما در حال حاضر کوبرنتیز 1.37 را اجرا نمی‌کند، لطفاً مستندات نسخه‌ای از کوبرنتیز را که قصد استفاده از آن را دارید بررسی کنید.

بررسی وضعیت اولیه کلاستر {#explore-initial-state}

می‌توانید کمی زمان بگذارید و وضعیت اولیه کلاستری را که DRA در آن فعال است مشاهده کنید، به‌ویژه اگر پیش‌تر از این APIها زیاد استفاده نکرده‌اید. اگر برای این آموزش کلاستر جدیدی راه‌اندازی کرده‌اید که هیچ درایوری روی آن نصب نشده و هنوز هیچ درخواست Pod برای برآورده شدن ندارد، خروجی این دستورها هیچ منبعی را نشان نخواهد داد.

  1. فهرست DeviceClassها را دریافت کنید:

    kubectl get deviceclasses

    خروجی مشابه زیر است:

    No resources found

  2. فهرست ResourceSliceها را دریافت کنید:

    kubectl get resourceslices

    خروجی مشابه زیر است:

    No resources found

  3. فهرست ResourceClaimها و ResourceClaimTemplateها را دریافت کنید.

    kubectl get resourceclaims -A
kubectl get resourceclaimtemplates -A

    خروجی مشابه زیر است:

    No resources found
No resources found

تا اینجا تأیید کرده‌اید که DRA در کلاستر فعال است و به‌درستی پیکربندی شده است و هنوز هیچ درایور DRA منبعی را به APIهای DRA اعلام نکرده است.

نصب یک درایور DRA نمونه {#install-example-driver}

درایورهای DRA برنامه‌های شخص ثالثی هستند که روی هر نود کلاستر شما اجرا می‌شوند تا میان سخت‌افزار آن نود و مؤلفه‌های داخلی DRA در کوبرنتیز ارتباط برقرار کنند. روند نصب به درایوری که انتخاب می‌کنید بستگی دارد، اما به احتمال زیاد درایور به‌صورت یک daemonset روی همه نودهای کلاستر یا گروهی از آن‌ها (با استفاده از انتخابگرها یا سازوکارهای مشابه) مستقر می‌شود.

برای دستورالعمل‌های دقیق نصب، مستندات درایور خود را بررسی کنید. این دستورالعمل‌ها ممکن است شامل یک Helm chart، مجموعه‌ای از مانیفست‌ها یا ابزارهای استقرار دیگر باشند.

این آموزش برای نمایش نحوه نصب درایور از یک درایور نمونه استفاده می‌کند که در مخزن kubernetes-sigs/dra-example-driver قرار دارد. این درایور نمونه، GPUهای شبیه‌سازی‌شده‌ای را به کوبرنتیز اعلام می‌کند تا Podهای شما بتوانند با آن‌ها کار کنند.

آماده‌سازی کلاستر برای نصب درایور {#prepare-cluster-driver}

برای ساده‌تر شدن پاک‌سازی، یک فضای نام (namespace) با نام dra-tutorial بسازید:

  1. فضای نام را ایجاد کنید:

    kubectl create namespace dra-tutorial

    در محیط عملیاتی، به احتمال زیاد از ایمیجی استفاده می‌کنید که پیش‌تر توسط سازنده درایور یا سازمان خودتان منتشر یا تأیید شده است، و نودهای شما باید به رجیستری ایمیجی که ایمیج درایور در آن میزبانی می‌شود دسترسی داشته باشند. در این آموزش، برای شبیه‌سازی دسترسی به ایمیج یک درایور DRA، از ایمیج عمومیِ منتشرشده dra-example-driver استفاده می‌کنید.

  2. با اجرای دستور زیر از داخل یکی از نودهای کلاستر، تأیید کنید که نودهای شما به این ایمیج دسترسی دارند:

    docker pull registry.k8s.io/dra-example-driver/dra-example-driver:v0.2.0

استقرار مؤلفه‌های درایور DRA

در این آموزش، مؤلفه‌های حیاتی درایور منبع نمونه را یکی‌یکی با kubectl نصب می‌کنید.

  1. یک DeviceClass بسازید که نمایانگر انواع دستگاه‌هایی باشد که این درایور DRA پشتیبانی می‌کند:
dra/driver-install/deviceclass.yaml
apiVersion: resource.k8s.io/v1
kind: DeviceClass
metadata:
  name: gpu.example.com
spec:
  selectors:
  - cel: 
      expression: "device.driver == 'gpu.example.com'"

```shell
kubectl apply --server-side -f https://k8s.io/examples/dra/driver-install/deviceclass.yaml
```

  1. آبجکت‌های ServiceAccount، ClusterRole و ClusterRoleBinding را بسازید. درایور از این آبجکت‌ها برای کسب مجوز تعامل با API کوبرنتیز در این کلاستر استفاده می‌کند:

    1. ServiceAccount را بسازید:
dra/driver-install/serviceaccount.yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: dra-example-driver-service-account
  namespace: dra-tutorial
  labels:
    app.kubernetes.io/name: dra-example-driver
    app.kubernetes.io/instance: dra-example-driver

    ```shell
    kubectl apply --server-side -f https://k8s.io/examples/dra/driver-install/serviceaccount.yaml
    ```

1.  ClusterRole را بسازید:
dra/driver-install/clusterrole.yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: dra-example-driver-role
rules:
- apiGroups: ["resource.k8s.io"]
  resources: ["resourceclaims"]
  verbs: ["get"]
- apiGroups: [""]
  resources: ["nodes"]
  verbs: ["get"]
- apiGroups: ["resource.k8s.io"]
  resources: ["resourceslices"]
  verbs: ["get", "list", "watch", "create", "update", "patch", "delete"]

    ```shell
    kubectl apply --server-side -f https://k8s.io/examples/dra/driver-install/clusterrole.yaml
    ```

1.  ClusterRoleBinding را بسازید:
dra/driver-install/clusterrolebinding.yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: dra-example-driver-role-binding
subjects:
- kind: ServiceAccount
  name: dra-example-driver-service-account
  namespace: dra-tutorial
roleRef:
  kind: ClusterRole
  name: dra-example-driver-role
  apiGroup: rbac.authorization.k8s.io

    ```shell
    kubectl apply --server-side -f https://k8s.io/examples/dra/driver-install/clusterrolebinding.yaml
    ```
  1. یک priority class برای درایور DRA بسازید. این PriorityClass از پیش‌دستی (preemption) روی مؤلفه درایور DRA جلوگیری می‌کند؛ مؤلفه‌ای که مسئول عملیات مهم چرخه عمر Podهای دارای درخواست است. درباره اولویت و پیش‌دستی Pod اینجا بیشتر بخوانید.
dra/driver-install/priorityclass.yaml
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: dra-driver-high-priority
value: 1000000
globalDefault: false
description: "This priority class should be used for DRA driver pods only."

```shell
kubectl apply --server-side -f https://k8s.io/examples/dra/driver-install/priorityclass.yaml
```
  1. خودِ درایور DRA را به‌صورت یک DaemonSet مستقر کنید که برای اجرای فایل اجرایی درایور نمونه با مجوزهای فراهم‌شده در مراحل بالا پیکربندی شده است. این DaemonSet مجوزهایی را دارد که در مراحل قبل به ServiceAccount اعطا کردید.
dra/driver-install/daemonset.yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: dra-example-driver-kubeletplugin
  namespace: dra-tutorial
  labels:
    app.kubernetes.io/name: dra-example-driver
spec:
  selector:
    matchLabels:
      app.kubernetes.io/name: dra-example-driver
  updateStrategy:
    type: RollingUpdate
  template:
    metadata:
      labels:
        app.kubernetes.io/name: dra-example-driver
    spec:
      priorityClassName: dra-driver-high-priority
      serviceAccountName: dra-example-driver-service-account
      securityContext:
        {}
      containers:
      - name: plugin
        securityContext:
          privileged: true
        image: registry.k8s.io/dra-example-driver/dra-example-driver:v0.2.0
        imagePullPolicy: IfNotPresent
        command: ["dra-example-kubeletplugin"]
        resources:
          {}
        # Production drivers should always implement a liveness probe
        # For the tutorial we simply omit it
        # livenessProbe:
        #   grpc:
        #     port: 51515
        #     service: liveness
        #   failureThreshold: 3
        #   periodSeconds: 10
        env:
        - name: CDI_ROOT
          value: /var/run/cdi
        - name: KUBELET_REGISTRAR_DIRECTORY_PATH
          value: "/var/lib/kubelet/plugins_registry"
        - name: KUBELET_PLUGINS_DIRECTORY_PATH
          value: "/var/lib/kubelet/plugins"
        - name: NODE_NAME
          valueFrom:
            fieldRef:
              fieldPath: spec.nodeName
        - name: NAMESPACE
          valueFrom:
            fieldRef:
              fieldPath: metadata.namespace
        # Simulated number of devices the example driver will pretend to have.
        - name: NUM_DEVICES
          value: "9"
        - name: HEALTHCHECK_PORT
          value: "51515"
        volumeMounts:
        - name: plugins-registry
          mountPath: "/var/lib/kubelet/plugins_registry"
        - name: plugins
          mountPath: "/var/lib/kubelet/plugins"
        - name: cdi
          mountPath: /var/run/cdi
      volumes:
      - name: plugins-registry
        hostPath:
          path: "/var/lib/kubelet/plugins_registry"
      - name: plugins
        hostPath:
          path: "/var/lib/kubelet/plugins"
      - name: cdi
        hostPath:
          path: /var/run/cdi

```shell
kubectl apply --server-side -f https://k8s.io/examples/dra/driver-install/daemonset.yaml
```

این DaemonSet با اتصال‌های حجم (volume mount) لازم پیکربندی شده است تا بتواند
با دایرکتوری زیربنایی رابط دستگاه کانتینر (Container Device Interface یا CDI)
تعامل کند و سوکت خود را از طریق دایرکتوری `kubelet/plugins` در اختیار `kubelet`
قرار دهد.

درخواست منابع و استقرار یک Pod {#claim-resources-pod}

برای درخواست منابع با استفاده از DRA، ResourceClaimها یا ResourceClaimTemplateهایی می‌سازید که منابع مورد نیاز Podهای شما را تعریف می‌کنند. در درایور نمونه، یک ویژگی ظرفیت حافظه برای دستگاه‌های GPU ساختگی ارائه شده است. این بخش نشان می‌دهد چگونه با استفاده از cel نیازمندی‌های خود را در یک ResourceClaim بیان کنید، آن ResourceClaim را در مشخصات یک Pod انتخاب کنید و تخصیص منبع را مشاهده کنید.

این آموزش تنها یک نمونه ساده از ResourceClaim در DRA را نشان می‌دهد. برای آشنایی بیشتر با ResourceClaimها، صفحه تخصیص پویای منابع را بخوانید.

ساخت ResourceClaim

در این بخش، یک ResourceClaim می‌سازید و در یک Pod به آن ارجاع می‌دهید. درخواست هر چه باشد، فیلد deviceClassName الزامی است و دامنه درخواست را به یک کلاس دستگاه مشخص محدود می‌کند. خودِ درخواست می‌تواند شامل یک عبارت cel باشد که به ویژگی‌هایی ارجاع می‌دهد که ممکن است درایورِ مدیریت‌کننده آن کلاس دستگاه اعلام کرده باشد.

در این مثال، درخواستی برای هر GPU‌ای می‌سازید که ظرفیت حافظه‌ای بیش از 10Gi اعلام کرده باشد. ویژگی‌ای که درایور نمونه ظرفیت را با آن ارائه می‌کند، به شکل device.capacity['gpu.example.com'].memory است. همچنین توجه کنید که نام این درخواست some-gpu تعیین شده است.

dra/driver-install/example/resourceclaim.yaml
apiVersion: resource.k8s.io/v1
kind: ResourceClaim
metadata:
 name: some-gpu
 namespace: dra-tutorial
spec:
   devices:
     requests:
     - name: some-gpu
       exactly:
         deviceClassName: gpu.example.com
         selectors:
         - cel:
             expression: "device.capacity['gpu.example.com'].memory.compareTo(quantity('10Gi')) >= 0"

kubectl apply --server-side -f https://k8s.io/examples/dra/driver-install/example/resourceclaim.yaml

ساخت Podای که به آن ResourceClaim ارجاع می‌دهد

در ادامه، مانیفست Podای آمده است که در فیلد spec.resourceClaims.resourceClaimName به ResourceClaimی که همین حالا ساختید، یعنی some-gpu، ارجاع می‌دهد. سپس نام محلی این درخواست، یعنی gpu، در فیلد spec.containers.resources.claims.name به کار می‌رود تا درخواست به کانتینر زیربنایی Pod تخصیص یابد.

dra/driver-install/example/pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: pod0
  namespace: dra-tutorial
  labels:
    app: pod
spec:
  containers:
  - name: ctr0
    image: ubuntu:24.04
    command: ["bash", "-c"]
    args: ["export; trap 'exit 0' TERM; sleep 9999 & wait"]
    resources:
      claims:
      - name: gpu
  resourceClaims:
  - name: gpu
    resourceClaimName: some-gpu

kubectl apply --server-side -f https://k8s.io/examples/dra/driver-install/example/pod.yaml

تأیید کنید که Pod مستقر شده است:

kubectl get pod pod0 -n dra-tutorial

خروجی مشابه زیر است:

NAME   READY   STATUS    RESTARTS   AGE
pod0   1/1     Running   0          9s

بررسی وضعیت DRA

پس از ساخت Pod، کلاستر تلاش می‌کند آن Pod را روی نودی زمان‌بندی کند که کوبرنتیز بتواند ResourceClaim را در آن برآورده کند. در این آموزش، درایور DRA روی همه نودها مستقر شده است و روی همه آن‌ها GPUهای ساختگی اعلام می‌کند و همه این GPUها ظرفیت کافی برای برآورده کردن درخواست Pod اعلام کرده‌اند. بنابراین کوبرنتیز می‌تواند این Pod را روی هر نودی زمان‌بندی کند و هر یک از GPUهای ساختگی آن نود را تخصیص دهد.

وقتی کوبرنتیز یک GPU ساختگی را به یک Pod تخصیص می‌دهد، درایور نمونه در هر کانتینری که GPU به آن تخصیص یافته، متغیرهای محیطی اضافه می‌کند. این متغیرها نشان می‌دهند که یک درایور منبع واقعی کدام GPUها را به آن کانتینرها تزریق می‌کرد و آن‌ها را چگونه پیکربندی می‌کرد. به این ترتیب می‌توانید با بررسی این متغیرهای محیطی ببینید سیستم Podها را چگونه مدیریت کرده است.

  1. لاگ‌های Pod را بررسی کنید که نام GPU ساختگیِ تخصیص‌یافته را گزارش می‌کنند:

    kubectl logs pod0 -c ctr0 -n dra-tutorial | grep -E "GPU_DEVICE_[0-9]+=" | grep -v "RESOURCE_CLAIM"

    خروجی مشابه زیر است:

    declare -x GPU_DEVICE_0="gpu-0"

  2. وضعیت آبجکت ResourceClaim را بررسی کنید:

    kubectl get resourceclaims -n dra-tutorial

    خروجی مشابه زیر است:

    NAME       STATE                AGE
some-gpu   allocated,reserved   34s

    در این خروجی، ستون STATE نشان می‌دهد که ResourceClaim تخصیص یافته و رزرو شده است.

  3. جزئیات ResourceClaim با نام some-gpu را بررسی کنید. بخش status در ResourceClaim اطلاعاتی درباره دستگاه تخصیص‌یافته و Podای که دستگاه برای آن رزرو شده است در بر دارد:

    kubectl get resourceclaim some-gpu -n dra-tutorial -o yaml

    خروجی مشابه زیر است:

apiVersion: resource.k8s.io/v1
    kind: ResourceClaim
    metadata:
      creationTimestamp: "2025-08-20T18:17:31Z"
      finalizers:
      - resource.kubernetes.io/delete-protection
      name: some-gpu
      namespace: dra-tutorial
      resourceVersion: "2326"
      uid: d3e48dbf-40da-47c3-a7b9-f7d54d1051c3
    spec:
      devices:
        requests:
        - exactly:
            allocationMode: ExactCount
            count: 1
            deviceClassName: gpu.example.com
            selectors:
            - cel:
                expression: device.capacity['gpu.example.com'].memory.compareTo(quantity('10Gi'))
                >= 0
          name: some-gpu
    status:
      allocation:
        devices:
          results:
          - device: gpu-0
            driver: gpu.example.com
            pool: kind-worker
            request: some-gpu
        nodeSelector:
          nodeSelectorTerms:
          - matchFields:
            - key: metadata.name
              operator: In
              values:
              - kind-worker
      reservedFor:
      - name: pod0
        resource: pods
        uid: c4dadf20-392a-474d-a47b-ab82080c8bd7

  1. برای اینکه ببینید درایور تخصیص دستگاه را چگونه انجام داده است، لاگ‌های Podهای DaemonSet درایور را دریافت کنید:

    kubectl logs -l app.kubernetes.io/name=dra-example-driver -n dra-tutorial

    خروجی مشابه زیر است:

    I0820 18:17:44.131324       1 driver.go:106] PrepareResourceClaims is called: number of claims: 1
I0820 18:17:44.135056       1 driver.go:133] Returning newly prepared devices for claim 'd3e48dbf-40da-47c3-a7b9-f7d54d1051c3': [{[some-gpu] kind-worker gpu-0 [k8s.gpu.example.com/gpu=common k8s.gpu.example.com/gpu=d3e48dbf-40da-47c3-a7b9-f7d54d1051c3-gpu-0]}]

اکنون Podای را که با استفاده از DRA دستگاه درخواست می‌کند با موفقیت مستقر کرده‌اید، تأیید کرده‌اید که Pod روی نود مناسبی زمان‌بندی شده است و دیدید که انواع API مرتبط با DRA با وضعیت تخصیص به‌روزرسانی شده‌اند.

حذف Podای که درخواست دارد {#delete-pod-claim}

وقتی Podای که درخواست دارد حذف می‌شود، درایور DRA تخصیص منبع را آزاد می‌کند تا منبع برای زمان‌بندی‌های آینده در دسترس باشد. برای بررسی این رفتار، Podای را که در مراحل قبل ساختید حذف کنید و تغییرات متناظر را در ResourceClaim و درایور مشاهده کنید.

Pod با نام pod0 را حذف کنید:

kubectl delete pod pod0 -n dra-tutorial

خروجی مشابه زیر است:

pod "pod0" deleted

مشاهده وضعیت DRA

وقتی Pod حذف می‌شود، درایور تخصیص دستگاه را از ResourceClaim آزاد می‌کند و منبع ResourceClaim را در API کوبرنتیز به‌روزرسانی می‌کند. این ResourceClaim تا زمانی که در یک Pod جدید به آن ارجاع داده شود، در وضعیت pending باقی می‌ماند.

  1. وضعیت ResourceClaim با نام some-gpu را بررسی کنید:

    kubectl get resourceclaims -n dra-tutorial

    خروجی مشابه زیر است:

    NAME       STATE     AGE
some-gpu   pending   76s

  2. با بررسی لاگ‌های درایور، تأیید کنید که درایور لغو آماده‌سازی دستگاه را برای این درخواست انجام داده است:

    kubectl logs -l app.kubernetes.io/name=dra-example-driver -n dra-tutorial

    خروجی مشابه زیر است:

    I0820 18:22:15.629376       1 driver.go:138] UnprepareResourceClaims is called: number of claims: 1

اکنون Podای را که درخواست داشت حذف کرده‌اید و مشاهده کردید که درایور، آماده‌سازی منبع سخت‌افزاری زیربنایی را لغو کرد و APIهای DRA را به‌روزرسانی کرد تا نشان دهد منبع دوباره برای زمان‌بندی‌های آینده در دسترس است.

پاکسازی

برای پاک‌سازی منابعی که در این آموزش ساختید، مراحل زیر را دنبال کنید:

kubectl delete namespace dra-tutorial
kubectl delete deviceclass gpu.example.com
kubectl delete clusterrole dra-example-driver-role
kubectl delete clusterrolebinding dra-example-driver-role-binding
kubectl delete priorityclass dra-driver-high-priority
