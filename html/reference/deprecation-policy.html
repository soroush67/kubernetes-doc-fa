سیاست منسوخ‌سازی کوبرنتیز

این سند سیاست منسوخ‌سازی (deprecation) را برای جنبه‌های مختلف سیستم تشریح می‌کند.

کوبرنتیز سیستمی بزرگ با اجزا و مشارکت‌کنندگان بسیار است. مانند هر نرم‌افزار دیگری از این دست، مجموعه قابلیت‌های آن به‌طور طبیعی با گذشت زمان تکامل می‌یابد و گاهی لازم می‌شود یک قابلیت حذف شود. این قابلیت می‌تواند یک API، یک flag یا حتی یک ویژگی کامل باشد. برای جلوگیری از اختلال در کار کاربران موجود، کوبرنتیز برای بخش‌هایی از سیستم که قرار است حذف شوند، از یک سیاست منسوخ‌سازی پیروی می‌کند.

منسوخ‌سازی بخش‌هایی از API

از آنجا که کوبرنتیز یک سیستم مبتنی بر API است، API نیز با گذشت زمان تکامل یافته تا درک رو‌به‌رشد از حوزه مسئله را منعکس کند. API کوبرنتیز در واقع مجموعه‌ای از APIها به نام «گروه‌های API» (API groups) است و هر گروه API به‌طور مستقل نسخه‌بندی می‌شود. نسخه‌های API در سه مسیر اصلی قرار می‌گیرند که هرکدام سیاست منسوخ‌سازی متفاوتی دارند:

مثال مسیر
v1 GA (به‌طور عمومی در دسترس، پایدار)
v1beta1 بتا (پیش از انتشار)
v1alpha1 آلفا (آزمایشی)

یک نسخه انتشار مشخص از کوبرنتیز می‌تواند هر تعداد گروه API و از هر کدام هر تعداد نسخه را پشتیبانی کند.

قواعد زیر بر منسوخ‌سازی عناصر API حاکم است. این عناصر شامل موارد زیر هستند:

  • منابع REST (یا همان آبجکت‌های API)
  • فیلدهای منابع REST
  • حاشیه‌نویسی‌ها (annotations) روی منابع REST، شامل حاشیه‌نویسی‌های «بتا» اما نه حاشیه‌نویسی‌های «آلفا».
  • مقادیر شمارشی یا ثابت
  • ساختارهای پیکربندی اجزا

این قواعد میان انتشارهای رسمی اعمال می‌شوند، نه میان کامیت‌های دلخواه روی شاخه master یا شاخه‌های انتشار.

قاعده ۱: عناصر API فقط با افزایش نسخه گروه API قابل حذف هستند.

هنگامی که یک عنصر API در نسخه‌ای مشخص به یک گروه API افزوده شد، صرف‌نظر از مسیر، نمی‌توان آن را از آن نسخه حذف کرد یا رفتار آن را به‌طور چشمگیری تغییر داد.

توجه:

به دلایل تاریخی، دو گروه API «یکپارچه» (monolithic) وجود دارد: «core» (بدون نام گروه) و «extensions». منابع به‌تدریج از این گروه‌های API قدیمی به گروه‌های API تخصصی‌تر و متناسب با حوزه کاری منتقل خواهند شد.

قاعده ۲: آبجکت‌های API باید بتوانند در یک نسخه انتشار مشخص، میان نسخه‌های API بدون از دست رفتن اطلاعات رفت‌وبرگشت (round-trip) کنند؛ مگر منابع REST کاملی که در برخی نسخه‌ها وجود ندارند.

برای مثال، یک آبجکت می‌تواند با v1 نوشته شود، سپس با v2 خوانده و دوباره به v1 تبدیل شود و منبع v1 حاصل با نسخه اصلی یکسان خواهد بود. بازنمایی در v2 ممکن است با v1 متفاوت باشد، اما سیستم می‌داند چگونه در هر دو جهت میان آن‌ها تبدیل کند. افزون بر این، هر فیلد جدیدی که در v2 افزوده می‌شود باید بتواند به v1 و بالعکس رفت‌وبرگشت کند؛ یعنی ممکن است v1 ناچار باشد فیلدی معادل بیفزاید یا آن را به‌صورت یک حاشیه‌نویسی (annotation) نمایش دهد.

قاعده ۳: یک نسخه API در یک مسیر مشخص نمی‌تواند به نفع نسخه API کم‌پایدارتر منسوخ شود.

  • نسخه‌های GA API می‌توانند جایگزین نسخه‌های بتا و آلفا شوند.
  • نسخه‌های بتا API می‌توانند جایگزین نسخه‌های بتا و آلفای قبلی شوند، اما نمی‌توانند جایگزین نسخه‌های GA شوند.
  • نسخه‌های آلفا API می‌توانند جایگزین نسخه‌های آلفای قبلی شوند، اما نمی‌توانند جایگزین نسخه‌های GA یا بتا شوند.

قاعده ۴الف: طول عمر API بر اساس سطح پایداری آن تعیین می‌شود

  • نسخه‌های GA API می‌توانند به‌عنوان منسوخ علامت‌گذاری شوند، اما نباید در طول یک نسخه اصلی (major) کوبرنتیز حذف شوند
  • نسخه‌های بتا API حداکثر ۹ ماه یا ۳ نسخه فرعی (minor) پس از معرفی (هرکدام که طولانی‌تر است) منسوخ می‌شوند، و ۹ ماه یا ۳ نسخه فرعی پس از منسوخ شدن (هرکدام که طولانی‌تر است) دیگر ارائه نمی‌شوند
  • نسخه‌های آلفا API می‌توانند در هر نسخه انتشار و بدون اطلاع‌رسانی قبلی درباره منسوخ‌سازی حذف شوند

این امر تضمین می‌کند که پشتیبانی از API بتا، حداکثر اختلاف نسخه پشتیبانی‌شده یعنی ۲ نسخه انتشار را پوشش می‌دهد و APIها روی نسخه‌های بتای ناپایدار متوقف نمی‌مانند و استفاده تولیدی‌ای را انباشته نمی‌کنند که با پایان یافتن پشتیبانی از API بتا مختل شود.

توجه:

در حال حاضر برنامه‌ای برای یک بازنگری نسخه اصلی (major) کوبرنتیز که APIهای GA را حذف کند وجود ندارد.

توجه:

تا زمانی که #52185 حل نشده است، هیچ نسخه API‌ای که در ذخیره‌سازی ماندگار شده باشد نباید حذف شود. ارائه نقاط پایانی REST برای آن نسخه‌ها ممکن است غیرفعال شود (مطابق جدول‌های زمانی منسوخ‌سازی در این سند)، اما API server باید همچنان قادر به رمزگشایی/تبدیل داده‌های ماندگارشده پیشین از ذخیره‌سازی باشد.

قاعده ۴ب: نسخه «ترجیحی» (preferred) API و «نسخه ذخیره‌سازی» (storage version) برای یک گروه مشخص نباید پیش از انتشاری که هم نسخه جدید و هم نسخه قبلی را پشتیبانی می‌کند، ارتقا یابد

کاربران باید بتوانند به نسخه جدیدی از کوبرنتیز ارتقا دهند و سپس به نسخه قبلی بازگردند، بدون آنکه چیزی را به نسخه جدید API تبدیل کنند یا دچار خرابی شوند (مگر آنکه صراحتاً از قابلیت‌هایی استفاده کرده باشند که تنها در نسخه جدیدتر موجودند). این موضوع به‌ویژه در بازنمایی ذخیره‌شده آبجکت‌ها مشهود است.

همه این موارد با مثال بهتر توضیح داده می‌شود. فرض کنید یک نسخه انتشار کوبرنتیز، به نام X، یک گروه API جدید معرفی می‌کند. هر نسخه جدید کوبرنتیز تقریباً هر ۴ ماه (۳ بار در سال) منتشر می‌شود. جدول زیر شرح می‌دهد که در یک سری از نسخه‌های انتشار بعدی، کدام نسخه‌های API پشتیبانی می‌شوند.

منابع REST (یا همان آبجکت‌های API)

یک منبع REST فرضی به نام Widget را در نظر بگیرید که در جدول زمانی بالا در API نسخه v1 وجود داشته و باید منسوخ شود. ما منسوخ‌سازی را همزمان با انتشار X+1 مستند و اعلام می‌کنیم. منبع Widget هنوز در API نسخه v1 (منسوخ) وجود دارد، اما در v2alpha1 وجود ندارد. منبع Widget تا انتشار X+8 و از جمله آن همچنان وجود دارد و کار می‌کند. تنها در انتشار X+9، زمانی که API نسخه v1 از رده خارج می‌شود، منبع Widget دیگر وجود نخواهد داشت و رفتار آن حذف می‌شود.

از کوبرنتیز v1.19 به بعد، ارسال یک درخواست API به نقطه پایانی REST API منسوخ‌شده:

  1. یک هدر Warning (مطابق تعریف RFC7234، بخش ۵.۵) را در پاسخ API برمی‌گرداند.

  2. یک حاشیه‌نویسی (annotation) با مقدار "k8s.io/deprecated":"true" را به رویداد ممیزی ثبت‌شده برای آن درخواست می‌افزاید.

  3. یک متریک از نوع gauge با نام apiserver_requested_deprecated_apis را در فرایند kube-apiserver روی مقدار 1 تنظیم می‌کند. این متریک دارای برچسب‌های group، version، resource و subresource است که می‌توان آن‌ها را با متریک apiserver_request_total ترکیب (join) کرد، و نیز برچسب removed_release که نسخه‌ای از کوبرنتیز را نشان می‌دهد که در آن API دیگر ارائه نخواهد شد. پرس‌وجوی Prometheus زیر اطلاعات مربوط به درخواست‌هایی را که به APIهای منسوخ‌شده ارسال شده‌اند و در v1.22 حذف خواهند شد، برمی‌گرداند:

    apiserver_requested_deprecated_apis{removed_release="1.22"} * on(group,version,resource,subresource) group_right() apiserver_request_total

فیلدهای منابع REST

مانند منابع REST کامل، یک فیلد منفرد که در API نسخه v1 وجود داشته است باید تا زمان حذف API نسخه v1 وجود داشته باشد و کار کند. برخلاف منابع کامل، APIهای v2 می‌توانند بازنمایی متفاوتی برای فیلد انتخاب کنند، به شرط آنکه امکان رفت‌وبرگشت (round-trip) وجود داشته باشد. برای مثال، یک فیلد v1 به نام «magnitude» که منسوخ شده است، ممکن است در API نسخه v2 «deprecatedMagnitude» نامیده شود. وقتی v1 سرانجام حذف شود، فیلد منسوخ‌شده می‌تواند از v2 حذف شود.

مقادیر شمارشی یا ثابت

مانند منابع REST کامل و فیلدهای آن‌ها، یک مقدار ثابت که در API نسخه v1 پشتیبانی می‌شده است باید تا زمان حذف API نسخه v1 وجود داشته باشد و کار کند.

ساختارهای پیکربندی اجزا

پیکربندی‌های اجزا مشابه منابع REST نسخه‌بندی و مدیریت می‌شوند.

کارهای آینده

با گذشت زمان، کوبرنتیز نسخه‌های API با جزئیات دقیق‌تر را معرفی خواهد کرد و در آن مرحله این قواعد در صورت نیاز تنظیم خواهند شد.

منسوخ‌سازی یک flag یا CLI

سیستم کوبرنتیز از چندین برنامه مختلف تشکیل شده است که با یکدیگر همکاری می‌کنند. گاهی یک نسخه انتشار کوبرنتیز ممکن است flagها یا دستورهای CLI (که روی هم «عناصر CLI» نامیده می‌شوند) را در این برنامه‌ها حذف کند. برنامه‌ها به‌طور طبیعی به دو گروه اصلی تقسیم می‌شوند: برنامه‌های رو به کاربر و برنامه‌های رو به مدیر، که سیاست منسوخ‌سازی آن‌ها اندکی متفاوت است. مگر آنکه یک flag صراحتاً با پیشوند «alpha» یا «beta» همراه باشد یا به این صورت مستند شده باشد، GA در نظر گرفته می‌شود.

عناصر CLI عملاً بخشی از API سیستم هستند، اما از آنجا که مانند REST API نسخه‌بندی نمی‌شوند، قواعد منسوخ‌سازی آن‌ها به شرح زیر است:

قاعده ۵الف: عناصر CLI مربوط به اجزای رو به کاربر (مانند kubectl) باید پس از منسوخ‌سازی اعلام‌شده خود دست‌کم به مدت زیر کار کنند:

  • GA: ۱۲ ماه یا ۲ نسخه انتشار (هرکدام که طولانی‌تر است)
  • بتا: ۳ ماه یا ۱ نسخه انتشار (هرکدام که طولانی‌تر است)
  • آلفا: ۰ نسخه انتشار

قاعده ۵ب: عناصر CLI مربوط به اجزای رو به مدیر (مانند kubelet) باید پس از منسوخ‌سازی اعلام‌شده خود دست‌کم به مدت زیر کار کنند:

  • GA: ۶ ماه یا ۱ نسخه انتشار (هرکدام که طولانی‌تر است)
  • بتا: ۳ ماه یا ۱ نسخه انتشار (هرکدام که طولانی‌تر است)
  • آلفا: ۰ نسخه انتشار

قاعده ۵ج: عناصر رابط خط فرمان (CLI) نمی‌توانند به نفع عناصر CLI کم‌پایدارتر منسوخ شوند

مشابه قاعده ۳ برای APIها، اگر یک عنصر از رابط خط فرمان با پیاده‌سازی جایگزینی عوض می‌شود، مثلاً با تغییر نام یک عنصر موجود یا با روی‌آوردن به استفاده از پیکربندی‌ای که از یک فایل تأمین می‌شود به‌جای آرگومان خط فرمان، آن جایگزین توصیه‌شده باید سطح پایداری یکسان یا بالاتری داشته باشد.

قاعده ۶: عناصر CLI منسوخ‌شده باید هنگام استفاده هشدار صادر کنند (با امکان غیرفعال‌سازی اختیاری).

منسوخ‌سازی یک قابلیت یا رفتار

گاهی یک نسخه انتشار کوبرنتیز لازم است قابلیت یا رفتاری از سیستم را که توسط API یا CLI کنترل نمی‌شود منسوخ کند. در این حالت، قواعد منسوخ‌سازی به شرح زیر است:

قاعده ۷: رفتارهای منسوخ‌شده باید دست‌کم ۱ سال پس از منسوخ‌سازی اعلام‌شده خود کار کنند.

اگر قابلیت یا رفتار با پیاده‌سازی جایگزینی عوض می‌شود که پذیرش آن مستلزم کار است، باید در صورت امکان تلاش شود گذار ساده‌تر شود. اگر پیاده‌سازی جایگزین زیر کنترل سازمان کوبرنتیز باشد، قواعد زیر اعمال می‌شوند:

قاعده ۸: قابلیت یا رفتار نباید به نفع پیاده‌سازی جایگزینی که کم‌پایدارتر است منسوخ شود

برای مثال، یک قابلیت GA را نمی‌توان به نفع یک جایگزین بتا منسوخ کرد. با این حال، پروژه کوبرنتیز کاربران را تشویق می‌کند که حتی پیش از آنکه پیاده‌سازی‌های جایگزین به همان سطح بلوغ برسند، آن‌ها را بپذیرند و به آن‌ها گذار کنند. این امر به‌ویژه برای بررسی موارد استفاده جدید یک قابلیت یا دریافت بازخورد زودهنگام درباره جایگزین اهمیت دارد.

پیاده‌سازی‌های جایگزین گاهی ممکن است ابزارها یا محصولات خارجی باشند؛ برای مثال، یک قابلیت ممکن است از kubelet به container runtime ای منتقل شود که تحت کنترل پروژه کوبرنتیز نیست. در چنین مواردی، این قاعده قابل اعمال نیست، اما باید تلاش شود اطمینان حاصل شود که مسیر گذاری وجود دارد که در سطح بلوغ اجزا سازش نمی‌کند. در مثال container runtimeها، این تلاش ممکن است شامل کوشش برای اطمینان از این باشد که container runtimeهای محبوب نسخه‌هایی دارند که هنگام پیاده‌سازی رفتار جایگزین، همان سطح پایداری را ارائه می‌دهند.

قواعد منسوخ‌سازی برای قابلیت‌ها و رفتارها بدان معنا نیست که همه تغییرات سیستم تابع این سیاست هستند. این قواعد تنها بر رفتارهای مهم و قابل مشاهده برای کاربر اعمال می‌شوند که بر درستی برنامه‌های در حال اجرا روی کوبرنتیز یا بر مدیریت کلاسترهای کوبرنتیز تأثیر می‌گذارند و به‌طور کامل حذف می‌شوند.

استثنای این قاعده، feature gateها هستند. feature gateها جفت‌های کلید=مقدار هستند که به کاربران اجازه می‌دهند قابلیت‌های آزمایشی را فعال/غیرفعال کنند.

feature gateها برای پوشش چرخه عمر توسعه یک قابلیت در نظر گرفته شده‌اند و قرار نیست APIهای بلندمدت باشند. بنابراین انتظار می‌رود پس از آنکه یک قابلیت به GA برسد یا کنار گذاشته شود، منسوخ و حذف شوند.

با عبور یک قابلیت از مراحل مختلف، feature gate مرتبط با آن نیز تکامل می‌یابد. چرخه عمر قابلیت و feature gate متناظر با آن به این صورت است:

  • آلفا: feature gate به‌طور پیش‌فرض غیرفعال است و کاربر می‌تواند آن را فعال کند.
  • بتا: feature gate به‌طور پیش‌فرض فعال است و کاربر می‌تواند آن را غیرفعال کند.
  • GA: feature gate منسوخ می‌شود (به "منسوخ‌سازی" مراجعه کنید) و غیرعملیاتی (non-operational) می‌شود.
  • GA، پایان دوره منسوخ‌سازی: feature gate حذف می‌شود و فراخوانی‌های مربوط به آن دیگر پذیرفته نمی‌شوند.

منسوخ‌سازی {#deprecation}

قابلیت‌ها را می‌توان در هر نقطه از چرخه عمر پیش از GA حذف کرد. وقتی قابلیت‌ها پیش از GA حذف می‌شوند، feature gateهای مرتبط با آن‌ها نیز منسوخ می‌شوند.

وقتی یک فراخوانی تلاش می‌کند یک feature gate غیرعملیاتی را غیرفعال کند، فراخوانی با شکست مواجه می‌شود تا از سناریوهای پشتیبانی‌نشده‌ای که در غیر این صورت ممکن است بی‌صدا اجرا شوند جلوگیری شود.

در برخی موارد، حذف قابلیت‌های پیش از GA به زمان قابل‌توجهی نیاز دارد. feature gateها می‌توانند تا زمانی که قابلیت مرتبط با آن‌ها به‌طور کامل حذف شود عملیاتی باقی بمانند و در آن نقطه خود feature gate می‌تواند منسوخ شود.

وقتی حذف یک feature gate برای یک قابلیت GA نیز به زمان قابل‌توجهی نیاز دارد، فراخوانی‌های feature gateها می‌توانند عملیاتی باقی بمانند، به شرط آنکه feature gate تأثیری بر قابلیت نداشته باشد و خطایی ایجاد نکند.

قابلیت‌هایی که قرار است توسط کاربران غیرفعال شوند باید سازوکاری برای غیرفعال‌سازی قابلیت در feature gate مرتبط داشته باشند.

نسخه‌بندی feature gateها با اجزایی که پیش‌تر بحث شد متفاوت است، بنابراین قواعد منسوخ‌سازی به شرح زیر است:

قاعده ۹: feature gateها باید هنگامی منسوخ شوند که قابلیت متناظر تحت کنترل آن‌ها به‌شرح زیر از یک مرحله چرخه عمر عبور می‌کند. feature gateها باید دست‌کم به مدت زیر کار کنند:

  • قابلیت بتا تا GA: ۶ ماه یا ۲ نسخه انتشار (هرکدام که طولانی‌تر است)
  • قابلیت بتا تا EOL: ۳ ماه یا ۱ نسخه انتشار (هرکدام که طولانی‌تر است)
  • قابلیت آلفا تا EOL: ۰ نسخه انتشار

قاعده ۱۰: feature gateهای منسوخ‌شده باید هنگام استفاده با یک هشدار پاسخ دهند. وقتی یک feature gate منسوخ می‌شود باید هم در یادداشت‌های انتشار و هم در راهنمای CLI متناظر مستند شود. هم هشدارها و هم مستندات باید مشخص کنند که آیا یک feature gate غیرعملیاتی است یا خیر.

منسوخ‌کردن یک متریک

هر یک از اجزای control plane کوبرنتیز متریک‌هایی را ارائه می‌دهد (معمولاً از طریق endpoint با مسیر /metrics) که معمولاً توسط مدیران کلاستر دریافت و پردازش می‌شوند. همه متریک‌ها یکسان نیستند: برخی از متریک‌ها معمولاً به عنوان SLI به کار می‌روند یا برای تعیین SLO مورد استفاده قرار می‌گیرند و اهمیت بیشتری دارند. سایر متریک‌ها ماهیت آزمایشی‌تری دارند یا عمدتاً در فرایند توسعه کوبرنتیز استفاده می‌شوند.

بر این اساس، متریک‌ها در سه کلاس پایداری (ALPHA، BETA، STABLE) قرار می‌گیرند؛ این موضوع بر حذف یک متریک در طول یک نسخه کوبرنتیز اثر می‌گذارد. این کلاس‌ها بر اساس اهمیت درک‌شده‌ی متریک تعیین می‌شوند. قوانین منسوخ‌کردن و حذف یک متریک به شرح زیر است:

قانون ۱۱a: متریک‌ها، برای کلاس پایداری متناظر خود، باید دست‌کم به مدت زیر کار کنند:

  • STABLE: ۴ نسخه یا ۱۲ ماه (هر کدام که طولانی‌تر باشد)
  • BETA: ۲ نسخه یا ۸ ماه (هر کدام که طولانی‌تر باشد)
  • ALPHA: ۰ نسخه

قانون ۱۱b: متریک‌ها، پس از اعلام منسوخ‌شدن خود، باید دست‌کم به مدت زیر کار کنند:

  • STABLE: ۳ نسخه یا ۹ ماه (هر کدام که طولانی‌تر باشد)
  • BETA: ۱ نسخه یا ۴ ماه (هر کدام که طولانی‌تر باشد)
  • ALPHA: ۰ نسخه

متن توضیحات متریک‌های منسوخ‌شده با یک اعلان منسوخ‌شدن به صورت '(Deprecated from x.y)' شروع می‌شود و هنگام ثبت متریک، یک لاگ هشدار تولید خواهد شد. مانند متریک‌های پایدار و منسوخ‌نشده، متریک‌های منسوخ‌شده نیز به‌طور خودکار در endpoint متریک‌ها ثبت می‌شوند و بنابراین قابل مشاهده‌اند.

در یک نسخه بعدی (زمانی که deprecatedVersion متریک برابر با current_kubernetes_version - 3 باشد)، یک متریک منسوخ‌شده به متریک پنهان (hidden) تبدیل می‌شود. برخلاف متریک‌های منسوخ‌شده، متریک‌های پنهان دیگر به‌طور خودکار در endpoint متریک‌ها ثبت نمی‌شوند (و از این رو پنهان هستند). با این حال، می‌توان آن‌ها را با یک فلگ خط فرمان روی فایل اجرایی (--show-hidden-metrics-for-version=) به‌طور صریح فعال کرد. این امکان به مدیران کلاستر یک راه نجات می‌دهد تا اگر نتوانسته‌اند به هشدارهای منسوخ‌شدن پیشین واکنش نشان دهند، به‌درستی از یک متریک منسوخ‌شده مهاجرت کنند. متریک‌های پنهان باید پس از یک نسخه حذف شوند.

استثناها

هیچ سیاستی نمی‌تواند همه موقعیت‌های ممکن را پوشش دهد. این سیاست یک سند زنده است و با گذر زمان تکامل خواهد یافت. در عمل، موقعیت‌هایی پیش خواهد آمد که به‌خوبی در این سیاست نمی‌گنجند یا این سیاست در آن‌ها به مانعی جدی تبدیل می‌شود. چنین موقعیت‌هایی باید با SIGها و رهبران پروژه مطرح شوند تا بهترین راه‌حل‌ها برای آن موارد خاص یافت شود، و همواره باید به خاطر داشت که کوبرنتیز متعهد است سیستمی پایدار باشد که تا حد امکان هرگز کاربران را دچار اختلال نکند. استثناها همواره در همه یادداشت‌های انتشار (release notes) مرتبط اعلام خواهند شد.
