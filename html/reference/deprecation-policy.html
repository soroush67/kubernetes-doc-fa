سیاست منسوخ‌سازی کوبرنتیز

این سند سیاست منسوخ‌سازی (deprecation) را برای جنبه‌های مختلف سیستم به‌تفصیل شرح می‌دهد.

کوبرنتیز سیستمی بزرگ با اجزا و مشارکت‌کنندگان فراوان است. مانند هر نرم‌افزار دیگری از این دست، مجموعه‌ی قابلیت‌های آن به‌طور طبیعی در طول زمان تکامل می‌یابد و گاهی لازم است قابلیتی حذف شود. این قابلیت ممکن است یک API، یک فلگ یا حتی یک قابلیت کامل باشد. کوبرنتیز برای اینکه کار کاربران فعلی مختل نشود، برای بخش‌هایی از سیستم که قرار است حذف شوند از یک سیاست منسوخ‌سازی پیروی می‌کند.

منسوخ‌سازی بخش‌هایی از API

از آنجا که کوبرنتیز سیستمی مبتنی بر API است، API آن در طول زمان تکامل یافته تا درک رو‌به‌رشد از حوزه‌ی مسئله را بازتاب دهد. در واقع API کوبرنتیز مجموعه‌ای از APIهاست که «گروه‌های API» نامیده می‌شوند و هر گروه API به‌طور مستقل نسخه‌بندی می‌شود. نسخه‌های API در ۳ مسیر اصلی قرار می‌گیرند و هر مسیر سیاست منسوخ‌سازی متفاوتی دارد:

نمونه مسیر
v1 عرضه‌ی عمومی یا GA (generally available، پایدار)
v1beta1 بتا (پیش‌انتشار)
v1alpha1 آلفا (آزمایشی)

هر انتشار کوبرنتیز می‌تواند از هر تعداد گروه API و از هر تعداد نسخه از هر گروه پشتیبانی کند.

قواعد زیر بر منسوخ‌سازی اجزای API حاکم است. این اجزا عبارت‌اند از:

  • منابع REST (یا همان آبجکت‌های API)
  • فیلدهای منابع REST
  • حاشیه‌نویسی‌ها (annotation) روی منابع REST، از جمله حاشیه‌نویسی‌های «بتا»، اما نه حاشیه‌نویسی‌های «آلفا».
  • مقادیر شمارشی یا ثابت
  • ساختارهای پیکربندی اجزا

این قواعد میان انتشارهای رسمی اعمال می‌شوند، نه میان کامیت‌های دلخواه در شاخه‌ی master یا شاخه‌های انتشار.

قاعده‌ی شماره ۱: اجزای API را فقط می‌توان با افزایش نسخه‌ی گروه API حذف کرد.

هنگامی که یک جزء API در نسخه‌ای مشخص به یک گروه API افزوده شد، صرف‌نظر از مسیر آن، دیگر نمی‌توان آن را از آن نسخه حذف کرد یا رفتارش را به‌طور چشمگیری تغییر داد.

توجه:

به دلایل تاریخی، ۲ گروه API «یکپارچه» وجود دارد: «core» (بدون نام گروه) و «extensions». منابع به‌تدریج از این گروه‌های API قدیمی به گروه‌های API تخصصی‌تر منتقل خواهند شد.

قاعده‌ی شماره ۲: آبجکت‌های API باید بتوانند در یک انتشار مشخص، بدون از دست رفتن اطلاعات، میان نسخه‌های API رفت‌وبرگشت (round-trip) داشته باشند؛ به‌جز منابع REST کاملی که در برخی نسخه‌ها وجود ندارند.

برای مثال، می‌توان آبجکتی را به‌صورت v1 نوشت، سپس آن را به‌صورت v2 خواند و دوباره به v1 تبدیل کرد و منبع v1 حاصل باید با نسخه‌ی اصلی یکسان باشد. ممکن است نمایش آبجکت در v2 با v1 متفاوت باشد، اما سیستم می‌داند چگونه در هر دو جهت میان آن‌ها تبدیل کند. افزون بر این، هر فیلد جدیدی که در v2 افزوده می‌شود باید بتواند به v1 و برعکس رفت‌وبرگشت داشته باشد؛ یعنی ممکن است لازم شود v1 فیلدی معادل اضافه کند یا آن را به‌صورت یک حاشیه‌نویسی نمایش دهد.

قاعده‌ی شماره ۳: هیچ نسخه‌ی API در یک مسیر مشخص را نمی‌توان به نفع نسخه‌ای ناپایدارتر از API منسوخ کرد.

  • نسخه‌های GA از API می‌توانند جایگزین نسخه‌های بتا و آلفای API شوند.
  • نسخه‌های بتای API می‌توانند جایگزین نسخه‌های بتا و آلفای قبلی شوند، اما نمی‌توانند جایگزین نسخه‌های GA از API شوند.
  • نسخه‌های آلفای API می‌توانند جایگزین نسخه‌های آلفای قبلی شوند، اما نمی‌توانند جایگزین نسخه‌های GA یا بتای API شوند.

قاعده‌ی شماره ۴الف: طول عمر API را سطح پایداری آن تعیین می‌کند

  • نسخه‌های GA از API ممکن است منسوخ اعلام شوند، اما نباید در طول یک نسخه‌ی اصلی (major) کوبرنتیز حذف شوند.
  • نسخه‌های بتای API حداکثر ۹ ماه یا ۳ انتشار فرعی پس از معرفی (هر کدام طولانی‌تر باشد) منسوخ می‌شوند و ۹ ماه یا ۳ انتشار فرعی پس از منسوخ‌شدن (هر کدام طولانی‌تر باشد) دیگر ارائه نمی‌شوند.
  • نسخه‌های آلفای API ممکن است در هر انتشاری و بدون اعلام قبلی منسوخ‌شدن حذف شوند.

این قاعده تضمین می‌کند که پشتیبانی از APIهای بتا حداکثر اختلاف نسخه‌ی پشتیبانی‌شده، یعنی ۲ انتشار را پوشش دهد و APIها روی نسخه‌های بتای ناپایدار متوقف نمانند؛ چرا که در این صورت استفاده‌ی عملیاتی از آن‌ها انباشته می‌شود و با پایان پشتیبانی از API بتا مختل خواهد شد.

توجه:

در حال حاضر هیچ برنامه‌ای برای بازنگری نسخه‌ی اصلی کوبرنتیز که APIهای GA را حذف کند وجود ندارد.

توجه:

تا زمانی که مسئله‌ی #52185 حل نشود، هیچ نسخه‌ای از API که در ذخیره‌ساز ماندگار شده است قابل حذف نیست. می‌توان ارائه‌ی endpointهای REST برای آن نسخه‌ها را غیرفعال کرد (مشروط به زمان‌بندی‌های منسوخ‌سازی این سند)، اما سرور API باید همچنان بتواند داده‌هایی را که پیش‌تر در ذخیره‌ساز ماندگار شده‌اند رمزگشایی یا تبدیل کند.

قاعده‌ی شماره ۴ب: نسخه‌ی «ترجیحی» API و «نسخه‌ی ذخیره‌سازی» یک گروه مشخص تنها پس از انتشاری که از هر دو نسخه‌ی جدید و قبلی پشتیبانی کند، می‌توانند ارتقا یابند

کاربران باید بتوانند به انتشار جدیدی از کوبرنتیز ارتقا دهند و سپس به انتشار قبلی بازگردند، بی‌آنکه چیزی را به نسخه‌ی جدید API تبدیل کنند یا با خرابی مواجه شوند (مگر آنکه به‌طور صریح از قابلیت‌هایی استفاده کرده باشند که فقط در نسخه‌ی جدیدتر وجود دارند). این موضوع به‌ویژه در نمایش ذخیره‌شده‌ی آبجکت‌ها نمود دارد.

همه‌ی این موارد با مثال بهتر روشن می‌شود. انتشاری از کوبرنتیز با نسخه‌ی X را در نظر بگیرید که یک گروه API جدید معرفی می‌کند. هر انتشار جدید کوبرنتیز تقریباً هر ۴ ماه یک بار (۳ انتشار در سال) منتشر می‌شود. جدول زیر نشان می‌دهد که در مجموعه‌ای از انتشارهای بعدی از کدام نسخه‌های API پشتیبانی می‌شود.

منابع REST (یا همان آبجکت‌های API)

یک منبع REST فرضی به نام Widget را در نظر بگیرید که در جدول زمانی بالا در API v1 وجود داشته و اکنون باید منسوخ شود. ما منسوخ‌شدن آن را هم‌زمان با انتشار X+1 مستند و اعلام می‌کنیم. منبع Widget همچنان در نسخه‌ی v1 از API (منسوخ‌شده) وجود دارد، اما در v2alpha1 وجود ندارد. این منبع در انتشارها تا X+8 (شامل خود آن) همچنان وجود دارد و کار می‌کند. تنها در انتشار X+9، یعنی زمانی که عمر API v1 به پایان رسیده است، منبع Widget دیگر وجود نخواهد داشت و رفتار آن حذف می‌شود.

از کوبرنتیز نسخه‌ی 1.19 به بعد، ارسال درخواست API به یک endpoint منسوخ‌شده‌ی REST API پیامدهای زیر را دارد:

  1. یک سرآیند Warning (مطابق تعریف RFC7234، بخش 5.5) در پاسخ API بازگردانده می‌شود.

  2. حاشیه‌نویسی "k8s.io/deprecated":"true" به رویداد ممیزی ثبت‌شده برای آن درخواست افزوده می‌شود.

  3. متریک gauge با نام apiserver_requested_deprecated_apis در فرایند kube-apiserver روی 1 تنظیم می‌شود. این متریک برچسب‌های group، version، resource و subresource را دارد که می‌توان آن را با متریک apiserver_request_total پیوند داد، و همچنین برچسب removed_release را دارد که انتشاری از کوبرنتیز را نشان می‌دهد که در آن API دیگر ارائه نخواهد شد. کوئری Prometheus زیر اطلاعات درخواست‌هایی را بازمی‌گرداند که به APIهای منسوخ‌شده‌ای ارسال شده‌اند که در v1.22 حذف خواهند شد:

    apiserver_requested_deprecated_apis{removed_release="1.22"} * on(group,version,resource,subresource) group_right() apiserver_request_total

فیلدهای منابع REST

همانند منابع کامل REST، هر فیلد مجزایی که در API v1 وجود داشته است باید تا زمان حذف API v1 وجود داشته باشد و کار کند. برخلاف منابع کامل، APIهای v2 می‌توانند نمایش متفاوتی برای آن فیلد برگزینند، به شرط آنکه امکان رفت‌وبرگشت حفظ شود. برای مثال، فیلدی در v1 به نام «magnitude» که منسوخ شده است، ممکن است در API v2 «deprecatedMagnitude» نام بگیرد. هنگامی که v1 سرانجام حذف شود، فیلد منسوخ‌شده را نیز می‌توان از v2 حذف کرد.

مقادیر شمارشی یا ثابت

همانند منابع کامل REST و فیلدهای آن‌ها، هر مقدار ثابتی که در API v1 پشتیبانی می‌شده است باید تا زمان حذف API v1 وجود داشته باشد و کار کند.

ساختارهای پیکربندی اجزا

پیکربندی‌های اجزا مشابه منابع REST نسخه‌بندی و مدیریت می‌شوند.

کارهای آینده

کوبرنتیز به‌مرور زمان نسخه‌های API جزئی‌تری معرفی خواهد کرد و در آن هنگام این قواعد در صورت نیاز اصلاح خواهند شد.

منسوخ‌سازی یک فلگ یا CLI

سیستم کوبرنتیز از چندین برنامه‌ی مختلف تشکیل شده است که با یکدیگر همکاری می‌کنند. گاهی ممکن است یک انتشار کوبرنتیز فلگ‌ها یا دستورهای CLI (که مجموعاً «اجزای CLI» نامیده می‌شوند) را از این برنامه‌ها حذف کند. این برنامه‌ها به‌طور طبیعی در دو گروه اصلی جای می‌گیرند: برنامه‌های کاربرمحور و برنامه‌های مدیرمحور، که سیاست‌های منسوخ‌سازی آن‌ها اندکی با هم تفاوت دارد. هر فلگی که به‌صراحت با پیشوند «alpha» یا «beta» مشخص یا به این عنوان مستند نشده باشد، GA در نظر گرفته می‌شود.

اجزای CLI در عمل بخشی از API سیستم هستند، اما چون به همان شیوه‌ی REST API نسخه‌بندی نمی‌شوند، قواعد منسوخ‌سازی آن‌ها به شرح زیر است:

قاعده‌ی شماره ۵الف: اجزای CLI در اجزای کاربرمحور (مانند kubectl) باید پس از اعلام منسوخ‌شدن، دست‌کم به مدت زیر کار کنند:

  • نسخه‌ی GA: ۱۲ ماه یا ۲ انتشار (هر کدام طولانی‌تر باشد)
  • نسخه‌ی بتا: ۳ ماه یا ۱ انتشار (هر کدام طولانی‌تر باشد)
  • نسخه‌ی آلفا: ۰ انتشار

قاعده‌ی شماره ۵ب: اجزای CLI در اجزای مدیرمحور (مانند kubelet) باید پس از اعلام منسوخ‌شدن، دست‌کم به مدت زیر کار کنند:

  • نسخه‌ی GA: ۶ ماه یا ۱ انتشار (هر کدام طولانی‌تر باشد)
  • نسخه‌ی بتا: ۳ ماه یا ۱ انتشار (هر کدام طولانی‌تر باشد)
  • نسخه‌ی آلفا: ۰ انتشار

قاعده‌ی شماره ۵ج: اجزای رابط خط فرمان (CLI) را نمی‌توان به نفع اجزای CLI ناپایدارتر منسوخ کرد

مشابه قاعده‌ی شماره ۳ برای APIها، اگر جزئی از رابط خط فرمان با پیاده‌سازی جایگزینی عوض شود، مثلاً با تغییر نام یک جزء موجود یا با استفاده از پیکربندی خوانده‌شده از یک فایل به‌جای آرگومان خط فرمان، آن جایگزین پیشنهادی باید سطح پایداری برابر یا بالاتری داشته باشد.

قاعده‌ی شماره ۶: اجزای منسوخ‌شده‌ی CLI باید هنگام استفاده هشدار صادر کنند (این هشدار را می‌توان به‌صورت اختیاری غیرفعال کرد).

منسوخ‌سازی یک قابلیت یا رفتار

گاهی لازم است یک انتشار کوبرنتیز قابلیت یا رفتاری از سیستم را منسوخ کند که تحت کنترل API یا CLI نیست. در این حالت، قواعد منسوخ‌سازی به شرح زیر است:

قاعده‌ی شماره ۷: رفتارهای منسوخ‌شده باید دست‌کم تا ۱ سال پس از اعلام منسوخ‌شدن کار کنند.

اگر قابلیت یا رفتاری با پیاده‌سازی جایگزینی عوض شود که پذیرش آن به کار و تلاش نیاز دارد، باید تا حد امکان برای ساده‌سازی این گذار تلاش شود. اگر پیاده‌سازی جایگزین تحت کنترل سازمان کوبرنتیز باشد، قواعد زیر اعمال می‌شوند:

قاعده‌ی شماره ۸: قابلیت یا رفتار نباید به نفع پیاده‌سازی جایگزینی که پایداری کمتری دارد منسوخ شود

برای مثال، قابلیتی که به‌طور عمومی در دسترس (GA) است نمی‌تواند به نفع جایگزینی در مرحله‌ی بتا منسوخ شود. با این حال، پروژه‌ی کوبرنتیز کاربران را تشویق می‌کند که حتی پیش از رسیدن پیاده‌سازی‌های جایگزین به همان سطح بلوغ، آن‌ها را بپذیرند و به آن‌ها مهاجرت کنند. این کار به‌ویژه برای بررسی موارد استفاده‌ی جدید یک قابلیت یا دریافت بازخورد زودهنگام درباره‌ی جایگزین اهمیت دارد.

پیاده‌سازی‌های جایگزین گاهی ممکن است ابزارها یا محصولات خارجی باشند؛ برای مثال، ممکن است قابلیتی از kubelet به محیط اجرای کانتینری منتقل شود که تحت کنترل پروژه‌ی کوبرنتیز نیست. در چنین مواردی این قاعده قابل اعمال نیست، اما باید تلاش شود تا مسیر گذاری فراهم باشد که سطح بلوغ اجزا را به خطر نیندازد. در مثال محیط‌های اجرای کانتینر، این تلاش ممکن است شامل اطمینان از این باشد که محیط‌های اجرای کانتینر پرکاربرد نسخه‌هایی داشته باشند که ضمن پیاده‌سازی آن رفتار جایگزین، همان سطح پایداری را ارائه دهند.

قواعد منسوخ‌سازی قابلیت‌ها و رفتارها به این معنا نیست که همه‌ی تغییرات سیستم تابع این سیاست هستند. این قواعد فقط درباره‌ی رفتارهای مهم و قابل‌مشاهده برای کاربر اعمال می‌شوند که بر درستی برنامه‌های در حال اجرا روی کوبرنتیز یا بر مدیریت کلاسترهای کوبرنتیز اثر می‌گذارند و به‌طور کامل حذف می‌شوند.

استثنای قاعده‌ی بالا feature gateها هستند. هر feature gate یک جفت key=value است که به کاربران امکان می‌دهد قابلیت‌های آزمایشی را فعال یا غیرفعال کنند.

هدف از feature gateها پوشش چرخه‌ی عمر توسعه‌ی یک قابلیت است و قرار نیست APIهای بلندمدت باشند. بنابراین انتظار می‌رود پس از GA شدن یا کنار گذاشته شدن یک قابلیت، منسوخ و حذف شوند.

هم‌زمان با عبور یک قابلیت از مراحل مختلف، feature gate مربوط به آن نیز تکامل می‌یابد. چرخه‌ی عمر قابلیت در تطابق با feature gate متناظر آن به این صورت است:

  • آلفا: feature gate به‌طور پیش‌فرض غیرفعال است و کاربر می‌تواند آن را فعال کند.
  • بتا: feature gate به‌طور پیش‌فرض فعال است و کاربر می‌تواند آن را غیرفعال کند.
  • نسخه‌ی GA: feature gate منسوخ می‌شود (به «منسوخ‌سازی» مراجعه کنید) و از کار می‌افتد.
  • نسخه‌ی GA پس از پایان دوره‌ی منسوخ‌سازی: feature gate حذف می‌شود و فراخوانی‌های آن دیگر پذیرفته نمی‌شوند.

منسوخ‌سازی

قابلیت‌ها را می‌توان در هر نقطه‌ای از چرخه‌ی عمر پیش از GA حذف کرد. هنگامی که قابلیت‌ها پیش از GA حذف می‌شوند، feature gateهای مرتبط با آن‌ها نیز منسوخ می‌شوند.

هنگامی که فراخوانی‌ای بخواهد feature gate ازکارافتاده‌ای را غیرفعال کند، آن فراخوانی با شکست مواجه می‌شود تا از سناریوهای پشتیبانی‌نشده‌ای که ممکن است در غیر این صورت بی‌صدا اجرا شوند جلوگیری شود.

در برخی موارد، حذف قابلیت‌های پیش از GA زمان قابل‌توجهی می‌طلبد. در این موارد، feature gateها می‌توانند تا حذف کامل قابلیت مرتبط با خود فعال بمانند و پس از آن، خود feature gate را می‌توان منسوخ کرد.

اگر حذف feature gate یک قابلیت GA نیز زمان قابل‌توجهی بطلبد، فراخوانی‌های feature gate می‌توانند همچنان فعال بمانند، به شرط آنکه feature gate هیچ اثری بر قابلیت نداشته باشد و هیچ خطایی ایجاد نکند.

قابلیت‌هایی که قرار است کاربران بتوانند آن‌ها را غیرفعال کنند، باید سازوکاری برای غیرفعال‌سازی قابلیت در feature gate مرتبط داشته باشند.

نسخه‌بندی feature gateها با اجزایی که پیش‌تر بررسی شد متفاوت است؛ بنابراین قواعد منسوخ‌سازی آن‌ها به شرح زیر است:

قاعده‌ی شماره ۹: هنگامی که قابلیتی که feature gate کنترل می‌کند به شکل زیر از یک مرحله‌ی چرخه‌ی عمر به مرحله‌ی دیگر می‌رود، feature gate باید منسوخ شود. feature gateها باید دست‌کم به مدت زیر کار کنند:

  • قابلیت بتا به GA: ۶ ماه یا ۲ انتشار (هر کدام طولانی‌تر باشد)
  • قابلیت بتا به پایان عمر (EOL): ۳ ماه یا ۱ انتشار (هر کدام طولانی‌تر باشد)
  • قابلیت آلفا به پایان عمر: ۰ انتشار

قاعده‌ی شماره ۱۰: feature gateهای منسوخ‌شده باید هنگام استفاده با هشدار پاسخ دهند. هنگامی که یک feature gate منسوخ می‌شود، باید هم در یادداشت‌های انتشار و هم در راهنمای CLI مربوط مستند شود. هم هشدارها و هم مستندات باید مشخص کنند که آیا feature gate از کار افتاده است یا خیر.

منسوخ کردن یک متریک

هر یک از مؤلفه‌های control plane کوبرنتیز متریک‌هایی را ارائه می‌دهد که معمولاً از طریق اندپوینت /metrics در دسترس هستند و مدیران کلاستر معمولاً آن‌ها را جمع‌آوری می‌کنند. همهٔ متریک‌ها یکسان نیستند. برخی از آن‌ها معمولاً به‌عنوان SLI یا برای تعیین SLOها به کار می‌روند و از این رو اهمیت بیشتری دارند. متریک‌های دیگر ماهیتی آزمایشی‌تر دارند یا عمدتاً در فرایند توسعهٔ کوبرنتیز استفاده می‌شوند.

بر این اساس، متریک‌ها در سه ردهٔ پایداری (ALPHA، BETA و STABLE) قرار می‌گیرند. این رده بر نحوهٔ حذف یک متریک در نسخه‌های کوبرنتیز اثر می‌گذارد. ردهٔ هر متریک بر پایهٔ اهمیتی تعیین می‌شود که برای آن در نظر گرفته می‌شود. قواعد منسوخ کردن و حذف یک متریک به شرح زیر است:

قاعدهٔ شمارهٔ ۱۱الف: متریک‌ها، بسته به ردهٔ پایداری خود، باید دست‌کم به مدت زیر کار کنند:

  • پایدار (STABLE): ۴ نسخه یا ۱۲ ماه (هر کدام که طولانی‌تر باشد)
  • بتا (BETA): ۲ نسخه یا ۸ ماه (هر کدام که طولانی‌تر باشد)
  • آلفا (ALPHA): ۰ نسخه

قاعدهٔ شمارهٔ ۱۱ب: متریک‌ها پس از اعلام منسوخ شدن باید دست‌کم به مدت زیر کار کنند:

  • پایدار: ۳ نسخه یا ۹ ماه (هر کدام که طولانی‌تر باشد)
  • بتا: ۱ نسخه یا ۴ ماه (هر کدام که طولانی‌تر باشد)
  • آلفا: ۰ نسخه

در ابتدای متن توضیح متریک‌های منسوخ‌شده، رشتهٔ اعلان منسوخ شدن '(Deprecated from x.y)' افزوده می‌شود و هنگام ثبت متریک نیز یک لاگ هشدار صادر می‌شود. متریک‌های منسوخ‌شده نیز، مانند همتایان پایدار و منسوخ‌نشدهٔ خود، به‌طور خودکار در اندپوینت متریک‌ها ثبت می‌شوند و در نتیجه قابل مشاهده هستند.

در نسخهٔ بعدی (زمانی که مقدار deprecatedVersion متریک برابر با current_kubernetes_version - 3 شود)، متریک منسوخ‌شده به یک متریک پنهان تبدیل می‌شود. برخلاف متریک‌های منسوخ‌شده، متریک‌های پنهان دیگر به‌طور خودکار در اندپوینت متریک‌ها ثبت نمی‌شوند (و به همین دلیل پنهان نامیده می‌شوند). با این حال، می‌توان آن‌ها را به‌صراحت با یک فلگ خط فرمان در فایل اجرایی (--show-hidden-metrics-for-version=) فعال کرد. این امکان راه گریزی در اختیار مدیران کلاستر می‌گذارد تا اگر نتوانسته‌اند به هشدارهای پیشین دربارهٔ منسوخ شدن واکنش نشان دهند، به‌درستی از متریک منسوخ‌شده مهاجرت کنند. متریک‌های پنهان باید پس از یک نسخه حذف شوند.

استثناها

هیچ سیاستی نمی‌تواند همهٔ موقعیت‌های ممکن را پوشش دهد. این سیاست سندی زنده است و به مرور زمان تکامل می‌یابد. در عمل، موقعیت‌هایی پیش خواهد آمد که به‌خوبی در چارچوب این سیاست نمی‌گنجند یا این سیاست در آن‌ها به مانعی جدی تبدیل می‌شود. چنین موقعیت‌هایی باید با SIGها و رهبران پروژه مطرح شوند تا بهترین راه‌حل برای همان موارد خاص پیدا شود. در این میان همواره باید به یاد داشت که کوبرنتیز متعهد است سامانه‌ای پایدار باشد که تا حد امکان هرگز کار کاربران را مختل نکند. استثناها همیشه در تمام یادداشت‌های انتشار مرتبط اعلام خواهند شد.
