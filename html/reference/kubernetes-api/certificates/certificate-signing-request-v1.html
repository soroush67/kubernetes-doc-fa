CertificateSigningRequest

آبجکت‌های CertificateSigningRequest سازوکاری برای دریافت گواهی‌های x509 فراهم می‌کنند؛ به این صورت که یک درخواست امضای گواهی ارسال می‌شود و تأیید و صدور آن به‌صورت ناهمگام انجام می‌گیرد. Kubeletها از این API برای دریافت موارد زیر استفاده می‌کنند: 1. گواهی‌های کلاینت برای احراز هویت نزد kube-apiserver (با signerName برابر &#34;kubernetes.io/kube-apiserver-client-kubelet&#34;). 2. گواهی‌های سرور برای نقاط انتهایی TLS که kube-apiserver می‌تواند به‌صورت امن به آن‌ها متصل شود (با signerName برابر &#34;kubernetes.io/kubelet-serving&#34;). از این API می‌توان برای درخواست گواهی‌های کلاینت جهت احراز هویت نزد kube-apiserver (با signerName برابر &#34;kubernetes.io/kube-apiserver-client&#34;) یا برای دریافت گواهی از امضاکننده‌های سفارشیِ غیر کوبرنتیز استفاده کرد.

CertificateSigningRequest {#CertificateSigningRequest}

آبجکت‌های CertificateSigningRequest سازوکاری برای دریافت گواهی‌های x509 فراهم می‌کنند؛ به این صورت که یک درخواست امضای گواهی ارسال می‌شود و تأیید و صدور آن به‌صورت ناهمگام انجام می‌گیرد.

Kubeletها از این API برای دریافت موارد زیر استفاده می‌کنند:

  1. گواهی‌های کلاینت برای احراز هویت نزد kube-apiserver (با signerName برابر "kubernetes.io/kube-apiserver-client-kubelet").
  2. گواهی‌های سرور برای نقاط انتهایی TLS که kube-apiserver می‌تواند به‌صورت امن به آن‌ها متصل شود (با signerName برابر "kubernetes.io/kubelet-serving").

از این API می‌توان برای درخواست گواهی‌های کلاینت جهت احراز هویت نزد kube-apiserver (با signerName برابر "kubernetes.io/kube-apiserver-client") یا برای دریافت گواهی از امضاکننده‌های سفارشیِ غیر کوبرنتیز استفاده کرد.

expirationSeconds
integer		 expirationSeconds مدت اعتبار درخواستی برای گواهی صادرشده است. امضاکننده گواهی ممکن است گواهی‌ای با مدت اعتبار متفاوت صادر کند؛ بنابراین کلاینت باید برای تعیین مدت واقعی، تفاوت بین فیلدهای notBefore و notAfter را در گواهی صادرشده بررسی کند. پیاده‌سازی‌های درون‌درختی (in-tree) امضاکننده‌های شناخته‌شده کوبرنتیز در نسخه v1.22 و بالاتر تا زمانی به این فیلد احترام می‌گذارند که مدت درخواستی از حداکثر مدتی که طبق پرچم خط فرمان --cluster-signing-duration در kube-controller-manager می‌پذیرند بیشتر نباشد. امضاکننده‌های گواهی ممکن است به دلایل مختلف به این فیلد توجه نکنند: 1. امضاکننده قدیمی که از این فیلد اطلاعی ندارد (مانند پیاده‌سازی‌های درون‌درختی پیش از v1.22) 2. امضاکننده‌ای که حداکثر پیکربندی‌شده‌اش از مدت درخواستی کوتاه‌تر است 3. امضاکننده‌ای که حداقل پیکربندی‌شده‌اش از مدت درخواستی بلندتر است حداقل مقدار معتبر برای expirationSeconds برابر 600 است، یعنی 10 دقیقه.

signerName *
string		 signerName امضاکننده درخواستی را مشخص می‌کند و یک نام واجد شرایط (qualified name) است. درخواست‌های list/watch برای CertificateSigningRequestها می‌توانند با استفاده از fieldSelector به‌صورت "spec.signerName=NAME" بر اساس این فیلد فیلتر شوند. امضاکننده‌های شناخته‌شده کوبرنتیز عبارت‌اند از: 1. "kubernetes.io/kube-apiserver-client": گواهی‌های کلاینتی صادر می‌کند که می‌توان از آن‌ها برای احراز هویت نزد kube-apiserver استفاده کرد. درخواست‌های این امضاکننده هرگز توسط kube-controller-manager به‌صورت خودکار تأیید نمی‌شوند و کنترل‌کننده "csrsigning" در kube-controller-manager می‌تواند آن‌ها را صادر کند. 2. "kubernetes.io/kube-apiserver-client-kubelet": گواهی‌های کلاینتی صادر می‌کند که kubeletها برای احراز هویت نزد kube-apiserver از آن‌ها استفاده می‌کنند. درخواست‌های این امضاکننده را کنترل‌کننده "csrapproving" در kube-controller-manager می‌تواند به‌صورت خودکار تأیید کند و کنترل‌کننده "csrsigning" در kube-controller-manager می‌تواند آن‌ها را صادر کند. 3. "kubernetes.io/kubelet-serving": گواهی‌های سروری صادر می‌کند که kubeletها برای ارائه نقاط انتهایی TLS از آن‌ها استفاده می‌کنند و kube-apiserver می‌تواند به‌صورت امن به آن‌ها متصل شود. درخواست‌های این امضاکننده هرگز توسط kube-controller-manager به‌صورت خودکار تأیید نمی‌شوند و کنترل‌کننده "csrsigning" در kube-controller-manager می‌تواند آن‌ها را صادر کند. جزئیات بیشتر در https://k8s.io/docs/reference/access-authn-authz/certificate-signing-requests/#kubernetes-signers در دسترس است. signerNameهای سفارشی نیز می‌توانند مشخص شوند. امضاکننده موارد زیر را تعریف می‌کند: 1. توزیع اعتماد: نحوه توزیع اعتماد (بسته‌های CA). 2. سوژه‌های مجاز و رفتار امضاکننده هنگامی که سوژه‌ای غیرمجاز درخواست شود. 3. افزونه‌های x509 الزامی، مجاز یا ممنوع در درخواست (از جمله اینکه آیا subjectAltNameها مجاز هستند، چه انواعی، محدودیت‌ها بر مقادیر مجاز) و رفتار امضاکننده هنگامی که افزونه‌ای غیرمجاز درخواست شود. 4. کاربردهای کلید / کاربردهای گسترش‌یافته کلید که الزامی، مجاز یا ممنوع هستند. 5. انقضا/طول عمر گواهی: اینکه توسط امضاکننده ثابت است یا مدیر می‌تواند آن را پیکربندی کند. 6. اینکه درخواست برای گواهی‌های CA مجاز است یا خیر.

CertificateSigningRequestStatus {#CertificateSigningRequestStatus}

CertificateSigningRequestStatus شامل شرایطی (conditions) است که وضعیت تأیید، رد یا شکست درخواست و همچنین گواهی صادرشده را نشان می‌دهند.

فیلدتوضیحات
certificate
string		 certificate پس از آنکه شرط Approved وجود داشته باشد، توسط امضاکننده با گواهی صادرشده پر می‌شود. این فیلد از طریق زیرمنبع /status تنظیم می‌شود و پس از مقداردهی، تغییرناپذیر است. اگر درخواست امضای گواهی رد شود، شرطی از نوع "Denied" اضافه می‌شود و این فیلد خالی می‌ماند. اگر امضاکننده نتواند گواهی را صادر کند، شرطی از نوع "Failed" اضافه می‌شود و این فیلد خالی می‌ماند. الزامات اعتبارسنجی: 1. certificate باید شامل یک یا چند بلوک PEM باشد. 2. همه بلوک‌های PEM باید برچسب "CERTIFICATE" داشته باشند، هیچ سرآیندی (header) نداشته باشند و داده کدگذاری‌شده باید یک ساختار Certificate از نوع ASN.1 با کدگذاری BER باشد، همان‌گونه که در بخش 4 از RFC5280 توضیح داده شده است. 3. محتوای غیر PEM می‌تواند پیش از بلوک‌های PEM با برچسب "CERTIFICATE" یا پس از آن‌ها بیاید و اعتبارسنجی نمی‌شود؛ این امر برای امکان درج متن توضیحی است، همان‌گونه که در بخش 5.2 از RFC7468 توضیح داده شده است. اگر بیش از یک بلوک PEM وجود داشته باشد و تعریف spec.signerName درخواستی خلاف آن را مشخص نکرده باشد، بلوک اول گواهی صادرشده است و بلوک‌های بعدی باید به‌عنوان گواهی‌های میانی در نظر گرفته شوند و در handshakeهای TLS ارائه شوند. گواهی با قالب PEM کدگذاری شده است. هنگام سریال‌سازی به JSON یا YAML، داده‌ها علاوه بر آن با base64 نیز کدگذاری می‌شوند، بنابراین ساختار آن به این صورت است: base64( -----BEGIN CERTIFICATE----- ... -----END CERTIFICATE----- )

resourceVersion string مقدار resourceVersion محدودیتی را تعیین می‌کند که مشخص می‌سازد درخواست از کدام نسخه‌های منبع ممکن است پاسخ داده شود. برای جزئیات، به https://kubernetes.io/docs/reference/using-api/api-concepts/#resource-versions مراجعه کنید. مقدار پیش‌فرض: تنظیم‌نشده

sendInitialEvents boolean گزینه `sendInitialEvents=true` را می‌توان همراه با `watch=true` تنظیم کرد. در این حالت، جریان watch با رویدادهای مصنوعی آغاز می‌شود که وضعیت فعلی آبجکت‌های مجموعه را بازتاب می‌دهند. پس از ارسال همه این رویدادها، یک رویداد مصنوعی "Bookmark" ارسال می‌شود. این bookmark مقدار ResourceVersion (RV) متناظر با مجموعه آبجکت‌ها را گزارش می‌کند و با حاشیه‌نویسی (annotation) `"k8s.io/initial-events-end": "true"` علامت‌گذاری می‌شود. پس از آن، جریان watch طبق معمول ادامه می‌یابد و رویدادهای watch مربوط به تغییرات (پس از RV) آبجکت‌های تحت نظر را ارسال می‌کند. هنگامی که گزینه `sendInitialEvents` تنظیم شده باشد، لازم است گزینه `resourceVersionMatch` نیز تنظیم شود. معنای درخواست watch به شرح زیر است:
- مقدار `resourceVersionMatch` = NotOlderThan به‌معنای «داده‌ای که دست‌کم به‌اندازه `resourceVersion` ارائه‌شده جدید باشد» تفسیر می‌شود و رویداد bookmark زمانی ارسال می‌شود که وضعیت دست‌کم تا یک `resourceVersion` همان‌قدر تازه‌تر از مقدار ارائه‌شده در ListOptions همگام شده باشد. اگر `resourceVersion` تنظیم نشده باشد، این حالت به‌عنوان «خواندن سازگار» تفسیر می‌شود و رویداد bookmark زمانی ارسال می‌شود که وضعیت دست‌کم تا لحظه‌ای که پردازش درخواست آغاز شده است همگام شده باشد.
- اگر `resourceVersionMatch` روی هر مقدار دیگری تنظیم شده یا تنظیم نشده باشد، خطای Invalid برگردانده می‌شود. اگر `resourceVersion=""` یا `resourceVersion="0"` باشد (به دلایل سازگاری با نسخه‌های قبلی) مقدار پیش‌فرض true است و در غیر این صورت false است.

timeoutSeconds integer مهلت زمانی برای فراخوانی list/watch. این مقدار مدت فراخوانی را، صرف‌نظر از هرگونه فعالیت یا عدم فعالیت، محدود می‌کند.

continue string هنگام دریافت نتایج بیشتر از سرور باید گزینه continue تنظیم شود. از آنجا که مقدار این گزینه را سرور تعیین می‌کند، کلاینت‌ها فقط می‌توانند از مقدار continue حاصل از نتیجه یک کوئری قبلی با پارامترهای کوئری یکسان (به جز مقدار continue) استفاده کنند و سرور ممکن است مقداری را که نمی‌شناسد رد کند. اگر مقدار continue مشخص‌شده دیگر معتبر نباشد، چه به دلیل انقضا (معمولاً پنج تا پانزده دقیقه) و چه به دلیل تغییر پیکربندی سرور، سرور با خطای 410 ResourceExpired همراه با یک توکن continue پاسخ می‌دهد. اگر کلاینت به فهرستی سازگار نیاز دارد، باید فهرست‌گیری را بدون فیلد continue از ابتدا شروع کند. در غیر این صورت، کلاینت می‌تواند درخواست فهرست دیگری را با توکنی که همراه خطای 410 دریافت کرده است ارسال کند؛ سرور با فهرستی پاسخ می‌دهد که از کلید بعدی شروع می‌شود، اما از جدیدترین snapshot گرفته شده است و با نتایج قبلی فهرست ناسازگار است. آبجکت‌هایی که پس از اولین درخواست فهرست ایجاد، تغییر یا حذف شده‌اند، تا زمانی که کلیدشان بعد از «کلید بعدی» باشد، در پاسخ گنجانده می‌شوند. این فیلد زمانی که watch برابر true باشد پشتیبانی نمی‌شود. کلاینت‌ها می‌توانند یک watch را از آخرین مقدار resourceVersion بازگردانده‌شده توسط سرور آغاز کنند، بدون اینکه هیچ تغییری را از دست بدهند.
fieldSelector string انتخابگری (selector) برای محدود کردن فهرست آبجکت‌های بازگردانده‌شده بر اساس فیلدهایشان. مقدار پیش‌فرض همه آبجکت‌ها را شامل می‌شود.
labelSelector string انتخابگری برای محدود کردن فهرست آبجکت‌های بازگردانده‌شده بر اساس برچسب‌هایشان. مقدار پیش‌فرض همه آبجکت‌ها را شامل می‌شود.
limit integer limit حداکثر تعداد پاسخ‌هایی است که برای یک فراخوانی فهرست بازگردانده می‌شود. اگر آیتم‌های بیشتری وجود داشته باشد، سرور فیلد `continue` را در فراداده فهرست روی مقداری تنظیم می‌کند که می‌توان آن را همراه با همان کوئری اولیه برای دریافت مجموعه بعدی نتایج به کار برد. در صورتی که همه آبجکت‌های درخواست‌شده فیلتر شوند، تنظیم limit ممکن است کمتر از تعداد درخواستی آیتم بازگرداند (حتی صفر آیتم)، و کلاینت‌ها برای تشخیص وجود نتایج بیشتر فقط باید به وجود فیلد continue تکیه کنند. سرورها می‌توانند آرگومان limit را پشتیبانی نکنند و در این صورت همه نتایج موجود را بازمی‌گردانند. اگر limit مشخص شده باشد و فیلد continue خالی باشد، کلاینت‌ها می‌توانند فرض کنند که نتیجه دیگری وجود ندارد. این فیلد زمانی که watch برابر true باشد پشتیبانی نمی‌شود. سرور تضمین می‌کند که آبجکت‌های بازگردانده‌شده هنگام استفاده از continue با آبجکت‌های یک فراخوانی فهرست واحد بدون limit یکسان باشند؛ یعنی هیچ آبجکتی که پس از صدور درخواست اول ایجاد، تغییر یا حذف شده باشد، در درخواست‌های بعدیِ ادامه‌دار گنجانده نمی‌شود. به این ویژگی گاهی snapshot سازگار گفته می‌شود و تضمین می‌کند کلاینتی که برای دریافت یک نتیجه بسیار بزرگ در تکه‌های کوچک‌تر از limit استفاده می‌کند، همه آبجکت‌های ممکن را می‌بیند. اگر آبجکت‌ها در حین فهرست‌گیری تکه‌تکه به‌روزرسانی شوند، نسخه‌ای از آبجکت که در زمان محاسبه اولین نتیجه فهرست وجود داشته است بازگردانده می‌شود.
pretty string اگر مقدار 'true' باشد، خروجی به‌صورت خوانا (pretty printed) نمایش داده می‌شود. مقدار پیش‌فرض 'false' است، مگر آنکه user-agent نشان دهد درخواست از مرورگر یا ابزار HTTP خط فرمان (curl و wget) ارسال شده است.
resourceVersion string resourceVersion محدودیتی تعیین می‌کند که یک درخواست از چه نسخه‌های منبعی می‌تواند پاسخ داده شود. برای جزئیات به https://kubernetes.io/docs/reference/using-api/api-concepts/#resource-versions مراجعه کنید. مقدار پیش‌فرض تنظیم‌نشده است.
resourceVersionMatch string resourceVersionMatch مشخص می‌کند resourceVersion چگونه در فراخوانی‌های فهرست اعمال شود. اکیداً توصیه می‌شود برای فراخوانی‌های فهرستی که resourceVersion در آن‌ها تنظیم شده است، resourceVersionMatch نیز تنظیم شود. برای جزئیات به https://kubernetes.io/docs/reference/using-api/api-concepts/#resource-versions مراجعه کنید. مقدار پیش‌فرض تنظیم‌نشده است.
sendInitialEvents boolean `sendInitialEvents=true` را می‌توان همراه با `watch=true` تنظیم کرد. در این حالت، جریان watch با رویدادهای مصنوعی (synthetic) آغاز می‌شود تا وضعیت فعلی آبجکت‌های موجود در مجموعه را تولید کند. پس از ارسال همه این رویدادها، یک رویداد مصنوعی "Bookmark" ارسال می‌شود. این bookmark مقدار ResourceVersion (RV) متناظر با مجموعه آبجکت‌ها را گزارش می‌کند و با حاشیه‌نویسی (annotation) `"k8s.io/initial-events-end": "true"` علامت‌گذاری می‌شود. پس از آن، جریان watch به روال معمول ادامه می‌دهد و رویدادهای مربوط به تغییرات (پس از RV) آبجکت‌های تحت نظر را ارسال می‌کند. هنگامی که گزینه `sendInitialEvents` تنظیم شده باشد، باید گزینه `resourceVersionMatch` نیز تنظیم شود. معنای درخواست watch به شرح زیر است:
- `resourceVersionMatch` برابر NotOlderThan است؛ این مقدار به معنای «داده‌ای دست‌کم به‌تازگی `resourceVersion` ارائه‌شده» تفسیر می‌شود و رویداد bookmark زمانی ارسال می‌شود که وضعیت با `resourceVersion`ای همگام شده باشد که دست‌کم به‌اندازه مقدار ارائه‌شده در ListOptions تازه است. اگر `resourceVersion` تنظیم نشده باشد، این حالت به‌عنوان «خواندن سازگار» تفسیر می‌شود و رویداد bookmark زمانی ارسال می‌شود که وضعیت دست‌کم تا لحظه‌ای که پردازش درخواست آغاز شده است همگام شده باشد.
- `resourceVersionMatch` روی هر مقدار دیگری تنظیم شده باشد یا تنظیم نشده باشد، خطای Invalid بازگردانده می‌شود. اگر `resourceVersion=""` یا `resourceVersion="0"` باشد (به دلایل سازگاری با نسخه‌های قبلی)، مقدار پیش‌فرض true است و در غیر این صورت false است.
shardSelector string shardSelector فهرست آبجکت‌های بازگردانده‌شده را با یک عبارت انتخابگر shard مبتنی بر CEL محدود می‌کند. قالب آن از تابع shardRange() همراه با || (عملگر منطقی OR) برای مشخص کردن یک یا چند بازه hash استفاده می‌کند: shardRange(object.metadata.uid, '0x0', '0x8000000000000000') shardRange(object.metadata.uid, '0x0', '0x8000000000000000') || shardRange(object.metadata.uid, '0x8000000000000000', '0x10000000000000000') مسیرهای فیلد از نحو object-rooted به سبک CEL (مانند "object.metadata.uid") استفاده می‌کنند، نه قالب fieldSelector (یعنی "metadata.uid"). مسیرهای پشتیبانی‌شده فعلی: - object.metadata.uid - object.metadata.namespace مقادیر hexStart و hexEnd رشته‌های literal در CEL هستند که داخل تک‌نقل‌قول قرار می‌گیرند و با پیشوند '0x' شروع می‌شوند؛ این دو به‌ترتیب کران پایین (شامل) و کران بالا (غیرشامل) را در فضای hash ۶۴ بیتی FNV-1a تعریف می‌کنند. بازه کامل [0x0, 0x10000000000000000) است که کران بالای غیرشامل آن برابر 2^64 است. مثال‌ها: تقسیم به ۲ shard: shard 0: shardRange(object.metadata.uid, '0x0000000000000000', '0x8000000000000000') shard 1: shardRange(object.metadata.uid, '0x8000000000000000', '0x10000000000000000') تقسیم به ۴ shard: shard 0: shardRange(object.metadata.uid, '0x0000000000000000', '0x4000000000000000') shard 1: shardRange(object.metadata.uid, '0x4000000000000000', '0x8000000000000000') shard 2: shardRange(object.metadata.uid, '0x8000000000000000', '0xc000000000000000') shard 3: shardRange(object.metadata.uid, '0xc000000000000000', '0x10000000000000000') این فیلد آلفا است و فعال‌سازی feature gate با نام ShardedListAndWatch را لازم دارد.
timeoutSeconds integer مهلت زمانی فراخوانی list/watch. این مقدار مدت فراخوانی را، صرف‌نظر از هرگونه فعالیت یا عدم فعالیت، محدود می‌کند.
watch boolean تغییرات منابع توصیف‌شده را زیر نظر می‌گیرد و آن‌ها را به‌صورت جریانی از اعلان‌های افزودن، به‌روزرسانی و حذف بازمی‌گرداند. resourceVersion را مشخص کنید.

sendInitialEvents boolean می‌توان `sendInitialEvents=true` را همراه با `watch=true` تنظیم کرد. در این حالت، جریان watch با رویدادهای مصنوعی (synthetic) آغاز می‌شود که وضعیت فعلی آبجکت‌های موجود در مجموعه را ارائه می‌دهند. پس از ارسال همه‌ی این رویدادها، یک رویداد مصنوعی "Bookmark" ارسال می‌شود. این bookmark مقدار ResourceVersion (RV) متناظر با مجموعه‌ی آبجکت‌ها را گزارش می‌کند و با حاشیه‌نویسی (annotation) به‌صورت `"k8s.io/initial-events-end": "true"` علامت‌گذاری می‌شود. پس از آن، جریان watch به‌طور معمول ادامه می‌یابد و رویدادهای متناظر با تغییرات آبجکت‌های تحت نظر (پس از RV) را ارسال می‌کند. وقتی گزینه‌ی `sendInitialEvents` تنظیم شده باشد، تنظیم گزینه‌ی `resourceVersionMatch` نیز الزامی است. معنای درخواست watch به شرح زیر است:
- مقدار `resourceVersionMatch` برابر NotOlderThan به این معنا تفسیر می‌شود: «داده‌هایی که دست‌کم به‌اندازه‌ی `resourceVersion` ارائه‌شده تازه باشند»، و رویداد bookmark زمانی ارسال می‌شود که وضعیت با `resourceVersion`ای همگام شده باشد که دست‌کم به‌اندازه‌ی مقدار مشخص‌شده در ListOptions تازه است. اگر `resourceVersion` تنظیم نشده باشد، این حالت «خواندن سازگار» تفسیر می‌شود و رویداد bookmark زمانی ارسال می‌شود که وضعیت دست‌کم تا لحظه‌ای که پردازش درخواست آغاز شده است همگام شده باشد.
- اگر `resourceVersionMatch` روی هر مقدار دیگری تنظیم شده باشد یا تنظیم نشده باشد، خطای Invalid بازگردانده می‌شود. اگر `resourceVersion=""` یا `resourceVersion="0"` باشد (به‌دلایل سازگاری با نسخه‌های قبلی)، مقدار پیش‌فرض true است و در غیر این صورت false است.
shardSelector string shardSelector فهرست آبجکت‌های بازگردانده‌شده را با استفاده از یک عبارت انتخابگر shard مبتنی بر CEL محدود می‌کند. قالب آن از تابع shardRange() همراه با || (عملگر OR منطقی) برای تعیین یک یا چند بازه‌ی hash استفاده می‌کند: shardRange(object.metadata.uid, '0x0', '0x8000000000000000') shardRange(object.metadata.uid, '0x0', '0x8000000000000000') || shardRange(object.metadata.uid, '0x8000000000000000', '0x10000000000000000') مسیر فیلدها از نحو CEL با ریشه‌ی object استفاده می‌کند (برای مثال "object.metadata.uid") و قالب fieldSelector (یعنی "metadata.uid") به کار نمی‌رود. در حال حاضر مسیرهای زیر پشتیبانی می‌شوند: - object.metadata.uid - object.metadata.namespace مقادیر hexStart و hexEnd رشته‌های literal در CEL و داخل single-quote هستند که پیشوند '0x' دارند و کران پایین (شامل) و کران بالا (غیرشامل) را در فضای hash الگوریتم FNV-1a با 64 بیت تعریف می‌کنند. بازه‌ی کامل [0x0, 0x10000000000000000) است که در آن کران بالای غیرشامل برابر 2^64 است. مثال‌ها: تقسیم به 2 shard: shard 0: shardRange(object.metadata.uid, '0x0000000000000000', '0x8000000000000000') shard 1: shardRange(object.metadata.uid, '0x8000000000000000', '0x10000000000000000') تقسیم به 4 shard: shard 0: shardRange(object.metadata.uid, '0x0000000000000000', '0x4000000000000000') shard 1: shardRange(object.metadata.uid, '0x4000000000000000', '0x8000000000000000') shard 2: shardRange(object.metadata.uid, '0x8000000000000000', '0xc000000000000000') shard 3: shardRange(object.metadata.uid, '0xc000000000000000', '0x10000000000000000') این فیلد آلفا است و فعال بودن feature gate با نام ShardedListAndWatch را الزامی می‌کند.
timeoutSeconds integer مهلت زمانی فراخوانی list/watch. این مقدار مدت فراخوانی را بدون توجه به فعالیت یا عدم فعالیت محدود می‌کند.
watch boolean تغییرات منابع توصیف‌شده را زیر نظر می‌گیرد و آن‌ها را به‌صورت جریانی از اعلان‌های افزودن، به‌روزرسانی و حذف بازمی‌گرداند. resourceVersion را مشخص کنید.

نامنوعتوضیحات
pretty string اگر مقدار 'true' باشد، خروجی به‌صورت خوانا (pretty print) چاپ می‌شود. مقدار پیش‌فرض 'false' است، مگر آنکه user-agent نشان دهد درخواست از مرورگر یا ابزار HTTP خط فرمان (curl و wget) ارسال شده است.
dryRun string وجود این پارامتر نشان می‌دهد که تغییرات نباید ماندگار شوند. دستور dryRun نامعتبر یا ناشناخته به پاسخ خطا می‌انجامد و درخواست دیگر پردازش نمی‌شود. مقادیر معتبر عبارت‌اند از: - All: همه‌ی مراحل dry run پردازش می‌شوند.
fieldManager string fieldManager نامی است که به عامل یا موجودیتی که این تغییرات را اعمال می‌کند نسبت داده می‌شود. مقدار آن باید حداکثر 128 نویسه باشد و فقط شامل نویسه‌های قابل چاپ باشد، همان‌طور که در https://golang.org/pkg/unicode/#IsPrint تعریف شده است. این فیلد برای درخواست‌های apply (از نوع application/apply-patch) الزامی است، اما برای انواع patch غیر از apply (JsonPatch، MergePatch، StrategicMergePatch) اختیاری است.
fieldValidation string fieldValidation به سرور دستور می‌دهد که با آبجکت‌های موجود در درخواست (POST/PUT/PATCH) که فیلدهای ناشناخته یا تکراری دارند چگونه برخورد کند. مقادیر معتبر عبارت‌اند از: - Ignore: هر فیلد ناشناخته‌ای را که بی‌سروصدا از آبجکت حذف می‌شود نادیده می‌گیرد و از میان فیلدهای تکراری، همه را به‌جز آخرین فیلدی که رمزگشا (decoder) با آن مواجه می‌شود نادیده می‌گیرد. این رفتار پیش‌فرض پیش از نسخه‌ی v1.23 است. - Warn: برای هر فیلد ناشناخته‌ای که از آبجکت حذف می‌شود و برای هر فیلد تکراری که با آن مواجه می‌شود، یک هشدار از طریق هدر استاندارد پاسخ هشدار (warning) ارسال می‌کند. اگر خطای دیگری وجود نداشته باشد، درخواست همچنان موفق می‌شود و از میان فیلدهای تکراری فقط آخرین مورد ماندگار می‌شود. این مقدار پیش‌فرض در نسخه‌ی v1.23 و بالاتر است. - Strict: اگر قرار باشد هر فیلد ناشناخته‌ای از آبجکت حذف شود یا فیلد تکراری وجود داشته باشد، درخواست با خطای BadRequest رد می‌شود. خطای بازگردانده‌شده از سرور شامل همه‌ی فیلدهای ناشناخته و تکراری مواجه‌شده است.
force boolean Force درخواست‌های Apply را «اجباری» می‌کند. به این معنا که کاربر فیلدهای دارای تعارض را که متعلق به دیگران است دوباره در اختیار می‌گیرد. برای درخواست‌های patch از نوع غیر apply، پرچم force باید تنظیم نشده باشد.
