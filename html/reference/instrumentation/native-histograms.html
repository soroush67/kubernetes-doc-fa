پشتیبانی از هیستوگرام‌های بومی برای متریک‌های کوبرنتیز

وضعیت ویژگی: Kubernetes [] ()

اجزای کوبرنتیز می‌توانند متریک‌های هیستوگرام را علاوه بر قالب هیستوگرام کلاسیک، در قالب هیستوگرام بومی Prometheus نیز ارائه کنند. هیستوگرام‌های بومی به‌جای مرزهای ثابت، از مرزهای نمایی برای باکت‌ها استفاده می‌کنند و بهره‌وری قابل‌توجهی در ذخیره‌سازی، عملکرد بهتر کوئری‌ها و دید دقیق‌تری نسبت به توزیع داده‌ها فراهم می‌کنند.

پیش از شروع {#before-you-begin}

برای استفاده از هیستوگرام‌های بومی به موارد زیر نیاز دارید:

  • کوبرنتیز نسخه v1.36 یا بالاتر. در نسخه v1.36 باید feature gate با نام NativeHistograms را به‌صورت دستی فعال کنید. از نسخه v1.37 این قابلیت در سطح بتا قرار دارد و به‌طور پیش‌فرض فعال است.
  • Prometheus نسخه 2.40 یا بالاتر برای جمع‌آوری (scrape) و ذخیره‌سازی هیستوگرام‌های بومی. برای پیکربندی به‌ازای هر job، Prometheus نسخه 3.0 به بالا توصیه می‌شود.

هیستوگرام‌های بومی چیستند؟

هیستوگرام‌های کلاسیک Prometheus از مرزهای ثابت برای باکت‌ها استفاده می‌کنند (برای مثال، [0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5, 10] ثانیه). هر باکت یک سری زمانی جداگانه (_bucket، _count، _sum) ایجاد می‌کند که می‌تواند به مشکلات زیر منجر شود:

  • هزینه‌های بالای ذخیره‌سازی در مقیاس بزرگ، زیرا هر هیستوگرام سری‌های زمانی بسیاری تولید می‌کند.
  • مشکلات دقت، زیرا نقاط داده‌ای که در یک بازه باکت پهن قرار می‌گیرند قابل تفکیک از یکدیگر نیستند. برای مثال، درخواستی که در 1µs تکمیل می‌شود و درخواستی که در 4ms تکمیل می‌شود، هر دو در یک باکت le="0.005" قرار می‌گیرند.

هیستوگرام‌های بومی با استفاده از مرزهای نمایی باکت‌ها که به‌طور خودکار با توزیع داده‌ها تطبیق پیدا می‌کنند، این محدودیت‌ها را برطرف می‌کنند. مزایای آن‌ها عبارت‌اند از:

  • کاهش حدود ۱۰ برابری تعداد سری‌های زمانی به‌ازای هر متریک هیستوگرام، که به‌طور چشمگیری فضای ذخیره‌سازی Prometheus را کاهش می‌دهد و عملکرد کوئری‌ها را بهبود می‌بخشد.
  • وضوح دقیق‌تر برای شناسایی افت عملکرد و تعیین آستانه‌های دقیق SLO.

نحوه عملکرد

هنگامی که feature gate با نام NativeHistograms فعال باشد، اجزای کوبرنتیز متریک‌های هیستوگرام را هم‌زمان در هر دو قالب کلاسیک و بومی ارائه می‌کنند (dual exposition). قالب بازگردانده‌شده به هدر Accept در درخواست HTTP بستگی دارد (مذاکره محتوا در Prometheus). Prometheus این هدر را به‌طور خودکار بر اساس پیکربندی scrape شما تنظیم می‌کند؛ فقط زمانی که مستقیماً از endpoint مربوط به /metrics کوئری می‌گیرید لازم است به آن توجه داشته باشید.

  • قالب متنی (Accept: text/plain، OpenMetrics 1.0): فقط باکت‌های هیستوگرام کلاسیک را بازمی‌گرداند. با تمام ابزارهای موجود سازگار است.

    # Classic histogram buckets (always present)
apiserver_request_duration_seconds_bucket{le="0.005"} 1000
apiserver_request_duration_seconds_bucket{le="0.01"} 2000
...
apiserver_request_duration_seconds_bucket{le="+Inf"} 10000
apiserver_request_duration_seconds_count 10000
apiserver_request_duration_seconds_sum 450.5

  • قالب Protobuf (Accept: application/vnd.google.protobuf): هم باکت‌های کلاسیک و هم داده‌های هیستوگرام بومی را در بر دارد. زمانی که scrape_native_histograms: true در پیکربندی scrape در Prometheus برای job مربوطه تنظیم شده باشد، Prometheus این قالب را به‌طور خودکار درخواست می‌کند.

این راهبرد ارائه دوگانه تضمین می‌کند که:

  • داشبوردها و هشدارهای موجود بدون نیاز به تغییر به کار خود ادامه می‌دهند.
  • کاربران می‌توانند کوئری‌ها را با سرعت دلخواه خود به هیستوگرام‌های بومی منتقل کنند.
  • Prometheus هر قالبی را که برای دریافت آن پیکربندی شده باشد ذخیره می‌کند.

فعال‌سازی هیستوگرام‌های بومی

فعال‌سازی هیستوگرام‌های بومی فرایندی دومرحله‌ای است: فعال‌کردن feature gate روی اجزای کوبرنتیز و پیکربندی Prometheus برای جمع‌آوری هیستوگرام‌های بومی.

مرحله ۱: اطمینان از فعال‌بودن feature gate در کوبرنتیز

feature gate با نام NativeHistograms در کوبرنتیز v1.37 به‌طور پیش‌فرض فعال است. اگر از کوبرنتیز v1.36 استفاده می‌کنید، یا اگر این قابلیت را به‌صورت صریح غیرفعال کرده‌اید، feature gate با نام NativeHistograms را روی اجزای کوبرنتیزی که می‌خواهید هیستوگرام‌های بومی را از آن‌ها ارائه کنید فعال نمایید:

--feature-gates=NativeHistograms=true

این feature gate برای اجزای زیر اعمال می‌شود:

  • kube-apiserver
  • kube-controller-manager
  • kube-scheduler
  • kubelet
  • kube-proxy

متریک‌های هر جزء مستقل از سایر اجزا هستند؛ می‌توانید feature gate را به‌ازای هر جزء فعال یا غیرفعال کنید.

مرحله ۲: پیکربندی Prometheus

پیکربندی Prometheus به نسخه آن بستگی دارد.

نسخه Prometheus پشتیبانی از هیستوگرام بومی پیکربندی نکات
< 2.40 ندارد N/A فقط هیستوگرام‌های کلاسیک. فعال‌کردن feature gate در کوبرنتیز تأثیری ندارد.
2.40 – 2.x آزمایشی --enable-feature=native-histograms (سراسری) یا همه یا هیچ؛ کنترل به‌ازای هر job وجود ندارد.
3.0 – 3.7 پایدار scrape_native_histograms و always_scrape_classic_histograms به‌ازای هر job پیکربندی به‌ازای هر job توصیه می‌شود. پرچم سراسری همچنان پشتیبانی می‌شود.
3.8 پایدار پیکربندی به‌ازای هر job (برای کنترل دقیق الزامی است) پرچم سراسری فقط مقدار پیش‌فرض را برای همه jobها تغییر می‌دهد.
3.9+ پایدار فقط scrape_native_histograms به‌ازای هر job پرچم سراسری حذف شده است. باید از پیکربندی به‌ازای هر job استفاده کرد.

برای Prometheus نسخه 3.x، جهت کنترل دقیق از پیکربندی به‌ازای هر job استفاده کنید:

scrape_configs:
  - job_name: 'kubernetes-apiservers'
    scrape_native_histograms: true            # Ingest native histograms
    always_scrape_classic_histograms: true     # Keep classic format during migration

در دوره مهاجرت هر دو گزینه را روی true تنظیم کنید. این کار به شما امکان می‌دهد هیستوگرام‌های بومی را دریافت کنید و در عین حال هیستوگرام‌های کلاسیک را برای داشبوردهای موجود نگه دارید.

توجه:

هیستوگرام‌های بومی به قالب ارائه Protobuf نیاز دارند. Prometheus این مورد را به‌طور پیش‌فرض به‌صورت خودکار مدیریت می‌کند. با این حال، اگر scrape_protocols را سفارشی‌سازی کرده‌اید، مطمئن شوید که PrometheusProto در فهرست وجود دارد.

مهاجرت داشبوردها و هشدارها

احتیاط:

اگر Prometheus با scrape_native_histograms: true اما always_scrape_classic_histograms: false (مقدار پیش‌فرض) پیکربندی شده باشد، Prometheus فقط هیستوگرام‌های بومی را دریافت می‌کند. داشبوردهای موجودی که از کوئری‌های هیستوگرام کلاسیک استفاده می‌کنند (برای مثال، histogram_quantile(..._bucket...)) هیچ داده‌ای نشان نخواهند داد. در طول مهاجرت همواره always_scrape_classic_histograms: true را تنظیم کنید.

هنگام مهاجرت از کوئری‌های هیستوگرام کلاسیک به بومی، این روند را دنبال کنید:

  1. فعال‌کردن هر دو قالب: مقادیر scrape_native_histograms: true و always_scrape_classic_histograms: true را در پیکربندی scrape در Prometheus تنظیم کنید.

  2. مهاجرت کوئری‌ها: کوئری‌های داشبورد و عبارت‌های هشدار را از توابع هیستوگرام کلاسیک به معادل‌های هیستوگرام بومی به‌روزرسانی کنید.

    کوئری کلاسیک:

    histogram_quantile(0.99, rate(apiserver_request_duration_seconds_bucket[5m]))

    کوئری هیستوگرام بومی:

    histogram_quantile(0.99, rate(apiserver_request_duration_seconds[5m]))

  3. بررسی در محیط staging: همه داشبوردها و هشدارها را با کوئری‌های هیستوگرام بومی پیش از استقرار در محیط production آزمایش کنید.

  4. غیرفعال‌کردن جمع‌آوری کلاسیک: پس از تکمیل و تأیید مهاجرت، مقدار always_scrape_classic_histograms: false را تنظیم کنید تا سربار ذخیره‌سازی کاهش یابد.

غیرفعال‌سازی هیستوگرام‌های بومی

می‌توانید هیستوگرام‌های بومی را در هر زمان با یکی از دو روش زیر غیرفعال کنید:

  • از سمت Prometheus (سریع‌ترین روش، بدون نیاز به راه‌اندازی مجدد کوبرنتیز؛ فقط Prometheus 3.x): مقدار scrape_native_histograms: false را به‌ازای هر job جمع‌آوری تنظیم کنید. Prometheus در بازه scrape بعدی دوباره به جمع‌آوری قالب کلاسیک بازمی‌گردد.

  • feature gate در کوبرنتیز: جزء مورد نظر را با --feature-gates=NativeHistograms=false مجدداً راه‌اندازی کنید. پس از راه‌اندازی مجدد، فقط قالب هیستوگرام کلاسیک ارائه می‌شود.

هنگامی که هیستوگرام‌های بومی غیرفعال شوند، endpoint متریک‌ها فقط به قالب هیستوگرام کلاسیک بازمی‌گردد. داده‌های تاریخی هیستوگرام بومی در Prometheus همچنان قابل کوئری‌گرفتن باقی می‌مانند.

عیب‌یابی

  • داشبوردها پس از فعال‌سازی هیستوگرام‌های بومی هیچ داده‌ای نشان نمی‌دهند : این مشکل زمانی رخ می‌دهد که Prometheus با scrape_native_histograms: true اما always_scrape_classic_histograms: false (مقدار پیش‌فرض) پیکربندی شده باشد و داشبوردهای شما همچنان از کوئری‌های هیستوگرام کلاسیک استفاده کنند (برای مثال، histogram_quantile(..._bucket...)).

    راه‌حل: مقدار always_scrape_classic_histograms: true را تنظیم کنید تا دریافت قالب کلاسیک در زمان مهاجرت داشبوردها بازگردانده شود.

  • افزایش مصرف حافظه پس از فعال‌سازی هیستوگرام‌های بومی : افزایش اندکی در حافظه برای ذخیره‌سازی باکت‌های هیستوگرام بومی مورد انتظار است که حداکثر به ۱۶۰ باکت به‌ازای هر هیستوگرام محدود می‌شود. برای افزایش‌های غیرمنتظره، process_resident_memory_bytes را پایش کنید.

    راه‌حل: اگر فشار حافظه شدید است، دریافت هیستوگرام بومی را در Prometheus غیرفعال کنید (scrape_native_histograms: false) یا feature gate کوبرنتیز را غیرفعال نمایید.

  • Prometheus خطاهایی درباره قالب ناشناخته متریک ثبت می‌کند : نسخه Prometheus شما برای درک هیستوگرام‌های بومی بسیار قدیمی است.

    راه‌حل: Prometheus را به نسخه 2.40 یا بالاتر ارتقا دهید یا هیستوگرام‌های بومی را در کوبرنتیز غیرفعال کنید.

  • اطمینان ندارید که هیستوگرام‌های بومی ارائه می‌شوند یا خیر : وضعیت feature gate را با کوئری‌گرفتن از kubernetes_feature_enabled{name="NativeHistograms"} در Prometheus بررسی کنید. مقدار 1 نشان می‌دهد که قابلیت فعال است. همچنین می‌توانید مستقیماً با قالب protobuf از endpoint متریک‌ها کوئری بگیرید:

    curl -H "Accept: application/vnd.google.protobuf;proto=io.prometheus.client.MetricFamily;encoding=delimited" \
  https://<component-address>/metrics

    پاسخ باید برای متریک‌های هیستوگرام شامل کدگذاری هیستوگرام بومی باشد.

منابع

  • برای جزئیات درباره قالب هیستوگرام بومی و توابع کوئری، مستندات هیستوگرام‌های بومی Prometheus را مطالعه کنید.
  • برای فهرست کامل متریک‌هایی که اجزای کوبرنتیز ارائه می‌کنند، مرجع متریک‌های کوبرنتیز را ببینید.
