kubectl create

ایجاد یک منبع از یک فایل یا از stdin

خلاصه

این دستور یک منبع را از یک فایل یا از stdin ایجاد می‌کند.

قالب‌های JSON و YAML پذیرفته می‌شوند.

kubectl create -f FILENAME

مثال‌ها

  # Create a pod using the data in pod.json
  kubectl create -f ./pod.json
  
  # Create a pod based on the JSON passed into stdin
  cat pod.json | kubectl create -f -
  
  # Edit the data in registry.yaml in JSON then create the resource using the edited data
  kubectl create -f registry.yaml --edit -o json

گزینه‌ها

--allow-missing-template-keys     Default: true

اگر true باشد، هنگامی که یک فیلد یا کلید map در قالب وجود نداشته باشد، از خطاهای قالب صرف‌نظر می‌شود. این گزینه فقط برای قالب‌های خروجی golang و jsonpath کاربرد دارد.
--dry-run string[="unchanged"]     Default: "none"

مقدار آن باید "none"، "server" یا "client" باشد. در راهبرد client، فقط آبجکتی که قرار است ارسال شود چاپ می‌شود و ارسالی صورت نمی‌گیرد. در راهبرد server، درخواست سمت سرور ارسال می‌شود، اما منبع ذخیره نمی‌شود.
--edit

منبع API را پیش از ایجاد ویرایش می‌کند
--field-manager string     Default: "kubectl-create"

نام مدیری (manager) که برای ردیابی مالکیت فیلدها استفاده می‌شود.
-f, --filename strings

نام فایل، دایرکتوری یا URL فایل‌هایی که برای ایجاد منبع استفاده می‌شوند
-h, --help

راهنمای دستور create
-k, --kustomize string

دایرکتوری kustomization را پردازش می‌کند. این فلگ را نمی‌توان همراه با -f یا -R به کار برد.
-o, --output string

قالب خروجی. یکی از این مقادیر: (json, yaml, kyaml, name, go-template, go-template-file, template, templatefile, jsonpath, jsonpath-as-json, jsonpath-file).
--raw string

نشانی URI خام برای ارسال درخواست POST به سرور. از ترابرد (transport) مشخص‌شده در فایل kubeconfig استفاده می‌کند.
-R, --recursive

دایرکتوری مشخص‌شده در -f, --filename را به‌صورت بازگشتی پردازش می‌کند. این گزینه زمانی مفید است که بخواهید مانیفست‌های مرتبطی را که در یک دایرکتوری سازمان‌دهی شده‌اند مدیریت کنید.
--save-config

اگر true باشد، پیکربندی آبجکت فعلی در حاشیه‌نویسی (annotation) آن ذخیره می‌شود. در غیر این صورت، حاشیه‌نویسی بدون تغییر می‌ماند. این فلگ زمانی مفید است که بخواهید در آینده دستور kubectl apply را روی این آبجکت اجرا کنید.
-l, --selector string

انتخابگر (selector) یا همان پرس‌وجوی برچسب برای فیلتر کردن، که از '='، '=='، '!='، 'in' و 'notin' پشتیبانی می‌کند (برای مثال -l key1=value1,key2=value2,key3 in (value3)). آبجکت‌های منطبق باید همه‌ی محدودیت‌های برچسب مشخص‌شده را برآورده کنند.
--show-managed-fields

اگر true باشد، هنگام چاپ آبجکت‌ها در قالب JSON یا YAML، فیلد managedFields حفظ می‌شود.
--template string

رشته‌ی قالب یا مسیر فایل قالب برای استفاده در حالت -o=go-template یا -o=go-template-file. قالب‌ها از نوع قالب‌های golang هستند [http://golang.org/pkg/text/template/#pkg-overview].
--validate string[="strict"]     Default: "strict"

مقدار آن باید یکی از این‌ها باشد: strict (یا true)، warn، ignore (یا false). مقدار "true" یا "strict" ورودی را با یک schema اعتبارسنجی می‌کند و در صورت نامعتبر بودن، درخواست را رد می‌کند. اگر ServerSideFieldValidation در api-server فعال باشد، اعتبارسنجی سمت سرور انجام می‌شود و در غیر این صورت، اعتبارسنجی سمت کلاینت که اطمینان کمتری دارد به کار می‌رود. مقدار "warn" در صورتی که اعتبارسنجی فیلد سمت سرور در API server فعال باشد، درباره‌ی فیلدهای ناشناخته یا تکراری هشدار می‌دهد بی‌آنکه درخواست را مسدود کند، و در غیر این صورت مانند "ignore" رفتار می‌کند. مقدار "false" یا "ignore" هیچ اعتبارسنجی schema انجام نمی‌دهد و فیلدهای ناشناخته یا تکراری را بی‌صدا کنار می‌گذارد.
--windows-line-endings

فقط زمانی کاربرد دارد که --edit=true باشد. مقدار پیش‌فرض آن، پایان خط بومی پلتفرم شماست.

گزینه‌های ارث‌بری شده از والد

--as string

نام کاربری که برای این عملیات جعل هویت (impersonate) می‌شود. این کاربر می‌تواند یک کاربر عادی یا یک حساب سرویس (service account) در یک فضای نام (namespace) باشد.
--as-group strings

گروهی که برای این عملیات جعل هویت می‌شود. برای مشخص کردن چند گروه می‌توان این فلگ را تکرار کرد.
--as-uid string

شناسه‌ی UID که برای این عملیات جعل هویت می‌شود.
--as-user-extra strings

اطلاعات اضافی کاربر که برای این عملیات جعل هویت می‌شوند. برای مشخص کردن چند مقدار برای یک کلید می‌توان این فلگ را تکرار کرد.
--cache-dir string     Default: "$HOME/.kube/cache"

دایرکتوری پیش‌فرض کش
--certificate-authority string

مسیر فایل گواهی مرجع صدور گواهی (certificate authority)
--client-certificate string

مسیر فایل گواهی کلاینت برای TLS
--client-key string

مسیر فایل کلید کلاینت برای TLS
--cluster string

نام کلاستری از kubeconfig که باید استفاده شود
--context string

نام context از kubeconfig که باید استفاده شود
--disable-compression

اگر true باشد، فشرده‌سازی پاسخ برای همه‌ی درخواست‌ها به سرور غیرفعال می‌شود
--insecure-skip-tls-verify

اگر true باشد، اعتبار گواهی سرور بررسی نمی‌شود. این کار اتصال‌های HTTPS شما را ناامن می‌کند
--kubeconfig string

مسیر فایل kubeconfig برای استفاده در درخواست‌های CLI.
--kuberc string

مسیر فایل kuberc برای استفاده در تنظیمات ترجیحی. می‌توان این قابلیت را با export کردن feature gate به‌صورت KUBECTL_KUBERC=false یا خاموش کردن آن با KUBERC=off غیرفعال کرد.
--match-server-version

الزام می‌کند که نسخه‌ی سرور با نسخه‌ی کلاینت مطابقت داشته باشد
-n, --namespace string

در صورت وجود، دامنه‌ی فضای نام برای این درخواست CLI
--password string

گذرواژه برای احراز هویت پایه (basic authentication) در API server
--profile string     Default: "none"

نام پروفایلی که باید ثبت شود. یکی از این مقادیر: (none|cpu|heap|goroutine|threadcreate|block|mutex|trace)
--profile-output string     Default: "profile.pprof"

نام فایلی که پروفایل در آن نوشته می‌شود
--proxy-url string

نشانی پراکسی برای استفاده در درخواست‌ها به API server
--request-timeout string     Default: "0"

مدت زمان انتظار پیش از صرف‌نظر کردن از یک درخواست به سرور. مقادیر غیرصفر باید واحد زمانی متناظر داشته باشند (برای مثال 1s، 2m یا 3h). مقدار صفر یعنی درخواست‌ها هیچ‌گاه به پایان مهلت زمانی نمی‌رسند.
-s, --server string

نشانی و پورت API server کوبرنتیز
--storage-driver-buffer-duration duration     Default: 1m0s

عملیات نوشتن در درایور ذخیره‌سازی به همین مدت بافر می‌شوند و سپس در قالب یک تراکنش واحد در بک‌اندهای غیرحافظه‌ای ثبت می‌شوند
--storage-driver-db string     Default: "cadvisor"

نام پایگاه داده
--storage-driver-host string     Default: "localhost:8086"

نشانی host:port پایگاه داده
--storage-driver-password string     Default: "root"

گذرواژه‌ی پایگاه داده
--storage-driver-secure

استفاده از اتصال امن به پایگاه داده
--storage-driver-table string     Default: "stats"

نام جدول
--storage-driver-user string     Default: "root"

نام کاربری پایگاه داده
--tls-server-name string

نام سرور برای اعتبارسنجی گواهی سرور. اگر مشخص نشود، از نام میزبانی استفاده می‌شود که برای برقراری ارتباط با سرور به کار رفته است
--token string

توکن Bearer برای احراز هویت در API server
--user string

نام کاربری از kubeconfig که باید استفاده شود
--username string

نام کاربری برای احراز هویت پایه در API server
--version version[=true]

گزینه‌های --version و --version=raw اطلاعات نسخه را چاپ می‌کنند و خارج می‌شوند؛ گزینه‌ی --version=vX.Y.Z... نسخه‌ی گزارش‌شده را تنظیم می‌کند
--warnings-as-errors

هشدارهای دریافتی از سرور را خطا در نظر می‌گیرد و با کد خروج غیرصفر خارج می‌شود

همچنین ببینید

  • kubectl - ابزار kubectl مدیر کلاستر کوبرنتیز را کنترل می‌کند
  • kubectl create clusterrole - ایجاد یک نقش کلاستر (cluster role)
  • kubectl create clusterrolebinding - ایجاد یک اتصال نقش کلاستر (cluster role binding) برای یک نقش کلاستر مشخص
  • kubectl create configmap - ایجاد یک ConfigMap از یک فایل محلی، دایرکتوری یا مقدار لفظی
  • kubectl create cronjob - ایجاد یک CronJob با نام مشخص‌شده
  • kubectl create deployment - ایجاد یک Deployment با نام مشخص‌شده
  • kubectl create ingress - ایجاد یک Ingress با نام مشخص‌شده
  • kubectl create job - ایجاد یک Job با نام مشخص‌شده
  • kubectl create namespace - ایجاد یک فضای نام با نام مشخص‌شده
  • kubectl create poddisruptionbudget - ایجاد یک PodDisruptionBudget با نام مشخص‌شده
  • kubectl create priorityclass - ایجاد یک PriorityClass با نام مشخص‌شده
  • kubectl create quota - ایجاد یک سهمیه (quota) با نام مشخص‌شده
  • kubectl create role - ایجاد یک نقش (role) با یک قاعده‌ی واحد
  • kubectl create rolebinding - ایجاد یک اتصال نقش (role binding) برای یک نقش یا نقش کلاستر مشخص
  • kubectl create secret - ایجاد یک Secret با استفاده از یک زیردستور مشخص
  • kubectl create service - ایجاد یک Service با استفاده از یک زیردستور مشخص
  • kubectl create serviceaccount - ایجاد یک حساب سرویس با نام مشخص‌شده
  • kubectl create token - درخواست یک توکن حساب سرویس
