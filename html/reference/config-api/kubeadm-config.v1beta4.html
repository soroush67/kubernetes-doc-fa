پیکربندی kubeadm (v1beta4)

نمای کلی

بسته v1beta4 نسخه v1beta4 از قالب فایل پیکربندی kubeadm را تعریف می‌کند. این نسخه با رفع چند مشکل جزئی و افزودن چند فیلد جدید، قالب v1beta3 را بهبود می‌بخشد.

فهرست تغییرات نسبت به v1beta3:

v1.35:

  • افزودن فیلد httpEndpoints به ClusterConfiguration.etcd.externalEtcd که می‌توان از آن برای پیکربندی نقاط پایانی HTTP برای ارتباط با etcd در v1beta4 استفاده کرد. این فیلد برای جداکردن ترافیک HTTP (مانند نقاط پایانی /metrics و /health) از ترافیک gRPC که توسط endpoints مدیریت می‌شود به کار می‌رود. این جداسازی کنترل دسترسی بهتری را ممکن می‌کند، زیرا نقاط پایانی HTTP را می‌توان بدون در معرض قراردادن رابط اصلی gRPC در دسترس قرار داد. این فیلد با پیکربندی --listen-client-http-urls در etcd متناظر است. در صورت مشخص‌نشدن، endpoints هم برای ترافیک gRPC و هم برای ترافیک HTTP استفاده خواهد شد.

v1.34:

  • افزودن "ECDSA-P384" به گزینه‌های مجاز الگوریتم رمزنگاری برای ClusterConfiguration.encryptionAlgorithm.

v1.33:

  • افزودن فیلد EtcdUpgrade به UpgradeConfiguration.plan که می‌توان از آن برای کنترل نمایش یا عدم نمایش طرح ارتقای etcd استفاده کرد.

v1.31:

  • پشتیبانی از متغیرهای محیطی سفارشی در مؤلفه‌های control plane در ClusterConfiguration. برای این کار از apiServer.extraEnvs، controllerManager.extraEnvs، scheduler.extraEnvs و etcd.local.extraEnvs استفاده کنید.
  • نوع API با نام ResetConfiguration اکنون در v1beta4 پشتیبانی می‌شود. کاربران می‌توانند با ارسال یک فایل --config به kubeadm reset، یک نود را بازنشانی کنند.
  • حالت اجرای آزمایشی (dry run) اکنون در InitConfiguration و JoinConfiguration قابل پیکربندی است.
  • نگاشت‌های موجود آرگومان‌های اضافی از نوع رشته/رشته با آرگومان‌های اضافی ساخت‌یافته جایگزین شده‌اند که از موارد تکراری پشتیبانی می‌کنند. این تغییر در ClusterConfiguration برای apiServer.extraArgs، controllerManager.extraArgs، scheduler.extraArgs و etcd.local.extraArgs اعمال می‌شود. همچنین برای nodeRegistration.kubeletExtraArgs نیز اعمال می‌شود.
  • افزودن ClusterConfiguration.encryptionAlgorithm که می‌توان از آن برای تعیین الگوریتم رمزنگاری نامتقارن مورد استفاده برای کلیدها و گواهی‌های این کلاستر استفاده کرد. مقدار آن می‌تواند یکی از "RSA-2048" (پیش‌فرض)، "RSA-3072"، "RSA-4096" یا "ECDSA-P256" باشد.
  • افزودن ClusterConfiguration.dns.disabled و ClusterConfiguration.proxy.disabled که می‌توان از آن‌ها برای غیرفعال‌کردن افزونه‌های CoreDNS و kube-proxy در زمان راه‌اندازی اولیه کلاستر استفاده کرد. رد شدن از فازهای افزونه‌های مربوطه در زمان ایجاد کلاستر نیز همین فیلدها را روی true تنظیم می‌کند.
  • افزودن فیلد nodeRegistration.imagePullSerial در InitConfiguration و JoinConfiguration که می‌توان از آن برای کنترل اینکه kubeadm ایمیج‌ها را به‌صورت ترتیبی یا موازی دریافت کند، استفاده کرد.
  • API با نام UpgradeConfiguration در kubeadm اکنون هنگام ارسال --config به زیردستورهای kubeadm upgrade در v1beta4 پشتیبانی می‌شود. استفاده از پیکربندی مؤلفه‌ها برای kubelet و kube-proxy، InitConfiguration و ClusterConfiguration منسوخ شده است و هنگام ارسال --config به زیردستورهای upgrade نادیده گرفته می‌شود.
  • افزودن ساختار Timeouts به InitConfiguration، JoinConfiguration، ResetConfiguration و UpgradeConfiguration که می‌توان از آن برای پیکربندی مهلت‌های زمانی مختلف استفاده کرد. فیلد ClusterConfiguration.timeoutForControlPlane با Timeouts.controlPlaneComponentHealthCheck جایگزین شده است. فیلد JoinConfiguration.discovery.timeout با timeouts.Discovery جایگزین شده است.
  • افزودن فیلدهای certificateValidityPeriod و caCertificateValidityPeriod به ClusterConfiguration. این فیلدها را می‌توان برای کنترل مدت اعتبار گواهی‌هایی که kubeadm در زیردستورهایی مانند init، join، upgrade و certs تولید می‌کند، به کار برد. مقادیر پیش‌فرض همچنان ۱ سال برای گواهی‌های غیر CA و ۱۰ سال برای گواهی‌های CA است. همچنان فقط گواهی‌های غیر CA با kubeadm certs renew قابل تمدید هستند.

مهاجرت از نسخه‌های قدیمی پیکربندی kubeadm

  • kubeadm نسخه v1.15.x و جدیدتر را می‌توان برای مهاجرت از v1beta1 به v1beta2 به کار برد.
  • kubeadm نسخه v1.22.x و جدیدتر دیگر از v1beta1 و APIهای قدیمی‌تر پشتیبانی نمی‌کند، اما می‌توان از آن برای مهاجرت از v1beta2 به v1beta3 استفاده کرد.
  • kubeadm نسخه v1.27.x و جدیدتر دیگر از v1beta2 و APIهای قدیمی‌تر پشتیبانی نمی‌کند.
  • kubeadm نسخه v1.31.x و جدیدتر را می‌توان برای مهاجرت از v1beta3 به v1beta4 به کار برد.

مفاهیم پایه

روش توصیه‌شده برای پیکربندی kubeadm این است که یک فایل پیکربندی YAML را با گزینه --config ارسال کنید. برخی از گزینه‌های پیکربندی تعریف‌شده در فایل پیکربندی kubeadm به‌صورت فلگ‌های خط فرمان نیز در دسترس هستند، اما در این روش فقط رایج‌ترین و ساده‌ترین موارد استفاده پشتیبانی می‌شوند.

یک فایل پیکربندی kubeadm می‌تواند شامل چندین نوع پیکربندی باشد که با سه خط تیره (---) از هم جدا می‌شوند.

kubeadm از انواع پیکربندی زیر پشتیبانی می‌کند:

apiVersion: kubeadm.k8s.io/v1beta4
kind: InitConfiguration

apiVersion: kubeadm.k8s.io/v1beta4
kind: ClusterConfiguration

apiVersion: kubelet.config.k8s.io/v1beta1
kind: KubeletConfiguration

apiVersion: kubeproxy.config.k8s.io/v1alpha1
kind: KubeProxyConfiguration

apiVersion: kubeadm.k8s.io/v1beta4
kind: JoinConfiguration

apiVersion: kubeadm.k8s.io/v1beta4
kind: ResetConfiguration

apiVersion: kubeadm.k8s.io/v1beta4
kind: UpgradeConfiguration

برای چاپ مقادیر پیش‌فرض اقدام‌های init و join از دستورهای زیر استفاده کنید:

kubeadm config print init-defaults
kubeadm config print join-defaults
kubeadm config print reset-defaults
kubeadm config print upgrade-defaults

فهرست انواع پیکربندی که باید در یک فایل پیکربندی گنجانده شوند، به اقدامی که انجام می‌دهید (init یا join) و به گزینه‌های پیکربندی‌ای که قصد استفاده از آن‌ها را دارید (مقادیر پیش‌فرض یا سفارشی‌سازی پیشرفته) بستگی دارد.

اگر برخی از انواع پیکربندی ارائه نشوند یا فقط به‌صورت ناقص ارائه شوند، kubeadm از مقادیر پیش‌فرض استفاده می‌کند؛ مقادیر پیش‌فرضی که kubeadm فراهم می‌کند شامل اعمال سازگاری مقادیر میان مؤلفه‌ها در صورت لزوم نیز هستند (برای مثال فلگ --cluster-cidr در controller manager و clusterCIDR در kube-proxy).

کاربران همواره می‌توانند مقادیر پیش‌فرض را بازنویسی کنند، به‌جز زیرمجموعه کوچکی از تنظیمات مرتبط با امنیت (برای مثال اعمال اجباری حالت مجوزدهی Node و RBAC در API server).

اگر کاربر نوع پیکربندی‌ای را ارائه کند که برای اقدامی که در حال انجام آن هستید مورد انتظار نیست، kubeadm آن نوع‌ها را نادیده می‌گیرد و یک هشدار چاپ می‌کند.

انواع پیکربندی kubeadm init

هنگام اجرای kubeadm init با گزینه --config، می‌توان از انواع پیکربندی زیر استفاده کرد: InitConfiguration، ClusterConfiguration، KubeProxyConfiguration و KubeletConfiguration، اما فقط یکی از InitConfiguration و ClusterConfiguration الزامی است.

apiVersion: kubeadm.k8s.io/v1beta4
kind: InitConfiguration
bootstrapTokens:
...
nodeRegistration:
...

نوع InitConfiguration باید برای پیکربندی تنظیمات زمان اجرا به کار رود؛ این تنظیمات در مورد kubeadm init شامل پیکربندی توکن bootstrap و همه تنظیماتی است که مختص نودی هستند که kubeadm روی آن اجرا می‌شود، از جمله:

  • NodeRegistration که شامل فیلدهای مربوط به ثبت نود جدید در کلاستر است؛ از آن برای سفارشی‌سازی نام نود، سوکت CRI مورد استفاده یا هر تنظیم دیگری که فقط باید روی این نود اعمال شود (برای مثال IP نود) استفاده کنید.

  • LocalAPIEndpoint که نقطه پایانی نمونه API server را که باید روی این نود مستقر شود نشان می‌دهد؛ برای مثال از آن برای سفارشی‌سازی آدرس اعلان‌شده (advertise address) API server استفاده کنید.

apiVersion: kubeadm.k8s.io/v1beta4
kind: ClusterConfiguration
networking:
  ...
etcd:
  ...
apiServer:
  extraArgs:
    ...
  extraVolumes:
    ...
...

نوع ClusterConfiguration باید برای پیکربندی تنظیمات سراسری کلاستر به کار رود، از جمله تنظیمات مربوط به:

  • networking که پیکربندی توپولوژی شبکه کلاستر را نگه می‌دارد؛ برای مثال از آن برای سفارشی‌سازی زیرشبکه Pod یا زیرشبکه سرویس‌ها استفاده کنید.

  • etcd: برای مثال از آن برای سفارشی‌سازی etcd محلی یا پیکربندی API server برای استفاده از یک کلاستر etcd خارجی استفاده کنید.

  • پیکربندی‌های kube-apiserver، kube-scheduler و kube-controller-manager؛ از آن‌ها برای سفارشی‌سازی مؤلفه‌های control plane با افزودن تنظیمات سفارشی یا بازنویسی تنظیمات پیش‌فرض kubeadm استفاده کنید.

apiVersion: kubeproxy.config.k8s.io/v1alpha1
kind: KubeProxyConfiguration
...

نوع KubeProxyConfiguration باید برای تغییر پیکربندی‌ای که به نمونه‌های kube-proxy مستقرشده در کلاستر ارسال می‌شود به کار رود. اگر این آبجکت ارائه نشود یا فقط به‌صورت ناقص ارائه شود، kubeadm مقادیر پیش‌فرض را اعمال می‌کند.

برای مستندات رسمی kube-proxy به https://kubernetes.io/docs/reference/command-line-tools-reference/kube-proxy/ یا https://pkg.go.dev/k8s.io/kube-proxy/config/v1alpha1#KubeProxyConfiguration مراجعه کنید.

apiVersion: kubelet.config.k8s.io/v1beta1
kind: KubeletConfiguration
...

نوع KubeletConfiguration باید برای تغییر پیکربندی‌هایی که به همه نمونه‌های kubelet مستقرشده در کلاستر ارسال می‌شوند به کار رود. اگر این آبجکت ارائه نشود یا فقط به‌صورت ناقص ارائه شود، kubeadm مقادیر پیش‌فرض را اعمال می‌کند.

برای مستندات رسمی kubelet به https://kubernetes.io/docs/reference/command-line-tools-reference/kubelet/ یا https://pkg.go.dev/k8s.io/kubelet/config/v1beta1#KubeletConfiguration مراجعه کنید.

انواع پیکربندی kubeadm join

هنگام اجرای kubeadm join با گزینه --config، باید نوع JoinConfiguration ارائه شود.

apiVersion: kubeadm.k8s.io/v1beta4
kind: JoinConfiguration
discovery:
  bootstrapToken:
    apiServerEndpoint: some-address:6443
    token: abcdef.0123456789abcdef
    unsafeSkipCAVerification: true
  tlsBootstrapToken: abcdef.0123456789abcdef

نوع JoinConfiguration باید برای پیکربندی تنظیمات زمان اجرا به کار رود؛ این تنظیمات در مورد kubeadm join شامل روش کشف (discovery) مورد استفاده برای دسترسی به اطلاعات کلاستر و همه تنظیماتی است که مختص نودی هستند که kubeadm روی آن اجرا می‌شود، از جمله:

  • nodeRegistration که شامل فیلدهای مربوط به ثبت نود جدید در کلاستر است؛ از آن برای سفارشی‌سازی نام نود، سوکت CRI مورد استفاده یا هر تنظیم دیگری که فقط باید روی این نود اعمال شود (برای مثال IP نود) استفاده کنید.

  • apiEndpoint که نقطه پایانی نمونه API server را که در نهایت باید روی این نود مستقر شود نشان می‌دهد.

انواع پیکربندی kubeadm upgrade

هنگام اجرای kubeadm upgrade با گزینه --config، باید نوع UpgradeConfiguration ارائه شود.

apiVersion: kubeadm.k8s.io/v1beta4
kind: UpgradeConfiguration
apply:
  ...
diff:
  ...
node:
  ...
plan:
  ...

ساختار UpgradeConfiguration شامل چند زیرساختار است که هر کدام فقط برای زیردستورهای مختلف kubeadm upgrade اعمال می‌شوند. برای مثال، زیرساختار apply با زیردستور kubeadm upgrade apply استفاده می‌شود و در چنین حالتی همه زیرساختارهای دیگر نادیده گرفته می‌شوند.

BootstrapToken یک توکن بوت‌استرپ را توصیف می‌کند که به‌صورت یک Secret در کلاستر ذخیره می‌شود.

فیلدتوضیحات
token [الزامی]
BootstrapTokenString

token برای برقراری اعتماد دوطرفه بین نودها و control plane به کار می‌رود. از آن برای پیوستن نودها به کلاستر استفاده می‌شود.
description
string

description پیامی خوانا برای انسان تعیین می‌کند که توضیح می‌دهد این توکن چرا وجود دارد و برای چه منظوری استفاده می‌شود، تا سایر مدیران بتوانند هدف آن را بدانند.
ttl
meta/v1.Duration

ttl مدت زمان زنده ماندن (time to live) این توکن را تعیین می‌کند. مقدار پیش‌فرض 24h است. expires و ttl متقابلاً ناسازگارند و نمی‌توان هر دو را همزمان تنظیم کرد.
