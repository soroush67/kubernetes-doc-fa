kubeadm Configuration (v1beta3)

Overview

بسته v1beta3 نسخه v1beta3 از قالب فایل پیکربندی kubeadm را تعریف می‌کند. این نسخه با رفع برخی مشکلات جزئی و افزودن چند فیلد جدید، قالب v1beta2 را بهبود می‌بخشد.

فهرست تغییرات نسبت به v1beta2:

  • فیلد منسوخ‌شده "ClusterConfiguration.useHyperKubeImage" حذف شده است. kubeadm دیگر از ایمیج hyperkube پشتیبانی نمی‌کند.
  • فیلد "ClusterConfiguration.dns.type" حذف شده است، زیرا CoreDNS تنها نوع سرور DNS است که kubeadm از آن پشتیبانی می‌کند.
  • تگ‌های "datapolicy" به فیلدهایی که اطلاعات محرمانه را نگه می‌دارند افزوده شده‌اند. در نتیجه، هنگام چاپ ساختارهای API با klog، مقادیر این فیلدها حذف می‌شوند.
  • فیلدهای "InitConfiguration.skipPhases" و "JoinConfiguration.skipPhases" افزوده شده‌اند تا امکان رد کردن فهرستی از فازها در زمان اجرای دستور kubeadm init/join فراهم شود.
  • فیلدهای "InitConfiguration.nodeRegistration.imagePullPolicy" و "JoinConfiguration.nodeRegistration.imagePullPolicy" افزوده شده‌اند تا بتوان سیاست دریافت ایمیج‌ها را در زمان اجرای "init" و "join" در kubeadm مشخص کرد. مقدار آن باید یکی از "Always"، "Never" یا "IfNotPresent" باشد. مقدار پیش‌فرض "IfNotPresent" است که رفتار موجود پیش از این افزوده شدن بوده است.
  • فیلدهای "InitConfiguration.patches.directory" و "JoinConfiguration.patches.directory" افزوده شده‌اند تا کاربر بتواند دایرکتوری‌ای را پیکربندی کند که پچ‌های مربوط به مؤلفه‌های مستقرشده توسط kubeadm از آن خوانده می‌شوند.
  • BootstrapToken* API و ابزارهای مرتبط با آن از گروه API با نام "kubeadm" به گروه جدیدی با نام "bootstraptoken" منتقل شده‌اند. نسخه v1beta3 از API مربوط به kubeadm دیگر ساختارهای BootstrapToken* را در بر نمی‌گیرد.

مهاجرت از نسخه‌های قدیمی پیکربندی kubeadm

  • kubeadm نسخه v1.15.x و جدیدتر را می‌توان برای مهاجرت از v1beta1 به v1beta2 به کار برد.
  • kubeadm نسخه v1.22.x و جدیدتر دیگر از v1beta1 و API های قدیمی‌تر پشتیبانی نمی‌کند، اما می‌توان از آن برای مهاجرت از v1beta2 به v1beta3 استفاده کرد.
  • kubeadm نسخه v1.27.x و جدیدتر دیگر از v1beta2 و API های قدیمی‌تر پشتیبانی نمی‌کند،

Basics

روش توصیه‌شده برای پیکربندی kubeadm این است که یک فایل پیکربندی YAML با گزینه --config ارسال شود. برخی از گزینه‌های پیکربندی تعریف‌شده در فایل پیکربندی kubeadm به‌صورت فلگ‌های خط فرمان نیز در دسترس هستند، اما در این روش فقط رایج‌ترین و ساده‌ترین موارد استفاده پشتیبانی می‌شوند.

یک فایل پیکربندی kubeadm می‌تواند چندین نوع پیکربندی را در خود داشته باشد که با سه خط تیره (---) از یکدیگر جدا می‌شوند.

kubeadm از انواع پیکربندی زیر پشتیبانی می‌کند:

apiVersion: kubeadm.k8s.io/v1beta3
kind: InitConfiguration

apiVersion: kubeadm.k8s.io/v1beta3
kind: ClusterConfiguration

apiVersion: kubelet.config.k8s.io/v1beta1
kind: KubeletConfiguration

apiVersion: kubeproxy.config.k8s.io/v1alpha1
kind: KubeProxyConfiguration

apiVersion: kubeadm.k8s.io/v1beta3
kind: JoinConfiguration

برای چاپ مقادیر پیش‌فرض اقدام‌های "init" و "join" از دستورات زیر استفاده کنید:

kubeadm config print init-defaults
kubeadm config print join-defaults

فهرست انواع پیکربندی که باید در یک فایل پیکربندی گنجانده شوند، به اقدامی که انجام می‌دهید (init یا join) و به گزینه‌های پیکربندی که قصد استفاده از آن‌ها را دارید (مقادیر پیش‌فرض یا سفارشی‌سازی پیشرفته) بستگی دارد.

اگر برخی انواع پیکربندی ارائه نشوند یا فقط به‌صورت ناقص ارائه شوند، kubeadm از مقادیر پیش‌فرض استفاده می‌کند؛ مقادیر پیش‌فرضی که kubeadm فراهم می‌کند، در صورت نیاز شامل اعمال هماهنگی مقادیر میان مؤلفه‌ها نیز هستند (برای مثال فلگ --cluster-cidr در controller manager و clusterCIDR در kube-proxy).

کاربران همیشه مجاز به بازنویسی مقادیر پیش‌فرض هستند، به‌جز زیرمجموعه کوچکی از تنظیمات که از نظر امنیتی اهمیت دارند (برای مثال اعمال اجباری حالت مجوزدهی Node و RBAC در API server).

اگر کاربر نوع پیکربندی‌ای را ارائه کند که برای اقدام در حال انجام انتظار نمی‌رود، kubeadm آن نوع‌ها را نادیده می‌گیرد و یک هشدار چاپ می‌کند.

Kubeadm init configuration types

هنگام اجرای kubeadm init با گزینه --config، انواع پیکربندی زیر قابل استفاده هستند: InitConfiguration، ClusterConfiguration، KubeProxyConfiguration و KubeletConfiguration، اما تنها وجود یکی از InitConfiguration و ClusterConfiguration الزامی است.

apiVersion: kubeadm.k8s.io/v1beta3
kind: InitConfiguration
bootstrapTokens:
  ...
nodeRegistration:
  ...

نوع InitConfiguration باید برای پیکربندی تنظیمات زمان اجرا استفاده شود که در مورد kubeadm init شامل پیکربندی bootstrap token و تمام تنظیماتی است که مختص نودی هستند که kubeadm روی آن اجرا می‌شود، از جمله:

  • NodeRegistration، که فیلدهای مرتبط با ثبت نود جدید در کلاستر را در بر دارد؛ از آن برای سفارشی‌سازی نام نود، سوکت CRI مورد استفاده یا هر تنظیم دیگری که باید فقط برای همین نود اعمال شود (برای مثال آدرس IP نود) استفاده کنید.

  • LocalAPIEndpoint، که نشان‌دهنده endpoint نمونه API server است که باید روی این نود مستقر شود؛ برای مثال از آن برای سفارشی‌سازی آدرس advertise شده API server استفاده کنید.

apiVersion: kubeadm.k8s.io/v1beta3
kind: ClusterConfiguration
networking:
  ...
etcd:
  ...
apiServer:
  extraArgs:
    ...
  extraVolumes:
    ...
...

نوع ClusterConfiguration باید برای پیکربندی تنظیمات سراسری کلاستر استفاده شود، از جمله تنظیمات مربوط به:

  • networking که پیکربندی توپولوژی شبکه کلاستر را در بر دارد؛ برای مثال از آن برای سفارشی‌سازی زیرشبکه Pod یا زیرشبکه سرویس‌ها استفاده کنید.

  • etcd: برای مثال از آن برای سفارشی‌سازی etcd محلی یا پیکربندی API server جهت استفاده از یک کلاستر etcd خارجی استفاده کنید.

  • پیکربندی‌های kube-apiserver، kube-scheduler و kube-controller-manager؛ از آن‌ها برای سفارشی‌سازی مؤلفه‌های control plane با افزودن تنظیمات سفارشی یا بازنویسی تنظیمات پیش‌فرض kubeadm استفاده کنید.

apiVersion: kubeproxy.config.k8s.io/v1alpha1
kind: KubeProxyConfiguration
  ...

نوع KubeProxyConfiguration باید برای تغییر پیکربندی‌ای استفاده شود که به نمونه‌های kube-proxy مستقرشده در کلاستر ارسال می‌شود. اگر این آبجکت ارائه نشود یا فقط به‌صورت ناقص ارائه شود، kubeadm مقادیر پیش‌فرض را اعمال می‌کند.

برای مستندات رسمی kube-proxy به https://kubernetes.io/docs/reference/command-line-tools-reference/kube-proxy/ یا https://pkg.go.dev/k8s.io/kube-proxy/config/v1alpha1#KubeProxyConfiguration مراجعه کنید.

apiVersion: kubelet.config.k8s.io/v1beta1
kind: KubeletConfiguration
  ...

نوع KubeletConfiguration باید برای تغییر پیکربندی‌هایی استفاده شود که به تمام نمونه‌های kubelet مستقرشده در کلاستر ارسال می‌شوند. اگر این آبجکت ارائه نشود یا فقط به‌صورت ناقص ارائه شود، kubeadm مقادیر پیش‌فرض را اعمال می‌کند.

برای مستندات رسمی kubelet به https://kubernetes.io/docs/reference/command-line-tools-reference/kubelet/ یا https://pkg.go.dev/k8s.io/kubelet/config/v1beta1#KubeletConfiguration مراجعه کنید.

Kubeadm join configuration types

هنگام اجرای kubeadm join با گزینه --config، باید نوع JoinConfiguration ارائه شود.

apiVersion: kubeadm.k8s.io/v1beta3
kind: JoinConfiguration
  ...

نوع JoinConfiguration باید برای پیکربندی تنظیمات زمان اجرا استفاده شود که در مورد kubeadm join شامل روش discovery مورد استفاده برای دسترسی به اطلاعات کلاستر و تمام تنظیماتی است که مختص نودی هستند که kubeadm روی آن اجرا می‌شود، از جمله:

  • nodeRegistration، که فیلدهای مرتبط با ثبت نود جدید در کلاستر را در بر دارد؛ از آن برای سفارشی‌سازی نام نود، سوکت CRI مورد استفاده یا هر تنظیم دیگری که باید فقط برای همین نود اعمال شود (برای مثال آدرس IP نود) استفاده کنید.

  • apiEndpoint، که نشان‌دهنده endpoint نمونه API server است که در نهایت باید روی این نود مستقر شود.

منسوخ‌شده: v1beta3 به نفع v1beta4 منسوخ شده است و در یک نسخه آینده، 1.34 یا بعد از آن، حذف خواهد شد. لطفاً مهاجرت کنید

BootstrapToken {#BootstrapToken}

در این بخش‌ها ظاهر می‌شود:

  • InitConfiguration

BootstrapToken یک توکن بوت‌استرپ را توصیف می‌کند که به‌صورت یک Secret در کلاستر ذخیره می‌شود.

فیلدتوضیحات
token [الزامی]
BootstrapTokenString

token برای برقراری اعتماد دوطرفه بین نودها و control planeها استفاده می‌شود. از این توکن برای پیوستن نودها به کلاستر استفاده می‌شود.
description
string

description یک پیام خوانا برای انسان تعیین می‌کند که توضیح می‌دهد این توکن چرا وجود دارد و برای چه مقصودی استفاده می‌شود، تا سایر مدیران بتوانند هدف آن را بدانند.
ttl
meta/v1.Duration

ttl مدت زمان بقای (time to live) این توکن را تعیین می‌کند. مقدار پیش‌فرض آن 24h است. فیلدهای expires و ttl متقابلاً ناسازگارند و نمی‌توان هر دو را همزمان تعیین کرد.
expires
meta/v1.Time

expires زمان انقضای این توکن را مشخص می‌کند. به‌طور پیش‌فرض، مقدار آن در زمان اجرا و بر اساس ttl به‌صورت پویا تعیین می‌شود. فیلدهای expires و ttl متقابلاً ناسازگارند و نمی‌توان هر دو را همزمان تعیین کرد.
usages
[]string

usages روش‌هایی را که می‌توان از این توکن استفاده کرد توصیف می‌کند. به‌طور پیش‌فرض می‌توان از آن برای برقراری اعتماد دوطرفه استفاده کرد، اما می‌توان این رفتار را در اینجا تغییر داد.
groups
[]string

groups گروه‌های اضافی را مشخص می‌کند که در صورت استفاده از این توکن برای احراز هویت، این توکن با آن گروه‌ها احراز هویت خواهد شد.

BootstrapTokenString {#BootstrapTokenString}

در این بخش‌ها ظاهر می‌شود:

  • BootstrapToken

BootstrapTokenString توکنی با قالب abcdef.abcdef0123456789 است که هم برای اعتبارسنجی در دسترس‌بودن عملی API server از دیدگاه نودِ در حال پیوستن، و هم به‌عنوان روش احراز هویت نود در مرحله بوت‌استرپ دستور "kubeadm join" استفاده می‌شود. این توکن کوتاه‌مدت است و باید کوتاه‌مدت باشد.

string 		توضیحی ارائه نشده است.

ClusterConfiguration {#kubeadm-k8s-io-v1beta3-ClusterConfiguration}

ClusterConfiguration شامل پیکربندی سراسری کلاستر برای یک کلاستر kubeadm است.

فیلدتوضیحات
apiVersion
string		kubeadm.k8s.io/v1beta3
kind
string		ClusterConfiguration
etcd
Etcd

etcd پیکربندی etcd را در بر دارد.
networking
Networking

networking پیکربندی توپولوژی شبکه کلاستر را در بر دارد.
kubernetesVersion
string

kubernetesVersion نسخه هدف control plane است.
controlPlaneEndpoint
string

controlPlaneEndpoint یک آدرس IP یا نام DNS پایدار برای control plane تعیین می‌کند. مقدار آن می‌تواند یک آدرس IP معتبر یا یک زیردامنه DNS مطابق RFC-1123 باشد که هر دو می‌توانند یک پورت TCP اختیاری داشته باشند. اگر controlPlaneEndpoint مشخص نشده باشد، از advertiseAddress + bindPort استفاده می‌شود؛ اگر controlPlaneEndpoint بدون پورت TCP مشخص شده باشد، از bindPort استفاده می‌شود. کاربردهای ممکن عبارت‌اند از:

  • در یک کلاستر با بیش از یک نمونه control plane، آدرس load balancer خارجیِ مستقر در جلوی نمونه‌های control plane باید به این فیلد اختصاص داده شود.
  • در محیط‌هایی که بازیافت اجباری نودها اعمال می‌شود، می‌توان از controlPlaneEndpoint برای اختصاص یک DNS پایدار به control plane استفاده کرد.
apiServer
APIServer

apiServer شامل تنظیمات اضافی برای API server است.
controllerManager
ControlPlaneComponent

controllerManager شامل تنظیمات اضافی برای controller manager است.
scheduler
ControlPlaneComponent

scheduler شامل تنظیمات اضافی برای زمان‌بند (scheduler) است.
dns
DNS

dns گزینه‌های افزونه DNS نصب‌شده در کلاستر را تعریف می‌کند.
certificatesDir
string

certificatesDir مشخص می‌کند که همه گواهی‌های موردنیاز در کجا ذخیره می‌شوند یا از کجا جست‌وجو می‌شوند.
imageRepository
string

imageRepository رجیستری کانتینری را که ایمیج‌ها از آن دریافت می‌شوند تعیین می‌کند. اگر خالی باشد، به‌طور پیش‌فرض از registry.k8s.io استفاده می‌شود. اگر نسخه کوبرنتیز یک بیلد CI باشد (نسخه کوبرنتیز با ci/ شروع شود)، gcr.io/k8s-staging-ci-images به‌طور پیش‌فرض برای مؤلفه‌های control plane و برای kube-proxy استفاده می‌شود، در حالی که registry.k8s.io برای سایر ایمیج‌ها استفاده خواهد شد.
featureGates
map[string]bool

featureGates شامل feature gateهای مختص kubeadm است که کاربر آن‌ها را فعال کرده است.

caCertHashes مجموعه‌ای از pinهای کلید عمومی را مشخص می‌کند که در صورت استفاده از کشف مبتنی بر توکن باید راستی‌آزمایی شوند. CA ریشه‌ای که در طول کشف یافت می‌شود باید با یکی از این مقادیر مطابقت داشته باشد. تعیین یک مجموعه خالی، pin کردن CA ریشه را غیرفعال می‌کند که می‌تواند ناامن باشد. هر هش به‌صورت <type>:<value> مشخص می‌شود که تنها نوع پشتیبانی‌شده فعلی "sha256" است. این مقدار یک هش SHA-256 با کدگذاری هگزادسیمال از آبجکت Subject Public Key Info (SPKI) در قالب ASN.1 با کدگذاری DER است. این هش‌ها را می‌توان برای مثال با OpenSSL محاسبه کرد.

taints [Required]
[]core/v1.Taint

فیلد taints taintهایی را مشخص می‌کند که آبجکت Node API باید با آن‌ها ثبت شود. اگر این فیلد تنظیم نشده باشد، یعنی nil باشد، برای نودهای control-plane مقدار پیش‌فرض آن یک taint مربوط به control-plane خواهد بود. اگر نمی‌خواهید نود control-plane شما taint داشته باشد، این فیلد را روی یک فهرست خالی تنظیم کنید، یعنی در فایل YAML مقدار taints: [] را بنویسید. این فیلد صرفاً برای ثبت Node استفاده می‌شود.
kubeletExtraArgs
map[string]string

فیلد kubeletExtraArgs آرگومان‌های اضافی را به kubelet منتقل می‌کند. آرگومان‌های این فیلد از طریق فایل محیطی (environment file) که kubeadm در زمان اجرا می‌نویسد و kubelet آن را بارگذاری می‌کند، به خط فرمان kubelet داده می‌شوند. این مقادیر، پیکربندی عمومی در سطح پایه موجود در ConfigMap با نام kubelet-config را بازنویسی می‌کنند. هنگام تجزیه (parse)، فلگ‌ها اولویت بالاتری دارند. این مقادیر محلی هستند و مختص نودی‌اند که kubeadm روی آن در حال اجراست. هر کلید در این map نام فلگ است، همان‌گونه که در خط فرمان ظاهر می‌شود، اما بدون خط تیره(های) ابتدایی.
ignorePreflightErrors
[]string

فیلد ignorePreflightErrors فهرستی از خطاهای pre-flight را فراهم می‌کند که هنگام ثبت نود جاری نادیده گرفته می‌شوند، برای مثال IsPrevilegedUser,Swap. مقدار all خطاهای همه بررسی‌ها را نادیده می‌گیرد.
imagePullPolicy
core/v1.PullPolicy

فیلد imagePullPolicy سیاست دریافت ایمیج را در طول عملیات "init" و "join" در kubeadm مشخص می‌کند. مقدار این فیلد باید یکی از "Always"، "IfNotPresent" یا "Never" باشد. اگر این فیلد تنظیم نشود، kubeadm مقدار پیش‌فرض آن را "IfNotPresent" قرار می‌دهد، یعنی در صورت نبودن ایمیج‌های موردنیاز روی میزبان، آن‌ها را دریافت می‌کند.

Patches {#kubeadm-k8s-io-v1beta3-Patches}

نمایش داده می‌شود در:

  • InitConfiguration

  • JoinConfiguration

Patches شامل گزینه‌های مربوط به اعمال patch بر مؤلفه‌هایی است که توسط kubeadm مستقر می‌شوند.

فیلدتوضیحات
directory
string

فیلد directory مسیر دایرکتوری‌ای است که شامل فایل‌هایی با نام "target[suffix][+patchtype].extension" است. برای مثال، "kube-apiserver0+merge.yaml" یا فقط "etcd.json". مقدار "target" می‌تواند یکی از "kube-apiserver"، "kube-controller-manager"، "kube-scheduler"، "etcd"، "kubeletconfiguration" و "corednsdeployment" باشد. مقدار "patchtype" می‌تواند یکی از "strategic"، "merge" یا "json" باشد و این مقادیر با قالب‌های patch پشتیبانی‌شده توسط kubectl مطابقت دارند. مقدار پیش‌فرض "patchtype" برابر "strategic" است. مقدار "extension" باید "json" یا "yaml" باشد. مقدار "suffix" یک رشته اختیاری است که می‌توان از آن برای تعیین این‌که کدام patchها زودتر و بر اساس ترتیب الفبایی-عددی اعمال شوند، استفاده کرد.
