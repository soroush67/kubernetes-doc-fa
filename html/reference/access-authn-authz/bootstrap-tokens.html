احراز هویت با Bootstrap Token‌ها

وضعیت ویژگی: Kubernetes v1.18 [stable] (پایدار)

Bootstrap Token‌ها توکن‌های حامل (bearer token) ساده‌ای هستند که برای ایجاد کلاستر‌های جدید یا افزودن نودهای جدید به یک کلاستر موجود طراحی شده‌اند. این توکن‌ها برای پشتیبانی از kubeadm ساخته شده‌اند، اما در سایر زمینه‌ها نیز برای کاربرانی که می‌خواهند کلاستر‌ها را بدون kubeadm راه‌اندازی کنند، قابل استفاده‌اند. همچنین طوری طراحی شده‌اند که از طریق سیاست RBAC با سامانهٔ kubelet TLS Bootstrapping کار کنند.

مروری بر Bootstrap Token‌ها {#bootstrap-tokens-overview}

Bootstrap Token‌ها به‌صورت نوع خاصی از Secret‌ها (با نوع bootstrap.kubernetes.io/token) تعریف می‌شوند که در فضای نام (namespace) kube-system قرار دارند. این Secret‌ها سپس توسط Bootstrap Authenticator در API Server خوانده می‌شوند. توکن‌های منقضی‌شده توسط کنترل‌کنندهٔ TokenCleaner در Controller Manager حذف می‌شوند. همچنین از این توکن‌ها برای ایجاد امضا برای یک ConfigMap مشخص که در فرایند «کشف» (discovery) استفاده می‌شود، از طریق کنترل‌کنندهٔ BootstrapSigner بهره گرفته می‌شود.

قالب توکن {#token-format}

Bootstrap Token‌ها به شکل abcdef.0123456789abcdef هستند. به‌طور دقیق‌تر، باید با عبارت منظم [a-z0-9]{6}\.[a-z0-9]{16} مطابقت داشته باشند.

بخش اول توکن «Token ID» است و اطلاعات عمومی محسوب می‌شود. از آن هنگام ارجاع به یک توکن استفاده می‌شود، بدون آنکه بخش محرمانه‌ای که برای احراز هویت به کار می‌رود افشا شود. بخش دوم «Token Secret» است و فقط باید با طرف‌های مورد اعتماد به اشتراک گذاشته شود.

فعال‌سازی احراز هویت با Bootstrap Token {#enabling-bootstrap-token-authentication}

احراز هویت‌کنندهٔ Bootstrap Token را می‌توان با فلگ زیر روی API server فعال کرد:

--enable-bootstrap-token-auth

پس از فعال‌سازی، توکن‌های bootstrap را می‌توان به‌عنوان اعتبارنامهٔ bearer token برای احراز هویت درخواست‌ها به API server به کار برد.

Authorization: Bearer 07401b.f395accd246ae52d

توکن‌ها با نام کاربری system:bootstrap:<token id> احراز هویت می‌شوند و عضو گروه system:bootstrappers هستند. گروه‌های اضافی را می‌توان در Secret مربوط به توکن مشخص کرد.

توکن‌های منقضی‌شده را می‌توان با فعال کردن کنترل‌کنندهٔ tokencleaner روی controller manager به‌صورت خودکار حذف کرد.

--controllers=*,tokencleaner

قالب Secret مربوط به Bootstrap Token {#bootstrap-token-secret-format}

هر توکن معتبر توسط یک Secret در فضای نام kube-system پشتیبانی می‌شود. سند کامل طراحی را می‌توانید اینجا بیابید.

شکل این Secret به صورت زیر است.

apiVersion: v1
kind: Secret
metadata:
  # Name MUST be of form "bootstrap-token-<token id>"
  name: bootstrap-token-07401b
  namespace: kube-system

# Type MUST be 'bootstrap.kubernetes.io/token'
type: bootstrap.kubernetes.io/token
stringData:
  # Human readable description. Optional.
  description: "The default bootstrap token generated by 'kubeadm init'."

  # Token ID and secret. Required.
  token-id: 07401b
  token-secret: f395accd246ae52d

  # Expiration. Optional.
  expiration: 2017-03-10T03:22:11Z

  # Allowed usages.
  usage-bootstrap-authentication: "true"
  usage-bootstrap-signing: "true"

  # Extra groups to authenticate the token as. Must start with "system:bootstrappers:"
  auth-extra-groups: system:bootstrappers:worker,system:bootstrappers:ingress

نوع Secret باید bootstrap.kubernetes.io/token و نام آن باید bootstrap-token-<token id> باشد. همچنین این Secret باید در فضای نام kube-system وجود داشته باشد.

اعضای usage-bootstrap-* نشان می‌دهند که این Secret برای چه مقصودی در نظر گرفته شده است. برای فعال شدن هر کاربرد، مقدار آن باید روی true تنظیم شود.

  • usage-bootstrap-authentication نشان می‌دهد که توکن را می‌توان به‌عنوان bearer token برای احراز هویت در API server به کار برد.
  • usage-bootstrap-signing نشان می‌دهد که توکن را می‌توان برای امضای ConfigMap با نام cluster-info به کار برد، همان‌طور که در ادامه توضیح داده شده است.

فیلد expiration زمان انقضای توکن را کنترل می‌کند. توکن‌های منقضی‌شده هنگام استفاده برای احراز هویت رد می‌شوند و در امضای ConfigMap نادیده گرفته می‌شوند. مقدار انقضا به‌صورت یک زمان مطلق UTC با استفاده از RFC3339 کدگذاری می‌شود. برای حذف خودکار توکن‌های منقضی‌شده، کنترل‌کنندهٔ tokencleaner را فعال کنید.

مدیریت توکن با kubeadm {#token-management-with-kubeadm}

می‌توانید از ابزار kubeadm برای مدیریت توکن‌ها در یک کلاستر در حال اجرا استفاده کنید. برای جزئیات، مستندات kubeadm token را ببینید.

امضای ConfigMap {#configmap-signing}

افزون بر احراز هویت، از توکن‌ها می‌توان برای امضای یک ConfigMap استفاده کرد. این کار در مراحل اولیهٔ فرایند bootstrap کلاستر، پیش از آنکه کلاینت به API server اعتماد کند، به کار می‌رود. ConfigMap امضاشده را می‌توان با توکن مشترک احراز اصالت کرد.

برای فعال‌سازی امضای ConfigMap، کنترل‌کنندهٔ bootstrapsigner را روی Controller Manager فعال کنید.

--controllers=*,bootstrapsigner

ConfigMap امضاشده، cluster-info در فضای نام kube-public است. روال معمول این است که کلاینت این ConfigMap را بدون احراز هویت و با نادیده گرفتن خطاهای TLS می‌خواند. سپس با بررسی امضای جاسازی‌شده در ConfigMap، صحت محتوای آن را اعتبارسنجی می‌کند.

ConfigMap ممکن است به این شکل باشد:

apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-info
  namespace: kube-public
data:
  jws-kubeconfig-07401b: eyJhbGciOiJIUzI1NiIsImtpZCI6IjA3NDAxYiJ9..tYEfbo6zDNo40MQE07aZcQX2m3EB2rO3NuXtxVMYm9U
  kubeconfig: |
    apiVersion: v1
    clusters:
    - cluster:
        certificate-authority-data: <really long certificate data>
        server: https://10.138.0.2:6443
      name: ""
    contexts: []
    current-context: ""
    kind: Config
    preferences: {}
    users: []

عضو kubeconfig در ConfigMap یک فایل پیکربندی است که فقط اطلاعات کلاستر در آن پر شده است. نکتهٔ کلیدی که از این طریق منتقل می‌شود، certificate-authority-data است. ممکن است این بخش در آینده گسترش یابد.

امضا یک امضای JWS در حالت «جداشده» (detached) است. برای اعتبارسنجی امضا، کاربر باید محتوای kubeconfig را طبق قواعد JWS کدگذاری کند (کدگذاری base64 با حذف هر = انتهایی). سپس این محتوای کدگذاری‌شده با قرار گرفتن بین دو نقطه، یک JWS کامل را تشکیل می‌دهد. می‌توانید JWS را با روش HS256 (یعنی HMAC-SHA256) و با استفاده از بخش محرمانهٔ توکن (برای نمونه f395accd246ae52d) به‌عنوان راز مشترک تأیید کنید. کاربران باید بررسی کنند که از HS256 استفاده شده است. ممکن است لازم باشد برای پذیرفته شدن راز در برخی ابزارهای اعتبارسنجی، با توجه به اینکه فقط ۱۶ بایت است، آن را از سمت راست با صفر پر کنید.

هشدار:

هر طرفی که یک توکن bootstrap در اختیار داشته باشد می‌تواند برای آن توکن یک امضای معتبر ایجاد کند. هنگام استفاده از امضای ConfigMap، توصیه نمی‌شود یک توکن یکسان با کلاینت‌های زیادی به اشتراک گذاشته شود، زیرا یک کلاینت آلوده‌شده می‌تواند به‌طور بالقوه حملهٔ man-in-the-middle را علیه کلاینت دیگری که برای bootstrap اعتماد TLS به این امضا متکی است، انجام دهد.

برای اطلاعات بیشتر، بخش جزئیات پیاده‌سازی kubeadm را مطالعه کنید.
