احراز هویت

این صفحه مروری بر احراز هویت (authentication) در کوبرنتیز ارائه می‌کند و تمرکز آن بر احراز هویت در API کوبرنتیز است.

کاربران در کوبرنتیز {#users-in-kubernetes}

همهٔ کلاسترهای کوبرنتیز دو دسته کاربر دارند: حساب‌های سرویس (service account) که توسط کوبرنتیز مدیریت می‌شوند، و کاربران عادی.

فرض بر این است که یک سرویس مستقل از کلاستر، کاربران عادی را به یکی از روش‌های زیر مدیریت می‌کند:

  • مدیری که کلیدهای خصوصی را توزیع می‌کند
  • یک مخزن کاربران مانند Keystone یا Google Accounts
  • یک فایل حاوی فهرستی از نام‌های کاربری و گذرواژه‌ها

از این منظر، کوبرنتیز آبجکتی که نمایانگر حساب‌های کاربران عادی باشد ندارد. کاربران عادی را نمی‌توان از طریق یک فراخوانی API به کلاستر افزود.

با وجود اینکه کاربر عادی را نمی‌توان از طریق فراخوانی API افزود، هر کاربری که گواهی معتبری ارائه کند که توسط مرجع صدور گواهی (CA) کلاستر امضا شده باشد، احراز هویت‌شده در نظر گرفته می‌شود. در این پیکربندی، کوبرنتیز نام کاربری را از فیلد common name در بخش 'subject' گواهی (برای مثال "/CN=bob") تعیین می‌کند. از آنجا به بعد، زیرسامانهٔ کنترل دسترسی مبتنی بر نقش (RBAC) مشخص می‌کند که آیا کاربر مجاز است عملیات خاصی را روی یک منبع انجام دهد یا خیر.

در مقابل، حساب‌های سرویس کاربرانی هستند که توسط API کوبرنتیز مدیریت می‌شوند. این حساب‌ها به فضاهای نام (namespace) مشخصی وابسته‌اند و به‌صورت خودکار توسط API server یا به‌صورت دستی از طریق فراخوانی‌های API ایجاد می‌شوند. حساب‌های سرویس به مجموعه‌ای از اعتبارنامه‌ها (credentials) مرتبط‌اند که به‌صورت Secrets ذخیره می‌شوند و در پادها mount می‌شوند تا فرایندهای درون کلاستر بتوانند با API کوبرنتیز ارتباط برقرار کنند.

درخواست‌های API یا به یک کاربر عادی یا یک حساب سرویس مرتبط می‌شوند، یا به‌عنوان درخواست‌های ناشناس در نظر گرفته می‌شوند. این بدان معناست که هر فرایندی در داخل یا خارج از کلاستر، از کاربر انسانی که kubectl را روی ایستگاه کاری خود تایپ می‌کند گرفته تا kubelets روی نودها و اجزای control plane، هنگام ارسال درخواست به API server باید احراز هویت شود، وگرنه به‌عنوان کاربر ناشناس در نظر گرفته می‌شود.

اگر تلاش کنید احراز هویت شوید و موفق باشد، API server به‌صورت خودکار شما را عضو گروه ویژهٔ system:authenticated قرار می‌دهد.

راهبردهای احراز هویت {#authentication-strategies}

کوبرنتیز از گواهی‌های کلاینت، توکن‌های bearer یا یک پروکسی احراز هویت‌کننده برای احراز هویت درخواست‌های API از طریق افزونه‌های احراز هویت استفاده می‌کند. هنگامی که درخواست‌های HTTP به API server ارسال می‌شوند، افزونه‌ها تلاش می‌کنند ویژگی‌های زیر را با درخواست مرتبط کنند:

  • نام کاربری (Username): رشته‌ای که کاربر نهایی را شناسایی می‌کند. مقادیر رایج می‌توانند kube-admin یا jane@example.com باشند.
  • UID: رشته‌ای که کاربر نهایی را شناسایی می‌کند و تلاش می‌کند از نام کاربری ثابت‌تر و یکتاتر باشد.
  • گروه‌ها (Groups): مجموعه‌ای از رشته‌ها که هر یک نشان‌دهندهٔ عضویت کاربر در یک مجموعهٔ منطقی نام‌دار از کاربران است. مقادیر رایج می‌توانند system:masters یا devops-team باشند.
  • فیلدهای اضافی (Extra fields): نگاشتی از رشته‌ها به فهرستی از رشته‌ها که اطلاعات تکمیلی‌ای را نگه می‌دارد که ممکن است برای مجوزدهنده‌ها (authorizers) مفید باشد.
توجه:

همهٔ مقادیر برای سامانهٔ احراز هویت مبهم (opaque) هستند و تنها زمانی اهمیت پیدا می‌کنند که توسط یک مجوزدهنده (authorizer) تفسیر شوند.

درخواست‌های ناشناس {#anonymous-requests}

در صورت فعال بودن، درخواست‌هایی که توسط سایر روش‌های احراز هویت پیکربندی‌شده رد نشوند، به‌عنوان درخواست‌های ناشناس در نظر گرفته می‌شوند و نام کاربری system:anonymous و گروه system:unauthenticated به آن‌ها داده می‌شود.

برای مثال، در سروری که احراز هویت با توکن پیکربندی شده و دسترسی ناشناس فعال است، درخواستی که یک bearer token نامعتبر ارائه کند، خطای 401 Unauthorized دریافت می‌کند. درخواستی که هیچ bearer token ارائه نکند، به‌عنوان درخواست ناشناس در نظر گرفته می‌شود.

دسترسی ناشناس به‌طور پیش‌فرض فعال است اگر از حالت مجوزدهی غیر از AlwaysAllow استفاده شود؛ می‌توانید با ارسال گزینهٔ خط فرمان --anonymous-auth=false به API server آن را غیرفعال کنید. مجوزدهنده‌های داخلی ABAC و RBAC نیازمند مجوزدهی صریح برای کاربر system:anonymous یا گروه system:unauthenticated هستند؛ اگر قواعد سیاستی قدیمی (از کوبرنتیز نسخهٔ 1.5 یا پیش از آن) دارید، آن قواعد قدیمی که به کاربر * یا گروه * دسترسی می‌دهند، به‌طور خودکار دسترسی کاربران ناشناس را مجاز نمی‌کنند.

پیکربندی احراز هویت‌کنندهٔ ناشناس {#anonymous-authenticator-configuration}

وضعیت ویژگی: Kubernetes [] ()

می‌توان از AuthenticationConfiguration برای پیکربندی احراز هویت‌کنندهٔ ناشناس استفاده کرد. اگر فیلد anonymous را در فایل AuthenticationConfiguration تنظیم کنید، نمی‌توانید گزینهٔ خط فرمان --anonymous-auth را تنظیم کنید.

مزیت اصلی پیکربندی احراز هویت‌کنندهٔ ناشناس با استفاده از فایل پیکربندی احراز هویت این است که علاوه بر فعال و غیرفعال کردن احراز هویت ناشناس، می‌توانید مشخص کنید کدام endpointها از احراز هویت ناشناس پشتیبانی کنند.

نمونه‌ای از فایل پیکربندی احراز هویت در ادامه آمده است:

---
#
# CAUTION: this is an example configuration.
#          Do not use this as-is for your own cluster!
#
apiVersion: apiserver.config.k8s.io/v1
kind: AuthenticationConfiguration
anonymous:
  enabled: true
  conditions:
  - path: /livez
  - path: /readyz
  - path: /healthz

در پیکربندی بالا، تنها endpointهای /livez، /readyz و /healthz برای درخواست‌های ناشناس قابل دسترسی هستند. هر endpoint دیگری به‌صورت ناشناس قابل دسترسی نخواهد بود، حتی اگر پیکربندی مجوزدهی شما آن را مجاز بداند.

روش‌های احراز هویت {#authentication-methods}

می‌توانید چندین روش احراز هویت را هم‌زمان فعال کنید. معمولاً باید دست‌کم از دو روش استفاده کنید:

  • توکن‌های حساب سرویس برای ServiceAccountها
  • دست‌کم یک روش دیگر برای احراز هویت کاربران (عادی)

روش‌های احراز هویت موجود عبارت‌اند از:

  • گواهی‌های کلاینت X.509
  • توکن‌های Bootstrap
  • توکن‌های حساب سرویس
  • فایل توکن ایستا
  • یکپارچه‌سازی‌های خارجی
    • JSON Web Tokens
    • توکن‌های OpenID Connect
    • احراز هویت توکن با Webhook
    • پروکسی معکوس احراز هویت‌کننده

هنگامی که چندین ماژول احراز هویت‌کننده فعال باشند، نخستین ماژولی که درخواست را با موفقیت احراز هویت کند، ارزیابی را کوتاه می‌کند (short-circuit) و ماژول‌های بعدی بررسی نمی‌شوند. API server ترتیب اجرای احراز هویت‌کننده‌ها را تضمین نمی‌کند.

گواهی‌های کلاینت X.509 {#x509-client-certificates}

هر کلاینت کوبرنتیز که گواهی کلاینت معتبری ارائه کند که توسط مرجع صدور گواهی (CA) اعتماد کلاینت (client trust) کلاستر امضا شده باشد، احراز هویت‌شده در نظر گرفته می‌شود. در این پیکربندی، کوبرنتیز نام کاربری را از فیلد commonName در subject گواهی تعیین می‌کند (برای مثال، commonName=bob نمایانگر کاربری با نام کاربری "bob" است). از آنجا به بعد، سازوکارهای مجوزدهی کوبرنتیز مشخص می‌کنند که آیا کاربر مجاز است عملیات خاصی را روی یک منبع انجام دهد یا خیر.

احراز هویت با گواهی کلاینت با ارسال گزینهٔ --client-ca-file=<SOMEFILE> به API server فعال می‌شود. این گزینه مرجع صدور گواهی اعتماد کلاینت کلاستر را پیکربندی می‌کند. فایل مورد اشاره باید شامل یک یا چند مرجع صدور گواهی باشد که API server هنگام نیاز به اعتبارسنجی گواهی‌های کلاینت می‌تواند از آن‌ها استفاده کند. اگر گواهی کلاینت ارائه و تأیید شود، common name موجود در subject به‌عنوان نام کاربری درخواست استفاده می‌شود. گواهی‌های کلاینت همچنین می‌توانند عضویت‌های گروهی کاربر را با استفاده از فیلدهای organization گواهی مشخص کنند. برای درج چند عضویت گروهی برای یک کاربر، چند فیلد organization را در گواهی قرار دهید.

برای آگاهی از نحوهٔ تولید گواهی کلاینت، به مدیریت گواهی‌ها مراجعه کنید، یا مثال کوتاهی را که در ادامهٔ همین صفحه آمده است مطالعه کنید.

گواهی‌های کلاینت سازگار با کوبرنتیز {#x509-client-certificates-k8s}

می‌توانید گواهی معتبری را که توسط یک CA در زنجیرهٔ اعتمادی صادر شده که API server برای گواهی‌های کلاینت می‌پذیرد، ارائه کنید و از آن برای احراز هویت در کوبرنتیز استفاده کنید. گواهی باید معتبر باشد؛ API server این موضوع را بر اساس ویژگی‌های notBefore و notAfter استاندارد X.509 بررسی می‌کند، و گواهی باید دارای extended key usage باشد که شامل احراز هویت کلاینت (ClientAuth) است.

توجه:

کوبرنتیز 1.37 از ابطال (revocation) گواهی پشتیبانی نمی‌کند. هر گواهی صادرشده تا زمان انقضا معتبر باقی می‌ماند.

نگاشت نام کاربری {#x509-client-certificates-k8s-username}

کوبرنتیز انتظار دارد گواهی کلاینت دارای ویژگی commonName (با OID برابر 2.5.4.3) باشد که به‌عنوان نام کاربری سوژه استفاده می‌شود.

نگاشت شناسهٔ کاربر (User ID) {#user-id-mapping}
وضعیت ویژگی: Kubernetes [] ()

برای استفاده از این قابلیت، گواهی باید ویژگی 1.3.6.1.4.1.57683.2 را داشته باشد، و feature gate با نام AllowParsingUserUIDFromCertAuth باید فعال باشد (به‌طور پیش‌فرض فعال است).

کوبرنتیز می‌تواند یک UID اختیاری کاربر را از گواهی استخراج کند. UID با نام کاربری متفاوت است؛ مقداری مبهم (opaque) است که معنای آن را فردی که گواهی را درخواست کرده است، یا در غیر این صورت کسی که قواعد تأیید گواهی را تنظیم کرده است، تعیین می‌کند.

برای مثال، UID ممکن است در یک کلاستر 1042 (یک عدد صحیح ساده) باشد، اما گواهی دیگری ممکن است d3f77937-ec82-4f16-8010-61821abe315a (یک UUID) را به‌عنوان UID به کار ببرد.

در اینجا مثالی برای توضیح این موضوع آمده است. اگر گواهی‌ای دارید که common name آن روی "Ada Lovelace" تنظیم شده و گواهی همچنین دارای ویژگی uid (با OID برابر 0.9.2342.19200300.100.1.1) با مقدار "aaking1815" است، کوبرنتیز نام کاربری کلاینت را "Ada Lovelace" در نظر می‌گیرد؛ کوبرنتیز ویژگی uid را نادیده می‌گیرد، زیرا OID اختصاصی CNCF که کوبرنتیز به دنبال آن است نیست. اگر می‌خواهید aaking1815 به‌عنوان UID توسط کوبرنتیز شناسایی شود، باید به‌عنوان مقدار ویژگی OID با شمارهٔ 1.3.6.1.4.1.57683.2 در subject گواهی تنظیم شود.

نگاشت گروه {#x509-client-certificates-k8s-group}

می‌توانید با گنجاندن ایستای اطلاعات گروه در گواهی، یک کاربر را به گروه‌ها نگاشت کنید. برای هر گروهی که کاربر عضو آن است، نام گروه را به‌عنوان یک organization (با OID برابر 2.5.6.4) در subject گواهی خود اضافه کنید. برای درج چند عضویت گروهی برای یک کاربر، چند organization را در subject گواهی قرار دهید (ترتیب اهمیتی ندارد). برای کاربر نمونه، distinguished name یک گواهی ممکن است CN=Ada Lovelace,O=Users,O=Staff,O=Programmers باشد که او را در گروه‌های "Programmers"، "Staff"، "system:authenticated" و "Users" قرار می‌دهد.

قرار دادن اطلاعات گروه در گواهی اختیاری است؛ اگر هیچ گروهی در گواهی مشخص نکنید، کاربر فقط عضو "system:authenticated" خواهد بود.

گواهی‌های کلاینت نود {#x509-client-certificates-nodes}

کوبرنتیز می‌تواند همین رویکرد را برای هویت نود به کار ببرد؛ نودها کلاینت‌های API server کوبرنتیز هستند که یک kubelet را اجرا می‌کنند (همچنین، هرچند در اینجا اهمیت کمتری دارد، API server معمولاً کلاینت هر نود نیز هست). برای مثال: نودی با نام "server-1a-antarctica42" و نام دامنهٔ "server-1a-antarctica42.cluster.example" می‌تواند از گواهی‌ای استفاده کند که برای "CN=system:node:server-1a-antarctica/42,O=system:nodes" صادر شده است. در این صورت نام کاربری نود "system:node:server-1a-antarctica/g42" است و نود عضو "system:authenticated" و "system:nodes" خواهد بود.

kubelet از گواهی و کلید خصوصی نود برای احراز هویت در API server کلاستر استفاده می‌کند.

توجه:

هویت‌های ماشینی نودها با ServiceAccountها یکسان نیستند.

مثال {#x509-client-certificates-example}

می‌توانید از ابزار خط فرمان openssl برای تولید یک درخواست امضای گواهی (certificate signing request) استفاده کنید:

# This example assumes that you already have a private key alovelace.pem
openssl req -new -key alovelace.pem -out alovelace-csr.pem -subj "/CN=alovelace/O=app1/O=app2"

این دستور یک درخواست امضا برای نام کاربری "alovelace" ایجاد می‌کند که به دو گروه "app1" و "app2" تعلق دارد. سپس می‌توانید این درخواست امضا را توسط مرجع صدور گواهی اعتماد کلاینت کلاستر خود امضا کنید تا گواهی‌ای به دست آورید که بتوانید برای احراز هویت کلاینت در کلاستر خود استفاده کنید.

توکن‌های Bootstrap {#bootstrap-tokens}

وضعیت ویژگی: Kubernetes v1.18 [stable] (پایدار)

برای تسهیل راه‌اندازی اولیهٔ کلاسترهای جدید، کوبرنتیز نوعی توکن Bearer با مدیریت پویا به نام Bootstrap Token دارد. این توکن‌ها به‌صورت Secret در فضای نام kube-system ذخیره می‌شوند و در آنجا می‌توان آن‌ها را به‌صورت پویا مدیریت و ایجاد کرد. Controller Manager شامل یک کنترل‌کنندهٔ TokenCleaner است که توکن‌های bootstrap را هنگام انقضا حذف می‌کند.

توکن‌ها به شکل [a-z0-9]{6}.[a-z0-9]{16} هستند. مؤلفهٔ اول شناسهٔ توکن (Token ID) و مؤلفهٔ دوم رمز توکن (Token Secret) است. توکن را به‌صورت زیر در یک هدر HTTP مشخص می‌کنید:

Authorization: Bearer 781292.db7bc3a58fc5f07e

باید احراز هویت‌کنندهٔ Bootstrap Token را با پرچم --enable-bootstrap-token-auth روی API Server فعال کنید. همچنین باید کنترل‌کنندهٔ TokenCleaner را از طریق آرگومان خط فرمان --controllers برای kube-controller-manager فعال کنید. این کار با چیزی شبیه --controllers=*,tokencleaner انجام می‌شود. اگر از ابزار kubeadm برای راه‌اندازی اولیهٔ کلاستر استفاده می‌کنید، این ابزار این کار را برای شما انجام می‌دهد.

این احراز هویت‌کننده با هویت system:bootstrap:<Token ID> احراز هویت می‌کند. این هویت در گروه system:bootstrappers قرار می‌گیرد. نام‌گذاری و گروه‌ها عمداً محدود شده‌اند تا کاربران را از استفاده از این توکن‌ها پس از مرحلهٔ راه‌اندازی اولیه منصرف کنند. از نام‌های کاربری و گروه می‌توان (و kubeadm نیز استفاده می‌کند) برای تدوین سیاست‌های مجوزدهی مناسب جهت پشتیبانی از راه‌اندازی اولیهٔ یک کلاستر بهره برد.

لطفاً برای مستندات تفصیلی دربارهٔ احراز هویت‌کنندهٔ Bootstrap Token و کنترل‌کننده‌ها، و همچنین نحوهٔ مدیریت این توکن‌ها با kubeadm، به Bootstrap Tokens مراجعه کنید.

قرار دادن bearer token در درخواست {#putting-a-bearer-token-in-a-request}

هنگام استفاده از احراز هویت با bearer token از یک کلاینت HTTP، API server انتظار دارد هدر Authorization با مقدار Bearer <token> وجود داشته باشد. bearer token باید دنباله‌ای از کاراکترها باشد که بتوان آن را تنها با استفاده از امکانات کدگذاری و نقل‌قول (quoting) خود HTTP در مقدار یک هدر HTTP قرار داد. برای مثال: اگر bearer token برابر 31ada4fd-adec-460c-809a-9e56ceb75269 باشد، در هدر HTTP به‌صورت زیر ظاهر می‌شود.

Authorization: Bearer 31ada4fd-adec-460c-809a-9e56ceb75269

توکن‌های حساب سرویس {#service-account-tokens}

حساب سرویس (service account) یک احراز هویت‌کنندهٔ خودکار فعال است که از bearer tokenهای امضاشده برای تأیید درخواست‌ها استفاده می‌کند. این افزونه دو پرچم اختیاری می‌پذیرد:

  • --service-account-key-file فایلی حاوی کلیدهای خصوصی یا عمومی x509 RSA یا ECDSA با کدگذاری PEM که برای تأیید توکن‌های ServiceAccount استفاده می‌شود. فایل مشخص‌شده می‌تواند شامل چندین کلید باشد و پرچم را می‌توان چندین بار با فایل‌های مختلف مشخص کرد. اگر مشخص نشود، از --tls-private-key-file استفاده می‌شود.
  • --service-account-lookup اگر فعال باشد، توکن‌هایی که از API حذف می‌شوند باطل (revoke) خواهند شد.

ServiceAccountها معمولاً به‌صورت خودکار توسط API server ایجاد می‌شوند و از طریق ServiceAccount Admission Controller با پادهای در حال اجرا در کلاستر مرتبط می‌شوند. Bearer tokenها در مکان‌های شناخته‌شده‌ای در پادها mount می‌شوند و به کلاینت‌های درون کلاستر اجازه می‌دهند در API server احراز هویت شوند. ServiceAccountها را می‌توان با استفاده از فیلد serviceAccountName در spec یک Pod به‌صورت صریح با Podها مرتبط کرد.

توجه:

serviceAccountName معمولاً حذف می‌شود، زیرا این کار به‌صورت خودکار انجام می‌شود.

در اینجا مانیفست (جزئی) یک Deployment آمده است که با ServiceAccount به نام bob-the-bot اجرا می‌شود:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
  namespace: default
spec:
  replicas: 3
  template:
    metadata:
    # ...
    spec:
      serviceAccountName: bob-the-bot
      containers:
      - name: nginx
        image: nginx:1.14.2

bearer tokenهای حساب سرویس برای استفاده در خارج از کلاستر کاملاً معتبرند و می‌توان از آن‌ها برای ایجاد هویت برای کارهای (job) بلندمدتی استفاده کرد که می‌خواهند با API کوبرنتیز ارتباط برقرار کنند. برای ایجاد دستی یک حساب سرویس، از دستور kubectl create serviceaccount (NAME) استفاده کنید. این دستور یک حساب سرویس در فضای نام جاری ایجاد می‌کند.

kubectl create serviceaccount jenkins

serviceaccount/jenkins created

می‌توانید یک توکن مرتبط را به‌صورت دستی ایجاد کنید:

kubectl create token jenkins

توکن ایجادشده یک JSON Web Token (JWT) امضاشده است.

JWT امضاشده را می‌توان به‌عنوان bearer token برای احراز هویت با حساب سرویس مورد نظر استفاده کرد. برای اطلاع از نحوهٔ گنجاندن توکن در یک درخواست، بالا را ببینید. معمولاً این توکن‌ها برای دسترسی درون کلاستر به API server در پادها mount می‌شوند، اما از خارج از کلاستر نیز قابل استفاده‌اند.

حساب‌های سرویس با نام کاربری system:serviceaccount:(NAMESPACE):(SERVICEACCOUNT) احراز هویت می‌شوند و به گروه‌های system:serviceaccounts و system:serviceaccounts:(NAMESPACE) اختصاص می‌یابند.

هشدار:

از آنجا که توکن‌های حساب سرویس را می‌توان در آبجکت‌های API از نوع Secret نیز ذخیره کرد، هر کاربری که دسترسی نوشتن به Secretها دارد می‌تواند یک توکن درخواست کند، و هر کاربری که دسترسی خواندن به آن Secretها دارد می‌تواند به‌عنوان آن حساب سرویس احراز هویت شود. در اعطای مجوزها به حساب‌های سرویس و قابلیت‌های خواندن یا نوشتن برای Secretها احتیاط کنید.

یکپارچه‌سازی‌های خارجی {#external-integrations}

کوبرنتیز به‌صورت بومی از JWT و OpenID Connect (OIDC) پشتیبانی می‌کند؛ بخش احراز هویت با JSON Web Token را ببینید.

یکپارچه‌سازی با سایر پروتکل‌های احراز هویت (برای مثال: LDAP، SAML، Kerberos و طرح‌های جایگزین X.509) را می‌توان با استفاده از یک پراکسی احراز هویت یا با یکپارچه‌سازی با یک وب‌هوک احراز هویت انجام داد.

همچنین می‌توانید از هر روش سفارشی دیگری که گواهی‌های X.509 کلاینت را برای کلاینت‌ها صادر می‌کند استفاده کنید، مشروط بر اینکه API server به گواهی‌های معتبر اعتماد کند. برای آگاهی از نحوه ایجاد یک گواهی، بخش گواهی‌های X.509 کلاینت را مطالعه کنید.

اگر برای کلاینت‌ها گواهی صادر می‌کنید، این بر عهده شماست (به‌عنوان مدیر پلتفرم ابری) که اطمینان حاصل کنید دوره اعتبار گواهی و سایر تصمیم‌های طراحی‌ای که اتخاذ می‌کنید، سطح امنیتی مناسبی را فراهم می‌کنند.

احراز هویت با JSON Web Token

می‌توانید کوبرنتیز را به‌گونه‌ای پیکربندی کنید که کاربران را با استفاده از توکن‌های سازگار با JSON Web Token (JWT) احراز هویت کند. سازوکار احراز هویت JWT برای توکن‌های ServiceAccount که خود کوبرنتیز صادر می‌کند به کار می‌رود، و همچنین می‌توانید از آن برای یکپارچه‌سازی با سایر منابع هویت استفاده کنید.

احراز هویت‌کننده تلاش می‌کند یک ID token خام را تجزیه کند و بررسی کند که توسط صادرکننده (issuer) پیکربندی‌شده امضا شده باشد. برای توکن‌هایی که به‌صورت خارجی صادر شده‌اند، کلید عمومی لازم برای تأیید امضا با استفاده از OIDC discovery از نقطه پایانی عمومی صادرکننده کشف می‌شود.

حداقل payload معتبر JWT باید شامل claimهای زیر باشد:

{
  "iss": "https://example.com",   // must match the issuer.url
  "aud": ["my-app"],              // at least one of the entries in issuer.audiences must match the "aud" claim in presented JWTs.
  "exp": 1234567890,              // token expiration as Unix time (the number of seconds elapsed since January 1, 1970 UTC)
  "<username-claim>": "user"      // this is the username claim configured in the claimMappings.username.claim or claimMappings.username.expression
}

توکن‌های OpenID Connect

OpenID Connect گونه‌ای از OAuth2 است که برخی ارائه‌دهندگان OAuth2، از جمله Microsoft Entra ID، Salesforce و Google، از آن پشتیبانی می‌کنند. افزونه اصلی این پروتکل نسبت به OAuth2، فیلد اضافه‌ای است که همراه با access token بازگردانده می‌شود و ID Token نام دارد. این توکن یک JSON Web Token (JWT) با فیلدهای شناخته‌شده، مانند ایمیل کاربر، است که توسط سرور امضا شده است.

برای شناسایی کاربر، احراز هویت‌کننده از id_token (و نه access_token) موجود در پاسخ توکن OAuth2 به‌عنوان bearer token استفاده می‌کند. برای اطلاع از نحوه قرار دادن توکن در درخواست، بالا را ببینید.

  1. وارد ارائه‌دهنده هویت (identity provider) خود شوید.

  2. ارائه‌دهنده هویت شما یک access_token، یک id_token و یک refresh_token در اختیارتان قرار می‌دهد.

  3. هنگام استفاده از kubectl، id_token خود را با آرگومان خط فرمان --token به کار ببرید یا آن را مستقیماً به kubeconfig خود اضافه کنید.

  4. kubectl توکن id_token شما را در هدری به نام Authorization به سرور API ارسال می‌کند.

  5. سرور API بررسی می‌کند که امضای JWT معتبر باشد.

  6. بررسی کنید که id_token منقضی نشده باشد.

    اگر عبارات CEL در AuthenticationConfiguration پیکربندی شده باشند، اعتبارسنجی claim و/یا کاربر انجام می‌شود.

  7. اطمینان حاصل می‌شود که کاربر مجاز است.

  8. پس از تأیید مجوز، سرور API پاسخی را به kubectl بازمی‌گرداند.

  9. kubectl بازخورد را به کاربر ارائه می‌دهد.

از آنجا که تمام داده‌های لازم برای اعتبارسنجی هویت شما در id_token وجود دارد، کوبرنتیز نیازی ندارد برای این منظور با ارائه‌دهنده هویت تماس بگیرد («phone home»). در مدلی که هر درخواست بدون حالت (stateless) است، این رویکرد راه‌حلی بسیار مقیاس‌پذیر برای احراز هویت فراهم می‌کند. با این حال چند چالش نیز دارد:

  1. کوبرنتیز هیچ «رابط وب» برای آغاز فرایند احراز هویت ندارد. مرورگر یا رابطی برای دریافت اعتبارنامه‌ها وجود ندارد؛ به همین دلیل ابتدا باید نزد ارائه‌دهنده هویت خود احراز هویت شوید.
  2. id_token را نمی‌توان باطل (revoke) کرد. این توکن مانند یک گواهی است، بنابراین باید کوتاه‌مدت باشد (فقط چند دقیقه)؛ در نتیجه دریافت مکرر توکن جدید در هر چند دقیقه می‌تواند بسیار آزاردهنده باشد.
  3. برای احراز هویت در داشبورد کوبرنتیز، باید از دستور kubectl proxy یا یک reverse proxy استفاده کنید که id_token را تزریق می‌کند.

استفاده از آرگومان‌های خط فرمان

برای فعال‌سازی این افزونه، آرگومان‌های خط فرمان زیر را برای سرور API پیکربندی کنید:

پارامتر توضیحات مثال الزامی
--oidc-issuer-url نشانی ارائه‌دهنده‌ای که به سرور API امکان می‌دهد کلیدهای عمومی امضا را کشف کند. فقط نشانی‌هایی که از طرح https:// استفاده می‌کنند پذیرفته می‌شوند. این مقدار معمولاً نشانی discovery ارائه‌دهنده است که مسیر آن خالی شده است. اگر نشانی OIDC discovery صادرکننده https://accounts.provider.example/.well-known/openid-configuration باشد، مقدار باید https://accounts.provider.example باشد بله
--oidc-client-id شناسه کلاینتی که همه توکن‌ها باید برای آن صادر شده باشند. kubernetes بله
--oidc-username-claim claim در JWT که به‌عنوان نام کاربری استفاده می‌شود. به‌طور پیش‌فرض sub است که انتظار می‌رود شناسه یکتای کاربر نهایی باشد. مدیران می‌توانند بسته به ارائه‌دهنده خود claimهای دیگری مانند email یا name را انتخاب کنند. با این حال، برای جلوگیری از تداخل نام با افزونه‌های دیگر، به claimهایی غیر از email پیشوند نشانی صادرکننده افزوده می‌شود. sub خیر
--oidc-username-prefix پیشوندی که به claimهای نام کاربری افزوده می‌شود تا از تداخل با نام‌های موجود (مانند کاربران system:) جلوگیری شود. برای مثال، مقدار oidc: نام‌های کاربری‌ای مانند oidc:jane.doe ایجاد می‌کند. اگر این آرگومان ارائه نشود و --oidc-username-claim مقداری غیر از email داشته باشد، پیشوند به‌طور پیش‌فرض ( Issuer URL )# خواهد بود که در آن ( Issuer URL ) مقدار --oidc-issuer-url است. با مقدار - می‌توان افزودن هرگونه پیشوند را غیرفعال کرد. oidc: خیر
--oidc-groups-claim claim در JWT که به‌عنوان گروه کاربر استفاده می‌شود. اگر این claim وجود داشته باشد، باید آرایه‌ای از رشته‌ها باشد. groups خیر
--oidc-groups-prefix پیشوندی که به claimهای گروه افزوده می‌شود تا از تداخل با نام‌های موجود (مانند گروه‌های system:) جلوگیری شود. برای مثال، مقدار oidc: نام‌های گروهی مانند oidc:engineering و oidc:infra ایجاد می‌کند. oidc: خیر
--oidc-required-claim یک جفت key=value که claim الزامی در ID Token را توصیف می‌کند. در صورت تنظیم، بررسی می‌شود که این claim با مقدار مطابق در ID Token وجود داشته باشد. برای مشخص کردن چند claim، این آرگومان را تکرار کنید. claim=value خیر
--oidc-ca-file مسیر گواهی مرجع صدور گواهی (CA) که گواهی وب ارائه‌دهنده هویت شما را امضا کرده است. به‌طور پیش‌فرض از CAهای ریشه میزبان استفاده می‌شود. /etc/kubernetes/ssl/kc-ca.pem خیر
--oidc-signing-algs الگوریتم‌های امضای پذیرفته‌شده. مقدار پیش‌فرض RS256 است. مقادیر مجاز عبارت‌اند از: RS256، RS384، RS512، ES256، ES384، ES512، PS256، PS384، PS512. این مقادیر در RFC 7518 به نشانی https://tools.ietf.org/html/rfc7518#section-3.1 تعریف شده‌اند. RS512 خیر
پیکربندی احراز هویت از طریق فایل {#using-authentication-configuration}

رویکرد فایل پیکربندی به شما امکان می‌دهد چندین احراز هویت‌کننده JWT پیکربندی کنید که هر کدام issuer.url و issuer.discoveryURL یکتای خود را دارند. فایل پیکربندی حتی اجازه می‌دهد عبارات CEL را برای نگاشت claimها به ویژگی‌های کاربر و برای اعتبارسنجی claimها و اطلاعات کاربر مشخص کنید. سرور API همچنین هنگام تغییر فایل پیکربندی، احراز هویت‌کننده‌ها را به‌طور خودکار بارگذاری مجدد می‌کند. می‌توانید از معیار (metric) با نام apiserver_authentication_config_controller_automatic_reload_last_timestamp_seconds برای پایش آخرین زمانی که پیکربندی توسط سرور API بارگذاری مجدد شده است استفاده کنید.

باید مسیر پیکربندی احراز هویت را با آرگومان خط فرمان --authentication-config برای سرور API مشخص کنید. اگر می‌خواهید به‌جای فایل پیکربندی از آرگومان‌های خط فرمان استفاده کنید، آن‌ها همچنان بدون تغییر کار خواهند کرد. برای دسترسی به قابلیت‌های جدید، مانند پیکربندی چندین احراز هویت‌کننده یا تنظیم چندین audience برای یک صادرکننده، باید به استفاده از فایل پیکربندی روی بیاورید.

برای استفاده از احراز هویت ساختاریافته، آرگومان خط فرمان --authentication-config را برای kube-apiserver مشخص کنید. نمونه‌ای از فایل پیکربندی احراز هویت ساختاریافته در ادامه نشان داده شده است.

توجه:

اگر --authentication-config را همراه با هر یک از آرگومان‌های خط فرمان --oidc-* مشخص کنید، این یک پیکربندی نادرست است. در این حالت، سرور API خطا گزارش می‌کند و بلافاصله خارج می‌شود. اگر می‌خواهید به استفاده از پیکربندی احراز هویت ساختاریافته روی بیاورید، باید آرگومان‌های خط فرمان --oidc-* را حذف کنید و به‌جای آن‌ها از فایل پیکربندی استفاده کنید.

    jwt.claimValidationRules[i].expression عبارتی را نشان می‌دهد که توسط CEL ارزیابی می‌شود. عبارات CEL به محتوای payload توکن دسترسی دارند که در متغیر CEL با نام claims سازمان‌دهی شده است. claims نگاشتی (map) از نام claimها (به‌صورت رشته) به مقادیر claimها (از هر نوع) است.

  • عبارت قانون اعتبارسنجی کاربر

    jwt.userValidationRules[i].expression عبارتی را نشان می‌دهد که توسط CEL ارزیابی می‌شود. عبارات CEL به محتوای userInfo دسترسی دارند که در متغیر CEL با نام user سازمان‌دهی شده است. برای آگاهی از schema مربوط به user، مستندات API با عنوان UserInfo را ببینید.

  • عبارت نگاشت claim

    jwt.claimMappings.username.expression، jwt.claimMappings.groups.expression، jwt.claimMappings.uid.expression و jwt.claimMappings.extra[i].valueExpression عبارتی را نشان می‌دهند که توسط CEL ارزیابی می‌شود. عبارات CEL به محتوای payload توکن دسترسی دارند که در متغیر CEL با نام claims سازمان‌دهی شده است. claims نگاشتی (map) از نام claimها (به‌صورت رشته) به مقادیر claimها (از هر نوع) است.

محدودیت‌ها {#oidc-limitations}
  1. Distributed claimها از طریق عبارت‌های CEL کار نمی‌کنند.

کوبرنتیز یک ارائه‌دهنده هویت (Identity Provider) مبتنی بر OpenID Connect ارائه نمی‌کند. می‌توانید از یک ارائه‌دهنده هویت عمومی OpenID Connect موجود استفاده کنید یا ارائه‌دهنده هویت خودتان را که پروتکل OpenID Connect را پشتیبانی می‌کند اجرا کنید.

برای اینکه یک ارائه‌دهنده هویت با کوبرنتیز کار کند، باید:

  1. از OpenID connect discovery پشتیبانی کند.

    کلید عمومی برای تأیید امضا، با استفاده از OIDC discovery از نقطه پایانی عمومی issuer کشف می‌شود. اگر از فایل پیکربندی احراز هویت استفاده می‌کنید، ارائه‌دهنده هویت نیازی ندارد نقطه پایانی discovery را به‌صورت عمومی در دسترس قرار دهد. می‌توانید نقطه پایانی discovery را در مکانی متفاوت از issuer (مثلاً به‌صورت محلی در داخل کلاستر) میزبانی کنید و issuer.discoveryURL را در فایل پیکربندی مشخص نمایید.

  2. با TLS و با رمزنگارهای (cipher) منسوخ‌نشده اجرا شود.

  3. گواهی امضاشده توسط یک CA داشته باشد (حتی اگر CA یک CA تجاری نباشد یا خودامضا باشد).

توضیحی درباره الزام شماره ۳ بالا، یعنی لزوم داشتن گواهی امضاشده توسط CA: اگر ارائه‌دهنده هویت خودتان را مستقر می‌کنید، باید گواهی وب‌سرور ارائه‌دهنده هویت شما توسط گواهی‌ای امضا شده باشد که پرچم CA در آن روی TRUE تنظیم شده است، حتی اگر خودامضا باشد. دلیل این امر آن است که پیاده‌سازی کلاینت TLS در GoLang در رعایت استانداردهای مربوط به اعتبارسنجی گواهی بسیار سخت‌گیر است. اگر CA در دسترس ندارید، می‌توانید با استفاده از ابزارهای استاندارد تولید گواهی، یک CA ساده و یک جفت گواهی و کلید امضاشده ایجاد کنید.

احراز هویت با توکن Webhook

احراز هویت webhook در کوبرنتیز سازوکاری است که با ارسال یک فراخوانی HTTP، توکن‌های bearer را اعتبارسنجی می‌کند.

در ارتباط با نحوهٔ پیکربندی API server، گزینه‌های زیر وجود دارند:

  • --authentication-token-webhook-config-file: یک فایل پیکربندی که چگونگی دسترسی به سرویس webhook راه دور را توصیف می‌کند.
  • --authentication-token-webhook-cache-ttl: مدت زمانی که تصمیم‌های احراز هویت در حافظهٔ نهان نگهداری می‌شوند. مقدار پیش‌فرض دو دقیقه است.
  • --authentication-token-webhook-version: مشخص می‌کند که برای ارسال و دریافت اطلاعات از webhook، از آبجکت‌های TokenReview با نسخهٔ authentication.k8s.io/v1beta1 استفاده شود یا authentication.k8s.io/v1. مقدار پیش‌فرض v1beta1 است.

فایل پیکربندی از قالب فایل kubeconfig استفاده می‌کند. در این فایل، clusters به سرویس راه دور و users به webhook مربوط به API server اشاره می‌کند. یک نمونه به شکل زیر است:

# Kubernetes API version
apiVersion: v1
# kind of the API object
kind: Config
# clusters refers to the remote service.
clusters:
  - name: name-of-remote-authn-service
    cluster:
      certificate-authority: /path/to/ca.pem         # CA for verifying the remote service.
      server: https://authn.example.com/authenticate # URL of remote service to query. 'https' recommended for production.

# users refers to the API server's webhook configuration.
users:
  - name: name-of-api-server
    user:
      client-certificate: /path/to/cert.pem # cert for the webhook plugin to use
      client-key: /path/to/key.pem          # key matching the cert

# kubeconfig files require a context. Provide one for the API server.
current-context: webhook
contexts:
- context:
    cluster: name-of-remote-authn-service
    user: name-of-api-server
  name: webhook

پروکسی معکوس احراز هویت‌کننده {#authenticating-proxy}

هشدار:

اگر مرجع صدور گواهی (CA) دارید که در زمینه‌ای دیگر نیز استفاده می‌شود، به آن مرجع صدور گواهی برای شناسایی کلاینت‌های پروکسی احراز هویت‌کننده اعتماد نکنید، مگر آنکه خطرات آن و سازوکارهای محافظت از استفادهٔ آن CA را درک کرده باشید.

API server را می‌توان به‌گونه‌ای پیکربندی کرد که کاربران را از روی مقادیر هدر درخواست، مانند X-Remote-User، شناسایی کند. این قابلیت برای استفاده همراه با یک پروکسی احراز هویت‌کننده طراحی شده است که این هدرها را تنظیم می‌کند.

استفاده از پروکسی معکوس احراز هویت‌کننده با جعل هویت کاربر متفاوت است. در جعل هویت کاربر، یک کاربر از API server می‌خواهد درخواست را طوری در نظر بگیرد که گویی توسط کاربری دیگر ارسال شده است. در پروکسی معکوس احراز هویت‌کننده، API server به کلاینت مستقیم خود اعتماد می‌کند که اطلاعات مربوط به هویت اصل (principal) ارسال‌کنندهٔ درخواست اولیه را ارائه دهد.

برای آشنایی با پیکربندی این قابلیت از طریق آرگومان‌های خط فرمان، به پیکربندی هدرهای درخواست وب مراجعه کنید.

نمونه {#authenticating-proxy-example}

برای مثال، با این پیکربندی:

--requestheader-username-headers=X-Remote-User
--requestheader-group-headers=X-Remote-Group
--requestheader-extra-headers-prefix=X-Remote-Extra-

این درخواست:

GET / HTTP/1.1
X-Remote-User: fido
X-Remote-Group: dogs
X-Remote-Group: dachshunds
X-Remote-Extra-Acme.com%2Fproject: some-project
X-Remote-Extra-Scopes: openid
X-Remote-Extra-Scopes: profile

منجر به این اطلاعات کاربر می‌شود:

name: fido
groups:
- dogs
- dachshunds
extra:
  acme.com/project:
  - some-project
  scopes:
  - openid
  - profile

گواهی کلاینت {#reverse-proxy-client-certificate}

برای جلوگیری از جعل هدر، پروکسی احراز هویت‌کننده ملزم است پیش از بررسی هدرهای درخواست، یک گواهی کلاینت معتبر را به API server ارائه دهد تا در برابر CA مشخص‌شده اعتبارسنجی شود.

برای حالت احراز هویت مبتنی بر هدر درخواست، به مرجع گزینهٔ خط فرمان مراجعه کنید.

از CA‌ای که در زمینه‌ای دیگر استفاده می‌شود دوباره استفاده نکنید، مگر آنکه خطرات آن و سازوکارهای محافظت از استفادهٔ آن CA را درک کرده باشید.

یکپارچه‌سازی فایل توکن ایستا {#static-token-file}

هنگامی که گزینهٔ --token-auth-file=<SOMEFILE> در خط فرمان داده شود، API server توکن‌های bearer ایستا را از یک فایل می‌خواند. در کوبرنتیز 1.37، توکن‌ها به‌طور نامحدود معتبر می‌مانند و فهرست توکن‌ها بدون راه‌اندازی مجدد API server قابل تغییر نیست.

فایل توکن یک فایل CSV با حداقل ۳ ستون است: توکن، نام کاربر، شناسهٔ یکتای کاربر (uid)، و پس از آن فهرستی اختیاری از نام گروه‌ها که با ویرگول از هم جدا شده‌اند.

توجه:

اگر بیش از یک گروه دارید، ستون باید داخل دابل‌کوتیشن قرار گیرد، مانند:

token,user,uid,"group1,group2,group3"

استفاده از فایل توکن ایستا برای توکن‌هایی مناسب است که ماهیتاً بلندمدت و ایستا هستند و شاید هرگز چرخانده (rotate) نشوند. همچنین زمانی مفید است که کلاینت به یک API server مشخص در control plane محلی باشد، مانند یک عامل پایش (monitoring agent).

اگر در زمان آماده‌سازی کلاستر از این روش استفاده می‌کنید و سپس به روش احراز هویت دیگری که برای بلندمدت استفاده خواهد شد منتقل می‌شوید، باید توکنی را که برای راه‌اندازی اولیه (bootstrap) به کار رفته غیرفعال کنید (این کار نیازمند راه‌اندازی مجدد هر API server است).

در شرایط دیگر، و به‌ویژه جایی که چرخش بسیار سریع توکن اهمیت دارد، پروژهٔ کوبرنتیز استفاده از احراز هویت‌کنندهٔ توکن webhook را به‌جای این سازوکار توصیه می‌کند.

جعل هویت کاربر {#user-impersonation}

جعل هویت کاربر روشی فراهم می‌کند که در آن یک کاربر می‌تواند از طریق هدرهای جعل هویت (impersonation) به‌عنوان کاربری دیگر عمل کند.

پیکربندی احراز هویت {#api-server-authn-config}

می‌توانید احراز هویت کوبرنتیز را یا با استفاده از آرگومان‌های خط فرمان یا با استفاده از یک فایل پیکربندی پیکربندی کنید.

معمولاً از ترکیبی از این رویکردها استفاده می‌شود.

پیکربندی از طریق آرگومان‌های خط فرمان {#api-server-authn-config-cli}

می‌توانید از آرگومان‌های خط فرمان زیر برای پیکربندی نحوهٔ احراز هویت کلاینت‌ها توسط control plane کلاستر خود استفاده کنید.

مرجع خط فرمان مربوط به API server تمام آرگومان‌های خط فرمان مرتبط را با جزئیات بیشتری شرح می‌دهد.

پیکربندی احراز هویت ناشناس {#api-server-authn-config-cli-anonymous}

--anonymous-auth
مشخص می‌کند که آیا کلاینت‌هایی که احراز هویت نشده‌اند می‌توانند از طریق درگاه امن API server درخواست ارسال کنند یا خیر. درخواست‌های ناشناس دارای نام کاربری system:anonymous و نام گروه system:unauthenticated هستند. همچنین درخواست‌های ناشناس را ببینید.

پیکربندی توکن Bootstrap {#api-server-authn-config-cli-bootstrap}

--enable-bootstrap-token-auth
هنگامی که این پرچم تنظیم شده باشد، می‌توانید از توکن‌های bootstrap برای احراز هویت استفاده کنید.

پیکربندی احراز هویت با گواهی {#api-server-authn-config-cli-x-509}

--client-ca-file
مسیر trust anchor(های) مورد استفاده برای اعتبارسنجی هویت کلاینت، زمانی که کلاینت‌ها از احراز هویت با گواهی X.509 استفاده می‌کنند.

پیکربندی OIDC {#api-server-authn-config-cli-oidc}

--oidc-ca-file
مسیر trust anchor(های) مورد استفاده برای اعتبارسنجی هویت کلاینت، زمانی که کلاینت‌ها از OIDC استفاده می‌کنند.
--oidc-client-id
شناسهٔ کلاینت (client ID) برای کلاینت OpenID Connect.
--oidc-username-claim
نام یک claim در JWT که برای تعیین نام کاربری استفاده می‌شود. نام claim پیش‌فرض sub است، زیرا این claim باید شناسهٔ یکتای کاربر نهایی باشد. می‌توانید claimهای دیگری مانند email یا name را انتخاب کنید. برای claimهایی غیر از sub یا email، kube-apiserver یک پیشوند به نام گروه اضافه می‌کند (تا از تداخل نام‌ها جلوگیری شود).
--oidc-username-prefix
پیشوندی که به ابتدای claimهای نام کاربری افزوده می‌شود تا از تداخل با نام‌های موجود (مانند کاربران system:) جلوگیری شود. برای مثال، مقدار oidc: نام‌های کاربری‌ای مانند oidc:jane.doe ایجاد می‌کند. اگر این آرگومان ارائه نشود و مقدار --oidc-username-claim چیزی غیر از email باشد، پیشوند به‌طور پیش‌فرض ( Issuer URL )# خواهد بود که در آن ( Issuer URL ) مقدار --oidc-issuer-url است. می‌توانید مقدار پیشوند را - تعیین کنید تا افزودن پیشوند به نام کاربری غیرفعال شود.
--oidc-groups-claim
نام یک claim سفارشی OpenID Connect برای تعیین گروه‌های کاربر. claim موجود در توکن باید آرایه‌ای از رشته‌ها باشد. مقدار پیش‌فرض ندارد.
--oidc-groups-prefix
پیشوندی که به ابتدای claimهای گروه افزوده می‌شود تا از تداخل با نام‌های موجود (مانند گروه‌های system:) جلوگیری شود. برای مثال، مقدار oidc: نام‌های گروهی مانند oidc:engineering و oidc:infra ایجاد می‌کند. پیشوند پیش‌فرض oidc: است.
--oidc-issuer-url
نشانی URL صادرکنندهٔ OpenID. طرح (scheme) این URL باید https باشد. اگر نشانی OIDC discovery مربوط به صادرکننده https://accounts.provider.example/.well-known/openid-configuration باشد، مقدار آن باید https://accounts.provider.example باشد.
--oidc-required-claim
claim‌ای که پیش از آنکه کوبرنتیز یک کلاینت را احراز هویت کند، باید در توکن وجود داشته باشد. قالب آن key=value است. می‌توانید این آرگومان را بیش از یک بار مشخص کنید.
--oidc-signing-algs
الگوریتم‌های امضای پذیرفته‌شده. مقادیر مجاز عبارت‌اند از: RS256، RS384، RS512، ES256، ES384، ES512، PS256، PS384، PS512. این مقادیر در RFC 7518 تعریف شده‌اند. مقدار پیش‌فرض RS512 است.

پیکربندی ServiceAccount {#api-server-authn-config-cli-sa}

--api-audiences
مخاطب (audience) احراز هویت را برای توکن‌های service account تعریف می‌کند.
--service-account-extend-token-expiration
این پرچم تمدید انقضای projected service account را هنگام تولید توکن فعال می‌کند، که به گذار ایمن از توکن‌های قدیمی (legacy) به قابلیت توکن‌های service account مقید (bound) کمک می‌کند. احراز هویت اعتبارنامه‌های service account را ببینید.
--service-account-issuer
شناسهٔ صادرکنندهٔ توکن service account. صادرکننده این شناسه را در claim با نام iss هر توکن صادرشده اعلام می‌کند. پروژهٔ کوبرنتیز توصیه می‌کند در اینجا از یک URL با طرح https استفاده شود.
--service-account-jwks-uri
URI مربوط به JSON Web Key Set را در سند discovery که در /.well-known/openid-configuration ارائه می‌شود، بازنویسی (override) می‌کند.
--service-account-key-file
مسیر فایلی که حاوی کلیدهای عمومی یا خصوصی X.509 با رمزگذاری PEM (از نوع RSA یا ECDSA) است و برای تأیید توکن‌های ServiceAccount استفاده می‌شود. فایل مشخص‌شده می‌تواند حاوی چند کلید باشد و می‌توانید این آرگومان را چندین بار با مسیرهای متفاوت مشخص کنید.
--service-account-lookup
اگر true باشد، API server به‌عنوان بخشی از احراز هویت بررسی می‌کند که توکن‌های ServiceAccount در etcd وجود دارند.
--service-account-max-token-expiration
بیشینهٔ مدت اعتبار یک توکن که توسط صادرکنندهٔ توکن service account ایجاد می‌شود، به‌صورت یک رشتهٔ مدت‌زمان (duration) کوبرنتیز.
--service-account-signing-endpoint
مسیر سوکتی که یک امضاکنندهٔ JWT خارجی روی آن گوش می‌دهد. می‌توانید از این گزینه برای یکپارچه‌سازی با یک امضاکنندهٔ توکن خارجی استفاده کنید.
--service-account-signing-key-file
مسیر فایلی که حاوی کلید خصوصی فعلی صادرکنندهٔ توکن service account است. تغییراتی که در این فایل هنگام اجرای API server اعمال شوند، دوباره خوانده نمی‌شوند.

پیکربندی توکن ایستا {#api-server-authn-config-cli-bearer}

--token-auth-file
مسیر فایل پیکربندی توکن‌های bearer ایستا. تغییراتی که در این فایل هنگام اجرای API server اعمال شوند، دوباره خوانده نمی‌شوند.

پیکربندی احراز هویت با Webhook {#api-server-authn-config-cli-webhook}

--authentication-token-webhook-cache-ttl
مدت‌زمانی (به‌صورت مشخصات duration کوبرنتیز) که API server باید نتیجهٔ فراخوانی‌های HTTP برای اعتبارسنجی توکن‌ها را در حافظهٔ نهان نگه دارد.
--authentication-token-webhook-config-file
مسیر یک پیکربندی کلاینت با قالب kubeconfig که مشخص می‌کند API server هنگام انجام فراخوانی‌های HTTP چگونه احراز هویت می‌کند. تغییراتی که در این فایل هنگام اجرای API server اعمال شوند، دوباره خوانده نمی‌شوند.
--authentication-token-webhook-version
نسخهٔ API مربوط به TokenReview که هنگام انجام فراخوانی‌های HTTP برای بررسی توکن‌ها استفاده می‌شود.

پیکربندی احراز هویت درخواست وب {#api-server-authn-config-cli-reverse-proxy}

احتیاط:

پیش از تعیین این آرگومان‌های خط فرمان، باید مستندات مربوط به پیکربندی پروکسی احراز هویت را مطالعه کنید، زیرا توصیه‌های امنیتی مهمی دربارهٔ امنیت اطلاعات وجود دارد که باید آن‌ها را رعایت کنید.

--requestheader-client-ca-file
الزامی. مسیر یک بستهٔ گواهی با رمزگذاری PEM که حاوی trust anchor(های) برای اعتبارسنجی هویت پروکسی احراز هویت است.
یک گواهی کلاینت معتبر باید ارائه شود و در برابر مراجع صدور گواهی موجود در فایل مشخص‌شده اعتبارسنجی گردد، پیش از آنکه هدرهای درخواست برای نام‌های کاربری بررسی شوند.
--requestheader-allowed-names
اختیاری. فهرستی از مقادیر Common Name (CN) که با کاما از هم جدا شده‌اند.
اگر تنظیم شود، پیش از بررسی هدرهای درخواست برای نام‌های کاربری، باید یک گواهی کلاینت معتبر با CN موجود در فهرست مشخص‌شده ارائه شود. اگر خالی باشد، هر CN مجاز است.
--requestheader-username-headers
الزامی؛ بدون حساسیت به بزرگی و کوچکی حروف. نام هدرهایی که برای هویت کاربر، به ترتیب بررسی می‌شوند.
نخستین هدری که حاوی مقدار باشد به‌عنوان نام کاربری استفاده می‌شود.
--requestheader-group-headers
اختیاری؛ بدون حساسیت به بزرگی و کوچکی حروف. نام هدرهایی که برای گروه‌های کاربر، به ترتیب بررسی می‌شوند.
X-Remote-Group پیشنهاد می‌شود. تمام مقادیر موجود در تمام هدرهای مشخص‌شده به‌عنوان نام گروه استفاده می‌شوند.
--requestheader-extra-headers-prefix
اختیاری؛ بدون حساسیت به بزرگی و کوچکی حروف. پیشوندهای هدری که برای تعیین اطلاعات اضافی دربارهٔ کاربر جست‌وجو می‌شوند.
X-Remote-Extra- پیشنهاد می‌شود. داده‌های اضافی معمولاً توسط افزونه(های) احراز مجوز پیکربندی‌شده استفاده می‌شوند. از هر هدری که با هر یک از پیشوندهای مشخص‌شده آغاز شود، پیشوند حذف می‌شود. باقی‌ماندهٔ نام هدر به حروف کوچک تبدیل می‌شود و رمزگشایی درصدی (percent-decode) می‌گردد و به کلید extra تبدیل می‌شود و مقدار هدر، مقدار extra خواهد بود.

پیکربندی از طریق فایل پیکربندی {#api-server-authn-config-file}

وضعیت ویژگی: Kubernetes [] ()

هنگامی که آرگومان خط فرمان --authentication-config را به kube-apiserver می‌دهید، API server فایلی را که در مسیر مشخص‌شده قرار دارد بارگذاری می‌کند و از محتوای آن فایل برای پیکربندی احراز هویت استفاده می‌کند.

محتوای آن فایل را می‌توان در حین اجرای API server تغییر داد و در این صورت، API server پس از آن فایل را دوباره می‌خواند.

توجه:

تغییرات این فایل باید به‌صورت اتمیک انجام شود (برای مثال: نوشتن در یک فایل موقت هم‌سطح، سپس تغییر نام فایل موقت برای جایگزینی این فایل).

افزونه‌های اعتبارنامهٔ client-go {#client-go-credential-plugins}

وضعیت ویژگی: Kubernetes v1.22 [stable] (پایدار)

k8s.io/client-go و ابزارهایی که از آن استفاده می‌کنند، مانند kubectl و kubelet، قادرند یک فرمان خارجی را اجرا کنند تا اعتبارنامه‌های کاربر را دریافت نمایند.

این قابلیت برای یکپارچه‌سازی‌های سمت کلاینت با پروتکل‌های احراز هویتی در نظر گرفته شده است که به‌صورت بومی توسط k8s.io/client-go پشتیبانی نمی‌شوند (مانند LDAP، Kerberos، OAuth2، SAML و غیره). افزونه منطق مختص پروتکل را پیاده‌سازی می‌کند و سپس اعتبارنامه‌های مبهم (opaque) را برای استفاده بازمی‌گرداند. تقریباً تمام موارد استفاده از افزونه‌های اعتبارنامه به یک مؤلفهٔ سمت سرور با پشتیبانی از webhook token authenticator نیاز دارند تا قالب اعتبارنامه‌ای را که افزونهٔ کلاینت تولید کرده است تفسیر کند.

توجه:

نسخه‌های قدیمی‌تر kubectl پشتیبانی داخلی برای احراز هویت در AKS و GKE را شامل می‌شدند، اما این پشتیبانی دیگر وجود ندارد.

نمونهٔ مورد استفاده {#example-use-case}

در یک سناریوی فرضی، یک سازمان یک سرویس خارجی اجرا می‌کند که اعتبارنامه‌های LDAP را با توکن‌های امضاشدهٔ مختص کاربر مبادله می‌کند. این سرویس همچنین قادر است به درخواست‌های webhook token authenticator برای اعتبارسنجی توکن‌ها پاسخ دهد. کاربران باید یک افزونهٔ اعتبارنامه را روی ایستگاه کاری خود نصب کنند.

برای احراز هویت در برابر API:

  • کاربر یک فرمان kubectl اجرا می‌کند.
  • افزونهٔ اعتبارنامه از کاربر اعتبارنامه‌های LDAP را درخواست می‌کند و اعتبارنامه‌ها را با سرویس خارجی در ازای یک توکن مبادله می‌کند.
  • افزونهٔ اعتبارنامه توکن را به client-go بازمی‌گرداند و client-go آن را به‌عنوان توکن bearer در برابر API server استفاده می‌کند.
  • API server از webhook token authenticator برای ارسال یک TokenReview به سرویس خارجی استفاده می‌کند.
  • سرویس خارجی امضای توکن را تأیید می‌کند و نام کاربری و گروه‌های کاربر را بازمی‌گرداند.

فرمت‌های ورودی و خروجی

دستور اجراشده یک آبجکت ExecCredential را در stdout چاپ می‌کند. k8s.io/client-go با استفاده از اعتبارنامه‌های بازگردانده‌شده در status، در برابر API کوبرنتیز احراز هویت می‌کند. به دستور اجراشده، یک آبجکت ExecCredential از طریق متغیر محیطی KUBERNETES_EXEC_INFO به‌عنوان ورودی داده می‌شود. این ورودی شامل اطلاعات مفیدی مانند نسخه API مورد انتظار آبجکت ExecCredential بازگردانده‌شده و همچنین این است که آیا افزونه می‌تواند برای تعامل با کاربر از stdin استفاده کند یا خیر.

هنگامی که دستور از یک نشست تعاملی (یعنی یک ترمینال) اجرا می‌شود، stdin می‌تواند مستقیماً در اختیار افزونه قرار گیرد. افزونه‌ها باید از فیلد spec.interactive در آبجکت ExecCredential ورودی موجود در متغیر محیطی KUBERNETES_EXEC_INFO استفاده کنند تا مشخص شود آیا stdin فراهم شده است یا خیر. نیازمندی افزونه به stdin (یعنی اینکه stdin برای اجرای موفق افزونه اختیاری است، اکیداً لازم است، یا هرگز استفاده نمی‌شود) از طریق فیلد user.exec.interactiveMode در kubeconfig اعلام می‌شود (مقادیر معتبر در جدول زیر آمده است). فیلد user.exec.interactiveMode در client.authentication.k8s.io/v1beta1 اختیاری و در client.authentication.k8s.io/v1 الزامی است.

مقدار interactiveMode معنا
Never این افزونه exec هرگز نیازی به ورودی استاندارد ندارد؛ بنابراین افزونه exec صرف‌نظر از اینکه ورودی استاندارد برای دریافت ورودی از کاربر در دسترس باشد یا نباشد، اجرا خواهد شد.
IfAvailable این افزونه exec در صورت در دسترس بودن ورودی استاندارد مایل به استفاده از آن است، اما در صورت در دسترس نبودن آن نیز می‌تواند کار کند. بنابراین افزونه exec صرف‌نظر از اینکه stdin برای دریافت ورودی از کاربر در دسترس باشد یا نباشد، اجرا خواهد شد. اگر ورودی استاندارد برای دریافت ورودی از کاربر در دسترس باشد، در اختیار این افزونه exec قرار می‌گیرد.
Always این افزونه exec برای اجرا به ورودی استاندارد نیاز دارد؛ بنابراین افزونه exec تنها در صورتی اجرا می‌شود که ورودی استاندارد برای دریافت ورودی از کاربر در دسترس باشد. اگر ورودی استاندارد برای دریافت ورودی از کاربر در دسترس نباشد، افزونه exec اجرا نخواهد شد و اجراکننده افزونه exec یک خطا بازمی‌گرداند.

برای استفاده از اعتبارنامه‌های توکن حامل (bearer token)، افزونه یک توکن را در status آبجکت ExecCredential بازمی‌گرداند.

دسترسی API به اطلاعات احراز هویت یک کلاینت {#self-subject-review}

وضعیت ویژگی: Kubernetes v1.28 [stable] (پایدار)

می‌توانید از API به نام SelfSubjectReview استفاده کنید تا دریابید کلاستر کوبرنتیز شما چگونه اطلاعات احراز هویت شما را به‌عنوان یک کلاینت شناسایی و نگاشت می‌کند. این امر چه زمانی که به‌عنوان کاربر (که معمولاً نمایانگر یک شخص واقعی است) احراز هویت می‌شوید و چه زمانی که به‌عنوان ServiceAccount احراز هویت می‌شوید، کار می‌کند.

در یک کلاستر معمول کوبرنتیز، همه کاربران احراز هویت‌شده می‌توانند SelfSubjectReview ایجاد کنند. دسترسی به این کار توسط ClusterRole توکار system:basic-user مجاز شده است.

توانایی یک کلاینت برای آگاهی از هویت خود، هنگام عیب‌یابی یک جریان احراز هویت پیچیده که در یک کلاستر کوبرنتیز به کار رفته است، بسیار مفید است؛ برای مثال، اگر از احراز هویت توکن با webhook یا یک پروکسی احراز هویت استفاده می‌کنید.

اگر می‌خواهید این اطلاعات را در خط فرمان پرس‌وجو کنید، به دسترسی CLI به اطلاعات احراز هویت مراجعه کنید.

دسترسی HTTP به اطلاعات احراز هویت {#self-subject-review-http-api}

SelfSubjectReview هیچ فیلد قابل پیکربندی ندارد. هنگام دریافت یک درخواست، API server کوبرنتیز فیلد status را با ویژگی‌های کاربر پر می‌کند و آن را به کاربر بازمی‌گرداند. این کار یک منبع نام‌دار را در کلاستر شما ذخیره نمی‌کند: نمی‌توانید SelfSubjectReview را بازیابی کنید و پس از تکمیل درخواست POST شما، دور ریخته می‌شود.

نمونه درخواست (بدنه درخواست یک SelfSubjectReview خواهد بود):

POST /apis/authentication.k8s.io/v1/selfsubjectreviews

{
  "apiVersion": "authentication.k8s.io/v1",
  "kind": "SelfSubjectReview"
}

توجه:

API server کوبرنتیز فیلد userInfo را پس از اعمال همه سازوکارهای احراز هویت پر می‌کند، از جمله جعل هویت (impersonation). اگر شما یا یک پروکسی احراز هویت با استفاده از جعل هویت یک SelfSubjectReview ایجاد کنید، جزئیات و ویژگی‌های کاربری را مشاهده می‌کنید که هویت او جعل شده است.

این پاسخ نمونه همه فیلدهای موجود را نشان نداد؛ همه سازوکارهای احراز هویت تمام فیلدهای موجود را پر نمی‌کنند. برای مشاهده فیلدهای موجود، به مرجع API مربوط به SelfSubjectReview مراجعه کنید.
