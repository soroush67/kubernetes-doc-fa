احراز هویت

این صفحه مروری بر احراز هویت (authentication) در کوبرنتیز ارائه می‌دهد و تمرکز آن بر احراز هویت در API کوبرنتیز است.

کاربران در کوبرنتیز

همه‌ی کلاسترهای کوبرنتیز دو دسته کاربر دارند: حساب‌های سرویس (service account) که کوبرنتیز آن‌ها را مدیریت می‌کند، و کاربران عادی.

فرض بر این است که یک سرویس مستقل از کلاستر، کاربران عادی را به یکی از روش‌های زیر مدیریت می‌کند:

  • مدیری که کلیدهای خصوصی را توزیع می‌کند
  • یک مخزن کاربران مانند Keystone یا Google Accounts
  • فایلی شامل فهرستی از نام‌های کاربری و گذرواژه‌ها

از این نظر، کوبرنتیز هیچ آبجکتی برای نمایش حساب‌های کاربران عادی ندارد. نمی‌توان کاربران عادی را با یک فراخوانی API به کلاستر اضافه کرد.

با اینکه نمی‌توان کاربر عادی را از طریق فراخوانی API اضافه کرد، هر کاربری که گواهی معتبری ارائه دهد که مرجع صدور گواهی (CA) کلاستر آن را امضا کرده باشد، احرازهویت‌شده به شمار می‌آید. در این پیکربندی، کوبرنتیز نام کاربری را از فیلد common name در بخش «subject» گواهی (برای مثال، "/CN=bob") تعیین می‌کند. پس از آن، زیرسیستم کنترل دسترسی مبتنی بر نقش (RBAC) تعیین می‌کند که آیا کاربر مجاز به انجام عملیاتی مشخص روی یک منبع هست یا نه.

در مقابل، حساب‌های سرویس کاربرانی هستند که API کوبرنتیز آن‌ها را مدیریت می‌کند. این حساب‌ها به فضاهای نام مشخصی وابسته‌اند و API server آن‌ها را به‌طور خودکار ایجاد می‌کند یا می‌توان آن‌ها را به‌صورت دستی و از طریق فراخوانی‌های API ایجاد کرد. حساب‌های سرویس به مجموعه‌ای از اعتبارنامه‌ها گره خورده‌اند که به‌صورت Secrets ذخیره می‌شوند. این اعتبارنامه‌ها در پادها mount می‌شوند تا فرایندهای درون کلاستر بتوانند با API کوبرنتیز ارتباط برقرار کنند.

هر درخواست API یا به یک کاربر عادی وابسته است، یا به یک حساب سرویس، یا به‌عنوان درخواست ناشناس در نظر گرفته می‌شود. یعنی هر فرایندی در داخل یا خارج از کلاستر، از کاربر انسانی‌ای که روی ایستگاه کاری خود kubectl را اجرا می‌کند گرفته تا kubelets روی نودها و اعضای control plane، هنگام ارسال درخواست به API server باید احراز هویت شود؛ در غیر این صورت با آن مانند یک کاربر ناشناس رفتار می‌شود.

اگر برای احراز هویت تلاش کنید و موفق شوید، API server به‌طور خودکار شما را عضو گروه ویژه‌ی system:authenticated علامت‌گذاری می‌کند.

راهبردهای احراز هویت

کوبرنتیز برای احراز هویت درخواست‌های API از طریق افزونه‌های احراز هویت، از گواهی‌های کلاینت، توکن‌های حامل (bearer token) یا یک پراکسی احراز هویت استفاده می‌کند. هنگامی که درخواست‌های HTTP به API server فرستاده می‌شوند، افزونه‌ها تلاش می‌کنند ویژگی‌های زیر را به درخواست نسبت دهند:

  • نام کاربری (Username): رشته‌ای که کاربر نهایی را شناسایی می‌کند. مقادیر رایج می‌توانند kube-admin یا jane@example.com باشند.
  • شناسه‌ی کاربر (UID): رشته‌ای که کاربر نهایی را شناسایی می‌کند و تلاش می‌کند از نام کاربری پایدارتر و یکتاتر باشد.
  • گروه‌ها (Groups): مجموعه‌ای از رشته‌ها که هر کدام عضویت کاربر را در یک مجموعه‌ی منطقیِ نام‌دار از کاربران نشان می‌دهد. مقادیر رایج می‌توانند system:masters یا devops-team باشند.
  • فیلدهای اضافی (Extra fields): نگاشتی از رشته‌ها به فهرست‌هایی از رشته‌ها که اطلاعات تکمیلی‌ای را نگه می‌دارد که ممکن است برای مجوزدهنده‌ها مفید باشد.
توجه:

همه‌ی این مقادیر برای سیستم احراز هویت مبهم (opaque) هستند و فقط زمانی معنا پیدا می‌کنند که یک مجوزدهنده آن‌ها را تفسیر کند.

درخواست‌های ناشناس

اگر این قابلیت فعال باشد، درخواست‌هایی که سایر روش‌های احراز هویتِ پیکربندی‌شده آن‌ها را رد نکنند، به‌عنوان درخواست ناشناس در نظر گرفته می‌شوند و نام کاربری system:anonymous و گروه system:unauthenticated به آن‌ها داده می‌شود.

برای مثال، در سروری که احراز هویت با توکن در آن پیکربندی شده و دسترسی ناشناس نیز فعال است، درخواستی که توکن حامل نامعتبری ارائه کند خطای 401 Unauthorized دریافت می‌کند، اما با درخواستی که هیچ توکن حاملی ارائه نکند مانند یک درخواست ناشناس رفتار می‌شود.

اگر از حالت مجوزدهیی غیر از AlwaysAllow استفاده شود، دسترسی ناشناس به‌طور پیش‌فرض فعال است؛ می‌توانید با ارسال گزینه‌ی خط فرمان --anonymous-auth=false به API server آن را غیرفعال کنید. مجوزدهنده‌های داخلی ABAC و RBAC نیازمند مجوزدهی صریح به کاربر system:anonymous یا گروه system:unauthenticated هستند؛ اگر قواعد سیاست قدیمی (مربوط به کوبرنتیز نسخه‌ی ۱.۵ یا پیش از آن) دارید، آن دسته از قواعد قدیمی که به کاربر * یا گروه * دسترسی می‌دهند، به‌طور خودکار به کاربران ناشناس اجازه‌ی دسترسی نمی‌دهند.

پیکربندی احرازکننده‌ی ناشناس

وضعیت ویژگی: Kubernetes [] ()

برای پیکربندی احرازکننده‌ی ناشناس می‌توان از AuthenticationConfiguration استفاده کرد. اگر فیلد anonymous را در فایل AuthenticationConfiguration تنظیم کنید، دیگر نمی‌توانید گزینه‌ی خط فرمان --anonymous-auth را تنظیم کنید.

مزیت اصلی پیکربندی احرازکننده‌ی ناشناس با فایل پیکربندی احراز هویت این است که افزون بر فعال و غیرفعال کردن احراز هویت ناشناس، می‌توانید تعیین کنید کدام endpointها از احراز هویت ناشناس پشتیبانی کنند.

نمونه‌ای از فایل پیکربندی احراز هویت در ادامه آمده است:

---
#
# CAUTION: this is an example configuration.
#          Do not use this as-is for your own cluster!
#
apiVersion: apiserver.config.k8s.io/v1
kind: AuthenticationConfiguration
anonymous:
  enabled: true
  conditions:
  - path: /livez
  - path: /readyz
  - path: /healthz

در پیکربندی بالا، فقط endpointهای /livez، /readyz و /healthz برای درخواست‌های ناشناس در دسترس هستند. هیچ endpoint دیگری به‌صورت ناشناس در دسترس نخواهد بود، حتی اگر پیکربندی مجوزدهی شما اجازه‌ی آن را بدهد.

روش‌های احراز هویت

می‌توانید چند روش احراز هویت را هم‌زمان فعال کنید. معمولاً باید دست‌کم از دو روش استفاده کنید:

  • توکن‌های حساب سرویس برای ServiceAccountها
  • دست‌کم یک روش دیگر برای احراز هویت کاربران (عادی)

روش‌های احراز هویت موجود عبارت‌اند از:

  • گواهی‌های کلاینت X.509
  • توکن‌های راه‌اندازی
  • توکن‌های حساب سرویس
  • فایل توکن ایستا
  • یکپارچه‌سازی‌های خارجی
    • توکن‌های وب JSON
    • توکن‌های OpenID Connect
    • احراز هویت با توکن از طریق Webhook
    • پراکسی معکوسِ احراز هویت

هنگامی که چند ماژول احرازکننده فعال باشد، نخستین ماژولی که درخواست را با موفقیت احراز هویت کند، ارزیابی را متوقف می‌کند و بقیه بررسی نمی‌شوند. API server هیچ تضمینی درباره‌ی ترتیب اجرای احرازکننده‌ها نمی‌دهد.

گواهی‌های کلاینت X.509 {#x509-client-certificates}

هر کلاینت کوبرنتیز که گواهی کلاینت معتبری ارائه دهد که مرجع صدور گواهیِ اعتماد کلاینت (client trust CA) کلاستر آن را امضا کرده باشد، احرازهویت‌شده به شمار می‌آید. در این پیکربندی، کوبرنتیز نام کاربری را از فیلد commonName در بخش subject گواهی تعیین می‌کند (برای مثال، commonName=bob نشان‌دهنده‌ی کاربری با نام کاربری "bob" است). پس از آن، سازوکارهای مجوزدهی کوبرنتیز تعیین می‌کنند که آیا کاربر مجاز به انجام عملیاتی مشخص روی یک منبع هست یا نه.

احراز هویت با گواهی کلاینت با ارسال گزینه‌ی --client-ca-file=<SOMEFILE> به API server فعال می‌شود. این گزینه مرجع صدور گواهیِ اعتماد کلاینت کلاستر را پیکربندی می‌کند. فایلِ مشخص‌شده باید شامل یک یا چند مرجع صدور گواهی باشد که API server بتواند هنگام اعتبارسنجی گواهی‌های کلاینت از آن‌ها استفاده کند. اگر یک گواهی کلاینت ارائه و تأیید شود، common name موجود در subject به‌عنوان نام کاربری درخواست استفاده می‌شود. گواهی‌های کلاینت همچنین می‌توانند عضویت کاربر در گروه‌ها را از طریق فیلدهای organization گواهی مشخص کنند. برای اینکه کاربر عضو چند گروه باشد، چند فیلد organization در گواهی قرار دهید.

برای آشنایی با نحوه‌ی تولید گواهی کلاینت، به مدیریت گواهی‌ها مراجعه کنید یا مثال کوتاهی را که در ادامه‌ی همین صفحه آمده است بخوانید.

گواهی‌های کلاینت سازگار با کوبرنتیز {#x509-client-certificates-k8s}

می‌توانید گواهی معتبری را که یک CA در زنجیره‌ی اعتمادِ موردپذیرش API server برای گواهی‌های کلاینت صادر کرده است ارائه دهید و از آن برای احراز هویت در کوبرنتیز استفاده کنید. گواهی باید معتبر باشد؛ API server این موضوع را بر اساس ویژگی‌های notBefore و notAfter استاندارد X.509 بررسی می‌کند. همچنین گواهی باید دارای کاربرد کلید توسعه‌یافته (extended key usage) باشد که احراز هویت کلاینت (ClientAuth) را شامل شود.

توجه:

کوبرنتیز 1.37 از ابطال (revocation) گواهی پشتیبانی نمی‌کند. هر گواهی‌ای که صادر شود تا زمان انقضا معتبر باقی می‌ماند.

نگاشت نام کاربری {#x509-client-certificates-k8s-username}

کوبرنتیز انتظار دارد گواهی کلاینت دارای ویژگی commonName (با OID 2.5.4.3) باشد که به‌عنوان نام کاربری subject استفاده می‌شود.

وضعیت ویژگی: Kubernetes [] ()

برای استفاده از این قابلیت، گواهی باید ویژگی 1.3.6.1.4.1.57683.2 را داشته باشد و feature gate با نام AllowParsingUserUIDFromCertAuth نیز باید فعال باشد (این feature gate به‌طور پیش‌فرض فعال است).

کوبرنتیز می‌تواند یک UID اختیاری برای کاربر را از گواهی استخراج کند. UID با نام کاربری متفاوت است؛ مقداری مبهم است که معنای آن را درخواست‌دهنده‌ی گواهی، یا کسی که قواعد تأیید گواهی را تنظیم کرده است، تعیین می‌کند.

برای مثال، UID ممکن است در یک کلاستر 1042 (یک عدد صحیح ساده) باشد، اما گواهی دیگری ممکن است از d3f77937-ec82-4f16-8010-61821abe315a (یک UUID) به‌عنوان UID استفاده کند.

مثالی برای توضیح این موضوع: فرض کنید گواهی‌ای دارید که common name آن "Ada Lovelace" است و ویژگی uid (با OID 0.9.2342.19200300.100.1.1) نیز با مقدار "aaking1815" در آن تنظیم شده است. در این حالت کوبرنتیز نام کاربری کلاینت را "Ada Lovelace" در نظر می‌گیرد و ویژگی uid را نادیده می‌گیرد، زیرا این ویژگی همان OID مختص CNCF که کوبرنتیز به دنبال آن است نیست. اگر می‌خواهید کوبرنتیز مقدار aaking1815 را به‌عنوان UID بشناسد، این مقدار باید به‌عنوان مقدار ویژگی OID 1.3.6.1.4.1.57683.2 در subject گواهی تنظیم شود.

نگاشت گروه {#x509-client-certificates-k8s-group}

می‌توانید با قرار دادن ایستای اطلاعات گروه در گواهی، کاربر را به گروه‌ها نگاشت کنید. برای هر گروهی که کاربر عضو آن است، نام گروه را به‌عنوان یک organization (با OID 2.5.6.4) در subject گواهی خود اضافه کنید. برای اینکه کاربر عضو چند گروه باشد، چند organization در subject گواهی قرار دهید (ترتیب آن‌ها اهمیتی ندارد). برای کاربر نمونه، distinguished name گواهی می‌تواند CN=Ada Lovelace,O=Users,O=Staff,O=Programmers باشد که او را در گروه‌های "Programmers"، "Staff"، "system:authenticated" و "Users" قرار می‌دهد.

قرار دادن اطلاعات گروه در گواهی اختیاری است؛ اگر هیچ گروهی در گواهی مشخص نکنید، کاربر فقط عضو "system:authenticated" خواهد بود.

گواهی‌های کلاینت نودها {#x509-client-certificates-nodes}

کوبرنتیز می‌تواند همین رویکرد را برای هویت نودها نیز به کار ببرد؛ نودها کلاینت‌هایی از API server کوبرنتیز هستند که یک kubelet را اجرا می‌کنند (همچنین، هرچند در اینجا اهمیت کمتری دارد، API server معمولاً خودش نیز کلاینتِ هر نود است). برای مثال، نودی با نام "server-1a-antarctica42" و نام دامنه‌ی "server-1a-antarctica42.cluster.example" می‌تواند از گواهی‌ای استفاده کند که برای "CN=system:node:server-1a-antarctica/42,O=system:nodes" صادر شده است. در این صورت نام کاربری نود "system:node:server-1a-antarctica/g42" خواهد بود و نود عضو گروه‌های "system:authenticated" و "system:nodes" است.

kubelet برای احراز هویت در API server کلاستر از گواهی و کلید خصوصی نود استفاده می‌کند.

توجه:

هویت‌های ماشینی نودها با ServiceAccountها یکسان نیستند.

مثال {#x509-client-certificates-example}

می‌توانید با ابزار خط فرمان openssl یک درخواست امضای گواهی (CSR) تولید کنید:

# This example assumes that you already have a private key alovelace.pem
openssl req -new -key alovelace.pem -out alovelace-csr.pem -subj "/CN=alovelace/O=app1/O=app2"

این دستور یک درخواست امضا برای نام کاربری "alovelace" ایجاد می‌کند که به دو گروه "app1" و "app2" تعلق دارد. سپس می‌توانید این درخواست امضا را به مرجع صدور گواهیِ اعتماد کلاینتِ کلاستر خود بدهید تا آن را امضا کند و گواهی‌ای به دست آورید که بتوانید از آن برای احراز هویت کلاینت در کلاستر استفاده کنید.

توکن‌های راه‌اندازی

وضعیت ویژگی: Kubernetes v1.18 [stable] (پایدار)

برای ساده‌سازی راه‌اندازی (bootstrapping) کلاسترهای جدید، کوبرنتیز نوعی توکن حامل با مدیریت پویا به نام توکن راه‌اندازی (Bootstrap Token) دارد. این توکن‌ها به‌صورت Secret در فضای نام kube-system ذخیره می‌شوند و در آنجا می‌توان آن‌ها را به‌صورت پویا مدیریت و ایجاد کرد. Controller Manager شامل کنترل‌کننده‌ای به نام TokenCleaner است که توکن‌های راه‌اندازی را پس از انقضا حذف می‌کند.

این توکن‌ها به شکل [a-z0-9]{6}.[a-z0-9]{16} هستند. بخش نخست، شناسه‌ی توکن (Token ID) و بخش دوم، رمز توکن (Token Secret) است. توکن را به این صورت در یک سرآیند HTTP مشخص می‌کنید:

Authorization: Bearer 781292.db7bc3a58fc5f07e

باید احرازکننده‌ی توکن راه‌اندازی را با فلگ --enable-bootstrap-token-auth روی API Server فعال کنید. همچنین باید کنترل‌کننده‌ی TokenCleaner را از طریق آرگومان خط فرمان --controllers برای kube-controller-manager فعال کنید. این کار با مقداری مانند --controllers=*,tokencleaner انجام می‌شود. اگر از ابزار kubeadm برای راه‌اندازی کلاستر استفاده کنید، این کار را برای شما انجام می‌دهد.

این احرازکننده، درخواست را با هویت system:bootstrap:<Token ID> احراز می‌کند. این هویت در گروه system:bootstrappers قرار می‌گیرد. نام‌گذاری و گروه‌ها عمداً محدود شده‌اند تا کاربران از به‌کارگیری این توکن‌ها پس از مرحله‌ی راه‌اندازی منصرف شوند. از این نام‌های کاربری و گروه می‌توان برای تدوین سیاست‌های مجوزدهی مناسب جهت پشتیبانی از راه‌اندازی کلاستر استفاده کرد (و kubeadm نیز از آن‌ها استفاده می‌کند).

برای مستندات مفصل درباره‌ی احرازکننده و کنترل‌کننده‌های توکن راه‌اندازی و نیز نحوه‌ی مدیریت این توکن‌ها با kubeadm، به توکن‌های راه‌اندازی مراجعه کنید.

قرار دادن توکن حامل در درخواست

هنگام استفاده از احراز هویت با توکن حامل در یک کلاینت HTTP، API server انتظار دارد سرآیند Authorization با مقدار Bearer <token> وجود داشته باشد. توکن حامل باید دنباله‌ای از نویسه‌ها باشد که بتوان آن را تنها با امکانات کدگذاری و نقل‌قول (quoting) خود HTTP در مقدار یک سرآیند HTTP قرار داد. برای مثال، اگر توکن حامل 31ada4fd-adec-460c-809a-9e56ceb75269 باشد، در سرآیند HTTP به شکل زیر نمایش داده می‌شود.

Authorization: Bearer 31ada4fd-adec-460c-809a-9e56ceb75269

توکن‌های حساب سرویس

حساب سرویس، احرازکننده‌ای است که به‌طور خودکار فعال است و برای تأیید درخواست‌ها از توکن‌های حاملِ امضاشده استفاده می‌کند. این افزونه دو فلگ اختیاری می‌پذیرد:

  • فلگ --service-account-key-file: فایلی شامل کلیدهای خصوصی یا عمومی RSA یا ECDSA از نوع x509 با کدگذاری PEM که برای تأیید توکن‌های ServiceAccount به کار می‌رود. فایل مشخص‌شده می‌تواند چند کلید داشته باشد و می‌توان این فلگ را چند بار با فایل‌های مختلف مشخص کرد. اگر مشخص نشود، از --tls-private-key-file استفاده می‌شود.
  • فلگ --service-account-lookup: اگر فعال باشد، توکن‌هایی که از API حذف شده‌اند باطل می‌شوند.

ServiceAccountها معمولاً به‌طور خودکار توسط API server ایجاد می‌شوند و از طریق کنترل‌کننده‌ی پذیرش ServiceAccount به پادهایی که در کلاستر اجرا می‌شوند مرتبط می‌شوند. توکن‌های حامل در مسیرهای شناخته‌شده‌ای در پادها mount می‌شوند و به کلاینت‌های درون کلاستر امکان می‌دهند در API server احراز هویت شوند. می‌توان ServiceAccountها را با فیلد serviceAccountName در spec یک Pod به‌طور صریح به Podها مرتبط کرد.

توجه:

معمولاً فیلد serviceAccountName حذف می‌شود، زیرا این کار به‌طور خودکار انجام می‌شود.

در ادامه مانیفستی (ناقص) برای یک Deployment آمده است که با ServiceAccountی به نام bob-the-bot اجرا می‌شود:

توکن ایجادشده یک توکن وب JSON (JWT) امضاشده است.

از این JWT امضاشده می‌توان به‌عنوان توکن حامل برای احراز هویت با هویتِ حساب سرویس مربوطه استفاده کرد. برای آشنایی با نحوه‌ی قرار دادن توکن در درخواست، به بخش بالا مراجعه کنید. معمولاً این توکن‌ها برای دسترسی درون‌کلاستری به API server در پادها mount می‌شوند، اما از خارج از کلاستر نیز می‌توان از آن‌ها استفاده کرد.

هشدار:

از آنجا که توکن‌های حساب سرویس می‌توانند در آبجکت‌های API از نوع Secret نیز ذخیره شوند، هر کاربری که دسترسی نوشتن روی Secretها داشته باشد می‌تواند توکن درخواست کند، و هر کاربری که دسترسی خواندن آن Secretها را داشته باشد می‌تواند با هویت آن حساب سرویس احراز هویت شود. هنگام اعطای مجوز به حساب‌های سرویس و اعطای قابلیت خواندن یا نوشتن Secretها، احتیاط کنید.

یکپارچه‌سازی‌های خارجی

کوبرنتیز به‌طور بومی از JWT و OpenID Connect (OIDC) پشتیبانی می‌کند. برای اطلاعات بیشتر، احراز هویت با JSON Web Token را ببینید.

یکپارچه‌سازی با سایر پروتکل‌های احراز هویت (برای مثال LDAP، SAML، Kerberos و طرح‌های جایگزین X.509) را می‌توان با استفاده از یک پروکسی احراز هویت یا از طریق یکپارچه‌سازی با یک وبهوک احراز هویت انجام داد.

همچنین می‌توانید از هر روش سفارشی دیگری که گواهی‌های کلاینت X.509 را برای کلاینت‌ها صادر می‌کند استفاده کنید، به این شرط که API server به گواهی‌های معتبر اعتماد کند. برای آشنایی با نحوهٔ تولید یک گواهی، بخش گواهی‌های کلاینت X.509 را بخوانید.

اگر برای کلاینت‌ها گواهی صادر می‌کنید، شما (به‌عنوان مدیر پلتفرم ابری) مسئول هستید اطمینان حاصل کنید که مدت اعتبار گواهی و سایر تصمیم‌های طراحی‌تان سطح امنیت مناسبی فراهم می‌کنند.

احراز هویت با JSON Web Token

می‌توانید کوبرنتیز را طوری پیکربندی کنید که کاربران را با توکن‌های سازگار با JSON Web Token (JWT) احراز هویت کند. کوبرنتیز برای توکن‌های ServiceAccount که خودش صادر می‌کند از سازوکار احراز هویت JWT استفاده می‌کند. شما نیز می‌توانید از همین سازوکار برای یکپارچه‌سازی با سایر منابع هویت بهره بگیرید.

احرازکنندهٔ هویت (authenticator) ابتدا تلاش می‌کند توکن هویت خام (raw ID token) را تجزیه کند و سپس بررسی می‌کند که این توکن را صادرکنندهٔ (issuer) پیکربندی‌شده امضا کرده باشد. برای توکن‌هایی که خارج از کلاستر صادر شده‌اند، کلید عمومی لازم برای بررسی امضا با استفاده از OIDC discovery از نقطهٔ پایانی عمومی صادرکننده به دست می‌آید.

حداقل محتوای معتبر یک JWT باید شامل ادعاهای (claims) زیر باشد:

{
  "iss": "https://example.com",   // must match the issuer.url
  "aud": ["my-app"],              // at least one of the entries in issuer.audiences must match the "aud" claim in presented JWTs.
  "exp": 1234567890,              // token expiration as Unix time (the number of seconds elapsed since January 1, 1970 UTC)
  "<username-claim>": "user"      // this is the username claim configured in the claimMappings.username.claim or claimMappings.username.expression
}

توکن‌های OpenID Connect

OpenID Connect گونه‌ای از OAuth2 است که برخی از ارائه‌دهندگان OAuth2، به‌ویژه Microsoft Entra ID، Salesforce و Google، از آن پشتیبانی می‌کنند. مهم‌ترین افزونهٔ این پروتکل نسبت به OAuth2، فیلد دیگری به نام ID Token است که همراه با توکن دسترسی (access token) بازگردانده می‌شود. این توکن یک JSON Web Token (JWT) است که فیلدهای شناخته‌شده‌ای مانند ایمیل کاربر دارد و سرور آن را امضا می‌کند.

احرازکنندهٔ هویت برای شناسایی کاربر، مقدار id_token (و نه access_token) را از پاسخ توکن در OAuth2 به‌عنوان توکن حامل (bearer token) به کار می‌برد. برای آشنایی با نحوهٔ قرار دادن توکن در درخواست، بخش بالا را ببینید.

  1. به ارائه‌دهندهٔ هویت (identity provider) خود وارد شوید.

  2. ارائه‌دهندهٔ هویت یک access_token، یک id_token و یک refresh_token در اختیار شما قرار می‌دهد.

  3. هنگام کار با kubectl، مقدار id_token را با آرگومان خط فرمان --token به کار ببرید یا آن را مستقیماً به فایل kubeconfig خود اضافه کنید.

  4. ابزار kubectl مقدار id_token شما را در سرآیندی به نام Authorization به سرور API می‌فرستد.

  5. سرور API از معتبر بودن امضای JWT اطمینان حاصل می‌کند.

  6. بررسی می‌شود که id_token منقضی نشده باشد.

    اگر عبارت‌های CEL در AuthenticationConfiguration پیکربندی شده باشند، اعتبارسنجی ادعاها و/یا کاربر انجام می‌شود.

  7. بررسی می‌شود که کاربر مجوز لازم را داشته باشد.

  8. پس از تأیید مجوز، سرور API پاسخی به kubectl بازمی‌گرداند.

  9. ابزار kubectl نتیجه را به کاربر اطلاع می‌دهد.

از آنجا که تمام داده‌های لازم برای تأیید هویت شما در id_token وجود دارد، کوبرنتیز نیازی ندارد برای این کار با ارائه‌دهندهٔ هویت تماس بگیرد. در مدلی که همهٔ درخواست‌ها بی‌حالت (stateless) هستند، این روش راه‌حلی بسیار مقیاس‌پذیر برای احراز هویت فراهم می‌کند. با این حال، چند چالش نیز به همراه دارد:

  1. کوبرنتیز هیچ «رابط وبی» برای آغاز فرایند احراز هویت ندارد. هیچ مرورگر یا رابطی برای دریافت اطلاعات اعتبارسنجی (credentials) وجود ندارد و به همین دلیل باید ابتدا نزد ارائه‌دهندهٔ هویت خود احراز هویت کنید.
  2. امکان ابطال id_token وجود ندارد. این توکن مانند یک گواهی است، بنابراین باید عمر کوتاهی (فقط چند دقیقه) داشته باشد و همین موضوع ممکن است دریافت توکن جدید در هر چند دقیقه را بسیار آزاردهنده کند.
  3. برای احراز هویت در داشبورد کوبرنتیز، باید از فرمان kubectl proxy یا یک پراکسی معکوس (reverse proxy) استفاده کنید که id_token را به درخواست‌ها تزریق کند.

با روش فایل پیکربندی می‌توانید چندین احرازکنندهٔ هویت JWT را پیکربندی کنید که هر کدام issuer.url و issuer.discoveryURL یکتای خود را دارند. فایل پیکربندی حتی امکان تعیین عبارت‌های CEL را فراهم می‌کند تا ادعاها را به ویژگی‌های کاربر نگاشت کنید و ادعاها و اطلاعات کاربر را اعتبارسنجی کنید. همچنین هر زمان که فایل پیکربندی تغییر کند، سرور API احرازکننده‌های هویت را به‌طور خودکار دوباره بارگذاری می‌کند. برای پایش آخرین زمان بارگذاری مجدد پیکربندی در سرور API می‌توانید از متریک apiserver_authentication_config_controller_automatic_reload_last_timestamp_seconds استفاده کنید.

باید مسیر فایل پیکربندی احراز هویت را با آرگومان خط فرمان --authentication-config به سرور API بدهید. اگر بخواهید به‌جای فایل پیکربندی از آرگومان‌های خط فرمان استفاده کنید، این آرگومان‌ها همچنان مانند گذشته کار می‌کنند. برای دسترسی به قابلیت‌های جدید، مانند پیکربندی چند احرازکنندهٔ هویت یا تعیین چند مخاطب (audience) برای یک صادرکننده، به استفاده از فایل پیکربندی روی بیاورید.

برای استفاده از احراز هویت ساخت‌یافته، آرگومان خط فرمان --authentication-config را برای kube-apiserver تعیین کنید. نمونه‌ای از فایل پیکربندی احراز هویت ساخت‌یافته در ادامه آمده است.

توجه:

تعیین هم‌زمان --authentication-config با هر یک از آرگومان‌های خط فرمان --oidc-* پیکربندی نادرست به شمار می‌رود. در این حالت، سرور API خطا گزارش می‌کند و بلافاصله خارج می‌شود. اگر می‌خواهید به پیکربندی احراز هویت ساخت‌یافته روی بیاورید، باید آرگومان‌های خط فرمان --oidc-* را حذف کنید و به‌جای آن‌ها از فایل پیکربندی استفاده کنید.

    فیلد jwt.claimValidationRules[i].expression عبارتی را نشان می‌دهد که CEL آن را ارزیابی می‌کند. عبارت‌های CEL به محتوای بدنهٔ توکن دسترسی دارند که در متغیر CEL با نام claims سازمان‌دهی شده است. متغیر claims نگاشتی از نام ادعاها (به‌صورت رشته) به مقادیر ادعاها (از هر نوعی) است.

  • عبارت قاعدهٔ اعتبارسنجی کاربر

    فیلد jwt.userValidationRules[i].expression عبارتی را نشان می‌دهد که CEL آن را ارزیابی می‌کند. عبارت‌های CEL به محتوای userInfo دسترسی دارند که در متغیر CEL با نام user سازمان‌دهی شده است. برای آشنایی با طرح‌وارهٔ user، به مستندات API مربوط به UserInfo مراجعه کنید.

محدودیت‌ها {#oidc-limitations}
  1. ادعاهای توزیع‌شده (distributed claims) از طریق عبارت‌های CEL کار نمی‌کنند.

کوبرنتیز هیچ ارائه‌دهندهٔ هویت (Identity Provider) مبتنی بر OpenID Connect ارائه نمی‌کند. می‌توانید از یک ارائه‌دهندهٔ هویت عمومی و موجود مبتنی بر OpenID Connect استفاده کنید یا ارائه‌دهندهٔ هویت خودتان را که از پروتکل OpenID Connect پشتیبانی می‌کند اجرا کنید.

ارائه‌دهندهٔ هویت برای کار با کوبرنتیز باید شرایط زیر را داشته باشد:

  1. از OpenID connect discovery پشتیبانی کند.

    کلید عمومی لازم برای بررسی امضا، با استفاده از سازوکار OIDC discovery از نقطهٔ پایانی (endpoint) عمومی صادرکننده به دست می‌آید. اگر از فایل پیکربندی احراز هویت استفاده می‌کنید، لازم نیست ارائه‌دهندهٔ هویت نقطهٔ پایانی discovery را به‌صورت عمومی در دسترس قرار دهد. می‌توانید نقطهٔ پایانی discovery را در مکانی جدا از صادرکننده (مثلاً به‌صورت محلی در داخل کلاستر) میزبانی کنید و مقدار issuer.discoveryURL را در فایل پیکربندی مشخص کنید.

  2. روی TLS و با رمزهایی (cipher) که منسوخ نشده‌اند اجرا شود.

  3. گواهی‌ای داشته باشد که یک CA آن را امضا کرده است (حتی اگر آن CA تجاری نباشد یا خودامضا باشد).

نکته‌ای دربارهٔ شرط شمارهٔ ۳ بالا، یعنی لزوم داشتن گواهی امضاشده توسط CA: اگر ارائه‌دهندهٔ هویت خودتان را مستقر می‌کنید، گواهی وب‌سرور آن باید با گواهی‌ای امضا شده باشد که پرچم CA آن برابر با TRUE است، حتی اگر این گواهی خودامضا باشد. علت این است که پیاده‌سازی کلاینت TLS در زبان Go در رعایت استانداردهای مربوط به اعتبارسنجی گواهی بسیار سخت‌گیر است. اگر CA در دسترس ندارید، می‌توانید با ابزارهای استاندارد تولید گواهی، یک CA ساده و یک گواهی امضاشده به همراه جفت کلید آن بسازید.

احراز هویت توکن با وب‌هوک

در کوبرنتیز، احراز هویت با وب‌هوک (webhook authentication) سازوکاری است که برای تأیید توکن‌های حامل (bearer token) یک فراخوانی HTTP به سرویسی بیرونی انجام می‌دهد.

برای پیکربندی API server از گزینه‌های زیر استفاده می‌شود:

  • گزینهٔ --authentication-token-webhook-config-file فایل پیکربندی‌ای است که نحوهٔ دسترسی به سرویس وب‌هوک راه‌دور را توصیف می‌کند.
  • گزینهٔ --authentication-token-webhook-cache-ttl مدت زمان نگهداری تصمیم‌های احراز هویت در حافظهٔ نهان (cache) را تعیین می‌کند. مقدار پیش‌فرض آن دو دقیقه است.
  • گزینهٔ --authentication-token-webhook-version تعیین می‌کند که برای ارسال و دریافت اطلاعات از وب‌هوک، از آبجکت‌های TokenReview نسخهٔ authentication.k8s.io/v1beta1 استفاده شود یا نسخهٔ authentication.k8s.io/v1. مقدار پیش‌فرض آن v1beta1 است.

فایل پیکربندی از قالب فایل kubeconfig استفاده می‌کند. در این فایل، clusters به سرویس راه‌دور و users به وب‌هوک API server اشاره دارد. نمونه‌ای از آن در ادامه آمده است:

# Kubernetes API version
apiVersion: v1
# kind of the API object
kind: Config
# clusters refers to the remote service.
clusters:
  - name: name-of-remote-authn-service
    cluster:
      certificate-authority: /path/to/ca.pem         # CA for verifying the remote service.
      server: https://authn.example.com/authenticate # URL of remote service to query. 'https' recommended for production.

# users refers to the API server's webhook configuration.
users:
  - name: name-of-api-server
    user:
      client-certificate: /path/to/cert.pem # cert for the webhook plugin to use
      client-key: /path/to/key.pem          # key matching the cert

# kubeconfig files require a context. Provide one for the API server.
current-context: webhook
contexts:
- context:
    cluster: name-of-remote-authn-service
    user: name-of-api-server
  name: webhook

پراکسی معکوس احراز هویت‌کننده {#authenticating-proxy}

هشدار:

اگر مرجع صدور گواهی (CA) شما در زمینهٔ دیگری نیز استفاده می‌شود، برای شناسایی کلاینت‌های پراکسی احراز هویت‌کننده به آن مرجع صدور گواهی اعتماد نکنید، مگر آنکه خطرها و سازوکارهای محافظت از نحوهٔ استفاده از آن CA را به‌خوبی بشناسید.

می‌توان API server را طوری پیکربندی کرد که کاربران را از روی مقادیر سرآیندهای درخواست، مانند X-Remote-User، شناسایی کند. این قابلیت برای استفاده همراه با یک پراکسی احراز هویت‌کننده (authenticating proxy) طراحی شده است که این سرآیندها را تنظیم می‌کند.

استفاده از پراکسی معکوس احراز هویت‌کننده با جعل هویت کاربر (user impersonation) تفاوت دارد. در جعل هویت کاربر، یک کاربر از API server می‌خواهد که با درخواست چنان رفتار کند که گویی کاربر دیگری آن را فرستاده است. اما در پراکسی معکوس احراز هویت‌کننده، API server به کلاینت مستقیم خود اعتماد می‌کند تا اطلاعات مربوط به هویت موجودیتی را که درخواست اصلی را ارسال کرده است، در اختیارش بگذارد.

برای آشنایی با پیکربندی این قابلیت از طریق آرگومان‌های خط فرمان، به پیکربندی سرآیندهای درخواست وب مراجعه کنید.

نمونه {#authenticating-proxy-example}

برای نمونه، با این پیکربندی:

--requestheader-username-headers=X-Remote-User
--requestheader-group-headers=X-Remote-Group
--requestheader-extra-headers-prefix=X-Remote-Extra-

این درخواست:

GET / HTTP/1.1
X-Remote-User: fido
X-Remote-Group: dogs
X-Remote-Group: dachshunds
X-Remote-Extra-Acme.com%2Fproject: some-project
X-Remote-Extra-Scopes: openid
X-Remote-Extra-Scopes: profile

به اطلاعات کاربری زیر منجر می‌شود:

name: fido
groups:
- dogs
- dachshunds
extra:
  acme.com/project:
  - some-project
  scopes:
  - openid
  - profile

گواهی کلاینت {#reverse-proxy-client-certificate}

برای جلوگیری از جعل سرآیندها، پراکسی احراز هویت‌کننده باید پیش از بررسی سرآیندهای درخواست، یک گواهی کلاینت معتبر به API server ارائه کند تا در برابر CA مشخص‌شده اعتبارسنجی شود.

برای حالت احراز هویت با سرآیند درخواست، به مرجع گزینه‌های خط فرمان مراجعه کنید.

از CAای که در زمینهٔ دیگری استفاده می‌شود دوباره استفاده نکنید، مگر آنکه خطرها و سازوکارهای محافظت از نحوهٔ استفاده از آن CA را به‌خوبی بشناسید.

یکپارچه‌سازی با فایل توکن ایستا {#static-token-file}

هنگامی که گزینهٔ --token-auth-file=<SOMEFILE> در خط فرمان به API server داده شود، این سرور توکن‌های حامل ایستا را از یک فایل می‌خواند. در کوبرنتیز 1.37، این توکن‌ها برای همیشه معتبر می‌مانند و فهرست توکن‌ها را نمی‌توان بدون راه‌اندازی دوبارهٔ API server تغییر داد.

فایل توکن یک فایل CSV با دست‌کم ۳ ستون است: توکن، نام کاربری و uid کاربر، که پس از آن‌ها می‌توان فهرستی اختیاری از نام گروه‌ها را به‌صورت جداشده با ویرگول آورد.

توجه:

اگر بیش از یک گروه دارید، آن ستون باید درون گیومهٔ دوتایی قرار گیرد؛ برای نمونه:

token,user,uid,"group1,group2,group3"

استفاده از فایل توکن ایستا برای توکن‌هایی مناسب است که ذاتاً طولانی‌مدت و ایستا هستند و شاید هرگز چرخش (rotation) نیابند. این روش همچنین زمانی سودمند است که کلاینت، مانند یک عامل پایش، به‌صورت محلی در کنار یک API server مشخص در control plane قرار دارد.

اگر از این روش در هنگام آماده‌سازی کلاستر استفاده می‌کنید و سپس به روش احراز هویت دیگری که قرار است در درازمدت به کار رود مهاجرت می‌کنید، باید توکنی را که برای راه‌اندازی اولیه (bootstrapping) استفاده شده است غیرفعال کنید (این کار به راه‌اندازی دوبارهٔ هر یک از API serverها نیاز دارد).

در سایر موقعیت‌ها، به‌ویژه هنگامی که چرخش بسیار سریع توکن اهمیت دارد، پروژهٔ کوبرنتیز توصیه می‌کند به‌جای این سازوکار از یک احرازکنندهٔ هویت توکن با وب‌هوک استفاده کنید.

جعل هویت کاربر

جعل هویت کاربر روشی فراهم می‌کند که با آن یک کاربر می‌تواند از طریق سرآیندهای جعل هویت، در نقش کاربری دیگر عمل کند.

پیکربندی احراز هویت {#api-server-authn-config}

احراز هویت در کوبرنتیز را می‌توانید با استفاده از آرگومان‌های خط فرمان یا یک فایل پیکربندی پیکربندی کنید.

معمولاً ترکیبی از این دو روش به کار گرفته می‌شود.

پیکربندی از طریق آرگومان‌های خط فرمان {#api-server-authn-config-cli}

با آرگومان‌های خط فرمان زیر می‌توانید نحوهٔ احراز هویت کلاینت‌ها توسط control plane کلاستر خود را پیکربندی کنید.

مرجع خط فرمان سرور API همهٔ آرگومان‌های خط فرمان مرتبط را با جزئیات بیشتری شرح می‌دهد.

پیکربندی احراز هویت ناشناس {#api-server-authn-config-cli-anonymous}

--anonymous-auth
تعیین می‌کند که آیا کلاینت‌هایی که احراز هویت نشده‌اند می‌توانند از طریق پورت امن سرور API درخواست ارسال کنند یا نه. نام کاربری درخواست‌های ناشناس system:anonymous و نام گروه آن‌ها system:unauthenticated است. همچنین بخش درخواست‌های ناشناس را ببینید.

پیکربندی توکن راه‌اندازی {#api-server-authn-config-cli-bootstrap}

--enable-bootstrap-token-auth
وقتی این فلگ تنظیم شده باشد، می‌توانید برای احراز هویت از توکن‌های راه‌اندازی (bootstrap tokens) استفاده کنید.

پیکربندی احراز هویت با گواهی {#api-server-authn-config-cli-x-509}

--client-ca-file
مسیر لنگر (یا لنگرهای) اعتماد برای اعتبارسنجی هویت کلاینت، در حالتی که کلاینت‌ها از احراز هویت با گواهی X.509 استفاده می‌کنند.

پیکربندی OIDC {#api-server-authn-config-cli-oidc}

--oidc-ca-file
مسیر لنگر (یا لنگرهای) اعتماد برای اعتبارسنجی هویت کلاینت، در حالتی که کلاینت‌ها از OIDC استفاده می‌کنند.
--oidc-client-id
شناسهٔ کلاینت برای کلاینت OpenID Connect.
--oidc-username-claim
نام یک claim در JWT برای تعیین نام کاربری؛ یعنی claimی که به‌عنوان نام کاربری به کار می‌رود. نام پیش‌فرض این claim برابر sub است، زیرا این مقدار باید شناسه‌ای یکتا برای کاربر نهایی باشد. می‌توانید claimهای دیگری مانند email یا name را انتخاب کنید. برای claimهایی غیر از sub یا email، kube-apiserver یک پیشوند به نام گروه اضافه می‌کند (تا از تداخل نام‌ها جلوگیری شود).
--oidc-username-prefix
پیشوندی که به ابتدای claimهای نام کاربری افزوده می‌شود تا از تداخل با نام‌های موجود (مانند کاربران system:) جلوگیری شود. برای مثال، مقدار oidc: نام‌های کاربری‌ای مانند oidc:jane.doe ایجاد می‌کند. اگر این آرگومان ارائه نشود و --oidc-username-claim مقداری غیر از email داشته باشد، پیشوند به‌طور پیش‌فرض ( Issuer URL )# خواهد بود که در آن ( Issuer URL ) مقدار --oidc-issuer-url است. برای غیرفعال کردن پیشوندگذاری نام کاربری، می‌توانید مقدار پیشوند را - تعیین کنید.
--oidc-groups-claim
نام یک claim سفارشی OpenID Connect برای تعیین گروه‌های کاربر. این claim در توکن باید آرایه‌ای از رشته‌ها باشد. مقدار پیش‌فرضی ندارد.
--oidc-groups-prefix
پیشوندی که به ابتدای claimهای گروه افزوده می‌شود تا از تداخل با نام‌های موجود (مانند گروه‌های system:) جلوگیری شود. برای مثال، مقدار oidc: نام‌های گروهی مانند oidc:engineering و oidc:infra ایجاد می‌کند. پیشوند پیش‌فرض oidc: است.
--oidc-issuer-url
نشانی URL صادرکنندهٔ OpenID. طرح (scheme) این URL باید https باشد. اگر نشانی کشف OIDC صادرکننده https://accounts.provider.example/.well-known/openid-configuration باشد، مقدار این آرگومان باید https://accounts.provider.example باشد.
--oidc-required-claim
claimی که باید پیش از احراز هویت کلاینت توسط کوبرنتیز در توکن وجود داشته باشد. قالب آن key=value است. می‌توانید این آرگومان را بیش از یک بار مشخص کنید.
--oidc-signing-algs
الگوریتم‌های امضای پذیرفته‌شده. مقادیر مجاز عبارت‌اند از: RS256، RS384، RS512، ES256، ES384، ES512، PS256، PS384 و PS512. این مقادیر در RFC 7518 تعریف شده‌اند. مقدار پیش‌فرض RS512 است.

پیکربندی ServiceAccount {#api-server-authn-config-cli-sa}

--api-audiences
مخاطب (audience) احراز هویت را برای توکن‌های حساب سرویس تعریف می‌کند.
--service-account-extend-token-expiration
این فلگ تمدید انقضای توکن‌های projected حساب سرویس را هنگام تولید توکن فعال می‌کند. این قابلیت به گذار امن از توکن‌های قدیمی به قابلیت توکن‌های مقید حساب سرویس کمک می‌کند. بخش احراز هویت اعتبارنامه‌های حساب سرویس را ببینید.
--service-account-issuer
شناسهٔ صادرکنندهٔ توکن حساب سرویس. صادرکننده این شناسه را در claim iss هر توکن صادرشده درج می‌کند. پروژهٔ کوبرنتیز توصیه می‌کند در اینجا از یک URL با طرح https استفاده کنید.
--service-account-jwks-uri
نشانی URI مربوط به JSON Web Key Set را در سند کشفی که در /.well-known/openid-configuration ارائه می‌شود، بازنویسی می‌کند.
--service-account-key-file
مسیر فایلی حاوی کلیدهای عمومی یا خصوصی X.509 با کدگذاری PEM (از نوع RSA یا ECDSA) که برای تأیید توکن‌های ServiceAccount استفاده می‌شوند. فایل مشخص‌شده می‌تواند چند کلید داشته باشد و می‌توانید این آرگومان را چند بار با مسیرهای مختلف تعیین کنید.
--service-account-lookup
اگر مقدار آن true باشد، سرور API در فرایند احراز هویت بررسی می‌کند که توکن‌های ServiceAccount در etcd وجود داشته باشند.
--service-account-max-token-expiration
بیشینهٔ مدت اعتبار توکنی که صادرکنندهٔ توکن حساب سرویس ایجاد می‌کند، به‌صورت یک رشتهٔ مدت‌زمان کوبرنتیز.
--service-account-signing-endpoint
مسیر سوکتی که یک امضاکنندهٔ خارجی JWT روی آن گوش می‌دهد. با این آرگومان می‌توانید با یک امضاکنندهٔ خارجی توکن یکپارچه شوید.
--service-account-signing-key-file
مسیر فایلی که کلید خصوصی فعلی صادرکنندهٔ توکن حساب سرویس را در خود دارد. تغییراتی که هنگام اجرای سرور API در این فایل اعمال شوند، دوباره خوانده نمی‌شوند.

پیکربندی توکن ایستا {#api-server-authn-config-cli-bearer}

--token-auth-file
مسیر فایل پیکربندی برای توکن‌های حامل ایستا (static bearer tokens). تغییراتی که هنگام اجرای سرور API در این فایل اعمال شوند، دوباره خوانده نمی‌شوند.

پیکربندی احراز هویت وب‌هوک {#api-server-authn-config-cli-webhook}

--authentication-token-webhook-cache-ttl
مدت زمانی (به‌صورت یک مشخصهٔ مدت‌زمان کوبرنتیز) که سرور API باید نتیجهٔ فراخوانی‌های HTTP برای اعتبارسنجی توکن‌ها را در حافظهٔ نهان نگه دارد.
--authentication-token-webhook-config-file
مسیر یک پیکربندی کلاینت در قالب kubeconfig که مشخص می‌کند سرور API هنگام انجام فراخوانی‌های HTTP چگونه احراز هویت شود. تغییراتی که هنگام اجرای سرور API در این فایل اعمال شوند، دوباره خوانده نمی‌شوند.
--authentication-token-webhook-version
نسخهٔ API مربوط به TokenReview که هنگام انجام فراخوانی‌های HTTP برای بررسی توکن‌ها به کار می‌رود.

پیکربندی احراز هویت درخواست وب {#api-server-authn-config-cli-reverse-proxy}

احتیاط:

پیش از تعیین این آرگومان‌های خط فرمان، باید مستندات مربوط به پیکربندی پروکسی احراز هویت را بخوانید، زیرا این مستندات توصیه‌های مهمی دربارهٔ امنیت اطلاعات دارند که باید از آن‌ها پیروی کنید.

--requestheader-client-ca-file
الزامی. مسیر یک بستهٔ گواهی با کدگذاری PEM که لنگر (یا لنگرهای) اعتماد را برای اعتبارسنجی هویت پروکسی احراز هویت در خود دارد.
پیش از آنکه هدرهای درخواست برای یافتن نام‌های کاربری بررسی شوند، باید یک گواهی کلاینت معتبر ارائه شود و با مراجع صدور گواهی موجود در فایل مشخص‌شده اعتبارسنجی شود.
--requestheader-allowed-names
اختیاری. فهرستی از مقادیر Common Name (CN) که با کاما از هم جدا شده‌اند.
اگر تنظیم شود، پیش از آنکه هدرهای درخواست برای یافتن نام‌های کاربری بررسی شوند، باید یک گواهی کلاینت معتبر ارائه شود که CN آن در فهرست مشخص‌شده باشد. اگر خالی باشد، هر CNی مجاز است.
--requestheader-username-headers
الزامی؛ بدون حساسیت به بزرگی و کوچکی حروف. نام هدرهایی که به ترتیب برای یافتن هویت کاربر بررسی می‌شوند.
نخستین هدری که مقدار داشته باشد، به‌عنوان نام کاربری استفاده می‌شود.
--requestheader-group-headers
اختیاری؛ بدون حساسیت به بزرگی و کوچکی حروف. نام هدرهایی که به ترتیب برای یافتن گروه‌های کاربر بررسی می‌شوند.
استفاده از X-Remote-Group پیشنهاد می‌شود. همهٔ مقادیر موجود در همهٔ هدرهای مشخص‌شده به‌عنوان نام گروه استفاده می‌شوند.
--requestheader-extra-headers-prefix
اختیاری؛ بدون حساسیت به بزرگی و کوچکی حروف. پیشوندهای هدری که برای تعیین اطلاعات اضافی دربارهٔ کاربر جست‌وجو می‌شوند.
استفاده از X-Remote-Extra- پیشنهاد می‌شود. داده‌های اضافی معمولاً توسط افزونه (یا افزونه‌های) مجوزدهی پیکربندی‌شده استفاده می‌شوند. از هر هدری که با یکی از پیشوندهای مشخص‌شده شروع شود، آن پیشوند حذف می‌شود. باقی‌ماندهٔ نام هدر به حروف کوچک تبدیل و رمزگشایی درصدی (percent-decoded) می‌شود و به کلید اضافی تبدیل می‌شود، و مقدار هدر نیز مقدار اضافی خواهد بود.

پیکربندی از طریق فایل پیکربندی {#api-server-authn-config-file}

وضعیت ویژگی: Kubernetes [] ()

وقتی آرگومان خط فرمان --authentication-config را به kube-apiserver می‌دهید، سرور API فایلی را از مسیری که مشخص کرده‌اید بارگذاری می‌کند و از محتوای آن برای پیکربندی احراز هویت استفاده می‌کند.

محتوای این فایل را می‌توان هنگام اجرای سرور API تغییر داد؛ در این صورت، سرور API پس از آن فایل را دوباره می‌خواند.

توجه:

تغییرات این فایل باید به‌صورت اتمیک انجام شوند (برای مثال: ابتدا در یک فایل موقت هم‌جوار بنویسید و سپس با تغییر نام فایل موقت، آن را جایگزین این فایل کنید).

مسیر فایل پیکربندی {#api-server-authn-config-cli-general}

--authentication-config
این آرگومان خط فرمان ویژه مشخص می‌کند که می‌خواهید احراز هویت را با استفاده از یک فایل پیکربندی، پیکربندی کنید.

مثال {#api-server-authn-config-file-example}

در ادامه نمونه‌ای از یک فایل پیکربندی احراز هویت (ساختاریافتهٔ) کوبرنتیز آمده است:

---
#
# CAUTION: this is an example configuration.
#          Check and amend this before you use it in your own cluster!
#
apiVersion: apiserver.config.k8s.io/v1
kind: AuthenticationConfiguration
anonymous:
  enabled: false

افزونه‌های اعتبارنامهٔ client-go

وضعیت ویژگی: Kubernetes v1.22 [stable] (پایدار)

کتابخانهٔ k8s.io/client-go و ابزارهایی که از آن استفاده می‌کنند، مانند kubectl و kubelet، می‌توانند یک فرمان خارجی را برای دریافت اعتبارنامه‌های کاربر اجرا کنند.

این قابلیت برای یکپارچه‌سازی سمت کلاینت با پروتکل‌های احراز هویتی طراحی شده است که k8s.io/client-go به‌صورت بومی از آن‌ها پشتیبانی نمی‌کند (مانند LDAP، Kerberos، OAuth2، SAML و غیره). افزونه منطق مخصوص پروتکل را پیاده‌سازی می‌کند و سپس اعتبارنامه‌هایی مبهم (opaque) را برای استفاده برمی‌گرداند. تقریباً همهٔ موارد استفاده از افزونه‌های اعتبارنامه به یک مؤلفهٔ سمت سرور نیاز دارند که از احرازکنندهٔ توکن وب‌هوک پشتیبانی کند تا قالب اعتبارنامهٔ تولیدشده توسط افزونهٔ کلاینت را تفسیر کند.

توجه:

نسخه‌های قدیمی‌تر kubectl پشتیبانی داخلی برای احراز هویت در AKS و GKE داشتند، اما این پشتیبانی دیگر وجود ندارد.

نمونهٔ مورد استفاده

در یک مورد استفادهٔ فرضی، سازمانی یک سرویس خارجی را اجرا می‌کند که اعتبارنامه‌های LDAP را با توکن‌های امضاشدهٔ مخصوص هر کاربر مبادله می‌کند. این سرویس همچنین می‌تواند به درخواست‌های احرازکنندهٔ توکن وب‌هوک برای اعتبارسنجی توکن‌ها پاسخ دهد. کاربران باید یک افزونهٔ اعتبارنامه را روی ایستگاه کاری خود نصب کنند.

برای احراز هویت در برابر API:

  • کاربر یک فرمان kubectl اجرا می‌کند.
  • افزونهٔ اعتبارنامه اعتبارنامه‌های LDAP را از کاربر درخواست می‌کند و آن‌ها را با سرویس خارجی در ازای یک توکن مبادله می‌کند.
  • افزونهٔ اعتبارنامه توکن را به client-go برمی‌گرداند و client-go از آن به‌عنوان توکن حامل (bearer token) در برابر سرور API استفاده می‌کند.
  • سرور API با استفاده از احرازکنندهٔ توکن وب‌هوک یک TokenReview را به سرویس خارجی ارسال می‌کند.
  • سرویس خارجی امضای توکن را تأیید می‌کند و نام کاربری و گروه‌های کاربر را برمی‌گرداند.

قالب‌های ورودی و خروجی

فرمان اجراشده یک آبجکت ExecCredential را در stdout چاپ می‌کند. کتابخانهٔ k8s.io/client-go با استفاده از اعتبارنامه‌های برگردانده‌شده در status، در برابر API کوبرنتیز احراز هویت می‌کند. یک آبجکت ExecCredential نیز از طریق متغیر محیطی KUBERNETES_EXEC_INFO به‌عنوان ورودی به فرمان اجراشده داده می‌شود. این ورودی اطلاعات مفیدی دارد؛ مثلاً نسخهٔ API مورد انتظار برای آبجکت ExecCredential برگشتی، و اینکه آیا افزونه می‌تواند برای تعامل با کاربر از stdin استفاده کند یا نه.

هنگامی که افزونه از یک نشست تعاملی (یعنی یک ترمینال) اجرا می‌شود، می‌توان stdin را مستقیماً در اختیار آن گذاشت. افزونه‌ها باید با استفاده از فیلد spec.interactive در آبجکت ExecCredential ورودی که از متغیر محیطی KUBERNETES_EXEC_INFO دریافت می‌شود، تشخیص دهند که آیا stdin فراهم شده است یا نه. نیازمندی‌های یک افزونه به stdin (یعنی اینکه برای اجرای موفق افزونه، stdin اختیاری است، الزاماً لازم است یا هرگز استفاده نمی‌شود) از طریق فیلد user.exec.interactiveMode در kubeconfig اعلام می‌شود (برای مقادیر معتبر، جدول زیر را ببینید). فیلد user.exec.interactiveMode در client.authentication.k8s.io/v1beta1 اختیاری و در client.authentication.k8s.io/v1 الزامی است.

مقدار interactiveMode معنا
Never این افزونهٔ exec هرگز به ورودی استاندارد نیاز ندارد؛ بنابراین صرف‌نظر از اینکه ورودی استاندارد برای دریافت ورودی کاربر در دسترس باشد یا نه، اجرا می‌شود.
IfAvailable این افزونهٔ exec ترجیح می‌دهد در صورت در دسترس بودن ورودی استاندارد از آن استفاده کند، اما بدون آن نیز می‌تواند کار کند. بنابراین صرف‌نظر از اینکه stdin برای دریافت ورودی کاربر در دسترس باشد یا نه، اجرا می‌شود. اگر ورودی استاندارد برای دریافت ورودی کاربر در دسترس باشد، در اختیار این افزونهٔ exec قرار می‌گیرد.
Always این افزونهٔ exec برای اجرا به ورودی استاندارد نیاز دارد؛ بنابراین فقط در صورتی اجرا می‌شود که ورودی استاندارد برای دریافت ورودی کاربر در دسترس باشد. اگر ورودی استاندارد در دسترس نباشد، افزونهٔ exec اجرا نمی‌شود و اجراکنندهٔ افزونهٔ exec خطا برمی‌گرداند.

برای استفاده از اعتبارنامه‌های توکن حامل (bearer token)، افزونه یک توکن را در status آبجکت ExecCredential برمی‌گرداند.

client.authentication.k8s.io/v1
{
  "apiVersion": "client.authentication.k8s.io/v1",
  "kind": "ExecCredential",
  "status": {
    "token": "my-bearer-token"
  }
}
client.authentication.k8s.io/v1beta1
{
  "apiVersion": "client.authentication.k8s.io/v1beta1",
  "kind": "ExecCredential",
  "status": {
    "token": "my-bearer-token"
  }
}

به‌عنوان جایگزین، می‌توان یک گواهی و کلید کلاینت با کدگذاری PEM برگرداند تا از احراز هویت کلاینت TLS استفاده شود. اگر افزونه در فراخوانی بعدی گواهی و کلید متفاوتی برگرداند، k8s.io/client-go اتصال‌های موجود با سرور را می‌بندد تا دست‌دهی (handshake) جدید TLS انجام شود.

در صورت تعیین، هر دو فیلد clientKeyData و clientCertificateData باید وجود داشته باشند.

فیلد clientCertificateData می‌تواند گواهی‌های میانی بیشتری را برای ارسال به سرور در خود داشته باشد.

  "kind": "ExecCredential",
  "status": {
    "clientCertificateData": "-----BEGIN CERTIFICATE-----\n...\n-----END CERTIFICATE-----",
    "clientKeyData": "-----BEGIN RSA PRIVATE KEY-----\n...\n-----END RSA PRIVATE KEY-----"
  }
}
client.authentication.k8s.io/v1beta1
{
  "apiVersion": "client.authentication.k8s.io/v1beta1",
  "kind": "ExecCredential",
  "status": {
    "clientCertificateData": "-----BEGIN CERTIFICATE-----\n...\n-----END CERTIFICATE-----",

  }
}

پاسخ می‌تواند به‌صورت اختیاری زمان انقضای اعتبارنامه را نیز در قالب یک برچسب زمانی RFC 3339 در بر داشته باشد.

وجود یا نبودِ زمان انقضا پیامدهای زیر را دارد:

  • اگر زمان انقضا درج شده باشد، توکن حامل و اعتبارنامه‌های TLS تا رسیدن زمان انقضا، یا تا زمانی که سرور با کد وضعیت HTTP 401 پاسخ دهد، یا تا خروج فرایند در حافظهٔ نهان نگه‌داری می‌شوند.

دسترسی API به اطلاعات احراز هویت یک کلاینت {#self-subject-review}

وضعیت ویژگی: Kubernetes v1.28 [stable] (پایدار)

با API مربوط به SelfSubjectReview می‌توانید دریابید که کلاستر کوبرنتیز شما چگونه اطلاعات احراز هویتتان را نگاشت می‌کند تا شما را به‌عنوان یک کلاینت شناسایی کند. این روش، چه به‌عنوان یک کاربر (که معمولاً نمایندهٔ یک شخص واقعی است) احراز هویت کنید و چه به‌عنوان یک ServiceAccount، کار می‌کند.

در یک کلاستر کوبرنتیز معمولی، همهٔ کاربران احراز هویت‌شده می‌توانند SelfSubjectReview ایجاد کنند. این دسترسی را ClusterRole داخلی system:basic-user مجاز می‌کند.

توانایی کلاینت در شناختن هویت خودش، هنگام عیب‌یابی یک جریان پیچیدهٔ احراز هویت در کلاستر کوبرنتیز بسیار سودمند است؛ برای نمونه، اگر از احراز هویت با توکن وب‌هوک یا یک پراکسی احراز هویت استفاده می‌کنید.

اگر می‌خواهید این اطلاعات را از خط فرمان پرس‌وجو کنید، دسترسی CLI به اطلاعات احراز هویت را ببینید.

دسترسی HTTP به اطلاعات احراز هویت {#self-subject-review-http-api}

آبجکت‌های SelfSubjectReview هیچ فیلد قابل‌پیکربندی‌ای ندارند. سرور API کوبرنتیز با دریافت درخواست، status را با ویژگی‌های کاربر پر می‌کند و آن را به کاربر برمی‌گرداند. این کار هیچ منبع نام‌داری را در کلاستر شما ذخیره نمی‌کند: نمی‌توانید SelfSubjectReview را بازیابی کنید و پس از تکمیل درخواست POST شما، دور ریخته می‌شود.

نمونهٔ درخواست (بدنهٔ درخواست یک SelfSubjectReview است):

POST /apis/authentication.k8s.io/v1/selfsubjectreviews

{

  "kind": "SelfSubjectReview"
}

سرور API کوبرنتیز پس از اعمال همهٔ سازوکارهای احراز هویت، از جمله جعل هویت (impersonation)، فیلد userInfo را پر می‌کند. اگر شما یا یک پراکسی احراز هویت با استفاده از جعل هویت یک SelfSubjectReview ایجاد کنید، جزئیات و ویژگی‌های کاربری را می‌بینید که هویتش جعل شده است.

این نمونهٔ پاسخ همهٔ فیلدهای موجود را نشان نمی‌دهد؛ همهٔ سازوکارهای احراز هویت همهٔ فیلدهای موجود را پر نمی‌کنند. برای دیدن فیلدهای موجود، مرجع API آبجکت SelfSubjectReview را ببینید.
