برچسب‌ها، حاشیه‌نویسی‌ها و taintهای شناخته‌شده

کوبرنتیز همهٔ برچسب‌ها، حاشیه‌نویسی‌ها (annotation) و taintهای موجود در فضاهای نام (namespace) kubernetes.io و k8s.io را برای خود رزرو کرده است.

این سند هم مرجعی برای این مقادیر است و هم نقطهٔ هماهنگی برای تخصیص آن‌ها.

برچسب‌ها، حاشیه‌نویسی‌ها و taintهای استفاده‌شده روی آبجکت‌های API

apf.kubernetes.io/autoupdate-spec

نوع: حاشیه‌نویسی

نمونه: apf.kubernetes.io/autoupdate-spec: "true"

محل استفاده: آبجکت‌های FlowSchema و PriorityLevelConfiguration

اگر مقدار این حاشیه‌نویسی روی یک FlowSchema یا PriorityLevelConfiguration برابر با true باشد، مدیریت spec آن آبجکت بر عهدهٔ kube-apiserver خواهد بود. اگر سرور API یک آبجکت APF را نشناسد و شما آن را برای به‌روزرسانی خودکار حاشیه‌نویسی کرده باشید، سرور API کل آن آبجکت را حذف می‌کند. در غیر این صورت، سرور API مشخصات آبجکت را مدیریت نمی‌کند. برای جزئیات بیشتر، بخش نگهداری آبجکت‌های پیکربندی اجباری و پیشنهادی را بخوانید.

نمونه: applyset.kubernetes.io/additional-namespaces: "namespace1,namespace2"

محل استفاده: آبجکت‌هایی که والد ApplySet هستند.

استفاده از این حاشیه‌نویسی در مرحلهٔ آلفا است. در کوبرنتیز نسخهٔ 1.37، می‌توانید این حاشیه‌نویسی را روی Secretها، ConfigMapها یا منابع سفارشی به کار ببرید، به شرطی که CustomResourceDefinition تعریف‌کنندهٔ آن‌ها برچسب applyset.kubernetes.io/is-parent-type را داشته باشد.

این حاشیه‌نویسی بخشی از مشخصه‌ای است که برای پیاده‌سازی هرس مبتنی بر ApplySet در kubectl استفاده می‌شود. این حاشیه‌نویسی روی آبجکت والدی قرار می‌گیرد که برای ردیابی یک ApplySet به کار می‌رود و دامنهٔ ApplySet را به فراتر از فضای نام خود آبجکت والد (در صورت وجود) گسترش می‌دهد. مقدار آن فهرستی جداشده با کاما از نام فضاهای نامی است که آبجکت‌ها در آن‌ها قرار دارند و با فضای نام والد متفاوت‌اند.

cluster-autoscaler.kubernetes.io/safe-to-evict

نوع: حاشیه‌نویسی

نمونه: cluster-autoscaler.kubernetes.io/safe-to-evict: "true"

محل استفاده: Pod

وقتی مقدار این حاشیه‌نویسی "true" باشد، مقیاس‌دهندهٔ خودکار کلاستر (cluster autoscaler) می‌تواند یک Pod را بیرون کند، حتی اگر قوانین دیگر در حالت عادی مانع این کار شوند. مقیاس‌دهندهٔ خودکار کلاستر هرگز Podهایی را که مقدار این حاشیه‌نویسی در آن‌ها صراحتاً "false" تنظیم شده است بیرون نمی‌کند. می‌توانید این مقدار را روی Podهای مهمی تنظیم کنید که می‌خواهید همچنان در حال اجرا بمانند. اگر این حاشیه‌نویسی تنظیم نشده باشد، مقیاس‌دهندهٔ خودکار کلاستر از رفتار خود در سطح Pod پیروی می‌کند.

config.kubernetes.io/local-config

نوع: حاشیه‌نویسی

نمونه: config.kubernetes.io/local-config: "true"

محل استفاده: همهٔ آبجکت‌ها

از این حاشیه‌نویسی در مانیفست‌ها استفاده می‌شود تا یک آبجکت به‌عنوان پیکربندی محلی علامت‌گذاری شود که نباید به API کوبرنتیز ارسال شود.

مقدار "true" برای این حاشیه‌نویسی اعلام می‌کند که این آبجکت فقط در ابزارهای سمت کلاینت مصرف می‌شود و نباید به سرور API ارسال شود.

با مقدار "false" می‌توان اعلام کرد که آبجکت باید به سرور API ارسال شود، حتی اگر در غیر این صورت محلی فرض شود.

این حاشیه‌نویسی بخشی از مشخصهٔ توابع مدل منابع کوبرنتیز (Kubernetes Resource Model یا KRM) است که Kustomize و ابزارهای شخص ثالث مشابه از آن استفاده می‌کنند. برای مثال، Kustomize آبجکت‌های دارای این حاشیه‌نویسی را از خروجی نهایی ساخت خود حذف می‌کند.

container.apparmor.security.beta.kubernetes.io/* (منسوخ‌شده) {#container-apparmor-security-beta-kubernetes-io}

نوع: حاشیه‌نویسی

نمونه: container.apparmor.security.beta.kubernetes.io/my-container: my-custom-profile

محل استفاده: Podها

با این حاشیه‌نویسی می‌توانید پروفایل امنیتی AppArmor را برای یک کانتینر درون Pod کوبرنتیز مشخص کنید. از نسخهٔ v1.30 کوبرنتیز، باید به‌جای آن از فیلد appArmorProfile استفاده کرد. برای اطلاعات بیشتر، آموزش AppArmor را ببینید. این آموزش نشان می‌دهد که چگونه می‌توان با AppArmor توانایی‌ها و دسترسی‌های یک کانتینر را محدود کرد.

پروفایل مشخص‌شده، مجموعه قوانین و محدودیت‌هایی را تعیین می‌کند که فرایند کانتینری‌شده باید از آن‌ها پیروی کند. این کار به اعمال سیاست‌های امنیتی و جداسازی کانتینرها کمک می‌کند.

اگر مقدار برچسب kubernetes.io/os در یک Pod با مقدار همین برچسب روی نود مطابقت نداشته باشد، kubelet روی آن نود Pod را نمی‌پذیرد. با این حال، kube-scheduler این موضوع را در نظر نمی‌گیرد. از سوی دیگر، اگر برای Pod سیستم‌عاملی مشخص کرده باشید که با سیستم‌عامل نود محل اجرای kubelet یکسان نباشد، kubelet از اجرای آن Pod خودداری می‌کند. برای جزئیات بیشتر، بخش سیستم‌عامل Pod را ببینید.

addonmanager.kubernetes.io/mode

نوع: برچسب

مثال: addonmanager.kubernetes.io/mode: "Reconcile"

محل استفاده: همهٔ آبجکت‌ها

برای تعیین شیوهٔ مدیریت یک افزونهٔ کلاستر (add-on) می‌توانید از برچسب addonmanager.kubernetes.io/mode استفاده کنید. این برچسب می‌تواند یکی از سه مقدار Reconcile، EnsureExists یا Ignore را داشته باشد.

  • مقدار Reconcile: منابع افزونه به‌صورت دوره‌ای با وضعیت مورد انتظار تطبیق داده می‌شوند. در صورت وجود هرگونه تفاوت، مدیر افزونه‌ها منابع را در صورت نیاز دوباره ایجاد، بازپیکربندی یا حذف می‌کند. اگر برچسبی مشخص نشده باشد، این حالت پیش‌فرض است.
  • مقدار EnsureExists: فقط وجود منابع افزونه بررسی می‌شود و این منابع پس از ایجاد تغییر نمی‌کنند. اگر نمونه‌ای از منبع با آن نام وجود نداشته باشد، مدیر افزونه‌ها منبع را ایجاد یا دوباره ایجاد می‌کند.
  • مقدار Ignore: منابع افزونه نادیده گرفته می‌شوند. این حالت برای افزونه‌هایی مفید است که با مدیر افزونه‌ها سازگار نیستند یا کنترل‌کنندهٔ دیگری آن‌ها را مدیریت می‌کند.

برای جزئیات بیشتر، مدیر افزونه‌ها را ببینید.

kubernetes.io/enforce-mountable-secrets (منسوخ‌شده) {#enforce-mountable-secrets}

نوع: حاشیه‌نویسی (annotation)

مثال: kubernetes.io/enforce-mountable-secrets: "true"

محل استفاده: ServiceAccount

توجه:

حاشیه‌نویسی kubernetes.io/enforce-mountable-secrets از نسخهٔ v1.32 کوبرنتیز منسوخ شده است. برای جداسازی دسترسی به Secretهای مانت‌شده، از فضاهای نام (namespace) جداگانه استفاده کنید.

مقدار این حاشیه‌نویسی باید true باشد تا اعمال شود. اگر مقدار آن را "true" قرار دهید، کوبرنتیز قوانین زیر را برای Podهایی که با این ServiceAccount اجرا می‌شوند اعمال می‌کند:

  1. نام Secretهایی که به‌صورت حجم (volume) مانت می‌شوند باید در فیلد secrets مربوط به ServiceAccount فهرست شده باشد.
  2. نام Secretهایی که در envFrom کانتینرها (از جمله کانتینرهای sidecar و init) به آن‌ها ارجاع داده می‌شود نیز باید در فیلد secrets مربوط به ServiceAccount فهرست شده باشد. اگر هر یک از کانتینرهای یک Pod به Secretای ارجاع دهد که در فیلد secrets مربوط به ServiceAccount فهرست نشده است (حتی اگر این ارجاع با optional مشخص شده باشد)، آن Pod راه‌اندازی نمی‌شود و خطایی تولید می‌شود که ارجاع نامعتبر به Secret را نشان می‌دهد.
  3. Secretهایی که در imagePullSecrets یک Pod به آن‌ها ارجاع داده می‌شود باید در فیلد imagePullSecrets مربوط به ServiceAccount نیز وجود داشته باشند؛ در غیر این صورت، آن Pod راه‌اندازی نمی‌شود و خطایی تولید می‌شود که ارجاع نامعتبر به Secret دریافت ایمیج را نشان می‌دهد.

این قوانین هنگام ایجاد یا به‌روزرسانی یک Pod بررسی می‌شوند. اگر Pod از این قوانین پیروی نکند، راه‌اندازی نمی‌شود و پیام خطایی نمایش داده خواهد شد. اگر Pod در حال اجرا باشد و مقدار حاشیه‌نویسی kubernetes.io/enforce-mountable-secrets را به true تغییر دهید، یا ServiceAccount مرتبط را طوری ویرایش کنید که ارجاع به Secret مورد استفادهٔ آن Pod حذف شود، Pod همچنان به اجرای خود ادامه می‌دهد.

kubernetes.io/ingress-bandwidth

مثال: kubernetes.io/ingress-bandwidth: 10M

می‌توانید شکل‌دهی ترافیک (traffic shaping) مبتنی بر کیفیت سرویس را روی یک Pod اعمال کنید و پهنای باند در دسترس آن را عملاً محدود سازید. ترافیک ورودی به Pod با شکل‌دهی بسته‌های صف‌شده مدیریت می‌شود تا داده‌ها به‌طور مؤثر پردازش شوند. برای محدود کردن پهنای باند یک Pod، فایل JSON تعریف آبجکت را بنویسید و سرعت ترافیک داده را با حاشیه‌نویسی kubernetes.io/ingress-bandwidth مشخص کنید. واحد نرخ ورودی، بیت بر ثانیه است و به‌صورت یک Quantity مشخص می‌شود. برای مثال، 10M به معنای ۱۰ مگابیت بر ثانیه است.

توجه:

حاشیه‌نویسی شکل‌دهی ترافیک ورودی یک قابلیت آزمایشی است. برای فعال‌سازی پشتیبانی از شکل‌دهی ترافیک، باید افزونهٔ bandwidth را به فایل پیکربندی CNI خود (به‌طور پیش‌فرض /etc/cni/net.d) اضافه کنید و مطمئن شوید که فایل اجرایی آن در پوشهٔ bin مربوط به CNI (به‌طور پیش‌فرض /opt/cni/bin) قرار دارد.

topology.kubernetes.io/zone {#topologykubernetesiozone}

نوع: برچسب

مثال: topology.kubernetes.io/zone: "us-east-1c"

محل استفاده: Node، PersistentVolume

روی Node: مؤلفهٔ kubelet یا cloud-controller-manager خارجی این برچسب را با اطلاعات دریافتی از ارائه‌دهندهٔ ابر پر می‌کند. این برچسب فقط در صورت استفاده از ارائه‌دهندهٔ ابر تنظیم می‌شود. با این حال، اگر با توپولوژی شما سازگار باشد، می‌توانید آن را روی نودها تنظیم کنید.

روی PersistentVolume: تأمین‌کننده‌های حجم آگاه از توپولوژی، محدودیت‌های وابستگی نود (node affinity) را به‌طور خودکار روی PersistentVolume تنظیم می‌کنند.

هر ناحیه (zone) یک دامنهٔ خرابی منطقی را نشان می‌دهد. کلاسترهای کوبرنتیز معمولاً برای افزایش دسترس‌پذیری در چند ناحیه گسترده می‌شوند. تعریف دقیق ناحیه به پیاده‌سازی زیرساخت واگذار شده است، اما از ویژگی‌های رایج یک ناحیه می‌توان به تأخیر بسیار کم شبکه در داخل ناحیه، رایگان بودن ترافیک شبکه در داخل ناحیه و مستقل بودن خرابی آن از نواحی دیگر اشاره کرد. برای مثال، نودهای درون یک ناحیه ممکن است از یک سوئیچ شبکهٔ مشترک استفاده کنند، اما نودهای نواحی مختلف نباید چنین اشتراکی داشته باشند.

هر منطقه (region) دامنهٔ بزرگ‌تری است که از یک یا چند ناحیه تشکیل می‌شود. گسترش کلاسترهای کوبرنتیز در چند منطقه رایج نیست. تعریف دقیق ناحیه یا منطقه به پیاده‌سازی زیرساخت واگذار شده است، اما از ویژگی‌های رایج مناطق می‌توان به تأخیر بیشتر شبکه میان مناطق نسبت به داخل آن‌ها، غیرصفر بودن هزینهٔ ترافیک شبکه میان مناطق و مستقل بودن خرابی از نواحی یا مناطق دیگر اشاره کرد. برای مثال، نودهای درون یک منطقه ممکن است زیرساخت برق مشترکی (مانند UPS یا ژنراتور) داشته باشند، اما نودهای مناطق مختلف معمولاً چنین اشتراکی ندارند.

کوبرنتیز چند فرض دربارهٔ ساختار نواحی و مناطق دارد:

  1. مناطق و نواحی ساختار سلسله‌مراتبی دارند: نواحی زیرمجموعه‌های سرهٔ مناطق هستند و هیچ ناحیه‌ای نمی‌تواند در ۲ منطقه قرار داشته باشد.
  2. نام نواحی در میان مناطق یکتاست؛ برای مثال، منطقهٔ "africa-east-1" ممکن است از نواحی "africa-east-1a" و "africa-east-1b" تشکیل شده باشد.

می‌توان با اطمینان فرض کرد که برچسب‌های توپولوژی تغییر نمی‌کنند. با اینکه برچسب‌ها از نظر فنی تغییرپذیرند، مصرف‌کنندگان آن‌ها می‌توانند فرض کنند که یک نود بدون حذف و ایجاد مجدد، میان نواحی جابه‌جا نمی‌شود.

کوبرنتیز می‌تواند از این اطلاعات به روش‌های گوناگون استفاده کند. برای مثال، زمان‌بند به‌طور خودکار می‌کوشد Podهای یک ReplicaSet را در میان نودهای یک کلاستر تک‌ناحیه‌ای توزیع کند تا تأثیر خرابی نودها کاهش یابد (به kubernetes.io/hostname مراجعه کنید). در کلاسترهای چندناحیه‌ای، این رفتار توزیع در سطح نواحی نیز اعمال می‌شود تا تأثیر خرابی نواحی کاهش یابد. این کار با SelectorSpreadPriority انجام می‌شود.

جای‌گذاری با SelectorSpreadPriority به‌صورت بهترین تلاش انجام می‌شود. اگر نواحی کلاستر شما ناهمگن باشند (برای مثال، تعداد یا نوع نودها یا نیازمندی‌های منابع Podها متفاوت باشد)، این جای‌گذاری ممکن است مانع توزیع یکسان Podها در میان نواحی شود. در صورت تمایل، می‌توانید با استفاده از نواحی همگن (با تعداد و نوع یکسان نودها) احتمال توزیع نابرابر را کاهش دهید.

زمان‌بند (از طریق گزارهٔ VolumeZonePredicate) همچنین تضمین می‌کند که Podهای درخواست‌کنندهٔ یک حجم مشخص، فقط در همان ناحیه‌ای قرار بگیرند که آن حجم در آن است. حجم‌ها را نمی‌توان میان نواحی مختلف متصل کرد.

اگر PersistentVolumeLabel از برچسب‌گذاری خودکار PersistentVolumeهای شما پشتیبانی نمی‌کند، بهتر است برچسب‌ها را به‌صورت دستی اضافه کنید (یا پشتیبانی از PersistentVolumeLabel را بیفزایید). با PersistentVolumeLabel، زمان‌بند از مانت شدن حجم‌های ناحیه‌ای دیگر در Podها جلوگیری می‌کند. اگر زیرساخت شما چنین محدودیتی ندارد، اصلاً نیازی به افزودن برچسب‌های ناحیه به حجم‌ها نیست.

نوع: Taint

مثال: node.kubernetes.io/out-of-service:NoExecute

استفاده‌شده روی: Node

کاربر می‌تواند این taint را به‌صورت دستی به یک نود اضافه کند و آن را خارج از سرویس علامت بزند. اگر نودی با این taint خارج از سرویس علامت‌گذاری شود، Podهایی از آن که toleration منطبق با این taint را نداشته باشند به‌اجبار حذف می‌شوند و عملیات جداسازی حجم‌ها (volume) برای Podهای در حال خاتمه روی آن نود بلافاصله انجام می‌شود. به این ترتیب، Podهای نود خارج از سرویس می‌توانند به‌سرعت روی نود دیگری بازیابی شوند.

یکپارچه‌سازی‌های رسمی کوبرنتیز با AWS از این حاشیه‌نویسی استفاده می‌کنند تا مشخص کنند آیا یکپارچه‌سازی ارائه‌دهنده ابری AWS باید Serviceای با type: LoadBalancer را مدیریت کند یا نه.

دو مقدار مجاز وجود دارد:

nlb
مؤلفه cloud controller manager یک Network Load Balancer پیکربندی می‌کند
external
مؤلفه cloud controller manager هیچ متعادل‌کننده باری را پیکربندی نمی‌کند

اگر Serviceای با type: LoadBalancer را در AWS مستقر کنید و حاشیه‌نویسی service.beta.kubernetes.io/aws-load-balancer-type را تنظیم نکنید، یکپارچه‌سازی AWS یک Elastic Load Balancer کلاسیک مستقر می‌کند. این رفتار در نبود حاشیه‌نویسی، پیش‌فرض است، مگر اینکه خلاف آن را مشخص کنید.

وقتی مقدار این حاشیه‌نویسی را روی Serviceای با type: LoadBalancer برابر با external قرار دهید و کلاستر شما یک استقرار فعال از کنترل‌کننده متعادل‌کننده بار AWS داشته باشد، این کنترل‌کننده تلاش می‌کند متعادل‌کننده باری را بر اساس مشخصات Service مستقر کند.

احتیاط:

حاشیه‌نویسی service.beta.kubernetes.io/aws-load-balancer-type را روی آبجکت Service موجود تغییر ندهید و به آن اضافه نکنید. برای جزئیات بیشتر، مستندات AWS در این زمینه را ببینید.

ابزار kubeadm این حاشیه‌نویسی را روی ConfigMapهایی قرار می‌دهد که برای پیکربندی مؤلفه‌ها مدیریت می‌کند. این حاشیه‌نویسی شامل یک هش (SHA-256) است که با آن مشخص می‌شود آیا کاربر برای یک مؤلفهٔ خاص، تنظیماتی متفاوت با مقادیر پیش‌فرض kubeadm اعمال کرده است یا نه.

node-role.kubernetes.io/control-plane

نوع: برچسب

استفاده‌شده روی: Node

این برچسب نشانگری است که مشخص می‌کند نود برای اجرای مؤلفه‌های control plane به کار می‌رود. ابزار kubeadm این برچسب را روی نودهای control plane تحت مدیریت خود اعمال می‌کند. سایر ابزارهای مدیریت کلاستر نیز معمولاً این taint را تنظیم می‌کنند.

با افزودن این برچسب به نودهای control plane می‌توانید زمان‌بندی Podها را فقط روی این نودها ساده‌تر کنید یا از اجرای Podها روی control plane جلوگیری کنید. اگر این برچسب تنظیم شده باشد، کنترل‌کنندهٔ EndpointSlice هنگام محاسبهٔ راهنماهای آگاه از توپولوژی (Topology Aware Hints) آن نود را نادیده می‌گیرد.

node-role.kubernetes.io/*

نوع: برچسب

مثال: node-role.kubernetes.io/gpu: gpu

استفاده‌شده روی: Node

این برچسب اختیاری زمانی روی یک نود اعمال می‌شود که بخواهید نقش آن نود را مشخص کنید. نقش نود (متن پس از / در کلید برچسب) را می‌توان تعیین کرد، مشروط بر اینکه کل کلید از قواعد نحو برچسب‌های آبجکت پیروی کند.

کوبرنتیز یک نقش نود مشخص به نام control-plane تعریف می‌کند. برای علامت‌گذاری این نقش نود می‌توانید از برچسب node-role.kubernetes.io/control-plane استفاده کنید.

node-role.kubernetes.io/control-plane {#node-role-kubernetes-io-control-plane-taint}

نوع: Taint

مثال: node-role.kubernetes.io/control-plane:NoSchedule

استفاده‌شده روی: Node

ابزار kubeadm این taint را روی نودهای control plane اعمال می‌کند تا قرارگیری Podها روی این نودها را محدود کند و فقط به Podهای مشخصی اجازهٔ زمان‌بندی روی آن‌ها را بدهد.

اگر این taint اعمال شده باشد، نودهای control plane فقط اجازهٔ زمان‌بندی بارهای کاری حیاتی را روی خود می‌دهند. می‌توانید با دستور زیر این taint را به‌صورت دستی از یک نود مشخص حذف کنید.

kubectl taint nodes <node-name> node-role.kubernetes.io/control-plane:NoSchedule-

نوع: Taint

استفاده‌شده روی: Node

مثال: node-role.kubernetes.io/master:NoSchedule

ابزار kubeadm پیش‌تر این taint را روی نودهای control plane اعمال می‌کرد تا فقط بارهای کاری حیاتی روی آن‌ها زمان‌بندی شوند. اکنون taint با نام node-role.kubernetes.io/control-plane جایگزین آن شده است. ابزار kubeadm دیگر این taint منسوخ‌شده را تنظیم نمی‌کند و به کار نمی‌برد.

resource.kubernetes.io/admin-access {resource-kubernetes-io-admin-access}

نوع: برچسب

مثال: resource.kubernetes.io/admin-access: "true"

استفاده‌شده روی: Namespace

از این برچسب برای اعطای دسترسی مدیریتی به برخی از نوع‌های API گروه resource.k8s.io در یک فضای نام استفاده می‌شود. وقتی این برچسب با مقدار "true" (با حساسیت به بزرگی و کوچکی حروف) روی یک فضای نام تنظیم شود، می‌توان از adminAccess: true در همهٔ نوع‌های API فضای‌نام‌دار resource.k8s.io استفاده کرد. در حال حاضر، این مجوز بر آبجکت‌های ResourceClaim و ResourceClaimTemplate اعمال می‌شود.

برای اطلاعات بیشتر، دسترسی مدیریتی در تخصیص پویای منابع را ببینید.
