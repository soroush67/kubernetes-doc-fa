مروری بر API

این بخش اطلاعات مرجع API کوبرنتیز را ارائه می‌کند.

رابط REST API بنیان اصلی کوبرنتیز است. همهٔ عملیات، ارتباط میان مؤلفه‌ها و فرمان‌های کاربران خارجی، فراخوانی‌های REST API هستند که API Server آن‌ها را پردازش می‌کند. به همین دلیل، هر چیزی در پلتفرم کوبرنتیز یک آبجکت API به شمار می‌رود و مدخل متناظری در API دارد.

مرجع API کوبرنتیز فهرست API مربوط به نسخهٔ v1.37 کوبرنتیز را ارائه می‌کند.

برای آشنایی با مفاهیم کلی، API کوبرنتیز را بخوانید. در کنترل دسترسی به API کوبرنتیز توضیح داده شده است که کلاینت‌ها چگونه می‌توانند خود را به سرور API کوبرنتیز احراز هویت کنند و درخواست‌هایشان چگونه مجوزدهی می‌شود.

نسخه‌بندی API

طرح‌واره‌های سریال‌سازی JSON و Protobuf برای تغییر طرح‌واره از دستورالعمل‌های یکسانی پیروی می‌کنند. توضیحات زیر هر دو قالب را در بر می‌گیرد.

نسخه‌بندی API و نسخه‌بندی نرم‌افزار به‌طور غیرمستقیم با یکدیگر مرتبط‌اند. رابطهٔ میان این دو در پیشنهاد نسخه‌بندی API و انتشار شرح داده شده است.

نسخه‌های مختلف API سطوح متفاوتی از پایداری و پشتیبانی را نشان می‌دهند. اطلاعات بیشتر دربارهٔ معیارهای هر سطح را می‌توانید در مستندات تغییرات API بیابید.

خلاصهٔ هر سطح در ادامه آمده است:

  • آلفا:

    • نام این نسخه‌ها شامل alpha است (برای مثال، v1alpha1).
    • نسخه‌های آلفای توکار API به‌طور پیش‌فرض غیرفعال هستند و برای استفاده از آن‌ها باید صراحتاً در پیکربندی kube-apiserver فعال شوند.
    • نرم‌افزار ممکن است اشکال‌هایی داشته باشد. فعال‌کردن یک قابلیت ممکن است این اشکال‌ها را آشکار کند.
    • پشتیبانی از API آلفا ممکن است در هر زمان و بدون اطلاع قبلی متوقف شود.
    • این API ممکن است در انتشارهای بعدی نرم‌افزار، بدون اطلاع قبلی و به شکلی ناسازگار تغییر کند.
    • به دلیل خطر بیشتر بروز اشکال و نبود پشتیبانی بلندمدت، توصیه می‌شود این نرم‌افزار فقط در کلاسترهای آزمایشی کوتاه‌عمر استفاده شود.

  • بتا:

    • نام این نسخه‌ها شامل beta است (برای مثال، v2beta3).

    • نسخه‌های بتای توکار API به‌طور پیش‌فرض غیرفعال هستند و برای استفاده از آن‌ها باید صراحتاً در پیکربندی kube-apiserver فعال شوند (به‌جز نسخه‌های بتای APIهایی که پیش از کوبرنتیز 1.22 معرفی شده‌اند و به‌طور پیش‌فرض فعال بوده‌اند).

    • حداکثر طول عمر نسخه‌های بتای توکار API از زمان معرفی تا منسوخ‌شدن، ۹ ماه یا ۳ انتشار فرعی (هر کدام طولانی‌تر باشد) است؛ از زمان منسوخ‌شدن تا حذف نیز همین سقف ۹ ماه یا ۳ انتشار فرعی (هر کدام طولانی‌تر باشد) برقرار است.

    • این نرم‌افزار به‌خوبی آزمایش شده است و فعال‌کردن قابلیت‌ها ایمن به شمار می‌رود.

    • پشتیبانی از قابلیت‌ها متوقف نخواهد شد، اما جزئیات آن‌ها ممکن است تغییر کند.

    • طرح‌واره و/یا معناشناسی آبجکت‌ها ممکن است در نسخهٔ بتا یا پایدار بعدی API به شکلی ناسازگار تغییر کند. در چنین مواردی، دستورالعمل‌های مهاجرت ارائه می‌شود. سازگاری با نسخهٔ بتا یا پایدار بعدی API ممکن است به ویرایش یا ایجاد دوبارهٔ آبجکت‌های API نیاز داشته باشد و کار ساده‌ای نباشد. این مهاجرت ممکن است برای برنامه‌هایی که به آن قابلیت وابسته‌اند، به توقف موقت سرویس نیاز داشته باشد.

    • استفاده از این نرم‌افزار در محیط‌های عملیاتی توصیه نمی‌شود، زیرا انتشارهای بعدی ممکن است تغییرات ناسازگاری به همراه داشته باشند. برای گذار به نسخه‌های بتا یا پایدار بعدی API، پس از آنکه نسخهٔ بتای API منسوخ شد و دیگر ارائه نمی‌شود، باید از نسخه‌های بتای API استفاده کرد.

توجه:

لطفاً قابلیت‌های بتا را امتحان کنید و بازخورد خود را ارائه دهید. پس از خروج قابلیت‌ها از مرحلهٔ بتا، شاید اعمال تغییرات بیشتر عملی نباشد.

  • پایدار:
    • نام نسخه به شکل vX است که در آن X یک عدد صحیح است.
    • نسخه‌های پایدار API در تمام انتشارهای آینده در یک نسخهٔ اصلی کوبرنتیز در دسترس می‌مانند و در حال حاضر برنامه‌ای برای بازنگری نسخهٔ اصلی کوبرنتیز به‌گونه‌ای که APIهای پایدار حذف شوند، وجود ندارد.

گروه‌های API

گروه‌های API گسترش API کوبرنتیز را آسان‌تر می‌کنند. گروه API در مسیر REST و در فیلد apiVersion یک آبجکت سریال‌شده مشخص می‌شود.

کوبرنتیز چندین گروه API دارد:

  • گروه core (که legacy نیز نامیده می‌شود) در مسیر REST با آدرس /api/v1 قرار دارد. این گروه به‌عنوان بخشی از فیلد apiVersion مشخص نمی‌شود؛ برای مثال، apiVersion: v1.
  • گروه‌های نام‌دار در مسیر REST با الگوی /apis/$GROUP_NAME/$VERSION قرار دارند و از apiVersion: $GROUP_NAME/$VERSION استفاده می‌کنند (برای مثال، apiVersion: batch/v1). فهرست کامل گروه‌های API پشتیبانی‌شده را می‌توانید در مرجع API کوبرنتیز بیابید.

فعال یا غیرفعال‌کردن گروه‌های API {#enabling-or-disabling}

برخی منابع و گروه‌های API به‌طور پیش‌فرض فعال هستند. می‌توانید با تنظیم --runtime-config روی سرور API، آن‌ها را فعال یا غیرفعال کنید. فلگ --runtime-config زوج‌های <key>[=<value>] جداشده با ویرگول را می‌پذیرد که پیکربندی زمان اجرای سرور API را توصیف می‌کنند. اگر بخش =<value> حذف شود، مانند آن است که =true مشخص شده باشد. برای مثال:

  • برای غیرفعال‌کردن batch/v1، مقدار --runtime-config=batch/v1=false را تنظیم کنید
  • برای فعال‌کردن batch/v2alpha1، مقدار --runtime-config=batch/v2alpha1 را تنظیم کنید
  • برای فعال‌کردن نسخه‌ای مشخص از یک API، مانند storage.k8s.io/v1beta1/csistoragecapacities، مقدار --runtime-config=storage.k8s.io/v1beta1/csistoragecapacities را تنظیم کنید
توجه:

هنگام فعال یا غیرفعال‌کردن گروه‌ها یا منابع، باید سرور API و controller manager را دوباره راه‌اندازی کنید تا تغییرات --runtime-config اعمال شوند.

ماندگاری داده‌ها

کوبرنتیز وضعیت سریال‌شدهٔ خود را در قالب منابع API در etcd می‌نویسد و به این ترتیب ذخیره می‌کند.

گام‌های بعدی

  • دربارهٔ قراردادهای API بیشتر بیاموزید
  • مستندات طراحی aggregator را بخوانید
  • با اعتبارسنجی اعلانی API آشنا شوید.
