زبان Common Expression Language در کوبرنتیز

در API کوبرنتیز از زبان Common Expression Language (CEL) برای تعریف قواعد اعتبارسنجی، قواعد سیاست‌ها و سایر محدودیت‌ها یا شرط‌ها استفاده می‌شود.

عبارت‌های CEL مستقیماً در سرور API ارزیابی می‌شوند. به همین دلیل، CEL در بسیاری از کاربردهای توسعه‌پذیری، جایگزین مناسبی برای سازوکارهای خارج از فرایند مانند وب‌هوک‌ها (webhooks) است. عبارت‌های CEL شما تا زمانی که مؤلفه سرور API در control plane در دسترس باشد، همچنان اجرا می‌شوند.

مروری بر زبان

زبان CEL نحو ساده‌ای دارد که به عبارت‌ها در زبان‌های C، C++، Java، JavaScript و Go شباهت دارد.

زبان CEL برای جاسازی در برنامه‌ها طراحی شده است. هر «برنامه» CEL یک عبارت واحد است که به یک مقدار واحد ارزیابی می‌شود. عبارت‌های CEL معمولاً کوتاه و «تک‌خطی» هستند و به‌خوبی در فیلدهای رشته‌ای منابع API کوبرنتیز جای می‌گیرند.

ورودی‌های یک برنامه CEL «متغیرها» هستند. هر فیلد API کوبرنتیز که حاوی CEL است، در مستندات API مشخص می‌کند که چه متغیرهایی برای استفاده در آن فیلد در دسترس‌اند. برای مثال، در فیلد x-kubernetes-validations[i].rules از CustomResourceDefinitionها، متغیرهای self و oldSelf در دسترس هستند و به وضعیت قبلی و فعلی داده‌های منبع سفارشی اشاره می‌کنند که عبارت CEL باید آن‌ها را اعتبارسنجی کند. سایر فیلدهای API کوبرنتیز ممکن است متغیرهای متفاوتی تعریف کنند. برای اینکه بدانید کدام متغیرها برای یک فیلد در دسترس‌اند، به مستندات API آن فیلد مراجعه کنید.

توابع، قابلیت‌ها و تنظیمات زبانی CEL از بازگردانی (rollback) control plane کوبرنتیز پشتیبانی می‌کنند. برای مثال، مقادیر اختیاری CEL (CEL Optional Values) در کوبرنتیز 1.29 معرفی شد؛ بنابراین فقط سرورهای API با این نسخه یا نسخه‌های جدیدتر، درخواست‌های نوشتنِ عبارت‌های CEL را که از مقادیر اختیاری CEL استفاده می‌کنند می‌پذیرند. با این حال، اگر کلاستر به کوبرنتیز 1.28 بازگردانده شود، عبارت‌های CEL که از «مقادیر اختیاری CEL» استفاده می‌کنند و از قبل در منابع API ذخیره شده‌اند، همچنان به‌درستی ارزیابی می‌شوند.

کتابخانه‌های CEL کوبرنتیز

کوبرنتیز علاوه بر کتابخانه‌های جامعه CEL، کتابخانه‌های CEL مخصوص به خود را نیز دارد که در همه جاهایی که CEL در کوبرنتیز استفاده می‌شود، در دسترس هستند.

کتابخانه لیست کوبرنتیز

کتابخانه لیست شامل توابع indexOf و lastIndexOf است که مشابه توابع رشته‌ای هم‌نام خود عمل می‌کنند. این توابع اولین یا آخرین اندیس موقعیتیِ عنصر داده‌شده را در لیست برمی‌گردانند.

کتابخانه لیست همچنین توابع min، max و sum را در بر دارد. تابع sum روی همه انواع عددی و همچنین نوع duration پشتیبانی می‌شود. توابع min و max روی همه انواع قابل مقایسه پشتیبانی می‌شوند.

تابع isSorted نیز به‌عنوان یک تابع کمکی ارائه شده است و روی همه انواع قابل مقایسه پشتیبانی می‌شود.

نمونه‌ها:

نمونه‌هایی از عبارت‌های CEL که از توابع کتابخانه لیست استفاده می‌کنند
عبارت CEL هدف
names.isSorted() بررسی می‌کند که لیستی از نام‌ها به ترتیب الفبایی نگه داشته شده باشد
items.map(x, x.weight).sum() == 1.0 بررسی می‌کند که مجموع «وزن‌های» لیستی از آبجکت‌ها برابر 1.0 باشد
lowPriorities.map(x, x.priority).max() < highPriorities.map(x, x.priority).min() بررسی می‌کند که دو مجموعه از اولویت‌ها با هم هم‌پوشانی نداشته باشند
names.indexOf('should-be-first') == 1 الزام می‌کند که اولین نام در یک لیست مقدار مشخصی باشد

برای اطلاعات بیشتر، به godoc کتابخانه لیست کوبرنتیز مراجعه کنید.

کتابخانه URL کوبرنتیز

برای اینکه پردازش URLها آسان‌تر و امن‌تر شود، توابع زیر اضافه شده‌اند:

  • تابع isURL(string) بررسی می‌کند که آیا یک رشته طبق بسته net/url در Go یک URL معتبر است یا نه. این رشته باید یک URL مطلق باشد.
  • تابع url(string) URL یک رشته را به URL تبدیل می‌کند و اگر رشته یک URL معتبر نباشد، خطا برمی‌گرداند.

پس از تجزیه با تابع url، آبجکت URL حاصل دسترسی‌دهنده‌های getScheme، getHost، getHostname، getPort، getEscapedPath و getQuery را در اختیار می‌گذارد.

کتابخانه آدرس IP کوبرنتیز

برای اینکه پردازش آدرس‌های IP آسان‌تر و امن‌تر شود، توابع زیر اضافه شده‌اند:

  • تابع isIP(string) بررسی می‌کند که آیا یک رشته آدرس IP معتبری است یا نه.
  • تابع ip(string) IP یک رشته را به آبجکت آدرس IP تبدیل می‌کند و اگر رشته آدرس IP معتبری نباشد، خطا برمی‌گرداند.

در هر دو تابع، آدرس IP باید یک آدرس IPv4 یا IPv6 باشد. آدرس‌های IPv6 نگاشت‌شده از IPv4 (مانند ::ffff:1.2.3.4) مجاز نیستند. آدرس‌های IP دارای zone (مانند fe80::1%eth0) مجاز نیستند. صفرهای ابتدایی در اکتت‌های آدرس IPv4 مجاز نیستند.

پس از تجزیه با تابع ip، آبجکت IP حاصل مجموعه توابع عضو زیر را در اختیار می‌گذارد:

توابع عضو در دسترس برای آبجکت آدرس IP
تابع عضو مقدار بازگشتی CEL توضیحات
isCanonical() bool اگر آدرس IP به شکل استاندارد (canonical) خود باشد، true برمی‌گرداند. هر آدرس IP دقیقاً یک شکل استاندارد دارد؛ بنابراین فیلدهایی که آدرس‌های IP را به شکل استاندارد نگه می‌دارند، هنگام بررسی برابری یا یکتایی می‌توانند صرفاً مانند رشته در نظر گرفته شوند.
family() int خانواده آدرس IP را برمی‌گرداند: 4 برای IPv4 و 6 برای IPv6.
isUnspecified() bool اگر آدرس IP، آدرس نامشخص (unspecified) باشد، true برمی‌گرداند. این آدرس یا آدرس IPv4 برابر "0.0.0.0" است یا آدرس IPv6 برابر "::".
isLoopback() bool اگر آدرس IP، آدرس loopback باشد، true برمی‌گرداند. این آدرس یا یک آدرس IPv4 با مقدار 127.x.x.x است یا یک آدرس IPv6 با مقدار ::1.
isLinkLocalMulticast() bool اگر آدرس IP یک آدرس multicast از نوع link-local باشد، true برمی‌گرداند. این آدرس یا یک آدرس IPv4 با مقدار 224.0.0.x است یا یک آدرس IPv6 در شبکه ff00::/8.
isLinkLocalUnicast() bool اگر آدرس IP یک آدرس unicast از نوع link-local باشد، true برمی‌گرداند. این آدرس یا یک آدرس IPv4 با مقدار 169.254.x.x است یا یک آدرس IPv6 در شبکه fe80::/10.
isGlobalUnicast() bool اگر آدرس IP یک آدرس unicast سراسری (global) باشد، true برمی‌گرداند. این آدرس یا یک آدرس IPv4 است که صفر یا 255.255.255.255 نباشد، یا یک آدرس IPv6 است که آدرس unicast از نوع link-local، loopback یا multicast نباشد.

کتابخانهٔ CIDR کوبرنتیز

کتابخانهٔ CIDR یک افزونهٔ کتابخانهٔ توابع CEL است که توابعی برای تجزیهٔ نمادگذاری CIDR فراهم می‌کند.

cidr

این تابع رشته‌ای را که با نمادگذاری CIDR نوشته شده است به نمایشی از یک نشانی شبکه تبدیل می‌کند. اگر رشته نمادگذاری CIDR معتبری نباشد، خطا رخ می‌دهد. مقدار CIDR باید نشانی یک زیرشبکهٔ IPv4 یا IPv6 همراه با ماسک باشد. صفرهای ابتدایی در هشتایی‌های (octet) نشانی IPv4 مجاز نیستند. نشانی‌های IPv6 نگاشته‌شده به IPv4 (مانند ::ffff:1.2.3.4/24) نیز مجاز نیستند.

cidr(<string>) <CIDR>

نمونه‌ها:

نمونه‌هایی از عبارت‌های CEL که از تابع cidr استفاده می‌کنند
عبارت CEL هدف
cidr('192.168.0.0/16') یک نشانی IPv4 همراه با ماسک CIDR برمی‌گرداند.
cidr('::1/128') یک نشانی IPv6 همراه با ماسک CIDR برمی‌گرداند.
cidr('192.168.0.0/33') خطا رخ می‌دهد، زیرا طول پیشوند از اندازهٔ نشانی IPv4 بیشتر است.
cidr('::1/129') خطا رخ می‌دهد، زیرا طول پیشوند از اندازهٔ نشانی IPv6 بیشتر است.
cidr('192.168.0.1/16') خطا رخ می‌دهد، زیرا پس از پیشوند بیت‌های غیرصفر وجود دارد.

isCIDR

اگر رشته نمایش معتبری از یک زیرشبکه همراه با ماسک در نمادگذاری CIDR باشد، این تابع مقدار true برمی‌گرداند. مقدار CIDR باید نشانی یک زیرشبکهٔ IPv4 یا IPv6 همراه با ماسک باشد. صفرهای ابتدایی در هشتایی‌های نشانی IPv4 مجاز نیستند. نشانی‌های IPv6 نگاشته‌شده به IPv4 (مانند ::ffff:1.2.3.4/24) نیز مجاز نیستند.

کتابخانهٔ مجوزدهندهٔ کوبرنتیز

در عبارت‌های CEL در API که متغیری از نوع Authorizer در دسترس است، می‌توان از مجوزدهنده (authorizer) برای انجام بررسی‌های مجوز برای هویت درخواست‌دهنده (principal)، یعنی کاربر احراز هویت‌شدهٔ درخواست، استفاده کرد.

بررسی‌های مجوز برای منابع API به این صورت انجام می‌شوند:

  1. گروه و منبعی را که باید بررسی شود مشخص کنید: Authorizer.group(string).resource(string) ResourceCheck
  2. در صورت نیاز، هر ترکیبی از توابع سازندهٔ زیر را فراخوانی کنید تا دامنهٔ بررسی مجوز محدودتر شود. توجه کنید که این توابع نوع گیرنده را برمی‌گردانند و می‌توان آن‌ها را به‌صورت زنجیره‌ای فراخوانی کرد:
    • ResourceCheck.subresource(string) ResourceCheck
    • ResourceCheck.namespace(string) ResourceCheck
    • ResourceCheck.name(string) ResourceCheck
  3. برای انجام بررسی مجوز، ResourceCheck.check(verb string) Decision را فراخوانی کنید.
  4. برای بررسی نتیجهٔ بررسی مجوز، allowed() bool یا reason() string را فراخوانی کنید.

بررسی‌های مجوز برای موارد غیرمنبعی به این صورت انجام می‌شوند:

  1. فقط یک مسیر را مشخص کنید: Authorizer.path(string) PathCheck
  2. برای انجام بررسی مجوز، PathCheck.check(httpVerb string) Decision را فراخوانی کنید.
  3. برای بررسی نتیجهٔ بررسی مجوز، allowed() bool یا reason() string را فراخوانی کنید.

برای انجام بررسی مجوز برای یک حساب سرویس (service account):

  • Authorizer.serviceAccount(namespace string, name string) Authorizer

کتابخانهٔ قالب کوبرنتیز

کتابخانهٔ format توابعی برای اعتبارسنجی قالب‌های رایج رشته در کوبرنتیز فراهم می‌کند. این کتابخانه در messageExpression قواعد اعتبارسنجی کاربرد دارد و با آن می‌توان پیام‌های خطای دقیق‌تری ارائه کرد.

این کتابخانه برای هر قالب نام‌دار یک تابع format() و همچنین یک تابع عمومی format.named() فراهم می‌کند.

  • تابع format.named(string) → ?Format: اگر قالبی با نام داده‌شده وجود داشته باشد، آبجکت Format آن را برمی‌گرداند. در غیر این صورت، optional.none را برمی‌گرداند.
  • تابع format.<formatName>() -> Format: توابع کمکی برای همهٔ قالب‌های نام‌دار نیز در دسترس هستند. برای مثال، format.dns1123Label() آبجکت Format مربوط به برچسب‌های DNS-1123 را برمی‌گرداند.
  • تابع <Format>.validate(string) -> list<string>?: رشتهٔ داده‌شده را با قالب مقایسه و اعتبارسنجی می‌کند. اگر رشته معتبر باشد، optional.none را برمی‌گرداند؛ در غیر این صورت، یک مقدار اختیاری (optional) شامل فهرستی از رشته‌های خطای اعتبارسنجی برمی‌گرداند.

کتابخانهٔ semver کوبرنتیز

کوبرنتیز از نسخهٔ v1.34 امکان تجزیه و مقایسهٔ رشته‌هایی را فراهم می‌کند که از مشخصهٔ Semantic Versioning 2.0.0 پیروی می‌کنند. برای آشنایی با الگوهای پذیرفته‌شده، به مستندات semver.org مراجعه کنید.

  • تابع isSemver(string) بررسی می‌کند که آیا یک رشته، نسخهٔ معنایی معتبری است یا نه.
  • تابع semver(string) یک رشته را به آبجکت Semver تبدیل می‌کند یا در غیر این صورت به خطا می‌انجامد.

می‌توان آرگومان بولی اختیاری normalize را به isSemver و semver داد. اگر مقدار آن true باشد، فرایند نرمال‌سازی هر پیشوند «v» را حذف می‌کند، برای نسخه‌هایی که فقط مؤلفهٔ major یا major.minor دارند، شماره‌های minor و patch را برابر 0 قرار می‌دهد و همهٔ صفرهای ابتدایی را حذف می‌کند.

پس از تجزیهٔ رشته با تابع semver، آبجکت Semver حاصل، کتابخانهٔ توابع عضو زیر را در اختیار می‌گذارد:

توابع عضو در دسترس برای یک آبجکت Semver
تابع عضو مقدار بازگشتی CEL توضیح
major() int شمارهٔ نسخهٔ اصلی (major) را برمی‌گرداند.
minor() int شمارهٔ نسخهٔ فرعی (minor) را برمی‌گرداند.
patch() int شمارهٔ وصله (patch) را برمی‌گرداند.
isLessThan(<Semver>) bool اگر و تنها اگر گیرنده از عملوند کوچک‌تر باشد، true برمی‌گرداند.
isGreaterThan(<Semver>) bool اگر و تنها اگر گیرنده از عملوند بزرگ‌تر باشد، true برمی‌گرداند.
compareTo(<Semver>) int گیرنده را با عملوند مقایسه می‌کند و اگر برابر باشند 0، اگر گیرنده بزرگ‌تر باشد 1 و اگر گیرنده از عملوند کوچک‌تر باشد -1 برمی‌گرداند.

بررسی نوع

زبان CEL یک زبان با نوع‌دهی تدریجی است.

برخی از فیلدهای API کوبرنتیز حاوی عبارت‌های CEL هستند که نوع آن‌ها به‌طور کامل بررسی می‌شود. برای مثال، قواعد اعتبارسنجی CustomResourceDefinitions به‌طور کامل از نظر نوع بررسی می‌شوند.

برخی دیگر از فیلدهای API کوبرنتیز حاوی عبارت‌های CEL با بررسی نوع جزئی هستند. عبارتی با بررسی نوع جزئی، عبارتی است که برخی از متغیرهای آن نوع ایستا و برخی دیگر نوع پویا دارند. برای مثال، در عبارت‌های CEL مربوط به ValidatingAdmissionPolicies متغیر request نوع‌دار است، اما متغیر object نوع پویا دارد. در نتیجه، عبارتی که شامل request.namex باشد در بررسی نوع رد می‌شود، زیرا فیلد namex تعریف نشده است. اما object.namex حتی وقتی فیلد namex برای انواع منابعی که object به آن‌ها اشاره می‌کند تعریف نشده باشد، از بررسی نوع عبور می‌کند، زیرا object نوع پویا دارد.

با ماکروی has() در عبارت‌های CEL می‌توان پیش از تلاش برای دسترسی به مقدار یک فیلد از متغیری با نوع پویا، وجود آن فیلد را بررسی کرد. برای مثال:

has(object.namex) ? object.namex == 'special' : request.name == 'special'

از has() برای بررسی وجود فیلد استفاده کنید، اما برای بررسی اینکه یک map حاوی کلید معینی است یا نه، از آن استفاده نکنید. برای مثال، عبارت has(object.metadata.labels['example.com/environment']) را ننویسید. برای بررسی کلیدهای map، به جای آن از عملگر in استفاده کنید. برای مثال:

has(object.metadata.labels) && 'example.com/environment' in object.metadata.labels

این عبارت پیش از بررسی اینکه map حاوی کلید example.com/environment است یا نه، وجود metadata.labels را بررسی می‌کند.

مقایسهٔ برابری برای آرایه‌هایی که x-kubernetes-list-type آن‌ها set یا map است، ترتیب عناصر را نادیده می‌گیرد. برای مثال، اگر آرایه‌ها نمایانگر مقادیر set کوبرنتیز باشند، [1, 2] == [2, 1] برقرار است.

الحاق آرایه‌هایی که x-kubernetes-list-type دارند، از معناشناسی همان نوع لیست پیروی می‌کند:

set
عملگر X + Y اجتماعی را انجام می‌دهد که در آن موقعیت همهٔ عناصر X در آرایه حفظ می‌شود و عناصر غیرمشترک Y با حفظ ترتیب جزئی‌شان به انتها افزوده می‌شوند.
map
عملگر X + Y ادغامی را انجام می‌دهد که در آن موقعیت همهٔ کلیدهای X در آرایه حفظ می‌شود، اما هنگامی که مجموعه‌کلیدهای X و Y اشتراک داشته باشند، مقادیر با مقادیر Y بازنویسی می‌شوند. عناصری از Y که کلیدهای غیرمشترک دارند، با حفظ ترتیب جزئی‌شان به انتها افزوده می‌شوند.

محدودیت‌های منابع

زبان CEL تورینگ‌کامل نیست و سازوکارهای ایمنی گوناگونی برای محیط عملیاتی فراهم می‌کند تا زمان اجرا را محدود کند. قابلیت‌های محدودیت منابع در CEL دربارهٔ پیچیدگی عبارت‌ها به توسعه‌دهندگان بازخورد می‌دهند و به محافظت از سرور API در برابر مصرف بیش از حد منابع هنگام ارزیابی کمک می‌کنند. از قابلیت‌های محدودیت منابع CEL برای جلوگیری از مصرف بیش از حد منابع سرور API در فرایند ارزیابی CEL استفاده می‌شود.

یکی از عناصر کلیدی قابلیت‌های محدودیت منابع، واحد هزینه است که CEL آن را برای ردیابی مصرف CPU تعریف می‌کند. واحدهای هزینه مستقل از بار سیستم و سخت‌افزار هستند. این واحدها قطعی (deterministic) نیز هستند؛ یعنی برای هر عبارت CEL و دادهٔ ورودی معین، ارزیابی آن عبارت در مفسر CEL همواره به هزینهٔ یکسانی می‌انجامد.

بسیاری از عملیات اصلی CEL هزینهٔ ثابتی دارند. ساده‌ترین عملیات، مانند مقایسه‌ها (برای مثال <)، هزینه‌ای برابر 1 دارند. برخی از عملیات هزینهٔ ثابت بالاتری دارند؛ برای مثال، اعلان لیترال لیست هزینهٔ پایهٔ ثابتی برابر 40 واحد هزینه دارد.

هزینهٔ فراخوانی توابعی که در کد بومی پیاده‌سازی شده‌اند، بر اساس پیچیدگی زمانی عملیات تخمین زده می‌شود. برای مثال، هزینهٔ عملیاتی که از عبارات منظم استفاده می‌کنند، مانند match و find، با مقدار تقریبی length(regexString)*length(inputString) تخمین زده می‌شود. این هزینهٔ تقریبی بازتاب‌دهندهٔ پیچیدگی زمانی بدترین حالت در پیاده‌سازی RE2 زبان Go است.

بودجهٔ هزینهٔ زمان اجرا

همهٔ عبارت‌های CEL که کوبرنتیز ارزیابی می‌کند، به یک بودجهٔ هزینهٔ زمان اجرا محدود هستند. بودجهٔ هزینهٔ زمان اجرا تخمینی از مصرف واقعی CPU است که با افزایش یک شمارندهٔ واحد هزینه در حین تفسیر عبارت CEL محاسبه می‌شود. اگر مفسر CEL دستورالعمل‌های بیش از حدی اجرا کند، از بودجهٔ هزینهٔ زمان اجرا فراتر می‌رود، اجرای عبارت‌ها متوقف می‌شود و خطایی رخ می‌دهد.

برخی از منابع کوبرنتیز یک بودجهٔ هزینهٔ زمان اجرای اضافی تعریف می‌کنند که اجرای چند عبارت را محدود می‌کند. اگر مجموع هزینهٔ عبارت‌ها از این بودجه فراتر رود، اجرای عبارت‌ها متوقف می‌شود و خطایی رخ می‌دهد. برای مثال، اعتبارسنجی یک منبع سفارشی، بودجهٔ هزینهٔ زمان اجرای به‌ازای هر اعتبارسنجی برای همهٔ قواعد اعتبارسنجی دارد که برای اعتبارسنجی آن منبع سفارشی ارزیابی می‌شوند.

محدودیت‌های هزینهٔ تخمینی

برای برخی از منابع کوبرنتیز، سرور API ممکن است همچنین بررسی کند که آیا زمان اجرای تخمینی عبارت‌های CEL در بدترین حالت، اجرای آن‌ها را بیش از حد پرهزینه می‌کند یا نه. در این صورت، سرور API با رد کردن عملیات ایجاد یا به‌روزرسانی‌ای که آن عبارت CEL را در منابع API قرار می‌دهند، از نوشته شدن آن عبارت در منابع API جلوگیری می‌کند. این قابلیت تضمین قوی‌تری فراهم می‌کند که عبارت‌های CEL نوشته‌شده در منبع API، در زمان اجرا بدون فراتر رفتن از بودجهٔ هزینهٔ زمان اجرا ارزیابی شوند.
